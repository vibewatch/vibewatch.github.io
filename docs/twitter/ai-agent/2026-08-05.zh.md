# Twitter AI Agent - 2026-08-05

## 1. 人们在讨论什么

### 1.1 技能已成为可安装的运行层，而不只是可复用的提示词（🡕）

最强烈的产品化信号，是讨论重点从技能设计转向技能分发。保留的四条内容都聚焦于文档、安装器、官方插件渠道、精选打包，以及位于单个技能之上的运行层。相比 8 月 4 日将技能视为可提供证据的工件，8 月 5 日的讨论更进一步转向：人们在日常代理工作中如何发现、安装、路由和维护这些技能。

[@mattpocockuk](https://x.com/mattpocockuk) [发布](https://x.com/mattpocockuk/status/2084985277102031137)（1,219 个赞，49 条回复，38,104 次浏览，747 次收藏）发布了 `mattpocock/skills` v1.2，提供完整文档、Claude Code 插件市场插件、通过 `agents/openai.yaml` 提供的 Codex 支持，以及 `/wizard`、`/to-questionnaire` 和 `/wait-what` 等新的工作流技能。附带的安装器页面信息量很大，因为它把两条公开分发路径并列展示出来：可编辑的 `npx skills@latest add mattpocock/skills` 安装方式，以及由 Claude Code 托管的插件；同时还展示了该项目 1,350 万次安装量和跨代理定位。

![AIHero 安装器页面，展示可编辑安装、Claude Code marketplace 安装，以及 1350 万次 skills.sh 安装](https://pbs.twimg.com/media/HO9Yh5MWUAE7p-b.jpg)

公开的 [README](https://github.com/mattpocock/skills) 进一步强化了这种打包策略：一种路径会把技能复制到仓库中，供本地编辑；另一种插件路径则让技能保持托管且只读。一条回复补上了当天最直接的痛点信号：这套技能之所以有用，恰恰因为它覆盖面广；但也正因如此，如果没有一个能为具体任务推荐合适技能的助手，就会让人感到不知所措。

[@rlaope](https://x.com/rlaope) [指出](https://x.com/rlaope/status/2084883447873753155)（45 个赞，1 条回复，3,317 次浏览，60 次收藏）表示，Hermes 用户“实际上只需要一个插件”，随后将 [oh-my-hermes](https://github.com/rlaope/oh-my-hermes) 定位为位于 Hermes 原生技能之上的运行层。其官网称，该工具在不替代 Hermes 的前提下，补上了规划、研究、编码交接、运维和项目记忆；附图之所以重要，是因为它们展示了同一套工作流如何贯穿 Hermes Desktop、CLI 和消息端，并展示了关于记忆分层、范围化回执、经审核的技能草稿以及调度策略的实时问题积压，而不是一张静态的发布海报。

[@alex_prompter](https://x.com/alex_prompter) [提出](https://x.com/alex_prompter/status/2085054816888484123)（8 个赞，2 条回复，3,443 次浏览）展示了一个简洁的 `SKILL.md` 结构，明确列出了触发条件、输入/输出以及“NOT FOR”边界。这虽然只是个较小信号，但符合相同趋势：人们正努力让技能足够可审计、可组合，避免大型技能库最终陷入路由歧义。

**讨论洞察：** 真正有价值的分歧，不在于技能是否有效，而在于如何让它们持续可用。Matt Pocock 的回复暴露了发现过载问题，而 oh-my-hermes 则明确把自己定位为解决插件疲劳和工作流误路由的方案。

**与前一天的比较：** 8 月 4 日将技能框定为可训练、且有证据支撑的对象。到了 8 月 5 日，讨论重心转向了打包、安装入口，以及让不断扩大的技能目录保持可用所需的运行层。

### 1.2 Harness 工程成为公开基准与逆向工程竞赛（🡕）

保留的五条内容都把 harness 当作真正的产品表层：需要被记录、逆向、基准测试，并围绕它共同训练。这个主题把 8 月 3 日的测量语言和 8 月 4 日的生命周期讨论，扩展成一场更公开的竞争：谁最能揭示、解释并改进模型周围的系统。

[@morganlinton](https://x.com/morganlinton) [收藏](https://x.com/morganlinton/status/2084719560343846954)（505 个赞，3 条回复，129,314 次浏览，787 次收藏）称 Pi 的 harness 工程指南是他读过的“关于高效 harness 工程最棒的内容”，这本身就说明这个主题已经值得被当作一门独立技艺来研究。更具体地说，[@swyx](https://x.com/swyx) [指出](https://x.com/swyx/status/2085073764551962960)（82 个赞，10 条回复，8,623 次浏览，83 次收藏）把读者引向 Latent.Space 对 [ChatGPT Work](https://latent.space/p/unpacking-chatgpt-work) 的公开复原。该复原描述了一款基于 Codex harness、运行在云端 microVM 中的知识工作产品，支持浏览器使用、插件，以及由产品层管理的跨任务服务，如 Library、Projects、Personal Context 和 Memory。附带的上下文架构图很有信息量，因为它明确展示了一个不那么显然的设计选择：任务本地工作目录位于独立的 OpenAI 管理层之下，因此跨线程连续性并不只是“同一台电脑上的共享文件”。

![ChatGPT Work 上下文架构图，展示位于 OpenAI 管理层之下的任务本地工作目录，以及用于 library、projects、plugins、personal context 和 memory 的层级](https://pbs.twimg.com/media/HO-rZzmbwAAZDYo.jpg)

[@johannes_hage](https://x.com/johannes_hage) [介绍](https://x.com/johannes_hage/status/2085095925920440466)（152 个赞，5 条回复，8,107 次浏览，51 次收藏）介绍了 [Prime Agent](https://www.primeintellect.ai/blog/prime-agent)。其公开发布帖描述了持久化 IPython REPL、以编程方式调用子代理、代理间直接通信，以及对提示词、记忆、技能和子代理执行 CRUD 操作。架构图之所以重要，是因为它直接展示了其宣称的控制回路：任务 -> 模型 -> IPython kernel -> `rlm` / 子代理 -> 持续演化的 harness 状态。

![Prime Agent 架构图，展示模型、持久化 IPython 内核、子代理以及持续运行的 harness 状态](https://pbs.twimg.com/media/HO--hKWaIAAAiOj.jpg)

Prime Agent 的第二条推文来自 [@Dr_Singularity](https://x.com/Dr_Singularity) [强调](https://x.com/Dr_Singularity/status/2085098595372744945)（343 个赞，21 条回复，20,024 次浏览，86 次收藏），展现了这条叙事的基准测试一面。图表很有信息量，因为它显示 Prime Agent + Opus 5 在 ARC-AGI-3 上达到 95.5%，略高于 95.4% 的人类基线，并分别绘出了 Sol、Terra 和 GLM 5.2 的曲线。

![ARC-AGI-3 计算扩展图表，显示 Prime Agent 加上 Opus 5 达到 95.5%，而人类基线为 95.4%](https://pbs.twimg.com/media/HO_B80sXsAAWORZ.jpg)

[@ren_hongyu](https://x.com/ren_hongyu) [发布](https://x.com/ren_hongyu/status/2085084609315033586)（166 个赞，9 条回复，8,633 次浏览，8 次收藏）介绍了 Muse Spark 1.2 和 [Muse Code](https://research.meta.ai/blog/introducing-muse-code-and-muse-spark-1-2)。Meta 表示，后者是一款终端编码代理，具备持久化异步后台代理、可精确重放的事件日志，以及捆绑的 `/plan`、`/grill` 和 `/goal` 技能。基准测试图片将 Muse Code 与 Claude Code、Codex、Grok Build 等在 Terminal-Bench 2.1、DeepSWE 1.1、Meta Internal Coding Bench、GDPVal-AA V2 和 MCP Atlas 上进行了比较，但回复中也出现了有价值的质疑：一位读者表示，很难在公开网络上找到 Muse Code；另一位则质疑图表是否足够诚实。

**讨论洞察：** 最明显的可信度模式是，第三方解读正在成为产品表层的一部分。Latent.Space 帖子下的回复称，harness 拆解往往比官方文档更有用；而 Muse Code 帖子的回复则表明，缺乏透明公开入口的发布图表会立刻招致反弹。

**与前一天的比较：** 8 月 3 日把 harness 视为要做基准测试的对象。8 月 4 日则把它与轨迹、记忆和生命周期控制联系起来。到了 8 月 5 日，它已经成为一种独立的公开拆解与发布类别。

### 1.3 掌控构建完成后的表层，与构建代理本身同样重要（🡕）

第三组内容聚焦于核心代理构建完成之后的一切：谁可以使用它、它如何被发现、它携带哪些权限，以及它如何实现自身结算。四条保留内容从不同角度表达了同一个观点：如果访问、路由、分发和结算仍然靠临时拼凑，那么仅仅交付模型循环远远不够。

[@rileybrown](https://x.com/rileybrown) [表示](https://x.com/rileybrown/status/2085077630001287349)（71 个赞，8 条回复，7,636 次浏览，100 次收藏）称，Vercel 的内部代理 `V` 已经与近 1,000 名员工协同工作，随后围绕一个熟悉的分叉组织起公开讨论：是一个 GOD 代理，还是一组权限和计算机访问能力各不相同的小代理。最有用的回复分成两边：一种观点认为，权限边界最终会迫使团队走向多代理方案；另一种则警告说，单一内部代理可能看起来比实际更强，因为它只看得到“Vercel 式工作”。

[@Fetch_ai](https://x.com/Fetch_ai) [总结](https://x.com/Fetch_ai/status/2084919840108646834)（107 个赞，1 条回复，6,067 次浏览）把构建后的表层定义为部署、发现、编排、用户访问和支付，并将其栈映射到 uAgents、Agentverse、ASI:One 和 Fetch Business。与此同时，[@ama_protocol](https://x.com/ama_protocol) [定位为](https://x.com/ama_protocol/status/2084708895508021477)（54 个赞，49 条回复，611 次浏览）将 Amadeus 同时定位为目的地产品（`ama hub`）和供第三方应用嵌入的代理层（`AMA Embed`），并围绕真实资金操作提供私密但可证明的记录。

[@wardenprotocol](https://x.com/wardenprotocol) [推出](https://x.com/wardenprotocol/status/2085047751457305022)（47 个赞，14 条回复，7,177 次浏览）介绍了 [Halo](https://wardenprotocol.org/blog/halo-launch)：一个运行在 Base 上、处于公开 alpha 阶段的点对点 AI 推理市场。在这里，代理可以作为一等消费者，从 USDC 存款中支付费用，并使用本地 OpenAI 兼容端点，而不必携带服务商 API 密钥。该发布帖最清晰的主张并不是模型新颖性，而是分发与结算设计：以钱包作为凭证，由运营方提供供给，并在首次存款后通过 gas 赞助实现使用。

**讨论洞察：** 这些帖子并未在“是否会出现更多代理”上产生分歧；分歧在于瓶颈到底是权限、可移植性、发现，还是结算。但四者都默认，瓶颈不在核心提示词循环之内。

**与前一天的比较：** 8 月 4 日聚焦于钱包、托管和支出控制。到了 8 月 5 日，这一视角已经扩展为完整的端到端表层，涵盖内部触达、公开发现和机器付费使用。

## 2. 什么让人感到沮丧

### 技能丰富度带来了新的路由与发现问题

严重程度：高。[@mattpocockuk](https://x.com/mattpocockuk) [发布](https://x.com/mattpocockuk/status/2084985277102031137)（1,219 个赞，49 条回复，38,104 次浏览，747 次收藏）发布了一次覆盖面很广的技能更新，但最尖锐的回复称，技能范围已经“有点让人不知所措”，并明确要求提供一个 `skills-helper`，来为任务挑选合适技能。[@rlaope](https://x.com/rlaope) [回应](https://x.com/rlaope/status/2084883447873753155)（45 个赞，1 条回复，3,317 次浏览，60 次收藏）则把一个插件定位为削减“认知负担”的运行层；[@alex_prompter](https://x.com/alex_prompter) [回答](https://x.com/alex_prompter/status/2085054816888484123)（8 个赞，2 条回复，3,443 次浏览）则在 `SKILL.md` 中加入了明确的触发条件和“NOT FOR”边界。当前的应对方式是精选、更强的边界，以及位于原始技能文件夹之上的封装层。这个方向值得投入，因为这种摩擦恰恰出现在技能库变得足够有用、开始增长的时候。

### Harness 仍然足够不透明，以至于必须由第三方来解释

严重程度：高。[@morganlinton](https://x.com/morganlinton) [称之为](https://x.com/morganlinton/status/2084719560343846954)（505 个赞，3 条回复，129,314 次浏览，787 次收藏）称一份 harness 工程指南是他在这一主题上读过的最佳内容；[@swyx](https://x.com/swyx) [发送](https://x.com/swyx/status/2085073764551962960)（82 个赞，10 条回复，8,623 次浏览，83 次收藏）则把读者引向 [ChatGPT Work](https://latent.space/p/unpacking-chatgpt-work) 的外部复原，而不是官方产品说明。该帖下的回复称，harness 解读正变得比官方文档更有用；而针对 [@ren_hongyu](https://x.com/ren_hongyu) 的 [Muse Code 发布](https://x.com/ren_hongyu/status/2085084609315033586)（166 个赞，9 条回复，8,633 次浏览，8 次收藏）的回复，则抱怨这款产品很难在公开网络上找到，基准图表也不够透明。人们通过收藏拆解文章、比较图表和依赖外部解读来应对。这个方向值得投入，因为一个隐藏的 harness 很难获得信任、被比较或被复现。

### 企业部署最终仍绕不开权限、连续性和访问表层

严重程度：高。[@rileybrown](https://x.com/rileybrown) [表示](https://x.com/rileybrown/status/2085077630001287349)（71 个赞，8 条回复，7,636 次浏览，100 次收藏）称 Vercel 的内部代理已经服务近 1,000 人，但讨论立刻转向：是否根本不该只有一个代理，或者团队是否需要多个拥有不同权限和计算机访问能力的代理。公开的 [ChatGPT Work 重构](https://latent.space/p/unpacking-chatgpt-work) 又提出了另一种连续性抱怨：跨任务上下文是通过产品层服务来中介的，而不是通过一个自由共享的工作空间直接传递。[@Fetch_ai](https://x.com/Fetch_ai) [总结](https://x.com/Fetch_ai/status/2084919840108646834)（107 个赞，1 条回复，6,067 次浏览）也把同样的构建后负担描述为部署、发现、编排、用户访问和支付。当前的变通方式，是在模型循环之外叠加更多路由、更多产品层上下文，以及更多明确表层。这个方向值得投入，因为多条彼此独立的帖子都把它描述为“构建代理”之后真正的工作。

### 代理金融和开放推理需要的是信任层，而不只是钱包

严重程度：中。[@ama_protocol](https://x.com/ama_protocol) [将其定义为](https://x.com/ama_protocol/status/2084708895508021477)（54 个赞，49 条回复，611 次浏览）把 Amadeus 的重点放在两个缺失环节上：一个可以发现并运行代理的地方，以及一份私密但可证明的记录，用来说明代理如何动用真实资金。[@wardenprotocol](https://x.com/wardenprotocol) [推出](https://x.com/wardenprotocol/status/2085047751457305022)（47 个赞，14 条回复，7,177 次浏览）则用钱包、存款、运营方供给和可验证推理来定位 [Halo](https://wardenprotocol.org/blog/halo-launch)，但这两款产品目前卖点更多仍是周边的信任设计，而不是主流使用证据。当前的应对方式是托管、预算、可证明记录，以及受钱包约束的访问。这个方向值得投入，但今天的证据仍然偏早、偏基础设施，尚未显示出广泛采用。

## 3. 人们希望哪些产品存在

### 位于技能库之上的技能选择器

实际需求。最明确的需求来自对 [@mattpocockuk](https://x.com/mattpocockuk) 的 [v1.2 发布](https://x.com/mattpocockuk/status/2084985277102031137)（1,219 个赞，49 条回复，38,104 次浏览，747 次收藏）的回复：技能库很强大，但覆盖面已经广到需要一个 `skills-helper` 来推荐该运行什么。[@rlaope](https://x.com/rlaope) [将其定义为](https://x.com/rlaope/status/2084883447873753155)（45 个赞，1 条回复，3,317 次浏览，60 次收藏）把同一缺口描述为插件疲劳；[@alex_prompter](https://x.com/alex_prompter) [回答](https://x.com/alex_prompter/status/2085054816888484123)（8 个赞，2 条回复，3,443 次浏览）则用更严格的触发和边界规则来应对。缺失的产品不是更大的目录，而是技能的推荐器和治理器。机会：直接。

### 一个具备明确权限和持久上下文的代理团队统一入口

实际且紧迫的需求。[@rileybrown](https://x.com/rileybrown) [制作](https://x.com/rileybrown/status/2085077630001287349)（71 个赞，8 条回复，7,636 次浏览，100 次收藏）明确提出了“一个 GOD 代理，还是多个更小的代理”这一问题，最有力的回复称，最终通常会收敛到权限问题。[ChatGPT Work 拆解](https://latent.space/p/unpacking-chatgpt-work) 和 [@Fetch_ai](https://x.com/Fetch_ai) 的 [技术栈总结](https://x.com/Fetch_ai/status/2084919840108646834)（107 个赞，1 条回复，6,067 次浏览）都暗示着同一个缺失层：一个持久的统一入口，能够跨代理、上下文、设备和服务路由工作，同时不把连续性隐藏在不透明的产品管线之后。现有产品已部分覆盖这一问题，因此机会属于竞争性市场，而不是空白市场。机会：竞争性。

### 足够公开、可供审计的基准测试表层，而不只是供人仰望

实际需求。[@morganlinton](https://x.com/morganlinton) [收藏](https://x.com/morganlinton/status/2084719560343846954)（505 个赞，3 条回复，129,314 次浏览，787 次收藏）的一份外部 harness 指南、[@swyx](https://x.com/swyx) [分享](https://x.com/swyx/status/2085073764551962960)（82 个赞，10 条回复，8,623 次浏览，83 次收藏）对 ChatGPT Work 的外部复原，以及回复中对 [@ren_hongyu](https://x.com/ren_hongyu) 的 [Muse Code 图表](https://x.com/ren_hongyu/status/2085084609315033586)（166 个赞，9 条回复，8,633 次浏览，8 次收藏）提出的质疑，都指向同一个愿望：如果 harness 如此重要，人们就希望看到公开文档、可复现评测，以及关于这些数字究竟意味着什么的解释。这一问题一半是工具问题，一半是报告问题。机会：竞争性。

### 以钱包为边界、并提供可证明记录的代理金融执行层

Fetch.ai、Halo 和 Agent Arena 则把构建表层扩展到了编码之外。一个组织交付和发现，一个组织支付和供给，一个组织公开评测流量。它们合在一起表明，越来越多构建者正在从“代理能不能行动”转向“用户能不能触达它、给它付费，并把它与别人比较”。

## 7. 机会在哪里

**[+++] 技能打包、发现和治理层** —— Matt Pocock 的 1,350 万次安装技能包、要求提供 `skills-helper` 的回复、oh-my-hermes 试图置于插件蔓延之上的做法，以及 `SKILL.md` 边界模板，都指向同一个缺口：一旦技能足够多，就必须有人负责推荐、路由、约束和维护。证据横跨第 1、2、3 和 5 节，因此这是这组数据里近期最强的产品机会。

**[+++] 具备权限感知能力的代理统一入口** —— Riley Brown 对 Vercel 的采访明确提出了“一个 GOD 代理，还是多个权限化代理”这一权衡；ChatGPT Work 的公开拆解揭示了仍有多少连续性由产品层中介；Fetch.ai 则把部署、发现、编排、访问和支付描述为构建完成后的真实旅程。持续一致的机会，是打造一个统一入口，在不丢失控制和连续性的前提下，跨代理、服务和上下文路由工作。

**[++] 公开 harness 可观测性与基准审计工具** —— Morgan Linton 收藏了一份 harness 指南，Latent.Space 做了逆向工程，Prime Agent 公开了架构和基准主张，而 Muse Code 的图表也遭到质疑，这些都表明市场确实需要公开解释和可审计评测。这个机会有现实意义，但竞争也很激烈：很多人都能发布图表，能成为值得信赖的比较入口的人却少得多。

**[+] 代理支付、推理与信任通道** —— Amadeus 和 Halo 都指出，光有钱包并不够；发现、可证明记录、运营方供给和支出边界同样重要。证据具体，但仍处于早期，因此这是一个正在形成的机会，而不是已经充分验证的市场。

## 8. 要点

1. **技能不再只是可复用的提示词；它们已经成为带有安装器、文档和治理问题的产品。** Matt Pocock 的 v1.2 发布，以及要求提供 `skills-helper` 的回复，同时展示了规模和新的发现负担；oh-my-hermes 则展示了在原始技能之上增加封装层的平行路径。（[来源](https://x.com/mattpocockuk/status/2084985277102031137)）
2. **Harness 工程如今已经成为人们会拿来做基准测试、逆向分析和公开比较的对象。** 当天最有力的证据，包括 Morgan Linton 收藏 harness 指南、Latent.Space 对 ChatGPT Work 的复原、Prime Agent 的开放架构，以及 Muse Code 充满争议的图表。（[来源](https://x.com/johannes_hage/status/2085095925920440466)）
3. **对于许多团队来说，构建完成后的表层已经成为真正的工程难题。** Riley Brown 对 Vercel 的采访、Fetch.ai 从构建到服务的技术栈，以及 ChatGPT Work 由产品层管理的连续性，都表明代理存在之后最棘手的部分在于权限、上下文、发现和访问。（[来源](https://x.com/rileybrown/status/2085077630001287349)）
4. **代理支付与推理通道正在变得更具体，但目前看起来仍更像基础设施押注，而不是已经稳定的需求。** Halo 的公开 alpha 发布，以及 Amadeus 的中心/嵌入式拆分，都进一步补充了钱包、记录和服务发现等细节；但与打包和 harness 两大主题相比，这两条讨论都还没有像前者那样清晰展现广泛用户采用。（[来源](https://x.com/wardenprotocol/status/2085047751457305022)）
