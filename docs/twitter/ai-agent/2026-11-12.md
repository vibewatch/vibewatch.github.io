# Twitter AI Agent - 2026-11-12

## 1. What People Are Talking About

### 1.1 Long-running agents are being treated as reliability systems 🡕

A detailed engineering post distinguishes short agents, where retrying a stateless call may be sufficient, from multi-hour runs that can fail late, repeat side effects, or lose state. The proposed controls are familiar distributed-systems patterns: checkpointing, idempotency, durable event logs, and resumable workflows.

[@arpit_bhayani](https://x.com/arpit_bhayani) [argued](https://x.com/arpit_bhayani/status/2120852903925793264) (308 likes, 53 replies, 10,343 views, 160 bookmarks) that a long-running agent failing near the end can waste API cost and elapsed time. The post lists provider rate limits, network failures, pod eviction, context overflow, and human pauses as possible interruptions, and says these are often software-system problems rather than model problems.

**Discussion insight:** A reply simply says the "step 95 of 100" example hurts; the captured thread contains empathy more than counter-evidence.

**Comparison to prior day:** Nov. 11 discussed workflow evaluation and harness reliability. Today's post makes late-run recovery and state durability the central design concern.

### 1.2 Security response is framed as an engineering bottleneck →

One practitioner argues that improving incident response can improve delivery speed as well, and that agent-generated changes increase the need for disciplined patching, testing, and feedback loops. The article expands the talk's themes to back pressure and property-based testing; it is an engineering position, not a measured industry-wide result.

[@GeoffreyHuntley](https://x.com/GeoffreyHuntley) [shared](https://x.com/GeoffreyHuntley/status/2120602355066659231) (160 likes, 15 replies, 6,740 views, 167 bookmarks) a talk on security and software engineering. Its [write-up](https://ghuntley.com/answer/) argues for optimizing incident response and describes loops, back pressure, and property-based testing as part of the engineering approach.

**Comparison to prior day:** The previous report's reliability discussion focused on agent behavior and observability; this post extends the frame to maintaining and securing the software around agents.

### 1.3 Reusable skills and role-specific model routing are becoming practical patterns 🡕

Two posts describe ways to package or divide work instead of repeating broad instructions in every session. One proposes splitting implementation, repository search, and review across Claude models; another describes Microsoft's open .NET skills collection, including upgrade, data, testing, and MCP-server workflows.

[@xsmryze](https://x.com/xsmryze) [described](https://x.com/xsmryze/status/2120635742548312351) (63 likes, 10 replies, 6,231 views, 83 bookmarks) a Claude Code setup that assigns routine implementation to Sonnet, repository searches to Haiku, and selected planning or review decisions to Opus. A reply says the advisor role is what saves the most cost for them; the token savings are the author's experience, not a benchmark.

[@AntonMartyniuk](https://x.com/AntonMartyniuk) [presented](https://x.com/AntonMartyniuk/status/2120859198988632457) (74 likes, 16 replies, 2,045 views, 68 bookmarks) Microsoft's [dotnet/skills repository](https://github.com/dotnet/skills) as reusable instructions for coding agents. The post's infographic groups skills by plugin, including testing, upgrades, and MCP work.

![Microsoft .NET skills grouped by plugin, including testing, upgrade, data, and MCP skills](https://pbs.twimg.com/media/HW7OMmUXUAAbnkX.jpg)

## 2. What Frustrates People

### A long-running agent can lose a nearly complete run

**Severity: High for multi-hour tasks; prevalence is not established.** The author lists rate limits, timeouts, worker eviction, context overflow, and human pauses as possible interruptions, and warns that retrying can repeat side effects. Checkpointing, idempotency, durable logs, and resumable execution are the proposed coping methods. ([@arpit_bhayani](https://x.com/arpit_bhayani/status/2120852903925793264) (308 likes, 53 replies, 10,343 views, 160 bookmarks, 7 quotes, 19 retweets))

### Reusable skills can be stale or too generic for a project

**Severity: Medium.** The .NET skills post says the shared instructions do not know a team's project conventions. A reply also points out that the post's 99-skill, 14-plugin snapshot was already outdated relative to the repository's main branch. That creates a practical maintenance issue: consumers need to verify the current skill list and add local context. ([post](https://x.com/AntonMartyniuk/status/2120859198988632457) (74 likes, 16 replies, 2,045 views, 68 bookmarks, 12 retweets), [repository](https://github.com/dotnet/skills), [correction](https://x.com/jacobho79/status/2120874903499092036) (1 reply, 12 views))

### Security work can compete with delivery time

**Severity: Medium, based on one practitioner's account.** Geoffrey Huntley argues that incident response and patching need to keep pace with changes, and that security should be treated as engineering work rather than a separate late-stage check. The post offers a position and examples, not a prevalence estimate. ([talk write-up](https://ghuntley.com/answer/))

## 3. What People Wish Existed

### Resumable workflows for long-running work

The requested capabilities are explicit: checkpoints, idempotent actions, durable event logs, and the ability to resume after a provider, infrastructure, or human pause. These are practical requirements for agents whose work spans hours, not simply longer context windows. **Urgency: High for long jobs. Opportunity: Direct.** ([source](https://x.com/arpit_bhayani/status/2120852903925793264) (308 likes, 53 replies, 10,343 views, 160 bookmarks, 7 quotes, 19 retweets))

### Skills that fit a team's project and stay current

The .NET skills post says shared instructions do not know a specific repository's conventions, while a reply notes that the count was already stale. Local overlays and versioned skill catalogs are partial workarounds. **Urgency: Medium. Opportunity: Direct.** ([post](https://x.com/AntonMartyniuk/status/2120859198988632457) (74 likes, 16 replies, 2,045 views, 68 bookmarks, 12 retweets), [correction](https://x.com/jacobho79/status/2120874903499092036) (1 reply, 12 views))

### Faster, more observable security response

Geoffrey Huntley's write-up calls for engineering that makes incident response faster, with testing and back-pressure practices around changes. It is an aspiration rather than a specific product request. **Urgency: High when incidents occur. Opportunity: Aspirational.** ([write-up](https://ghuntley.com/answer/))
