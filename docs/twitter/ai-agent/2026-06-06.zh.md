# Twitter AI 智能体 - 2026-06-06

## 1. 人们在讨论什么

### 1.1 “harness engineering”开始沉淀为可复制的操作资产 🡕

6 月 6 日，AI 智能体领域最突出的主题是：“harness engineering”不再只是像一份待读清单，而是开始以团队可直接复制的资产形式出现：路线图、智能体章程、运行时架构图和技术栈图。共有 5 条入选内容支撑了这一主题。

[@aakashgupta](https://x.com/aakashgupta) [总结了](https://x.com/aakashgupta/status/2062986823689974044)（65 个赞、5 条回复、10,798 次浏览、94 次收藏）分享了一份 OpenAI 团队路线图：第 1—2 个月聚焦代码仓库可理解性，第 3—4 个月聚焦自动化验证，第 5—6 个月则通过规格说明和评估，向 PM 与设计师开放系统。随附路线图通过点名 AGENTS.md、文档树、审查者角色、E2E 测试和“假门”实验，把这一推进路径具体化；同时还把目标量化为 100 万行代码、25 万行提示词，以及零人工键入代码。

![路线图图片，展示了面向 agent 驱动工程的仓库可读性、自动化验证和杠杆扩展阶段](https://pbs.twimg.com/media/HKEzlTubcAAtF70.jpg)

[@PrajwalTomar_](https://x.com/PrajwalTomar_) [分享了](https://x.com/PrajwalTomar_/status/2063270866558067069)（48 个赞、4 条回复、2,574 次浏览、86 次收藏）分享了一份经过脱敏处理的 Hermes Agent SOUL.md 模板。这张截图的重要之处在于，它把运行契约写得非常明确：立场、自主性、使命、问责和提出异议的方式，都被写成了一等配置。讨论串认为，智能体之所以总是在每一步都来请求许可，原因正是缺少这一层。

![SOUL.md 模板截图，定义了 Hermes agent 的立场、自主性、使命和责任](https://pbs.twimg.com/media/HKI16wZakAAhgdQ.jpg)

[@_lopopolo](https://x.com/_lopopolo) [认为](https://x.com/_lopopolo/status/2062950475989725465)（83 个赞、9 条回复、10,597 次浏览、71 次收藏）认为，智能体系统需要明确“何时、如何去获取上下文”的预期，而不是堆一堆泛泛规则。回复进一步刻画了失败模式：有人问，AGENTS.md 之所以存在，是否很大程度上是因为上下文窗口在长时运行中依然会失效；另一人说，自动压缩会让确定性地向上下文里塞信息变得不可靠；还有人提出“图书管理员”智能体，专门负责为工作智能体检索正确上下文。

[@pauliusztin_](https://x.com/pauliusztin_) [概述了](https://x.com/pauliusztin_/status/2063236967987298550)（16 个赞、9 条回复、274 次浏览、10 次收藏）提出了一套四层 AI 软件架构：展示层、带统一记忆的 harness/运行时、通过技能、CLI 和 MCP 客户端实现的连接层，以及位于更底层的 MCP 服务器。随附架构图对持久化执行、重试、检查点、权限和 MCP 应用分别应处于哪一层，给出了少见的具体说明；回复则认为，真正把聊天循环变成后台工作进程的，正是持久化执行。

![架构图，展示了位于 harness runtime 之上的呈现层、skills/CLI/MCP 连接，以及下方的 MCP servers](https://pbs.twimg.com/media/HKErAgAWMAAYlhN.jpg)

**讨论洞察：** 回复里并没有人要求更大的上下文窗口。大家要的是铺好的工作流、主动寻求上下文的行为、检查点，以及更清晰的运行契约，让智能体不必靠猜。

**与前一天对比：** 6 月 5 日，人们还在争论 harness engineering 是否就是缺失的关键技能；到了 6 月 6 日，这一论点已经变成了可复制的资产。

### 1.2 成本治理与按任务分配模型路由，变得更加具体 🡕

第二个主题簇把智能体运营视为预算和路由问题，而不是品牌站队。共有 3 条入选内容支撑了这一主题。

[@chamath](https://x.com/chamath) [认为](https://x.com/chamath/status/2063292917964517830)（897 个赞、115 条回复、278,744 次浏览、856 次收藏）指出，前沿闭源模型与强开源模型之间的能力差距，收窄速度远快于价格差距。他的成本表显示：若每月处理 10 亿输入 token 加 10 亿输出 token，GPT-5.5 Pro 约为 105,000 美元，Claude Opus 4.8 约为 30,000 美元，DeepSeek V4 Pro 约为 5,220 美元，DeepSeek R1 约为 2,740 美元。随后他建议：大规模任务用 DeepSeek，高可靠性需求用 Opus，只有在额外能力确实能回本时，才用 GPT-5.5 Pro。回复中也有很有价值的反驳：同口径基准测试依然重要，企业级 AI 需要追踪、token 预算和明确命名的 ROI 目标，而不只是更便宜的模型。

[@AlexFinn](https://x.com/AlexFinn) [列出了](https://x.com/AlexFinn/status/2063375100293124232)（108 个赞、20 条回复、6,149 次浏览、144 次收藏）总结了 Hermes 的 7 条实践，实质上就是一份模型路由手册：为每个模型使用不同配置，把 GPT-5.5 分配给编程，把 Opus 分配给写作和研究，把本地模型分配给廉价、重复性工作；然后把重型工作流放到 /background，并在记忆质量下降时，收紧 cron 任务和压缩设置。后续更正串之所以重要，是因为它表明这些配置并不是静态的厂商押注，而是持续进行中的运营选择，甚至细到本地究竟哪一版 Qwen 真能跑起来。

[@levie](https://x.com/levie) [认为](https://x.com/levie/status/2063055332545540096)（139 个赞、27 条回复、23,187 次浏览、70 次收藏）认为，编程仍然是最容易让智能体发挥作用的领域，恰恰因为这类工作可验证，而且上下文已经以数字形式存在于代码库里。回复把这一点进一步延伸到其他知识工作：瓶颈并不是模型原始智力，而是有多少真实上下文仍然只存在于某位资深员工脑中，或散落在无结构的共享盘里。

**讨论洞察：** 有价值的分歧不在于哪家实验室领先，而在于什么时候高级模型真的值得那笔钱，以及模型之上还需要叠加多少路由、评估和治理。

**与前一天对比：** 6 月 5 日，大家还在把模型之上的脚手架视为护城河；到了 6 月 6 日，讨论里已经出现了明确的月度支出表和逐模型操作手册。

### 1.3 智能体框架继续演变成带桌面界面、市场与支付能力的产品 🡕

第三个主题簇讨论的是分发表面：桌面控制中心、店面和可变现界面，而不只是又一个裸框架。共有 4 条入选内容支撑了这一主题。

[@iamlukethedev](https://x.com/iamlukethedev) [报道称](https://x.com/iamlukethedev/status/2063081062473859097)（99 个赞、11 条回复、11,115 次浏览、51 次收藏）指出，Hermes Agent v0.16 已不再只是 CLI 层框架，而是一个平台：它提供 macOS、Windows 和 Linux 桌面应用、Web 管理后台、快速设置、拖放文件、MCP 服务器管理、记忆控制以及远程实例连接。回复称，通过 Tailscale 进行远程访问的体验很快，同时也提出了一个在线上的边缘案例：主模型 token 用尽后，如何切换到后备模型。

[@trythreews](https://x.com/trythreews) [已发布](https://x.com/trythreews/status/2063223928483697090)（373 个赞、61 条回复、20,856 次浏览、18 次收藏）展示了一个 3D AI 智能体平台，将浏览器原生渲染、多 LLM 对话、原生 Solana 钱包、链上身份、实时语音和一行嵌入标签结合在一起。公开的 [three.ws](https://three.ws) 网站进一步补全了产品表面：200+ 动作片段、多人世界、USDC 按次聊天付费、WebXR 放置，以及 MCP/A2A 连接能力。这让它看起来不再像演示，而更像是一个具身化运行时加市场。

[@MeltedMindz](https://x.com/MeltedMindz) [介绍了](https://x.com/MeltedMindz/status/2063009047318855856)（18 个赞、2 条回复、603 次浏览）介绍了 [Postera](https://postera.dev)：一个基于 Base、使用 x402 的智能体对智能体市场，智能体可以发布 SKILL.md 文件，并直接以 USDC 收款，平台不抽取订阅分成。[@AxiomBot](https://x.com/AxiomBot) [展示了](https://x.com/AxiomBot/status/2063306043925631108)（14 个赞、4 条回复、369 次浏览）则展示了它在实际中的样子：一个出售付费技能的店面页面，列出 MCP/A2A/x402 端点、链上收据、买家数量、复购指标和个人资料评分。这张图之所以重要，是因为它把智能体商业化变成了一个可见的仪表盘，价格、收据和信任信号一目了然。

![Postera 上 Axiom 资料页的截图，展示了付费 skills、已声明的 endpoints、链上凭证和评分明细](https://pbs.twimg.com/media/HKJV6dHaoAA8Jus.jpg)

**讨论洞察：** 讨论重心持续从模型 IQ 转向用户真正能操作的表面：远程控制、记忆设置、身份、收款和店面指标。

**与前一天对比：** 6 月 4 日的信息流里还充满了对“面向智能体的工作界面”的需求；到了 6 月 6 日，已经有更多已发布的产品界面可供指认。

## 2. 什么让人沮丧

### 没有控制平面时，token 预算太容易被烧穿

严重程度：高。[@chamath](https://x.com/chamath/status/2063292917964517830)（897 个赞、115 条回复、278,744 次浏览、856 次收藏）明确指出，团队仍在默认使用最昂贵的模型，在缺乏治理的情况下烧掉大量预算；回复则认为，企业级 AI 需要追踪、token 预算和明确命名的 ROI 目标，而不是模糊的试验。[@AlexFinn](https://x.com/AlexFinn/status/2063375100293124232)（108 个赞、20 条回复、6,149 次浏览、144 次收藏）则以运营者视角展示了当前的权宜之计：按模型配置拆分工作，把更便宜的任务交给本地模型，并在运行时退化时主动调 cron 任务和压缩设置。这个方向值得做产品，因为痛点已经是按美元来表达，而不只是按延迟来表达。

### 智能体在会话之间仍会遗忘、压缩过度或靠猜

严重程度：高。[@_lopopolo](https://x.com/_lopopolo/status/2062950475989725465)（83 个赞、9 条回复、10,597 次浏览、71 次收藏）指出，harness 不能依赖把所有信息都塞进上下文里，尤其是在自动压缩之后。[@DamiDefi](https://x.com/DamiDefi/status/2063279068985127271)（108 个赞、7 条回复、11,156 次浏览、16 次收藏）则从用户侧描述了同样的痛点：大多数智能体在每次会话结束后都会丢掉学到的东西，而 Hermes 之所以显得不同，只是因为它把运行时技能、持久记忆和离线优化叠加在了一起。[@AlexFinn](https://x.com/AlexFinn/status/2063375100293124232) 补充了运营侧症状——只有把 Hermes 的压缩阈值调低后，记忆丢失才有所改善；回复还说，一旦智能体接触真实文件和账户，权限与 RAM 限制就会变成整个产品的核心。这个方向值得做产品，因为今天的应对方式仍然是手动调参、来回切配置，以及围绕记忆层做营销。

### 验证仍落后于生成

严重程度：高。[@Vtrivedy10](https://x.com/Vtrivedy10/status/2063068668049740254)（48 个赞、4 条回复、3,799 次浏览、34 次收藏）称，高效验证是自我改进型智能体最大的瓶颈之一，并认为长任务需要中间验证关卡，而不只是最终答案检查。[@vigilcodes](https://x.com/vigilcodes/status/2063128003325120871)（5 个赞、1 条回复、104 次浏览）则通过发布 VIGIL 给出回应：它提供一个单一 MCP 端点，包含面向 Base 的审批、蜜罐、token、钱包和撤销工具。[@dani_avila7](https://x.com/dani_avila7/status/2063099370375880765)（8 个赞、2 条回复、679 次浏览、11 次收藏）显示，同样的压力也开始进入代码评审：SkillSpector 已并入 Claude Code Templates 仓库，因此技能 PR 会在合并前接受扫描。这个方向值得做产品，因为信息流显示团队正在把验证前移，但仍把它当作一个必须外挂的独立层。

## 3. 人们希望什么东西存在

### 能直接跑在工作流内部的低成本验证层

这是最明确的现实需求。[@Vtrivedy10](https://x.com/Vtrivedy10/status/2063068668049740254)（48 个赞、4 条回复、3,799 次浏览、34 次收藏）表示，中间验证是长周期智能体的瓶颈，真正的问题在于能否把成本压低到足以规模化使用。[@vigilcodes](https://x.com/vigilcodes/status/2063128003325120871)（5 个赞、1 条回复、104 次浏览）和 [@dani_avila7](https://x.com/dani_avila7/status/2063099370375880765)（8 个赞、2 条回复、679 次浏览、11 次收藏）都给出了部分答案——一个 MCP 扫描器和一个 PR 扫描器——但今天的证据仍显示，这些更像点状方案，而不是一层默认验证基础设施。机会：直接。

### 同时整合路由、权限和持久记忆的控制平面

这是一个现实而紧迫的需求。[@chamath](https://x.com/chamath/status/2063292917964517830) 把模型选择视为治理与路由问题，而不是模型大战。[@AlexFinn](https://x.com/AlexFinn/status/2063375100293124232) 和 [@iamlukethedev](https://x.com/iamlukethedev/status/2063081062473859097) 描述了这一需求在运营层面的具体形态：按模型区分配置、配轻量桌面界面的远程算力、记忆调优、仪表盘控制，以及智能体接触真实文件和账户之后的权限边界。机会：直接且竞争激烈。部分答案已经存在，但信息流表明，运营者仍在手工拼接成本路由、记忆和权限。

### 在智能体开始靠猜之前，先把团队上下文整理得可理解

这是实际需求，不是情绪诉求。[@aakashgupta](https://x.com/aakashgupta/status/2062986823689974044) 把路线图的前三分之一都放在代码仓库可理解性和文档上，[@_lopopolo](https://x.com/_lopopolo/status/2062950475989725465) 认为提示词必须收敛成铺好的工作流，而不是泛泛地往上下文里塞东西，[@levie](https://x.com/levie/status/2063055332545540096) 及其回复则指出，许多非代码领域最有用的上下文仍然只存在于人的脑中或无人管理的硬盘里。[@tom_doerr](https://x.com/tom_doerr/status/2063310953039487279) 给出了一个较窄的答案——autoskills 会自动识别技术栈并安装精选技能——但今天的证据表明，大多数团队仍在手动完成这种翻译。机会：直接。

- **优势** — 人们点出的具体优点
- **局限** — 帖子中可见的具体抱怨、缺口或失败模式

整体满意度光谱偏务实，而非意识形态化。[@chamath](https://x.com/chamath/status/2063292917964517830) 和 [@AlexFinn](https://x.com/AlexFinn/status/2063375100293124232) 都按任务和成本来路由模型，而 [@pauliusztin_](https://x.com/pauliusztin_/status/2063236967987298550) 和 [@elora_khatun](https://x.com/elora_khatun/status/2063087975488204948) 则把 MCP 视为混合技术栈中的一环，还需要配合技能和 CLI。常见的权宜做法包括：在远程算力之上保留桌面界面、在提示前先预处理文件、用发布技能代替超长提示词，以及在智能体执行合并或签名之前扫描高风险操作。[@sharbel](https://x.com/sharbel/status/2063183887337975985) 和 [@vigilcodes](https://x.com/vigilcodes/status/2063128003325120871) 让竞争格局的变化变得清晰：上下文准备层与安全层，正在作为独立产品类别吸引注意力。

## 7. 机会在哪里

**[+++］ 用于路由、权限和记忆的 agent 控制平面** — ［@chamath](https://x.com/chamath/status/2063292917964517830) 为模型路由给出了明确的月度成本区间，而 [@AlexFinn](https://x.com/AlexFinn/status/2063375100293124232) 和 [@iamlukethedev](https://x.com/iamlukethedev/status/2063081062473859097) 则显示，运营者已经在管理按模型区分的配置、桌面控制、远程算力和记忆设置。这个方向很强，因为痛点同时横跨财务、可靠性和访问控制。

**[++］ 以验证为先的 runtime 层** — ［@Vtrivedy10](https://x.com/Vtrivedy10/status/2063068668049740254) 把高效验证描述为核心瓶颈，[@dani_avila7](https://x.com/dani_avila7/status/2063099370375880765) 把技能扫描前移到 PR 审查，[@vigilcodes](https://x.com/vigilcodes/status/2063128003325120871) 则通过 MCP 交付签名前检查。这个方向机会中等，因为买方已经可见、需求也很明确，但方案仍零散分布在 CI、运行时和链上扫描器之间。

**[++］ 仓库可读性与 skill 安装基础设施** — ［@aakashgupta](https://x.com/aakashgupta/status/2062986823689974044)、[@PrajwalTomar_](https://x.com/PrajwalTomar_/status/2063270866558067069) 和 [@tom_doerr](https://x.com/tom_doerr/status/2063310953039487279) 都指向同一个需求：在智能体开始靠猜之前，把其设置明确下来。这个方向机会中等，因为需求显而易见，公开资产也在不断出现，但市场仍分散在教育、模板和安装器之间。

**[+］ Agent 商业化与具身接口** — ［@trythreews](https://x.com/trythreews/status/2063223928483697090)、[@MeltedMindz](https://x.com/MeltedMindz/status/2063009047318855856) 和 [@AxiomBot](https://x.com/AxiomBot/status/2063306043925631108) 显示，智能体正在获得身体、钱包、店面和直接支付能力。这个方向仍处于萌芽期，因为虽然已有在线产品，但可见营收、买家数量和信任系统都还早。

## 8. 要点

1. **6 月 6 日的 harness engineering，核心是资产，不是观点。** 路线图、SOUL.md 模板和运行时架构图，把智能体运营变成了团队今天就能复制的文件和图示。（[来源](https://x.com/aakashgupta/status/2062986823689974044)）
2. **模型路由如今已经是一个单位经济学问题。** Chamath 的表把 GPT-5.5 Pro、Claude Opus 4.8、DeepSeek V4 Pro 和 DeepSeek R1 放进了同一张月度成本表，而 AlexFinn 的配置建议也采取了同样思路：不同模型做不同工作。（[来源](https://x.com/chamath/status/2063292917964517830)）
3. **界面层正在快速变宽。** Hermes 桌面端、three.ws 和 Postera 都把智能体当作桌面应用、具身界面或店面，而不是纯聊天循环。（[来源](https://x.com/iamlukethedev/status/2063081062473859097)）
4. **记忆仍然是运营断层线。** _lopopolo 指出，长时运行不能依赖确定性地把信息塞进上下文；而 Hermes 支持者之所以持续吸引注意力，也正是因为他们承诺下一次会话不会从空白开始。（[来源](https://x.com/_lopopolo/status/2062950475989725465)）
5. **安全与上下文准备正在成为独立产品类别。** SkillSpector、VIGIL 和 GitHub 爆发榜都指向同一件事：围绕模型的扫描器、压缩层和代码知识工具，需求正在上升。（[来源](https://x.com/sharbel/status/2063183887337975985)）
