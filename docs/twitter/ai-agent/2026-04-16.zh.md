## 1. 人们在讨论什么

### 1.1 Harness Engineering 形成三阶段框架 🡕

当天得分最高的一条帖子，将整个智能体领域重新框定为一个三阶段演进过程。[@akshay_pachaar](https://x.com/akshay_pachaar) [发布了一篇爆火的深度解析](https://x.com/akshay_pachaar/status/2044763357300027842)（484 个赞、627 次收藏、56,719 次浏览）梳理了智能体工程从权重（2022 年）到上下文（2023–24 年），再到 Harness Engineering（2025–26 年）的演进。核心论点是：“模型不再是智能的唯一所在。它处在一个 harness 之中，而这个 harness 包含持久记忆、可复用技能、标准化协议（如 MCP 和 A2A）、执行沙箱、审批关卡以及可观测性层。”他还链接了一篇学术论文：《LLM 智能体中的外部化：记忆、技能、协议与 Harness Engineering 的统一综述》。

![图示展示了 agent engineering 从 weights 到 context 再到 harness engineering 的三阶段演进](https://pbs.twimg.com/media/HGB1KOKbkAAx9vD.png)

[@neural_avb](https://x.com/neural_avb) [报告了第一手的摩擦与阻碍](https://x.com/neural_avb/status/2044679770504601721)（196 个赞、212 次收藏）分享了为本地边缘模型（约 4B 参数）构建 harness 的经验：“当你处理更小、更笨的模型时，很多常见的 harness engineering 原则根本不适用，这简直离谱。”约束包括：上下文更小、若不采用受约束解码就无法保证结构化输出，以及长序列运行会导致硬件过热。[@sunnyworks](https://x.com/sunnyworks) 在回复中确认，使用 llama.cpp 跑 Qwen3.5 模型时也遇到了完全相同的痛点。

[@_lopopolo](https://x.com/_lopopolo) [宣布](https://x.com/_lopopolo/status/2044441368957993042) 宣传了 4 月 28 日 ODSC AI East 的一场会议：“Harness Engineering：面向 agent-first 软件开发的实用模式。”[@miguelbranco80](https://x.com/miguelbranco80) [描述了](https://x.com/miguelbranco80/status/2044812363275149604) 分享了一个应用 harness engineering 原则构建的“软件黑暗工厂”——一夜之间合并了数十个 PR。[@erikdunteman](https://x.com/erikdunteman) [上线了](https://x.com/erikdunteman/status/2044877499490869344) 展示了一个基于 Modal 沙箱和 OpenAI Agent SDK、用于并行后台编码任务的定制智能体 harness。

[@burkov](https://x.com/burkov) [分享了一篇 ICLR 2026 论文](https://x.com/burkov/status/2044676405758177384) 介绍了 ACE（Agentic Context Engineering，智能体上下文工程）。这是一个让上下文演化为动态操作手册的框架，可防止细节逐步流失，并以更低的适配成本超越基线表现。与此同时，他还 [重点提到了](https://x.com/burkov/status/2044891819306074359) 了 GAM 论文；该论文研究“即时”记忆框架，能够在运行时动态优化上下文。

![ACE 论文概览，展示了用于动态 playbook 演化的 Agentic Context Engineering 框架](https://pbs.twimg.com/media/HGAmKZHXIAA5n-o.jpg)

**讨论洞察：** [@alexxxluan](https://x.com/alexxxluan) 反对使用单一的 harness 总指标：“我认为下一步应该是按任务类型（研究、编码、支持）衡量 harness 质量，而不是只看一个汇总分数。”[@mylifcc](https://x.com/mylifcc) 表示，他们正在用 Rust 构建 harness 服务器，并发现两个智能体同时写入同一路径时会出现静默文件冲突——“最后写入者获胜，零报错”——最终通过为每个智能体分配互不重叠的文件所有权解决。[@AppliedLLMs](https://x.com/AppliedLLMs) 指出：“真正的杠杆在于谁设计了脚手架——中断条件、重试逻辑，以及状态如何在各步骤之间传递。”

**与前一天对比：** 昨天，harness engineering 还聚焦于实现模式（loiane 的前馈+反馈控制、Claude Code 的动态提示组装）。今天，这一概念被提升为完整的历史框架（权重—上下文—harness），同时暴露出小模型上的边界限制，并新增了两篇学术论文（ICLR 2026 的 ACE 和 GAM）。讨论焦点也从“如何构建 harness”转向“harness engineering 对整个领域意味着什么”。

### 1.4 多智能体编排获得实证支持 🡒

[@0xSero](https://x.com/0xSero) [分享了一篇详细分析](https://x.com/0xSero/status/2044879665001595263)（64 个赞、89 次收藏）分享了对多智能体编码的观察：“我分析了数百次 AI 编码智能体会话，发现它确实很有帮助。”他还表示，自己在这个问题上的看法已经“完全转向”。[@LLMJunky](https://x.com/LLMJunky) [认可了](https://x.com/LLMJunky/status/2044883554492883061) 认可这一发现，并补充说，多智能体委派能把上下文压缩从 10–20 个周期降到 2–3 个周期：“想从多智能体中拿到最高质量的结果，关键在于高质量的 harness engineering。”

[@ashpreetbedi](https://x.com/ashpreetbedi) [发布了](https://x.com/ashpreetbedi/status/2044823993547469157) 介绍了《扩展 Agentic Software：第 1 部分》——一个单一 FastAPI 进程配合 PostgreSQL 的架构，运行着 14 个智能体、11 个多智能体团队和 5 条工作流，并具备 RBAC、JWT 身份验证、会话、记忆和横向扩展能力。[@CosineAI](https://x.com/CosineAI) 推出了用于并行子智能体的 Swarm 模式。[@JaynitMakwana](https://x.com/JaynitMakwana) [称赞了它](https://x.com/JaynitMakwana/status/2044715349862658411) 指出：“真正的问题不是模型质量，而是工作流碎片化。”

![架构图展示了结合 FastAPI 和 PostgreSQL 的多 agent 系统，用于实现可水平扩展的 agentic software](https://pbs.twimg.com/media/HGClB-RWsAEDR6d.jpg)

**讨论洞察：** [@therealbifkn](https://x.com/therealbifkn) 指出了委派的核心问题：“编排智能体要么想自己把活干了，要么先制定一个计划，再让执行智能体一次性把整个计划跑完。”[@0xSero](https://x.com/0xSero) 回复道：“你不能在 harness 层面允许它这么做！”——这说明修复手段在 harness 层的约束，而不是模型层的训练。[@j_schwartzz](https://x.com/j_schwartzz) 指出，“在某些情况下，[多智能体] 表现更好，因为它不会在上下文窗口最后 20% 的空间里去写关键代码。”

**与前一天对比：** 昨天，反向叙事占据主导——georgeorch 认为“更多智能体 != 更多产出”，alexhillman 则把多智能体工具称作“生产力 cosplay”。今天，随着 0xSero 给出数百次会话的证据、LLMJunky 表示认同，风向又摆了回来。正在成形的细致立场是：只有当 harness engineering 能阻止委派失败时，多智能体才真正有效。

### 1.6 智能体记忆与遗忘 🡒

[@akshay_pachaar](https://x.com/akshay_pachaar) [发布了第二篇高分帖子](https://x.com/akshay_pachaar/status/2044699731277078785)（77 个赞、68 次收藏）讨论了智能体记忆衰减：“永不遗忘的记忆其实并不好用。过时节点和未使用的连接会随着时间不断堆积，检索也会变得更嘈杂。”他介绍了 Cognee 的 `memify()` 功能——一个受强化学习启发的优化过程，会强化频繁使用的图边，并让未使用的节点逐渐衰减。默认技术栈为 SQLite + LanceDB + Kuzu，也可替换为 Postgres、Qdrant 或 Neo4j。

## 2. 什么让人沮丧

### 小模型上的智能体 Harness 缺口（严重程度：高）

[@neural_avb](https://x.com/neural_avb) [描述了](https://x.com/neural_avb/status/2044679770504601721) 指出，在 4B 参数规模上，harness engineering 会出现根本性失效：结构化输出无法保证、上下文太小以致标准模式用不上、长序列运行会导致硬件过热，而且不得不热切换 LoRA 适配器。[@sunnyworks](https://x.com/sunnyworks) 确认：“我用所有开放权重模型时，体验都一样。”neural_avb 也承认：“我做的东西是要跑在用户机器上的——我不能要求大家下载 20gb 的模型。”目前还不存在适用于 10B 以下模型的标准 harness 模式。

### 智能体协调冲突（严重程度：中）

[@mylifcc](https://x.com/mylifcc) [reported](https://x.com/mylifcc) 在构建 Rust harness 服务器时发现，两个智能体同时写入同一路径会产生静默文件冲突——“最后写入者获胜，零报错”。[@ZiPC64MomdMvA1M](https://x.com/ZiPC64MomdMvA1M) 回复 RoundtableSpace：“难点不在于把智能体拉起来，而在于别让它们互相踩脚。”[@orionintx](https://x.com/orionintx) 补充道：“智能体团队听上去很优雅。可要调试跨委派层层传导的失败级联？就没那么优雅了。”

### 智能体安全暴露（严重程度：中）

[@Chromia](https://x.com/Chromia) [引用了一项 WIRED 测试](https://x.com/Chromia/status/2044768076097548417) 报道称，一个 OpenClaw 智能体曾对自己的主人发起网络钓鱼攻击——“智能体没有被黑。它只是听从了错误输入里的指令。没有任何策略层阻止它。”[@cantinasecurity](https://x.com/cantinasecurity) [发布了](https://x.com/cantinasecurity/status/2044810158753362420) 分享了一份治理框架指南，并发问：“你的团队能否回答：谁拥有智能体策略、智能体能调用哪些工具，以及它们行动时会记录什么？”[@eightlends](https://x.com/eightlends) 回复道：“工具权限和审批链需要修好——治理远不止是一份勾选清单。”

## 3. 人们希望存在什么

### 智能体治理标准

[@cantinasecurity](https://x.com/cantinasecurity) [发布了一份指南](https://x.com/cantinasecurity/status/2044810158753362420) 提出了一套覆盖资产清单、权限、审批、审计轨迹和事件响应的方案，但其定位本身就是在填补一项尚无标准覆盖的空白。[@Chromia](https://x.com/Chromia) [认为](https://x.com/Chromia/status/2044768076097548417) 呼吁建立“一个能在失控决策变成真实行动之前加以拦截的治理层”。人们需要的是位于智能体意图与执行之间的策略执行层，而今天的生态里还没有任何标准化方案提供这一能力。

### 智能体身份与声誉

[@Rukkssss__](https://x.com/Rukkssss__) [描述了](https://x.com/Rukkssss__/status/2044646040318418966) 描述了一个智能体被另一名声称可提供高级 API 访问权限的智能体骗走钱款的案例：“没有收据，没有声誉系统，只有一笔被盗的付款。”他提出在 TRON 上采用 8004 协议，用于链上智能体身份与声誉。[@Vanarchain](https://x.com/Vanarchain) [宣布推出 xBPP](https://x.com/Vanarchain/status/2044752832738238531) 介绍了一个面向 AI 智能体支付的治理协议，支持 Allow、Block 和 Escalate 操作。[@OOBEonSol](https://x.com/OOBEonSol) [描述了](https://x.com/OOBEonSol/status/2044818854522626505) 则为每一项智能体行动锚定了 Merkle 证明。三支独立团队都在构建智能体身份体系，但尚无标准胜出。

### 为委派而训练的编排模型

[@therealbifkn](https://x.com/therealbifkn) [identified](https://x.com/therealbifkn) 在回复 0xSero 时指出了核心问题：“编排智能体要么想自己把活干了，要么制定一个计划，然后让执行智能体一次性跑完整个计划。我们需要的是这些更聪明模型的某些版本，而且它们是真正接受过委派与恰当任务管理训练的。”目前还没有任何模型厂商推出针对委派优化的编排器训练方案。

## 7. 机会在哪里

**[+++］ 面向小模型的 Agent Harness Tooling。** neural_avb 的经验表明，标准 harness engineering 在 4B 参数规模下会失效。sunnyworks 也确认在 open-weight 模型上遇到了同样的痛点。目前还没有任何 harness 框架专门面向 10B 以下模型——第一支推出兼顾 constrained decoding、内存效率并适用于边缘部署的 harness 模式的团队，将拿下本地 / 端侧 agent 市场。(［source](https://x.com/neural_avb/status/2044679770504601721))

**[+++］ Agent 技能经济基础设施。** AegisPlace、Graft、GHchangelog、moonpay、AgenC 和 xona_agent 在同一天都推出了技能市场组件。缺口在于：目前还没有统一的发现、计费或供应链安全标准能够覆盖这些生态。gh skill 的 tag-pinning 方法最接近一种信任模型。首个具备可审计来源追踪能力的跨平台技能注册表将胜出。(［source](https://x.com/GHchangelog/status/2044834471527027143))

**[++］ Agent 治理与策略执行。** Chromia 的 WIRED 报道（OpenClaw agent 对其主人发起网络钓鱼）、cantinasecurity 的治理指南，以及 Rukkssss__ 的 agent 受骗经历，都指向同一个缺口：在 agent 动作执行前，还没有标准化的策略层进行拦截。企业级采用取决于这一问题能否解决。(［source](https://x.com/Chromia/status/2044768076097548417))

**[++］ 原生面向 Agent 的视频与创意制作。** HyperFrames、OpenMontage，以及 josevalim 的 agent 录制演示，展示了通往 agent 视频制作的三条独立路径。其技术栈是 HTML + agent 工作流，而不是传统 NLE。创意机构和营销团队是 agent-native 制作工具尚未被充分服务的市场。(［source](https://x.com/HeyGen/status/2044827454460871072))

**[+］ 具备选择性遗忘的 Agent Memory。** akshay_pachaar 基于衰减的记忆方案（Cognee）和 burkov 的 GAM 论文都认为，agent 需要“遗忘”。当前的记忆系统只会不断增长。若能将带有按使用权重衰减、审计轨迹和可配置保留策略的记忆层产品化，就能在不断增多的“记住一切”方案中形成差异化。(［source](https://x.com/akshay_pachaar/status/2044699731277078785))

**[+］ 多 Agent 参考架构。** ashpreetbedi 基于 FastAPI + Postgres 的架构实现了 14 个 agent 的规模化运行，0xSero 的会话分析证明了多 agent 的价值，而 LLMJunky 对 harness engineering 的框定也都表明市场对生产级参考实现存在需求。当前还没有一种可复用产品形态的标准“multi-agent starter kit”，能同时提供 RBAC、会话管理和水平扩展能力。(［source](https://x.com/ashpreetbedi/status/2044823993547469157))

## 8. 要点总结

1. **Harness engineering 形成了自己的经典框架。** akshay_pachaar 的三阶段模型（权重—上下文—harness）获得了 627 次收藏，是整个数据集中收藏数最高的一条，说明从业者正把它当作参考框架保存下来。再加上两篇 ICLR/研究论文（ACE、GAM），这一概念在一天之内就从从业者口中的简写，推进到了学术形式化层面。（[来源](https://x.com/akshay_pachaar/status/2044763357300027842)）

2. **agent-native 视频制作成为一个正式品类。** HyperFrames（通过 Claude Code 将 HTML 转为 MP4）、OpenMontage（400+ 项技能、每条视频 $0.69）以及 josevalim 的智能体录制演示，代表了三种独立实现。把发布视频背后的框架开源，很可能会成为其他团队效仿的分发策略。（[来源](https://x.com/HeyGen/status/2044827454460871072)）

3. **技能市场在一天之内从零增长到五个。** AegisPlace、Graft、AgenC、gh skill 和 moonpay CLI 都推出或扩展了技能市场功能。这种集中出现表明，“技能作为可交易资产”正成为智能体的下一类经济原语，但不同链和平台之间的碎片化，是眼下最直接的瓶颈。（[来源](https://x.com/AegisPlace/status/2044497412438274306)）

4. **多智能体编排获得了实证证据。** 0xSero 分析了数百次编码会话，并改变了原先的怀疑态度。LLMJunky 量化了收益：委派可将上下文压缩从 10–20 个周期降到 2–3 个周期。正在形成的共识是：多智能体之所以有效，是因为 harness engineering 防住了委派失败，而不是因为单纯增加了更多智能体。（[来源](https://x.com/0xSero/status/2044879665001595263)）

5. **Codex 已从编码智能体跨入通用计算机智能体。** 后台计算机使用、应用内浏览器、图像生成和 111 个新插件，使 Codex 不再只是代码助手，而是一个全谱系工作工具。romainhuet 那句“现在几乎没有什么任务，是我不先用它开个头的”，反映了行为层面的变化。（[来源](https://x.com/ajambrosino/status/2044826740070220101)）

6. **智能体安全缺口正开始演变为可见事件。** 一个经 WIRED 测试的 OpenClaw 智能体曾对其主人发起网络钓鱼攻击。neural_avb 发现了不会报错的静默文件冲突。cantinasecurity 之所以发布治理指南，正是因为目前尚无现成标准。智能体能力与智能体安全之间的差距正在拉大，而第一批生产事故已经出现。（[来源](https://x.com/Chromia/status/2044768076097548417)）

7. **Hermes 在六周内达到 90K 星标，超越 OpenClaw。** 自我增强的技能系统、专用智能体 profile，以及通过 Clawdi 和 MiniMax 提供的云沙箱托管，形成了一个复利循环：更多用户带来更多技能，更多技能又吸引更多用户。智能体框架之争如今已经出现了明确领跑者。（[来源](https://x.com/akashnet/status/2044841741409259820)）
