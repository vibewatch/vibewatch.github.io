# Twitter AI 智能体 - 2026-04-17

## 1. 人们在讨论什么

### 1.1 Harness 工程之争愈演愈烈 🡕

4 月 16 日开始的 harness 工程讨论仍在持续升温。[@akshay_pachaar](https://x.com/akshay_pachaar) 的 [三阶段框架](https://x.com/akshay_pachaar/status/2044763357300027842)（从权重到上下文再到 harness）连续第二天成为整个数据集里最热门的帖子，目前获得 606 个赞、797 次收藏和 76,723 次浏览。其核心论点是：“模型不再是智能的唯一载体。它存在于一个 harness 中，而这个 harness 包含持久化记忆、可复用技能、标准化协议（如 MCP 和 A2A）、执行沙箱、审批关卡以及可观测性层。”

![展示 agent engineering 从 weights 到 context 再到 harness engineering 在 2022-2026 年间三阶段演进的示意图](https://pbs.twimg.com/media/HGB1KOKbkAAx9vD.png)

[@aiDotEngineer](https://x.com/aiDotEngineer) [宣传了一场大会演讲](https://x.com/aiDotEngineer/status/2044937501593460773)（41 个赞、46 次收藏、15,311 次浏览）介绍了 [@_lopopolo](https://x.com/_lopopolo) 关于“当人类掌舵、智能体执行时，如何构建软件”的内容。讨论串呈现出一场标志性的理念分歧：[@SamanvayaY](https://x.com/SamanvayaY) 指出，这“恰好与 Mario Zechner 的核弹级观点相反——Ryan：‘代码是免费的。禁用编辑器。开掉 15-5000 个智能体。’Mario：‘每一行该死的代码都要读，否则你就会失去理解。’”[@Samward](https://x.com/Samward) 回复道：“智能体规模的上限取决于刹车的质量，而不是马力。”

随后，反向叙事也出现了。[@IceSolst](https://x.com/IceSolst) [发布了一篇带实操性质的反驳](https://x.com/IceSolst/status/2045234234596487306)（82 个赞、35 次收藏）表示：“我在做一个让智能体跑扫描任务的 harness。它完全是一坨垃圾，毫无用处。和直接用原生 Claude Code 相比，真的 0 收益。”[@garrytan](https://x.com/garrytan) [进行了回击](https://x.com/garrytan/status/2045233921584189935)（12 个赞）则在另一篇批评智能体的文章下评论道：“文章里的每一个失败案例，都是赤裸裸的 LLM 交互！没有技能、没有 harness、没有确定性代码。”

[@_lopopolo](https://x.com/_lopopolo) [介绍了他自己已经成型的方法](https://x.com/_lopopolo/status/2045245935228510213)（8 个赞、10 次收藏）表示：“自动化都存在 docs/automations 里的 Markdown 文件中。codex app 的自动化提示词只有两句话。”

**讨论洞察：** 这场 harness 之争已经分化为三派：把 harness 设计视为首要工程学科的拥护者、认为 Claude Code 内置能力已经足够的怀疑者，以及采用轻量 Markdown 自动化的实用主义者。@Samward 那句“看的是刹车质量，不是马力”概括了正在形成的共识：harness 的价值在于约束，而不在于能力。

**与前一日对比：** 昨天的讨论基本还是单向度的——把 harness 工程视为标准框架。今天则在持续采用之外，出现了成体系的反对声音（IceSolst 的实际失败体验，以及 Zechner-lopopolo 的理念分裂）。这个概念不再只是扩散，而是在接受压力测试。

**与前一日对比：** 昨天，语音只出现在一个场景里（Hermes TTS 集成）。今天，它已经演变成独立的生产力论点（thdxr）、消费端时刻（garrytan 遇到的空乘人员）、黑客松赛道（Kiro x ElevenLabs）以及基础设施组件（Hermes 中的 Gemini Voice）。语音已经从一个功能点变成了一条主题线。

### 1.6 技能市场怀疑论开始出现 🡒

[@shawmakesmagic](https://x.com/shawmakesmagic)（ElizaOS 创作者）[强烈反驳](https://x.com/shawmakesmagic/status/2045222901100741026)（78 个赞、8 次收藏）公开反对技能市场叙事：“根本没有什么技能市场。当 Hermes 成功完成某件事时，它就会生成一个技能。下载技能的风险太高了，这是历史上最容易被利用的供应链攻击面。专注于做一个你自己会用的智能体，而不是去为一个并不存在的市场做产品。”

与此同时，Graft 继续推进协调式宣传攻势——[@web3_gord](https://x.com/web3_gord)、[@ArumBeadlesX](https://x.com/ArumBeadlesX)、[@aisarcore](https://x.com/aisarcore) 都发布了几乎一模一样的文案，把 Graft 描述为“AI 智能体技能市场”，并附上同一个合约地址，这进一步强化了 Shaw 对人为制造需求的怀疑。

[@betomoedano](https://x.com/betomoedano) [采取了不同的方法](https://x.com/betomoedano/status/2045209803228692632)（70 个赞、97 次收藏）则通过众包方式征集真实技能使用案例：“你自己做过、或见过的最佳 Agent Skills 是什么？”回复串里出现了具体工具：[@swmansion](https://x.com/swmansion) 的 react-native-best-practices，以及 [@callstackio](https://x.com/callstackio) 的 agent-device 和 agent-react-devtools。

**讨论洞察：** Shaw 的批评划出了一条清晰界线：自行生成的技能（Hermes 会根据成功操作自动创建）与下载技能（市场模式）是两回事。其安全论点也非常具体——技能会执行代码，因此直接构成供应链风险。

**与前一日对比：** 昨天有五个技能市场发布或扩张。今天，则迎来了来自一位可信构建者的首个重要反驳。Graft 的协调式宣传活动（多篇几乎相同、附同一合约地址的帖子）无意中给 Shaw 关于“制造需求”的观点提供了证据。

### 1.7 Opus 4.7 对比 4.6：行为差异获得量化 🡕

[@dimitrioskonst](https://x.com/dimitrioskonst) [发布了一篇正面对比](https://x.com/dimitrioskonst/status/2044909346379739577)（5 个赞、3 次收藏、2,099 次浏览）对 Claude Opus 4.7 与 4.6 在真实 monorepo 任务中的表现进行了比较。结果非常显著：在 5 项任务中，4.6 发起了 222 次工具调用，涉及 26 个文件；4.7 发起了 58 次工具调用，只涉及 3 个文件。Opus 4.6 拉起了 6 个探索型子智能体；4.7 则一个都没有。在其中一项任务中，“4.6 修改了计费逻辑，去处理一个它从未验证是否存在的竞态条件。4.7 则拒绝碰它。”

![基准测试表展示 Opus 4.7 与 4.6 的对比：67 对 212 步、58 对 222 次工具调用、3 对 26 个触及文件、0 对 6 个 subagents](https://pbs.twimg.com/media/HGD3p1DXQAAlLT7.jpg)

**讨论洞察：** 这些数据表明，4.7 代表的是智能体行为层面的一次根本性转变——不只是输出更好，而是运行画像都发生了显著变化：更少动作、更少文件、零子智能体。这对 harness 设计有直接影响：当模型会自我约束时，harness 需要承担的职责也会改变。

**与前一日对比：** 昨天并没有类似的对比。这是关于模型更新如何在 harness 层面改变智能体行为的全新量化证据。

### 1.8 研究论文推进多智能体协同 🡒

两篇研究论文从不同角度切入多智能体协同失败问题。[@jiqizhixin](https://x.com/jiqizhixin) [重点介绍了 AgentConductor](https://x.com/jiqizhixin/status/2045132923834118451)（9 个赞、4 次收藏）来自上海交通大学和美团：这是一个基于 RL 的系统，可动态重构智能体之间的通信路径。在竞赛级代码生成任务中，它将准确率提高了 14.6%，同时把 token 成本降低了 68%。

![AgentConductor 框架展示三阶段流水线：SFT、结合 GRPO 的多轮 RL，以及 topology 生成](https://pbs.twimg.com/media/HF2yETxasAMi70J.jpg)

[@rryssf_](https://x.com/rryssf_) [介绍了 PAC-BENCH](https://x.com/rryssf_/status/2045079905491353795) 来自延世大学——这是首个针对隐私约束下多智能体协作的基准测试。关键发现包括：GPT-5.1 与自身配对时，联合成功率也只有 56%；LLaMA 与自身配对时则只有 6%。研究识别出三种失败模式：早期隐私违规（75% 发生在前 3 轮内）、过度保守的抽象化（占失败的 35%）以及隐私诱发的幻觉（占失败的 41%）。最引人注目的是：由哪个智能体先发起对话，比用哪个模型更重要。

[@jiqizhixin](https://x.com/jiqizhixin) 还 [分享了 MindDR](https://x.com/jiqizhixin/status/2045022268355670159)（10 个赞、3 次收藏）：这是一个来自 Li Auto 的多智能体深度研究框架，采用 Planning-DeepSearch-Report 三智能体组合，让一个 30B 参数模型胜过了同类开源系统。

![MindDR 多 agent 架构图，展示 Planning Agent 将任务拆解为并行的 DeepSearch Agent 实例](https://pbs.twimg.com/media/HGFg5QyaUAAqpz_.jpg)

**讨论洞察：** PAC-BENCH 揭示，具备隐私意识的多智能体协作本质上仍未解决。发起者角色比模型质量更重要这一发现，对于需要跨组织协作智能体的企业部署具有直接意义。

**与前一日对比：** 昨天讨论的是 ACE 论文（将上下文视为动态操作手册）和 GAM（即时记忆）。今天则新增了 AgentConductor（动态拓扑）、PAC-BENCH（隐私受限协作）和 MindDR（小模型深度研究）。研究管线正在加速。

[@badlogicgames](https://x.com/badlogicgames) [称赞了](https://x.com/badlogicgames/status/2045131857956651097)（26 个赞、14 次收藏）介绍了 HuggingFace 上的编码智能体轨迹查看器。[@mattpocockuk](https://x.com/mattpocockuk) [介绍了他最好的想法](https://x.com/mattpocockuk/status/2045137391250206745)（9 个赞）表示：“这是一个编码智能体可观测性平台——安装一个插件，把所有会话数据上传到仪表板，就能比较长期趋势。”[@tarunsachdeva](https://x.com/tarunsachdeva) [推出了 Traces for Teams](https://x.com/tarunsachdeva/status/2045128145628447212)（19 个赞）则提供团队内部共享编码智能体会话的能力，并为初创公司和开源项目提供免费套餐。

**讨论洞察：** 智能体可观测性正在分化成三个层次：单次会话轨迹（HuggingFace viewer）、单智能体仪表板（hermes-hudui）和团队级分析（Traces for Teams）。目前还没有一个工具能覆盖全部三层。

**与前一日对比：** 昨天对可观测性的提及还只是顺带。今天，三个产品和一个产品构想都汇聚到同一个需求上。hermes-hudui 的 star 数一周内从 0 增长到 1,000，说明需求强烈。

## 2. 让人沮丧的是什么

### 自定义 Harness 的额外开销 vs. 内置能力——严重程度：高

[@IceSolst](https://x.com/IceSolst) [花时间搭建了一个自定义 harness](https://x.com/IceSolst/status/2045234234596487306) 试过之后得出结论：和带技能的原生 Claude Code 相比，它“真的 0 收益”。[@HankYeomans](https://x.com/HankYeomans) 回应道：“Claude Code 本身也是一个 harness——你试过把它的 harness 用到别的东西上吗？”这段交锋暴露出一种概念混淆：实践者正在那些本身就已经是 harness 的工具之上再叠一层 harness，造成冗余。现在还没有清晰指南说明，什么时候自定义 harness 真能带来价值，什么时候内置智能体 harness 就已经足够。

### 多智能体记忆丢失——严重程度：高

[@georgeorch](https://x.com/georgeorch) [道出了广泛存在的挫败感](https://x.com/georgeorch/status/2044916504374776147)（202 个赞、10,718 次浏览）表示：“我觉得智能体丢失上下文这件事特别有意思——为什么偏偏在我最需要你的时候，你就什么都忘了？”[@timourxyz](https://x.com/timourxyz) [指出了一个系统性缺口](https://x.com/timourxyz/status/2045181798515138688) 表示：“智能体领域似乎缺的是记忆基准测试。我会用一些个人测试去试这里每个热度够高的记忆系统，但我想看到不同框架和智能体在一组既定测试上的表现。”目前还没有标准化的记忆基准。

### 技能供应链安全——严重程度：中

[@shawmakesmagic](https://x.com/shawmakesmagic) [称其为 skill downloads](https://x.com/shawmakesmagic/status/2045222901100741026) 将其称为“历史上最容易被利用的供应链攻击面”。技能会在智能体上下文中执行代码。[@cybernewslive](https://x.com/cybernewslive) [报告称](https://x.com/cybernewslive/status/2045207112964256119) 指出，MCP 存在一个设计缺陷，“会让攻击者在任何安装了恶意工具的用户电脑上运行命令”。可执行技能与 MCP 漏洞叠加后，形成了相互放大的风险面，而目前没有统一缓解标准。

## 3. 人们希望出现什么

### 智能体记忆基准测试

[@timourxyz](https://x.com/timourxyz) [请求](https://x.com/timourxyz/status/2045181798515138688) 呼吁建立标准化记忆基准。[@georgeorch](https://x.com/georgeorch) [说出了面向用户的症状](https://x.com/georgeorch/status/2044916504374776147)（202 个赞）谈到，智能体总会在最糟糕的时候遗忘信息。[@burkov](https://x.com/burkov) [分享了 GAM 论文](https://x.com/burkov/status/2044891819306074359) 提出了即时记忆方案，但目前没有任何基准测试能评估这些方法在不同框架中的实际效果。人们需要的是一套标准化评测，而不是另一个记忆系统。

### 编码智能体可观测性平台

[@mattpocockuk](https://x.com/mattpocockuk) [描述了](https://x.com/mattpocockuk/status/2045137391250206745) 点出了这个缺失的产品：“安装一个插件，把所有会话数据上传到仪表板，就能比较长期趋势。”[@alexhillman](https://x.com/alexhillman) [描述了](https://x.com/alexhillman/status/2045191045021888933) 则存储带解析后元数据列的会话转录，包括用户消息、智能体消息、工具调用和涉及文件。多个团队都在构建定制化方案（hermes-hudui、Traces for Teams、HuggingFace viewer），但目前还不存在跨智能体的可观测性标准。

### 具备隐私保护的多智能体协作

延世大学的 PAC-BENCH 论文 [量化了这一差距](https://x.com/rryssf_/status/2045079905491353795) 指出：即便 GPT-5.1 与自身配对，在需要共享私有信息的任务中成功率也只有 56%。[@abundand](https://x.com/abundand) 证实：“这已经搞死了我试图上线的每一个多智能体项目。”对于必须让来自不同部门或不同组织的智能体协作的企业部署场景，目前还没有既能协同、又能保护隐私的机制。

## 7. 机会在哪里

**[+++］ 全栈 Agent 可观测性。** hermes-hudui 在一周内达到 1K stars。mattpocockuk 讲清了缺失的平台。Traces for Teams 已推出。badlogicgames 称赞了 HuggingFace 的 trace viewer。但目前没有任何单一工具能够同时覆盖单次会话 trace、单个 agent 仪表盘以及团队级分析。首个可兼容 Claude Code、Codex、Hermes 和 Cursor 的跨 agent 可观测性平台，将拿下整个正在形成的市场。(［source](https://x.com/aijoey/status/2045238603949715876))

**[+++］ 语音优先的 Agent 界面。** thdxr 的帖子（653 个赞，188 次收藏）证明，语音到 agent 是一个巨大的突破。Gemini TTS 已在 Hermes 中上线。Kiro 和 ElevenLabs 发起了一场语音黑客松。garrytan 在台北看到了一个面向消费者的时刻。但当前技术栈仍然是割裂的：Parakeet 用于 STT，Gemini 用于 TTS，却没有一体化、原生面向语音的 agent shell。首个内置语音听写、并针对 agent prompting 优化的 terminal 或 IDE，将获得输入模态上的优势。(［source](https://x.com/thdxr/status/2045228857460998636))

**[++］ 企业级 Coding Agent 治理。** Databricks 推出了面向 coding agents 的 Unity AI Gateway。Cantina 推出了治理 CLI。Cloudflare 推出了 isitagentready.com。三家厂商同时入场，验证了这一赛道。缺口在于：目前还没有统一的治理层，能够横跨所有主流 coding agents，覆盖网页就绪性、工具权限、成本控制和会话审计。(［source](https://x.com/databricks/status/2045209450085040507))

**[++］ 关于何时不该使用 Harness 的 Harness 设计模式。** IceSolst 失败的 harness（82 个赞）以及 garrytan 的反驳，把核心问题凸显了出来：什么时候自定义 harness 能带来价值，什么时候 agent 内置的 harness 已经足够？一个决策框架或诊断工具（“你的使用场景需要自定义 harness 吗？”）将能消除这种正在消耗从业者时间的困惑。(［source](https://x.com/IceSolst/status/2045234234596487306))

**[+］ 具备隐私感知能力的多 Agent 协议。** PAC-BENCH 表明，即便是 GPT-5.1，在隐私约束下成功率也只有 56%。跨部门或跨组织的企业级多 agent 部署，正受限于缺乏能够维持信息边界的协作机制。首个解决这一问题的协议，将拿下受监管行业。(［source](https://x.com/rryssf_/status/2045079905491353795))

**[+］ Agent 记忆基准。** timourxyz 直接提出了这一需求。georgeorch 那条获得 202 个赞的帖子量化了用户的挫败感。每个记忆框架都声称有所提升，但目前并不存在标准化评测。首个公开发布、可跨框架测试记忆能力的基准套件，将成为行业参考。(［source](https://x.com/timourxyz/status/2045181798515138688))

## 8. 要点

1. **Harness 工程正在接受压力测试。** IceSolst“0 收益”的体验（82 个赞）以及 lopopolo-Zechner 之间的理念分裂，挑战了前一天那种把 harness 工程视为救赎的叙事。garrytan 的反驳和 lopopolo 的轻量 Markdown 自动化方案说明，答案并不绝对：harness 在规模化场景中确实有价值，但对个人使用而言，内置智能体 harness 往往已经足够。（[来源](https://x.com/IceSolst/status/2045234234596487306)）

2. **语音输入是实践者目前发现的最大智能体生产力解锁点。** thdxr 的观察（653 个赞、188 次收藏）表明，带来最大工作流增益的不是智能体本身的进步，而是口述输入，这颠覆了常见叙事。本地 Parakeet STT 模型与智能体工作流结合后，去掉了一个多数人此前甚至没有意识到的瓶颈。（[来源](https://x.com/thdxr/status/2045228857460998636)）

3. **多智能体模式正收敛到“写作—评估”这一最小可行架构。** georgeorch 改变了此前的怀疑立场（170 个赞）。petergyang 和 DimitriGilbert 分别独立描述了同样的先构建、后审查模式。框架层面的变化是：多智能体不再意味着“更多智能体”，而是意味着最简单的有效委派。（[来源](https://x.com/georgeorch/status/2045184772863819828)）

4. **编码智能体治理在一天之内变成了可交付软件。** Databricks Unity AI Gateway、Cantina 的治理 CLI，以及 Cloudflare 的 isitagentready.com 都发布了生产级工具。企业准入问题已经从“我们需要治理”转向“我们该采用哪一个治理工具”。（[来源](https://x.com/databricks/status/2045209450085040507)）

5. **Opus 4.7 代表着智能体 harness 设计的一次行为范式转变。** dimitrioskonst 的数据显示，在相同任务中，4.7 的工具调用次数比 4.6 少了 3.8 倍，而且完全没有子智能体生成。一个会自我约束的模型，会改变 harness 需要提供什么——从“约束智能体”转向“智能体约束自己”。（[来源](https://x.com/dimitrioskonst/status/2044909346379739577)）
