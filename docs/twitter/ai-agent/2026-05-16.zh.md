# Twitter AI Agent - 2026-05-16

## 1. 大家在讨论什么

### 1.1 Harness 工程正变成可度量的运营工作 🡕

Harness 工程仍是核心话题，但支撑这一话题的证据形态已经变了。相比那种泛泛而谈“智能体需要更好的脚手架”的观点，最有分量的帖子开始聚焦于具体的可观测性层、清晰的框架映射、团队成本仪表盘，以及运行长期存续 harness 的经济账。至少有六条内容扎实的帖子支撑了这一主题，甚至连玩笑都不再围绕提示词，而是转向了嵌套控制循环。

[@IntuitMachine](https://x.com/IntuitMachine) [总结道](https://x.com/IntuitMachine/status/2055244573463527814)（19 个赞、2 条回复、1,392 次浏览、32 次收藏）发布了 [Agentic Harness Engineering 论文](https://arxiv.org/abs/2604.25850)，称经过十轮由可观测性驱动的 harness 编辑，Terminal-Bench 2 的 pass@1 从 69.7% 提升到 77.0%，并且这一改进还迁移到了 SWE-bench-verified，同时 token 用量减少了 12%。推文中的摘要截图也明确点出了论文的核心主张：真正带来提升的不是新的基础模型，而是对组件、经验和决策的可观测性。

![Agentic Harness Engineering 的摘要截图，展示了三层可观测性以及 Terminal-Bench 2 从 69.7% 提升到 77.0%](https://pbs.twimg.com/media/HIWx3WCWAAALcA2.png)

[@IntuitMachine](https://x.com/IntuitMachine) [关于 Sylph AI 的 harness-evolution 论文](https://x.com/IntuitMachine/status/2055245758727700646) 的配套线程（38 个赞、2 条回复、1,250 次浏览、37 次收藏）也在推动同一方向：Worker、Evaluator 和 Evolution 智能体会自动重写 harness，而元进化循环则学习如何把这种模式适配到新领域。相关的公开成果是 [你将构建的最后一个 Harness](https://arxiv.org/abs/2604.21003)，这让当天的讨论不再像是“放大版的提示词工程”，而更像是自动化运行时工程的开端。

[@FUCORY](https://x.com/FUCORY) [认为](https://x.com/FUCORY/status/2055675961195089964)（78 个赞、5 条回复、9,629 次浏览、82 次收藏）表示，Bun 的重写是 harness 工程目前最好的在线实例之一，因为这项工作的重点本质上是长期运行的工作流设计，而不只是 LLM 输出质量。那张配图之所以重要，是因为它把 Bun 的 harness 概念与 Smithers 原语一一对应起来；而回复区又补上了基准测试讨论里少见的细节：用于内存管理的生命周期分类器，以及刻意设计的背压机制。

[@valentinmihov](https://x.com/valentinmihov) [报道](https://x.com/valentinmihov/status/2055708681065402566)（13 个赞、5 条回复、867 次浏览）表示，他所在团队的 harness 结合了 Multica 看板、运行在 Codex 上的 Hermes Agent、Hindsight 记忆系统、自定义技能、内部监控、OAuth2 SSO，以及由 Git 管理的基础设施。他说，这套配置消耗了大约 600 million tokens，API 成本约为 $3,000；相比之下，他估计同样的事情若靠 DevOps 来做，大概要花两个月。这让“智能体式工程”从抽象模式变成了明确的运维预算。

![一个看板式摘要，展示内部 agentic engineering harness 的 Kanban 计数、约 6 亿 tokens、约 3000 美元的 API 成本，以及快 8 倍的说法](https://pbs.twimg.com/media/HIdYJcDXEAAv_-g.jpg)

**讨论洞察：** [@BenjDicken](https://x.com/BenjDicken) [记录了](https://x.com/BenjDicken/status/2055287231322185959)（583 个赞、22 条回复、19,613 次浏览、150 次收藏）用“智能体 → while 循环子智能体 → 嵌套 while 循环智能体 harness”这句话概括了 2026 年的工程现实。这个玩笑之所以奏效，正因为它贴合了那些严肃帖子的共同主题：更多循环、更多记忆策略、更多编排层，也就意味着更多丢失可观测性的机会。

**与前一天的对比：** 5 月 15 日，人们还主要通过架构图、可观测性论文和参考课程来理解 harness。到了 5 月 16 日，讨论依旧火热，但已经进一步深入到可测量的改变量、框架映射，以及团队层面的成本与技术栈披露。

### 1.3 身份与治理成为智能体商业的难点 🡕

关于商业化的讨论，已经从简单的市场发现转向缺失的信任层。最有分量的内容都在谈智能体身份、同意边界、可审计性，以及当智能体开始真实地进行交易或相互调用技能时，工作该如何结算。

[@felix_fan](https://x.com/felix_fan) [写道](https://x.com/felix_fan/status/2055529244869231072) 称（59 个赞、15 条回复、5,627 次浏览），Trust Wallet 正在沿两条路线推进：一条是面向开发者侧，用 Agent Kit 加上 EIP-8004 构建链上智能体身份；另一条则是面向消费者，仍由用户持有密钥，并在每一步都给出同意。[Cryptobriefing](https://cryptobriefing.com/ai-crypto-wallets-consensus-miami/) 和 [PYMNTS](https://www.pymnts.com/cryptocurrency/2026/crypto-wallets-just-got-rebuilt-for-a-world-run-by-ai/) 的公开报道也用文字呈现了同样的分野：一边是更自主的钱包和转账，另一边则是会话上限、防护措施和责任归属问题。

[@sijlalhussain](https://x.com/sijlalhussain) [认为](https://x.com/sijlalhussain/status/2055650038127157707)（12 个赞、1 条回复、301 次浏览）认为，智能体商业中的信任问题，本质上是运营治理架构问题，而不是品牌问题。他分享的图片比推文本身更有价值，因为它把问题提炼成五项具体要求——身份验证、人类监督、透明度、数据安全，以及可追责的治理。

![源自 McKinsey 的 agentic commerce 信任框架，展示了身份验证、人工监督、透明度、数据安全和问责治理](https://pbs.twimg.com/media/HIci0OBXoAMUA5B.jpg)

[@Unibase_AI](https://x.com/Unibase_AI) [宣布](https://x.com/Unibase_AI/status/2055631252779409519)（19 个赞、75 条回复、101 次引用、31,573 次浏览）提到 Flap 进入 BitAgent 的 ERC-8183 市场，提供跨多条链的自主代币发行技能。最有用的证据并不在主帖，而是在点赞最高的回复里：可组合的技能调用仍然需要托管、交付物哈希和评估者结算，真实工作才能完成结算，这也说明在热潮之下，市场底层基础设施仍有大量缺口。**讨论洞察：** 这也是当天分歧最鲜明的一组讨论。看多的市场类帖子一直在强调可发现、可组合的技能；批评性的回复则不断把话题拉回到同意、归属、托管，以及当智能体完成——或未能完成——一项付费任务时，究竟该由谁拍板。

**与前一天对比：** 5 月 15 日关注的是智能体如何注册、发现服务，以及如何按次调用付费。5 月 16 日则补上了这套流程之下更棘手的问题：智能体到底是谁、继承了什么权限、活动如何审计，以及市场中的工作最终究竟如何结算。

## 2. 什么最让人沮丧

### Harness 层的构建和调试成本依然过高

最严重的挫败点在于，在模型能够被信任去执行长任务之前，要做出可靠的智能体，仍然需要大量 harness 工作。[@IntuitMachine](https://x.com/IntuitMachine) [总结道](https://x.com/IntuitMachine/status/2055244573463527814)（19 个赞、2 条回复、1,392 次浏览、32 个收藏）把 AHE 论文视为对 harness 组件纠缠、轨迹噪声过大，以及编辑到底是帮了忙还是添了乱却难以归因这些问题的回应。[@valentinmihov](https://x.com/valentinmihov) [报道](https://x.com/valentinmihov/status/2055708681065402566)（13 个赞、5 条回复、867 次浏览）表示，就算有 AI 加速，他们团队搭自己的 harness 仍花了大约 6 亿个 token 和约 $3,000 的 API 成本。[@BenjDicken](https://x.com/BenjDicken) [转向了](https://x.com/BenjDicken/status/2055287231322185959)（583 个赞、22 条回复、19,613 次浏览、150 个收藏）则把这种运维层面的蔓延变成了当天最具代表性的笑话：嵌套的智能体循环，而这也正是它能引发共鸣的原因。严重程度：高。眼下看得见的解决办法，不是把提示词写得更简单，而是把 harness 结构做得更明确——加入记忆分类器、批评器、映射和审计层。值得投入建设，因为即便是能力很强的一线操作者，发帖时也仍然把这类系统描述得既昂贵又脆弱。

### 智能体仍然缺乏自己的身份、责任和结算边界

第二个高严重度问题是，智能体执行时继承了太多人类身份，却几乎没有足够明确、面向智能体本身的问责边界。[@pvergadia](https://x.com/pvergadia) [警告](https://x.com/pvergadia/status/2055487369449754843)（7 个赞、7 条回复、1,094 次浏览）指出，10 个智能体完全可能都跑在同一组长期有效的凭证之下，却根本无法分辨到底是哪一个执行了动作；该帖还引用了 1Password CTO Nancy Wang 对“智能体会永久继承权限”这一问题的看法。[@felix_fan](https://x.com/felix_fan) [表示](https://x.com/felix_fan/status/2055529244869231072)（59 个赞、15 条回复、5,627 次浏览）表示，Trust Wallet 依然把开发者自主权和消费者同意分开处理，而 [PYMNTS 报道](https://www.pymnts.com/cryptocurrency/2026/crypto-wallets-just-got-rebuilt-for-a-world-run-by-ai/) 也提出了同样的观点：系统里仍少不了会话上限、责任界定，以及人工审批这个环节。围绕 [@Unibase_AI](https://x.com/Unibase_AI) [BitAgent 发布帖](https://x.com/Unibase_AI/status/2055631252779409519)（19 个赞、75 条回复、101 条引用、31,573 次浏览）的一条高赞回复则认为，可组合的技能调用仍然需要托管、交付物哈希和评估者结算，真实工作才能真正完成清算。严重程度：高。当前的权宜之计是设置明确的同意闸门、钱包限额和人工接管。值得投入建设，因为信任层显然落后于市场层。

### 现有 UI 和 TUI 仍然缺少运营级控制能力

即便底层运行时已经具备能力，界面质量仍然是现实中的阻碍。[@abboskhonovv](https://x.com/abboskhonovv) [表示](https://x.com/abboskhonovv/status/2055566572064821637)（9 个赞、1 条回复、417 次浏览）表示，他试了 4 个不同的 Hermes Web UI，却都遇到了布局古怪或功能缺失的问题，于是自己做了 [Hermium](https://github.com/abboskhonov/hermium)，加入模型切换、聊天管理、技能面板和 cron 控制。[@zebassembly](https://x.com/zebassembly) [表示](https://x.com/zebassembly/status/2055426117079609509)（27 个赞、8 条回复、1,437 次浏览）表示，当前编码智能体的 TUI 存在太多琐碎问题，以至于他们虽然喜欢底层产品，还是想自己做一个智能体。[@karrisaarinen](https://x.com/karrisaarinen) [展示了](https://x.com/karrisaarinen/status/2055476478952059227)（61 个赞、6 条回复、6,281 次浏览、88 个收藏）则展示了更好的样子：设置、开关、集成和引导都应直接在产品里可见，而不是被埋在提示词文件中。严重程度：中。当前的变通办法是自己替换 UI 层。值得投入建设，因为这种痛点具体、反复出现，而且直接关系到操作者的日常工作流，而不是审美偏好。![Hermium 界面，展示本地 Hermes 聊天和研究输出视图，旨在增加模型切换、聊天管理、技能和 cron 控制](https://pbs.twimg.com/media/HIbV8v5WIAAql61.jpg)

## 3. 人们希望看到什么

### 可验证的智能体身份与结算规则

最明确的现实需求，不是再来一个市场，而是其下方的规则层。[@pvergadia](https://x.com/pvergadia) [表示](https://x.com/pvergadia/status/2055487369449754843)（7 个赞、7 条回复、1,094 次浏览）指出，智能体仍然缺乏属于自己的身份，这使得继承权限和归属认定成了一个“RIGHT NOW”问题。[@felix_fan](https://x.com/felix_fan) [将其定位为](https://x.com/felix_fan/status/2055529244869231072)（59 个赞、15 条回复、5,627 次浏览）给出的答案是 Trust Wallet 的 Agent Kit 加上 EIP-8004：在开发者侧提供身份能力，同时让用户在消费端保留密钥与同意权；而在 [@Unibase_AI](https://x.com/Unibase_AI) [BitAgent 发布帖](https://x.com/Unibase_AI/status/2055631252779409519)（19 个赞、75 条回复、101 条引用、31,573 次浏览）下，有回复认为，托管、交付物哈希和评估方结算机制仍然缺位。机会：直接。这个需求具体、可操作，而当前的钱包和市场发布仅部分解决了它。

### 能跨越会话重置且受治理的记忆

另一个反复出现的需求，是归运营者所有、而非归模型供应商所有的持久状态。[ODEI 产品页面](https://app.odei.ai) 明确围绕“停止每天早上重建上下文”这一需求进行销售，承诺在 Claude Code、Codex 和 Gemini 之上提供持久化世界模型、治理循环和审计凭证。[@valentinmihov](https://x.com/valentinmihov) [表示](https://x.com/valentinmihov/status/2055708681065402566)（13 个赞、5 条回复、867 次浏览）表示，他自己的 harness 需要一套专门的 Hindsight 记忆系统；而 [@muskonomy](https://x.com/muskonomy) [构建了](https://x.com/muskonomy/status/2055546378026434604)（41 个赞、6 条回复、1,676 次浏览）认为，Grok 与 Hermes 的价值恰恰在于记忆能跨会话、跨消息界面持续存在。机会：直接。需求非常务实，且已有多个产品在围绕它销售，但市场看起来仍处于早期且较为分散的阶段。

### 面向运营者的持久智能体前端

人们还想要那种“可操作”的智能体运行时，而不只是功能强大。[@abboskhonovv](https://x.com/abboskhonovv) [开发了](https://x.com/abboskhonovv/status/2055566572064821637)（9 个赞、1 条回复、417 次浏览）因为现有 Hermes UI 缺少模型切换、聊天管理、技能可见性和 cron 控制，于是做了 Hermium。[@zebassembly](https://x.com/zebassembly) [表示](https://x.com/zebassembly/status/2055426117079609509)（27 个赞、8 条回复、1,437 次浏览）指出，当前 coding-agent TUI 仍有太多本可修复的小毛病；[@karrisaarinen](https://x.com/karrisaarinen) [展示了](https://x.com/karrisaarinen/status/2055476478952059227)（61 个赞、6 条回复、6,281 次浏览、88 次收藏）则表示，理想的替代方案应是一个具备可见开关、引导和集成的 UI，而不是把一切藏在隐性的约定里。机会：直接且竞争激烈。这个需求已经说得很明白，但多个构建者也正朝着同一个答案收敛。

| Hermium | 智能体 UI | (+) | 自托管前端，支持模型切换、持久会话、斜杠命令和使用洞察 | 项目非常新，且完全依赖底层 Hermes |

| Agent Kit + EIP-8004 | 钱包 / 身份基础设施 | (+/-) | 在保留用户同意流程的同时，为智能体提供链上身份和可编程操作 | 在当前的钱包发布中，同意、责任与结算问题仍未解决 |

总体来看，当工具提供清晰的控制界面或基于领域的知识，而不是让运营者用提示词临时拼凑一切时，满意度最高。可见的迁移趋势，是从原始的“提示词 + 工具”组合，转向受治理的运行时、持久记忆层、经验证的技能包，以及明确展示开关、集成和预算的前端。当基础设施足够好但 UX 偏弱时，主要的变通办法是构建像 Hermium 这样的包装式 UI，或转向像 Linear Agent 这类已经暴露出运营者所需控制项的产品。竞争压力最强的地方，正是运行时与控制能力相交的区域：harness 工具、持久记忆/治理、工作流桥接，以及钱包身份技术栈。

## 7. 机会在哪里**[+++] Harness 可观测性与演进工具**——AHE 论文、Sylph 元演进循环、Bun 到 Smithers 的映射，以及 @valentinmihov 的成本仪表盘，都指向同一个缺口：团队至今仍在模型与任务之间这一层花费真金白银，以及大量操作人员时间。能让 harness 修改可检查、可比对、可做基准测试，并且低成本快速迭代的产品，已从第 1、2、4 和 6 节获得支撑。

**[+++] Agent 身份、同意与评估结算**——关于身份缺口的讨论、Trust Wallet 的双轨钱包设计、McKinsey 的信任分类法，以及 BitAgent 关于托管、交付物哈希和评估结算的回复，都指向一个缺失环节：agent 行动与可追责结果之间的基础设施仍不完善。这是一个很强的机会点，因为痛点和局部解决方案都一再出现。

**[++] 持久化 agent 的操作前端**——Hermium 之所以存在，是因为现有 Hermes UI 连基本控制项都没做好；zebassembly 也明确表示想要更好的编程 agent TUI；而 Linear 的截图则显示，市场确实需要可见的设置项和集成能力。这不是一片空白市场，而是一个竞争中的赛道，但需求直接且高频。

**[+] 语音优先编程与实时 agent 交接**——Codex 实时功能的截图，以及 Zubin Pratap 对语音技术栈的分类，都表明一个围绕低延迟、后台执行的“边说—边构建—边讲解”工作流市场正在浮现。相关证据仍然偏早期，但现在已经是公开的、具体的，并且对应到真实的代码和 UI 产物。
