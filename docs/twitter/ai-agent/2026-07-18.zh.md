# Twitter AI 智能体 - 2026-07-18

## 1. 人们在讨论什么

### 1.1 harness 工程成了解释智能体成败的默认答案（🡕）

至少有六条入选内容认为，模型质量已经不再是主要变量。当天最强势的帖子认为，真正拉开差距的，如今在 harness、验证、记忆和控制层。相比 7 月 16 日“同一个模型，不同的系统”的提法，7 月 18 日进一步把 harness 工程推到核心位置，并把它与具体的检查清单、角色边界和运行数据绑定起来。

[@0xCodez](https://x.com/0xCodez) [表示](https://x.com/0xCodez/status/2078108100351943130)（141 个赞、16 条回复、15,712 次浏览、215 个书签）称，Anthropic 的内部栈由模型、harness、智能体和上下文构成，还特意强调“RAG 是一种反模式。用 grep”，把注意力从模型升级转向基于文件的记忆和面向任务的 harness。[@sairahul1](https://x.com/sairahul1) [认为](https://x.com/sairahul1/status/2078461284132282637)（134 个赞、18 条回复、15,887 次浏览、184 个书签）称，循环工程真正关心的是触发器、独立检查器、持久记忆和可观测性，而不只是更好的提示词。[@neil_xbt](https://x.com/neil_xbt) [写道](https://x.com/neil_xbt/status/2078392579532427299)（82 个赞、31 条回复、4,327 次浏览）称，“智能体并不难，难的是 harness”，随后把 harness 拆成工具、记忆/状态、约束、验证和编排。

![架构图展示了一个认知核心，与工作记忆、长期记忆、安全层以及工具执行相连，后者共同构成了智能体周围的操作系统](https://pbs.twimg.com/media/HNgtgJQbAAAdi4N.jpg)

[@ParamSiddh](https://x.com/ParamSiddh) [列出](https://x.com/ParamSiddh/status/2078128841537835501)（71 个赞、5 条回复、2,977 次浏览、89 个书签）列出了 AI 工程师现在需要掌握的具体能力：工具契约、降级模式 UX、检索评估、可观测性、安全工程、多租户隔离和循环预算。[@cyrilXBT](https://x.com/cyrilXBT) [补充说](https://x.com/cyrilXBT/status/2078431335127933063)（110 个赞、31 条回复、11,874 次浏览、62 个书签）提出了一个由模型、harness、工具和环境组成的四层生产级智能体模型，并附上了少见的具体数字：93% 的权限提示会在未阅读的情况下被批准，复杂任务中只有 16.4% 会触发澄清；Anthropic 团队还用 16 个协同智能体构建了一个可编译 Linux 6.9 的 C 编译器，API 成本约为 $20,000。

**讨论洞察：** 回复里并没有人要求更花哨的提示词。大家要的是固定的审查智能体、成本更低的否决循环、硬停止条件、幂等操作、降级模式，以及始终明确保留的人类判断。即便是那条一度试探“删掉引导”的讨论，也有人直接回应：一旦没有引导，可靠性就会下降。

**与前一天对比：** 7 月 16 日把“同一个模型，不同的系统”与资源配置摩擦并列为主要主题。到了 7 月 18 日，这一框架被推到正中央，并被明确的角色、检查清单和生产指标进一步具象化。

至少有七条入选内容把智能体质量视为状态管理和度量问题。这一天的讨论已经不再停留在“用循环”，而是转向明确的图式路由、记忆整理和上下文质量评分。

## 2. 什么让人感到沮丧

### 记忆依然失灵，因为智能体记住了太多垃圾，却没有足够结构

人们烦恼的并不是“我们需要更多 token”，而是智能体忘掉了该记住的东西，却保留了不该保留的内容。针对 [@sairahul1](https://x.com/sairahul1/status/2078461284132282637) 的一条回复明确要求，记忆应当能被人检查、更新、删除和补充。[@N01ennn](https://x.com/N01ennn) [报道](https://x.com/N01ennn/status/2078440268123000874)（45 个赞、11 条回复、1,201 次浏览、31 个书签）指出，Anthropic 的记忆演讲已经提醒过：带内记忆会碰到天花板，需要版本控制、权限和“做梦”式整理。[@coreyhainesco](https://x.com/coreyhainesco) [构建了](https://x.com/coreyhainesco/status/2078184482713346218)（55 个赞、7 条回复、4,558 次浏览、79 个书签）之所以提出第二大脑技能，正是因为一堆扁平、可搜索的材料还不够；[@chenzeling4](https://x.com/chenzeling4) [提到了](https://x.com/chenzeling4/status/2078299470874435729)（1 个赞、42 次浏览）介绍了 [Context Mode](https://github.com/mksglu/context-mode)，其仓库主张把工具输出减少 98%，并保留跨运行的会话记忆。

![五层记忆与状态管理框架，展示了工作记忆、长期记忆、持久状态、记忆管理以及同步/一致性](https://pbs.twimg.com/media/HNhwqY9bIAALUzO.jpg)

![Context Mode README 截图，介绍了上下文窗口缩减、持久会话记忆以及跨平台的 MCP 路由](https://pbs.twimg.com/media/HNeaWwga8AA_EVU.jpg)

严重程度：高。当前可见的应对方式包括外部记忆层、wiki 式链接、上下文压缩和显式状态同步，而不是指望更大的上下文窗口自然表现得像持久记忆。这一方向值得直接投入，因为相关痛点同时出现在高互动量讨论和互动量较低、但实现细节很具体的帖子里。

### 仅靠日志，仍不足以证明任务完成、经过审查或结果正确

[@nykdotdev](https://x.com/nykdotdev) [认为](https://x.com/nykdotdev/status/2078565576759521520)（11 个赞、4 条回复、636 次浏览、9 个书签）指出，难点已经不再是让智能体动起来，而是弄清究竟发生了什么：谁负责这项任务、实际执行了什么、哪些内容经过审查、什么环节悄悄失败了，以及声称的输出是否得到验证。[@omarsar0](https://x.com/omarsar0) [强调了](https://x.com/omarsar0/status/2078585861315432645)（35 个赞、16 条回复、3,406 次浏览、41 个书签）介绍了上下文评分方法，因为薄弱的上下文之后会表现为幻觉、工具误用或暴露于提示注入；其中一条回复进一步点明，真正的失败往往“在前两步就已经开始了”，因为当时可见的是错误的上下文窗口。即便是基准测试表现亮眼的帖子，也招致了同样的质疑：一条针对 [@XFreeze](https://x.com/XFreeze/status/2078530775679684967) 的回复称，私有基准里 70 项做成 69 项，如果任务列表、污染检查和审计轨迹不公开，仍然只是营销。

严重程度：高。人们正通过增加审查关卡、上下文评分、来源谱系检查和完成回执来应对，但这批内容仍显示，在“智能体运行过”和“结果值得信任”之间，缺了一层关键能力。这一方向值得直接投入，因为它横跨编码、研究和多智能体运营。

### 安全和执行边界依然很容易出错

[@ParamSiddh](https://x.com/ParamSiddh) [列出](https://x.com/ParamSiddh/status/2078128841537835501)（71 个赞、5 条回复、2,977 次浏览、89 个书签）把提示注入防御、数据泄露防护、权限边界、工具预算和终止条件列为标准工程问题，而非边缘案例。[@AiCamila_](https://x.com/AiCamila_) [发布了](https://x.com/AiCamila_/status/2078533775659876639)（2 个赞、46 次浏览）介绍了一套安全蓝图，覆盖输入防护栏、工具与操作安全、行为控制、输出控制，以及监控或审计。[@GrokInsider](https://x.com/GrokInsider) [报道](https://x.com/GrokInsider/status/2078236723905982836)（55 个赞、3 条回复、7,100 次浏览）指出，Grok Build CLI 加入了 `require_sha`，以阻止远程插件跟随可变分支或标签；在目录删除失败后，它还移除了持久化本地 shell。公开的 [Hugging Face 2026 年 7 月事件披露](https://huggingface.co/blog/security-incident-july-2026) 则把风险具体化了：一个自治智能体系统利用数据集处理的执行路径，借助窃取的凭据实现权限升级；由于安全防护栏阻止对真实攻击产物做取证分析，防御方被迫放弃托管的前沿模型。

![生产级智能体安全与护栏蓝图，涵盖输入过滤、工具安全、行为控制、输出检查以及监控或审计](https://pbs.twimg.com/media/HNhvco2boAAZxJ5.jpg)

严重程度：高。当前可见的应对方式包括插件钉住版本、默认故障关闭、审计日志，以及为事件响应保留开源权重或自托管备用方案。这一方向值得直接投入，因为相关痛点已不再是假设；无论是推文还是外部事件报告，都描述了具体的失效面。

## 3. 人们希望出现什么

### 可检查、可裁剪、可同步，并能跨会话存续的记忆

这里的需求既实际又紧迫：人们想要的不只是更大的上下文窗口，而是可检查、可整理、可信赖的记忆。[@sairahul1](https://x.com/sairahul1/status/2078461284132282637) 下的回复明确要求，用户应能更新或删除记忆；[@coreyhainesco](https://x.com/coreyhainesco) [展示了](https://x.com/coreyhainesco/status/2078184482713346218)（55 个赞、7 条回复、4,558 次浏览、79 个书签）希望得到一个相互链接的第二大脑，而不是一堆扁平笔记；[@chenzeling4](https://x.com/chenzeling4) [提到了](https://x.com/chenzeling4/status/2078299470874435729)（1 个赞、42 次浏览）介绍了 [Context Mode](https://github.com/mksglu/context-mode)，可在保留会话记忆的同时压缩嘈杂的工具输出。[@AiCamila_](https://x.com/AiCamila_) [将其定义为](https://x.com/AiCamila_/status/2078535110291513379)（9 个赞、135 次浏览）把缺失的实现层归纳为短期记忆、长期记忆、持久状态、记忆管理和同步。今天已经有一些不完整的答案，但信息流仍表明，“有上下文”和“能正确记住”之间依然存在缺口。机会：直接投入。

### 能把运行变成回执的控制平面

人们要的是运行结束后的证据，而不只是转录记录。[@nykdotdev](https://x.com/nykdotdev) [认为](https://x.com/nykdotdev/status/2078565576759521520)（11 个赞、4 条回复、636 次浏览、9 个书签）指出，智能体运营需要任务分配、执行、审查、批准、完成回执和验证证据；[@omarsar0](https://x.com/omarsar0) [指出了](https://x.com/omarsar0/status/2078585861315432645)（35 个赞、16 条回复、3,406 次浏览、41 个书签）则把上下文评分视为判断一次智能体运行能否保持可靠的先行指标。围绕 [@XFreeze](https://x.com/XFreeze/status/2078530775679684967) 的基准讨论，最终也变成了对可审计任务列表、污染检查和单位成功成本的期待，而不是只看排行榜上的单一数字。Mission Control 和 ProofAgent Harness 目前只能部分满足这一需求，但紧迫性依然很高，因为这一痛点横跨编码智能体、研究智能体和多智能体团队。机会：直接投入。

### 具备清晰角色边界和来源谱系感知研究能力的图式编排
