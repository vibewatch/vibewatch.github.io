# Twitter AI Agent - 2026-05-27

## 1. 大家在讨论什么

### 1.1 Skills 成为编辑器原生资产，拥有自己的训练与执行闭环 🡕

5 月 27 日最明显的变化是，人们不再主要把 skills 当作市场里的“库存”，而是开始把它们视为编码环境中的一等产品能力。至少有四条强信号支持这一点：一条关于训练 skill，一条关于在编辑器中交付 skill，一条关于在子代理中隔离 skill，另一条则关于如何在大得多的基准面上评估 skill。

[@daniel_mac8](https://x.com/daniel_mac8) [展示了](https://x.com/daniel_mac8/status/2059244838789218409)（352 个赞、16 条回复、25,274 次浏览、432 次收藏）展示了他如何通过 `/goal` 模式，把最新的 harness engineering 论文直接拉进 Codex，而不只是先收藏起来。他的例子围绕 [SkillOpt](https://arxiv.org/abs/2605.23904) 和 [SkillOpt 仓库](https://github.com/microsoft/SkillOpt) 展开：两者都将 `SKILL.md` 风格的指令视为可训练的外部状态，配合有界文本编辑和留出验证；其中报告称，在 Codex harness 中，GPT-5.5 提升了 24.8 个百分点，在 Claude Code 中提升了 19.1 个百分点。

![展示在 SkillOpt 论文旁的 Codex，说明了面向编码代理的从研究到本地技能的工作流程](https://pbs.twimg.com/media/HJPoII4XoAA35nt.jpg)

[@zeddotdev](https://x.com/zeddotdev) [宣布](https://x.com/zeddotdev/status/2059746303068762493)（203 个赞、7 条回复、6,296 次浏览）指出，Zed 1.4.2 现已支持将 skills 作为其代理的可复用指令。比标题更重要的是后续讨论：Zed 表示，skills 可以全局生效，也可以按项目配置；可以被发现，也可以仅在显式调用时启用；同时还替代了旧版 Rules Library。而公开的 [Zed 技能文档](https://zed.dev/docs/ai/skills) 进一步证实，这个单元是一个命名文件夹，内含 `SKILL.md`、可选引用、脚本以及 registry 导入。

[@code](https://x.com/code) [新增了](https://x.com/code/status/2059681426979553304)（28 个赞、3 条回复、4,248 次浏览、10 次收藏）则在这一思路上又加了一层运行时能力：现在，工具调用很多或研究任务很重的 skills，可以放到专用子代理里运行，从而保持主聊天上下文整洁。这是一次小更新，但它实际改变了 skill 的能力边界：skill 不再只是注入指令，也可以接管嘈杂的执行过程。

[@smoothasfkk](https://x.com/smoothasfkk) [认为](https://x.com/smoothasfkk/status/2059500139048493179)（21 个赞、10 条回复、113 次浏览）指出，EvoSkill 与 Harbor 的集成把评估面从单一基准扩展到了 190+ 个基准，并配套容器化任务与验证器奖励。尽管互动量不高，但它强化了与 SkillOpt 相同的方向：skills 正越来越多地围绕明确的验证闭环来调优，而不是依赖直觉。

**讨论洞察：** 相关帖子受到欢迎的，是具体可控的操作界面，而不是模糊的“自我改进代理”说法。人们想看到的是有界编辑、对 skill 文件的明确可见性，以及针对工具密集型 skill 的运行时隔离。

**与前一天比较：** 5 月 26 日的重点是 skill 市场和可安装的 skill 包；到了 5 月 27 日，讨论进一步转向编辑器原生执行、可训练的 skill 文件，以及有基准测试背书的 skill 演化。

### 1.2 Harness engineering 逐渐沉淀为沙箱、遥测与记忆治理 🡕

第二个强主题是，人们不再把 harness engineering 仅仅当作一个术语，而是把它视为控制、安全与可运维性真正落地的地方。支撑这一判断的信号有五类：系统扩展研究、一套精选的 harness 资料、沙箱执行、面向 SIEM 的遥测，以及一串把“记忆”重构为“新鲜度问题”的回复。

[@dair_ai](https://x.com/dair_ai) [认为](https://x.com/dair_ai/status/2059294269698199929)（72 个赞、12 条回复、4,506 次浏览、77 次收藏）指出，代理式 AI 的下一个瓶颈是“系统扩展”，而不只是模型扩展。相关论文 [从模型扩展到系统扩展：在 Agentic AI 中扩展 Harness](https://papers.cool/arxiv/2605.26112) 将上下文治理、可信记忆和动态 skill 路由列为核心瓶颈，这意味着 harness 本身正在成为主要工程界面。

![系统扩展论文的第一页，重点突出上下文治理、可信记忆和动态技能路由](https://pbs.twimg.com/media/HJQVOX_bEAATe44.png)

[@_vmlops](https://x.com/_vmlops) [分享了](https://x.com/_vmlops/status/2059615043550146754)（38 个赞、2 条回复、2,889 次浏览、50 次收藏）介绍了一个 [awesome-harness-engineering](https://github.com/ai-boost/awesome-harness-engineering) 资料集合，将整套栈梳理为上下文交付、工具、skills 与 MCP、权限、记忆、验证、可观测性、调试以及人在回路控制。它的重要性在于，把一个模糊的流行概念变成了一张明确的系统地图。

[@pamelafox](https://x.com/pamelafox) [指出](https://x.com/pamelafox/status/2059501019210580346)（4 个赞、185 次浏览）指出，沙箱正成为编码代理的默认组成部分。她举的例子把 VS Code 预览版 [代理沙箱化](https://code.visualstudio.com/docs/copilot/concepts/trust-and-safety#_agent-sandboxing)、[NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell) 和 Docker 的沙箱工具串了起来；公开文档则把这一点讲得更具体：操作系统级的文件与网络限制，正在取代“尽力而为”的提示词审查，成为主要控制平面。

[@jqdsouza](https://x.com/jqdsouza) [表示](https://x.com/jqdsouza/status/2059722561597157770)（6 个赞、4 条回复、92 次浏览）指出，Agent Beacon 现在会把遥测送入 Microsoft Sentinel，并捕获 VS Code Copilot Chat 内的活动。帖子本身不大，但它带来了一个真实的企业需求信号：安全团队希望代理活动进入他们已经在使用的监控系统。

[@hwchase17](https://x.com/hwchase17) [转发了](https://x.com/hwchase17/status/2059487107144655356)（114 个赞、6 条回复、19,563 次浏览、151 次收藏）介绍了一个记忆与持续学习项目，但最有力的证据来自回复。[@r_rajan4ever](https://x.com/r_rajan4ever/status/2059489430654882300) 说，难点在于决定哪些内容该进权重、记忆数据库还是实时上下文；[@TomGiant1](https://x.com/TomGiant1/status/2059505038448332810) 则表示，悄然衰减的陈旧记忆比完全没有记忆更糟。

**讨论洞察：** 回复不断回到同一个限制：存储很容易，治理才难。沙箱、审批疲劳、陈旧记忆和 SIEM 可见性，都被当作 harness 失效，而不是模型失效。

**与前一天比较：** 5 月 26 日已经出现治理和策略相关信号，但 5 月 27 日把讨论范围从工具调用控制进一步扩展到了运行时隔离、可观测性和记忆新鲜度。

### 1.3 构建者把代理工作包装成组织、操作平台和专业操作员 🡒

第三个主题聚焦于那些让代理不再像单一聊天框、而更像一块操作平台的产品。相关项目从代理组织架构，到后台桌面控制，再到面向语音和安全工作的垂直操作员都有涉及。

[@Sumanth_077](https://x.com/Sumanth_077) [介绍了](https://x.com/Sumanth_077/status/2059627798676079086)（11 个赞、4 条回复、724 次浏览、10 次收藏）将 [Alook](https://github.com/alookai/alook) 描述为一个自托管协作平台：编码代理在其中拥有角色、汇报关系、邮箱地址、日程和共享记忆。公开 README 进一步补充了看板、日历、本地优先执行和可追踪决策，使其更像一层“AI 公司”操作系统，而不只是又一个助手外壳。

[@trycua](https://x.com/trycua) [发布了](https://x.com/trycua/status/2059688960838828391)（15 个赞、7 条回复、729 次浏览、8 次收藏）介绍了 [Cua Driver](https://github.com/trycua/cua) 的 Windows 支持：Claude Code、Codex 或自定义代理可以通过 CLI 或 MCP 驱动真实 Windows 应用，同时桌面仍可正常使用。讨论串还补充了实际切入点：WPF 应用的 QA 闭环、没有 API 的旧桌面软件自动化，以及 [@sureshkanbu](https://x.com/sureshkanbu/status/2059694783820394829) 的一条回复——在今天的多代理工作流里，真正的阻碍是“抢焦点”。

![Cua Driver 演示展示了由代理控制的 Windows 桌面应用，而非仅限浏览器的自动化](https://pbs.twimg.com/media/HJV2QzhWkAQs1TA.jpg)

[@HowToAI_](https://x.com/HowToAI_) [重点提到了](https://x.com/HowToAI_/status/2059602834312794187)（26 个赞、1 条回复、1,149 次浏览、26 次收藏）介绍了 [Dograh](https://github.com/dograh-hq/dograh)：一个拖拽式语音代理构建器，定位为 Vapi 和 Retell 的开源、自托管替代方案。Dograh 的 README 也支撑了这种“反锁定”定位：基于 Docker 的自托管、用户自带模型与电话服务商，以及内置的 QA/测试节点。

[@VivekIntel](https://x.com/VivekIntel) [分享了](https://x.com/VivekIntel/status/2059730587032993797)（18 个赞、605 次浏览、15 次收藏）介绍了 [PentestAgent](https://github.com/GH05TCREW/PentestAgent)。其公开 README 描述了 assist、agent 和 crew 模式，Docker 与 Kali 执行路径，MCP server 支持，以及可直接使用 `nmap`、`sqlmap` 和 `metasploit` 等工具。这很好体现了当天更广泛的模式：把代理包装成拥有自身运行时、工具和工作流语义的领域操作员。

**讨论洞察：** 最有价值的回复关注的不是模型质量，而是操作摩擦。尤其在 Cua 的讨论串中，重点集中在不抢焦点的自动化，以及那些至今仍承载真实业务流程的旧版 Windows 软件。

**与前一天比较：** 5 月 26 日更偏向头像、生成式画布等界面层；到 5 月 27 日，则转向更持久的操作平台：组织架构、后台桌面控制和专业操作员。

## 2. 什么让人感到沮丧

### 审批提示和仅靠提示词的护栏仍然太弱

严重程度：高。[@pamelafox](https://x.com/pamelafox) [提到](https://x.com/pamelafox/status/2059501019210580346)（4 个赞、185 次浏览）指出，沙箱正成为编码代理中的一个独立趋势，并提到 VS Code 沙箱以及 OpenShell 和 Docker 的方案。公开的 [VS Code 沙箱文档](https://code.visualstudio.com/docs/copilot/concepts/trust-and-safety#_agent-sandboxing) 把原因说得很清楚：审批疲劳、命令解析限制、提示注入，以及对外部服务的非预期操作，在仅靠提示词的审批模型下都依然存在，这也是为什么操作系统级文件与网络边界如此重要。[NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell) 则从运行时一侧提出了同样的抱怨：每个沙箱默认只开放最小出站访问，要放开更多权限，必须通过声明式 YAML 策略。

![VS Code 提示显示某条命令需要在沙箱外运行，说明了已批准执行与非沙箱执行之间的边界](https://pbs.twimg.com/media/HJTRPqracAAzzwF.png)

[@jqdsouza](https://x.com/jqdsouza) [补充说](https://x.com/jqdsouza/status/2059722561597157770)（6 个赞、4 条回复、92 次浏览）指出，安全和平台团队仍在要求对 Copilot Chat 与代理活动有更多可见性，这也是 Agent Beacon 把遥测推入 Microsoft Sentinel 的原因。人们现在的应对方式，是在代理外围叠加沙箱、策略引擎和 SIEM 遥测，而不是单纯相信提示词。值得构建：是。

### 记忆很容易存，可信却很难维持

严重程度：高。[@hwchase17](https://x.com/hwchase17) [转发了](https://x.com/hwchase17/status/2059487107144655356)（114 个赞、6 条回复、19,563 次浏览、151 次收藏）介绍了一个开源的记忆与持续学习代理，但最有实质内容的反应立刻质疑了记忆层。[@r_rajan4ever](https://x.com/r_rajan4ever/status/2059489430654882300) 说，真正难的是把内容路由到权重、记忆数据库和实时上下文；[@TomGiant1](https://x.com/TomGiant1/status/2059505038448332810) 则警告说，当文件路径、API 或配置已经漂移，而代理还在按旧状态继续行动时，记忆会悄悄变得危险。当前的应对办法，是重新验证、更严格的晋升规则，以及缩短对已存记忆的信任时长。值得构建：是。

### 上下文和 token 消耗仍在浪费真金白银

严重程度：中。[@Shruti_0810](https://x.com/Shruti_0810) [报道称](https://x.com/Shruti_0810/status/2059573068348133829)（18 个赞、6 条回复、1,141 次浏览）指出，一个 Claude Code 工作流在切换到 InsForge skills 和基于 CLI 的上下文工程后，token 消耗从 10.4M 降到 3.7M，成本从 9.21 美元降到 2.81 美元，错误数从 10 次降到 0。讨论串并没有把这当成小修小补：[@TuracTheThinker](https://x.com/TuracTheThinker/status/2059578239287267779) 表示，比起更大的上下文窗口，更重要的是展示哪些行或哪些来源塑造了答案；多条回复则把这种节省视为改变构建者“能负担什么尝试”的关键变化。人们的应对方式，是投资上下文工程和后端能力面，而不只是购买更大的窗口。值得构建：是。

## 3. 人们希望存在什么

### 可测量、可调优、可跨运行时迁移的 skill 系统

最强烈的产品愿望不是“更多提示词”，而是一整套 skill 生命周期。[@daniel_mac8](https://x.com/daniel_mac8) [展示了](https://x.com/daniel_mac8/status/2059244838789218409)（352 个赞、16 条回复、25,274 次浏览、432 次收藏）展示了一种把 [SkillOpt](https://arxiv.org/abs/2605.23904) 这类研究直接移植进 Codex 的工作流；[@zeddotdev](https://x.com/zeddotdev) [发布了](https://x.com/zeddotdev/status/2059746303068762493)（203 个赞、7 条回复、6,296 次浏览）展示了编辑器原生 skills；[@code](https://x.com/code) [新增了](https://x.com/code/status/2059681426979553304)（28 个赞、3 条回复、4,248 次浏览、10 次收藏）则展示了用于运行重型 skills 的专用子代理。需求非常实际：构建者希望 skills 能一次创建、验证、改进，并在不同环境间复用。机会：直接。

### 默认安全、内置审计与遥测的运行时

人们显然在呼唤一种默认安全的代理运行时，并且能在事后告诉操作方到底发生了什么。[@pamelafox](https://x.com/pamelafox) [提到了](https://x.com/pamelafox/status/2059501019210580346)（4 个赞、185 次浏览）提到了沙箱趋势；[VS Code 文档](https://code.visualstudio.com/docs/copilot/concepts/trust-and-safety#_agent-sandboxing) 明确指出，面对注入和疲劳，审批流程会失灵；[OpenShell](https://github.com/NVIDIA/OpenShell) 展示了文件、进程、网络和推理控制；[@jqdsouza](https://x.com/jqdsouza) [表示](https://x.com/jqdsouza/status/2059722561597157770)（6 个赞、4 条回复、92 次浏览）则表明，企业正在要求把 Copilot Chat 遥测接入 Sentinel。这是一个已有部分答案浮现的实际需求，因此机会既直接，也竞争激烈。

### 更像团队而不是聊天的多代理工作区

Alook 和 Cua 的讨论串指向一个非常具体的愿望：代理能够在后台持续工作、彼此协调，并操作人们已经在使用的软件。[@Sumanth_077](https://x.com/Sumanth_077) [介绍了](https://x.com/Sumanth_077/status/2059627798676079086)（11 个赞、4 条回复、724 次浏览、10 次收藏）将 Alook 描述为面向编码代理、以电子邮件为原生协调方式的组织架构；[@trycua](https://x.com/trycua) [发布了](https://x.com/trycua/status/2059688960838828391)（15 个赞、7 条回复、729 次浏览、8 次收藏）则展示了面向需要驱动真实桌面软件的代理的后台 Windows computer-use 能力。需求不是理想化的，而是非常务实的：保留上下文、保留角色，别再把所有工作流都硬塞回一个前台聊天窗格。机会：直接且竞争激烈。

### 更便宜、更可追溯的编码代理上下文工程

InsForge 讨论串让一个更窄但很具体的需求浮出了水面：如何在不为浪费买单的情况下，把后端状态和检索上下文喂给编码代理。[@Shruti_0810](https://x.com/Shruti_0810) [声称](https://x.com/Shruti_0810/status/2059573068348133829)（18 个赞、6 条回复、1,141 次浏览）展示了 token 和错误数的大幅下降；[InsForge 仓库](https://github.com/InsForge/InsForge) 则解释了这类方案为何吸引人：通过 MCP 和 CLI 暴露认证、数据库、存储、计算与部署能力，并以代理可以检查和操作的方式呈现出来。这个需求仍然早期、也很拥挤，但足够具体。机会：竞争性机会。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 评价 | 优势 | 局限 |
|---|---|---|---|---|
| SkillOpt | Skill 优化 | (+) | 有界文本编辑、留出验证、跨 harness 迁移、推理时无额外开销 | 最适合目标可验证的场景；开放式工作仍需要更强的评估器 |
| Zed skills | 编辑器 skill 系统 | (+) | 全局和项目本地作用域、可发现或仅显式调用模式、`SKILL.md` 打包 | 新功能面；且仅限特定编辑器 |
| `@code` 中的专用 skill 子代理 | 编码代理运行时 | (+/-) | 让工具密集型或研究密集型 skills 不占用主上下文窗口 | 公开细节目前仍主要限于功能讨论串 |
| VS Code 代理沙箱 | 代理沙箱 | (+/-) | 操作系统级文件/网络隔离、检查点审查、沙箱内自动审批 | 预览功能；目前主要聚焦终端命令 |
| OpenShell | 沙箱运行时 | (+/-) | 声明式 YAML 策略、默认最小出站权限、可热重载策略、支持多个代理 CLI | Alpha 阶段，并明确仍是“单人模式” |
| Alook | 多代理编排 | (+) | 组织架构、电子邮件原生协作、日历、共享记忆、本地优先执行 | 公开声量较小，生态仍早期 |
| Cua Driver / Cua | Computer-use 运行时 | (+) | 通过 CLI/MCP 在后台操作电脑、可回放轨迹、支持旧桌面应用 | Windows 支持刚推出，且公开仓库覆盖的平台范围也不止单一工作流 |
| Dograh | 语音代理平台 | (+) | 拖拽式构建器、自托管、BYO 服务商、内置测试/QA 节点 | 语音垂直领域；仍需额外运维一套栈 |
| InsForge | 代理后端平台 | (+/-) | 通过 MCP/CLI 暴露认证、数据库、存储、计算、部署和模型网关能力面 | 当前节省效果的证据仍以个案和讨论串为主 |
| PentestAgent | 安全操作员 | (+/-) | assist/agent/crew 模式、Docker/Kali 执行、MCP server 模式、直接使用标准安全工具 | 敏感领域，滥用风险明显；必须面向已授权目标 |
| EvoSkill + Harbor | 评估与 skill 演化 | (+) | 容器化任务、验证器奖励，以及更大的 skill 演化基准面 | 在当天讨论中，公开可见的操作者采用度低于编辑器 skill 工具 |

整体满意度明显更偏向那些用可见系统结构取代隐性提示纪律的工具。[@zeddotdev](https://x.com/zeddotdev) [发布了](https://x.com/zeddotdev/status/2059746303068762493)（203 个赞、7 条回复、6,296 次浏览）展示了基于文件的 skill 系统；[@daniel_mac8](https://x.com/daniel_mac8) [展示了](https://x.com/daniel_mac8/status/2059244838789218409)（352 个赞、16 条回复、25,274 次浏览、432 次收藏）展示了如何基于研究调优这些文件；[@pamelafox](https://x.com/pamelafox) [指出](https://x.com/pamelafox/status/2059501019210580346)（4 个赞、185 次浏览）则把沙箱指认为必需的运行时层，而不是可有可无的谨慎措施。

当天反复出现的应对模式也非常一致：从提示工程转向上下文工程或 harness engineering，从审批提示转向运行时隔离，从单体助手转向明确角色或子代理。迁移压力还以更细小的方式显现：Zed 从 Rules Library 转向 skills，Cua 把浏览器式自动化推进为后台桌面控制，InsForge 则把后端上下文重新定义为 MCP 和 CLI 能力面，而不是藏在基础设施里。

## 7. 机会在哪里

** 默认安全、内置审计与遥测的代理运行时 [+++] Secure harness control planes** — The strongest multi-source gap sits at the runtime boundary. [@pamelafox](https://x.com/pamelafox) [提到了](https://x.com/pamelafox/status/2059501019210580346) 提到了沙箱；[VS Code 文档](https://code.visualstudio.com/docs/copilot/concepts/trust-and-safety#_agent-sandboxing) 解释了为什么提示审批会失效；[OpenShell](https://github.com/NVIDIA/OpenShell) 把策略以代码形式暴露出来；[@jqdsouza](https://x.com/jqdsouza/status/2059722561597157770) 则显示出对 SIEM 级遥测的需求。这个机会很强，因为痛点具备运营属性、安全敏感，而且会反复出现。

** 可移植的 skill 生命周期工具 ** — SkillOpt、Zed skills、`@code` 子代理和 EvoSkill 都指向同一个需求：在不同环境之间创建、验证、调优、路由并复用 skills。这个机会很强，因为数据表明，从研究、编辑器 UX 到基准基础设施，各层都存在需求。

** 面向团队与旧软件的代理操作系统 ** — Alook 和 Cua 展示了同一问题的两面：代理需要角色、记忆，以及对企业现有软件的访问能力。这个机会中等，因为市场上已经有可信的早期进入者，但相关工作流黏性强、表面积也大。

** 面向编码代理的上下文成本与可追溯性层 ** — InsForge 讨论串虽然只是一个数据点，但很有价值，因为它把上下文工程直接和更低成本、更少失败联系在一起。这个方向看起来仍在浮现，而非已经被充分验证，但成本压力已经真实到足以产生影响。

## 8. 要点

1. ** Skills 正在变成一层受管理的软件，而不只是提示习惯。** 最有力的证据来自 SkillOpt 以验证为门控的调优闭环、Zed 稳定版 skills 发布，以及 `@code` 为重型 skills 增加专用子代理。（[daniel_mac8](https://x.com/daniel_mac8/status/2059244838789218409), [Zed](https://x.com/zeddotdev/status/2059746303068762493), [代码](https://x.com/code/status/2059681426979553304)）
2. ** 如今，信任是在 harness 层赢得或失去的。** 系统扩展论文将上下文治理、可信记忆和动态 skill 路由列为瓶颈；沙箱工具和遥测相关帖子则以产品形态呈现了同样的担忧。（[dair_ai](https://x.com/dair_ai/status/2059294269698199929), [pamelafox](https://x.com/pamelafox/status/2059501019210580346), [jqdsouza](https://x.com/jqdsouza/status/2059722561597157770)）
3. ** 记忆问题依然无解，因为新鲜度比存储更重要。** 记忆讨论串中最有价值的回复认为，真正的挑战是当外部世界变化时的路由、失效处理和重新验证。（[hwchase17 讨论串](https://x.com/hwchase17/status/2059487107144655356), [r_rajan4ever 的回复](https://x.com/r_rajan4ever/status/2059489430654882300), [TomGiant1 的回复](https://x.com/TomGiant1/status/2059505038448332810)）
4. ** 构建者正在把代理包装成拥有自身角色与运行时的操作平台。** Alook 把代理变成邮件加组织架构的工作流，而 Cua Driver 则把 Windows 应用变成代理可实际使用的执行界面。（[Alook](https://x.com/Sumanth_077/status/2059627798676079086), [Cua Driver](https://x.com/trycua/status/2059688960838828391)）
5. ** 成本与控制的重要性，开始和模型原始质量一样高。** InsForge 讨论串量化了更低的 token 支出与更少的错误，而 Dograh 和 OpenShell 的材料则都把开放性与可控基础设施当作一等特性来卖。（[InsForge 讨论串](https://x.com/Shruti_0810/status/2059573068348133829), [Dograh](https://github.com/dograh-hq/dograh), [OpenShell](https://github.com/NVIDIA/OpenShell)）
