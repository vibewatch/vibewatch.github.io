# Twitter AI Agent - 2026-06-22

## 1. 人们在讨论什么

### 1.1 编排话题已从“框架怎么搭”转向有基准结果支撑的单端点产品（🡕）

最强的一组讨论，把前一天关于框架的争论推进成了带有具体公开证据的产品主张。至少有四条强信号支撑这一主题，讨论重心也从“怎么写提示词”转向“如何把编排、委派和验证封装成交付形态”。

[@SakanaAILabs](https://x.com/SakanaAILabs) [介绍了](https://x.com/SakanaAILabs/status/2068861630327443966)（652 个赞、37 条回复、80,691 次浏览、349 次收藏）将 Sakana Fugu 描述为封装在单一模型 API 背后的完整多智能体编排系统。关联的 [Fugu 页面](https://sakana.ai/fugu/) 补上了发布推文中仅被轻描淡写提到的证据：展示了自主机器学习研究、历史文档阅读、CAD 生成、蒙眼国际象棋和股票交易等案例，其中包括一次 AutoResearch 运行：Fugu-Ultra 在一张 H100 上用约 14 小时完成了 123 次实验，并取得了报告中最佳的平均 BPB。

[@SakanaAILabs](https://x.com/SakanaAILabs) [解释了](https://x.com/SakanaAILabs/status/2068862344684581023)（114 个赞、4 条回复、7,732 次浏览、30 次收藏）指出，Fugu 本身就是一个经过训练、可调用其他 LLM 的 LLM，甚至可以递归调用自身，同时在内部处理模型选择、委派、验证和综合。这种架构之所以重要，是因为它把当天最核心的判断说透了：被售卖的产品不只是底层模型，更是围绕模型池构建的控制层。

![Sakana Fugu 架构图，展示单个请求如何通过内部 LLM 池进行路由，并经过委派、验证和综合](https://pbs.twimg.com/media/HLYTUWxawAAEJN-.png)

[@RoundtableSpace](https://x.com/RoundtableSpace) [指向了](https://x.com/RoundtableSpace/status/2069099343769170389)（81 个赞、11 条回复、51,014 次浏览、50 次收藏）提到了 Anthropic 的 [构建高效智能体](https://www.anthropic.com/engineering/building-effective-agents) 指南。该指南明确区分工作流与智能体，并梳理了提示链、路由、并行化、编排器-工作者以及评估器-优化器等模式。[@DanKornas](https://x.com/DanKornas) [发布了](https://x.com/DanKornas/status/2068771160469262568)（34 个赞、5 条回复、1,530 次浏览、34 次收藏）提到 [AI 开发模式](https://github.com/PaulDuvall/ai-development-patterns)：一个公开的 24 种模式目录，按基础、开发、运营和实验四条路径组织，并明确以框架工程的视角讨论前馈/反馈与计算/推理控制。

![AI Development Patterns 仓库示意图，展示基础、开发和运维三个层面的 24 种模式](https://pbs.twimg.com/media/HLXAZs-XAAAKZ4-.jpg)

**讨论洞察：** 最有价值的反驳集中在失败处理，而非模型质量。有人在回复 Sakana 时追问，Fugu 如何在长时程、高风险任务中维持验证与一致性；而围绕 Anthropic 链接展开的讨论，则聚焦于如何避免把糟糕提示词当成“经验法则”，主张先选择更简单、可检查的模式。

**与前一天相比：** 6 月 21 日的讨论仍主要被课程、模式和围绕框架的约束钩子所主导。到了 6 月 22 日，主题没变，但已推进到有基准结果的产品和官方框架文档。

### 1.2 面向团队规模的智能体工作空间成为一级产品类别（🡕）

第二个主题是，真正的瓶颈已不再是让一个智能体完成一项任务，而是如何让智能体在团队、会话和运行时之间保持可见、带状态、可治理。至少有五条强信号支撑这一主题。

[@huang_chao4969](https://x.com/huang_chao4969) [开源了](https://x.com/huang_chao4969/status/2068930040616923551)（93 个赞、8 条回复、5,250 次浏览、75 次收藏）将 AgentSpace 描述为一个供人类与智能体协作的工作空间，具备明确的角色、负责人、权限、排期和可审计性。公开的 [AgentSpace 仓库](https://github.com/HKUDS/AgentSpace) 让这一设计更具体：其中介绍了 AgentRouter 对 Claude Code、Codex、OpenClaw、Hermes 和 nanobot 的支持，以及共享工作区、审批和远程守护进程执行。

![AgentSpace README，展示“Human + Agents”工作空间框架和共享智能体协作模型](https://pbs.twimg.com/media/HLZQxKsbYAAr9XE.jpg)

[@goyalshaliniuk](https://x.com/goyalshaliniuk) [认为](https://x.com/goyalshaliniuk/status/2068869077326549262)（28 个赞、10 条回复、427 次浏览、6 次收藏）指出，Claude Code 每次重置会话后，开发者仍得重新解释自己的代码库，并把 Memanto 作为一个本地优先的修复方案提了出来。其 [PyPI 页面](https://pypi.org/project/memanto/) 和 [仓库](https://github.com/moorcheh-ai/memanto) 表示，它为 Claude Code、Cursor、Codex 和另外 14+ 个智能体提供持久记忆，包含 `remember`、`recall` 和 `answer` 原语、13 类类型化记忆，以及完全本地化的 Docker/Ollama 路径。

[@_philschmid](https://x.com/_philschmid) [宣布了](https://x.com/_philschmid/status/2069108134044467487)（39 个赞、9 条回复、2,655 次浏览、12 次收藏）提到 Google 的 Interactions API 已正式可用。公开的 [Interactions 概览](https://ai.google.dev/gemini-api/docs/interactions-overview) 表示，它现在是新 Gemini 项目的推荐接口，并新增了通过 `previous_interaction_id` 实现的服务端状态、借助 `background=true` 实现的后台执行、可观测的执行步骤，以及同时覆盖模型与 Antigravity、Deep Research 等智能体的统一 API 入口。

![Interactions API 示例代码，展示通过单一接口调用 Gemini 模型和智能体](https://pbs.twimg.com/media/HLbwvkUXkAAPUJd.jpg)

[@DataScienceDojo](https://x.com/DataScienceDojo) [重点介绍了](https://x.com/DataScienceDojo/status/2069058361778229396)（1 个赞、170 次浏览、1 次收藏）提到 DeerFlow 2.0，[DeerFlow 仓库](https://github.com/bytedance/deer-flow) 将其描述为一个面向子智能体、记忆、沙箱和可扩展技能的开源超级智能体框架。[@dew_yashtwt](https://x.com/dew_yashtwt) [推出了](https://x.com/dew_yashtwt/status/2069050272685621333) 提到 Supercode beta（50 个赞、4 条回复、2,522 次浏览、33 次收藏），将其描述为一个开源终端 SWE 智能体，支持整机级操作、持久记忆和明确的审批关卡；公开的 [仓库](https://github.com/yashdev9274/supercli) 则展示了其 CLI、终端 Web 客户端、仪表盘和共享技能所采用的 Bun + Turborepo + Next.js + TypeScript 技术栈。

**讨论洞察：** 这里的怀疑主要来自运维层面。Supercode 的回复里立刻有人问 beta 是否已经坏掉；而在 Interactions API 的发布回复中，也有人抱怨官方 Google .NET SDK 仍未跟上。需求显然存在，但市场要的是耐用的底层管线，而不是炫目的演示。

**与前一天相比：** 6 月 21 日更偏向持久化私有运行时和故障恢复。6 月 22 日则把同样的关切推进到团队工作空间、持久记忆和统一 API，让智能体工作不再局限于某个人的终端。

### 1.3 围绕支付、技能和企业验证的安全执行护栏仍在扩张（🡒）

第三个主题是，智能体的落地正在不断催生相邻的安全与控制层。当天的证据重点不在更聪明的推理，而在更安全的支付、更安全的能力安装，以及更可审计的企业级执行。

[@trythreews](https://x.com/trythreews) [发布了](https://x.com/trythreews/status/2068951336918638699)（214 个赞、48 条回复、19,175 次浏览、13 次收藏）提到一个可直接接入 x402 端点的支付弹窗，能够处理钱包检测、切链、签名、结算和浏览器端消费上限。[@nichxbt](https://x.com/nichxbt) [新增了](https://x.com/nichxbt/status/2068978079637405783)（51 个赞、12 条回复、1,855 次浏览、8 次收藏）则补充了更大的背景：由 Linux Foundation 托管、拥有主要生态支持者，截至 2026 年 4 月下旬累计交易已超过 1.65 亿笔，活跃智能体约 69,000 个，但也承认当前大量流量仍然嘈杂且带有投机性。

[@probiex007](https://x.com/probiex007) [指出了](https://x.com/probiex007/status/2069108151886995707)（1 个赞、68 次浏览、1 次收藏）提到 NVIDIA 的 [SkillSpector](https://github.com/NVIDIA/SkillSpector)。该仓库 README 表示，它可在 16 个类别中检查 64 种漏洞模式，并声称被扫描技能中有 26.1% 存在漏洞，5.2% 显示出可能的恶意意图。这让“技能供应链风险”更难再被当作抽象问题一笔带过。

![SkillSpector README，展示漏洞百分比以及该扫描器的多类别安全检查](https://pbs.twimg.com/media/HLbXad1a4AEK72E.jpg)

[@GoogleCloudTech](https://x.com/GoogleCloudTech) [报道了](https://x.com/GoogleCloudTech/status/2068770931447570457)（63 个赞、2 条回复、6,386 次浏览、16 次收藏）提到，Google 使用专门的多智能体系统将大型 TensorFlow 模型迁移到 JAX。关联的 [Google Cloud 文章](https://cloud.google.com/blog/topics/developers-practitioners/6x-faster-migration-from-tensorflow-to-jax) 表示，该系统使用了分层 Playbook、数学等价性检查和 LLM 裁判，并在复杂 YouTube 模型迁移中实现了据称 6.4x-8x 的加速。

**讨论洞察：** 最强的成熟信号在于，这些控制措施如今都很具体：浏览器强制执行的消费上限、技能扫描器、数学验证和质量裁判。最有价值的谨慎提醒则来自 x402 那条宏观讨论本身：当前交易总量中仍含有相当多的投机噪声。

**与前一天相比：** 6 月 21 日已经显现出技能扫描和治理框架开始受到关注。到了 6 月 22 日，这些能力进一步走向实操，落在支付 UX、安装时扫描以及已公开的企业验证闭环上。

## 2. 什么让人沮丧

### 共享上下文依然太容易丢失

严重程度：高。[@goyalshaliniuk](https://x.com/goyalshaliniuk) [表示](https://x.com/goyalshaliniuk/status/2068869077326549262)（28 个赞、10 条回复、427 次浏览、6 次收藏）指出，Claude Code 用户每次会话结束都得付出“上下文税”：重新解释仓库、重述决策，并把 token 浪费在重复背景上。Anthropic 的 [高效智能体指南](https://www.anthropic.com/engineering/building-effective-agents) 由 [@RoundtableSpace](https://x.com/RoundtableSpace) [这里](https://x.com/RoundtableSpace/status/2069099343769170389)（81 个赞、11 条回复、51,014 次浏览、50 次收藏）分享，从另一个角度指向同一结构性问题：把记忆、工具和工作流视为一等构件，而不是只打磨提示词。Google 的 [Interactions API 文档](https://ai.google.dev/gemini-api/docs/interactions-overview) 由 [@_philschmid](https://x.com/_philschmid) [这里](https://x.com/_philschmid/status/2069108134044467487)（39 个赞、9 条回复、2,655 次浏览、12 次收藏）发布，实际上是平台级的应对方案：服务端状态、后台任务和执行时间线，让开发者不必手动重建上下文。这个方向值得投入，因为同一天里，终端用户抱怨、框架指南和平台设计都在指向同一个痛点。

### 安全执行智能体，仍需要在模型外再套一层控制壳

严重程度：高。[@trythreews](https://x.com/trythreews) [发布了](https://x.com/trythreews/status/2068951336918638699)（214 个赞、48 条回复、19,175 次浏览、13 次收藏）提到一个支付弹窗，在 x402 之上补上了钱包交互、收据和浏览器端消费上限；这本身就说明，协议层支付还不足以支撑真实使用。[@probiex007](https://x.com/probiex007) [展示了](https://x.com/probiex007/status/2069108151886995707)（1 个赞、68 次浏览、1 次收藏）提到 NVIDIA 的 SkillSpector，其 [README](https://github.com/NVIDIA/SkillSpector) 表示，被扫描技能中有 26.1% 存在漏洞，5.2% 显示出可能的恶意意图。[@GoogleCloudTech](https://x.com/GoogleCloudTech) [展示了](https://x.com/GoogleCloudTech/status/2068770931447570457)（63 个赞、2 条回复、6,386 次浏览、16 次收藏）则展示了同一个问题在企业场景中的版本：其 TF 到 JAX 的迁移系统必须依赖分层 Playbook、数学等价性检查和 LLM 裁判，输出才会被信任。这三个例子的应对模式高度一致：不要单独相信原始的智能体循环。

### 当智能体只活在某个人的终端里，团队使用就仍然会断裂

严重程度：中。[@huang_chao4969](https://x.com/huang_chao4969) [构建了](https://x.com/huang_chao4969/status/2068930040616923551)（93 个赞、8 条回复、5,250 次浏览、75 次收藏）围绕 AgentSpace 指出了一个直接问题：大多数智能体仍是“一人、一终端、一个聊天会话”的工具。[@dew_yashtwt](https://x.com/dew_yashtwt) [推出了](https://x.com/dew_yashtwt/status/2069050272685621333) 提到 Supercode beta（50 个赞、4 条回复、2,522 次浏览、33 次收藏），但最早的回复就是在问产品是不是坏了，这也提醒人们，更大范围的机器控制在带来上行空间的同时，也会增加运维负担。[@DataScienceDojo](https://x.com/DataScienceDojo) [指向了](https://x.com/DataScienceDojo/status/2069058361778229396)（1 个赞、170 次浏览、1 次收藏）提到 DeerFlow 2.0 这个具备子智能体、记忆和沙箱的框架，这再次说明，团队正在拼装越来越多的基础设施，只为让多步骤智能体工作变得可管理。这个方向值得投入，但市场已经在从简单聊天界面转向更厚重的控制平面。

## 3. 人们希望存在什么

### 能把智能体变成组织资产的共享工作空间

最明确的实际需求，是一层能把私有智能体配置转化为团队共享基础设施的系统。[@huang_chao4969](https://x.com/huang_chao4969) [描述了](https://x.com/huang_chao4969/status/2068930040616923551)（93 个赞、8 条回复、5,250 次浏览、75 次收藏）直白地点出了问题：智能体单独使用时很强，但一旦真实团队需要角色、审批、排期和问责，就会掉链子。公开的 [AgentSpace 仓库](https://github.com/HKUDS/AgentSpace) 现在给出了一种答案，但这个需求显然不止对应某一个产品。机会：直接。

### 重置后仍能保留记忆，而不会反过来增加基础设施负担

第二个需求，是能持久保留上下文，但又不逼开发者搭起整套检索栈。[@goyalshaliniuk](https://x.com/goyalshaliniuk) [将其定义为](https://x.com/goyalshaliniuk/status/2068869077326549262)（28 个赞、10 条回复、427 次浏览、6 次收藏）描述的是每次 Claude Code 重置后都得反复解释；而 Memanto 的 [文档](https://pypi.org/project/memanto/) 则把解决方案定位为本地优先的持久记忆，无需维护向量数据库。Google 的 [Interactions API 概览](https://ai.google.dev/gemini-api/docs/interactions-overview) 由 [@_philschmid](https://x.com/_philschmid) [这里](https://x.com/_philschmid/status/2069108134044467487)（39 个赞、9 条回复、2,655 次浏览、12 次收藏）发布，也从平台侧指向同一需求：服务端托管状态和后台执行。机会：直接。

### 围绕智能体动作的更安全安装、支付与审批层

信息流不断暗示同一个尚缺的产品类别：一层能让智能体动作在执行前、执行中和执行后都可审计的封装。[@probiex007](https://x.com/probiex007) [分享了](https://x.com/probiex007/status/2069108151886995707)（1 个赞、68 次浏览、1 次收藏）对应 SkillSpector 的安装时扫描；[@trythreews](https://x.com/trythreews) [新增了](https://x.com/trythreews/status/2068951336918638699)（214 个赞、48 条回复、19,175 次浏览、13 次收藏）对应 x402 流程所需的钱包交互、收据和消费上限；[@GoogleCloudTech](https://x.com/GoogleCloudTech) [展示了](https://x.com/GoogleCloudTech/status/2068770931447570457)（63 个赞、2 条回复、6,386 次浏览、16 次收藏）则说明，即便是内部迁移系统，也必须先有硬验证闭环，输出才会被信任。这个需求现实且迫切，但竞争也不小。机会：直接。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| Sakana Fugu | 编排模型/API | (+/-) | 单一端点即可完成模型路由、委派、验证和综合；在研究和近编码任务上已有公开案例 | 回复里很快就有人质疑一致性、成本，以及相比其他封装到底有多少真正新意 |
| AgentSpace | 共享智能体工作空间 | (+) | 角色、负责人、审批、审计轨迹、排期，以及面向多运行时的 AgentRouter | 这是非常新的产品类别；它与相邻工作空间工具的差异仍会引发疑问 |
| Memanto | 记忆智能体 | (+) | 本地优先的持久记忆、无需向量数据库、广泛的编码智能体集成、类型化记忆类别 | 又增加了一个需要维护的组件；当天更多得到构建者兴趣，而非广泛用户验证 |
| Interactions API | 智能体/模型 API | (+) | 模型与智能体共用单一接口，支持服务端状态、后台任务和可观测执行步骤 | SDK 生态仍未完全同步；每次交互的设置仍需重复声明 |
| AI Development Patterns | 工作流目录 | (+) | 提供 24 种模式地图，用于引入框架、安全和开发控制 | 仅提供指导，本身并不强制合规 |
| DeerFlow 2.0 | 超级智能体框架 | (+) | 子智能体、记忆、沙箱、可扩展技能，且以 MIT 协议开源 | 搭建成本高于轻量提示词或聊天工具 |
| SkillSpector | 安全扫描器 | (+) | 覆盖 16 类风险的 64 种模式，支持 CVE 查询，输出适合接入 CI | 重点是安装时的技能审查，不是完整的运行时治理 |
| Supercode | 终端 SWE 智能体 | (+/-) | 整机操作、审批、持久记忆、多模型支持，以及 Web + CLI 界面 | 广泛权限和 beta 期可靠性问题会抬高运维风险 |
| x402 | 支付协议 | (+/-) | 支持机器支付的 HTTP 端点，生态支持在扩展，且已出现可用的弹窗封装 | 早期活动仍然嘈杂；没有额外层时，钱包交互依然很难用 |
| GLM 5.2 | 开放权重模型/API 分发 | (+) | AWS Marketplace 和 Akash 上架降低了编码智能体工作负载的接入门槛 | 当天主要证据集中在分发与定位，而非深入的生产案例 |

整体满意度最高的，仍是模型周围那些明确的控制层：工作空间、记忆、扫描器、Playbook 和有状态 API。至于覆盖面更广的 beta 智能体，以及那些在缺乏同等级别安全措施下就宣称具备自主性的产品，评价则更为分化。

一个清晰的迁移趋势反复出现：人们正在从一次性的提示词技巧，转向框架、共享工作空间、记忆层和验证闭环。即便是模型分发新闻，也遵循了同样的模式。[@CarolGLMs](https://x.com/CarolGLMs) [宣布了](https://x.com/CarolGLMs/status/2068902098696339811)（299 个赞、16 条回复、40,310 次浏览、41 次收藏）提到 AWS Marketplace 上的 GLM 5.2，而 [@akashnet](https://x.com/akashnet) [新增了](https://x.com/akashnet/status/2069112975152054652)（43 个赞、2 条回复、3,303 次浏览、2 次收藏）提到同一模型在 Akash 上的可用性，因此当天关于开放模型的讨论，主要都在于构建者能在哪里把这些模型接入现有框架。

## 7. 机会在哪里

**[+++] 面向团队的共享智能体控制平面** —— AgentSpace、Memanto、Interactions API、DeerFlow 和 Supercode 都在指向同一个缺口：如果智能体要成为真实团队的一部分，而不是某个人的私人工具，就需要共享上下文、可恢复工作、审批和运行时可移植性。这个方向很强，因为直接抱怨、新产品和平台原语在同一天同时出现。

**[++] 面向智能体动作的安全与验证封装层** —— SkillSpector 的扫描器、x402 弹窗的消费上限与收据，以及 Google 经过数学验证的迁移系统，都表明市场需要能让智能体行为可检查、可设边界的产品。这个方向机会中等，因为需求非常明显，但已有多家构建者正从不同角度汇聚于此。

**[+] 开放模型分发加编排适配器** —— Sakana Fugu、AWS Marketplace 上的 GLM 5.2，以及 Akash 上的 GLM 5.2，都指向一个增长中的需求：为现有编码框架和云工作流提供替代性的模型接入路径。这个方向仍处于起步阶段，因为分发信号真实存在，但差异化空间依然拥挤，当前竞争更多建立在可用性上，而非已被证明的下游结果。

## 8. 要点

1. **编排正在成为产品层，而不只是实现细节。** Sakana Fugu 是最清晰的例子，而 Anthropic 的公开框架则为同一思路提供了更简单的架构词汇。（[来源](https://x.com/SakanaAILabs/status/2068861630327443966)）
2. **下一轮智能体竞争的主战场是团队运营，而不是个人提示词。** AgentSpace、Memanto、Interactions API、DeerFlow 和 Supercode 的重点都放在共享上下文、可恢复性、审批或沙箱执行上，而不是单纯押注一个更大的模型。（[来源](https://x.com/huang_chao4969/status/2068930040616923551)）
3. **安全的智能体动作，仍需要围绕循环外加明确封装层。** x402 弹窗补上了消费上限和收据，SkillSpector 把技能视为高风险安装面，而 Google 的迁移系统则要求输出上线前先经过硬验证。（[来源](https://x.com/trythreews/status/2068951336918638699)）
4. **开放模型的动能目前主要体现在分发，而不是丰富的部署证据。** GLM 5.2 当天最强的信号，是它面向编码智能体工作负载在 AWS Marketplace 和 Akash 上的可用性，而不是有充分文档支撑的生产案例。（[来源](https://x.com/CarolGLMs/status/2068902098696339811)）
5. **讨论正在持续从提示词转向框架。** AI Development Patterns、Anthropic 的工作流分类，以及持久记忆产品，都把模型周围那个耐久系统视为真正的杠杆来源。（[来源](https://x.com/DanKornas/status/2068771160469262568)）
