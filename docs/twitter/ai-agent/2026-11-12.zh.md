# Twitter AI 智能体 - 2026-11-12

## 1. 大家在讨论什么

### 1.1 长时间运行的智能体正被视为可靠性系统 🡕

一篇详尽的工程文章区分了短时运行的智能体和需要运行数小时的任务：前者重试一次无状态调用或许就够了，后者却可能在接近结束时失败、重复触发副作用，或丢失状态。文章提出的控制措施都是常见的分布式系统模式：检查点、幂等性、持久化事件日志和可恢复工作流。

[@arpit_bhayani](https://x.com/arpit_bhayani) [认为](https://x.com/arpit_bhayani/status/2120852903925793264)（308 个赞，53 条回复，10,343 次浏览，160 次收藏）指出，长时间运行的智能体若在接近结束时失败，可能会白白耗费 API 费用和时间。帖子列出可能导致中断的因素，包括服务提供商限流、网络故障、Pod 被驱逐、上下文溢出和人工暂停，并指出这些问题往往属于软件系统问题，而非模型问题。

**讨论要点：** 一条回复只说，“100 步里的第 95 步”这个例子让人很心疼；截取的讨论串更多是在表达共情，几乎没有反驳证据。

**与前一日对比：** 11 月 11 日讨论的是工作流评估和工具链可靠性。今天的帖子则把运行后期的故障恢复和状态持久性作为核心设计问题。

### 1.2 安全响应被视为工程瓶颈 →

一位从业者认为，改进事件响应也能提升交付速度；智能体生成的变更越多，就越需要有纪律地打补丁、进行测试并建立反馈闭环。这篇文章将演讲中的主题延伸到背压和基于属性的测试；这是一种工程观点，并非经过测量的全行业结论。

[@GeoffreyHuntley](https://x.com/GeoffreyHuntley) [分享了](https://x.com/GeoffreyHuntley/status/2120602355066659231)（160 个赞，15 条回复，6,740 次浏览，167 次收藏）分享了一场关于安全与软件工程的演讲。其中，[文章](https://ghuntley.com/answer/) 主张优化事件响应，并将工程循环、背压和基于属性的测试纳入工程方法。

**与前一日对比：** 前一份报告讨论可靠性时，重点是智能体行为和可观测性；这篇帖子则将视角扩展到智能体周边软件的维护与安全保障。

### 1.3 可复用技能和按角色路由模型正成为实用模式 🡕

两篇帖子介绍了如何打包或拆分工作，而不是每次会话都重复提供宽泛指令。一篇建议用不同的 Claude 模型分别负责实现、代码库搜索和评审；另一篇介绍微软开源的 .NET 技能集合，涵盖升级、数据、测试和 MCP 服务器工作流。

[@xsmryze](https://x.com/xsmryze) [描述了](https://x.com/xsmryze/status/2120635742548312351)（63 个赞，10 条回复，6,231 次浏览，83 次收藏）展示了一套 Claude Code 配置方案：日常实现交给 Sonnet，代码库搜索交给 Haiku，部分规划或评审决策则交给 Opus。有回复者称，对自己而言，顾问角色最能节省成本；节省的令牌数量只是作者的个人体验，并非基准测试结果。

[@AntonMartyniuk](https://x.com/AntonMartyniuk) [介绍了](https://x.com/AntonMartyniuk/status/2120859198988632457)（74 个赞，16 条回复，2,045 次浏览，68 次收藏）介绍了微软开源的 [dotnet/skills 仓库](https://github.com/dotnet/skills)：一套供编码智能体使用的可复用指令。帖子中的信息图按插件归类技能，包括测试、升级和 MCP 相关工作。

![Microsoft .NET 技能，按插件分组，涵盖测试、升级、数据和 MCP 技能](https://pbs.twimg.com/media/HW7OMmUXUAAbnkX.jpg)

**讨论要点：** 一条针对 .NET 帖子的回复指出，代码库的实际进展已经超出帖子发布时的快照：现在有 16 个插件和 108 个技能文件，而不是 14 个插件和 99 个技能文件（[回复](https://x.com/jacobho79/status/2120874903499092036)（1 条回复，12 次浏览））。这是对快照数据的有用更正，并非对技能格式的异议。

**与前一日对比：** 11 月 11 日从概念层面讨论了持久化记忆和可复用技能；今天的案例则展示了模型路由方案，以及一个针对具体任务的技能集合。

## 2. 大家感到挫败的地方

### 长时间运行的智能体可能丢失几乎完成的运行进度

**严重程度：对于多小时任务而言较高； 普遍程度尚未得到证实。** 作者列举了速率限制、超时、工作进程被驱逐、上下文溢出和人工暂停等可能导致中断的因素，并提醒说，重试可能会重复产生副作用。建议的应对方法包括检查点、幂等性、持久化日志和可恢复执行。 ([@arpit_bhayani](https://x.com/arpit_bhayani/status/2120852903925793264)（308 个赞，53 条回复，10,343 次浏览，160 次收藏，7 条引用，19 次转发）)

### 可复用技能可能过时，或不够贴合项目

**严重程度：中。** 这篇 .NET 技能帖指出，共享指令不了解团队的项目规范。还有回复指出，帖中列出的 99 项技能、14 个插件，相较于仓库主分支的内容已经过时。这带来了实际的维护问题：使用者需要核实当前的技能列表，并补充本地项目背景。 ([帖子](https://x.com/AntonMartyniuk/status/2120859198988632457)（74 个赞，16 条回复，2,045 次浏览，68 次收藏，12 次转发）, [仓库](https://github.com/dotnet/skills), [更正](https://x.com/jacobho79/status/2120874903499092036)（1 条回复，12 次浏览）)

### 安全工作可能挤占交付时间

**严重程度：中，依据一位从业者的说法。** Geoffrey Huntley 认为，事件响应和补丁更新需要跟上变化的步伐；安全工作应被视为工程工作，而不是项目后期的一项独立检查。这篇帖子表达了一种观点并列举了实例，并未估算这种情况的普遍程度。 ([演讲整理稿](https://ghuntley.com/answer/))

## 3. 人们希望拥有哪些功能

### 支持恢复长时间运行任务的工作流

人们明确提出了这些需求：检查点、幂等操作、持久化事件日志，以及在服务提供方、基础设施或人工暂停后恢复执行的能力。对于工作持续数小时的智能体来说，这些都是实际需求，而不只是需要更长的上下文窗口。**紧迫性：长任务中较高。机会：直接。** ([来源](https://x.com/arpit_bhayani/status/2120852903925793264)（308 个赞，53 条回复，10,343 次浏览，160 次收藏，7 条引用，19 次转发）)

### 贴合团队项目且保持更新的技能

这篇 .NET 技能帖指出，共享指令不了解特定仓库的规范；另有回复指出，帖中列出的技能数量已经过时。本地覆盖层和带版本管理的技能目录只能部分解决这一问题。**紧迫性：中。机会：直接。** ([帖子](https://x.com/AntonMartyniuk/status/2120859198988632457)（74 个赞，16 条回复，2,045 次浏览，68 次收藏，12 次转发）, [更正](https://x.com/jacobho79/status/2120874903499092036)（1 条回复，12 次浏览）)

### 更快、可观测性更强的安全响应

Geoffrey Huntley 的文章主张通过工程手段加快事件响应，并围绕变更做好测试和背压管理。这是一种愿景，而非具体的产品需求。**紧迫性：发生事件时较高。机会：愿景性。** ([文章](https://ghuntley.com/answer/))
