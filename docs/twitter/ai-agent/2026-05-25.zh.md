# Twitter AI Agent - 2026-05-25

## 1. 人们在讨论什么

### 1.1 Agent 记忆正从上下文窗口迁移到可复用文件中 🡕

5 月 25 日最明显的模式是，构建者不再想把所有工具、MCP 和笔记都塞进实时上下文里。他们想要的是冷存储、选择性加载，以及可复用的技能产物。至少有四个保留条目指向同一个方向：Obsidian 笔记、Markdown 技能记忆、可迁移的技能库，以及用于 harness 设计的资源包。

[@EXM7777](https://x.com/EXM7777) [描述了](https://x.com/EXM7777/status/2058609483790836095)（289 个赞，15 条回复，16,368 次浏览，437 个收藏）提出用 Obsidian 作为记忆层，存放那些需要保持可搜索、但不应长期加载在 Claude Code 或 Codex 中的工具。最有力的一条回复把这个想法进一步提炼成架构语言：工具记忆放在冷存储里，活跃执行上下文保持“热”状态，只在任务真正需要时拉取少量相关内容。

[@GithubProjects](https://x.com/GithubProjects) [重点展示了](https://x.com/GithubProjects/status/2058595860657893483)（81 个赞，4 条回复，7,735 次浏览，93 个收藏）将 Acontext 定位为原生支持 Markdown 的技能记忆层。[Acontext 仓库](https://github.com/memodb-io/Acontext) 将其描述为“作为记忆层的 Agent Skills”，而附图中的 README 卡片比推文本身更能体现成熟度：有网站和文档链接，已发布 PyPI 和 npm 包，核心、API 和 CLI 测试也都通过。

![Acontext 的 README 卡片，展示了网站/文档链接、已发布的软件包以及通过的测试](https://pbs.twimg.com/media/HJGaBppbMAAgGIs.jpg)

[@DanKornas](https://x.com/DanKornas) [分享了](https://x.com/DanKornas/status/2058771524547489942)（34 个赞，4 条回复，1,684 次浏览，44 个收藏）介绍了 SkillX，[SkillX 仓库](https://github.com/zjunlp/SkillX) 称它能把成功轨迹提炼为可复用的规划技能、功能技能和原子技能，并在无需重新训练的情况下接入能力较弱的 Agent。[@tom_doerr](https://x.com/tom_doerr) [添加了](https://x.com/tom_doerr/status/2058727422623674502)（55 个赞，4 条回复，3,110 次浏览，69 个收藏）则分享了一份 [200+ 项 harness engineering 资源列表](https://github.com/Picrew/awesome-agent-harness)，把同一主题整理成公开的文件、工具和实践地图。

**讨论洞察：** 回复里并没有人要求更大的窗口，而是在呼吁更清晰地划分归档与运行时、更明确地说明工具为何被加载，以及能跨会话、跨 Agent 持续存在的可复用文件。

**与前一天相比：** 5 月 24 日已经在推动可编辑记忆和选择性加载；到了 5 月 25 日，这种基于文件的路线变得更明确：一边是 Obsidian 冷存储，另一边是 Acontext 和 SkillX 这类可交付的技能库。

### 1.2 Harness 工程从口号变成了具体的设计学科 🡕

第二个大主题是，Agent 构建者如今开始把提示词、上下文和 harness 视为彼此独立的工程层。最强的帖子并不是模型发布，而是围绕模型之外、可靠 Agent 环境还需要什么的图示、实现指南和文章。

[@sjsandeep_jain](https://x.com/sjsandeep_jain) [认为](https://x.com/sjsandeep_jain/status/2058438583351152735)（97 个赞，10 条回复，1,406 次浏览，45 个收藏）指出，如今“最重要的 AI 技能”已经是围绕模型设计系统，而不是孤立地做提示词工程。附图把三者区分得很明确：提示词工程塑造单次请求，上下文工程决定哪些内容留在窗口内，而 harness 工程则把收集、执行、验证和重试封装成一台机器。

![将 prompt、context 以及 gather-act-verify 循环分离展示的 harness engineering 图示](https://pbs.twimg.com/media/HJEK-jbboAAgPg9.jpg)

[@bibryam](https://x.com/bibryam) [特别指出了](https://x.com/bibryam/status/2058909142069170392)（101 个赞，5 条回复，5,569 次浏览，134 个收藏）把一篇 OpenAI 文章称为“harness 工程师的金矿”，强调的是 Agent 可稳定运行的环境、把工程判断机械化编码的方式，以及 Agent 可读取的可观测性。回复串补上了关键提醒：一旦可观测性变成 Agent 可读，执行边界本身也会进入安全模型。

[@harjtaggar](https://x.com/harjtaggar) [总结了](https://x.com/harjtaggar/status/2058646609173610953)（120 个赞，14 条回复，9,916 次浏览，26 个收藏）则更直白地描述了真实体验：每个 Agent 项目一开始都很简单，最后却都会深陷检索质量、上下文工程和跨模态评估循环。[@tom_doerr](https://x.com/tom_doerr) [佐证了这一点](https://x.com/tom_doerr/status/2058727422623674502)（55 个赞，4 条回复，3,110 次浏览，69 个收藏）则给出了 Picrew harness 资源清单，仓库将其描述为一个汇集项目、工具、基准和实用指南的精选列表。

**讨论洞察：** 实际问题已经不再是“什么提示词有效？”，而是“该收集什么、该保留加载什么、如何验证，以及 harness 自身失效时会发生什么？”

**与前一天相比：** 5 月 24 日，harness 工程还只是逐渐成为共同语言；到 5 月 25 日，讨论已经转向资源库、实现图示，以及构建者可以立即上手的基础设施指导。

### 1.3 重验证的 Agent 系统进入主流讨论 🡕

最值得注意的突破信号是，Agent 系统开始出现在那些必须检查正确性、而不是只凭口头断言的领域里。形式化证明搜索、形式化代码生成，以及面向安全的 Agent 套件，都出现在同一天的内容集中。

[@pushmeet](https://x.com/pushmeet) [报告了](https://x.com/pushmeet/status/2058936037754224998)（696 个赞，45 条回复，40,683 次浏览，181 个收藏）称 Google DeepMind 的 AlphaProof Nexus 解决了 9 个开放的 Erdős 问题、44 个 OEIS 问题、一个已有 15 年历史的代数几何问题，以及一个已有 7 年历史的极小极大优化问题。公开的 [AlphaProof Nexus 结果仓库](https://github.com/google-deepmind/alphaproof-nexus-results) 包含这些已解问题的 Lean 证明；附带的证明表格之所以重要，是因为它表明这并不是含糊的“AI 解决了数学问题”式说法，而是与明确证明技术绑定、可由机器检查的输出。

![证明表，列出了已解决问题的 AlphaProof Nexus conjecture ID 和证明技术](https://pbs.twimg.com/media/HJLPWp5WgAA7cBb.png)

[@getjonwithit](https://x.com/getjonwithit) [介绍了](https://x.com/getjonwithit/status/2058706179216359885)（83 个赞，4 条回复，7,220 次浏览，49 个收藏）介绍了一个面向计算物理和应用数学的编程与形式化验证 Agent，目标是生成 DSL 代码、在 Lean、Isabelle 或 Rocq 中形式化正确性属性，然后编译出可证明正确的 C 代码。回复明确指出了真正的约束：代码的形式正确性并不等同于底层物理模型的正确性，因此验证范围仍需谨慎界定。

[@The_Cyber_News](https://x.com/The_Cyber_News) [分享了](https://x.com/The_Cyber_News/status/2058815833217044796)（56 个赞，3 条回复，2,815 次浏览，30 个收藏）介绍了 Pentest Agent Suite，相关 [Cyber Security News 文章](https://cybersecuritynews.com/pentest-agent-suite/) 称这一开源包涵盖 50 个专用安全 Agent、26 个斜杠命令、19 个 CLI 工具，以及一个覆盖七个编码平台的跨 IDE 安装器。对构建者来说，这是一个很强的信号，因为它把安全审查封装成了结构化的 Agent 工作面，而不是又一个通用助手。

**讨论洞察：** 最有说服力的 Agent 主张，都是那些绑定了检查器的：Lean、证明助手、仓库规则，或安全工作流。这组数据奖励的是可验证性，而不是单纯更强的自主性。

**与前一天相比：** 5 月 24 日强调的是争议处理、仪表板和审查闸门等信任界面；到 5 月 25 日，这种倾向进一步推进到了数学可检验证明、形式化代码路径，以及面向安全的 Agent 框架。

## 2. 什么让人沮丧

### 上下文膨胀仍在让 Agent 变得更差，而不是更好

严重程度：高。[@EXM7777](https://x.com/EXM7777) [写道](https://x.com/EXM7777/status/2058609483790836095)（289 个赞，15 条回复，16,368 次浏览，437 个收藏）指出，把更多技能、MCP 和上下文堆进 Claude Code 或 Codex，只会让它们更慢、更不可预测。[@harjtaggar](https://x.com/harjtaggar) [表示](https://x.com/harjtaggar/status/2058646609173610953)（120 个赞，14 条回复，9,916 次浏览，26 个收藏）指出，Agent 项目很快就会陷入检索与评估复杂性；[@GithubProjects](https://x.com/GithubProjects) [推广了](https://x.com/GithubProjects/status/2058595860657893483)（81 个赞，4 条回复，7,735 次浏览，93 个收藏）则把 Acontext 明确呈现为对抗不透明记忆堆叠的替代方案。眼下可见的应对方式是选择性加载和外部记忆存储，但这也把更多架构工作压到了构建者身上。是否值得为此构建：是——这个痛点反复出现、具有操作层面的现实性，而且已经在塑造人们日常使用 Agent 的方式。

### 可靠性工作仍被藏在“Agent 工程”这个标签之下

严重程度：高。[@sjsandeep_jain](https://x.com/sjsandeep_jain) [展示了](https://x.com/sjsandeep_jain/status/2058438583351152735)（97 个赞，10 条回复，1,406 次浏览，45 个收藏）指出，提示词、上下文和 harness 问题现在必须分开工程化处理；[@bibryam](https://x.com/bibryam) [认为](https://x.com/bibryam/status/2058909142069170392)（101 个赞，5 条回复，5,569 次浏览，134 个收藏）则指出，真正的工作在于环境设计、机械化反馈回路，以及 Agent 可读取的可观测性。[@harjtaggar](https://x.com/harjtaggar) [概括道](https://x.com/harjtaggar/status/2058646609173610953)（120 个赞，14 条回复，9,916 次浏览，26 个收藏）直接说出了这种挫败：人们原本以为可以快速搭起来，最后却一头扎进检索质量和跨模态评估循环。是否值得为此构建：是——这正是为什么“简单”的 Agent 点子仍然需要真正工程投入的主要原因。

### 开源 Agent 仍需要更友好的控制中枢

严重程度：中。[@hasantoxr](https://x.com/hasantoxr) [表示](https://x.com/hasantoxr/status/2058954220934766799)（31 个赞，6 条回复，1,757 次浏览，37 个收藏）指出，Hermes Desktop 之所以存在，是因为终端优先的 Agent 隐藏了太多状态、悄悄出错，还把原本普通的配置过程变得过于技术化。回复总体支持，但也带着怀疑：有人说这正是开源 Agent 需要的界面，也有人提醒，GUI 可能只是让失败更容易被看见。是否值得为此构建：是——这种工作流痛点非常实际，也关系到更广泛的采用，尽管单靠 UI 并不能解决更深层的可靠性问题。

## 3. 人们希望存在什么

### 留在实时上下文窗口之外、但可搜索的冷存储

这是数据里最直接的需求。[@EXM7777](https://x.com/EXM7777) [想要](https://x.com/EXM7777/status/2058609483790836095)（289 个赞，15 条回复，16,368 次浏览，437 个收藏）展示了一个不断扩大的、由 Obsidian 支撑的工具库，只在任务需要时才加载；最有力的回复也用系统语言表达了同样的意思：选项放进冷存储，执行放进热上下文。Acontext 和 SkillX 是部分答案，但真正的需求是那种可搜索、可版本化、并且能低成本留在提示词之外的记忆。机会：直接。

### 可检查、可重放、可被信任的 Agent 输出

最清晰的信号来自重验证的构建者。[@pushmeet](https://x.com/pushmeet) [分享了](https://x.com/pushmeet/status/2058936037754224998)（696 个赞，45 条回复，40,683 次浏览，181 个收藏）提到 AlphaProof Nexus 并链接到了形式化证明，[@getjonwithit](https://x.com/getjonwithit) [将其定义为](https://x.com/getjonwithit/status/2058706179216359885)（83 个赞，4 条回复，7,220 次浏览，49 个收藏）把形式化验证作为新编程 Agent 的核心功能，[@The_Cyber_News](https://x.com/The_Cyber_News) [指向了](https://x.com/The_Cyber_News/status/2058815833217044796)（56 个赞，3 条回复，2,815 次浏览，30 个收藏）则展示了完整的安全 Agent 套件。缺失的并不是更自信的文字，而是能被证明系统、仓库规则或安全闸门检查的输出。机会：直接且竞争激烈。

### 让普通人也能用起来的开源 Agent 控制中枢

[@hasantoxr](https://x.com/hasantoxr) [认为](https://x.com/hasantoxr/status/2058954220934766799)（31 个赞，6 条回复，1,757 次浏览，37 个收藏）指出，Hermes Desktop 之所以重要，是因为大多数开源 Agent 仍让用户直面配置摩擦、隐藏状态和终端复杂性。这是一个现实的产品需求，而不是理想化愿景。这里的竞争很可能会很激烈，因为底层 Agent 能力正越来越开放，而界面与故障恢复体验仍然薄弱。机会：直接且竞争激烈。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| Obsidian | 外部记忆层 | (+) | 让工具在实时上下文之外仍可搜索；适合选择性加载工作流 | 仍然依赖人工整理，内容新鲜度也很重要 |
| Acontext | 技能记忆层 | (+) | 可编辑的 Markdown 技能、无 API 锁定、支持 ZIP 导出，软件包成熟度也清晰可见 | 从软件包版本和社区规模看仍属早期 |
| SkillX | 技能知识库框架 | (+) | 三级技能层级、可从轨迹自动蒸馏、支持可迁移技能库 | 工作流研究色彩较重；对主流团队仍偏早期 |
| AlphaProof Nexus | 形式化证明 Agent | (+) | 可由机器检查的 Lean 证明和公开结果仓库，让相关主张具备可验证性 | 适用领域较窄，形式化负担高 |
| awesome-agent-harness | 资源库 | (+) | 公开汇总大量 harness 项目、基准和指南 | 它是参考列表，不是执行系统 |
| Pentest Agent Suite | 安全 Agent 框架 | (+/-) | 专用 Agent、斜杠命令、MCP 基础设施、跨工具安装器 | 这里的证据主要来自一篇新闻写作和一条推文，而非广泛的操作者反馈 |
| Hermes Desktop | Agent 控制界面 | (+/-) | 更易管理配置、记忆、工具、提供商、日程和日志 | UI 提升了可见性，但回复仍质疑它是否解决了更深层的失效模式 |

总体来看，人们更偏好基于文件的记忆、明确的结构，以及能展示自己在做什么的系统。当工具减少隐藏状态或提升可复用性时，满意度最高；而当表面积扩张快于可靠性证明时，评价就会变得复杂。当天帖子里反复出现的共同应对方式很一致：保持工作集小、把可复用知识版本化，并在输出外围加上一种检查器。

Acontext 和 SkillX 是最清晰的记忆层构建，但它们解决的是相邻问题。Acontext 把学习结果打包成人类可读的文件，并可跨环境导出；SkillX 则把成功轨迹转成结构化、可复用的技能层级。二者背后的共同触发因素，就是第 1 到第 4 节反复出现的那种挫败：Agent 总在重新学习团队早已知道的东西。

AlphaProof Nexus 和 Pentest Agent Suite 则把同样的“打包”思路带进了重验证工作。一者把证明搜索变成公开的 Lean 产物；另一者把进攻性安全变成带斜杠命令和工具基础设施的多 Agent 框架。反复出现的构建模式不是“再来一个聊天机器人”，而是围绕那些输出必须被检查的领域，做出可复用的封装层。

Hermes Desktop 代表的是这股趋势中的可用性层。它在这组数据里的重要性，不在于绝对新颖，而在于开源 Agent 构建者如今开始把精力投向界面、日程、日志和故障恢复，而不只是继续堆更多自主性。

## 6. 新动态与值得关注的内容
