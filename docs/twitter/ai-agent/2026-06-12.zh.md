# Twitter AI Agent - 2026-06-12

## 1. 人们在讨论什么

### 1.1 验证层已成为应对自主智能体风险的默认答案（🡕）

6 月 12 日最强的一组讨论，焦点不是原始自主性，而是可证明性。高信号帖子不断收敛到同一个要求：如果智能体要写代码、安装插件、转移资金，或在不同系统间携带身份，运营方就希望获得可验证的输出、可审计的安装过程，以及能支撑长时间运行的审查界面。

[@Test_Sprite](https://x.com/Test_Sprite) [宣布](https://x.com/Test_Sprite/status/2065238279784735014)（89 个赞、72 条回复、47 次收藏、1,840 次浏览）介绍了开源项目 [TestSprite CLI](https://github.com/TestSprite/testsprite-cli)，并将其描述为一个由智能体调用的端到端测试闭环：像真实用户一样操作线上应用，返回单一故障包，并在修复后重新检查。其 README 比这条推文走得更远：它把 TestSprite 定位为智能体编程的验证层，并指向 [CoderCup](https://codercup.ai)，作为“只要验证始终留在闭环中，更便宜的模型也能做出最正确的应用”这一说法的公开证据。

[@kevinkern](https://x.com/kevinkern) [推出](https://x.com/kevinkern/status/2065152449027924195)（13 个赞、19 次收藏、1,220 次浏览）介绍了 [Planr](https://github.com/EchoForge31/planr)：一个面向编程智能体、本地优先的任务图系统，其中工作项可以相互阻塞或解锁，每项任务结束时都会附带工作日志，且必须由第二个智能体重新运行证据，工作才算完成。公开 README 进一步补充了实现细节：Rust CLI、SQLite 图存储、MCP 集成，以及一个用于本地检查的浏览器审查工作区。

[@XFreeze](https://x.com/XFreeze) [认为](https://x.com/XFreeze/status/2065333739312590983)（159 个赞、39 条回复、10,372 次浏览、26 次收藏）认为，xAI 的 Grok Build Plugin Marketplace 真正重要的不是覆盖面，而是信任，因为每个远程插件都固定到特定的 commit SHA，并会在安装时接受验证。xAI 公开的 [plugin-marketplace 仓库](https://github.com/xai-org/plugin-marketplace) 也证实，远程来源必须固定到完整的 40 位 commit SHA，而 Grok Build 会在克隆后重新验证 `HEAD == sha`。

![Grok Build marketplace 界面截图，展示已上线插件及其技能、命令和 MCP 服务器数量](https://pbs.twimg.com/media/HKmJtw5bQAAI5XA.jpg)

[@virtuals_io](https://x.com/virtuals_io) [发布](https://x.com/virtuals_io/status/2065324579669897236)（164 个赞、22 条回复、9,566 次浏览、18 次收藏）认为，ERC-8126 可让智能体在不暴露内部私密信息的前提下，证明其安全审查状态或钱包控制权。配图卡片和公开的 [EIP 条目](https://eip.tools/eip/8126) 都将其标注为 AI 智能体验证标准，因此这条推文并不只是口号式评论，而是在具体尝试为可移植信任建立标准。

![ERC-8126 草案卡片，显示 AI Agent Verification 标准标题、作者和所需 EIPs](https://pbs.twimg.com/media/HKmBwqcbkAA2rw9.jpg)

**讨论洞察：** 回复并未只是歌颂开放性。大家反复回到信任界面的盲点上，比如希望在安装前看到插件内容清单，也希望验证信息能随智能体一起流转，而不是被锁在某一家供应商的技术栈里。

**与前一天相比：** 6 月 11 日强调的是可检查的软件工厂、审批和恢复路径。到 6 月 12 日，这种担忧进一步落到了具体产物上：验证 CLI、任务图、固定 SHA 的插件目录，以及验证标准草案。

### 1.2 Harness engineering 从编程扩展到设计、研究和招聘（🡕）

第二大主题是，harness engineering 正从编程智能体的一门专门方法，扩展成更广泛的运营模式。当天的帖子显示，已有公司为此招聘，设计师要求专门的 playground 基础设施，研究人员明确列出缺失的控制原语，开发者则通过拆分规划与实现来控制成本并提高审查质量。

[@itsericlay](https://x.com/itsericlay) [发布](https://x.com/itsericlay/status/2065109232115220901)（179 个赞、32 条回复、133 次收藏、17,968 次浏览）发布了一组正在招聘的职位，其中包括一个 Founding Harness Engineer 岗位，基础年薪为 130,000-200,000 美元，另加股权。这之所以重要，是因为整条招聘串把 harness 工作视为独立预算项，而回复区随即开始争论，这样的薪酬是否匹配该岗位的职责范围和人才稀缺性。

[@yitong](https://x.com/yitong) [提出](https://x.com/yitong/status/2065464869529452569)（146 个赞、17 条回复、63 次收藏、8,016 次浏览）认为，Figma 应该构建明确的设计 playground，让设计师维护约束、测试、技能和设计原则，同时让团队成员向智能体请求新的原型。回复中，有开发者表示他们团队已经用一次性的 spike 分支来做交互式原型；但作者回应说，干净、轻量、独立的仓库能让智能体迭代更快，也能让“design infra”像创意指导一样，成为一项真实岗位职能。

[@Vtrivedy10](https://x.com/Vtrivedy10) [概述](https://x.com/Vtrivedy10/status/2065144884810440916)（60 个赞、7 条回复、76 次收藏、3,180 次浏览）列出了“auto-research as a service” harness 所需要的条件：持久化沙箱基础设施、文件系统和凭证管理、带有强先验的技能文件、外部训练/工具 CLI、强制执行的运行预算，以及一个类似 `/goal` 的原语。这条帖子之所以值得注意，在于它用运营术语明确点出了缺失的产品界面，而不是泛泛要求一个更聪明的模型。

[@DanHMcInerney](https://x.com/DanHMcInerney) [分享](https://x.com/DanHMcInerney/status/2065469817734254901)（60 个赞、86 次收藏、27,735 次浏览）介绍了 [architect-loop](https://github.com/DanMcInerney/architect-loop)，并表示应由 Fable 负责设计和审查，由 Codex 5.5 负责构建。该仓库对这种分工有精确记录：先写规范和关卡，再由 Codex 在隔离的 git worktree 中工作，最后由 Fable 在集成前裁决证据是否过关。

**讨论洞察：** 回复进一步收紧了这项工作的定义。招聘帖下关于薪酬的争论、设计 playground 帖下“为什么不直接在应用里做原型”的质疑，以及 architect-loop 以仓库为中心的规则，都指向同一点：harness engineering 正逐渐变成定义边界、预算和可审查状态的工作，而不只是写巧妙提示词。

**与前一天相比：** 6 月 11 日把 harness engineering 当作一个新兴劳动力市场。到了 6 月 12 日，人们已经把这份工作的具体内容补齐了：设计沙箱、研究预算，以及模型路由打法。

### 1.3 模型竞争转向 token 效率与安全云端执行（🡕）

第三组讨论，关注点不再是“谁是最强模型”的炫耀，而是某个模型或平台能否让长时间运行的智能体工作更便宜、更可移植，或更容易监督。最有意思的帖子把性能描述成一种运营决策，涉及 token 消耗、执行环境和运行持久性。

[@Kimi_Moonshot](https://x.com/Kimi_Moonshot) [发布](https://x.com/Kimi_Moonshot/status/2065377579130142937)（172 个赞、19 条回复、20 条引用、2,500 次浏览）介绍 Kimi-K2.7-Code，将其定位为开源编程模型：在 Kimi Code Bench v2 上提升 21.8%，在 Program Bench 上提升 11.0%，在 MLS Bench Lite 上提升 31.5%，推理 token 使用量比 K2.6 低 30%。配图明确说明了这一定位：一张图将 K2.7 与 GPT-5.5、Opus 4.8 在编程和智能体基准上的表现做对比；另一张图则主张，在三个内部基准上，K2.7 以比 K2.6 更少的 token 取得了更好的结果，因此在成本轴上向左移动。

![基准测试图表，对比 Kimi K2.7 Code 与 Kimi K2.6、GPT-5.5 和 Opus 4.8 在编程和 agent 任务中的表现](https://pbs.twimg.com/media/HKmxoVmagAAJKj8.jpg)

![散点图，显示 Kimi K2.7 Code 在使用比 Kimi K2.6 更少 token 的同时提升了基准测试分数](https://pbs.twimg.com/media/HKmxpGYaUAAstZB.jpg)

[@mojombo](https://x.com/mojombo) [撰文](https://x.com/mojombo/status/2065499556188397599)（41 个赞、3 条回复、4,522 次浏览）称，Ona（前身为 Gitpod）将加入 OpenAI，把安全云端执行和异步智能体编排带入 Codex。Ona 公开的 [公告](https://ona.com/stories/ona-joins-openai) 表示，其每周生产环境智能体会话数已增长 13 倍，并把核心资产描述为可信、由客户控制的云环境，使工作能够跨设备持续，并深入企业系统内部。

[@mlejva](https://x.com/mlejva) [描述](https://x.com/mlejva/status/2065497322419863772)（25 个赞、6 条回复、5 条引用、3,862 次浏览、12 次收藏）介绍了一个面向金融机构的生产方案：Rogo 将 Claude Managed Agents 与自托管 E2B 沙箱配对，所有由智能体生成的代码运行都在隔离的 microVM 中执行，且具备完整的可审计性与可追溯性。还有一条回复补充了一个实用监督规则：低置信度工作在到达客户之前，仍应先转交人工。

**讨论洞察：** 共同的问题不是智能体能不能做更多，而是其运行时能否让输出既负担得起，又可治理。Kimi 的自身叙事聚焦于更低的推理 token 使用，而 Ona 和 Rogo 案例则聚焦于持久性、隔离与审计轨迹。

**与前一天相比：** 6 月 11 日最强的能力信号，是 Fable 在知识工作上的准确性。到 6 月 12 日，重点已转向更便宜的推理、模型角色拆分，以及能承载长时间运行工作的安全环境。

## 2. 什么让人感到挫败

### 生成之后，验证依然会失灵

严重程度：高。[@Test_Sprite](https://x.com/Test_Sprite) [将其定义为](https://x.com/Test_Sprite/status/2065238279784735014)（89 个赞、72 条回复、1,840 次浏览、47 次收藏）直接点出了核心问题：智能体可以跑一整夜，却依然不知道它做出来的东西到底能不能用。[@kevinkern](https://x.com/kevinkern) [回应](https://x.com/kevinkern/status/2065152449027924195)（13 个赞、1,220 次浏览）则给出了一种任务图方案：每个任务都要以工作日志收尾，并由第二个智能体重新运行证据，这也说明修补方式仍然非常依赖人工流程。之所以说这很值得做成产品，是因为这两条帖子都默认这个缺口已经普遍到需要专门工具，而不是靠一次性的提示词技巧来补。

### 长时间运行的自主性仍需要明确的预算、状态和恢复机制

严重程度：高。[@Vtrivedy10](https://x.com/Vtrivedy10) [列出](https://x.com/Vtrivedy10/status/2065144884810440916)（60 个赞、76 次收藏、3,180 次浏览）逐项列出了自动研究所缺失的原语：持久化沙箱基础设施、凭证、外部预算更新，以及目标原语。[@DanHMcInerney](https://x.com/DanHMcInerney) [表示](https://x.com/DanHMcInerney/status/2065469817734254901)（60 个赞、86 次收藏、27,735 次浏览）表示 Fable“太烧钱”，随后又在 [architect-loop](https://github.com/DanMcInerney/architect-loop) 中把规划与审查交给 Fable，把实现工作转给 Codex。[@mojombo](https://x.com/mojombo) [补充](https://x.com/mojombo/status/2065499556188397599)（41 个赞、4,522 次浏览）则认为，安全云端执行与异步编排如今已经战略性到足以让 OpenAI 收购 Ona。之所以值得构建，是因为当前的应对模式仍然是一种架构层面的权宜之计：按角色拆分模型，把工作迁移到受控云环境，并把恢复状态保存到聊天窗口之外。

### 插件、身份与支付之间的信任边界仍然割裂

严重程度：高。[@XFreeze](https://x.com/XFreeze) [重点介绍](https://x.com/XFreeze/status/2065333739312590983)（159 个赞、39 条回复、10,372 次浏览）把固定 SHA 的插件安装视为 Grok Build 市场真正的解锁点，而 xAI 自己的 [目录 README](https://github.com/xai-org/plugin-marketplace/blob/main/README.md) 仍警告称，第三方插件可能执行任意代码，且未经 xAI 验证。[@virtuals_io](https://x.com/virtuals_io) [推送](https://x.com/virtuals_io/status/2065324579669897236)（164 个赞、22 条回复、9,566 次浏览）将 ERC-8126 视为一种方式，让智能体可以在不泄露内部信息的前提下证明代码审查状态或钱包控制权；而 [@Cloudflare](https://x.com/Cloudflare) [连接](https://x.com/Cloudflare/status/2065279639535456392)（49 个赞、4,964 次浏览）则把智能体支付连接到了 Web Bot Auth 和 Mastercard 基础设施上。之所以痛感强烈，是因为每一层都在用不同方式处理信任问题，这意味着团队仍得自己把插件来源、身份凭证和支付权限拼接起来。

## 3. 人们希望出现什么

### 面向智能体的通用运行账本

人们想要的是一个控制平面：它能记住一次运行，执行预算，并在事后证明到底发生了什么。[@Vtrivedy10](https://x.com/Vtrivedy10) [概述](https://x.com/Vtrivedy10/status/2065144884810440916)（60 个赞、7 条回复、3,180 次浏览、76 次收藏）提出了持久化沙箱、凭证管理和外部强制预算；[@kevinkern](https://x.com/kevinkern) [推出](https://x.com/kevinkern/status/2065152449027924195)（13 个赞、1,220 次浏览、19 次收藏）则提出了一个任务图，让审查证据和恢复机制都留在仓库内部。[@mojombo](https://x.com/mojombo) [撰文](https://x.com/mojombo/status/2065499556188397599)（41 个赞、3 条回复、4,522 次浏览）认为，安全云端执行和异步编排已经战略性到足以把 Ona 纳入 Codex。再结合 Ona 的 [公开说明](https://ona.com/stories/ona-joins-openai)，这一诉求还出现了企业版形态：工作能跨设备持续，状态、工具和访问权限都由客户掌控。这是一个有明确直接需求的现实问题。机会：直接。

### 面向非工程团队的智能体 playground

[@yitong](https://x.com/yitong) [提出](https://x.com/yitong/status/2065464869529452569)（146 个赞、17 条回复、8,016 次浏览、63 次收藏）提出了一个设计 playground，让设计师维护约束、测试和原则，同时允许团队成员向智能体请求原型。回复通过对比“独立、轻量的 playground”和“在主应用里用 spike 分支做原型”，让这种需求更具体了。这不是愿景式想象：缺失的产品不是另一个通用模型，而是一个支持快速迭代、共享和可重置实验的沙箱界面。机会：直接。

### 在运行中就公开花费与工具的研究 harness

[@Vtrivedy10](https://x.com/Vtrivedy10) [描述](https://x.com/Vtrivedy10/status/2065144884810440916)（60 个赞、7 条回复、3,180 次浏览、76 次收藏）提出一种服务型产品：在一次运行尚未结束时，就暴露文件系统访问、凭证处理、外部训练/工具 CLI 以及花费更新。[@DanHMcInerney](https://x.com/DanHMcInerney) [分享](https://x.com/DanHMcInerney/status/2065469817734254901)（60 个赞、27,735 次浏览、86 次收藏）则提到 [architect-loop 仓库](https://github.com/DanMcInerney/architect-loop)，从编程侧指向同一需求：把昂贵的规划与较便宜的实现拆开，并强制进行以证据为依据的审查。需求既紧迫又实际，因为开发者已经在手工拼装这些控制机制。机会：直接。

### 面向自主智能体的可移植信任与支付轨道

[@virtuals_io](https://x.com/virtuals_io) [发布](https://x.com/virtuals_io/status/2065324579669897236)（164 个赞、22 条回复、9,566 次浏览、18 次收藏）认为，验证应当与签发方无关，并且能被不同应用读取；[@Cloudflare](https://x.com/Cloudflare) [连接](https://x.com/Cloudflare/status/2065279639535456392)（49 个赞、4,964 次浏览）则提出将可信智能体认证接入 Mastercard 支持的支付体系。这个需求显然真实存在，但比前面的工作流类机会更依赖生态，因为身份、权限和清算都跨越公司边界。机会：竞争性。

| [Kimi-K2.7-Code](https://x.com/Kimi_Moonshot/status/2065377579130142937) | 编程模型 | (+/-) | 相比 K2.6，在内部编程和智能体基准上更强，推理 token 使用量降低 30%，并以开源形式发布 | 6 月 12 日的公开证据主要仍来自厂商自身，且对比图显示 GPT-5.5 或 Opus 在若干基准上仍领先 |
| [ERC-8126](https://eip.tools/eip/8126) | 验证标准 | (+/-) | 承诺在不暴露私密内部信息的前提下，为审查状态和钱包控制权提供可移植证明 | 仍处于标准草案阶段，采用度和互操作性尚未得到验证 |
| [Ona](https://ona.com/stories/ona-joins-openai) | 云端执行 / 编排 | (+) | 由客户控制的云环境、可跨设备持续的工作流程，以及企业上下文与访问控制 | 公开信息更偏重企业定位和收购叙事，而不是广泛可用的自助式工作流 |
| [Cloudflare Agentic Commerce stack + Mastercard Agent Pay](https://www.cloudflare.com/press/press-releases/2025/cloudflare-collaborates-with-leading-payments-companies-to-secure-and-enable-agentic-commerce/) | 支付 / 认证基础设施 | (+/-) | 将可信智能体认证连接到支付轨道和自主资源采购 | 跨公司依赖使落地速度慢于独立开发者工具 |

总体满意度最高的情况，是工具把“证明”或“控制”清楚地展示出来。TestSprite、Planr、Ona 和 architect-loop 最有力的主张，都来自它们展示了证据、状态或审查如何超出单次聊天会话而持续存在。相反，当工具扩展能力的速度快于信任建设，情绪就会变得复杂，比如仍带有明确安全免责声明的开放插件市场，或那些高度依赖基准叙事、但公开证据仍主要来自厂商自身的模型发布。

最清晰的权宜方案都是结构性的。开发者把昂贵的规划器与更便宜的执行器拆开，把记忆留在仓库或受控云里，引入二次审查智能体，并要求可移植验证，而不是相信某个平台内部状态本身。竞争焦点正从“我的模型更聪明”转向“我的运行时、控制平面和信任界面，能否把自主工作变得足够安全、足够可用”。

TestSprite CLI 最突出的地方，在于它把验证定义为智能体编程缺失的那一层，而不是一个附加测试运行器。最强的支撑证据是公开且可操作的：Apache-2.0 仓库、两条命令的安装路径，以及一项与端到端评测挂钩的公开排行榜主张，而不只是基准文字描述。

architect-loop 和 Planr 从两个角度展示了同一种更广泛的构建者模式。architect-loop 通过拆分规划/审查与实现来优化模型角色，Planr 则通过给智能体提供具备依赖感知的队列，以及正式的审查/证据路径，来优化协作。两者都是围绕仓库组织的答案，针对的是同一个痛点：长时间运行的智能体工作需要能跨越会话边界保留下来的记忆、检查点和证明。

插件市场则是当天最明确的“平台化”信号。它把智能体能力变成可安装模块，同时又通过 SHA 固定和明确的来源校验，把信任策略嵌进分发层。能力封装与安全姿态的这种组合，在当天最强的一批构建者产物中反复出现。

## 7. 机会在哪里

**[+++] 验证与恢复控制平面** —— 证据同时来自多个章节：TestSprite 把失效行为转成可复用故障包，Planr 把工作转成已验证任务图，architect-loop 在构建者动手前就冻结关卡，而 Ona/Rogo 则强调持久状态与可审计性。这个模式之所以强，是因为同一个缺失层同时出现在编程、研究和企业部署中。

**[++] Budgeted playgrounds and sandboxes for agent work** — [@yitong](https://x.com/yitong) [提出](https://x.com/yitong/status/2065464869529452569)（146 个赞、17 条回复、8,016 次浏览、63 次收藏）提出专门的设计 playground，[@Vtrivedy10](https://x.com/Vtrivedy10) [概述](https://x.com/Vtrivedy10/status/2065144884810440916)（60 个赞、7 条回复、3,180 次浏览、76 次收藏）提出带预算约束的研究沙箱，而 Ona 加 E2B 则展示了安全执行的企业版。这是一个中等强度的机会：需求直接存在，但每个垂直领域可能都需要各自的 UX 和集成界面。

**[+] 可移植的信任、身份与支付轨道** —— ERC-8126、Grok Build 市场，以及 Cloudflare 与 Mastercard，都指向同一个正在形成的层：智能体若想广泛行动，就需要可移植证明、安装来源信息，以及机器速度级别的权限体系。这个信号真实存在，但相比上面的工作流控制机会，它更早期，也更依赖标准推进。

## 8. 要点

1. **关于 AI 智能体的讨论已明确转向“证明界面”。** 验证 CLI、任务图、固定 SHA 的市场和 ERC-8126 都在竞争着把智能体行为变得可审计，而不只是更有能力。（[来源](https://x.com/Test_Sprite/status/2065238279784735014)）
2. **如今，harness engineering 指的是跨职能的运营设计，而不只是编程提示词。** 证据横跨 Founding Harness Engineer 招聘、设计 playground 提案以及研究 harness 规格。（[来源](https://x.com/itsericlay/status/2065109232115220901)）
3. **模型竞争如今不仅看基准胜负，也看 token 消耗和运行时控制。** Kimi 卖点是更低的推理 token 使用，architect-loop 把昂贵规划与廉价执行拆开，而 Ona 的收购则把安全异步编排提升为战略基础设施。（[来源](https://x.com/Kimi_Moonshot/status/2065377579130142937)）
4. **无论企业采用还是商业落地，都依赖可信的执行边界。** 6 月 12 日最强的部署信号，都是把智能体能力与隔离、来源证明或经认证的支付轨道绑定在一起，而不是只强调原始自主性。（[来源](https://x.com/Cloudflare/status/2065279639535456392)）
