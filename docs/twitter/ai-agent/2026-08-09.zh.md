# Twitter AI Agent - 2026-08-09

## 1. 人们在讨论什么

### 1.1 业务工作流压过了泛泛而谈的智能体讨论（🡕）

相比 8 月 8 日对治理、路由和市场的关注，8 月 9 日最强的一组讨论明显更偏向运营实务：智能体该如何为真实团队执行增长、报告、外联、入职引导和内部知识工作。最有价值的帖子不再抽象谈论自主性，而是点名具体的数据系统、工具和产出物。

[@gregisenberg](https://x.com/gregisenberg) [列出](https://x.com/gregisenberg/status/2086534549341610457)（478 个赞、63 条回复、43,965 次浏览）列出了 23 个具体的“营销智能体”闭环，帮助初创公司实现 PMF 或 $1M ARR，包括：根据 Stripe 退款原因发送挽回流失客户的邮件；依据 PostHog 功能标记自动淘汰效果不佳的入职引导实验；基于 Apollo 丰富数据后的定价页跟进；每周追踪 ChatGPT、Claude 和 Perplexity 的 LLM 回答；以及根据 Linear 工单生成更新日志。其独特之处不在于提出了新框架，而在于默认增长工作如今就是一串等待接入数据和工具的可重复闭环。

[@undefinedKi](https://x.com/undefinedKi) [总结](https://x.com/undefinedKi/status/2086440382808600645)（32 个赞、10 条回复、2,161 次浏览）把 Stripe 公开的 Kai 案例研究视为当天最清晰的企业案例。公开的 [LangChain 文章解析](https://www.langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents) 称，Kai 是面向非工程师的全公司生产力智能体，一周内搭建完成，Stripe 每周有 83% 的员工在使用，并由来自 100 多个团队的 1,000 多项技能支撑，其中 Marketing 和 GTM 的采用率尤其高。这让讨论从“智能体也许能帮助业务团队”转向一种已有文档记录的生产模式，用于报告、仪表盘、文档和数据综合。

![Stripe Kai 架构图，展示了从请求到技能选择、工具加载、沙箱执行、文件系统同步、产物输出的流程，并注明当技能数量超过约 150 个后，质量会开始下降](https://pbs.twimg.com/media/HPSGeJ3XgAAypiS.jpg)

[@thekuchhs](https://x.com/thekuchhs) [汇总](https://x.com/thekuchhs/status/2086360496337477870)（10 个赞、4 条回复、1,020 次浏览）关注的是面向营销的智能体仓库，而不是通用框架，点名提到 [OpenOutreach](https://github.com/eracle/OpenOutreach)、[OpenCMO](https://github.com/Lling0000/OpenCMO)，以及数个 Claude Code 营销技能包。公开的 [marketingskills 仓库](https://github.com/coreyhaines31/marketingskills) 通过 CRO、入职引导、流失预防、推荐、revops、潜客开发和程序化 SEO 等技能，把这一转变具体化；[OpenOutreach](https://github.com/eracle/OpenOutreach) 将自己定位为自托管、以邮件为先的 AI 销售智能体；[OpenCMO](https://github.com/Lling0000/OpenCMO) 则把 SEO、GEO、SERP 和社区监测整合为一个增长闭环。

**讨论洞察：** 关于采用的争论是务实的，而不是意识形态式的。[@addyosmani](https://x.com/addyosmani) [认为](https://x.com/addyosmani/status/2086537405763551551)（84 个赞、21 条回复、12,355 次浏览）认为，更大的差距在前沿之外：许多公司的开发者几乎还没打开过 Claude 或 Codex。回复随即把这一点转化为对信任、确定性和可见案例的讨论，而不是要求更强的原始能力。

**与前一天对比：** 8 月 8 日把智能体视为商业与治理问题；8 月 9 日则把它们视为业务运营层，必须在营销、分析、报告和外呼中证明自身价值。

### 1.2 harness 词汇正在固化为生产实践准则（🡕）

第二组讨论试图让这个领域的新语言不再那么神秘。当天最有分量的内容不再是口号式帖子，而是把 harness、闭环、图、重试和故障处理，变成团队真正可以采用的清单、基准和操作图。

[@PawelHuryn](https://x.com/PawelHuryn) [翻译](https://x.com/PawelHuryn/status/2086448359624052862)（33 个赞、7 条回复、2,180 次浏览）把 2026 年术语表压缩成一份直白的 12 项操作速查表，涵盖 skill、MCP、上下文工程、评测、harness、闭环工程、图工程和意图工程。真正的增量价值在回复里：一条回复说，loop 和 harness 仍然太常被混用；另一条则说，衡量一个 harness 的真正标准，是团队能否看出智能体为什么卡住，并及时介入。

[@MrAhmadAwais](https://x.com/MrAhmadAwais) [认为](https://x.com/MrAhmadAwais/status/2086211883624014100)（99 个赞、25 条回复、5,522 次浏览）指出，糟糕的 harness 设计会让同一个模型的成本高出 2 到 5 倍。附带的仪表盘之所以重要，是因为它把这种说法变成了可测量的主张：图片显示，Command Code 使用 DeepSeek V4 Flash 时，每十亿 token 成本为 $5，缓存命中率为 98.17%；同一面板中，Claude Code 的成本为 $20。

![Command Code 仪表板，对比了不同 coding harness 的报告 token 成本和缓存命中率，其中包括 98.17% 的缓存命中率，以及 DeepSeek V4 Flash 每十亿 token 5 美元的价格线](https://pbs.twimg.com/media/HPO1gx5bsAAxuxv.jpg)

[@AiCamila_](https://x.com/AiCamila_) [提出](https://x.com/AiCamila_/status/2086413542065086469)（10 个赞、1 条回复、128 次浏览）介绍了一个用于永久失败智能体任务的死信队列框架，包括保留上下文、重放、保留策略和告警。这个帖子互动不高，但信号很强，因为它把失败的智能体运行视为需要检查和重放的生产对象，而不是可以忽略的日志。

[@cyrilXBT](https://x.com/cyrilXBT) [提出异议](https://x.com/cyrilXBT/status/2086342714795409866)（79 个赞、28 条回复、5,376 次浏览）质疑一种未经验证的“图工程让闭环效果提升 1000 倍”的说法，并明确把读者引向 Anthropic 公开的知识图谱实战手册。这种怀疑很重要，因为它表明，在运营层面的主张被反复传播并固化为准则之前，人们确实需要公开、可检查的证据。

**讨论洞察：** 反复出现的问题已不再是“什么是 harness”，而是“究竟是 harness 的哪一部分在起作用：选择、缓存、重试、重放、审计，还是隔离？”即便是怀疑性的回复，也很有建设性：它们试图剥离炒作，直到控制面清晰可见。

**与前一天对比：** 8 月 8 日把可移植技能和评测抬升为缺失的基础设施；8 月 9 日则进一步把这种趋势推进到生产实践准则，给出了 DLQ、缓存、重试的图示，以及非专业人士也能使用的术语。

### 1.3 记忆与技能选择看起来像是下一阶段的扩展瓶颈（🡕）

记忆并未退出讨论，但语气变了。大家感兴趣的问题不再是智能体应不应该记忆，而是如何选择正确的技能、如何保持共享状态的正确性，以及在记忆或上下文悄然漂移时如何恢复。

[@undefinedKi](https://x.com/undefinedKi) [强调](https://x.com/undefinedKi/status/2086440382808600645)（32 个赞、10 条回复、2,161 次浏览）给出了最具体的公开案例：Stripe 的 Kai 无法一次性加载全部 500 多个内部 MCP 工具和 1,000 多项技能，因此采用两阶段系统，由技能选择来决定工具加载。同一个 [LangChain 案例研究](https://www.langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents) 还指出，当系统提示词里结合的技能超过约 150 项时，模型质量会下降，这使技能选择本身就成为一个扩展问题。

[@Saboo_Shubham_](https://x.com/Saboo_Shubham_) [推出](https://x.com/Saboo_Shubham_/status/2086502073315811750)（21 个赞、8 条回复、2,815 次浏览）把 [LongHorizon-Harness](https://github.com/AMAP-ML/LongHorizon-Harness) 作为跨会话记忆、子智能体、按用户划分的沙箱，以及每夜维护流程的开放参考。公开仓库围绕已验证状态定义了管理者—执行者—审计者的分工；而讨论串中技术含量最高的回复称，矛盾处理被下放给记忆层，未解决的冲突不会暴露给用户，而基于精确文本的去重意味着相互矛盾的版本可能在两次处理之间并存。

[@vuduvations](https://x.com/vuduvations) [认为](https://x.com/vuduvations/status/2086226975128158312)（2 个赞、2 条回复、49 次浏览）认为，没有来源追踪和撤回机制的共享记忆，不算治理系统。附带海报把这一点提炼成一个简单区分：访问控制决定谁可以读取记忆，但不决定记忆是否真实、来自何处，也不解决一旦它通过智能体团队传播之后该如何撤回。

**讨论洞察：** 当天的讨论把记忆既视为便利层，也视为风险面。回复不断回到同一种故障模式：可复用的智能体越多，过时、矛盾或缺乏依据的状态就传播得越快。

**与前一天对比：** 8 月 8 日还在争论运行时该更深还是更简单；8 月 9 日则指出了两派内部一个更具体的问题：如何从庞大的技能目录中做选择，以及如何证明共享记忆依然可信。

### 1.4 操作界面持续走出终端（🡒）

8 月 8 日出现的操作界面主题保持不变，但重点进一步转向人们早已身处其中的界面：语音、手机、浏览器端工作区和收件箱。最有价值的帖子都明确交代了人工接管环节，而不是假装更强的自主性就能消除控制需求。

[@thdxr](https://x.com/thdxr) [认为](https://x.com/thdxr/status/2086523544754593854)（558 个赞、70 条回复、29,732 次浏览）认为，语音提示并不需要精心口述。回复补充了缺失的操作细节：有人建议在 llama.cpp 本地运行时，把 Whisper 的 beam search 调到高于默认值；另一个人则说，真正的问题在于如何把混乱的转录内容移交成明确的计划，并在执行高风险工具调用前进行确认。

[@chenzeling4](https://x.com/chenzeling4) [提到](https://x.com/chenzeling4/status/2086332401551298675)（1 个赞、122 次浏览）介绍了 [Happy](https://github.com/slopus/happy)，这是一个面向 Claude Code 和 Codex 的移动端与 Web 客户端。公开仓库称，它通过 `happy` 包装 `claude` 或 `codex`，提供手机访问、推送通知、端到端加密和即时设备切换，给出了“智能体卡在你的笔记本电脑上”这一问题的具体解法。

![Happy 的移动端和网页客户端截图，展示了如何通过手机和网页控制 Claude Code 与 Codex 会话，并支持端到端加密和跨设备访问](https://pbs.twimg.com/media/HPQkQ27acAET164.jpg)

[@chenzeling4](https://x.com/chenzeling4) [还指出](https://x.com/chenzeling4/status/2086361090674594060)（2 个赞、104 次浏览）介绍了 [holaOS](https://github.com/holaboss-ai/holaOS)，其仓库将其描述为一个本地优先工作区，让 Claude Code、Codex 和内置的 holaOS 智能体共享同一套记忆和集成层。[@smratitiwa88687](https://x.com/smratitiwa88687) [打包](https://x.com/smratitiwa88687/status/2086367268787888505)（11 个赞、1 条回复、535 次浏览）把 [Agentic Inbox](https://github.com/cloudflare/agentic-inbox) 作为一个实用的免费替代方案提出；仓库则确认了一种非常具体的应用原生模式：每个 Durable Object 对应一个邮箱和一份 SQLite，附件存放在 R2 中，而且 AI 发送邮件前必须得到明确确认。

**讨论洞察：** 人们问的不只是智能体该在哪里运行，也在问它该在哪里等他们：手机通知里、浏览器工作区里、收件箱侧栏里，还是那种在高风险操作前仍会停下来的语音流程里。

**与前一天对比：** 8 月 8 日为操作故事加入了手机访问和基于 tmux 的协同；8 月 9 日则把它扩展为端到端加密的移动控制、应用侧工作区、收件箱原生智能体，以及对语音作为输入界面的更严肃讨论。

## 2. 人们对什么感到挫败

### 跳过采用与信任鸿沟的前沿叙事

最明显的社交层面挫败并不是模型太弱，而是前沿构建者与其他所有人之间的鸿沟。[@addyosmani](https://x.com/addyosmani) [表示](https://x.com/addyosmani/status/2086537405763551551)（84 个赞、21 条回复、12,355 次浏览）指出，仍处于智能体工程早期阶段的公司，数量远多于已经运行数十个智能体的团队；一条回复用一个词概括这种滞后：信任。[@AiCamila_](https://x.com/AiCamila_) [翻译](https://x.com/AiCamila_/status/2086413542065086469)（10 个赞、1 条回复、128 次浏览）又把同一个问题落实到运营层面，称失败任务需要死信队列、保留上下文和重放。眼下的解决办法不是更多炒作，而是可见的可靠性控制面，以及一个能让人逐步建立信任的闭环。值得投入建设：高。

### 技能泛滥、上下文过载，以及无法自证的记忆

最具体的扩展性抱怨来自 Kai 的讨论。[@undefinedKi](https://x.com/undefinedKi) [报道称](https://x.com/undefinedKi/status/2086440382808600645)（32 个赞、10 条回复、2,161 次浏览）称，Stripe 已经观察到加载过多技能会导致质量下降；一条回复则说，某个拥有 200 多项技能的个人 Claude Code 配置也出现了退化，因为 frontmatter 吃掉了上下文。[@Saboo_Shubham_](https://x.com/Saboo_Shubham_) [分享](https://x.com/Saboo_Shubham_/status/2086502073315811750)（21 个赞、8 条回复、2,815 次浏览）提出了一个长时程 harness，但最尖锐的回复指出，矛盾处理仍然发生在用户看不见的界面之下。[@vuduvations](https://x.com/vuduvations) [制作](https://x.com/vuduvations/status/2086226975128158312)（2 个赞、2 条回复、49 次浏览）则直接点明更广泛的问题：访问控制不是正确性治理。当前的变通办法包括动态加载、固定技能、外部状态，以及人工维护来源纪律。值得投入建设：高。

### 生产语言仍然容易滑向表演化

另一个挫败点是术语膨胀。[@PawelHuryn](https://x.com/PawelHuryn) [简化](https://x.com/PawelHuryn/status/2086448359624052862)（33 个赞、7 条回复、2,180 次浏览）之所以发布术语表，正是因为产品经理不断听到同样的词被宽泛、松散地使用；一条回复说，没有状态的 loop 还不能算 harness。[@cyrilXBT](https://x.com/cyrilXBT) [拒绝](https://x.com/cyrilXBT/status/2086342714795409866)（79 个赞、28 条回复、5,376 次浏览）拒绝复述未经验证的“提升 1000 倍”的图工程故事，而 [@MrAhmadAwais](https://x.com/MrAhmadAwais) [认为](https://x.com/MrAhmadAwais/status/2086211883624014100)（99 个赞、25 条回复、5,522 次浏览）则指出，真正的检验标准是在同一个模型上测得的成本。人们的应对方式是：在信任这些术语之前，先要求基准、图示和明确的故障恢复路径。值得投入建设：中。

### 当输入很快而执行能力很强时，交接容易出错

语音讨论暴露出一个规模较小但很重要的运营挫败。[@thdxr](https://x.com/thdxr) [将其概括为](https://x.com/thdxr/status/2086523544754593854)（558 个赞、70 条回复、29,732 次浏览）认为，语音比怀疑者想象得更容易使用；但最有力的回复指出，代价最高的故障模式，是混乱的转录内容变成隐含计划，继而触发高风险操作。这其实是同一个交接问题在另一种模态中的体现：输入很快，却没有可见的意图检查点。当前的变通办法包括更好的转录设置、明确的规划步骤，以及在重要工具调用前做确认。值得投入建设：中。

## 3. 人们希望出现什么

### 能跑真实 GTM 工作的打包业务技能

最强烈的现实需求，是那些已经知道如何完成业务工作、而不只是会聊天的智能体。[@gregisenberg](https://x.com/gregisenberg) [详细说明](https://x.com/gregisenberg/status/2086534549341610457)（478 个赞、63 条回复、43,965 次浏览）展示了一长串等待接入的营销闭环；[@thekuchhs](https://x.com/thekuchhs) [收集](https://x.com/thekuchhs/status/2086360496337477870)（10 个赞、4 条回复、1,020 次浏览）则指向外联、增长监测和营销技能仓库。公开的 [marketingskills](https://github.com/coreyhaines31/marketingskills) repo 和 [OpenOutreach](https://github.com/eracle/OpenOutreach) repo 说明了原因：人们想要的是可插即用的 CRO、入职引导、潜客开发和外呼工作流，而不是另一个空白提示框。这是一个直接需求，且竞争已经存在。机会：直接。

### 技能加工具的可移植打包，且不再出现封装层漂移

打包问题再次被明确提上台面。[@NestorLab44](https://x.com/NestorLab44) [将其概括为](https://x.com/NestorLab44/status/2086498690340954120)（2 个赞、59 次浏览）把 Hermes 对可移植插件的支持称为工具切换上的突破；公开的 [Agent Plugins 1.0.0 公告](https://developers.googleblog.com/agent-plugins-package-your-skills-tools-and-more/) 表示，其目标是为 `plugin.json`、`skills/` 和 `mcp.json` 提供一个统一、可预测的目录，而不是每个客户端各自套一层不同封装。这条路线务实而紧迫，但仍不完整，因为安装、信任、沙箱和审批体验被有意排除在标准之外。机会：直接。

### 能证明来源并可被纠正的共享记忆

关于 Kai、LongHorizon-Harness 和共享记忆治理的帖子，都指向同一个缺失层：记忆必须能在规模化使用中保持有用，而不成为错误状态的无声放大器。[@vuduvations](https://x.com/vuduvations) [表示](https://x.com/vuduvations/status/2086226975128158312)（2 个赞、2 条回复、49 次浏览）认为，真正缺的是来源追踪和撤回机制；[@Saboo_Shubham_](https://x.com/Saboo_Shubham_) [提到](https://x.com/Saboo_Shubham_/status/2086502073315811750)（21 个赞、8 条回复、2,815 次浏览）则表明，矛盾处理很快就会变成一个独立的产品问题。这与其说是梦想，不如说是一层尚未补上的控制层。机会：直接。

### 能跨手机、收件箱、工作区和语音跟随操作者的控制面

当天还清楚地显示出一个愿望：智能体应当出现在用户已经工作的地方。[@chenzeling4](https://x.com/chenzeling4) [展示](https://x.com/chenzeling4/status/2086332401551298675)（1 个赞、122 次浏览）介绍了 Happy 对 Claude Code 和 Codex 的手机及 Web 控制；[@smratitiwa88687](https://x.com/smratitiwa88687) [打包](https://x.com/smratitiwa88687/status/2086367268787888505)（11 个赞、1 条回复、535 次浏览）介绍了 Agentic Inbox 这种收件箱原生的智能体界面；[@thdxr](https://x.com/thdxr) [持续推动](https://x.com/thdxr/status/2086523544754593854)（558 个赞、70 条回复、29,732 次浏览）则把语音视为实用输入渠道。这一需求不是无人区，而是竞争市场：多个构建者已经在不同界面上交付同一种控制面思路。机会：竞争性。

## 6. 新动态与值得关注的项目

### Stripe 的 Kai 让“业务智能体”命题变得具体

[@undefinedKi](https://x.com/undefinedKi) [提到](https://x.com/undefinedKi/status/2086440382808600645)（32 个赞、10 条回复、2,161 次浏览）是这批数据里最具体的企业案例研究，而公开的 [LangChain 文章](https://www.langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents) 正是它重要的原因。它记录了一个全公司智能体：每周使用率达到 83%，通过技能门控的工具加载来应对 500 多个工具和 1,000 多项技能，并把沙箱和摘要视为生产级基础能力，而不是事后补丁。

### Agentic Inbox 展示了在信任边界明确时，应用原生智能体应该是什么样

[cloudflare/agentic-inbox 仓库](https://github.com/cloudflare/agentic-inbox) 由 [@smratitiwa88687](https://x.com/smratitiwa88687) 的 [汇总](https://x.com/smratitiwa88687/status/2086367268787888505)（11 个赞、1 条回复、535 次浏览）带出，之所以值得关注，是因为它对架构和控制的描述异常具体。一个邮箱对应一个带 SQLite 的 Durable Object，附件存放在 R2 中，AI 用 Workers AI 起草回复，而真正发送仍需要明确确认。这比又一个通用聊天封装更接近一种具体的智能体模式。

### 可移植插件从抽象标准走向跨客户端打包路径

公开的 [Google 公告](https://developers.googleblog.com/agent-plugins-package-your-skills-tools-and-more/) 和 [agent-plugins-spec 仓库](https://github.com/agentplugins/agent-plugins-spec) 有意把打包层做得很小：`plugin.json`、`skills/`、`mcp.json`，再加上由客户端持有的扩展命名空间。[@NestorLab44](https://x.com/NestorLab44) [关联](https://x.com/NestorLab44/status/2086498690340954120)（2 个赞、59 次浏览）则把这一标准接到了 Hermes 里真实的工具切换场景上，这正是生态系统在规模化之前通常需要的那种朴素互操作步骤。
