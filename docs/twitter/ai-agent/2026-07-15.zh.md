# Twitter AI Agent - 2026-07-15

## 1. 人们在讨论什么

### 1.1 技能工程正在固化为可复用的支架设计（🡕）

最强的一组工程讨论认为，智能体的质量取决于包裹模型的系统，而不是某个巧妙的一次性提示词。至少五条保留内容从不同角度推动了同一框架：技能是结构化机制，支架是可检查的控制平面，任务世界则是可以组合、审计和修复的对象。这直接延续了 7 月 14 日关于循环与评估的讨论，但重点已经从术语转向可复用的实现模式。

[@hnshah](https://x.com/hnshah) [认为](https://x.com/hnshah/status/2077161597508956282)（126 个赞、6 条回复、30,637 次浏览、318 次收藏）表示，“AI 技能仍然在按提示词的方式编写”，并把读者引向 Paul Bakaus 的《技能工程：为什么要反对一次性 AI 设计》，该文将可复用技能定位为结构化、可由人引导的系统，而不是一次性自动化。[@ShenSeanChen](https://x.com/ShenSeanChen) [已开源](https://x.com/ShenSeanChen/status/2077145810828218600)（69 个赞、7 条回复、3,691 次浏览、107 次收藏）[Waku Agent](https://github.com/ShenSeanChen/waku-agent)，这是一个本地优先的助手，其 README 表示核心循环大约只有 95 行 Python，配有 SQLite 记忆、确定性测试，以及在仪表盘中可见、而非隐藏在框架背后的 LLM-as-judge 评估。[@TheodoreGalanos](https://x.com/TheodoreGalanos) [扩展了](https://x.com/TheodoreGalanos/status/2077171041982632270)（16 个赞、1 条回复、6,946 次浏览、26 次收藏）则借助 [Task Worlds / Meta-Harness](https://theharness.blog/blog/task-worlds-meta-harness/) 提出了同样的观点：它不把智能体任务当作通用提示词，而是视为带有命名证据、权限和修复循环的“世界”。

[@hugobowne](https://x.com/hugobowne) [预览了](https://x.com/hugobowne/status/2077193752347918594)（4 个赞、2 条回复、326 次浏览）介绍了一场现场工作坊：从一次模型调用开始，再围绕它搭建支架，包括工具 schema、记忆、护栏、追踪、评估和失败分析。

![Builder's Playbook 图示，展示了从模型调用到具备工具、记忆、护栏、追踪和评估的 agent harness 的演进过程](https://pbs.twimg.com/media/HNOsq70agAAD40O.png)

**讨论洞察：** 回复持续把这个主题拉回到失败模式上。Hiten Shah 那条帖子的一个回复称，Claude Code 插件之所以频繁失效，是因为它们“被写成了提示词，而不是真正带有回退机制的系统”；与此同时，[@gmickel](https://x.com/gmickel) [撰写了](https://x.com/gmickel/status/2077152602081669449)（3 个赞、681 次浏览、3 次收藏）表示，团队仍然需要学会“智能体式思维”，把技能当作基础原语，而不是束身衣；[Flow-Next](https://flow-next.dev) 的文档则通过持久化规范、对抗式审查循环，以及用于重要交接的“回执”，把这一点具体化了。

**与前一天相比：** 7 月 14 日的重点是循环类型、评估器关卡和受治理的技能。到了 7 月 15 日，讨论又下沉了一层：焦点转向这些循环和技能该如何编码，才能在模型、支架和上下文变化后依然存活。

### 1.2 循环工程开始变成课程、认证和检查清单（🡕）

第二个讨论簇显示，循环工程正从构建者之间的经验之谈，走向正式训练。证据不只是一些炒作口号：相关帖子提到了官方课程目录、认证备考，以及验证层、停止规则和进度记忆文件等明确的循环组件。

[@RoundtableSpace](https://x.com/RoundtableSpace) [提到了](https://x.com/RoundtableSpace/status/2077328568116244830)（28 个赞、12 条回复、22,052 次浏览）提到了其所称的 Anthropic 官方循环工程课程；与此同时，[@AlexRiad84837](https://x.com/AlexRiad84837) [整理了](https://x.com/AlexRiad84837/status/2077326553923661900)（16 个赞、7 条回复、131 次浏览）分享了一份包含 13 门课程的 Claude 学习清单，其中包括 [Claude 101](https://anthropic.skilljar.com/claude-101) 和 [Introduction to Agent Skills](https://anthropic.skilljar.com/introduction-to-agent-skills)；后者明确讲解了技能与 `CLAUDE.md`、hooks 和子智能体的区别。[@HeyAnjula](https://x.com/HeyAnjula) [分享了](https://x.com/HeyAnjula/status/2077316320496943211)（8 个赞、2 条回复、226 次浏览）给出了一份为期六周的 [Claude Certified Architect - Foundations](https://anthropic-partners.skilljar.com/claude-certified-architect-foundations-certification/486716) 考试备考计划，包含多工具智能体、团队工作流和多智能体研究流水线练习。[@aiedge_](https://x.com/aiedge_) [概述了](https://x.com/aiedge_/status/2077332434631438570)（8 个赞、1,067 次浏览）则总结了循环的六段解剖：触发器、执行层、验证器、停止规则、记忆和技能。

![课程目录图，列出了 Claude 101、Introduction to Agent Skills、Claude Code in Action、MCP 课程以及其他官方 Claude 培训内容](https://pbs.twimg.com/media/HNQlfB6aIAACr3i.jpg)

![循环结构图，展示了触发器、执行者、检查器、停止规则、记忆和技能](https://pbs.twimg.com/media/HNQq1yEbEAEFOyl.jpg)

**讨论洞察：** 这个讨论簇里最尖锐的回复出现在课程推文下：停止条件“是我最浪费 tokens 和时间的地方”，而官方材料往往在这部分着墨不足。这一批评也呼应了那篇循环解剖帖——它在失败停止、重试上限和 token 预算上的篇幅，比提示词本身还多。

**与前一天相比：** 前一天把评估和治理框定为运营必需品。到了今天，同样的理念已经以可教学内容和认证的形式出现，这说明循环工程正在成为入门培训界面，而不再只是高级实践者的习惯。

### 1.3 多智能体产品化开始聚焦真实工作界面，而不只是聊天窗口（🡕）

今天最清晰的构建动向，来自那些给智能体提供持久工作场所的人：让它们进入笔记库，通过基于角色的团队名册协作，并通过明确的 MCP 工具界面执行任务。相比昨天的议题追踪器和生命周期演示，今天的新内容更容易安装，也更贴近具体工作流。

[@israfill](https://x.com/israfill) [展示了](https://x.com/israfill/status/2077309923013386506)（16 个赞、9 条回复、1,078 次浏览）介绍了 Claudian，它把 Claude Code 接入 Obsidian，让智能体可以重写笔记、链接相关文件，并直接原地编辑 Markdown；[Claudian 仓库](https://github.com/YishenTu/claudian) 表示，它支持在库内行内编辑、计划模式、斜杠命令、技能和 MCP 服务器。[@sairahul1](https://x.com/sairahul1) [重点介绍了](https://x.com/sairahul1/status/2077326742218539296)（16 个赞、13 条回复、2,374 次浏览、21 次收藏）介绍了 [Agency Agents](https://github.com/msitarzewski/agency-agents)——一个拥有 131,820 stars 的专职智能体名册，覆盖工程、设计、营销、产品、测试和支持，并主张“专业化角色 + 循环”比“一条通用提示词”更具可扩展性。[@TheCodeMan__](https://x.com/TheCodeMan__) [分享了](https://x.com/TheCodeMan__/status/2077310158665908641)（8 个赞、3 条回复、246 次浏览）则展示了一个 [AI in .NET Starter Kit](https://thecodeman.net/ai-in-dotnet-starter-kit) 示例：利用 MCP 服务器运行负载测试、比较端点、检测线程池饥饿，并根据智能体的工具调用生成报告。

![Obsidian 截图，展示 Claudian 如何直接在 vault 图谱视图中读取和重写 markdown 文件](https://pbs.twimg.com/media/HNQWOi0aYAAaQ1b.jpg)

![Agency 名册截图，列出了专门的前端、后端、移动端、AI、DevOps、设计和支持 agents，并明确了各自职责](https://pbs.twimg.com/media/HNQhteubgAASPAk.jpg)

**讨论洞察：** 这个讨论簇下的回复主要在追问智能体集群的成本，以及不同角色之间的交接边界。一位回复者问，50 多个智能体的名册在 200 美元套餐下是否负担得起；另一位则问，团队如何避免 3 号智能体重做 1 号智能体已经定下来的事情。这些都是具体的编排问题，而不是对整体方向的反对。

**与前一天相比：** 7 月 14 日的构建者还主要在描述循环模式和治理层。7 月 15 日则增加了更具体的封装形式：可安装的笔记库助手、可下载的入门套件，以及预先组合好的智能体团队。

## 2. 什么让人沮丧

### 提示词式技能在模型、支架或上下文变化时依然会失效

当天最响亮的抱怨，并不是孤立地针对模型质量，而是针对脆弱的运行模式。[@hnshah](https://x.com/hnshah) [认为](https://x.com/hnshah/status/2077161597508956282)（126 个赞、6 条回复、30,637 次浏览、318 次收藏）指出，按提示词方式编写的技能，一旦模型、支架或上下文变化就会“崩塌”；一条回复则把失败说得更具体：Claude Code 插件在更新后反复失效，是因为它们编写时没有设计回退机制。[@gmickel](https://x.com/gmickel) [补充说](https://x.com/gmickel/status/2077152602081669449)（3 个赞、681 次浏览、3 次收藏）则表示，即便技能库本身很强，如果用户没学会把技能视为可组合的基础原语，依然会失败。严重程度：高，因为这个问题同时出现在产品使用和内部赋能中。

### 停止条件和交接仍然是自主运行里最昂贵的部分

多数关于循环的讨论，深层挫败感并不在于“怎么启动一个循环”，而在于“我怎么知道它什么时候该结束，以及如何防止智能体彼此踩踏？”Anthropic 课程推文下的一条回复说，退出条件是人们最浪费 tokens 和时间的地方；与此同时，[@aiedge_](https://x.com/aiedge_) [详细说明了](https://x.com/aiedge_/status/2077332434631438570)（8 个赞、1,067 次浏览）明确列出了成功与失败的停止规则、重试上限和 token 预算。[@sairahul1](https://x.com/sairahul1) [agency-agents 帖子](https://x.com/sairahul1/status/2077326742218539296)（16 个赞、13 条回复、2,374 次浏览、21 次收藏）也在回复中引出了同样的担忧：token 消耗，以及不同角色交接时的漂移。严重程度：高；常见的应对办法是增加验证器、进度文件和更窄的角色边界。

### 创意类智能体仍然会错过用户意图和框架语义

最尖锐的一手失败报告来自 [@luciascarlet](https://x.com/luciascarlet)，其 [描述了](https://x.com/luciascarlet/status/2077314180038746277)（12 个赞、4 条回复、715 次浏览）讲述了一项 Figma shader 任务：内置智能体把“加一个旋转手柄”的请求理解成把旋转范围增大到 3600 度，又把位置手柄映射成无法使用的相对坐标。这比“输出不好看”更深一层：智能体既误解了用户意图，也误解了自己所处界面模型的语义。

![Figma agent 输出截图，列出了 seed、position、scale、rotation 和 perspective 的调整内容，此前它误解了所请求的 rotation handle](https://pbs.twimg.com/media/HNQZe51WMAAT5CE.jpg)

严重程度：对设计工作流而言属于中高，因为这是语义层面的错误，排查成本高；从现有数据看，唯一的应对策略仍然是人工修正后重试。

### 生产级护栏仍被当作缺失的基础设施

[@AiCamila_](https://x.com/AiCamila_) [认为](https://x.com/AiCamila_/status/2077247613662003537)（12 个赞、3 条回复、188 次浏览）表示，大多数生产环境中的智能体失败，根源在于缺失护栏，而不是模型能力不足；随附蓝图将这一缺口拆解为政策/治理、输入验证、工具控制、输出检查，以及监控/回滚。

![蓝图展示了用于生产级 agents 的 policy/governance、输入护栏、工具与操作控制、输出护栏以及监控层](https://pbs.twimg.com/media/HNPdsRtbsAAl8y8.jpg)

严重程度：今天属于中等，因为讨论量低于循环主题，但仍值得投入建设，因为提出的这些控制项都直接对应真实部署中的失败面。

## 3. 人们希望存在什么

### 能跨越上下文和模型变化而存活的技能

Hiten Shah 的表述、他引用的 Paul Bakaus 文章，以及 Flow-Next 的指导说明，共同指向一个直接需求：技能应当像持久化的运行模块，而不是脆弱的提示词产物。人们想要的是这样的可复用指令：即使模型变了、仓库变了、周边支架演进了，也还能继续工作。[Introduction to Agent Skills](https://anthropic.skilljar.com/introduction-to-agent-skills)、Flow-Next 和 Waku 风格的支架今天已经提供了部分答案，但这个需求依旧现实且紧迫。机会：直接。

### 面向长时循环的验证器和停止规则脚手架

课程讨论里关于 token 浪费的回复、aiedge 的循环解剖帖，以及 agent roster 下关于交接的提问，都指向同一个缺口：团队需要标准化的方法来表达“完成”“重试”“放弃”和“请求帮助”。这不是一种愿景式需求；当这些规则停留在隐含状态时，人们已经在为此损失时间和成本。当前的部分答案包括自定义进度文件、LLM-as-judge 检查，以及硬性的迭代次数上限。机会：直接。

### 能直接操作真实知识库的智能体原生工作空间

Claudian 那条帖子清楚地表明，人们希望不再把笔记在聊天窗口内外来回复制，而是让智能体直接处理 Markdown、链接和笔记库结构。这是一个实践性而非情绪性的需求：人们想让笔记、规范和上下文成为可编辑的工作记忆，而不是粘贴进去的附件。Claudian 只解决了一部分问题，配置摩擦、CLI 路径问题和使用成本提醒依然存在。机会：竞争性。

### 成本可预测、漂移可控的多智能体交接

Agency Agents 的回复把缺失环节说得很明确：角色之间如何交接工作，才能不重做已经做过的决策？智能体集群跑起来到底要花多少钱？WebSwarm 通过递归委派和证据聚合给出了一个研究方向上的答案，但生产问题更宽泛：团队需要的是既能保留上下文、跟踪成本，又能防止角色分叉漂移的编排系统。机会：直接，但很可能会面临编排框架和平台厂商的强竞争。

## 4. 正在使用的工具和方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| [Waku Agent](https://github.com/ShenSeanChen/waku-agent) | 本地优先的智能体支架 | (+) | 可读的 Python 循环、SQLite 记忆、确定性评估与判官式评估、本地仪表盘 | 仍属早期项目，目前采用证据有限 |

| [Claudian](https://github.com/YishenTu/claudian) | Obsidian 工作空间插件 | (+) | 直接读写笔记库、行内编辑、计划模式、技能、MCP 支持 | 配置摩擦、CLI 路径问题，以及持续的模型使用成本 |

| [WebSwarm](https://arxiv.org/abs/2607.08662) | 递归研究框架 | (+) | 深搜与广搜模式、递归委派、证据聚合 | 可运行代码仍未完整发布 |
| Figma 内置智能体 | 设计智能体 | (-) | 能在设计工具内部直接处理 shader 编辑请求 | 首次使用就误读意图、误解界面语义，而且速度偏慢 |

明显的正向偏好集中在那些能让智能体行为可检查的方法上：可读循环、命名技能、明确停止规则、持久化规范，以及通过 MCP 暴露出来的工具界面。最大的迁移趋势，是从“把提示词写得更狠”转向“围着它搭一个支架”，无论那意味着一个本地优先仓库、一个 Obsidian 插件，还是一套角色名册。当智能体必须在开放式交接或视觉编辑语义中保住细腻的人类意图时，满意度就会下降，这也是为什么验证层和直接上下文工作空间会反复出现。

Waku Agent 是当天核心设计理念落成现实产物的最清晰例子。这个仓库不只是一个演示应用；它被定位成一份关于支架、循环、记忆和评估设计的可读蓝图，这与当天一再出现的主张完全一致：重在可检查性，而不是魔法般的提示词。Claudian 解决的是另一个相邻痛点：它给智能体一个持久工作空间，让记忆和编辑都发生在用户原本就在使用的笔记系统里。

Agency Agents 和 WebSwarm 展示了同一趋势的规模化一面。前者把专业角色打包成可安装的队友，后者则把递归委派打包成一种面向深广网页搜索的研究架构。两者都在回应信息流中其他地方出现的同一种构建者直觉：当工作需要拆解、审查和证据收集时，一个智能体只跑一轮远远不够。

![图示展示了一个 .NET 入门工具包，它结合了语义搜索、RAG，以及一个用于性能分析、配备 10 种工具的 MCP 服务器](https://pbs.twimg.com/media/HNQLYhuWAAA3CvV.jpg)

反复出现的构建模式高度一致：给智能体直接接入持久上下文，收窄其角色边界，加入验证器或审查层，并把工具边界说清楚。触发这些构建的痛点也同样一致：黑盒行为、交接过程中的上下文丢失，以及人类工作界面与智能体界面之间过多的复制粘贴。

## 6. 新鲜且值得关注的内容

### 面向网页研究的递归委派出现了具名架构

[@zarqXBT](https://x.com/zarqXBT) [重点介绍了](https://x.com/zarqXBT/status/2077320993685594524)（9 个赞、3 条回复、130 次浏览、6 次收藏）介绍了 [WebSwarm](https://arxiv.org/abs/2607.08662)，它把“生成子智能体，让它们深入探索，再汇总证据”变成了一种具体的递归编排模式。关联论文描述了 deep、wide、atom 和 entity-collect 等自适应搜索模式，以及向上汇聚证据、而非预先固定拆解任务的机制。这很重要，因为当天其他关于多智能体的讨论，大多还是产品封装或角色名册；而这是最清晰的公开成果，明确地把研究循环本身形式化了。

![来自 WebSwarm 论文的图示，展示了子 agents 之间的递归委派、搜索模式、证据收集和结果聚合](https://pbs.twimg.com/media/HNQgZIqWoAAEUX9.jpg)

### 代币化的智能体所有权变得更具体了，但证据仍然单薄

当天偏非工程的一组讨论，把智能体框定为经济参与者和链上资产，而不只是开发者工具。[@WorldOfMercek](https://x.com/WorldOfMercek) [梳理了](https://x.com/WorldOfMercek/status/2077328470787461162)（111 个赞、40 条回复、2,485 次浏览、20 次收藏）描述了一套去中心化 AI 栈，覆盖智能体需求、路由、推理、模型、GPU 供给和资本形成；与此同时，[@mickeymantled](https://x.com/mickeymantled) [认为](https://x.com/mickeymantled/status/2077159782843363473)（182 个赞、13 条回复、20,248 次浏览、6 次引用）则认为，Brainfart 的“mind pieces”让智能体本身成为资产，而不只是围绕它的代币。

![Galaxy Research 风格的生态系统地图，将去中心化 AI 项目归类为 agents、marketplaces、inference providers、model developers、GPU providers 和 capital formation](https://pbs.twimg.com/media/HNQnJu4XYAAWWT0.jpg)

## 7. 机会在哪里

**[+++] 持久化技能与支架基础设施** —— 第 1、2、4、5 节中最强的证据表明，人们已经不再想要“更好的提示词”；他们要的是可复用技能、可检查循环、可见评估，以及能跨越模型和上下文变化而存活的支架。Waku、Flow-Next、Bakaus/Hiten 的框架，以及那篇 meta-harness 文章都在直接支持这一点。

**[++] 面向长时循环的验证器、停止规则与交接控制** —— Anthropic 课程推文和 agent roster 推文下的回复都指出了同样的瓶颈：退出条件不清、token 浪费，以及角色漂移。这是一个很强的运营机会，因为痛点具体且反复出现，但它很可能会与编排厂商和模型平台功能直接竞争。

**[++] 面向持久上下文的智能体原生工作空间** —— Claudian 和 .NET 入门套件表明，市场需要的是活在工作本身所在位置的智能体：笔记库、仓库、API、仪表盘和结构化项目记忆。这个机会很真实，因为现有解决方案依然伴随配置摩擦、服务商成本，或者停留在教学定位，而不是无缝成熟的产品形态。

**[+] 智能体经济的证明与遥测** —— 链上讨论簇显示，人们确实对可拥有、可变现的智能体基础设施感兴趣；但回复同样在追问，其中是否真的存在持续稳定的需求。这就为那些能证明使用、归因和价值累积，而不只是描绘叙事的系统，创造了一个正在形成的机会。

## 8. 要点

1. **当天最重要的技术信息是：技能应当像系统，而不是像提示词。** Hiten Shah 的帖子、其引用的技能工程文章、Waku Agent 和 meta-harness 文章都汇聚到同一个判断：持久支架比一次性指令更重要。（[来源](https://x.com/hnshah/status/2077161597508956282)）
2. **循环工程正在变成正式课程。** 带有官方色彩的课程目录、认证备考和可视化循环检查清单，表明构建者如今期待获得关于技能、MCP、验证和停止规则的结构化训练。（[来源](https://x.com/RoundtableSpace/status/2077328568116244830)）
3. **最实用的产品化工作，发生在智能体接入真实工作界面的地方。** Obsidian 笔记库集成、MCP 驱动的开发工具，以及可读的本地支架，都比通用助手演示更具体，因为它们直接作用于持久上下文和真实工具。（[来源](https://x.com/israfill/status/2077309923013386506)）
4. **最难、也仍未解决的问题，依然是退出条件、交接和意图保真。** 回复抱怨 token 浪费和角色漂移，而 Figma shader 的案例则说明，智能体在第一次接触任务时，仍可能同时误解用户意图和界面语义。（[来源](https://x.com/luciascarlet/status/2077314180038746277)）
5. **一条并行发展的链上智能体叙事正在壮大，但证据缺口也非常明显。** 发帖者给出了生态图、所有权 UI 和市场主张，但这个讨论簇里最有力的回复立刻追问：这些智能体到底有没有创造真实需求？（[来源](https://x.com/WorldOfMercek/status/2077328470787461162)）
