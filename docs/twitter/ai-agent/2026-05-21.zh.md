# Twitter AI Agent - 2026-05-21

## 1. 人们在讨论什么

### 1.1 编程代理排行榜正在变成产品发布会和编排能力发布 🡕

5 月 21 日最强的一组讨论，核心不再是把编程代理当作抽象的模型发布来谈，而是把它们当作可落地的完整系统来评估：看基准表、单任务成本和编排层能力。支撑这一主题的是三条高信号推文和一条较小的开发者讨论串：Qwen 发布了面向“Agent 时代”的旗舰模型，Artificial Analysis 将 Cursor Composer 2.5 定位为成本—质量上的异常值，Claude Code 上线了确定性工作流，而一则 Gemini issue 分诊演示则显示，如今代理支撑框架已经可以轻到什么程度。相比 5 月 20 日聚焦语音延迟和通用代理速度，讨论进一步转向了编程代理的部署选型。

[@Alibaba_Qwen](https://x.com/Alibaba_Qwen) [介绍了](https://x.com/Alibaba_Qwen/status/2057450220708147250)（987 个赞、77 条回复、61,153 次浏览、155 次收藏）介绍了 Qwen3.7-Max：一款面向编程代理、可通过 MCP 集成处理办公任务、并支持长周期自主运行的旗舰模型。该帖称，它在一项内核优化任务上持续运行了 35 小时，工具调用超过 1,000 次；随附表格则显示，它在 12 项 agentic 评测中整体表现强劲，而不是只挑了一个有利基准。

[@ArtificialAnlys](https://x.com/ArtificialAnlys) [发布了](https://x.com/ArtificialAnlys/status/2057277363789197561)（95 个赞、7 条回复、5,296 次浏览）称 Cursor Composer 2.5 在其 Coding Agent Index 中拿到 62 分，排名第三，仅次于 Claude Code 中的 Claude Opus 4.7 和 Codex 中的 GPT-5.5。其独特之处不只是排名，还有成本：标准版每项任务 0.07 美元，Fast 版为 0.44 美元；推文还强调，相比 Composer 2，它在 SWE-Bench-Pro-Hard-AA 上提升了 35 分。

[@ClaudeCodeLog](https://x.com/ClaudeCodeLog) [报告称](https://x.com/ClaudeCodeLog/status/2057564555174113732)（115 个赞、9 条回复、9,315 次浏览、37 次收藏）称 Claude Code 2.1.147 新增了用于确定性多代理编排的 Workflow 工具，将 `/simplify` 重命名为 `/code-review`，并加固了 REPL 和 Workflow 沙箱，以防范 prototype-pollution 和 thenable 逃逸。这一点之所以重要，是因为编排与沙箱隔离已作为一等产品能力正式发布，而不再被视为私有支撑框架里的胶水代码。

[@_philschmid](https://x.com/_philschmid) [表示](https://x.com/_philschmid/status/2057513254856151339)（11 个赞、2 条回复、816 次浏览）称，他只用一条 curl 调用 Gemini API，就做出了一个 GitHub issue 分诊代理：把仓库克隆到沙箱、抓取 issue、进行分类，并运行复现代码。虽然这是个较小信号，但它与整体氛围一致：人们正在用具体执行闭环来评估编程代理，而不是看聊天式机灵程度。

**讨论洞察：** 成本、确定性和支撑框架的设计约束，几乎和原始分数一样重要。关于 Composer 的讨论里，价格区间和总耗时占据了与排行榜名次差不多的篇幅；而 Claude Code 的发布串则立刻引发追问：所谓确定性工作流，是否本质上就是一种新的编排支撑框架。

**与前一天的比较：** 5 月 20 日的基准讨论集中在适合语音的延迟、工具调用，以及模型是否足够快、能跑起语音闭环。到 5 月 21 日，焦点转向了编程代理基准表、编排原语，以及在不同代理产品层之间做选择的经济性。

### 1.2 技能捆绑和技能包目录正在成为真正的软件层 🡕

5 月 20 日出现的“打包”主题，在 5 月 21 日进一步升级，变成了关于组合规则、单命令安装和垂直领域目录的讨论。人们不再只是宣布有 bundle 或 skill hub 存在，而是开始解释：bundle 为什么会失效、哪些能力应该绑在一起，以及经过策展的技能包如何把编程代理从陈旧默认做法中拉出来。四个分量较足的例子支撑了这一主题。

[@shannholmberg](https://x.com/shannholmberg) [写道](https://x.com/shannholmberg/status/2057242484594573436)（62 个赞、7 条回复、4,354 次浏览、74 次收藏）称，Hermes Agent 的新技能捆绑只有在其中步骤能自然串联时才有效。她的核心警告非常具体：如果把几个彼此无关的技能塞进同一条用户消息里，指令就会相互竞争，代理会混乱，输出也会漂移。

[@shannholmberg](https://x.com/shannholmberg) 随后 [可视化展示了](https://x.com/shannholmberg/status/2057561011251769675)（23 个赞、7 条回复、1,198 次浏览、12 次收藏）又用明确的正反例重申了同一条规则：团队应该捆绑那些会反复执行的工作流，而不是把恰好在同一个项目里用到的零散工具硬塞在一起。

**讨论洞察：** Hermes 回复里最有价值的修正很明确：仅仅“高频使用”还不够。大家明确认为，一个 bundle 应该对应一条很少变化的路径；否则，固定顺序本身就会成为漂移和返工的来源。

**与前一天的比较：** 5 月 20 日让 bundle、浏览器技能中心和可安装的指导包进入视野。5 月 21 日则补上了组合启发式、垂直领域目录，也更清楚地表明：这些技能包正成为代理周边一层真正的软件。

### 1.3 治理讨论分化为运行时控制与“防守方被拦住” 🡕

5 月 21 日的安全讨论，比前一天多了一层更尖锐的矛盾：越来越多开发者在发布明确的运行时控制能力，但互动量最高的一条讨论，却来自一位维护者，称前沿模型的安全策略正在阻碍他们处理真实的 P0 防御问题。互动量较低的治理类帖子依然重要，因为它们非常具体，也与这一更大的抱怨形成呼应。

[@Teknium](https://x.com/Teknium) [认为](https://x.com/Teknium/status/2057286388299841860)（596 个赞、53 条回复、150,666 次浏览、52 次收藏）称，Anthropic 的安全限制阻止 Opus 审查并协助修复 Hermes Agent 的安全问题，造成一种不对称：攻击者可以持续试探，而维护者却被挡在模型协助之外。在后续回复中，他表示同一过滤器此前还曾阻止展示上一次漏洞利用浪潮中受影响的库列表；之后他又说 Anthropic 已主动联系，尝试为 Hermes 解封。

[@Alacritic_Super](https://x.com/Alacritic_Super) [表示](https://x.com/Alacritic_Super/status/2057292376276893751)（3 个赞、2 条回复、163 次浏览）称，Microsoft 的 Agent Governance Toolkit 直接把策略执行、零信任身份、执行沙箱、审计日志、kill switch 和运行时控制加入代理系统。[代码仓库](https://github.com/microsoft/agent-governance-toolkit) 表示，每一次工具调用、资源访问和代理间消息，都会在执行前先被评估；其立场是，仅靠提示词层面的安全控制，明显弱于应用层强制执行。

**讨论洞察：** 分歧已经不再是“治理是否重要”。开发者越来越认同，工具执行需要明确的策略层和隔离层；但 Teknium 的讨论也显示，大家同样对不透明的安全分类器感到不满，因为它们会阻止防守方做真实的分诊和修复工作。

**与前一天的比较：** 5 月 20 日强调治理工具包和运行时策略引擎正在成为新型基础设施。5 月 21 日则新增了一条来自维护者、更加尖锐的实际抱怨，以及数据集中第一个明显的机构信号：MCP 安全正成为正式的安全议题。

### 1.5 语音代理更接近“一条命令即可搭起来”和交易基础设施 🡒

语音仍然占据显著位置，但重点已从 5 月 20 日关于语音引擎和延迟预算的讨论，转向了可安装性和真实世界的执行层。支撑这一点的证据来自一篇开发者教程、一次电话与支付基础设施发布，以及一个技能包演示。人们不再只问语音代理够不够快，而是更关注它能多快搭起来，以及部署后究竟能做什么。

[@jerallaire](https://x.com/jerallaire) [表示](https://x.com/jerallaire/status/2057547767820456427)（197 个赞、48 条回复、11,181 次浏览、53 次收藏）称，Circle Agent Stack 现在允许代理注册电话号码，并借助 USDC 和 BlandAI 发起 AI-native 电话。[网站](https://agents.circle.com) 把 USDC 描述为付费 API 和其他代理操作中的“支付即认证”机制；回复里很快就冒出了 OTP 等现实边界问题。

[@exploraX_](https://x.com/exploraX_) [分享了](https://x.com/exploraX_/status/2057569914291122259)（15 个赞、3 条回复、381 次浏览、10 次收藏）介绍了一个基于 Claude Code 中 Agora 技能构建的语音代理，称只需一条命令就能安装技能包并跑起一个可打断的多轮演示。推文列出了具体栈：Deepgram 负责 STT，GPT-4o-mini 负责 LLM，MiniMax 负责 TTS；同时还支持持久化记忆、函数调用、视频，以及每个 App ID 20 个并发会话。

**与前一天的比较：** 5 月 20 日把语音代理视为一个由语音编排和亚秒级响应定义的系统问题。5 月 21 日则保留了基础设施视角，但把重点转向了单命令安装、统一 API，以及让语音代理真正可用的业务基础设施——电话号码、付费端点和认证。

## 2. 什么让人感到沮丧

### 生产代理拥有的权限，仍然超过治理能力

严重程度：高。[@Alacritic_Super](https://x.com/Alacritic_Super) [表示](https://x.com/Alacritic_Super/status/2057292376276893751)（3 个赞、2 条回复、163 次浏览）称，如今大多数 AI 代理在团队尚未建立起任何像样的控制平面之前，就已经有权限运行命令、读取机密、访问 API、修改代码并触发工作流。[Agent Governance Toolkit 代码仓库](https://github.com/microsoft/agent-governance-toolkit) 把这个问题具体化为：每一次工具调用、资源访问和代理间消息，都应该在执行前接受检查；与此同时，[@rseroter](https://x.com/rseroter) [指出](https://x.com/rseroter/status/2057494123855450544)（4 个赞、284 次浏览）则把 GKE Agent Sandbox 和 Agent Substrate 指为安全计算边界。当前的应对方式，是在模型之外增加策略检查、隔离和可审计性。值得投入，因为痛点非常具体，而公开可见的解决方案仍然偏早期。

### 一刀切的安全过滤器，可能把防守方挡在真实事件响应之外

严重程度：高。[@Teknium](https://x.com/Teknium) [认为](https://x.com/Teknium/status/2057286388299841860)（596 个赞、53 条回复、150,666 次浏览、52 次收藏）称，Anthropic 的安全控制阻止 Opus 审查 Hermes Agent 中的 P0 问题，甚至在此前一次漏洞利用浪潮中，连受影响依赖列表都不让看。后续回复称 Anthropic 已联系他们讨论 Hermes 解封，但核心抱怨没有变：安全系统对维护者的帮助，还不如对攻击者造成的阻碍来得明确。今天的替代做法是人工审查、临时豁免，或改用不会触发同类过滤器的较弱模型。值得投入，因为安全团队显然想要代理辅助防御，但他们需要的是能区分修复工作与滥用行为的策略。

### 上下文与记忆故障依然很难定位

严重程度：高。[@himanshustwts](https://x.com/himanshustwts) [写道](https://x.com/himanshustwts/status/2057165369912221759)（153 个赞、7 条回复、4,495 次浏览、131 次收藏）称，上下文工程和评测已经是核心技能；回复解释了原因：一位从业者描述了如何在推理前从 pgvector 中检索余弦相似的文本块，以更少约 5 倍的 token 和更少幻觉完成任务；另一位则指出，真正的失败模式是把 40k 个松散相关的 token 全塞进上下文，让模型自己“平均处理”。另一个互动量较小但更尖锐的讨论来自 [@HackrLife](https://x.com/HackrLife) [链接到](https://x.com/HackrLife/status/2057212292245430585)（2 个赞、2 条回复、21 次浏览），提到了 [《Agent Memory Failures Are Silent》](https://arxiv.org/abs/2605.03354) 这篇论文：团队往往无法判断，模型到底是忘了、从来不知道，还是没能检索到正确内容。当前的应对方式是做阶段感知评测、收紧检索，以及显式设计记忆结构。值得投入，因为这是反复出现的生产故障，而非边缘案例。

### 技能捆绑一旦打包的是“方便”而不是“工作流”，就会变吵

严重程度：中。[@shannholmberg](https://x.com/shannholmberg) [写道](https://x.com/shannholmberg/status/2057242484594573436)（62 个赞、7 条回复、4,354 次浏览、74 次收藏）称，Hermes bundle 只有在其中技能能自然组合时才有效；否则，代理会在一条消息里收到互相冲突的指令，输出就会漂移。回复又补充了第二种失败模式：当任务路径需要跳步或调整顺序时，bundle 也会失效，因为固定序列会在任务变化后依旧被机械重放。当前应对方式是：只捆绑稳定、重复的链路，把不相关的工具分开。值得投入，因为技能包的普及速度，已经快过了测试 bundle 组合性、顺序敏感性和来源可信度的工具发展速度。

### 语音代理更容易搭了，但真实世界边界情况会立刻冒出来

严重程度：中。[@svpino](https://x.com/svpino) [发布了](https://x.com/svpino/status/2057479207429767201)（67 个赞、5 条回复、6,223 次浏览、117 次收藏）称，AssemblyAI 的 Voice Agent API 取代了过去拼装多个组件的模式；在后续回复里，他还说，去年做同样的搭建需要四个独立 API key。但 [@jerallaire](https://x.com/jerallaire) [表示](https://x.com/jerallaire/status/2057547767820456427)（197 个赞、48 条回复、11,181 次浏览、53 次收藏）则显示，代理现在已经能拿到电话号码并用 USDC 发起 AI-native 电话，而评论区立刻开始追问 OTP 等运营细节。当前做法是先用统一语音 API 和新的支付/电话基础设施搭起来，再手工补剩余业务逻辑。值得投入，因为剩下的摩擦点已经不再是“新奇感”，而是部署 plumbing。

## 3. 人们希望存在什么

### 面向安全分诊、对防守方友好的代理访问

人们要的并不是更弱的安全，而是能区分正当修复与攻击性滥用的安全机制。[@Teknium](https://x.com/Teknium) [表示](https://x.com/Teknium/status/2057286388299841860)（596 个赞、53 条回复、150,666 次浏览、52 次收藏）称，他希望 Opus 能审查并帮助修复 Hermes Agent 的安全问题；而当天的治理类帖子则给出了一些不完整答案，例如 [Agent Governance Toolkit](https://github.com/microsoft/agent-governance-toolkit)、[Corridor](https://cursor.com/marketplace/corridor) 和 [GKE Agent Sandbox](https://cloud.google.com/blog/products/containers-kubernetes/bringing-you-agent-sandbox-on-gke-and-agent-substrate/)。这是一个现实且紧迫的需求，因为维护者已经在真实的加固与事件响应流程里尝试使用代理。机会：直接。

### 能指出“哪里出错了”，而不只是说“答案错了”的记忆层与支撑框架层

数据集中最强烈的未满足需求，是更好的代理记忆与上下文故障诊断。[@himanshustwts](https://x.com/himanshustwts) [写道](https://x.com/himanshustwts/status/2057165369912221759)（153 个赞、7 条回复、4,495 次浏览、131 次收藏）称，上下文工程和评测已成为核心技能；而 [@HackrLife](https://x.com/HackrLife) [链接到](https://x.com/HackrLife/status/2057212292245430585)（2 个赞、2 条回复、21 次浏览）则提到一篇论文，认为记忆故障往往是静默发生的，需要做阶段级定位。实际诉求是：系统能判断代理究竟是从未学到这个事实、没存下来，还是没检索出来。检索优先的配置、记忆文件夹和研究型诊断提供了部分答案，但整体需求仍未满足。机会：直接。

### 组合干净、值得信任的技能包

人们显然想要可复用的技能包，但他们也想知道：一个 bundle 是否结构良好、是否塞得过满、里面的指导是否仍然最新。[@shannholmberg](https://x.com/shannholmberg) [写道](https://x.com/shannholmberg/status/2057242484594573436)（62 个赞、7 条回复、4,354 次浏览、74 次收藏）称，随意组合 bundle 会造成漂移；而 [Modern Web Guidance](https://developer.chrome.com/docs/modern-web-guidance) 和 [Stanford REAP 技能目录](https://github.com/brycewang-stanford/Awesome-Agent-Skills-for-Empirical-Research) 则展示了，当内容边界清晰时，经过策展的技能包能创造多大价值。这个需求既现实又带竞争性：团队既想获得可安装能力，也想拥有测试、来源证明，以及技能包内部相互冲突时清晰的失效模式。机会：直接且竞争激烈。

### 覆盖电话、认证与支付边界的语音代理栈

这批语音代理开发者想要的不是又一个 demo，而是更少的活动部件和更多现实世界所需的基础设施。[@svpino](https://x.com/svpino) [发布了](https://x.com/svpino/status/2057479207429767201)（67 个赞、5 条回复、6,223 次浏览、117 次收藏）谈的是如何用一个 API 取代拼装式语音栈；而 [@jerallaire](https://x.com/jerallaire) [表示](https://x.com/jerallaire/status/2057547767820456427)（197 个赞、48 条回复、11,181 次浏览、53 次收藏）则显示，代理现在已经能拿到电话号码并借助 USDC 发起电话，随后立即暴露出 OTP 等运营边界问题。[@exploraX_](https://x.com/exploraX_) [展示了](https://x.com/exploraX_/status/2057569914291122259)（15 个赞、3 条回复、381 次浏览、10 次收藏）说明，单命令技能安装已经能让语音 demo 很快跑起来，但更广泛的需求仍是一整套覆盖语音、记忆、工具、电话、计费和合规的完整栈。机会：直接且竞争激烈。

当工具是围绕模型补齐系统能力，而不是假装替代系统其余部分时，整体反馈偏正面。bundle、策展型技能包、检索层、治理中间件、沙箱和统一语音 API 都获得了较好的接受度，因为它们降低了搭建成本或失败风险。情绪转为复杂时，通常是因为产品层过于受限——例如 Teknium 抱怨安全分诊被挡住——或者观测能力不足——例如记忆故障和 bundle 漂移讨论。

常见应对方式也很一致：开发者会把更小、经过检索的切片拉入上下文，而不是一次性全倒进去；只捆绑稳定的多步骤链路；在工具执行前设置策略检查；并通过可安装技能包来启动 Web 或语音工作，而不是从零写 prompt。迁移方向已经明显从单纯的提示词工程，转向支撑框架工程、技能打包、执行治理，以及面向代理的付费或认证基础设施。竞争压力也很明显：模型厂商在基准分数和成本上竞争，而生态厂商争夺的则是模型周边那一层，决定代理是否可靠到足以上线。

## 7. 机会在哪里

**[+++] 既能让防守方工作、又具备运行时治理的系统** — 最强的安全信号，把一条高传播的维护者抱怨——在真实漏洞处理中被拦住——与 AGT、GKE Agent Sandbox、Corridor 以及 NSA MCP 指南所代表的具体治理层放在了一起。机会之所以强，是因为市场显然需要执行前控制，但不需要那种会阻断正当加固和事件响应的粗暴安全系统。

**[+++] 面向支撑框架的记忆与上下文诊断** — Himanshu 的讨论、支撑框架综述、Kyle Vedder 的记忆配置，以及那篇关于静默记忆故障的论文，都指向同一个缺口：团队仍然很难判断代理是忘了、从未知道，还是取错了内容。这个机会很强，因为它同时出现在从业者建议、学术框架和具体故障分析中。

**[+++] 技能组合、来源证明与可安装专业能力** — Hermes 的 bundle 指导、Modern Web Guidance、Stanford 的实证研究目录和 Agora Skills 都说明，能力正在被打包。缺失的产品层是“验证”：一个工具需要能告诉用户，bundle 是否能干净组合、指导内容是否仍然最新，以及技能包在被强行加载进工作流前是否值得信任。

**[++] 具备电话、认证和支付能力的语音代理部署层** — AssemblyAI、Circle Agent Stack 和 Agora Skills 都降低了构建门槛，但也暴露出 OTP、计费和真实工作流集成方面仍待解决的边界问题。这是中等强度机会，因为需求显而易见，但这个赛道已经开始拥挤。

**[++] 成本感知型编程代理编排** — Qwen3.7-Max、Cursor Composer 2.5、Claude Code Workflows，以及轻量 Gemini 代理构建都表明，团队现在已经拥有真实的基准、价格和编排选项。仍然有空间做出这样一类产品：根据成本、延迟、失败风险和所需支撑框架深度来路由任务，而不是默认绑定单一代理产品层。

**[+] 面向科学与受监管领域的垂直 MCP 服务器** — MARRVEL-MCP 和科学发现论文暗示，更广泛的趋势可能是从通用助手转向内置评测与来源证明的领域工具链。这个信号仍在形成中，但它是最清晰的可防御差异化路径之一。

## 8. 要点

1. **编程代理如今正在被作为完整系统来营销和选择，而不只是基础模型。** Qwen 的发布、Composer 2.5 的定价图，以及 Claude Code 的工作流发布，都把代理产品层本身当成了产品。（[来源](https://x.com/Alibaba_Qwen/status/2057450220708147250)）
2. **技能打包正在成为真正的软件层，但组合质量如今成了首要约束。** Hermes 的 bundle 讨论关心的已不是 bundle 是否存在，而是如何避免指令冲突和固定顺序陷阱。（[来源](https://x.com/shannholmberg/status/2057242484594573436)）
3. **对于严肃的代理部署而言，治理已经成为核心系统问题。** 这一天既出现了明确的策略与沙箱工具，也出现了维护者的高声抱怨：一刀切的安全控制会妨碍真实防御工作。（[来源](https://x.com/Teknium/status/2057286388299841860)）
4. **上下文工程正在固化为支撑框架工程和记忆诊断。** 最清晰的公开建议是：少检索一点、结构化更多、观测清楚故障发生在哪里，而不是默认把上下文越撑越大。（[来源](https://x.com/himanshustwts/status/2057165369912221759)）
5. **语音代理正从拼装式 demo 转向可安装、可交易的完整栈。** 统一 API、单命令技能包，以及支付或电话轨道，都指向同一个下一步：让代理真正能运行在生产工作流里。（[来源](https://x.com/jerallaire/status/2057547767820456427)）
