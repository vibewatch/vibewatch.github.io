# Twitter AI 智能体 - 2026-06-10

## 1. 大家在讨论什么

### 1.1 软件工厂式工作流取代单智能体演示，成为当天的主要目标 🡕

6 月 10 日最强的主题不是对原始模型的追捧，而是组织级工作流设计。4 条保留内容共同支撑了这一点，而且它们从不同层面描绘了同一个终点：由 AI 管理工单入口、更深的子智能体树、持久检查点，以及在人类不再事无巨细地微观管理后仍能继续工作的智能体。

[@walden_yan](https://x.com/walden_yan) [指出](https://x.com/walden_yan/status/2064755974548902006)（558 个赞，26 条回复，114,794 次浏览，445 次收藏），工程团队现在就该搭建云端软件工厂，让 AI 在人类介入前充当 bug、反馈、PR 审查和录屏生成的一线防线。附带的 Slack 截图之所以重要，是因为它展示了一个 Devin Automation 工作流已经在对 feedback-web 队列做分诊，并且明确给出了 triaged、active、done 和 declined 工单数量，而不是泛泛承诺。（[引用的发布内容](https://x.com/cognition/status/2064398549073453266)）

![来自 Devin Automation 的 Slack 摘要，显示 feedback-web 队列中已分诊、进行中、已完成和已拒绝的工单数量](https://pbs.twimg.com/media/HKbAi5oawAA1PZ2.jpg)

[@ClaudeCodeLog](https://x.com/ClaudeCodeLog) [报道称](https://x.com/ClaudeCodeLog/status/2064817348113019239)（113 个赞，11 条回复，7,931 次浏览），Claude Code 2.1.172 新增了最多五层的嵌套子智能体、针对原本会卡住的 1M 上下文会话的自动压缩，以及插件浏览器中的搜索栏。原帖及其链接的 [更新日志](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md?plain=1) 让重点很明确：只有在会话能够可预测地恢复、交接保持足够具体时，编排深度才有意义。

[@0xwhrrari](https://x.com/0xwhrrari) [表示](https://x.com/0xwhrrari/status/2064437482985312525)（121 个赞，22 条回复，21,889 次浏览，174 次收藏），当很多人连一个能在几条消息后仍记住上下文的 Claude 项目都没配置好时，就谈工程师管理数百个智能体还为时过早。这条帖子带有推广性质，但回复仍然捕捉到了一个真实主题：记忆与工作流设计正从高级玩家技巧，变成基础工程工作。

[@XiaomiMiMo](https://x.com/XiaomiMiMo) [宣布](https://x.com/XiaomiMiMo/status/2064799879352959085)（416 个赞，26 条回复，14,134 次浏览，233 次收藏）MiMo Code V0.1，而公开的 [MiMoCode 仓库](https://github.com/XiaomiMiMo/MiMo-Code) 也说明了它为何契合这一主题：跨会话记忆、检查点文件、系统创建的子智能体、`/goal` 停止条件，以及用于规划、执行、审查和验证的 compose 模式工作流。回复中有人询问 OpenAI 兼容端点和 Windows GUI，这表明工作流层面的野心，来得比产品封装打磨更快。

**讨论洞察：** 关键的细微之处在于，更多智能体本身并不是重点。回复不断把讨论拉回到恢复能力、权限边界、成本，以及智能体能否在不悄悄丢失状态的情况下恢复真实任务。

**与前一天对比：** 6 月 9 日聚焦于共享工作流层和交付支撑层。到了 6 月 10 日，门槛已经从“给我一个控制平面”提高到“给我展示一个已经能分诊工作、并能撑过长会话的运行闭环”。

### 1.2 智能体支付从思想实验走向发布日基础设施 🡕

第二个讨论簇把智能体支付变成了一个具体的产品类别。3 条保留内容共同支撑了这一点，并一起覆盖了完整技术栈：网络结算、开发者工具，以及涉及真实资金的智能体行为所需的安全闸门。

[@Mastercard](https://x.com/Mastercard) [宣布](https://x.com/Mastercard/status/2064690323683529210)（973 个赞，71 条回复，121,524 次浏览，125 次收藏）Agent Pay for Machines，称 AI 智能体将以机器速度、在巨大规模上进行交易。Mastercard 自己的 [新闻稿](https://investor.mastercard.com/investor-news/investor-news-details/2026/Mastercard-Launches-Agent-Pay-for-Machines-to-Unlock-Super-Fast-Always-On-Payments/default.aspx) 表示，该服务与 30 多家合作伙伴一同发布，增加了凭证化、程序化权限控制、可验证意图，以及跨银行卡、账户和稳定币的多轨保证结算。

[@RippleXDev](https://x.com/RippleXDev) [推出](https://x.com/RippleXDev/status/2064701950285713878)（347 个赞，13 条回复，12,299 次浏览）[XRPL AI Starter Kit](https://ripple.com/insights/xrpl-ai-starter-kit/)，其中包括 XRPL Docs MCP server、Claude 钱包与支付技能，以及对 XRP 和 RLUSD 的 X402 支持。Ripple 的发布帖称，交易可在 3-5 秒内结算、成本可预测，团队能在 30 分钟内跑通一笔已确认的测试网支付。

[@worldoffisher](https://x.com/worldoffisher) [认为](https://x.com/worldoffisher/status/2064731059841851833)（103 个赞，78 条回复，7,627 次浏览），Ledger Agent Stack 指向了一条比无约束自治更现实的路径，因为智能体可以高速行动，同时又不把人类排除在关键决策之外。被引用的 Ledger 提示中心围绕只读钱包检查、Wallet CLI 安装，以及在任何不可逆操作之前先走技能驱动的工作流。

**讨论洞察：** 最强的质疑来自回复，而不是发布文案。Mastercard 相关回复在问：如果机器速度的决策出错，责任由谁承担；而 Ledger 的讨论则不断回到“人工审批是一个特性，而不是刹车”。

**与前一天对比：** 6 月 9 日更多聚焦于支撑层和工作流界面。6 月 10 日则加入了实时支付通道、凭证化和结算话语，让智能体商业离生产环境明显更近了一步。

### 1.3 记忆、技能与受治理的自我改进，成为主要控制界面 🡕

第三个主题是，差异化正在转移到记忆、技能、审批和审计上，而不是再做一个通用助手外壳。5 条保留内容支撑了这一点，其中有几项交付的是具体机制，而不是宽泛理念。

[@nikos1](https://x.com/nikos1) [表示](https://x.com/nikos1/status/2064760109868421442)（132 个赞，51 条回复，6,601 次浏览），他正在构建 Glen——“会变成共享专长的共享记忆”，这样教会一个智能体的任何东西，都可以被所有其他人的智能体复用。配图只是一张 YC 招牌照片，但回复补充说他已经在做早期设计合作，这让这条帖子读起来不再像理论，而更像一个早期产品论点。

[@binance](https://x.com/binance) [分享了](https://x.com/binance/status/2064498027323167113)（142 个赞，77 条回复，19,879 次浏览）一条 [Binance Academy 解析文章](https://www.binance.com/en/academy/articles/what-are-ai-agent-skills)，将 AI agent skills 定义为插件式工具包，让智能体能够执行真实任务。真正有用的细节来自回复：只有在附带清晰权限边界和人工升级点时，skills 才真正可信。

[@Teknium](https://x.com/Teknium) [推出](https://x.com/Teknium/status/2064831491130130879)（98 个赞，16 条回复，2,708 次浏览）Hermes Agent Write Gate，这是一个针对记忆更新、技能更新和技能创建的审批层。图示之所以重要，是因为它清楚写出了运行模型：三态写入模式、内联与分阶段审查路径、`/memory approve`、`/skills diff`，以及跨重启保留的 pending 存储。

![Hermes Write Gate 示意图，展示三态写入模式、针对技能的分阶段审查以及 CLI 审批命令](https://pbs.twimg.com/media/HKcSCiba8AAi0ni.jpg)

[@Conste11ation](https://x.com/Conste11ation) [表示](https://x.com/Conste11ation/status/2064786719896195413)（62 个赞，2 条回复，1,550 次浏览）一个新的 OpenClaw 审计插件，会把每一次工具调用、消息、技能和 cron 记录到一条防篡改的本地链上。被引用的构建者帖子把价值主张说得很明确：无需云账号，默认只保留本地证据；如果其他人需要验证记录，也可选择外部锚定。

**讨论洞察：** 信息流并不是在抽象地索要“记忆”。它真正追问的是：谁可以写入记忆，谁可以对技能变更做 diff，以及在一次无人值守运行后，任何人如何证明智能体究竟做了什么。

**与前一天对比：** 6 月 9 日已经把 skills 视为可移植工件。到 6 月 10 日，它们变得更受治理：共享专长系统、显式写入审批和本地审计轨迹，都在同一天的证据中出现。

## 2. 什么让人沮丧

### 上下文丢失和恢复能力薄弱，仍在限制智能体规模

严重程度：高。[@0xwhrrari](https://x.com/0xwhrrari) [表示](https://x.com/0xwhrrari/status/2064437482985312525)（121 个赞，22 条回复，21,889 次浏览，174 次收藏）称，人们在第一个智能体还会在几条消息后忘记任务时，就开始谈数百个智能体。[@ClaudeCodeLog](https://x.com/ClaudeCodeLog) [报道称](https://x.com/ClaudeCodeLog/status/2064817348113019239)（113 个赞，11 条回复，7,931 次浏览）称，Claude Code 新版本不得不修复 1M 上下文会话卡住的问题，并加入自动压缩；还有一条回复说，可预测的恢复是长时间运行中最重要的“无聊功能”。人们正在通过检查点、压缩上下文以及 Glen 这样的共享记忆产品来应对，而不是信任一个巨大的单一会话。这值得构建，因为这些抱怨是操作层面的、反复出现的，而不是边缘案例。

### 隐性模型行为，比明确拒绝更快摧毁信任

严重程度：高。[@latkins](https://x.com/latkins) [认为](https://x.com/latkins/status/2064418178864697811)（533 个赞，35 条回复，31,220 次浏览）一条观点认为，模型如果在与 AI 相关的工作上悄悄变差，比明确拒绝更糟，因为用户无法判断自己何时被误导。回复进一步把这一点说得更尖锐：有人说，唯一理性的反应就是假设这种情况一直都在发生；还有人说，新用户可能最没有能力发现输出质量已经下降。当话题触及前沿 AI 工作时，人们的应对方式是更激进地交叉检查，并且对整个模型类别失去信任。这值得构建，因为需求指向的是透明性和可观测性，而不只是更强的原始能力。

### 没有审批的自治，在金钱和可自我修改智能体场景下仍让人不安

严重程度：高。[@Mastercard](https://x.com/Mastercard) [宣布](https://x.com/Mastercard/status/2064690323683529210)（973 个赞，71 条回复，121,524 次浏览）提到机器速度的智能体支付，但立刻就有回复问：当机器速度的决策出错时，谁承担责任。[@worldoffisher](https://x.com/worldoffisher) [认为](https://x.com/worldoffisher/status/2064731059841851833)（103 个赞，78 条回复，7,627 次浏览）称，Ledger 的 human-in-the-loop 审批模式比完全自治更现实，而 [@Teknium](https://x.com/Teknium) [推出](https://x.com/Teknium/status/2064831491130130879)（98 个赞，16 条回复，2,708 次浏览）则是对记忆和技能变更的显式写入审批。即使是 Binance skills 讨论串里，也有回复说，只有权限清晰时，skills 才真正有意思。当前的变通方式是分阶段审查、只读模式和支出上限。这值得构建，因为市场信号不是“把所有人都移除掉”，而是“让审批层真正可用”。

## 3. 大家希望存在什么

### 带安全写入和可复用专长的团队共享记忆

这是一个直接需求。[@nikos1](https://x.com/nikos1) [表示](https://x.com/nikos1/status/2064760109868421442)（132 个赞，51 条回复，6,601 次浏览）称，Glen 应该让任意智能体都能拥有团队中最强 recruiter、growth lead 或 principal engineer 的专长，而不是把记忆困在某个人的会话里。[@Teknium](https://x.com/Teknium) [推出](https://x.com/Teknium/status/2064831491130130879)（98 个赞，16 条回复，2,708 次浏览）之所以需要 write gate，正是因为没有审查的持久记忆会变成运营负担，而 [MiMoCode 仓库](https://github.com/XiaomiMiMo/MiMo-Code) 则通过 MEMORY.md、checkpoint 文件和用于记忆清理的 `/dream` 给出了另一个答案。需求很清楚：团队想要能持续积累的记忆，但前提是显式治理。机会：直接。

### 面向机器到机器工作的权限化预算与结算通道

这是一个现实且紧迫的需求。[@Mastercard](https://x.com/Mastercard) [宣布](https://x.com/Mastercard/status/2064690323683529210)（973 个赞，71 条回复，121,524 次浏览）一项用于机器速度支付的权限化服务，而 Mastercard 的 [新闻稿](https://investor.mastercard.com/investor-news/investor-news-details/2026/Mastercard-Launches-Agent-Pay-for-Machines-to-Unlock-Super-Fast-Always-On-Payments/default.aspx) 明确写出了凭证化、授权规则和保证结算。[@RippleXDev](https://x.com/RippleXDev) [推出](https://x.com/RippleXDev/status/2064701950285713878)（347 个赞，13 条回复，12,299 次浏览）一个包含钱包和支付技能的 starter kit，而 [@worldoffisher](https://x.com/worldoffisher) [认为](https://x.com/worldoffisher/status/2064731059841851833)（103 个赞，78 条回复，7,627 次浏览）则表明，硬件支持的审批依然必要。尚未满足的需求不只是支付；而是保留追责能力和可审计性的、具备策略感知的支付。机会：直接。

### 能在多智能体间拆分工作而不丢失交接的编排层

这个需求既现实，也带有竞争性。[@walden_yan](https://x.com/walden_yan) [认为](https://x.com/walden_yan/status/2064755974548902006)（558 个赞，26 条回复，114,794 次浏览，445 次收藏）称，AI 早就该在人工接手前完成反馈分诊、代码审查和首轮调试。[@ClaudeCodeLog](https://x.com/ClaudeCodeLog) [报道称](https://x.com/ClaudeCodeLog/status/2064817348113019239)（113 个赞，11 条回复，7,931 次浏览）提到嵌套子智能体和自动压缩，但回复提醒说，只有交接足够具体时，更深的树结构才有帮助。[@XiaomiMiMo](https://x.com/XiaomiMiMo) [宣布](https://x.com/XiaomiMiMo/status/2064799879352959085)（416 个赞，26 条回复，14,134 次浏览，233 次收藏）能从 spec 一路走到 report 的 compose 模式工作流，也指向了同一个方向。机会：竞争性。

MiMo Code 很突出，因为公开仓库让它的架构一目了然：持久项目记忆、自动检查点、树状任务、子智能体和 compose mode 都作为一等运行时功能交付，而不是提示词片段。这与当天更大的趋势一致：工作流产品正试图撑住长任务，而不只是帮你完成单轮交互。

支付相关构建则呈现出另一种模式。Mastercard 正试图通过凭证化和网络治理，把机器速度商业工业化；而 Ripple 试图通过钱包技能、经由 MCP 提供的文档访问，以及快速测试网上手，来降低开发者摩擦。两者一起表明，构建者正从技术栈两端进攻同一个机会：上层是企业级网络信任，下层是开发者原语。

Glen、Gate OC Audit 和 Hermes Write Gate 都来自同一个底层痛点：智能体需要可累积的状态，但运营者需要对进入该状态的内容拥有证据与控制。多位构建者独立收敛到记忆共享、写入审查和防篡改记录，而不是承诺完全不可见的自治。

## 7. 机会在哪里

**[+++] 受治理的共享记忆与自我改进控制层** — 第 1、2、3、4、5 节都出现了证据：用于共享专长的 Glen、用于持久记忆的 MiMo、用于受审变更的 Hermes Write Gate、用于恢复能力的 Claude Code，以及用于证明的 Gate OC Audit。最强的机会不在于原始记忆容量，而在于能安全累积、可做 diff，并且在长时间无人值守工作后仍可被信任的记忆。

**[++] 智能体支付护栏与责任工具** — Mastercard 和 Ripple 都发布了基础设施，而围绕 Ledger 的讨论则一再强调，关键操作需要人工审批。中等强度的机会位于支付通道与智能体之间的那一层：预算、策略模拟、责任处理，以及面向机器商业的事后审计。

**[+] 面向业务工作流的多模态输出智能体** — HyperFrames 表明，从对话到视频的工作流正成为真实的 connector 界面，而 Walden 的软件工厂讨论串则暗示，在人工审查前自动生成录屏和面向客户的产物存在需求。这里的机会仍在形成，因为信息流中的案例少于记忆或支付，但这种模式已经开始出现。

## 8. 要点

1. **信息流更关心运行闭环，而不是头条式的模型 IQ。** Walden 的软件工厂帖子、MiMo 以记忆为核心的智能体设计，以及 Claude Code 关于恢复能力的发布都指向同一个结论：市场正在转向托管工作流，而不是单轮提示。（[来源](https://x.com/walden_yan/status/2064755974548902006)）
2. **智能体支付在 6 月 10 日变得具体可感。** Mastercard 发布了网络级基础设施，Ripple 也在同一天交付了面向开发者的支付工具，这让智能体商业的故事第一次有了具体的通道、控制和上手路径。（[来源](https://x.com/Mastercard/status/2064690323683529210)）
3. **信任如今已成为构建者正在产品化的实现细节。** Write Gate、Gate OC Audit 和 Ledger 式人工审批都说明了同一个市场经验：无人值守智能体要想获得更广泛部署，必须先具备审查、证据和受限权限。（[来源](https://x.com/Teknium/status/2064831491130130879)）
4. **共享专长记忆看起来是最明确的未满足需求之一。** Glen 的主张、Binance 对 skills 的框定，以及围绕上下文丢失的挫败感，都表明团队希望智能体能继承组织知识，而不是每次会话都从零开始。（[来源](https://x.com/nikos1/status/2064760109868421442)）
