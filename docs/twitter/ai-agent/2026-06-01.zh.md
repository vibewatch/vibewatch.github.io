# Twitter AI Agent - 2026-06-01

## 1. 人们在讨论什么

### 1.1 上下文工程成了生产瓶颈 🡕

讨论重心已经从抽象的 harness 之争，转向具体的上下文操作。共有五条入选内容支撑这一主题：一份公开的 harness 分类、一则来自 Box 的企业级提醒、一篇关于生产环境 OOM 的帖子、一篇可复用外部上下文管理论文，以及一个量化上下文浪费的代码库索引工具。

[@byanujpatel](https://x.com/byanujpatel) [分享](https://x.com/byanujpatel/status/2060967710008508607)（235 个赞，12,861 次浏览，304 次收藏）LangChain 公开发布的 [harness engineering 文章](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)，将 harness 定义为模型周围的一切，并把持久化存储、代码执行、长周期工作等目标能力，映射到文件系统、bash、沙箱、记忆与编排等组件上。

![将持久化存储、代码执行和长时程工作等期望的智能体行为，映射到文件系统、bash、沙箱、记忆和规划循环等特定 harness 组件的示意图](https://pbs.twimg.com/media/HJoHFx7bcAA8s1I.jpg)

[@levie](https://x.com/levie) [认为](https://x.com/levie/status/2061247380897579500)（173 个赞，33 条回复，33,132 次浏览，203 次收藏）指出，企业级 agent 之所以失效，是因为关键上下文分散在遗留系统、彼此不匹配的权限体系，以及从未转化为机器可读形式的“部落知识”之中。最有力的回复进一步明确了诉求：一位操作者表示，在老旧 CMS 之上加一层 Playwright 抽象后，系统就更适合 agent 使用；另一位则说，agent 需要“带凭证的记忆”，让每一条事实都能追溯到来源和变更历史。

[@arpit_bhayani](https://x.com/arpit_bhayani) [写道](https://x.com/arpit_bhayani/status/2061295678735954270)（150 个赞，5 条回复，6,244 次浏览，65 次收藏）指出，agent 系统在生产环境中最常见的故障仍然是 OOM：工具输出、API 结果和完整文档长期滞留在内存里，直到对话变长或负载升高，进程最终崩溃。他给出的修复办法——激进截断、流式处理、只检索所需上下文，以及把状态持久化到外部——让这个问题听起来更像经典系统工程问题，而不是模型能力不足。

[@dair_ai](https://x.com/dair_ai) [强调了](https://x.com/dair_ai/status/2061455253325971789)（72 个赞，8 条回复，3,177 次浏览，54 次收藏）介绍了 AdaCoM：训练一个独立的 LLM，来决定冻结状态的 agent 应保留哪些上下文、丢弃哪些上下文。论文截图是关键证据：它展示的是包裹在 agent 外部、可复用的上下文管理器，而不是又一种局限在提示词内部的补丁。

![AdaCoM 论文页面，展示了摘要以及一个外部上下文管理器的架构图，该管理器可为冻结的智能体裁剪或保留上下文](https://pbs.twimg.com/media/HJvCoJ5bkAAg86Z.jpg)

[@israfill](https://x.com/israfill) [推广了](https://x.com/israfill/status/2061383848047656963)（13 个赞，4 条回复）介绍了 CodeGraph，将其定位为面向编码 agent 的预索引代码知识图谱。截图比宣传语更有说服力：没有仓库图谱时，agent 会浪费 3,847 个 token 盲猜；有了图谱后，agent 无需额外反复搜索，就能拿到精确的调用点和影响路径。

![CodeGraph 对比图：并排展示了没有 repo 图时会浪费 token 的搜索，与建立索引后精确的符号搜索及零浪费 token 的效果](https://pbs.twimg.com/media/HJuBdz9agAAQtLs.png)

**讨论洞察：** 回复一再把标准从“给 agent 更多上下文”抬高到“给它新鲜的上下文、可追溯的来源，以及正确的保留策略”。

**与前一天对比：** 5 月 31 日还把 harness 工程当作设计清单；到了 6 月 1 日，上下文交付、压缩和记忆外置已经变成了具体工作。

### 1.4 Agent 经济相关帖子终于出现了小规模真实闭环，但信任仍然滞后 🡕

与前几天相比，市场和支付相关讨论更有操作细节：实时付款、先审核后结算的流程、可移植的 checkout skills，以及钱包签名消息。但回复始终绕回同一批缺失层：证据、信誉，以及足够多的交易对手，只有这样市场才真正有用。

## 2. 什么让人感到挫败

### 上下文蔓延，把出色演示拖成失败的生产 agent

严重程度：高。[@levie](https://x.com/levie) [认为](https://x.com/levie/status/2061247380897579500)（173 个赞，33 条回复，33,132 次浏览，203 次收藏）指出，企业 agent 会因为系统碎片化、权限不匹配和未被记录的“部落知识”而失效。[@arpit_bhayani](https://x.com/arpit_bhayani) [写道](https://x.com/arpit_bhayani/status/2061295678735954270)（150 个赞，5 条回复，6,244 次浏览，65 次收藏）指出，OOM 仍是最常见的生产故障，因为 agent 在内存里保留了过多工具输出和文档状态；而 [@israfill](https://x.com/israfill) [展示了](https://x.com/israfill/status/2061383848047656963)（13 个赞，4 条回复）则展示了一张前后对比截图，说明 CodeGraph 如何消除代码库盲搜所浪费的 3,847 个 token。人们目前的应对方式包括：在遗留系统上加 Playwright 抽象、激进截断、建立仓库索引，以及使用 AdaCoM 这类外部上下文管理器。这个方向值得投入，因为无论在编码 agent 还是知识工作 agent 中，这种痛苦都直接表现为故障、token 浪费和人工清理。

### 企业部署仍卡在运行时安全与治理上

严重程度：高。[@NousResearch](https://x.com/NousResearch) [宣布了](https://x.com/NousResearch/status/2061323987804713083)（392 个赞，42 条回复，41,025 次浏览，78 次收藏）提到 OpenShell 对 Hermes Agent 的支持；[@shannholmberg](https://x.com/shannholmberg) [认为](https://x.com/shannholmberg/status/2061368566256189656)（20 个赞，773 次浏览，11 次收藏）指出，正是这一运行时层，才终于让企业部署成为可能。[@codebrandes](https://x.com/codebrandes) [链接到](https://x.com/codebrandes/status/2061523983724589485)（66 个赞，13 条回复，3,913 次浏览）是 Gate AI 的开发者文章，称提示词注入、机密泄露和被劫持的工具调用，仍是日常 agent 用户真正面对的攻击面。人们正通过把护栏移出模型，放进沙箱、策略引擎、代理网关和可审计运行时来应对。这个方向值得投入，因为一旦 agent 拥有 shell 访问、工具和持久状态，仅靠提示词防御显然不够。

### 静态 skill 包浪费 token，还会造成配置漂移

严重程度：中高。[@room_ashish](https://x.com/room_ashish) [推介了](https://x.com/room_ashish/status/2061383482379755567)（8 个赞，200 次浏览）围绕一个明确抱怨展开：agent 每次请求都要读取所有 skill 描述。[@aiedge_](https://x.com/aiedge_) [链接到](https://x.com/aiedge_/status/2061213698115654062)（19 个赞，1,471 次浏览，33 次收藏）介绍了官方 Hermes Skills Hub，其公开外壳已经在加载所有注册表中的 88k+ skills；[@HuggingPapers](https://x.com/HuggingPapers) [指向了](https://x.com/HuggingPapers/status/2061385597277618531)（21 个赞，1,072 次浏览，14 次收藏）则介绍了 COLLEAGUE.SKILL 的多阶段蒸馏流程。应对模式已经很清楚：把 skills 托管在服务端、通过 MCP 在运行时解析，并围绕共享注册表做标准化，而不是在项目之间来回复制提示词文件。这个方向值得投入，因为成本会立刻体现为提示词变长、重复配置，以及不同工具之间行为不一致。

### 市场仍缺乏足够的信任与深度，难以形成流动性

严重程度：中高。[@tetsuoai](https://x.com/tetsuoai) [报道称](https://x.com/tetsuoai/status/2061412883867881737)（144 个赞，28 条回复，5,833 次浏览，31 次收藏）展示了 AgenC 的一次实时付款，但最早的一批回复中就有人要求提供证据。[@aashatwt](https://x.com/aashatwt) [构建了](https://x.com/aashatwt/status/2061509343397470600)（42 个赞，11 条回复，1,485 次浏览）介绍了 AgentLance，最有力的回复立刻指出，跨 marketplace 的信誉可移植性仍未解决。最直白的是，[@Ahmedhaq01](https://x.com/Ahmedhaq01) [表示](https://x.com/Ahmedhaq01/status/2061399399402516546)（18 个赞，12 条回复，224 次浏览）称他放弃了 agent marketplace 项目，因为生态还太早期，尚没有足够多的 agents 让市场变得有价值。这个方向值得投入，因为核心流程已经存在，但可重复的信任、发现机制和供给仍然薄弱。

## 3. 人们希望出现什么

### 带凭证、且保持新鲜的可移植上下文

最强烈的诉求不是“给我更大的上下文窗口”，而是“给我始终最新、带来源引用、又不会把 agent 搞崩的上下文”。Levie 的企业帖、Arpit Bhayani 的 OOM 帖子、AdaCoM 的可复用上下文管理器，以及 CodeGraph 的仓库索引，都指向同一个缺口。这是现实需求，不是愿景式想象，因为人们已经在手工搭抽象层和记忆层来补这个洞。机会：直接。

### 可跨 agent 使用、按运行时加载的 skill 层

Milkey、Hermes Skills Hub 和 COLLEAGUE.SKILL 都说明，用户想要的是一个共享的 skill 表面层：按需加载、跨工具可用，而且不必在不同项目之间复制提示词文件夹。这种需求是操作性的，而不是情绪性的：更低的 token 开销、更少的配置漂移，以及更好的治理。机会：直接。

### 跨框架的 agent 消息、身份与信誉

SIGNA 的宣传出发点就是一个抱怨：每个 agent 仍活在自己的孤岛上；而 AgenC 和 AgentLance 则说明，即便信任层尚未解决，支付闭环已经可以先跑起来。Ahmedhaq01 放弃 marketplace 项目的经历把未满足需求说得很明白：在 agents 能跨框架发现、验证并信任彼此之前，许多市场都会保持稀薄。机会：直接且竞争激烈。

### 可检查的轨迹与可恢复的会话

agent-trace、ActiveGraph、LiteParse 和 Memory Forge RS 各自解决了同一问题的一部分：团队需要可回放的轨迹、精确到源级别的审计线索，以及一种在上下文出错后无需把长会话从零重开的恢复方式。这是有明确工作流价值的现实可靠性需求。机会：直接。

| CodeGraph | 代码智能 / MCP | (+) | 本地语义索引、符号搜索、影响分析、更少的工具调用，以及对各类编码 agent 的广泛支持 | 需要按项目单独建立索引，且公开的节省数据仍来自厂商自有基准集 |

| Milkey | Skills 交付 / MCP | (+) | 共享 skills 按运行时加载，不会出现本地提示词漂移，一层即可覆盖多个编码 agent | 托管服务，对注册表和认证基础设施存在中心化依赖 |

| ActiveGraph | 状态 / 轨迹运行时 | (+) | 支持回放、分叉、差异比较、追加式事件日志，以及面向长运行 agent 的持久化图状态 | 相比简单的循环加记忆方案，架构开销更大 |
| LiteParse | 文档解析器 | (+) | 本地解析，并返回边界框和截图，可支撑精确到源区域的审计线索 | 在最复杂的版式和扫描件上，本地解析仍不如云端解析器 |

总体情绪偏向那些能减少上下文浪费、把控制权移出模型、并让 agent 行为事后可检查的工具。迁移路径很清晰：从静态 skill 文件夹转向按运行时加载的注册表，从只靠提示词的护栏转向策略运行时和流量网关，从盲目的文件搜索循环转向语义索引和可回放轨迹。Qwen3.7-Plus 和 MiniMax M3 也被当作“基准测试 + 定价”的产品包来评判，而不是抽象的前沿模型品牌。

CodeGraph 和 Gate AI 之所以格外突出，是因为它们都包裹在现有 agent 外层，而不是要求用户切换到一个全新的 agent。前者把代码库上下文和语义检索产品化；后者则把围绕模型 API 的内联安全、提示词压缩和可审计性产品化。

AgenC 和 SIGNA 展示了新兴商业栈正在分裂为两层。AgenC 处理任务发布、审核和结算；SIGNA 则专注于跨框架身份、消息和支付轨道。Unibase 的 AllScale checkout-skill 帖子说明，支付工作流已经开始被模块化成可移植 skills。

agent-trace、ActiveGraph、LiteParse 和 Memory Forge RS 体现了另一种构建模式：团队在努力让 agent 工作变得可检查、可回放、有源可依，甚至可编辑，而不只是试图让 agent 更自主。这是一个强信号，说明可观测性和恢复能力正在成为独立产品类别。

## 7. 机会在哪里

** [+++］ 面向生产级智能体的上下文操作系统** — 最有力的证据聚类来自 ［Aaron Levie 的企业上下文主题帖](https://x.com/levie/status/2061247380897579500)、[Arpit Bhayani 的 OOM 说明](https://x.com/arpit_bhayani/status/2061295678735954270)、[AdaCoM 的可复用上下文管理器帖子](https://x.com/dair_ai/status/2061455253325971789) 和 [CodeGraph 的代码库索引推介](https://x.com/israfill/status/2061383848047656963) 都指向同一个空白。未满足的需求不是原始 token 容量，而是横跨代码上下文和业务上下文的新鲜度、来源凭据、压缩、检索，以及抗故障的记忆机制。

** [++］ 运行时加载的技能交付与治理** — ［Milkey](https://x.com/room_ashish/status/2061383482379755567)、[Hermes Skills Hub](https://x.com/aiedge_/status/2061213698115654062)、[COLLEAGUE.SKILL](https://x.com/HuggingPapers/status/2061385597277618531) 和 [OpenShell/Hermes 运行时方案](https://x.com/NousResearch/status/2061323987804713083) 都指向同一个机会：团队希望 skills 能像基础设施一样被分发、按需加载，并在模型之外完成治理。

** [++］ 可审计轨迹与恢复工具** — ［agent-trace](https://x.com/Siddhant_K_code/status/2060972411642851796)、[ActiveGraph](https://x.com/yoheinakajima/status/2061556647512908063)、[LiteParse](https://x.com/jerryjliu0/status/2061551110150902060) 和 [Memory Forge RS](https://x.com/DanKornas/status/2061568715963912438) 从不同角度攻击同一个问题：当 agent 运行出错时，操作者需要回放、差异比较、源级证据，以及恢复路径。

** [+］ 跨框架智能体商业化与声誉** — ［AgenC Marketplace](https://x.com/tetsuoarena/status/2061407532074111055)、[SIGNA](https://x.com/Signa_Agent/status/2061450728535937109)、[BitAgent 上的 AllScale Checkout](https://x.com/Unibase_AI/status/2061391001756041375) 和 [AgentLance](https://x.com/aashatwt/status/2061509343397470600) 表明，支付与消息闭环已经开始跑通。正在浮现的缺口是可移植的信任：执行证明、信誉，以及足够多的交易对手，只有这样，这些市场才可能具备流动性。

## 8. 结论

1. **上下文处理如今已成为严肃 agent 面临的主要系统瓶颈。** Levie 的企业级提醒、Arpit Bhayani 的 OOM 帖子、AdaCoM 的外部上下文管理器，以及 CodeGraph 的索引仓库图谱，都指向同一变化：性能如今取决于 agent 看到了什么、保留了什么，以及丢弃了什么。（[来源](https://x.com/levie/status/2061247380897579500)）
2. **Agent 模型发布如今是按“基准测试 + 定价包”来评判，而不只是品牌事件。** Qwen3.7-Plus 和 MiniMax M3 都带着大范围基准表、多模态主张和具体的 API 经济性进入市场。（[来源](https://x.com/Alibaba_Qwen/status/2061506641120641494)）
3. **Skills 正在成为分发与运行时问题。** OpenShell、Milkey、Hermes Skills Hub 和 COLLEAGUE.SKILL 都把 skills 定义为受治理、托管、版本化的基础设施，而不是零散的提示词文件。（[来源](https://x.com/room_ashish/status/2061383482379755567)）
4. **Agent 商业化已不再是假设，但仍处于早期。** AgenC 和 SIGNA 展示了实时结算与钱包签名传输；与此同时，AgentLance 的回复和 Ahmedhaq01 的转向也说明，信誉和流动性仍是缺失层。（[来源](https://x.com/tetsuoarena/status/2061407532074111055)）
5. **可检查性正在成为独立的产品面。** agent-trace、ActiveGraph、LiteParse 和 Memory Forge RS 都建立在同一个判断之上：用户需要回放、比较、引用，甚至编辑 agent 历史，而不是盲目相信不透明的运行结果。（[来源](https://x.com/Siddhant_K_code/status/2060972411642851796)）
