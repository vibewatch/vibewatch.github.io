## 1. 大家在讨论什么

### 1.1 优化目标正从模型本身转向模型运行框架 ↑

多篇研究和产品相关帖子将焦点放在模型周边的运行时系统上，包括工具、上下文、权限、验证、记忆和反馈。一段广泛传播、据称来自 Karpathy 的视频称，小模型加上工具和反馈，表现可能胜过大模型；有人在回复中要求提供基准测试证据，因此，视频中关于模型规模的比较仍只是一种说法，并非经过验证的结果。[@Yarilo7brigada](https://x.com/Yarilo7brigada) [总结了](https://x.com/Yarilo7brigada/status/2123129806015652182)（737 个赞，74 次转推，27 条回复，71,648 次浏览，1,506 次收藏）。

另一条帖子配有一张独立制作的信息图，将 Anthropic 的工程文章和 Claude Code 文档归纳为运行框架的六个层面：工具、上下文、权限、钩子、验证和评测。帖子明确说明，这只是独立总结，并非 Anthropic 发布的内容。[@0xSynapz](https://x.com/0xSynapz) [发布了](https://x.com/0xSynapz/status/2123151831899517178)（10 个赞，13 条回复，101 次浏览，10 次收藏）。

Inferact 的 Simon Mo 表示，公司将基于 vLLM 构建一个自主推理系统，让它既能改进引擎，也能自我改进。有人在回复中询问，如何避免上游变更拖慢某些工作负载；Mo 回答说，变更会设为可选，以避免性能回退。[@simon_mo_](https://x.com/simon_mo_) [介绍了](https://x.com/simon_mo_/status/2123133742063706343)（483 个赞，61 次转推，24 条回复，39,052 次浏览，421 次收藏）。相关帖子介绍了这项计划。

关于有界自我更新的研究证据则更为具体。《安全个人递归自我改进》（Safe Personal RSI）研究保持模型权重和运行时代码不变，用 29 个可执行用例测试指令修改，并拒绝了 21 项高风险更新中的 20 项。论文报告称，一项获准的修复将攻击场景下的违规率从 10.7% 降至 0%，同时将安全任务完成率从 89.7% 提高到 100%。[@dair_ai](https://x.com/dair_ai) [总结了](https://x.com/dair_ai/status/2123511637584036078)（28 个赞，4 次转推，8 条回复，2,496 次浏览，34 次收藏）。相关论文：[预印本](https://arxiv.org/abs/2611.23651)。

Google 的 GUARD 预印本通过自检和基于遗憾的引导，只有在收益超过回退时才接受运行框架修改。帖子报告称，该方法在 43 项托管 SDK 任务上的准确率为 80.80%，比初始运行框架高 8.89 个百分点，每项任务的 token 数则减少了 54.5%。[@omarsar0](https://x.com/omarsar0) [总结了](https://x.com/omarsar0/status/2123420538030957015)（8 个赞，2 次转推，1 条回复，880 次浏览，8 次收藏）。相关研究：[论文](https://arxiv.org/abs/2611.23476)。

《自我改进记忆》论文探讨了一个相关的可移植性问题：经过优化的运行框架在底层模型改变后可能难以迁移。论文提出的记忆机制会记录每项修改的原因及其效果；研究报告称，在十轮编码运行中，与仅延续使用运行框架相比，该机制平均提升了 2.36 个百分点，同时指出，跨模型迁移并不总能胜过从头开始。[@Chinazhidx](https://x.com/Chinazhidx) [介绍了](https://x.com/Chinazhidx/status/2123309823060308148)（3 个赞，1 次转推，289 次浏览，2 次收藏）。相关论文：[研究](https://arxiv.org/abs/2611.18856)。

在更大胆的研究中，一篇 arXiv 预印本报告称，一个开放的 27B 模型改写了自身权重，在未见过的问题上准确率提高了 6.6 个百分点，并让受损副本在图像任务上的准确率恢复了 80% 以上。这是来自一个模型系列的研究结论；作者称，该系列中更小的模型并未实现提升。这并不能证明通用智能体能够安全地自我修改。[@FanJiajun67938](https://x.com/FanJiajun67938) [展示了](https://x.com/FanJiajun67938/status/2123183386801889776)（4 个赞，3 次转推，1 条引用推文，2,270 次浏览，1 次收藏）。相关预印本：[论文](https://arxiv.org/abs/2611.21885)。

### 1.2 评估正越来越贴近真实工作 ↑

Meta 的 MLE Agents 论文介绍了智能体如何为生产环境中的搜索排序系统提出、实现、训练和评估模型变更，同时由工程师掌控目标、探索方向和最终审核。论文报告称，智能体进行了 1,097 项实验，其中 325 项变更获采纳；在一次 A/B 测试中，搜索量提升了 0.23%。论文还指出，实验耗时数小时，离线指标可能与线上效果不一致，收益也可能趋于平缓。[@dair_ai](https://x.com/dair_ai) [总结了](https://x.com/dair_ai/status/2123423809839698400)（29 个赞、6 次转发、8 条回复、3,015 次浏览、26 次收藏）详见 [论文](https://arxiv.org/abs/2611.23910)。

## 2. 人们感到挫败的地方

### 现实场景中的延迟与安全

最明确的实际运行故障报告来自 CoRL 机器人研讨会：编程智能体执行任务时，真正用于操控机器人移动的时间仅占 20–36%；有一个智能体检测到作用力过大后，等了 48 秒才请求机器人回撤。报告还称，另一个智能体在出现风险信号后仍继续推挤，并主张采用无需等待模型响应的停止机制。报告中的任务结果每项任务仅基于 3 次试验，因此作者提醒，不应把观察到的成功率视为稳定的模型排名。值得投入开发的方向：本地低延迟安全控制，以及加快仿真到现实的迭代。[@junfanzhu98](https://x.com/junfanzhu98) [报告了](https://x.com/junfanzhu98/status/2123234896730792301)（5 次点赞、2 次转发、2 条回复、228 次浏览）。

### 脆弱的工作流程与监督负担

一位从业者描述了日常使用智能体的磨人之处：提示词流程繁琐、需要盯着脆弱的多智能体循环、纠正过度复杂的回答，还得应对智能体没能领会意图的情况。回复中还提到了人工合并审查造成的瓶颈和幻觉。这是一条详尽的第一人称经历，虽有少量回复表示认同，但不足以反映问题的普遍程度；它指出，人们需要能减轻监督负担、并在出错后顺利恢复的系统。[@tokenbender](https://x.com/tokenbender) [描述了](https://x.com/tokenbender/status/2123421151666000046)（69 次点赞、2 次转发、10 条回复、2,426 次浏览、16 次收藏）。

Hermes Enterprise 的一条回复也提到了设置方面的阻力：一位用户表示，配置和修复 Hermes 花的时间比使用它还多，并希望获得更好的设置指导。这条回复是具体的易用性信号，并非广泛的产品反馈。[@NousResearch](https://x.com/NousResearch) [宣布了](https://x.com/NousResearch/status/2123535954946257096)（440 次点赞、55 次转发、67 条回复、11,132 次浏览、77 次收藏）这项企业版部署。

### 任务最后一公里的完成情况仍不稳定

Stripe 的编程智能体评测显示，在受测的集成任务中，只有 29% 的运行结果满足全部标准，尽管插件提高了测得的分数。这是基准测试结果，不是用户投诉；它表明，即使平均得分更高，端到端任务的完整通过率仍可能不理想。可通过针对具体任务的检查和明确的完成标准来弥补这一差距。[@hazelcough](https://x.com/hazelcough) [总结了](https://x.com/hazelcough/status/2123481209963737473)（3 次点赞、2 次转发、1 次引用、86 次浏览）。

## 3. 人们希望出现什么

### 保留任务上下文的审批界面

TermiX 的演示展现了一项具体需求：在签署由智能体准备的交易前，将服务提供方、价格和双方约定的交付内容一并展示，这样用户无需从冗长的讨论串中重新拼凑背景，就能作出审批。这是一个实用且明确的机会：让审批内容易于理解、范围清晰。帖子的回复认同其中的信任问题，但不能独立证明这一需求普遍存在。[@0xDvox](https://x.com/0xDvox) [详细介绍了](https://x.com/0xDvox/status/2123483211699564721)（224 次点赞、5 次转发、143 条回复、10,068 次浏览）。

### 不再需要时刻盯着的智能体

一位从业者明确希望使用智能体不再那么磨人：减少繁琐的提示词流程、脆弱的循环，以及因没能领会意图而反复纠正的过程。这条帖子称赞了一种模型体验：即使用户表达不完整，或在对话中途改变想法，也能顺畅应对；但这只是个人偏好，并非广泛的对比结论。机会在于：让日常交互更具容错性，并减少监督工作。 [@tokenbender](https://x.com/tokenbender) [描述了](https://x.com/tokenbender/status/2123421151666000046)（69 个赞、2 次转发、10 条回复、2,426 次浏览、16 次收藏）。

### 更换模型后仍然有效的运行框架改进

一位从业者询问，更换模型后哪些经验真正能够迁移，并主张记录每项运行框架改动的原因及其效果，而不应只保留提示词或工具配置。所链接的研究报告称，在编码任务的10组配对运行中，带记忆的运行框架有9组胜过仅靠运行框架延续任务的方案；工作区对比中每种条件只运行了一次，因此结果值得关注，但证据有限。机会点：这对需要在模型更新期间持续维护智能体的团队而言尤为直接。 [@Howard_Pengg](https://x.com/Howard_Pengg) [比较了](https://x.com/Howard_Pengg/status/2123219313142485474)（1 个赞、3 条回复、193 次浏览）。
