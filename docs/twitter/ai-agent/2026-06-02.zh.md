# Twitter AI Agent - 2026-06-02

## 1. 人们在讨论什么

### 1.1 context、memory 和 harness 成了 Agent 构建者的共同语言 🡕

当天讨论最热的并不是哪个模型赢了基准测试，而是如何把 Agent 工作拆分为 context、memory 和 harness 三层，以及判断其中哪些层能在生产环境中真正形成复利。四条入选内容支撑了这一主题。

[@DataChaz](https://x.com/DataChaz) [认为](https://x.com/DataChaz/status/2061825344110199178)（230 个点赞、21 条回复、30,013 次浏览、348 次收藏）认为，真正能长期积累的能力包括 context engineering、工具设计、orchestrator-subagent 模式、严格的评测纪律、作为协议层的 MCP，以及“harness > model”的思维方式。最有价值的回复马上把这个观点往前推进了一步：有人说，如果 Agent 无法从崩溃的子进程中恢复，或无法续接会话，那么 harness 比 MCP 更重要；还有人说，harness 需要具备审计轨迹。

[@nabu_lines](https://x.com/nabu_lines) [写道](https://x.com/nabu_lines/status/2061498339439382551)（72 个点赞、46 条回复、2,008 次浏览）认为，构建者在沉迷排行榜频繁更替之前，应该先学会 context engineering、memory engineering 和 harness engineering。在后续回复中，他将 context engineering 定义为信号选择；将 memory engineering 定义为 Agent 随时间记住什么、遗忘什么、检索什么；将 harness engineering 定义为围绕模型构建的工具、工作流、编排、代码和系统设计。

[@mfpiccolo](https://x.com/mfpiccolo) [写道](https://x.com/mfpiccolo/status/2061474404014477543)（58 个点赞、5 条回复、13,319 次浏览、115 次收藏）认为，当工作单元是整个框架时，harness 臃肿就是一种结构性问题。他给出的修复方案是使用更小、可替换的 worker 和类型化函数，让检索、重排序和 provider 调用可以彼此独立替换，而不是不断把一个单体系统越堆越大。

**讨论洞察：** 回复不断把“harness > model”具体化为一组更明确的要求：崩溃恢复、会话续接、事件追踪，以及可审计的历史记录。

**与前一天对比：** 6 月 1 日的讨论把上下文处理视为生产瓶颈。到 6 月 2 日，这个问题有了更稳定的词汇框架，讨论也开始转向更小、更容易替换的组件。

### 1.2 多 Agent 架构图开始收敛到控制平面、验证循环和 memory manager 🡕

随着这套词汇逐渐稳定，人们分享的架构图也越来越相似：顶部是编排层，中间是专用 worker，底部是工具和 memory，外面再包一层验证或可观测性。四条入选内容支撑了这一主题。

[@MeenakshiYACS](https://x.com/MeenakshiYACS) [分享了](https://x.com/MeenakshiYACS/status/2061628873746321617)（83 个点赞、29 条回复、784 次浏览）分享了一套参考架构：在一张图里同时列出了用户与客户端入口、编排与控制平面、专用 Agent、工具、memory、监控、可靠性，以及治理或安全模块。它的核心判断与当天更广泛的讨论一致：Agent 本身不是系统，围绕 Agent 搭建的架构才是系统。

**讨论洞察：** 最有价值的回复并不太在意“多 Agent”这个标签本身，而更关心当专业 worker 共享状态时，如何协调、验证，以及在出错后如何恢复。

**与前一天对比：** 6 月 1 日更强调 harness 组件和安全运行时。到 6 月 2 日，传播开来的已经是完整的全栈架构图和按角色划分的循环，看起来更接近可复用的操作模型。

### 1.3 GitHub 和 Microsoft 正把 Agent 推进受治理的生产界面 🡕

最具体的平台动作来自 GitHub 和 Microsoft，而这两次发布都呼应了时间线中已经出现的运营者抱怨：阻碍生产落地的，与其说是模型质量，不如说是信任不足和上下文缺失。四条入选内容支撑了这一主题。

[@joaomdmoura](https://x.com/joaomdmoura) [表示](https://x.com/joaomdmoura/status/2061840271688839378)（36 个点赞、6 条回复、9,976 次浏览）认为，大多数 Agent 项目之所以 ROI 转负，并不是因为 Agent 失效，而是因为它们根本进不了生产环境。他说自己的团队经常跑的是 GPT-4o mini，真正的障碍是治理、可控的数据暴露范围，以及缺失的可观测性；Sam Charrington 在回复中补充说，如今仅靠测试已经不够，决定系统是否值得信任的是 guardrails、red-teaming、可观测性，以及合适的人类参与环路。

[@GHchangelog](https://x.com/GHchangelog) [宣布](https://x.com/GHchangelog/status/2061870568710848976)（4 个点赞、516 次浏览、5 次收藏）提到了 GitHub Agent Apps。链接的更新日志显示，合作伙伴 agent 现在可以从 GitHub Marketplace 安装，并可通过分配 issue、在 PR 评论里 @ 提及 agent，或在 Agents UI 中选择 agent 来调用。这意味着 agent 成了 GitHub 原生工作流界面的一部分，而不再只是旁路集成。

[@GHchangelog](https://x.com/GHchangelog) [宣布](https://x.com/GHchangelog/status/2061870626621558931)（3 个点赞、179 次浏览、3 次收藏）表示，Copilot code review 现在支持可定制的 agent skills 和 MCP 连接，并为更复杂的 pull request 新增了 Medium 分析层级。链接的更新日志称，审查现在可以从 issue tracker、文档、服务目录和事故处理工具中拉取上下文，而共享配置会把这些设置同时带到审查和 cloud-agent 工作流中。

[@Microsoft365Dev](https://x.com/Microsoft365Dev) [宣布](https://x.com/Microsoft365Dev/status/2061904436075610470)（7 个点赞、340 次浏览）把 Work IQ 称为“面向每个 Agent 的生产级智能”。Microsoft 的 devblog 将其描述为一个 agent-first 层，覆盖聊天、上下文、工具和工作区，并提供 A2A、远程 MCP、REST 端点、基于 Rego 的策略引擎，以及内置日志和可审计能力。

**讨论洞察：** 这些发布虽然路径略有不同，但都在解决同一个抱怨：给 agent 提供组织上下文，收窄工具暴露面，加上策略与日志，并让管理员能够控制成本和信任。

**与前一天对比：** 6 月 1 日还把运行时安全视为 Agent 周边正在形成的一层；到 6 月 2 日，GitHub 和 Microsoft 已经把这一层打包进了主流开发者工作流。

### 1.4 skills 正变成带有分发和反馈循环的可安装资产 🡕

关于 skills 的讨论，已经从“把 prompt 存到某个地方”转向仓库、安装器、市场和评测循环。四条入选内容支撑了这一主题。

## 2. 什么让人沮丧

### 生产信任和可观测性仍然挡住了本来能工作的 Agent

严重程度：高。[@joaomdmoura](https://x.com/joaomdmoura) [表示](https://x.com/joaomdmoura/status/2061840271688839378)（36 个点赞、6 条回复、9,976 次浏览）认为，大多数 Agent 项目 ROI 变负，并不是因为模型失效，而是因为组织不会把自己不信任的系统推上线。他举的例子很具体：无法满足的治理要求、无法控制的数据暴露，以及缺失的可观测性层。回复没有缓和这个抱怨，反而把它说得更尖锐：Sam Charrington 表示，如今测试是必要条件，但远远不够；真正带来部署信心的是 guardrails、red-teaming、可观测性，以及 human-in-the-loop 设计。[@DataChaz](https://x.com/DataChaz) [认为](https://x.com/DataChaz/status/2061825344110199178)（230 个点赞、21 条回复、30,013 次浏览、348 次收藏）下也有人回复称，如果 Agent 连崩溃子进程恢复或会话续接都做不到，技术栈其他部分几乎都不重要。人们当前的应对方式，是把上下文和控制能力推入 MCP 界面、策略引擎、审计日志，以及 GitHub code review 和 Work IQ 之类的审查工作流。这个方向值得投入，因为大型平台已经在围绕同样的痛点发布产品。

### 框架臃肿和协作开销让多 Agent 系统变得脆弱

严重程度：高。[@mfpiccolo](https://x.com/mfpiccolo) [写道](https://x.com/mfpiccolo/status/2061474404014477543)（58 个点赞、5 条回复、13,319 次浏览、115 次收藏）认为，harness 团队会陷入一种可预测的漂移循环：框架长出本不需要的功能，system prompt 越来越大，检索层翻倍，每个任务的成本最终涨到三倍。[@adxtyahq](https://x.com/adxtyahq) [表示](https://x.com/adxtyahq/status/2061887251181945099)（68 个点赞、8 条回复、1,440 次浏览、50 次收藏）认为，真正的挑战是让多个 agent、工具和工作流可靠协同，而其回复则抱怨协作、实时状态共享，以及 subagent 遗忘上下文的问题。[@hnshah](https://x.com/hnshah) [总结道](https://x.com/hnshah/status/2061881301993717886)（19 个点赞、9 条回复、4,732 次浏览、57 次收藏）谈到了并行 agent 的好处，但马上就有人追问竞态条件。大家的应对模式很一致：更小的 worker、类型化函数、checkpoint 恢复、计划或审查轨迹，以及更严格的验证循环。这个方向值得投入，因为这些失败最终会表现为成本上升、协作 bug，以及长时任务不可靠。

### memory 依然太容易被重置

严重程度：中高。[@nabu_lines](https://x.com/nabu_lines) [表示](https://x.com/nabu_lines/status/2061498339439382551)（72 个点赞、46 条回复、2,008 次浏览）认为，memory engineering 已经成了一门独立学科，并在回复中将其定义为决定 Agent 随时间记住什么、遗忘什么、检索什么、学习什么。[@adxtyahq](https://x.com/adxtyahq) [表示](https://x.com/adxtyahq/status/2061887251181945099)（68 个点赞、8 条回复、1,440 次浏览、50 次收藏）下面，有构建者问该如何防止 subagent 忘记上下文，并在几轮迭代后变得越来越不可靠。[@KaiteeShiks](https://x.com/KaiteeShiks) [表示](https://x.com/KaiteeShiks/status/2061863953504907566)（50 个点赞、4 条回复、1,994 次浏览）认为，很多 Agent 会“忘掉一切”，包括此前的决策、项目上下文、用户偏好和过去的互动；链接的 Memanto 仓库则试图通过 `remember`、`recall` 和 `answer` 让 memory 成为可查询的能力，不过该帖子本身被标记为 `#ad`。人们的应对方式包括：在工作流中明确设置 memory-manager 角色、保留持久化笔记，以及使用旁路 memory 工具，而不是假设基础 Agent 会自己记住一切。这个方向值得投入，因为 memory 丢失会直接浪费重复劳动，并破坏长会话稳定性。

### Agent 商业仍然缺少可移植的信任

严重程度：中。[@tetsuoai](https://x.com/tetsuoai) [表示](https://x.com/tetsuoai/status/2061795143045542336)（85 个点赞、11 条回复、3,422 次浏览、23 次收藏）称其 Solana marketplace 上线了 10 个新工作，并告诉用户去完成任务、通过审核、拿到报酬；但马上就有人追问，究竟由谁来判定工作是否真的完成：买家，还是平台的测试、审核和争议处理系统？[@aashatwt](https://x.com/aashatwt) [构建了](https://x.com/aashatwt/status/2061509343397470600)（47 个点赞、12 条回复、1,835 次浏览）介绍了带 verified enclaves 且没有 human in the loop 的 AgentLance，但最有力的回复指出，跨 marketplace 的声誉可移植性仍未解决。[@allscaleio](https://x.com/allscaleio) [表示](https://x.com/allscaleio/status/2061448859113734532)（43 个点赞、11 条回复、2,187 次浏览）称其 portable checkout skill 消除了支付基础设施工作，但回复仍在追问最基本的信任问题，例如默认由谁控制密钥。人们目前依靠人工审核、verified enclaves 和 portable checkout skills 来应对，但信任层依然是碎片化的。这个方向值得投入，因为支付和任务轨道已经存在，而验证、声誉和争议处理还不能在不同市场之间顺畅迁移。

## 3. 人们希望出现什么

### 带凭证、可恢复的持久化上下文

最明确的需求不是更大的上下文窗口，而是能在崩溃后继续存在、带有来源信息、并且事后可检查的上下文。[@DataChaz](https://x.com/DataChaz/status/2061825344110199178) 下面的回复要求崩溃恢复、会话续接和审计轨迹；[@hnshah](https://x.com/hnshah/status/2061881301993717886) 下面的回复认为，计划和审查工件才是让人类能够安全扩展并行 agent 的关键；而 [@joaomdmoura](https://x.com/joaomdmoura/status/2061840271688839378) 则表示，可观测性才是让 Agent 值得部署的信任基础。GitHub code review 的 MCP 支持和 Microsoft Work IQ 部分回应了这一需求，但二者都绑定在特定平台上。机会：直接。

### 无需手工搭检索管线的共享企业上下文

GitHub 的代码审查更新和 Work IQ 的公开预览材料之所以存在，是因为团队希望 Agent 能访问 issue tracker、文档、服务目录、邮件、会议、文件、聊天以及其他组织信号，而不用再手工搭一层检索系统。这种需求是务实且紧迫的，不是愿景式的：当前的替代方案仍是平台专属的 MCP 接线、插件配置，或定制 glue code。这些产品证明了需求存在，但还没有提供覆盖技术栈其余部分的通用上下文层。机会：直接且竞争激烈。

### 可在任何地方安装，并且能证明自己确实变好的可移植 skills

Matt Pocock 的 skills 仓库、Skill RSI、Play Billing Skills 和 ACP 都指向同一个诉求：把 skills 当成可移植资产，而不是静态 prompt 片段。构建者想要的是安装流程、跨 agent 兼容性、领域化工作流，以及能够证明新版本 skill 真的优于旧版本的证据。眼下这些部件是分散存在的——仓库、安装器、协议和评测循环——但还没有一个占主导地位的跨 agent 打包与评分层。机会：直接。

### 面向 agent-to-agent 工作的可移植信任与声誉

商业相关讨论里最有分量的回复，并不是要求更多 marketplace，而是在追问：Agent 怎么知道上次到底是谁交付了结果，谁来决定工作已经完成，以及争议如何跨市场解决。[@aashatwt](https://x.com/aashatwt/status/2061509343397470600) 立刻收到回复称，声誉可移植性仍未解决；[@tetsuoai](https://x.com/tetsuoai/status/2061795143045542336) 引来了关于验证的提问；[@allscaleio](https://x.com/allscaleio/status/2061448859113734532) 则显示，portable checkout skills 可以先解决支付流程，却还没解决信任流程。这是一个现实需求，但仍处在早期，而且竞争会非常激烈。机会：直接且竞争激烈。

总体来看，人们更偏好那些要么缩小工作单元、要么集中治理能力的工具。迁移路径很清楚：从 prompt 文件夹走向可安装的 skills 和协议，从单体 harness 走向 planner 与 validator 循环，从盲目往上下文里塞内容走向 MCP 和 Work IQ 这样的共享上下文层。竞争格局也很明确：GitHub 和 Microsoft 正在把信任与上下文打包进大型平台，而基于仓库的 skills 与 ACP 则在反方向上推动可移植性。

## 6. 新动态与值得关注的内容

### Co-Scientist 把多 Agent 论点变成了公开的科学产品

[@GoogleDeepMind](https://x.com/GoogleDeepMind) [介绍了](https://x.com/GoogleDeepMind/status/2061857539977842793)（300 个点赞、23 条回复、16,047 次浏览、90 次收藏）介绍了 Co-Scientist：一个基于 Gemini 的多 Agent 系统，能够生成、辩论并演化假设。链接的 DeepMind 文章详细解释了这套 agent coalition——generation、proximity、reflection、ranking、evolution、meta-review 和 supervisor 等角色——并将其与公开合作者和纤维化、ALS、衰老研究中的已发表案例联系起来。值得注意的转变在于，多 Agent 模式在这里以严肃科研产品的形式出现，并且有公开证据支撑，而不只是构建者式表演。

### ACP 让“自带 Agent”成为有文档支持的桌面工作流

[@windsurf](https://x.com/windsurf) [表示](https://x.com/windsurf/status/2061898147107045843)（18 个点赞、4 条回复、1,474 次浏览）表示，Codex CLI 现在可以在 Devin Desktop 中运行。链接的 ACP 文档将 Agent Client Protocol 描述为一种类似 LSP 的 coding agent 标准，并明确列出 Codex CLI、Claude Agent、OpenCode、Junie、Gemini CLI 和自定义 agent 为兼容对象。这一点很重要，因为互操作性正开始从演示走向有文档支撑的产品行为。

### portable checkout 成了一种 skill，而不再是集成项目

[@allscaleio](https://x.com/allscaleio) [表示](https://x.com/allscaleio/status/2061448859113734532)（43 个点赞、11 条回复、2,187 次浏览）表示，AllScale Checkout 已作为 BitAgent marketplace 上的 portable skill 上线。被引用的公告把这种新意具体化了：凭证设置、服务端签名、checkout intent 创建、支付状态轮询、webhook 验证和调试，都被打包成一个可复用的 skill 包，而不是又一个定制集成项目。这很值得关注，因为它表明支付工作流正开始变成可以在不同 agent 之间迁移的 skill 对象。

## 7. 机会在哪里

**[+++］ 受治理的上下文与可观测性层**——最有力的证据簇来自［@joaomdmoura](https://x.com/joaomdmoura/status/2061840271688839378)、GitHub 代码审查 MCP 发布、GitHub Agent Apps 和 Microsoft Work IQ。尚未被满足的需求并不是另一个更聪明的模型，而是一种让 Agent 获得组织上下文、策略、日志和可控信任、从而真正能够上线的方式。

**[+++] 可移植的 skills 打包与评测** —— Matt Pocock 的 skills 仓库、Skill RSI、Play Billing Skills、ACP，以及 GitHub 新推出的 skills 界面，都指向同一个切口：skills 需要分发、安装流程、互操作性和有证据支撑的版本管理。现在市场上已经有仓库、协议和实验，但还没有一个占主导地位的层把它们真正连接起来。

**[++] 更小的 harness 组件与协作工具** —— DataChaz 的框架、mfpiccolo 对框架臃肿的批评、adxtyahq 的工作流帖子，以及 hnshah 围绕持久化计划的讨论，都在说明编排单元应该更小。机会在于构建工具，让 subagent 更容易协调、恢复、检查和替换，而不至于把整个 harness 做成一座难以撼动的纪念碑。

**[++] 带来源信息的可查询 Agent memory** —— nabu_lines 对 memory engineering 的表述、adxtyahq 关于上下文漂移的回复串、Memanto 的旁路 memory 方案，以及当天反复出现的架构图，都指向同一个缺口：Agent 需要的是类型明确、可检查、可恢复的 memory，而不是简单塞进一大团上下文。

**[+] 面向 Agent 商业的可移植信任与声誉** —— AllScale Checkout、AgentLance 和 AgenC 说明支付、enclave 和任务闭环开始能跑起来了。尚未解决的是可移植的声誉、验证和争议处理层，这也是为什么回复不断追问，到底由谁来判定 Agent 的工作已经完成。

## 8. 要点

1. **讨论正在收敛为三层结构：context、memory 和 harness。** DataChaz 和 nabu_lines 都把持久优势放在这三层，而不是基准榜单的涨跌上；回复则进一步补上了崩溃恢复和审计轨迹，认为这才是成熟度的真正门槛。（[来源](https://x.com/DataChaz/status/2061825344110199178)）
2. **多 Agent 的可信度，如今取决于编排和验证，而不只是更多 Agent。** Meenakshi 的架构图、adxtyahq 的工作流、DataScienceDojo 的 supervisor 幻灯片，以及 hnshah 对“从计划走向判断”的总结，都收敛到控制平面、validator 或 critic 循环，以及持久化工件上。（[来源](https://x.com/adxtyahq/status/2061887251181945099)）
3. **平台 incumbents 正在比构建者更快地把信任缺口产品化。** joaomdmoura 把治理和可观测性点名为主要障碍；同一天，GitHub 和 Microsoft 就推出了原生 Agent 界面、MCP 支持的审查，以及受治理的上下文层。（[来源](https://x.com/joaomdmoura/status/2061840271688839378)）
4. **skills 正变得可安装、可移植，也越来越可度量。** Matt Pocock 的仓库、Skill RSI、Play Billing Skills 和 ACP 都把 skills 当成可安装、可跨 agent 迁移、可被评测的资产，而不是藏在 prompt 里的文本。（[来源](https://x.com/justinwetch/status/2061859002749964487)）
5. **Agent 商业在转移信任之前，已经能先转移资金。** AgenC、AgentLance 和 AllScale Checkout 展示了真实的支付和任务闭环，但回复始终回到验证、密钥所有权和可移植声誉这些问题上。（[来源](https://x.com/tetsuoai/status/2061795143045542336)）
6. **高信号的多 Agent 系统，开始出现在真实垂直领域，而不只是开发者工具里。** Co-Scientist 的公开发布表明，同样的 supervisor、辩论和排序模式，已经延伸到科学假设生成，并且有公开的合作者案例支撑。（[来源](https://x.com/GoogleDeepMind/status/2061857539977842793)）
