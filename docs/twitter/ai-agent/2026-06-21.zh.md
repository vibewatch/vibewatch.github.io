# Twitter AI Agent - 2026-06-21

## 1. 人们在讨论什么

### 1.1 Harness 工程继续从口号走向操作系统（🡒）

最强的一组讨论仍然围绕模型外部的控制层展开，但 6 月 21 日，这一主题进一步落到了公开、可检视的具体产物上：课程、模式目录、可强制执行的钩子，以及那些已经在多个智能体之间分配工作的操作者笔记。至少有五条强相关内容支撑了这一主题。

[@rohanpaul_ai](https://x.com/rohanpaul_ai) [引用](https://x.com/rohanpaul_ai/status/2068767074663690502)（109 个赞、8 条回复、8,509 次浏览、63 次收藏）Aravind Srinivas 表示，Codex、Perplexity Computer 和 Claude Code 都是与智能体 harness 配套的编排系统，而不只是模型封装。这一点之所以重要，是因为当天其余内容给出了这种 harness 的具体形态：课程材料、可复用模式，以及运行时强制机制。

[@_rohit_tiwari_](https://x.com/_rohit_tiwari_) [指向](https://x.com/_rohit_tiwari_/status/2068321419185078394)（62 个赞、4 条回复、2,263 次浏览、73 次收藏）Learn Harness Engineering 将这项工作界定为智能体环境设计、状态管理、验证、控制系统，以及面向 Claude Code 和 Codex 的可靠工作流。

![Harness Engineering 课程页面，展示了有关代理环境、状态管理、验证和控制系统的模块](https://pbs.twimg.com/media/HLQnWPQacAA2cPq.png)

[@DanKornas](https://x.com/DanKornas) [分享了](https://x.com/DanKornas/status/2068771160469262568)（17 个赞、3 条回复、972 次浏览、15 次收藏）AI Development Patterns；公开的 [AI Development Patterns 仓库](https://github.com/PaulDuvall/ai-development-patterns) 描述了覆盖基础、开发和运维的 24 种模式，并明确将其映射到 harness 工程中的前馈控制与反馈控制。这个仓库把原本常被当作“个人品味”的做法，转化为一系列具体的采用选择，例如安全沙箱、规范驱动开发、并行智能体、上下文持久化和自动修复。

[@sudoingX](https://x.com/sudoingX) [描述了](https://x.com/sudoingX/status/2068589629423657463)（70 个赞、10 条回复、4,099 次浏览、72 次收藏）一个实时运行的配置：在三台机器上部署 4-6 个智能体，用前沿模型处理高难度架构工作，用本地 Hermes Agent 承担大部分重构、起草和研究轮次。真正特别的细节在于模型周边的操作栈：用 tmux 保持持久会话，用 SSH mesh 保证可达性，并把 Git 仓库当作共享记忆。回复中，一位读者表示，最难且仍未解决的问题依然是写入冲突、按智能体划分角色、模型选择，以及 Git worktree 合并。

[@DanKornas](https://x.com/DanKornas) [重点介绍了](https://x.com/DanKornas/status/2068408778437840999)（15 个赞、3 条回复、1,066 次浏览、23 次收藏）Harmonist；其公开的 [Harmonist 仓库](https://github.com/GammaLabTechnologies/harmonist) 表示，如果所需审查者未运行、记忆未更新，或完整性检查失败，涉及代码改动的轮次就会被机械性阻断。这比单纯依赖提示词纪律更进一步：该仓库把协议执行定位为钩子层的门禁，而不是模型可以忽略的一条指令。

**讨论洞察：** 回复里，人们对抽象的“更好的提示词”兴趣不大，更关心尚未解决的协同问题：写入冲突、角色分配、模型路由，以及如何强制执行审查和记忆更新，而不只是要求模型去做。

**与前一天的比较：** 6 月 20 日的讨论还较为宽泛，聚焦循环、上下文层和 harness。6 月 21 日延续了同一主题，但把重心转向公开产物：一门课程、一个模式目录，以及一个核心主张是“智能体不应能够跳过规则”的仓库。

第二个主题是，行为层如今正被直接打包和分发，而围绕这些行为层的安全与治理工作，也正在独立成为一个产品类别。至少有四条强相关内容支撑了这一主题。

**讨论洞察：** 这场讨论越来越把 skills 和提示词视为可安装的软件供应链，而不是无害文本。这也是为什么当天构建者的精力一部分投向分享新的 skill 包，另一部分则投向围绕它们构建扫描器、清单和治理框架。

**与前一天的比较：** 6 月 20 日已经显示出纯行为层仓库正在获得关注。6 月 21 日则补上了更硬的一面：供应链验证、skill 扫描，以及一家银行公开发布自己的治理栈。

### 1.3 持久化的私有运行时比纯粹的演示魔法更重要（🡖）

第三个主题是，人们评判智能体运行时，看的是它能否持续运行、恢复、安排工作，并让有用的上下文保持活跃。整体氛围仍然积极，但最有力的证据指向的是耐久性和运维，而不是新奇感。

[@acoyfellow](https://x.com/acoyfellow) [介绍了](https://x.com/acoyfellow/status/2068504499333878090)（8 个赞、7 条回复、1,480 次浏览、18 次收藏）My AX 作为部署在用户 Cloudflare 账户中的单操作者运行时，支持持久化对话、自带 MCP 工具、周期性任务、受限子智能体和保留输出。公开的 [My AX 仓库](https://github.com/acoyfellow/my-ax) 补充了推文中只略微提及的运维细节：明确限制委派深度、定时任务、工作区快照和部署边界。

[@openclaw](https://x.com/openclaw) [宣布了](https://x.com/openclaw/status/2068567818862485740)（94 个赞、11 条回复、8,296 次浏览）OpenClaw v2026.6.9 带来了更稳定的智能体恢复能力、更强的 Codex 集成、更精简的分发，以及搜索和 skills 方面的改进。线程中的回复又通过列出重试、会话历史修复、回复对账和自动插件批准，让这份发布说明更为具体。

[@ScottyBeamIO](https://x.com/ScottyBeamIO) [描述了](https://x.com/ScottyBeamIO/status/2068616554493669565)（99 个赞、37 条回复、6,266 次浏览、88 次收藏）一种 Hermes Agent 配置：先起草 iMessage 回复，再从草稿与用户实际回复之间的差距中学习。技术上真正有意思的地方，不只是个性化这一主张本身，而是它的训练闭环：真实消息历史成为监督信号。

[@GoogleCloudTech](https://x.com/GoogleCloudTech) [分享了](https://x.com/GoogleCloudTech/status/2068770931447570457)（41 个赞、1 条回复、4,154 次浏览、14 次收藏）一个生产案例：专门化多智能体系统将大型 TensorFlow 模型迁移到 JAX。相关的 [Google Cloud 文章](https://cloud.google.com/blog/topics/developers-practitioners/6x-faster-migration-from-tensorflow-to-jax) 表示，该系统使用分层 Playbooks，并结合定量与定性验证，在复杂 YouTube 模型迁移中报告了 6.4x-8x 的加速。

**讨论洞察：** 最强的运行时相关帖子都传达出同一个潜台词：难点已经不再是让智能体一次做出一件惊艳的事，而是通过恢复、周期性执行、人类边界和明确验证，让它长期保持有用。

**与前一天的比较：** 6 月 20 日更关注智能体跨越手机、设备和消息等不同界面。6 月 21 日则把镜头收窄到持久化、恢复和企业级验证。

## 2. 什么让人感到沮丧

### 多智能体工作流仍然败在协调，而不是模型的原始质量

严重程度：高。[@sudoingX](https://x.com/sudoingX) [描述了](https://x.com/sudoingX/status/2068589629423657463)（70 个赞、10 条回复、4,099 次浏览、72 次收藏）展示了一个可运行的多智能体配置，但最有价值的回复立刻点出了尚未解决的瓶颈：写入冲突、按智能体设计角色、按任务选择模型，以及 Git worktree 合并。[@rohanpaul_ai](https://x.com/rohanpaul_ai) [引用](https://x.com/rohanpaul_ai/status/2068767074663690502)（109 个赞、8 条回复、8,509 次浏览、63 次收藏）则用更简短的方式给出了同样的判断：产品是编排系统加 harness，而不只是模型本身。[@DanKornas](https://x.com/DanKornas) [回应了](https://x.com/DanKornas/status/2068771160469262568)（17 个赞、3 条回复、972 次浏览、15 次收藏）之所以要发布一个模式目录，正是因为团队仍然需要一种方式，把临时性的智能体使用转化为可重复的工作流。当前的应对策略是明确搭建脚手架：模式、钩子、共享仓库，以及更窄的角色分工。

### 信任与合规落后于智能体的真实部署进度

严重程度：高。[@Dagnum_PI](https://x.com/Dagnum_PI) [表示](https://x.com/Dagnum_PI/status/2068453940203864487)（32 个赞、3 条回复、924 次浏览）指出，美联储、OCC 和 FDIC 仍然没有适用于受监管工作流中生成式或智能体式 AI 决策的审计框架。[@sytaylor](https://x.com/sytaylor) [重点介绍了](https://x.com/sytaylor/status/2068684111183495368)（58 个赞、6,528 次浏览、78 次收藏）则是 Santander 对这一空白的回应：公开发布用于护栏、治理、鲁棒性和供应商中立模型访问的仓库。[@simplifyinAI](https://x.com/simplifyinAI) [补充说](https://x.com/simplifyinAI/status/2068729682917224930)（15 个赞、2 条回复、605 次浏览、11 次收藏）又给出了更具战术性的信号——NVIDIA 的 SkillSpector，其仓库称，被扫描的 skills 中有超过四分之一包含漏洞。之所以值得为此投入建设，是因为这种痛点并非理论问题：人们分发和安装行为层产物的速度，已经快于机构标准化其可信方式的速度。

### 智能体可靠性和产品质量仍需持续维护

严重程度：中。[@openclaw](https://x.com/openclaw) [发布了](https://x.com/openclaw/status/2068567818862485740)（94 个赞、11 条回复、8,296 次浏览）这是一个聚焦于琐碎痛点、更稳定恢复和会话修复的版本，本身就说明长时间运行的运行时仍会以日常方式出错。[@Pragmatic_Eng](https://x.com/Pragmatic_Eng) [引用](https://x.com/Pragmatic_Eng/status/2068726099119329558)（51 个赞、1 条回复、27,675 次浏览、30 次收藏）Dax Raad 表示，产品“腐烂得比以往更快”，因为智能体工作流让团队很容易交付低质量成果，除非他们持续把质量建设当作日常实践。可行的缓解方式不是继续炒作模型，而是更好的恢复路径、更强的终端 UX，以及更明确的审查和验证层。

## 3. 人们希望有什么

### 可检视、无需从零发明的 harness，供团队直接采用

最明确的实际需求，是围绕 AI 辅助开发提供可复用的结构。[@_rohit_tiwari_](https://x.com/_rohit_tiwari_) [分享了](https://x.com/_rohit_tiwari_/status/2068321419185078394)（62 个赞、4 条回复、2,263 次浏览、73 次收藏）一门免费的 harness 工程课程；[@DanKornas](https://x.com/DanKornas) [发布了](https://x.com/DanKornas/status/2068771160469262568)（17 个赞、3 条回复、972 次浏览、15 次收藏）一个包含 24 种模式的目录；以及 [@alex_prompter](https://x.com/alex_prompter) [展示了](https://x.com/alex_prompter/status/2068401605112930742)（72 个赞、10 条回复、5,259 次浏览、128 次收藏）表明，纯行为层仓库本身如今也能吸引大量星标。这里的诉求是务实的，而非愿景式的：团队想要的是可以检视、复制并持续演化的现成作战手册。机会：直接。

### 面向 skills、审查和高风险决策的机械化信任层

第二个需求，是能够证明智能体遵守了协议，而不只是声称自己遵守了协议的系统。[@DanKornas](https://x.com/DanKornas) [重点介绍了](https://x.com/DanKornas/status/2068408778437840999)（15 个赞、3 条回复、1,066 次浏览、23 次收藏）Harmonist 基于钩子的阻断门禁；[@simplifyinAI](https://x.com/simplifyinAI) [提到了](https://x.com/simplifyinAI/status/2068729682917224930)（15 个赞、2 条回复、605 次浏览、11 次收藏）作为安装前扫描器的 SkillSpector；以及 [@Dagnum_PI](https://x.com/Dagnum_PI) [描述了](https://x.com/Dagnum_PI/status/2068453940203864487)（32 个赞、3 条回复、924 次浏览）围绕智能体决策监管空白的讨论。Santander 的公开仓库今天已经给出了一部分答案，但底层需求仍然远未被满足。机会：直接。

### 让记忆、任务和工具始终由操作者掌控的持久化私有运行时

人们对运行时的期待并不只是“更自主的智能体”，而是带有持久性与边界的自主能力。[@acoyfellow](https://x.com/acoyfellow) [展示了](https://x.com/acoyfellow/status/2068504499333878090)（8 个赞、7 条回复、1,480 次浏览、18 次收藏）My AX 是部署在用户 Cloudflare 账户中的个人运行时，支持持久化对话和周期性任务；[@sudoingX](https://x.com/sudoingX) [使用了](https://x.com/sudoingX/status/2068589629423657463)（70 个赞、10 条回复、4,099 次浏览、72 次收藏）则是本地 Hermes Agent，用于私密的隔夜工作。这个需求很务实，但市场很可能会相当拥挤，因为几乎每个严肃的运行时构建者都在朝持久化、调度，以及本地或操作者自有状态收敛。机会：竞争激烈。

## 4. 正在使用的工具和方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| Claude Code | 编码智能体 | (+) | 是循环、skills 和 harness 设计的核心参照点；一再被当作其他系统进行封装的基础运行时 | 信息流反复表明，如果没有 harness、钩子和记忆纪律，仅靠原始提示词是不够的 |
| Hermes Agent | 智能体运行时 | (+/-) | 适合本地/私有的大批量工作、消息个性化和全天候自动化 | 回复暴露出尚未解决的协调问题，例如写入冲突、角色分配和路由 |
| OpenClaw | 智能体运行时 | (+) | 围绕恢复、Telegram 交付、搜索和更强的 Codex 集成保持活跃的发布节奏 | 这次发布本身就说明，可靠性和各种小毛病仍需要持续修复 |
| Harmonist | 编排框架 | (+) | 通过机械式阻断门禁、记忆检查和供应链验证，把执行机制从提示词中抽离出来 | 比轻量提示词包更强调操作规范；仍属于早期采用者工具 |
| AI Development Patterns | 工作流目录 | (+) | 为团队提供覆盖准备度、开发和运维的 24 种模式采用路线图 | 它提供的是文档和结构，本身并不负责执行 |
| SkillSpector | 安全扫描器 | (+) | 扫描 skills、仓库、URL 和文件，检查 64 种漏洞模式并给出明确风险分数 | 重点是安装时的 skill 风险，而不是完整的运行时行为 |
| autoguardrails | 护栏 harness | (+) | 固定评测套件、单一可变的 `policy.md` 暴露面，以及 ASR 跟踪，构成清晰的研究闭环 | 范围较窄：面向单轮护栏实验，而不是完整的智能体工作流 |
| mech-gov-framework | 治理框架 | (+) | 硬门禁、歧义检查、治理指标和供应商中立后端支持 | 被定位为合成高风险决策框架，因此在生产环境中的采用仍处于早期 |
| llm_bridge | LLM 基础设施 | (+) | 通过统一接口连接 OpenAI、Bedrock、Gemini 或自定义后端，降低供应商锁定 | 它解决的是后端切换问题，本身不负责编排或信任机制 |
| My AX | 个人运行时 | (+/-) | 支持持久化对话、周期性任务、自带 MCP 工具和明确的操作限制 | 仓库称其仍属实验阶段，部署工作量较大，许多边界需要操作者自行管理 |

总体来看，人们对明确的系统评价偏正面，对一次性提示词则褒贬不一。当工具能够厘清模型周边的控制层——模式、钩子、清单、门禁或可重复的运行时边界——人们最为热情。最清晰的迁移模式是：用前沿模型处理高难度推理工作，把大批量或周期性任务转向本地或更低成本的运行时，并将模型后端与让它可靠的 harness 分离开来。

Santander 这一组项目是最明确的构建者信号，因为它不是单个仓库，而是一整套控制层组合：护栏、机械化治理、模型抽象、公平性测试、压力数据集，以及欺诈图生成，统一归属于一个公开组织。这个组合读起来不像个人副项目，更像一家受监管机构在公开其内部 AI 脚手架。

My AX 和 OpenClaw 则是运行时一侧的对应案例。它们之所以突出，是因为强调的是持久化运作——任务、恢复、保留状态和受限执行——而不是新奇演示。Tiny Place 则是那个延续了“智能体商业”线程的异类：它为智能体提供了一个协商和结算工作的场所。

## 7. 机会在哪里

**[+++] Agent governance and protocol enforcement** — Evidence came from several sections at once: Harmonist turns required reviews and memory updates into mechanical gates; SkillSpector treats skills as a risky install surface; Santander open-sourced guardrail and governance repos; and [@Dagnum_PI](https://x.com/Dagnum_PI) [描述了](https://x.com/Dagnum_PI/status/2068453940203864487) 受监管工作流中的智能体决策仍存在尚未填补的审计空白。这一机会很强，因为实践痛点、合规压力和开源构建者活动同时指向了它。

**[++] 持久化的私有多智能体运作** —— My AX、OpenClaw、Hermes Agent 工作流，以及 sudoingX 的本地多机配置，都指向同一种需求：智能体要能保留状态、干净恢复、安排工作，并始终处于操作者控制之下。这一机会属中等强度，因为需求很明确，但已有多家构建者正在朝这一方向收敛。

**[+] 专门化迁移与现代化智能体** —— Google 的 TF-to-JAX 迁移系统表明，只要具备强大的 Playbooks 和验证闭环，专门化智能体栈已经能够加速困难的代码转换工作。这一机会仍处于萌芽阶段，因为信号虽强，但目前仍集中在一个公开的企业案例上，而非广泛可比的一组部署。

## 8. 要点

1. **围绕智能体的讨论继续从提示词技巧转向 harness 设计。** 当天最强的产物是一门课程、一个模式仓库、一个通过钩子强制执行的框架，以及关于如何在多个智能体之间分配工作的操作者笔记。（[来源](https://x.com/rohanpaul_ai/status/2068767074663690502)）
2. **Skills 和 Markdown 仓库如今被当作软件供应链，而不是无害文本。** skills 优先的仓库清单、SkillSpector 的扫描器，以及 Harmonist 的清单检查结合在一起，表明团队如今已经预期要安装并审计行为层。（[来源](https://x.com/simplifyinAI/status/2068729682917224930)）
3. **面向智能体系统的治理正在成为一个清晰可见的构建类别。** Santander 的开源项目组合，以及银行业相关声音对监管空白的抱怨，都显示出市场对 AI 决策周边可审计控制层的需求正在上升。（[来源](https://x.com/sytaylor/status/2068684111183495368)）
4. **真正胜出的运行时案例强调的是耐久性，而不是炫技。** My AX、OpenClaw、Hermes 的个性化能力，以及 Google 的迁移系统，都更强调持久化、恢复或验证，而不是一次性演示。（[来源](https://x.com/openclaw/status/2068567818862485740)）
