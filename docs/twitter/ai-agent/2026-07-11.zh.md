# Twitter AI Agent - 2026-07-11

## 1. 人们在讨论什么

### 1.1 Harness 工程正固化为仓库级操作系统 🡕

7 月 11 日最热的讨论并不是某个单独的模型发布，而是重心从提示词技巧转向面向仓库的 Agent 操作系统：路由器、工作流文档、测试、审查通道、追踪记录，以及对哪些系统应当实际采取行动的明确界定。以下五项内容从不同角度提供了证据。

[@jamonholmgren](https://x.com/jamonholmgren) [认为](https://x.com/jamonholmgren/status/2076001786700394610)（680 个赞、35 条回复、43,131 次浏览、1,574 次收藏）表示，如今要实现可靠的 Agent 式编程，需要 AGENTS.md 路由器、自愈文档、强制运行应用、端到端测试、自定义 linter、跨 Agent 审查、会话工作表、任务队列、性能检查，以及交班前的完整验证。其独特之处在于，他把这些视为一个整体系统：Agent 应该自己运行应用、边做边修问题，并留下足够的追踪状态，以便另一个 Agent 或人类能在中途接手、继续推进。回复又补充了两个有用的细节：在 hook 阶段，确定性规则可以替代部分路由；缺失的工具应被推入 need-human-feedback 队列，而不是临时即兴凑方案。

[@dr_cintas](https://x.com/dr_cintas) [报道](https://x.com/dr_cintas/status/2075630574069592251)（621 个赞、51 条回复、55,521 次浏览、970 次收藏）表示，他目前最喜欢的工作流是让 Claude Fable 5 负责规格和审查，而由 Grok 4.5 通过 Grok CLI 负责实现。公开的 [Fable Advisor README](https://github.com/DannyMac180/fable-advisor) 也体现了这种“架构师”模式，并为正确性要求更高的工作增加了可选的 GPT-5.6 Sol 通道。回复中有人询问 Terra 和 Codex 版本，说明实践者已经迅速开始微调不同模型的分工通道，而不是寻找一个放之四海而皆准的“最终赢家”。

[@RoundtableSpace](https://x.com/RoundtableSpace) [指出](https://x.com/RoundtableSpace/status/2076045111960416617)（45 个赞、8 条回复、48,238 次浏览、21 次收藏）介绍了免费的 [学习 Harness Engineering](https://walkinglabs.github.io/learn-harness-engineering/en/) 课程，截图和主页都显示，同样的结构已经进入公开教学：AGENTS.md、初始化、验证、可观测性和清晰交接。这一点很重要，因为关于 harness 的讨论正在变成可复用的训练材料，而不再停留在小圈子的讨论串里。

[@heyitsurya](https://x.com/heyitsurya) [梳理了](https://x.com/heyitsurya/status/2075769546804228526)（39 个赞、3 条回复、199 次浏览、9 次收藏）梳理了 LLM、Agent、Agentic workflow 和多 Agent 系统之间的边界。附带的信息图之所以有参考价值，是因为它把每个标签都对应到自主性、控制方式和最适合的任务，让过度自动化的代价变得清晰可见。

![一张信息图，按自主性和最佳使用场景区分 LLM、agents、agentic workflows 和 multi-agent systems](https://pbs.twimg.com/media/HM6TgSmaUAAzwk8.jpg)

另一个规模较小但很具体的可移植性信号来自 [@ArchitectHappy_](https://x.com/ArchitectHappy_) [提到](https://x.com/ArchitectHappy_/status/2075939322235146595)（18 个赞、8 条回复、1,071 次浏览、11 次收藏）[wshobson/agents](https://github.com/wshobson/agents)。README 显示，该项目可从一个 Markdown 源文件生成 92 个插件、199 个 Agent、162 项技能和 106 条命令，覆盖 Claude Code、Codex、Cursor、OpenCode、Gemini CLI 和 Copilot。

**讨论洞察：** 共同趋势是把判断沉淀为能跨会话留存的文件和通道：路由、技能、hook、追踪、规格和交接产物。

**与前一天对比：** 7 月 10 日强调的是循环类型和适合 Agent 的仓库布局。到了 7 月 11 日，讨论进一步推进到完整的 Agent 操作系统：路由器、审查通道、任务队列，以及可跨不同 harness 迁移的脚手架。

### 1.2 图结构、记忆地图和规划架构被视为比更大模型更省钱 🡕

第二个讨论集群认为，真正的瓶颈并不是缺少前沿智能，而是线性规划、反复重新摸清仓库结构，以及高 token 消耗的检索。研究、基准测试和代码记忆工具从不同角度提出了同样的判断。

[@alex_verem](https://x.com/alex_verem) [表示](https://x.com/alex_verem/status/2075994424484732984)（256 个赞、18 条回复、36,635 次浏览、433 次收藏）表示，[Atomic Task Graph 论文](https://arxiv.org/abs/2607.01942) 表明，只要把工作分解成图结构而不是直线流程，7B-8B 的开源模型就能在 Agent 基准上与 GPT-4 竞争，甚至超过它。他强调的结论非常具体：在 ALFWorld 上，8B Llama 模型使用 ATG 得分 63.65，而 GPT-4 使用 ReAct 得分 41.24；同时，幻觉动作从 43% 降至 12%。

[@0xSweep](https://x.com/0xSweep) [认为](https://x.com/0xSweep/status/2075728385377177918)（47 个赞、41 条回复、4,603 次浏览）表示，仓库记忆在缩小尺度上其实是同一个问题：Agent 因为每次会话都从无状态开始，只能反复重读相同文件。公开的 [codebase-memory-mcp README](https://github.com/DeusData/codebase-memory-mcp) 称，它会为 158 种语言构建本地 AST 和混合 LSP 知识图谱，集成 11 个编码 Agent，并将 5 个示例性的结构查询从大约 412,000 个 token 降到约 3,400 个。回复也给出了恰当的限定：这个比例本身也许有挑样之嫌，但一种能随代码编辑持续更新的解析式地图，确实与会逐渐腐坏的摘要型记忆层有本质区别。

![codebase-memory-mcp 的知识图谱界面，展示了一个稠密的代码仓库图谱，并提供节点和边过滤器以便进行结构探索](https://pbs.twimg.com/media/HM539ixbcAAkNld.jpg)

[@ArtificialAnlys](https://x.com/ArtificialAnlys) [报道](https://x.com/ArtificialAnlys/status/2075739735822307577)（89 个赞、8 条回复、6,564 次浏览、10 次收藏）表示，Muse Spark 1.1 在 Opencode harness 的 Coding Agent Index 中得分 69，低于 Codex 中 GPT-5.5 medium 的 71，高于 Claude Code 中 Claude Opus 4.8 medium 的 67，每项任务成本约为 1.4 美元。这张图表之所以有信息量，是因为它直接展示了得分与成本的权衡，也引出了回复中的关键提醒：这些排名衡量的是“模型加 harness”的整体，因此即便是接近前沿的成绩截图，买方仍然需要在自己的真实工作负载上重跑。

![Artificial Analysis 图表，对比了 Codex、Claude Code、Opencode、Cursor 及其他 harness 在 coding-agent 指数得分和单任务成本方面的表现](https://pbs.twimg.com/media/HM6CSZZbYAAE-3Q.jpg)

[@NirantK](https://x.com/NirantK) [总结](https://x.com/NirantK/status/2075829950352068690)（58 个赞、8 条回复、4,296 次浏览、37 次收藏）更直白地给出了当天的结论：在生产环境里，专用 harness 很可能会胜过通用封装器，因为一旦任务走出演示场景，确定性的上下文工程和成本纪律就变得更重要。

**讨论洞察：** 共同信念是，如今规划结构和检索结构比模型再多一点分数更重要。更好的任务拆解、更便宜的查询方式，以及感知 harness 的评估，都被视为经济优势。

**与前一天对比：** 7 月 10 日已经把评估和答案契约进一步推向生产环境。7 月 11 日则新增了图规划和持久化代码地图，作为对暴力堆上下文和增加大模型开销的具体替代方案。

最强的构建者动能集中在这样一类基础设施：它们让 Agent 可以发布应用、查询业务数据、持有持久状态，或部署到金融轨道上。反复出现的语言不是个性，而是 MCP 端点、仪表盘、钱包认证、发布控制和运行时队列。

**与前一天对比：** 7 月 10 日已经出现了 CoinMarketCap Agent Hub 和发布仪表盘这类可安装的控制表面。到了 7 月 11 日，这股势头进一步收束为更偏运营的后端基础设施：业务数据 MCP、钱包支撑的数据库，以及兼具部署和金融能力的工作区。

### 1.4 治理、契约和托管式多 Agent 运行时仍是门槛层 🡕

即使在以构建者为主的数据集中，最冷静的帖子仍反复回到同一个问题：生产环境中的采纳，受阻的与其说是模型的原始输出能力，不如说是治理、问责，以及对 Agent 系统如何行为的明确控制。

[@michaeljburry](https://x.com/michaeljburry) [分享了](https://x.com/michaeljburry/status/2075836197230813517)（457 个赞、80 条回复、91,142 次浏览、172 次收藏）给出了一位实践者的看法：大规模 Agentic AI 需要编排、上下文工程、状态管理、多 Agent 协作、安全和合规层，但更难的问题是治理和文化。回复立刻强化了问责角度：总得有人为 Agent 的决策和失败模式负责。

[@SciFi](https://x.com/SciFi) [提到](https://x.com/SciFi/status/2075616554553577708)（1 个赞、119 次浏览、3 次收藏）介绍了论文 [From Prompts to Contracts](https://arxiv.org/abs/2607.08028)，截图和摘要都异常具体地说明了企业级 harness 应该编码什么：来源边界、实体路由、答案契约，以及围绕可替换模型边界的可复现追踪。这比泛泛而谈的治理讨论更有说服力，因为它把要求变成了由代码托管的产物和固定的验证场景。

![《From Prompts to Contracts》的摘要节选，描述了面向企业 LLM agents 的来源边界、实体路由、答案契约和可复现追踪](https://pbs.twimg.com/media/HM4SQd3XMAAIPbU.png)

[@seratch](https://x.com/seratch) [指出](https://x.com/seratch/status/2075760707870794157)（9 个赞、814 次浏览、4 次收藏）表示，OpenAI 的 Responses API 现在支持基于 GPT-5.6 模型的 beta 多 Agent 运行；[文档](https://developers.openai.com/api/docs/guides/responses-multi-agent) 称，根 Agent 可以生成并行子 Agent、向它们发消息、中断它们，并限制并发度。它与当天其他讨论的关联很重要：托管式多 Agent 正在到来，而实践者也正坚持要求明确路由、可追踪性和有边界的角色分工。

**讨论洞察：** 在企业讨论、研究和 API 文档中，人们想要的控制表面都很明确：有名字的 Agent、有名字的契约、有名字的追踪，以及有名字的责任人。

**与前一天对比：** 7 月 10 日的路由争论主要围绕 UI 默认设置和模型选择器。7 月 11 日的治理层则更深入：谁被允许采取行动、哪些答案在结构上被允许，以及同一时间允许运行多少个子 Agent。

## 2. 什么让人感到挫败

### 无状态的仓库探索仍在烧钱又耗时

严重程度：高。[@0xSweep](https://x.com/0xSweep) [介绍了](https://x.com/0xSweep/status/2075728385377177918)（47 个赞、41 条回复、4,603 次浏览）指出了一个熟悉的失败模式：编码 Agent 会反复搜索同一个仓库，因为它们在会话之间忘记了代码库，结果把一些基本的结构性问题变成高额的 token 账单。[@jamonholmgren](https://x.com/jamonholmgren) [展示了](https://x.com/jamonholmgren/status/2076001786700394610)（680 个赞、35 条回复、43,131 次浏览、1,574 次收藏）则展示了操作侧的手工补救方案：自愈文档、追踪、任务队列和显式路由，避免下一次运行从零开始。人们正在用代码地图、更好的文档和更多仓库侧记忆来应对。这值得投入建设，因为实践者和工具构建者说的是同一种税：不产生任何用户价值的“重新发现”工作。

### 可靠的 Agent 工作仍需要过多人工脚手架

严重程度：中高。当天传播最广的建议，本质上就是一份庞大的配置清单。[@jamonholmgren](https://x.com/jamonholmgren) [列出了](https://x.com/jamonholmgren/status/2076001786700394610) 把路由器、hook、linter、多 Agent 审查、工作表、基准测试和夜班技能列为基础设施；而 [@RoundtableSpace](https://x.com/RoundtableSpace) [推荐](https://x.com/RoundtableSpace/status/2076045111960416617)（45 个赞、8 条回复、48,238 次浏览、21 次收藏）甚至是一整套免费课程，专门教人如何做好 harness 工程。即便是可移植性方案 [wshobson/agents](https://github.com/wshobson/agents)，本身也是因为团队不想为每个 harness 反复重建同一套脚手架。人们正在通过课程、插件市场和复制仓库模板来应对。这值得投入建设，因为需求显而易见，但目前的配置过程仍像量身定制的仓库木工活。

### 治理和问责仍比原始编码输出更难

严重程度：高。[@michaeljburry](https://x.com/michaeljburry) [表示](https://x.com/michaeljburry/status/2075836197230813517)（457 个赞、80 条回复、91,142 次浏览、172 次收藏）表示，在生产级 Agent 系统里，治理和文化比技术底座更难，回复则聚焦于谁该为 Agent 行为负责。由 [@SciFi](https://x.com/SciFi) [这里](https://x.com/SciFi/status/2075616554553577708) 提出的论文 [From Prompts to Contracts](https://arxiv.org/abs/2607.08028)，则把同样的挫败推进到架构层：没有来源边界、答案契约和可复现追踪，提示词加检索的原型根本撑不到产品化。人们正在通过人工审查、明确边界和固定验证场景来应对。这值得投入建设，因为这个阻碍同时出现在实践者证言和正式研究中。

### 基准截图和路由信号仍然很容易被误读

严重程度：中。[@ArtificialAnlys](https://x.com/ArtificialAnlys) [发布了](https://x.com/ArtificialAnlys/status/2075739735822307577) 给出了一张清晰的得分-成本图，但最有价值的回复其实是提醒：每个得分都把模型和 harness 打包在了一起。[@dr_cintas](https://x.com/dr_cintas) [展示了](https://x.com/dr_cintas/status/2075630574069592251) 展示了 Fable 加 Grok 的混合工作流，而回复立刻有人要求 Terra 和 Codex 版本，这也说明路由选择仍然高度依赖人工，且远未稳定。人们的应对方式是重跑本地评估，并把架构师和实现者角色拆分给不同模型。这值得投入建设，因为市场仍缺少能随工作负载迁移、而不只是停留在排行榜截图上的路由与评估层。

## 3. 人们希望有哪些东西

### 面向 Agent 的仓库操作系统

最明确的愿望不是更聪明的提示词，而是一套可重复的系统。[@jamonholmgren](https://x.com/jamonholmgren) [介绍了](https://x.com/jamonholmgren/status/2076001786700394610) 展示了一整套路由器、文档、测试、追踪、审查通道和性能检查；[@RoundtableSpace](https://x.com/RoundtableSpace/status/2076045111960416617) 把人们引向一门完整的 harness 工程课程；[wshobson/agents](https://github.com/wshobson/agents) 则打包了一个跨 harness 的市场，因为团队显然不想再手工拼装同样的脚手架。实际需求，是一个预先接好路由、验证、交接和可观测性的起步系统。机会评级：[+++] 直接。

### 能跨会话和代码编辑持久存在的代码记忆

这项需求表达得非常明确。[@0xSweep](https://x.com/0xSweep/status/2075728385377177918) 把反复重新摸清仓库结构视为纯浪费；[@jamonholmgren](https://x.com/jamonholmgren/status/2076001786700394610) 则正因为会话记忆不可靠，才把文档和追踪当成记忆基础设施。人们似乎想要的是一种低成本的结构化记忆层：它能与代码库保持同步、对人类可见，并阻止 Agent 为仓库本已“知道”的内容反复付费。机会评级：[+++] 直接。

### 面向发布、数据、部署和金融的 Agent 后端基础设施

当天多位构建者实际上都在为“行动”寻找可靠轨道。Hands 把发布操作变成了清晰可见的工作流，TrustMRR 通过 API 和 MCP 模式暴露经过验证的创业公司数据，Naven Workspace 把部署和注资放进同一个 Agent 工作区，Mneme 则通过钱包认证把持久状态推进到 Postgres schema 中。实际需求，是一类原生面向 Agent 的后端基础设施：比定制胶水更易集成，又比让模型直接在原始系统上即兴操作更安全。机会评级：[++] 直接。

### 契约驱动的治理与路由策略层

最严肃的企业需求，是一套能在模型替换后仍然成立、并可扩展到演示之外的策略。[@michaeljburry](https://x.com/michaeljburry/status/2075836197230813517) 把治理和问责视为瓶颈，[From Prompts to Contracts](https://arxiv.org/abs/2607.08028) 将其落到明确的答案契约和追踪上，而 [@dr_cintas](https://x.com/dr_cintas/status/2075630574069592251) 加上 [@seratch](https://x.com/seratch/status/2075760707870794157) 则表明，跨模型与子 Agent 的路由已经成为一级问题。实际需求，是策略引擎：决定谁应当行动、走哪条模型通道、什么证据算完成，以及如何让整个运行过程保持可审计。机会评级：[++] 直接。

|---|---|---|---|---|
| Fable Advisor | 路由与编排插件 | (+) | 让 Fable 5 负责规格和审查，同时把实现路由到 Grok 4.5 或 GPT-5.6 Sol；内置跨厂商审查 | 需要多个厂商的 CLI，并手动配置明确的通道 |
| Learn Harness Engineering | 课程与参考资料 | (+) | 提供围绕 AGENTS.md、初始化、验证和交接的公开课程、项目与模板 | 属于教学材料，不是开箱即用的运行时 |
| codebase-memory-mcp | 本地代码记忆 MCP | (+) | 本地 AST 和混合 LSP 图；支持 158 种语言；结构查询速度快；大幅降低仓库探索的 token 消耗 | 收益在大仓库中最明显；用户仍需在自身工作负载上验证宣称的效果 |
| Artificial Analysis Coding Agent Index | 基准测试套件 | (+/-) | 把任务得分与单任务成本合并进一张直观图表 | 模型和 harness 被打包在一起，排名无法直接迁移 |
| Atomic Task Graph | 规划框架 | (+) | 图式拆解、并行分支和分支内修复可在无需额外训练的情况下提升 Agent 规划能力 | 研究成果，并非现成可用的生产工具 |
| OpenAI Responses Multi-agent | API 与运行时 | (+) | 支持托管式子 Agent 生成、消息传递、等待和并发控制 | 仍处于 beta；会增加 token 成本，且需要边界清晰的并行任务 |
| Hands | 发布平台 | (+) | 支持先草拟发布、分阶段上线、分享页面、反馈工单和崩溃循环 | 聚焦较窄，主要服务客户端应用发布操作 |
| TrustMRR API plus MCP pattern | 结构化业务数据 | (+) | 提供经验证的创业公司营收数据，支持按 MRR 和要价筛选，并提供适配 MCP 的访问路径 | 需要 API key，且只覆盖一个业务数据领域 |
| Mneme and mneme-mcp | Agent 数据库与记忆层 | (+) | 提供真实的 Postgres schema、钱包认证、向量搜索和原生 MCP 访问 | 早期产品，且带有偏加密场景的定位 |
| Naven Workspace | 部署与金融工作区 | (+/-) | 钱包支撑的工作区、运行时选择、部署流程和实时运营定位 | 新兴表面，依赖特定链和运行时 |
| Agentic Plugin Marketplace | 跨 harness 脚手架 | (+) | 通过一个 Markdown 源文件，为主流编码 harness 生成插件、Agent、技能和命令 | 目录很大，能力强但也更难策展和维护 |

当某个工具消除了具体的运营税项——token 消耗、发布摩擦、业务数据缺失，或跨 harness 的重复建设——整体满意度最高。常见的应对方式是：让一个高判断力模型负责把关，把大批量工作下放给更便宜的模型或确定性基础设施，并把更多系统暴露为文件、MCP 或仪表盘，而不是把一切都困在单一聊天循环中。

因此，迁移压力看起来并不像“从供应商 A 切到供应商 B”，而更像“停止依赖裸 completion”。获得 traction 的工具，都是在模型周围加上了路由、记忆、发布控制或结构化 API 的那一类。

Fable Advisor 和 codebase-memory-mcp 从两个不同方向攻击同一个成本问题。前者把高 token 消耗的实现工作从最昂贵的模型上分流出去，后者则把仓库结构变成本地图谱，直接消除不必要的检索 token。

Hands、TrustMRR MCP、Naven Workspace 和 mneme-mcp 的角色更像操作后板，而不是面向终端用户的聊天产品。反复出现的触发点是：构建者希望 Agent 能通过结构化接口完成发布、查询业务数据、部署或持有持久状态，同时这些接口仍然能被人类检查和治理。

跨 harness 脚手架这一模式也值得注意。Agentic Plugin Marketplace 之所以存在，是因为团队希望路由方法论、专门技能和可复用 Agent 能跟着他们在 Claude Code、Codex、Cursor、Gemini、OpenCode 和 Copilot 之间迁移，而不是在每个表面上从头再来。

## 6. 新近且值得关注的内容

### Atomic Task Graph 让“更聪明的规划、更小的模型”成为可衡量的主张

它之所以值得关注，在于足够具体。[@alex_verem](https://x.com/alex_verem) [重点提到](https://x.com/alex_verem/status/2075994424484732984)（256 个赞、18 条回复、36,635 次浏览、433 次收藏）介绍了 [Atomic Task Graph 论文](https://arxiv.org/abs/2607.01942)，称图式拆解和分支内修复能让 7B-8B 模型在 ALFWorld 上击败使用 ReAct 的 GPT-4，同时显著减少幻觉动作。这把“更好的规划会更有效”这一常见直觉，变成了公开可见的基准结果。

### OpenAI 的 Responses API 在 beta 中正式把托管式多 Agent 带上台面

[@seratch](https://x.com/seratch) [指出](https://x.com/seratch/status/2075760707870794157) 表示，OpenAI 已为 Responses API 增加多 Agent 支持；[beta 文档](https://developers.openai.com/api/docs/guides/responses-multi-agent) 详细列出了根 Agent 生成、子 Agent 消息传递、等待、中断和并发限制。这一点之所以值得关注，是因为当天许多实践者模式仍然依赖手工编排；现在，平台本身开始吸收这部分能力。

### Learn Harness Engineering 把社交媒体梗变成了公开课程体系

[@RoundtableSpace](https://x.com/RoundtableSpace) [分享了](https://x.com/RoundtableSpace/status/2076045111960416617)（45 个赞、8 条回复、48,238 次浏览、21 次收藏）介绍了免费的 [学习 Harness Engineering](https://walkinglabs.github.io/learn-harness-engineering/en/) 课程。这个网站之所以值得关注，是因为它围绕 AGENTS.md、初始化、验证、可观测性和交接，打包了课程、项目和可复用模板，意味着这门学问已经作为工程方法在被教授，而不再只是零散技巧的口耳相传。

### 《从提示词到契约》为企业级 harness 提供了具体架构

[@SciFi](https://x.com/SciFi) [提到](https://x.com/SciFi/status/2075616554553577708) [From Prompts to Contracts](https://arxiv.org/abs/2607.08028)，这篇论文之所以值得关注，是因为它点明了企业真正需要的基础原语：来源边界、实体路由、答案契约、验证产物和可复现追踪。在这批材料里，它是最清楚地把“可靠性”从口号落到可检查结构上的项目之一。

## 7. 机会在哪里

**[+++］ 面向 coding agents 的仓库操作系统** — ［@jamonholmgren](https://x.com/jamonholmgren/status/2076001786700394610)、[学习 Harness Engineering](https://walkinglabs.github.io/learn-harness-engineering/en/)、[Fable Advisor](https://github.com/DannyMac180/fable-advisor) 和 [wshobson/agents](https://github.com/wshobson/agents) 都指向同一个缺口：团队希望路由、验证、可观测性和交接能够预先组装好，而不是按仓库逐个重建。这一机会很强，因为需求既表现为痛点，也在同一天表现为积极的工具构建。

**[+++］ 持久化代码记忆与结构化检索层** — ［@0xSweep](https://x.com/0xSweep/status/2075728385377177918) 让 token 浪费变得明确可见，而 [Atomic Task Graph](https://arxiv.org/abs/2607.01942) 和 [@jamonholmgren](https://x.com/jamonholmgren/status/2076001786700394610) 也都强化了围绕上下文建立更好结构的广泛需求。这一机会很强，因为它解决的是反复出现、成本高昂的工作流税，而不是猜测性的功能请求。

**[++］ 面向发布、营收数据、部署和持久状态的 agent backplanes** — ［Hands](https://github.com/botiverse/hands)、[TrustMRR API](https://trustmrr.com/docs/api)、[Naven Workspace](https://x.com/NavenNetwork/status/2075957359760027728) 和 [Mneme](https://github.com/mnemedb/mnemedb) 都揭示了同一个机会：提供结构化表面，让 Agent 能做真正的工作，而不是在原始系统上即兴发挥。这一机会强度中等，因为需求很具体，但每个类别都伴随着信任、集成和领域约束。

**[++］ 基于契约的治理与路由策略服务** — ［@michaeljburry](https://x.com/michaeljburry/status/2075836197230813517)、[From Prompts to Contracts](https://arxiv.org/abs/2607.08028)、[@dr_cintas](https://x.com/dr_cintas/status/2075630574069592251)，以及 OpenAI 的 [multi-agent 文档](https://developers.openai.com/api/docs/guides/responses-multi-agent) 都在用不同方式表达同一件事：总得有人决定哪条通道行动、什么证据算完成，以及如何让整个运行过程保持可审计。这一机会强度中等，因为需求显而易见，但买方通常会是严肃团队，而不是普通用户。

**[+］ 面向 harness 的基准测试与评估产品** — ［@ArtificialAnlys](https://x.com/ArtificialAnlys/status/2075739735822307577) 给出了图表，而真正的机会来自回复：团队需要能把模型质量和 harness 质量分开的评估，并能反映自己的工作负载，而不是依赖通用排行榜。这一机会仍在形成，因为市场显然需要这种洞察，但解法空间还在成形中。

## 8. 结论

1. **重心已经从提示词转向仓库产物。** 当天传播最广的建议，把 AGENTS.md 路由器、自愈文档、测试、追踪和任务队列视为可靠编码 Agent 的真正底座，而不是可有可无的润色。（[来源](https://x.com/jamonholmgren/status/2076001786700394610)）
2. **如今的成本控制意味着改变 harness，而不只是更换模型。** Fable Advisor 把判断与“打字”分开，而 codebase-memory-mcp 则通过把仓库结构转为本地图谱，来解决反复检索造成的浪费。（[来源](https://x.com/dr_cintas/status/2075630574069592251), [仓库](https://github.com/DeusData/codebase-memory-mcp)）
3. **结构化规划和检索，如今已成为暴力扩规模的可信替代方案。** Atomic Task Graph 主打图式拆解和分支内修复，代码记忆工具主打持久结构查询；两者都试图减少上下文膨胀，而不是靠更高花费去硬扛。（[来源](https://arxiv.org/abs/2607.01942)）
4. **获得 traction 的构建者，交付的是轨道而不是个性。** Hands、TrustMRR MCP、Naven Workspace 和 mneme-mcp 都把发布、业务数据、部署或持久状态封装成了 Agent 可直接使用的结构化接口。（[来源](https://x.com/istdrc/status/2075619136751952219)）
5. **基准测试和企业论文如今都表明，harness 是产品的一部分。** 排行榜仍把模型和脚手架打包在一起，而企业级可靠性也越来越意味着契约、追踪、边界和显式路由，而不是对模型的盲目信任。（[来源](https://x.com/ArtificialAnlys/status/2075739735822307577), [论文](https://arxiv.org/abs/2607.08028)）
