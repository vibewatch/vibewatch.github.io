### 1.2 Harness Engineering 成为设计讨论的主轴 🡕

前几天出现的 “harness engineering” 概念，在这一天达到讨论密度峰值。[@TheAhmadOsman](https://x.com/TheAhmadOsman) [表示](https://x.com/TheAhmadOsman/status/2046721205344850406)（172 个赞、20 次收藏、6.7K 次浏览）表示：“Harness Engineering is the new Software Engineering.” 这在回复区引发争论——[@guigotgit](https://x.com/guigotgit) 说：“我觉得我们还没找到更好的名字。” 而 [@rugbist_](https://x.com/rugbist_) 则反驳：“harness engineering 听起来像是同一份工作，只是步骤更多，而且薪水可能更低。”

[@Vtrivedy10](https://x.com/Vtrivedy10) 出现在 3 个高互动帖子中。他在一篇 [与 @himanshustwts 的播客回顾](https://x.com/Vtrivedy10/status/2046942634321559707)（47 个赞、14 次收藏）中概述了这种实践：“从模型的能力和缺陷出发，围绕它们构建系统（一个 harness），以完成任务。” Traces 是“持续学习和自我改进型智能体的信号”。他还 [指出](https://x.com/Vtrivedy10/status/2046712699908944079)（19 个赞）指出，Google 和前沿公司“正在大力投入研究 harness 如何以及为何能让智能体表现更好”，并引用 [@addyosmani](https://x.com/addyosmani) 的观点：“一个还不错的模型配上优秀的 harness，胜过一个顶尖模型配上糟糕的 harness。”

[@Marktechpost](https://x.com/Marktechpost) [提出了“Coordination Engineering”](https://x.com/Marktechpost/status/2046993449262752126)（16 个赞、33.8K 次浏览）将 JiuwenClaw 的 AgentTeam 能力视为超越 harness engineering 的下一步：由 Leader Agent 负责的分层编排、统一的团队工作区，以及事件驱动的故障恢复。

### 1.4 Context Engineering 从概念走向架构图 🡕

[@mdancho84](https://x.com/mdancho84) [发布了](https://x.com/mdancho84/status/2046974114091389052)（39 个赞、32 次收藏）发布了一张三阶段演进图，区分 RAG、Agentic RAG 和“context engineering 中的 agentic search”。关键区别在于：context engineering 将文件搜索工具、技能加载工具、数据库工具、网页搜索工具、记忆工具和 shell 工具加入检索链路；带有 Skills YAML frontmatter 的文件和记忆文件，则成为上下文窗口中的一等组成部分。

![三阶段架构图，展示了从采用固定检索流水线的 RAG，演进到带有搜索工具和数据库的 Agentic RAG，再到情境工程中的 Agentic search；后者包含文件搜索、技能加载、数据库、网页搜索、记忆和 shell 工具，并将这些输入送入带有 Skills YAML frontmatter 和记忆文件的上下文窗口](https://pbs.twimg.com/media/HGhQGs9XEAAtMvz.jpg)

[@ihtesham2005](https://x.com/ihtesham2005) [拆解了 Anthropic 工程博客中的发现](https://x.com/ihtesham2005/status/2047057952331481423)（4 个赞、4 次收藏）讨论了 MCP 上下文膨胀问题：将 MCP 服务器呈现为文件系统后，工具定义加载量从 150,000 个 token 降至 2,000 个 token，减少 98.7%。在代码执行环境中先过滤数据、再交给模型，使 Playwright 快照从 56KB 缩小到 299 字节，也让包含 500 个请求的访问日志从 45KB 缩小到 155 字节。“变聪明的不是智能体，而是架构变得更干净了。”

[@_avichawla](https://x.com/_avichawla) [持续获得更多关注](https://x.com/_avichawla/status/2046685172666712571)（152 个赞、283 次收藏、38.4K 次浏览）介绍了 InsForge 的量化结果：10.4M token 降至 3.7M（缩减 2.8 倍）、错误从 10 个降至 0、成本从 9.21 美元降至 2.81 美元。[@megacode_ai](https://x.com/megacode_ai) 回复：“Context engineering 正在成为独立的一层技术栈。”

**Comparison to prior day:** 4 月 21 日首次出现了量化的 context engineering 结果（InsForge 2.8 倍、Claude Context 40%）。4 月 22 日则新增了架构图、Anthropic 自己的工程数据（98.7% 缩减），以及“文件系统即工具注册表”的模式，让 context engineering 从可测量结果走向可复现技术。

### 智能体记忆需要递归式管理——严重程度：高

### 基础设施价格压缩威胁智能体初创公司——严重程度：高

普遍程度：这是数据集中识别出的 30-50 家智能体基础设施初创公司共同面临的结构性问题。三家超大规模云厂商的同步收敛，让这一威胁比 4 月 21 日更为尖锐。

### AI 智能体加剧了工程工具之间的上下文丢失——严重程度：中

4 月 22 日，6 个独立账号描述了同一种失效模式。[@carlvellotti](https://x.com/carlvellotti)：“没有记忆——每次会话都从头开始……决策死在 Slack 讨论串里。” [@JaynitMakwana](https://x.com/JaynitMakwana)：“真正让工程团队付出代价的是上下文切换：从 Slack 到终端，再到 GitHub，然后又回到 Slack。” [@base10_](https://x.com/base10_)：“AI 不只是加快了工程工作，也把它割裂了。”

普遍程度：高，遍及使用 AI 编程智能体的工程团队。CodeRabbit Agent 是首个明确针对这一缺口推出的产品。

### Harness Engineering 缺乏职业身份认同——严重程度：低

[@TheAhmadOsman](https://x.com/TheAhmadOsman) 宣称“Harness Engineering is the new Software Engineering”，但回复区并不完全认同这种说法。[@guigotgit](https://x.com/guigotgit)：“我们还没找到更好的名字。” [@rugbist_](https://x.com/rugbist_)：“同一份工作，只是步骤更多，而且薪水可能更低。” [@ethankongee](https://x.com/ethankongee) 还指出了评估上的缺口：“我找到的大多数文章都太抽象了……没有扎实的基准测试，很难判断一个 harness 到底好不好。”

普遍程度：正在形成——这门学科已经存在，但尚未形成统一命名和标准化评估标准。

## 3. 人们希望出现什么

### 无需递归管理、能够自我整理的智能体记忆

[@eddiegreenwood_](https://x.com/eddiegreenwood_/status/2046875748238283015)（116 个赞、111.5K 次浏览）自己搭建了归档系统，却仍然需要一个智能体来管理它。核心缺口在于：没有框架能在不增加另一层智能体的情况下，自动区分哪些内容值得记住、哪些只是噪声。[@eddiegreenwood_](https://x.com/eddiegreenwood_) 在回复中总结道：“记忆很容易，整理才是真正的工作。”

机会：高——如果有一套具备内置相关性评分和自动清理能力、且运行在单一智能体循环内而非独立管理层中的记忆系统，就能切中这一需求。

### 标准化的 Harness Engineering 基准测试

[@ethankongee](https://x.com/ethankongee) [阐述了这一差距](https://x.com/TheAhmadOsman/status/2046721205344850406)：“我正在学习如何构建智能体 harness，但我找到的大多数文章都太抽象了，没法真正帮我判断自己的 harness 是否有效。没有扎实的基准测试，很难知道一个 harness 到底好不好。” [@SentientAGI](https://x.com/SentientAGI) 的 Arena Cohort 0 结果开始回应这一问题，但目前还没有公开基准能够将 harness 质量与模型质量分离开来。

机会：高——一种能够将智能体表现拆分为模型贡献和 harness 贡献的基准测试，将重塑团队评估和投资智能体基础设施的方式。

### 语音智能体的打断与状态管理

[@JamesClawn](https://x.com/JamesClawn) [指出了](https://x.com/Cloudflare/status/2046816309963378840) 指出了一种具体失效模式：“当打断只能停止音频，却没有取消待处理的工具调用时，语音智能体会失去信任，因为在智能体继续行动之前，记忆和轮次状态仍然需要被彻底撤销。” [@somi_ai](https://x.com/somi_ai) 确认：“目前大多数语音技术栈在用户试图插话时，仍然会在用户说到一半时把用户截断。”

机会：中——如果语音智能体框架能在工具调用层面而不只是音频层面处理打断，就能补上生产级语音部署中的结构性信任缺口。

### MCP 上下文膨胀出现了 98.7% 的削减方案

## 7. 机会在哪里

`[+++]` **智能体记忆整理系统** —— 递归管理问题是当天浏览量最高的挫败信号（111.5K 次浏览）。每个智能体框架都提供记忆存储，但没有一个能提供智能整理：决定哪些内容值得记住、何时遗忘，以及如何防止无关上下文污染新会话。具备内置相关性评分和自动清理能力、能在单一智能体循环中运行的记忆系统，可以对准这种“追龙”模式。来源：[@eddiegreenwood_](https://x.com/eddiegreenwood_/status/2046875748238283015)、[@_orcaman](https://x.com/_orcaman/status/2046879308161925565)、[@WalrusProtocol](https://x.com/WalrusProtocol/status/2047010404040405248)。

`[+++]` **Context engineering 工具与服务** —— 3 个独立数据点证实了巨大的上下文浪费：InsForge 的 2.8 倍 token 缩减、Anthropic 的 98.7% 工具定义缩减，以及 Cloudflare 的 Code Mode 模式。构建上下文优化层的团队——包括语义检索、文件系统即注册表、增量索引和上下文压缩——能够同时解决成本和可靠性问题。市场仍处早期，且高度碎片化。来源：[@_avichawla](https://x.com/_avichawla/status/2046685172666712571)、[@ihtesham2005](https://x.com/ihtesham2005/status/2047057952331481423)、[@mdancho84](https://x.com/mdancho84/status/2046974114091389052)。

`[++]` **Harness 基准测试与评估** —— Arena Cohort 0 的结果显示，在最终表现得分上，harness 质量足以与模型选择分庭抗礼，但目前还没有公开基准能够将 harness 贡献与模型贡献分离。标准化的 harness 评估框架将帮助团队决定该投资基础设施还是模型。[@ethankongee](https://x.com/ethankongee) 明确要求“针对不同任务和行业的基准测试”。来源：[@SentientAGI](https://x.com/SentientAGI/status/2046995270039482534)、[@ethankongee](https://x.com/TheAhmadOsman/status/2046721205344850406)。

`[++]` **工程工作流中的团队上下文持久化** —— 6 个独立账号描述了同一种失效：AI 编程会话会重置上下文，决策死在 Slack 讨论串里，团队每个 sprint 都得反复解释同样的背景。CodeRabbit Agent for Slack 是首个针对这一问题发布的产品，但问题并不局限于 Slack，而是延伸到所有协作界面。来源：[@harjotsgill](https://x.com/harjotsgill/status/2046955870588960969)、[@carlvellotti](https://x.com/carlvellotti)、[@base10_](https://x.com/base10_/status/2046963112406868454)。

`[+]` **原生面向智能体的视频与媒体创作** —— HeyGen 的 Hyperframes 是首个专为智能体创作视频而设计的开源框架。更广泛的趋势是：每一种媒体创作工具都曾为拿着鼠标的人类打造，而智能体需要原生接口。音频（ElevenLabs 技能）、视频（Hyperframes）以及作为智能体原语设计的图像工具，都将从不断增长的 UGC 自动化浪潮（Higgsfield、Hermes Agent）中获得即时需求。来源：[@sentient_agency](https://x.com/sentient_agency/status/2046885537878065511)、[@ElevenLabsDevs](https://x.com/ElevenLabsDevs/status/2047025917034209382)。

`[+]` **工具调用层面的语音智能体状态管理** —— 当前语音智能体框架能在音频层面处理打断，却无法在工具调用层面处理。当被打断的智能体继续执行待处理操作时，用户信任就会被破坏。Cloudflare 和 LiveKit 正在投入这一领域，但面向客户支持和电话服务等生产级语音部署的缺口仍然存在。来源：[@JamesClawn](https://x.com/JamesClawn)、[@Cloudflare](https://x.com/Cloudflare/status/2046816309963378840)、[@livekit](https://x.com/livekit/status/2047048713638453591)。

Harness engineering 凭借量化证据主导了设计讨论。Arena Cohort 0 显示，配备合适 harness 的开源 MiniMax M2.5，能够以 Claude Opus 4.5 成本的 1/30 达到接近前沿模型的表现。JiuwenClaw 提出“Coordination Engineering”，作为下一层抽象。正在形成的共识是：按每美元计算，harness 质量比模型选择更重要。来源：[@SentientAGI](https://x.com/SentientAGI/status/2046995270039482534)、[@Vtrivedy10](https://x.com/Vtrivedy10/status/2046942634321559707)、[@Marktechpost](https://x.com/Marktechpost/status/2046993449262752126)。

3. CodeRabbit Agent for Slack 引发了当天规模最大的单一产品讨论浪潮（其放大量传播的帖子获得 2,104 个赞、226.8K 次浏览）。6 个独立账号描述了同一个痛点：AI 编程智能体把工程上下文割裂到不同工具之间，团队因此被迫充当记忆层。来源：[@IndianTechGuide](https://x.com/IndianTechGuide/status/2046965448026272122)、[@harjotsgill](https://x.com/harjotsgill/status/2046955870588960969)、[@base10_](https://x.com/base10_/status/2046963112406868454)。

4. Context engineering 从可测量结果推进到了可复现的架构模式。Anthropic 自己的工程数据显示，将 MCP 服务器呈现为文件系统后，上下文减少了 98.7%。InsForge 凭借 2.8 倍 token 缩减继续获得关注。[@mdancho84](https://x.com/mdancho84) 的架构图则把从 RAG 到 agentic context engineering 的演进整理成了三阶段流程。来源：[@ihtesham2005](https://x.com/ihtesham2005/status/2047057952331481423)、[@_avichawla](https://x.com/_avichawla/status/2046685172666712571)、[@mdancho84](https://x.com/mdancho84/status/2046974114091389052)。

5. 智能体记忆成为当天最令人沮丧、也最难解决的问题。[@eddiegreenwood_](https://x.com/eddiegreenwood_) 描述了递归式管理模式——构建智能体来管理智能体记忆——该帖子获得 111.5K 次浏览。目前没有框架能在不增加管理层的情况下，提供可扩展的记忆整理能力。来源：[@eddiegreenwood_](https://x.com/eddiegreenwood_/status/2046875748238283015)。

6. Devin 改变了对多智能体系统的公开立场，在反对多智能体 10 个月后，实现了“具体流程”。但限定条件很重要：多智能体适用于针对性的用例，而不是通用架构。这与当天更广泛的趋势一致：基于证据、有选择地采用。来源：[@cognition](https://x.com/cognition/status/2047054526583050647)、[@walden_yan](https://x.com/walden_yan/status/2047054554433462360)。

7. Google Cloud（13 款产品）、ElevenLabs（语音隔离）和 .NET（三种编写方式）都发布了官方智能体技能仓库。Crypto Skill Hub 收录了横跨 97 个 MCP 服务器的 1,185 项技能。技能生态正从社区驱动转向厂商策展，而 `npx skills add` 正成为标准安装模式。来源：[@rseroter](https://x.com/rseroter/status/2047062761738494073)、[@ElevenLabsDevs](https://x.com/ElevenLabsDevs/status/2047025917034209382)、[@diegoxyz](https://x.com/diegoxyz/status/2046885322685067390)。

8. HeyGen 开源了 Hyperframes，这是首个专为 AI 智能体构建的视频渲染框架。输入 HTML，输出 MP4，并为 Claude Code、Cursor、Gemini CLI 和 Codex 提供技能。与此同时，由 Hermes Agent 驱动的 UGC 创作工具 Higgsfield Marketing Studio 也产生了多条高互动帖子，声称可以用每月 100 美元替代每条视频 500 美元的代理商服务。来源：[@sentient_agency](https://x.com/sentient_agency/status/2046885537878065511)。
