# Twitter AI Agent - 2026-05-31

## 1. 人们在讨论什么

### 1.1 Harness 工程不再只是概念，而成了产品规格 🡕

5 月 31 日，AI Agent 领域的核心讨论聚焦于：能力究竟存在于哪里？多条帖子反复给出的答案都是“harness”：围绕模型构建的提示词、技能、文件系统、编排、记忆、钩子和验证层。共有四条入选内容支撑这一主题。

[@byanujpatel](https://x.com/byanujpatel) [分享](https://x.com/byanujpatel/status/2060967710008508607)（200 个赞、11,057 次浏览、261 次收藏）LangChain 的公开 [线束工程文章](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)。帖子将“Agent = Model + Harness”定义为一个公式，并将提示词、工具、文件系统、编排逻辑、钩子和沙箱视为把模型智能转化为实用工作的那层代码。

[@pallavishekhar_](https://x.com/pallavishekhar_) [绘制了](https://x.com/pallavishekhar_/status/2061085262680297836)（79 个赞、4 条回复、4,712 次浏览、114 次收藏）展示了一条从记忆和 ReAct 循环一路延伸到可观测性与 harness 工程的发展脉络。其中最有价值的一条回复指出，harness 工程并不是在其他一切都完成后才出现的“第 16 步”，而是其他主题所处的那个外层框架。

[@RoundtableSpace](https://x.com/RoundtableSpace) [声称](https://x.com/RoundtableSpace/status/2061066574694695250)（150 个赞、17 条回复、55,244 次浏览、41 次收藏）称 Claude Code 能识别复杂任务、编写编排逻辑，并自动拉起一个 Agent swarm。回复则把这场演示提炼成了一份检查清单：可见的计划、隔离的工作流、验证机制、失败证据，以及成本可见性。

**讨论洞察：**“Harness 工程”不再只是专家之间的标签，而开始发挥实用的采购和设计检查清单作用。

**与前一天相比：** 5 月 28 日为 harness 工程奠定了公开的基本范式；到 5 月 31 日，它已经成了严肃 Agent 工作的默认架构语言。

### 1.2 默认技能膨胀和上下文开销，成了最主要的优化战场 🡕

最激烈的实际争论，并不是 Agent 是否需要技能，而是默认应该启用多少技能，以及这些技能每一轮会消耗多少注意力。共有三条入选内容支撑这一主题。

[@theo](https://x.com/theo) [抱怨](https://x.com/theo/status/2061019720552525963)（597 个赞、107 条回复、68,779 次浏览、204 次收藏）称 Hermes Agent 预先启用了 100 多项技能，其中很多与他的工作无关。他在澄清回复中表示，问题不只是菜单过于拥挤，还有一些技能已经在不该触发的地方触发了。

![Hermes 技能选择界面，显示了一长串默认启用的技能，横跨多个互不相关的类别，例如 Apple Notes、图像生成、GitHub 审查和 Minecraft 托管](https://pbs.twimg.com/media/HJo145bbYAA-PWd.png)

[@steipete](https://x.com/steipete) [反驳](https://x.com/steipete/status/2061072753998856696)（139 个赞、23 条回复、18,939 次浏览）认为 OpenClaw 应保持模块化和精简：只添加真正需要的内容。信息量最大的回复指出，更短的工具列表不仅更快，也更准确，因为它能减少错误选用工具、决策噪声和权限风险。

[@RoundtableSpace](https://x.com/RoundtableSpace) [认为](https://x.com/RoundtableSpace/status/2061081512477364318)（71 个赞、14 条回复、46,561 次浏览、37 次收藏）称，换用另一套技能与 CLI 组合后，Claude Code 的 token 用量从 1,040 万降至 370 万，错误数也从 10 次降为 0 次。回复随即要求拿出更有力的证据：相同任务、相同验收测试、相同推理负载。

**讨论洞察：**当天的优化目标不是“让 Agent 更强大”，而是“让默认能力面更小、更便宜、更容易检查”。

**与前一天相比：** 5 月 28 日仍把技能系统视为持续扩张的资产；到 5 月 31 日，讨论重点更像是裁剪、路由和范围控制。

### 1.3 构建者持续推出编排栈，但信任建立在可检查性之上 🡕

新项目不断出现，但只有在编排之外还能提供可审查性、轨迹归属或实时监督时，它们才真正显得有说服力。共有四条入选内容支撑这一主题。

[@tom_doerr](https://x.com/tom_doerr) [分享](https://x.com/tom_doerr/status/2061105709110940117)（123 个赞、5 条回复、6,101 次浏览、129 次收藏）介绍了 EpicStaff——一个面向运营团队的自托管编排平台。公开 [仓库](https://github.com/EpicStaff/EpicStaff) 表示，它是一个基于 Django 的可视化编辑器，支持 MCP/Python 集成，并通过 Redis/PostgreSQL 提供持久化上下文；而回复则认为，自托管仍然需要逐操作审批日志，以及良好的事后复盘可见性。

[@tom_doerr](https://x.com/tom_doerr) [还分享了](https://x.com/tom_doerr/status/2061070572344221880)（20 个赞、1,491 次浏览、25 次收藏）介绍了 Spring AI Alibaba 的 DeepResearch 栈。公开 [仓库](https://github.com/spring-ai-alibaba/deepresearch) 将其描述为一个具备多 Agent 规划、在线搜索、Hybrid RAG、反思、HITL、安全沙箱和报告生成能力的系统。

![DeepResearch 架构图，展示了一个多智能体研究系统中的编排、推理、记忆、工具和输出层](https://pbs.twimg.com/media/HJpkw4YX0AE2SNG.png)

[@eliautobot](https://x.com/eliautobot) [发布了](https://x.com/eliautobot/status/2061181114186600870)（9 个赞、1,720 次浏览、15 次收藏）介绍了一个面向 OpenClaw 的自托管“虚拟办公室”。公开 [仓库](https://github.com/eliautobot/my-virtual-office) 把 Agent 活动呈现为一个复古像素风办公室，提供实时状态、活动日志和 API 使用情况视图，让人们能看见 Agent 在做什么，而不是只能盯着日志。

[@ClementDelangue](https://x.com/ClementDelangue) [询问](https://x.com/ClementDelangue/status/2061196949101932899)（51 个赞、10 条回复、4,817 次浏览）呼吁提供更多公开的编码和 Agent 轨迹，以改进开放模型。引用的 Simon Willison 对 Codex 丢失会话导出功能的抱怨，以及关于受监管生产数据的回复，都让缺失的治理层变得显而易见：即使轨迹存在，运营方也未必拥有控制权，或有能力分享这些轨迹。

**讨论洞察：**仅有自托管和多 Agent 编排还不够。缺失的那一层是可检查性：审批日志、轨迹导出、可视化监督，以及兼顾隐私的数据集。

**与前一天相比：** 5 月 28 日强调的是持久化 Agent 的共享状态和连续性；到 5 月 31 日，讨论中新增了面向运营团队的具体产品和可视化监督，同时也暴露出轨迹归属仍是未解瓶颈。

## 2. 什么让人感到沮丧

### 默认技能包会制造噪声、错误选用工具和权限风险

严重程度：高。[@theo](https://x.com/theo) [展示了](https://x.com/theo/status/2061019720552525963)（597 个赞、107 条回复、68,779 次浏览、204 次收藏）展示了一个预先启用 100 多项技能的 Hermes 配置，并称其中一些技能已经在不该触发的地方触发了。[@steipete](https://x.com/steipete) [回答](https://x.com/steipete/status/2061072753998856696)（139 个赞、23 条回复、18,939 次浏览）认为精简、按需启用的能力面效果更好；回复也解释了原因：预先启用的技能会增加模型每轮都必须读取的上下文，从而放大决策噪声和权限风险。人们目前的应对方式包括禁用技能、选择更模块化的框架，或从零重建自己的工具面。这值得投入，因为这种痛点既立刻可感，也能通过错误数和操作员信任度直接衡量。

### 关于 token 和错误节省的说法，需要比演示式话术更强的证据

严重程度：中高。[@RoundtableSpace](https://x.com/RoundtableSpace) [声称](https://x.com/RoundtableSpace/status/2061081512477364318)（71 个赞、14 条回复、46,561 次浏览、37 次收藏）声称在更换上下文配置后，token 用量减少了约 3 倍，错误也下降了，但最靠前的回复追问，这种比较是否基于相同任务和相同验收测试。另一条回复则称，自己曾在一次错误循环里烧掉 400,000 个 token。信息流并不是在否定优化宣称，而是在要求它们可复现。这值得投入，因为团队越来越把上下文工程视为预算管理，也希望看到经得起重复运行的证据，而不只是截图。

### 有价值的 Agent 轨迹难以导出、拥有或分享

严重程度：高。[@ClementDelangue](https://x.com/ClementDelangue) [称其为](https://x.com/ClementDelangue/status/2061196949101932899)（51 个赞、10 条回复、4,817 次浏览）呼吁提供更多公开轨迹，但讨论很快撞上两个障碍：受监管的生产数据无法自由分享，而产品也可能在毫无预警的情况下取消会话导出功能。引用的 Simon Willison 对 Codex 丢失“Copy as Markdown”功能的抱怨，让所有权问题变得具体。人们目前只能依靠选择性贡献、临时导出，或在自己仍有控制权时分享手头能分享的仓库。这值得投入，因为轨迹数据同时是模型改进资产、审计凭证，也是平台锁定的载体。

### 仅靠自托管，并不能解决运营团队的信任问题

严重程度：中高。[@tom_doerr](https://x.com/tom_doerr) [推广了](https://x.com/tom_doerr/status/2061105709110940117)（123 个赞、5 条回复、6,101 次浏览、129 次收藏）介绍了一个面向运营团队的自托管编排方案，但回复立刻追问：出错之后谁来检查残局？每一步操作是否都能复核？目前可见的应对办法包括人工审批、外部日志，或干脆选择证据链更清晰的简单系统。这值得投入，因为运营买家关心的是出问题之后到底发生了什么，而不只是二进制跑在哪里。

## 3. 人们希望出现什么

### 精简、按需启用的技能面

最强烈的产品诉求并不是“给我更多技能”，而是“从小做起，只让我添加真正对应我工作的技能”。Theo 对 Hermes 的抱怨和 Steipete 对 OpenClaw 的回复，一起把这个愿望说得很明确。机会：直接。用户已经在手动裁剪能力面，以获得自己想要的行为。

### 可检查的编排

在 Dynamic Workflows 和 EpicStaff 的回复中，可见的计划、隔离的工作流、失败证据、逐操作审批和成本报告一再出现。人们要的不是只会产出惊艳结果的 Agent，而是会留下清晰纸面记录的 Agent。机会：直接。这是生产环境使用中的现实要求。

### 兼顾隐私的轨迹导出与数据集贡献

这场轨迹分享讨论清楚表明，人们希望贡献数据，但又不想放弃客户隐私或产品控制权。现有的 Hugging Face 轨迹集合只是起点，但信息流显示，对于受监管场景或被供应商锁定的场景，目前还没有被广泛采用的答案。机会：竞争性。需求很明确，但解决空间同时受隐私、合规和平台问题挤压。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| Hermes Agent | Agent 框架 | (+/-) | 开箱即带大量能力和自动生成的技能 | 默认能力面过宽，用户反映会错误触发工具，并带来过多菜单/上下文噪声 |
| OpenClaw | Agent 框架 | (+) | 模块化、精简，易于按任务定制 | 相比“全部启用”的打包方案，需要更有意识地配置 |
| Harness engineering patterns | 方法 | (+) | 为提示词、技能、文件系统、编排、钩子和沙箱提供了一套共同语言 | 如果不与可观测的计划、日志和失败证据结合，就可能停留在抽象层面 |
| EpicStaff | 编排平台 | (+/-) | 自托管可视化编辑器、Django 后端、持久化上下文、MCP/Python 集成 | 自托管本身并不能回答逐操作审查和审批需求 |
| DeepResearch | 研究 Agent 栈 | (+) | 多 Agent 规划、搜索、Hybrid RAG、反思、HITL、安全沙箱、报告生成 | 早期公开热度低于更高层的 harness 讨论 |
| My Virtual Office | 可观测性层 | (+) | 把不可见的 Agent 工作转化为实时状态、活动和 API 使用情况视图 | 仍处早期且偏小众，目前讨论量不高 |

总体情绪更偏向那些能减少不确定性的工具：明确 Agent 能做什么、实际做了什么，以及成本是多少。迁移压力正从宽泛的默认技能包，转向更精简、更易检查的配置。最大且尚未解决的缺口，并不是再加一个框架功能，而是操作员对证据链和轨迹的所有权。

## 5. 人们正在构建什么

| 项目 | 构建者 | 功能 | 解决的问题 | 技术栈 | 阶段 | 链接 |
|---|---|---|---|---|---|---|
| EpicStaff | EpicStaff | 面向运营团队的自托管可视化 AI 流程平台 | 运营团队需要可审查的 Agent 工作流，而不必把一切都交给工程师或不透明的 SaaS | Django 后端、Python 逻辑、MCP 集成、Redis/PostgreSQL 持久化 | Beta | [仓库](https://github.com/EpicStaff/EpicStaff) |
| DeepResearch | Spring AI Alibaba | 能规划、搜索、推理并生成报告的多 Agent 研究系统 | 复杂研究/报告任务需要在同一栈内整合编排、检索、反思和沙箱分析 | Java 17、Spring Boot 3.4、Spring AI、Hybrid RAG、Docker 沙箱、Tavily/Jina/Aliyun 搜索 | Beta | [仓库](https://github.com/spring-ai-alibaba/deepresearch) |
| My Virtual Office | eliautobot | 以复古像素风浏览器工作区实时可视化 OpenClaw Agent 活动 | 当 Agent 工作只表现为日志和终端输出时，很难进行监督 | 自托管浏览器 UI、OpenClaw 集成、实时状态/活动/API 视图 | Beta | [仓库](https://github.com/eliautobot/my-virtual-office) |

EpicStaff 最突出的地方在于，它直接面向运营团队，而不只是 AI 工程师。最重要的反馈是：一旦 Agent 触及运营场景，自托管只是基本门槛，买家仍然希望具备逐操作审批，以及出错后可回查的工作流。

DeepResearch 之所以突出，是因为它把讨论中反复被分开提及的许多 harness 组件打包到了一起：搜索、记忆、反思、安全执行和报告输出。那张架构图让整套技术栈变得一目了然，是文字本身难以做到的。

My Virtual Office 虽然体量较小，却揭示了一个值得关注的模式：随着 Agent 普及，一些构建者开始用更符合人类直觉的隐喻来解决可观测性问题，而不是继续堆叠更多仪表板和原始日志。

## 8. 要点

1. **Harness 工程如今已成为严肃 Agent 工作的共同系统语言。** LangChain 的文章、Pallavi Shekhar 的图谱和 Dynamic Workflow 的讨论，都把提示词、工具、记忆、编排和钩子视为同一个设计面。（[来源](https://x.com/byanujpatel/status/2060967710008508607)）
2. **社区正在反击臃肿的默认技能面。** Theo 展示的 Hermes 截图和 Steipete 对 OpenClaw 的回应，把“更少的工具”变成了具体的可靠性论据，而不只是风格偏好。（[来源](https://x.com/theo/status/2061019720552525963)）
3. **只有在展示工作如何被审查时，新的 Agent 产品才显得可信。** EpicStaff、DeepResearch 和 My Virtual Office 之所以受到关注，是因为它们分别承诺了可视化流程、架构清晰度或实时监督的某种组合。（[来源](https://x.com/tom_doerr/status/2061105709110940117)）
4. **轨迹所有权正变得和模型质量同样重要。** 对公开轨迹的需求立刻撞上隐私限制和导出功能消失的问题，说明数据访问如今已是核心的产品与治理议题。（[来源](https://x.com/ClementDelangue/status/2061196949101932899)）
