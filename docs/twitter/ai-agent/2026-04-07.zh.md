# Twitter AI Agent - 2026-04-07

## 1. 人们在讨论什么

### 1.1 Harness Engineering 走向主流（🡕）

4 月 7 日，AI Agent 讨论中最占主导地位的概念是 “harness engineering”。导火索是一档具有里程碑意义的 Latent Space 播客：节目披露，OpenAI 的 Frontier 团队正用一个超过 1M+ LOC 的代码库开展工作，其中没有人类编写的代码，也没有任何代码在合并前经过人工审查；系统每天消耗超过 1 billion tokens。

[@latentspacepod](https://x.com/latentspacepod) 发布了对 OpenAI 的 Ryan Lopopolo 的采访，详细介绍了 “Dark Factory”——一个由 50+ 个 Codex agents 并行处理、名为 Symphony 的代码库。它被形容为一个没有任何人类代码的“幽灵库”。Lopopolo 表示，如果团队每天没有使用 1B+ tokens、token 开销大约只有 $2-3K/day，那几乎可以说是“失职”（[帖子](https://x.com/latentspacepod/status/2041567210871959672)）。

![Latent Space 关于 Extreme Harness Engineering 的文章，展示了 OpenAI 提出的每天 10 亿 tokens 的 Dark Factory 概念](https://pbs.twimg.com/media/HFUahnLXcAAM_gT.jpg)

[@IntuitMachine](https://x.com/IntuitMachine) 发布了一套详细的 L1-L6 成熟度模型，将四个 AI 学科——Prompt Engineering、Context Engineering、Harness Engineering 和 Intent Engineering——映射到组织成熟度的不同阶段，且每一层都建立在前一层之上。图中显示，L4（Harness Engineering）是“改变 harness 会显著改变性能”的阶段（[帖子](https://x.com/IntuitMachine/status/2041503368695185720)）。

![L1-L6 AI 成熟度模型，将 Prompt、Context、Harness 到 Intent Engineering 进行映射，并展示内容阶段的演进](https://pbs.twimg.com/media/HFTgey-agAAKLvz.jpg)

[@DSPyOSS](https://x.com/DSPyOSS) 对术语不断翻新的现象进行了讽刺点评：“2022: prompt tricks!! 2023: prompt engineering!! 2024: agentic workflows! 2025: context engineering!! 2026: harness engineering!!! us: .. DSPy.” 一条来自 @tedhall23 的回复则提出了一个很实在的问题：对真正的公司而言，“确定性的 AI 工作流，和完全 agentic、会调用工具的行为”之间该如何取舍（[帖子](https://x.com/DSPyOSS/status/2041635988955377669)）。

[@caspar_br](https://x.com/caspar_br) 提炼出了实操层面的要点：“你可以从三个层面改进 agent：model、harness 和 context。大多数团队都盯着 model。但 context（skills、instructions）才是你迭代速度最快的层”（[帖子](https://x.com/caspar_br/status/2041593056236073105)）。

[@victor_explore](https://x.com/victor_explore) 将 Claude Code 源码泄露与 harness engineering 联系起来，认为“Agent Harness 才是真正的产品”，并称从 “vibe coding” 转向 harness engineering，是“工程师在 2026 年能做出的最有价值的转变”（[帖子](https://x.com/victor_explore/status/2041337229038215532)）。

**Discussion insight:** @MindTheGapMTG 进一步推进了这一观点：“如果模型表现出‘未说出口的战略性思考’，那你的约束层就是你与一个正在为非预期目标优化的系统之间唯一的隔离带。正因如此，我们会在每条 agent pipeline 上都运行 CLAUDE.md 治理文件。” 这说明，harness engineering 关乎的不只是性能，也关乎安全。

### 1.2 Agent 安全警钟拉响（🡕）

多条高互动帖子都在紧急警告 agent 安全问题，并给出了具体证据：市场中的恶意软件、迟迟未修复的漏洞，以及权限范围过大的问题。

[@JamesonCamp](https://x.com/JamesonCamp) 发出了一则尖锐警告：“OpenClaw 的 marketplace 里有 12% 根本就是恶意软件。键盘记录器。身份盗窃。你的 AI agent 就在那个 Gmail 里——而你妻子曾在里面给你发过孩子的 SSN。” 他还分享了自己遭遇 $55K Amex 欺诈的经历，并指出，agent 与“你的整个人生之间，没有任何人挡在中间”（[帖子](https://x.com/JamesonCamp/status/2041533186195574960)）。

**Discussion insight:** @usmaanbuildsAI 给出了可执行的建议：“在把任何 agent 接到个人工具之前，至少应该做到沙箱隔离、限定范围的 OAuth tokens，以及独立的服务账号。” @TrevorLongino 则提到，一项安全扫描服务可以作为部分解决方案。

[@DeryaTR_](https://x.com/DeryaTR_) 对 Claude Cowork 中一个尚未修复的文件外传漏洞表示担忧，并引用 Garry Tan 的话称：“攻击者可以利用一个尚未修复的漏洞，从 Cowork 中外传用户文件。” 这一漏洞最初由研究员 Johann Rehberger 发现，Anthropic 已确认问题存在，但尚未修复（[帖子](https://x.com/DeryaTR_/status/2041559218109427749)）。

[@AethirCloud](https://x.com/AethirCloud) 在一条长帖中梳理了更广泛的 OpenClaw 安全态势：“1,000+ 个恶意 skills、严重的 RCE 漏洞，以及 135K+ 个暴露实例。” 他们认为，共享 VPS 托管意味着“你的托管服务商仍保留完整管理员权限。你的 API keys、对话和 agent 行为，在基础设施层都是可见的”（[帖子](https://x.com/AethirCloud/status/2041492125775175695)）。

[@alex_prompter](https://x.com/alex_prompter) 点出了这一系统性问题：“18 个月前我们还在说 ‘AI 什么有用的事都做不了’，现在已经变成 ‘AI 对我的 Gmail、Slack 和 Salesforce 拥有完全访问权’。正常企业软件必须经过的每一道安全检查，我们全都跳过了”（[帖子](https://x.com/alex_prompter/status/2041542927801836006)）。

[@koylanai](https://x.com/koylanai) 分享了一个来自一线实践者的警示案例：在构建一个用 bash 脚本管理 git branches 的多 agent harness 时，“清理脚本在 repo 根目录执行了 git checkout -- .，结果把所有已跟踪文件的改动全都回滚了。” 教训是：“你的 agent system 越强大，你就越必须赋予它更大的权限。” Simon Willison 一篇文章中的两张图片进一步强化了最佳实践：自动化测试、版本控制纪律和人工 QA 会随着模型变强而“变得更重要，而不是更不重要”（[帖子](https://x.com/koylanai/status/2041526628468019621)）。

![Simon Willison 的文章，介绍了与 coding agents 协作所需的技能：自动化测试、规划、文档、版本控制和代码审查](https://pbs.twimg.com/media/HFTyWDjWsAAdBi4.jpg)

### 1.5 Skills 研究：一次现实检验（🡕）

一篇重要研究论文挑战了“agent skills 能稳定提升性能”这一假设，而实践者的反馈也印证了这一发现。

[@dair_ai](https://x.com/dair_ai) 强调了一篇来自 UC Santa Barbara 和 MIT 的论文：“How Well Do Agentic Skills Work in the Wild.” 该研究在逐步贴近真实世界的条件下测试了 34K 个真实技能，发现“随着条件变得更真实，性能增益会持续衰减，通过率会逐渐逼近无 skill 的基线水平。” 针对查询的 skill refinement 能部分恢复丢失的性能，将 Claude Opus 4.6 在 Terminal-Bench 2.0 上的通过率从 57.7% 提高到 65.5%。代码见 [github.com/UCSB-NLP-Chang/Skill-Usage](https://github.com/UCSB-NLP-Chang/Skill-Usage)（[帖子](https://x.com/dair_ai/status/2041540525539614797)）。

![研究论文摘要：How Well Do Agentic Skills Work in the Wild，显示研究发现技能带来的收益在更真实的环境中会下降](https://pbs.twimg.com/media/HFUCSdwbwAArTFu.jpg)

**Discussion insight:** @d_ai_1231 也给出了印证：“在 demo 里，agents 看起来像是‘已经完成’了，因为它们被喂了正确的 skills。但在真实使用中，它们常常会选错，于是底层一切都会崩掉。问题不在能力，而在选择。”

[@AlemTuzlak](https://x.com/AlemTuzlak) 提供了一个具体例子：“我今天试着让一个 agent 用 @tan_stack AI 做点真正酷的东西，结果……很糟。它以为自己用的是 Vercel AI SDK，还试图导入根本不存在的 APIs。” 他的解决方案是构建 TanStack AI skills 来填补这个缺口（[帖子](https://x.com/AlemTuzlak/status/2041581542179271112)）。

[@DerekNee](https://x.com/DerekNee) 提出了一个更广泛的问题：“we get a new agent framework every 12 hours but almost no one is building evals that keep up. a lot of this is vibe coded. how do we even know what's good?”（[帖子](https://x.com/DerekNee/status/2041525464045658587)）。

### 1.6 Memory Engineering 成为一门学科（🡕）

多条帖子都把 agent memory 视为一门独立的工程学科，并给出了架构图、神经科学类比和具体实现建议。

[@ConorBronsdon](https://x.com/ConorBronsdon) 分享了 Richmond（Oracle）提出的一套详细记忆架构分类：Memory Core 负责处理五类数据（vectors、graph、relational、spatial、JSON）；Memory Manager 负责统筹 retrieval、indexing、storage 和 decay；而 Context Window 则通过 token budget 决定模型实际能看到什么。核心洞见是：“不要删除，要遗忘。信息应该通过相关性评分和重要性加权来衰减，而不是硬删除。” 他还引用了一项醒目的数据：“78% of enterprises have AI agent pilots. Only ~14% have scaled one to production”（[帖子](https://x.com/ConorBronsdon/status/2041527667711971721)）。

![记忆工程架构：Memory Core 包含 5 种数据类型，Memory Manager 负责 retrieval/indexing/decay，Context Window 组合后输入 LLM](https://pbs.twimg.com/media/HFSHcmQaIAADlQd.jpg)

[@Mr_memsy](https://x.com/Mr_memsy) 分享了实操建议：“在 OpenClaw 中打开 /dreaming，再加上 temporal decay + embedding cache，你的 agent 就会开始积累知识，而不是对过时上下文产生幻觉。” 他还向构建者们提问如何处理长期记忆，由此引发了围绕 RAG、vector DBs 和自定义 reflection loops 的讨论（[帖子](https://x.com/Mr_memsy/status/2041582460526379362)）。

## 2. 什么让人沮丧

### Agent 权限与授权管理（高）

最尖锐的挫败感在于，agents 正在积累广泛权限，但缺乏足够的安全检查点。@alex_prompter 指出，整个行业“跳过了正常企业软件必须通过的每一道安全检查”。@JamesonCamp 关于 marketplace 中 12% 恶意软件、以及个人损失 $55K 的欺诈经历，说明了这种问题带来的现实后果。@koylanai 的经历也表明，即便是出于善意授予的 agent 权限，一旦作用范围超出操作者可追踪的边界，也会造成破坏：一个清理脚本抹掉了整个会话的工作成果。

### 技能选择与可靠性（高）

UC Santa Barbara/MIT 的研究显示，随着条件越来越接近真实世界，agent skills 的收益会持续衰减。@AlemTuzlak 的具体经历——agent 假定自己在用错误的 SDK，并导入根本不存在的 APIs——说明这不是理论问题。@DerekNee 抓住了更大的挫败点：“we get a new agent framework every 12 hours but almost no one is building evals.” 构建者无法判断什么真正有效，因为评估基础设施并没有跟上 framework 爆炸式增长的速度。

### Agent 记忆丢失（中）

@Mr_memsy 指出，“Default setups forget fast”，而 @ConorBronsdon 则引用了只有 14% 的企业 agent 试点能进入生产环境这一数据，并认为记忆架构是关键缺口之一。agents 如果无法跨会话保留上下文，就会制造重复劳动并削弱用户信任。

### 供应商锁定与订阅变更（中）

@Shaughnessy119 对 Anthropic 缩减 Claude 订阅中第三方工具覆盖范围的做法作出反应：“This is just mass deplatforming those using agents with centralized AI APIs.” 随后他迁移到了 Hermes Agent + Together.AI + 开源模型。这种被迫迁移会让那些已经围绕某一平台工作流投入大量精力的构建者感到沮丧。

### 模型对指令的遵循（中）

@gus_aragon 发现，Opus 4.6 会在它判断为简单的任务上选择性跳过 agent instructions：“No review. No security audit. No artifacts. It decides the process isn't worth it.” 指令放在哪里，比措辞本身更重要；而想要真正强制执行，还需要模型无法自行修改的基础设施（例如 git hooks）。

## 3. 人们希望出现什么

### Agent 治理基础设施（高）

@theboundlessvc 直接提出了这个问题：“when millions of agents are transacting on the web autonomously, who governs them? what permissions exist? what data can they touch? how do you audit what they did?” 信任层、协调层和合规层“none of it exists at the scale we need”。这是一个已经被明确点名、但当下仍无现成解法的缺口。机会：直接。

### 可靠的技能发现与检索（高）

UCSB/MIT 的研究表明，agents 很难从大型 skill 集合中选出相关技能。@dair_ai 指出，针对查询的 refinement 可以部分恢复损失的性能，但目前还没有可用于生产的方案。构建者需要的是一个能在大规模场景下工作的技能搜索层。机会：直接。

### 带合理衰减机制的跨会话 Agent 记忆（中）

@ConorBronsdon 的分类法显示，这套架构在理论上已经存在——相关性评分、重要性加权，以及“不要删除，要遗忘”——但还没有开箱即用的实现方案。@Mr_memsy 的变通做法（temporal decay + embedding cache）仍需手动搭建。机会：直接。

### 面向技能市场的 Agent 安全扫描（高）

既然 OpenClaw marketplace 中有 12% 被标记为恶意软件，而且已识别出 1000+ 个恶意 skills，构建者就需要在安装技能前先做自动安全扫描。@TrevorLongino 提到过一项扫描服务，但问题规模远远超出当前解决方案的覆盖范围。机会：直接。

### 标准化的 Agent 评估框架（中）

@DerekNee 对 “a lot of this is vibe coded” 的不满，反映出一个明确缺口：目前还没有标准化的 agent evaluation framework 来比较不同 agent frameworks。UCSB/MIT 的论文提供了一种路径，但采用仍处于早期。机会：竞争型。

## 6. 新动态与值得关注的内容

### OpenAI 的 Dark Factory：零人工代码，零人工审查
Ryan Lopopolo 对 OpenAI Frontier 的 Symphony 系统所作的详细介绍，是目前公开案例中最极端的 agent-only 开发样本：一个团队正在交付生产软件，代码库规模达 1M+ LOC，没有任何人类编写的代码，也没有任何代码在合并前经过人工审查。关键洞见在于：当 agent 失败时，这个团队不会去想“怎样把 prompt 写得更好”，而是会追问“缺了什么能力、上下文或结构？”——这正是 harness engineering 的实践（[来源](https://latent.space/p/harness-eng)）。

### GitHub 为 Copilot CLI 推出 Rubber Duck Agent
[@burkeholland](https://x.com/burkeholland) 报道称，GitHub Research 发布了一个 “Rubber Duck” agent，可自动让另一个 AI 家族的模型给出审查意见。他们的数据表明，跨模型审查能够带来可量化的质量提升（[帖子](https://x.com/burkeholland/status/2041640366189748339)）。

### 面向 Agent Swarms 的 Amazon S3 Files
[@skeptrune](https://x.com/skeptrune) 强调了 Amazon S3 Files——首个支持完整 POSIX 文件系统访问的云对象存储——可能成为 agent 基础设施的游戏规则改变者：“你不再需要启动一个 sandbox vm 来给 agents 提供 POSIX 工具访问。现在你可以把任意规模的算力指向 s3，在同一个文件系统上运行大规模并行的 agent swarms”（[帖子](https://x.com/skeptrune/status/2041657917708103915)）。

### 作为私有 Agent 基础设施的 Gemma 4
[@RoundtableSpace](https://x.com/RoundtableSpace) 指出，Google 发布的 Gemma 4 具备本地多模态推理、function calling 和 OpenClaw 兼容性，可能会“让替代订阅制 AI 变得现实得多”（[帖子](https://x.com/RoundtableSpace/status/2041640913496080553)）。

### Southwest Airlines 部署 GitLab Duo Agent Platform
[@bjmtweets](https://x.com/bjmtweets) 报道称，Southwest Airlines 已在 3,000+ 名工程师中采用 GitLab Duo Agent Platform，目标包括让 pipeline 组件升级实现 90% 自动化、自动修复 CVE，并用 agents 让“技术债成为过去”（[帖子](https://x.com/bjmtweets/status/2041649180826071224)）。

## 7. 机会在哪里

**[+++] Agent 安全与治理基础设施** —— 12% 的 marketplace 恶意软件、1000+ 个恶意 skills、主流平台中尚未修复的漏洞，以及面向自主 agent 交易几乎为零的治理基础设施。@theboundlessvc 将其称为“一个大多数人还没命名的类别”。第 1.2、2 和 3 节中的多条讨论都证明了这类需求的紧迫性。agent 能力与安全基础设施之间的鸿沟仍在扩大。

**[+++] 技能发现与质量保障** —— 研究已经证明，skills 在更真实的环境中收益会下降。当前没有任何可用于生产的方案，能帮助 agents 从大型技能集合中查找、评估并适配技能。UCSB/MIT 论文提出的 query-specific refinement 提供了一个起点。再叠加 marketplace 恶意软件问题，一个具备安全意识的技能发现层将产生复合价值。

**[++] Memory engineering 工具** —— 只有 14% 的企业 agent 试点进入了生产环境，而记忆架构是首要瓶颈之一。相关架构（5 类数据、衰减逻辑、跨会话保留）已经定义清楚，但还没有开箱即用的实现。先发优势仍在。

**[++] 面向受监管行业的 voice agent 基础设施** —— LiveKit 在发音上的工作已经指明了路径：医疗、法律和金融领域的专业 voice agents 需要音标控制、合规认证和低于 100ms 的延迟。Chatbase 和 Grok 正在通用 voice 场景竞争，但受监管的垂直行业仍供给不足。

**[+] 面向欠服务语言的本地化 skills** —— Hurmoz 已经证明，单个开发者借助 Claude Code 就能搭建出一整个语言生态（63 个 skills、5 种方言、20 个 government APIs）。在此之前，阿拉伯语的 agent skills 为零。还有数十种语言和地区存在同样的空白。

**[+] Agent-native 支付轨道** —— Grok CLI 的 Coinbase 集成和 ClawPlaza 的 USDC economy 只是早期信号。随着 agents 成为经济行为主体，能够处理自主交易中的安全、审计与合规问题的支付基础设施将成为刚需。

## 8. 要点总结

1. **Harness engineering 已成为严肃 agent 开发的主导范式。** OpenAI 的 Frontier 团队正在操作一个 1M+ LOC 的系统，没有人工代码，也没有人工审查，每天消耗 1B+ tokens。社区共识正从“改进模型”转向“改进 harness”。（[来源](https://x.com/latentspacepod/status/2041567210871959672)）

2. **Agent 安全正处于危机之中。** OpenClaw marketplace 中有 12% 被标记为恶意软件，Claude 的一个重大漏洞仍未修复，而整个行业跳过了正常企业软件必须经历的每一道安全检查。针对自主 agent 交易的治理基础设施几乎不存在。（[来源](https://x.com/JamesonCamp/status/2041533186195574960)）

3. **Agent skills 在真实条件下会退化。** UC Santa Barbara/MIT 基于 34K 个真实技能的研究显示，当 agents 必须自行发现技能时，性能会下滑到接近基线的水平。query-specific refinement 能部分恢复损失的性能。（[来源](https://x.com/dair_ai/status/2041540525539614797)）

4. **Voice agents 正以差异化定价和专业化能力进入生产环境。** Chatbase 推出了全渠道 voice，LiveKit 以 100ms TTFB 解决了医疗术语发音问题，而 Grok 则将价格压到 $0.05/minute。（[来源](https://x.com/livekit/status/2041586877497508305)）

5. **Memory engineering 正在成为一门独立学科。** 其架构已被清晰描绘出来（5 类数据、衰减逻辑、跨会话保留），但只有 14% 的企业 agent 试点真正进入生产环境——记忆仍是关键瓶颈。“不要删除，要遗忘”是核心设计原则。（[来源](https://x.com/ConorBronsdon/status/2041527667711971721)）

6. **Agent marketplaces 已经开始产生真实收入。** ClawPlaza 报告 90 天平台收入达 $326K，AI-Trader 拥有 12K+ stars 并支持真实交易，多个平台也推出了按次调用计费的 skill 变现模式。agent economy 已不再只是理论。（[来源](https://x.com/acedatacloud/status/2041574339502281174)）

7. **本地化是一个广阔的机会窗口。** 一名开发者构建了 63 个阿拉伯语 skills，覆盖 5 种方言和 20 个沙特 APIs——这是任何 agent 平台上的第一套阿拉伯语 skills。还有数十种语言目前没有任何 agent skill 覆盖。（[来源](https://x.com/Mosescreates/status/2041334007212749040)）
