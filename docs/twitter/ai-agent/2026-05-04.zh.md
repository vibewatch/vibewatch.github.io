## 1. 人们在讨论什么

### 1.1 Harness 工程走向成熟：自研还是采购，分歧更清晰了 🡒

关于 harness 工程的争论延续了 5 月 3 日的话题，但焦点已从“该不该自己做？”转向更实际的实现模式。[@_colemurray](https://x.com/_colemurray) [明确提出了反对构建的立场](https://x.com/_colemurray/status/2051045148252143669)（51 次点赞，50 次收藏）：“你们不太可能在子代理编排、压缩、渐进式披露等方面提出值得为此独自拥有整套 harness 的新想法。把时间投入到 harness 周边更有价值的部分：执行基础设施、自定义工具/MCP/技能，以及基于轨迹的自我改进。”

[@nichochar](https://x.com/nichochar) 直接反驳：“不同意。harness 在功能上其实很简单，但因为我们会把工作委托给它们，所以必须深入理解。所有构建者都应该熟悉自己工具的工作方式，而在 2026 年，亲自维护一个 harness 是做到这一点的最佳方式。” [@skastr052](https://x.com/skastr052) 则补充了更细致的看法：“模型与 harness 的耦合很可能会越来越强——例如，最近代码里的 /goal 命令，实际上只有和 codex 及其压缩后端配套时才真正可用。”

与此同时，Agentic Harness Engineering（AHE）论文借由 [@DataScienceDojo](https://x.com/DataScienceDojo) [报道](https://x.com/DataScienceDojo/status/2051421617087992291)（23 次浏览）获得关注：这是一个闭环系统，能够在不改动基础模型的情况下，自动演化编码代理周边的全部脚手架。关键结果是：经过 10 次迭代，Terminal-Bench 2 上的 pass@1 从 69.7% 提升到 77.0%，同时在 SWE-bench-verified 上 token 使用量减少了 12%。

[@MrAhmadAwais](https://x.com/MrAhmadAwais) [体现了内部自建的倾向](https://x.com/MrAhmadAwais/status/2051091268990808107)（14 次点赞）配了一段梗图视频：“‘我们可以内部自建一个编码代理 harness。’” [@dexhorthy](https://x.com/dexhorthy) [依然保持其反对立场](https://x.com/dexhorthy/status/2050931243181576669)（70 次点赞）：“嘿 Nikita，我真的很想再看点 AI 写的 harness 工程炒作废话，你能帮帮我吗？”

**与前一天对比：** 5 月 3 日的讨论从概念定义转向了战略层面的自研/采购决策。到 5 月 4 日，分歧进一步加深——如今，AHE 论文已拿出正式研究结果，为“自动化 harness 演化”阵营提供了支撑；而像 @nichochar 这样的实践者，则继续坚持“通过亲手构建来理解”。来自 @dexhorthy 的反炒作疲劳情绪仍在持续，形成稳定的制衡力量。

### 1.2 上下文工程开始形成结构化词汇 🡕

关于上下文工程的讨论，已经从泛泛倡导进入技术细节层面。[@_overment](https://x.com/_overment) [发布了详细解析](https://x.com/_overment/status/2051000796515308030)（7 次收藏）展示了多代理提示架构，并指出若干未解问题：“设置变化时，如何保留上下文缓存？除了压缩之外，如何保住重要上下文？当结果超出可用上下文窗口时，应该如何呈现给模型？”

![多智能体提示词架构图，展示缓存前缀结构、运行时说明、目录和缓存断点](https://pbs.twimg.com/media/HHac-q9W4AAVB4k.jpg)

[@avrldotdev](https://x.com/avrldotdev) [强调了](https://x.com/avrldotdev/status/2051345021593637194)（8 次收藏）分享了一篇深入讨论压缩的长文，涵盖 7 种理念及其优缺点。[@petergyang](https://x.com/petergyang) [分享了](https://x.com/petergyang/status/2051306157810282994)（9 次收藏）分享了一份免费的《原型开发的上下文工程工作手册》。[@NalyMetaX](https://x.com/NalyMetaX) [阐释了这一更广泛的转变](https://x.com/NalyMetaX/status/2051200080666059106)（56 次点赞）：“市场痴迷于提示词工程，但提示词不过是上下文缺失时贴上的创可贴。”

[@DanIsBuilding](https://x.com/DanIsBuilding) 在回复 @_overment 时抓住了这个转折点：“我个人认为，我们很快就会从模型成为瓶颈，转向 harness 设计成为瓶颈。上下文工程、工具披露和任务委派，已经在很大程度上拖住了现有模型的后腿。”

**与前一天对比：** 5 月 3 日时，上下文工程还只是 harness 争论中的次级主题。到 5 月 4 日，它已上升为独立议题，并出现了结构化材料，如架构图、工作手册和压缩策略分类体系。

### 1.3 消费级 GPU 上的本地模型编码代理 🡕

[@witcheer](https://x.com/witcheer) [详细说明了](https://x.com/witcheer/status/2051393306811121829)（64 次点赞，78 次收藏）展示了如今如何在单张 RTX 3090 上跑通完整的自主编码循环：使用 Qwen3.5-27B，在 262K 上下文下搭配 q4_0 KV cache。“模型会编写多文件代码、运行测试、修复自己的 bug，并交付结果。全部只用 24GB VRAM。” 这条线程还包含了 RTX 4060 Ti（8GB）和 RTX 3060（12GB）的配置方案。

[@sakurayukiai](https://x.com/sakurayukiai) 称赞道：“q4 KV cache 几乎是靠一己之力让消费级 GPU 还能支撑 agentic 工作流。” 但 [@oppollo11](https://x.com/oppollo11) 也提醒：“KV cache 用 q4_0 会导致结果不可靠，我建议不要低于 q8。” [@EdgeDimi](https://x.com/EdgeDimi) 则直言不讳：“复杂的 agentic 工作区根本不可能在合理时间内读完，更别提做好串行工具调用了。我不知道 512GB RAM 的硬件体验如何……但觉得这些小参数模型能做出什么实质性事情，未免太不切实际。”

**与前一天对比：** 5 月 3 日讨论的是本地模型的成本优势（例如 Mac Mini 方案）。到 5 月 4 日，讨论收窄到具体 GPU 配置和量化权衡，并给出了消费级硬件上的实际基准。

## 2. 什么让人感到沮丧

### Token 浪费与成本不透明

[@higgsfield](https://x.com/higgsfield) 把热门帖子的核心概括为“把 token 烧在臃肿的 schema 上”。[@AINativeLang](https://x.com/AINativeLang) [量化了](https://x.com/AINativeLang/status/2051127789181382765) 则量化了差距：7 周内总 AI 支出为 870 美元，而传统代理循环要花 3,000 美元以上——通过把编排层编译掉，而不是让 LLM 在运行时逐步推理，成本下降了 71%。

### 多代理协同的复杂性

[@hosseeb](https://x.com/hosseeb) [询问了](https://x.com/hosseeb/status/2051104883412193510)（37 次点赞，61 次收藏）发问：“你见过最疯狂的多代理工作流/配置是什么？” 回复显示，大多数配置依然很原始。[@0xgilbert](https://x.com/0xgilbert) 承认：“我每天直接跑 5 到 7 个代理。和一个经过精心编排的系统本应能管理的规模相比，这还是太保守了。” [@ercwl](https://x.com/ercwl) 则把多代理的极致形容得近乎荒诞：“巅峰状态，就是让 Claude 通过 Dispatch 和 computer use，在你的手机上控制 Codex 桌面应用。”

### Harness 话题疲劳

[@dexhorthy](https://x.com/dexhorthy) [表达了](https://x.com/dexhorthy/status/2050931243181576669)（70 次点赞）表达了对“AI 写的 harness 工程炒作废话”的厌倦；随后 [指出](https://x.com/dexhorthy/status/2051322005472059467) 又说自己“在上下文工程上早了 3 个月，在 lights off software factory 上早了 6 个月，在‘OH f**** TURN THE LIGHTS BACK ON’上又早了 6 个月。” 持续的反弹说明，这场讨论已经过了新鲜感峰值。

### 代理安全缺口

## 3. 人们希望出现什么

### 标准化的代理身份与授权

[@Aiagent_s](https://x.com/Aiagent_s) [描述了](https://x.com/Aiagent_s/status/2051260653697225097) 点出了这一缺口：“企业正在部署 AI 代理，却没有身份框架、没有权限范围控制、没有审计轨迹，也没有撤销机制。” Microsoft Agent 365 解决了其中一部分，但 [@RavenOfSpace](https://x.com/RavenOfSpace) 指出，IAM 并不是为拥有自身凭证的自主代理设计的。

### 无需沙箱的无头代理执行

[@hwchase17](https://x.com/hwchase17) [回应了](https://x.com/hwchase17/status/2051139834459443272)（33 次点赞，18 次收藏）回应了“在没有磁盘或 bash 访问权限的情况下运行 harness”的需求：“deepagents 可以配合‘虚拟文件系统’运行，从而玩出很多很棒的上下文工程技巧，而不需要真正的沙箱环境！” [@BrandGrowthOS](https://x.com/BrandGrowthOS) 评价道：“很聪明——所以你本质上是在 mock 文件系统调用，而不是去起容器。”

### 代理基础设施即服务

[@cycle_vega](https://x.com/cycle_vega) [指出了](https://x.com/cycle_vega/status/2051283818691064078) 提到了反复出现的痛点：“现在每个垂直 SaaS 都在做自己的 AI 代理。但触发器、会话持久化、API 编排、数据安全——每次都得重做一整套基础设施。Stripe 可没让每家创业公司都自己去造支付轨道。”

### 真正好用的代理记忆

[@EloPhanto](https://x.com/EloPhanto) 在回复 RunTrim 时给出了标准：“对编码代理来说，‘记忆’只有能回答这些问题，才配叫记忆：我动过什么？我承诺不动什么？和上次运行相比变了什么？有什么证据证明我已经完成？”

## 7. 机会在哪里

**[+++] 代理记忆与上下文持久化层。** 多个信号正在汇合：RunTrim 已推出面向编码代理的记忆/范围/控制层；PlugMem 获得 ICML 接收；@_overment 指出了尚未解决的上下文缓存问题；@EloPhanto 则定义了代理记忆必须证明什么。“无状态代理会话”与“持久、可审计的代理工作空间”之间的缺口，是当前被反复提及最多的未满足需求。

**[+++] 代理技能市场与分发。** Higgsfield CLI（526 次点赞，440 次收藏）领跑当天，SkillsBench 达到 1.1K stars，Autoskills 可以自动识别并安装技能，Shopify 也发布了官方 Hermes 技能。“npx skills add” 这种模式正在成为代理能力领域的 npm——谁能做好发现层和质量层，谁就有机会赢。

**[++] 代理治理与安全工具。** Microsoft Agent 365 已 GA，DeepMind 发布了代理攻击分类，@dipsybitsy 还报告了通过摩尔斯电码漏洞卷走 20 万美元的案例。@xBalbinus 对此的判断是：“下一款爆发的 AI 产品，未必是更聪明的代理，而可能是更安全的代理。” 企业需求已经明确，但供给仍然分散。

**[++] 编译式编排（零成本协同）。** AINL 展示了通过编译编排逻辑、而不是在每一步都让 LLM 推理，可实现 71% 的成本下降。随着代理工作负载增加，“编排税”会成为主导成本。能消除逐步推理开销的工具，具备结构性的成本优势。

**[+] 本地模型代理基础设施。** 消费级 GPU 配置（RTX 3060–3090）已经可以运行拥有 262K 上下文的 27B 模型，完成自主编码循环。“技术上能跑”与“足够可靠”之间的差距，为本地优先的代理工具创造了机会：自动处理量化权衡、模型选择和质量监控。

**[+] 原生面向代理的 SaaS 基础设施。** @cycle_vega 指出，每个垂直 SaaS 都在一遍遍重造触发器、会话持久化和 API 编排。一个“代理基础设施版 Stripe”——提供标准化触发器、状态管理和工具连接——有机会吃下这层不断重复出现的横向基础设施需求。

## 8. 要点总结

1. **技能层正在吞掉整个代理栈。** Higgsfield CLI 拿下 526 次点赞和 440 次收藏（当天 AI 相关帖子的最高分），再加上 Shopify 发布官方 Hermes 技能，都表明可安装、可组合的技能——而不是单体框架——正在成为代理能力分发的主要单位。（[来源](https://x.com/higgsfield/status/2051346056039039487)）

2. **Harness 工程已经进入“无聊但必要的基础设施”阶段。** 争论已经从“它是什么？”转向“是否该自动化它的演化？” AHE 论文取得 77% 的 pass@1，证明自动化 harness 优化是可行的；而 @nichochar 与 @_colemurray 的分歧，则说明实践者在自研还是采购上仍未达成共识。（[来源](https://x.com/_colemurray/status/2051045148252143669)）

3. **新的瓶颈是上下文工程，而不是模型质量。** @_overment 的详细架构图、@DanIsBuilding 关于“瓶颈将从模型转向 harness 设计”的判断，以及数据集中 12 次“context engineering”短语匹配，都指向同一个结论：上下文管理正逐渐取代模型能力，成为核心约束。（[来源](https://x.com/_overment/status/2051000796515308030)）

4. **Hermes Agent 生态的建设速度，超过了其他开源代理框架。** 桌面应用、Shopify 技能、HermesWorld MMORPG 插件、VPS 部署指南和 Kanban 编排，都在同一天上线或发布。社区贡献的广度说明，这是真实采用，而不只是炒作。（[来源](https://x.com/shmidtqq/status/2051326780758196416)）

5. **代理治理正从“可有可无”变成企业必需。** Microsoft Agent 365 GA、DeepMind 的代理陷阱分类，以及实践者报告的 20 万美元代理攻击，构成了一个由供给（厂商工具）、研究（攻击框架）和需求（真实损失）组成的三角。治理栈很可能会成为企业部署代理的标配。（[来源](https://x.com/WesRoth/status/2051210217757843923)）

6. **本地模型编码代理已经可行，但还谈不上可靠。** RTX 3090 上运行 Qwen3.5-27B 的方案证明了 262K 上下文下的技术可行性，但 q4_0 与 q8_0 的争论，以及 @EdgeDimi 的反对意见，都表明“能跑起来”和“我敢把生产代码交给它”之间仍有明显差距。（[来源](https://x.com/witcheer/status/2051393306811121829)）

7. **代理市场模式已经从概念走向竞争阶段。** Solana devnet 上的 AgenC、Hermes 技能市场、Swarms Marketplace、面向代理的黑客松赛道——至少已有 5 个独立团队在同时构建代理工作市场。概念已被验证，接下来比拼的是执行与分发。（[来源](https://x.com/tetsuoarena/status/2051258954655609153)）
