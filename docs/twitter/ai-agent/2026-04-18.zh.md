# Twitter AI Agent - 2026-04-18

## 1. 人们在讨论什么

### 1.1 harness 工程从理论走向实践 🡕

围绕 harness 工程的讨论，已经从定义之争转向具体的落地模式。[@_lopopolo](https://x.com/_lopopolo) 描述了一个 [Codex 自动化工作流](https://x.com/_lopopolo/status/2045245935228510213)：自动化流程以 Markdown 文件形式存放在 `docs/automations` 中，提示词只有两句话，用来引用 runbook 文件；每个自动化流程都会经过代码审查，由代码仓库负责并纳入版本控制（55 个赞、47 次收藏、2,844 次浏览）。[@michellelawson](https://x.com/michellelawson) 发布了 [45 分钟深度解析](https://x.com/michellelawson/status/2045322275335836132)，介绍“Claude Code、Codex、OpenClaw，以及你钟爱的所有 AI agent 背后的架构”（31 个赞、34 次收藏）。[@ghumare64](https://x.com/ghumare64) 分享了 [对 12 组件 harness 模型的详细分析](https://x.com/ghumare64/status/2045291112454402194)，指出记忆与上下文管理“被当作两个独立组件处理，但在生产环境里，它们其实是同一个问题戴着两顶帽子”，并强调记忆必须“比你最初使用的 harness 活得更久”（13 个赞、23 次收藏、1,573 次浏览）。agentmemory 项目据称通过 BM25 + 向量 + 知识图谱的混合检索，在 LongMemEval-S 上实现了 95.2% 的 R@5。[@forefy](https://x.com/forefy) 记录了具体的 [agentic harness 模式](https://x.com/forefy/status/2045260089808879890)，包括 Fork Subagent 与 Swarm Mode，以及 Bridge/Remote Control 模式。

**讨论洞察：** 这场讨论已经从“harness 就是产品”推进到工程细节：Markdown 作为 runbook、可移植的记忆层，以及模式目录。收藏量最高的帖子，提供的往往是可复现的模式，而不是哲学层面的立场。记忆可移植性成为目前最棘手、尚未解决的问题：各大主流 harness（Claude Code、LangGraph、OpenAI、Anthropic 的 Ralph Loop）都以不同方式实现记忆，而且彼此完全不互通。

**与前一天对比：** 4 月 17 日，harness 工程的主线还是 @akshay_pachaar 提出的三阶段框架（从权重到上下文再到 harness）这一顶层视角。到了 4 月 18 日，讨论进一步下沉到实现细节：Markdown runbook、记忆可移植性基准，以及具名架构模式。抽象层级降低，而收藏与点赞的比例上升，说明受众已从一般兴趣者转向实操者。

### 1.2 技能生态扩张与供应链安全之间的张力 🡕

两股相反的力量发生了碰撞：技能生态快速扩张，同时人们对技能供应链风险的担忧也在加剧。[@NousResearch](https://x.com/NousResearch) 宣布了一个 [与 Jim Liu（@dotey）的合作](https://x.com/NousResearch/status/2045613907004535011)，要把热门的信息图和设计技能移植到 Hermes Agent，这是当天热度最高的帖子（331 个赞、198 次收藏、18,501 次浏览）。这条引用推文提到，一个面向视觉内容技能的 GitHub 项目已获得 14k+ star。[@Baconbrix](https://x.com/Baconbrix) 宣布了 [作为官方 Claude Code 插件的 Expo Agent skills](https://x.com/Baconbrix/status/2045310352322433100)，声称“原生 UI 提升了 46%”（54 个赞、29 次收藏、2,054 次浏览）。[@sharbel](https://x.com/sharbel) 列出了 [10 个多数开发者不知道存在的 Claude Code 工具](https://x.com/sharbel/status/2045461633330229477)，覆盖技能、记忆持久化和编排工具（66 个赞、46 次收藏）。

![Claude Code 中的 Expo Agent skills 插件发现界面](https://pbs.twimg.com/media/HGJlYUibcAAwhXi.jpg)

与此同时，[@shawmakesmagic](https://x.com/shawmakesmagic) 认为存在 [不存在可行的 skill 市场](https://x.com/shawmakesmagic/status/2045222901100741026)：“下载一个技能的风险太高了，这是历史上最容易被利用的供应链攻击面。应该专注于打造自己会用的 agent，而不是为一个并不存在的市场做产品”（123 个赞、11 次收藏、4,800 次浏览）。[@DanKornas](https://x.com/DanKornas) 则给出了一个具体工具：[skill-scanner](https://x.com/DanKornas/status/2045398936278470918)。这是一款安全扫描器，结合基于模式的检测（YAML + YARA）、LLM-as-a-judge 和行为数据流分析，用于扫描第三方 agent 技能中的提示注入与数据外泄风险（0 个赞、5 次收藏）。

![展示 AI agent skills 多引擎检测的 Skill Scanner README](https://pbs.twimg.com/media/HGK3fkmWgAA2lMC.png)

**讨论洞察：** 技能生态正在分裂成两大阵营。平台厂商（Nous Research、Expo、MongoDB）正通过官方渠道提供经过筛选的第一方技能；与此同时，社区开发者则通过几乎未经审查的 GitHub 仓库传播技能。Shaw 的警告和 DanKornas 的扫描器，代表了针对这一攻击面的第一代应对方案。

**与前一天对比：** 4 月 17 日，对技能市场的怀疑还是一个新主题。到了 4 月 18 日，这种担忧明显升级：Shaw 的帖子获得了 123 个赞，高于前一天较为克制的表述；首个专用扫描工具 skill-scanner 也作为直接回应出现。

### 1.3 本地 AI agent 达到实用可行性门槛 🡕

越来越多的证据表明，本地模型推理已经跨过了 agent 工作所需的可用性门槛。[@sudoingX](https://x.com/sudoingX) 展示了 [本地运行的 Gemma 4 31B Dense Q4](https://x.com/sudoingX/status/2045468708307673454)：在配备 24GB 显存的 RTX 5090 mobile 上，通过 llama.cpp 实现 15 tok/s 的持续吞吐，仅凭一个提示词就生成了完整的 GPU marketplace UI，而且“没有提示词工程、没有 agentic harness、没有工具调用”（126 个赞、88 次收藏、14,183 次浏览）。后续回复写道：“这只需要 24GB 显存和一句话提示词。Google 做得很棒，模型并不差，差的是围绕本地模型的叙事。”

![llama-server 终端输出，显示 Gemma 4 31B 以 14.59 tok/s 进行推理，并附带 prompt cache 指标](https://pbs.twimg.com/media/HGL0niXbIAAEATb.png)

[@tom_doerr](https://x.com/tom_doerr) 分享了 [GenericAgent](https://x.com/tom_doerr/status/2045244196483711163)：这是一个仅约 3K 行核心代码的自进化自主 agent 框架，并登上 GitHub Trending 当日仓库榜第 1 名（44 个赞、38 次收藏、2,816 次浏览）。该框架会自动将执行路径固化为可复用技能，并在 30K 上下文窗口下运行。[@jahooma](https://x.com/jahooma) 详细介绍了 [免费编程 agent 的运行经济性](https://x.com/jahooma/status/2045307453311779296)，解释了在 8 张 B200 GPU 上为 GLM 5.1 提供服务时如何优化提示词缓存；“并发请求过多会破坏提示词缓存”，因此会话级优化是维持业务可持续运行的关键。

![Prompt cache 命中率图表，显示缓存命中率达 90.6%，并在高并发期间出现下降](https://pbs.twimg.com/media/HGJYRUja0AEkUhy.jpg)

**讨论洞察：** 本地 AI agent 已不再只是爱好者的玩具。24GB 消费级 GPU、量化的 30B+ 模型和轻量级推理服务器（llama.cpp）的组合，已经能产出实践者认为在单轮生成上可与云端 API 竞争的结果。瓶颈已从模型质量转向推理经济性和提示词缓存管理。

**与前一天对比：** 4 月 17 日讨论了语音优先和 Gemini CLI 等与本地相关的主题，但没有出现原始的本地推理基准。到了 4 月 18 日，则出现了具体硬件配置、token 吞吐数据，以及明确瞄准本地优先场景的 GenericAgent 框架。

### 1.4 Agent 工具是否已经过时之争 🡒

[@samhogan](https://x.com/samhogan) 发布了 [一个颇具挑衅性的观点](https://x.com/samhogan/status/2045359777270927699)，称“大多数围绕 LLM 构建的工具，都是为一个如今基本不存在的世界打造的”，并将 RAG、GraphRAG、多 agent 编排、ReAct 框架、提示词管理、LLMOps、评测工具、网关和微调库列为“过去 3 个月里全部过时”的类别（99 个赞、83 次收藏、16,655 次浏览）。在回复中，[@kylewgrove](https://x.com/kylewgrove) 表示：“有些编排工具，是为一个从未存在过的世界打造的。”[@a_protsyuk](https://x.com/a_protsyuk) 则反驳道：“RAG 并没有过时，只是不再特殊了——现在每个模型都内置了它，所以独立的‘RAG pipeline’产品已经死了。但面向真实生产工作流、具备重试、状态和人工交接能力的多 agent……正在增长。”

[@official_taches](https://x.com/official_taches) 分享了 [相关视角](https://x.com/official_taches/status/2045189214304714758)，讨论从 vibe coding 到结构化框架，再到一种新的中间地带：“在开始任何项目之前，我都会先让 AI 证明核心功能真的可行。先做一次性的、交互式的实验和 mockup。它快速、混乱、直接。我把这叫作 ‘vibe-proofing’”（38 个赞、3 次收藏、2,496 次浏览）。

**讨论洞察：** 数据集中收藏量最高的帖子，宣告整整一代 AI 工具已经过时。更细致的回复则揭示出更复杂的现实：独立工具产品正在消亡，但检索、编排、评测等底层能力并没有消失，而是被 harness 和模型能力吸收了。“vibe-proofing”则说明，实践者既想要 vibe coding 的速度，也想要结构化框架的质量。

**与前一天对比：** 这是 4 月 18 日出现的新主题。4 月 17 日关注的是该用哪些工具；4 月 18 日则开始质疑，整类工具是否还有存在的必要。

### 1.5 多 agent 编排开始具备基础设施 🡕

多个项目发布了具体的编排基础设施。[@tom_doerr](https://x.com/tom_doerr) 分享了 [Mission Control](https://x.com/tom_doerr/status/2045592487796916239)：这是一个自托管 AI agent 舰队编排面板，拥有 4.2k 个 GitHub star、32 个仪表板面板、实时 WebSocket 更新、零外部依赖（SQLite），并支持 OpenClaw、CrewAI、LangGraph 和 AutoGen 等多个网关（41 个赞、66 次收藏、2,927 次浏览）。

![Mission Control 仪表板，展示网关控制平面、会话路由器、事件流和系统负载指标](https://pbs.twimg.com/media/HGNnhxuWQAIDgo3.png)

[@Voxyz_ai](https://x.com/Voxyz_ai) 宣布了 Garry Tan 推出的 [GBrain v0.11](https://x.com/Voxyz_ai/status/2045432730104582314)，声称 Minions agent 编排“比 openclaw 默认 subagents 快 10 倍”。其基准数据显示：该方案可在 15 分钟内处理过去 36 个月的 19,240 条帖子，成本为 0 美元；相比之下，sub-agent 方案“40% 的运行失败，token 成本为 1.08 美元”（20 个赞、10 次收藏、7,423 次浏览）。其功能包括 spawn storm 防御（限制递归深度）、幂等任务执行，以及自动通知父 agent。[@camsoft2000](https://x.com/camsoft2000) 称赞了 [RepoPrompt 的编排工作流](https://x.com/camsoft2000/status/2045227088475468027)，其中“主 agent 为防止某个 subagent 在问题上空转，直接杀掉了它”（29 个赞、22 次收藏、3,310 次浏览）。[@matteocollina](https://x.com/matteocollina) 发布了 [Regina](https://x.com/matteocollina/status/2045452379085037918)：这是一个基于 Platformatic Watt 的生产级 agent 编排层，agent 以 Markdown 定义，每个 agent 都作为独立 worker thread 运行，并拥有自己的 SQLite 虚拟文件系统。

**讨论洞察：** 编排正在从概念框架转向运维仪表板。Mission Control 获得 66 次收藏、41 个赞，显示出构建者强烈的“先存后看”意图。GBrain 提供的具体基准数据（sub-agent 40% 失败率、10 倍速度说法）也让实践者能够拿来与自己的系统对照评估。

**与前一天对比：** 4 月 17 日通过 Google 的研究结论和 Av1d 的拆解讨论了多 agent 协作；4 月 18 日则从研究转向已交付的基础设施：Mission Control、GBrain v0.11、Regina 和 RepoPrompt 编排，代表的都是已部署工具，而不是论文。

### 1.6 Agent 安全成为一等议题 🡕

安全问题已经从零散警告升级为系统化工具。[@jiqizhixin](https://x.com/jiqizhixin) 报道了 [清华大学的 AgentWard](https://x.com/jiqizhixin/status/2045365707055956440)：这是一个全栈安全操作系统，将五层协同的纵深防御机制嵌入 agent 工作流：Foundation Scan、Input Sanitization、Cognition Protection、Decision Alignment 和 Execution Control（5 个赞、3 次收藏、509 次浏览）。

![AgentWard 架构图，展示围绕 OpenClaw 运行时推理循环的五层安全防护](https://pbs.twimg.com/media/HGGGy-FbYAIBMeG.jpg)

[@nebusecurity](https://x.com/nebusecurity) 报道称，其 [使用 GPT-5.4 的 AI 安全 agent](https://x.com/nebusecurity/status/2045398105932353907) 在 7 秒内发现了一个漏洞，并将其转化为“82,337 美元的漏洞赏金”（16 个赞、3 次收藏、597 次浏览）。[@ChainlCLzxti](https://x.com/ChainlCLzxti) 指出一个 [新的网络钓鱼技术](https://x.com/ChainlCLzxti/status/2045445872683737585)：AI agent 会通过分析社交媒体发帖风格，生成具有说服力的私信，“模拟官方客服”（13 个赞、0 次收藏、4,676 次浏览）。[@0xJeff](https://x.com/0xJeff) 分享了一个 [一个警示案例](https://x.com/0xJeff/status/2045384084365750546)，讲述他的 Hermes agent 出现幻觉，并使用 Bird CLI“胡言乱语，而不是直接帮我抓取推文”，之后又把这次失误写入记忆，作为纠偏措施（18 个赞、5 次收藏、2,274 次浏览）。

**讨论洞察：** Agent 安全正在分化成三个层级：学术界的纵深防御（AgentWard）、商业化的进攻型安全（Nebu 的 82K 美元赏金），以及个人层面的伤害缓解（0xJeff 的幻觉事件）。短期内最实用的工具，可能仍是 DanKornas 的 skill-scanner，用于在部署第三方技能前先做审核。

**与前一天对比：** 4 月 17 日，技能供应链安全刚被提出为一个担忧；到了 4 月 18 日，则出现了首个具体扫描工具（skill-scanner）、一个完整的学术安全框架（AgentWard），以及首个有报道的由 AI agent 发现的漏洞赏金（82,337 美元）。

## 2. 什么让人感到挫败

### 技能供应链信任——严重程度：高

[@shawmakesmagic](https://x.com/shawmakesmagic) 在一则 [被广泛传播的帖子](https://x.com/shawmakesmagic/status/2045222901100741026) 中称，技能是“历史上最容易被利用的供应链攻击面”（123 个赞、4,800 次浏览）。[@DanKornas](https://x.com/DanKornas) 在 [宣布 skill-scanner 的帖子](https://x.com/DanKornas/status/2045398936278470918) 中警告：“对第三方 agent 技能，应当像对待 shell 脚本一样保持怀疑。”目前，任何主流 agent 平台都还没有标准化的审查流程。

### Agent 记忆不可移植——严重程度：高

[@ghumare64](https://x.com/ghumare64) 记录了 [锁定问题](https://x.com/ghumare64/status/2045291112454402194)：“Claude Code：三级记忆层级。LangGraph：按命名空间组织的 JSON Stores。OpenAI：由 SQLite 或 Redis 支撑的 Sessions。每一种都解决了记忆问题，但它们彼此完全不通。换一个 harness，你积累的上下文就没了。”[@fxnction](https://x.com/fxnction) 也呼应道：“现在所有 agent——无论跑在 OpenClaw、Hermes 还是自定义技术栈上——都被困在各自的沙盒里。”

### 多 agent 失败率——严重程度：中

[@Av1dlive](https://x.com/Av1dlive) 引用了 [Google 研究](https://x.com/Av1dlive/status/2045437933818437732)，称“独立 agent 的失败率比单 agent 高 17 倍”（15 个赞、14 次收藏）。[@Voxyz_ai](https://x.com/Voxyz_ai) 报道了 GBrain v0.11 的基准结果，其中 [子 agent 方法“在 40% 的运行中失败”](https://x.com/Voxyz_ai/status/2045432730104582314)。[@ybouane](https://x.com/ybouane) 建议：“如果只用一个 agent，让它花更长时间把活做完，由于缓存机制，整体 token 消耗会低得多。”

### 生产环境中的 agent 幻觉——严重程度：中

[@0xJeff](https://x.com/0xJeff) 分享了一则 [事件](https://x.com/0xJeff/status/2045384084365750546)，称他的 Hermes agent“出现幻觉，开始使用 Bird CLI 胡言乱语，而不是直接帮我抓取推文”。修复方法是把这次事故写入记忆。[@Plar_ai](https://x.com/Plar_ai) 回复道：“现在想象一下，如果它接的是支付工具呢？同样的幻觉，只不过它下的就不是胡话，而是订单了。”

## 3. 人们希望存在什么

### 可移植的 agent 记忆标准

[@ghumare64](https://x.com/ghumare64) 在 [引用 agentmemory 的帖子](https://x.com/ghumare64/status/2045291112454402194) 中呼吁，让记忆“比你最初使用的 harness 活得更久，因为你开始用的 harness，不会是你最终用的 harness。今天是 Claude Code，明天是 Codex，再之后可能是下个月刚发布的任何东西”，并将其视为一种潜在解决方案（13 个赞、23 次收藏）。agentmemory 项目声称已在 Claude Code、Cursor、Gemini CLI 和 OpenCode 上提供 12 个 hook，但目前仍只是单个项目的努力，而非行业标准。

机会：跨 harness 的记忆协议可以让用户在切换 harness 时不再丢失上下文。当前的碎片化格局，正把用户锁死在最初的选择上。

### 自动化技能审查流水线

[@shawmakesmagic](https://x.com/shawmakesmagic) 宣称 [skill 市场没有可行性](https://x.com/shawmakesmagic/status/2045222901100741026)，没有信任就无从谈起。[@DanKornas](https://x.com/DanKornas) 构建了 [skill-scanner](https://x.com/DanKornas/status/2045398936278470918)，作为第一步，但它只覆盖检测，不包括持续监控、信誉评分或沙盒执行。

机会：完整的技能审查流水线（静态分析 + 运行时沙盒 + 社区信誉）将帮助平台建立它们想要的市场，同时解决实践者目前对技能市场缺乏信任的问题。

### 面向 SRE 工作流的 agent 可观测性

[@TheNJDevOpsGuy](https://x.com/TheNJDevOpsGuy) 描述了一套 [SRE Agent 架构](https://x.com/TheNJDevOpsGuy/status/2045529655357141196)，要求具备“合适的提示词/系统消息、能把 agent 变成 SRE 和可观测性专家的 agent 技能、一个足够好的 LLM，以及目标”（12 个赞、13 次收藏）。通用编码 agent 与 SRE 专用工具之间仍有明显鸿沟。

![SRE Agent 架构，展示触发源、MCP server 工具、agent skills 和基础设施目标](https://pbs.twimg.com/media/HGMuYOPXsAApMhr.jpg)

机会：面向 SRE 的专用 agent 技能，如果预置对 Prometheus、PagerDuty、Kubernetes 和各大云厂商的集成，就能打开一个高价值的垂直市场。

**GenericAgent** 走的是相反路线：核心代码约 3K 行，配备 9 个原子工具和约 100 行的 Agent Loop，让任意 LLM 获得系统级控制能力。其自进化机制会自动将执行路径固化为技能，并在 30K 上下文窗口下运行；相比之下，其他 agent 往往要消耗 200K-1M 的上下文。

## 7. 机会在哪里

`[+++]` **Agent 记忆可移植层** —— 各大主流 harness 都以不同方式实现记忆，彼此完全不互通。一个结合混合检索（BM25 + 向量 + 知识图谱）的跨 harness 记忆协议，将有望解决用户对锁定效应的头号抱怨。[@ghumare64](https://x.com/ghumare64/status/2045291112454402194) 记录了这一问题；agentmemory 则凭借 12 个跨工具 hook 展现出早期 traction。

`[+++]` **技能安全与审查基础设施** —— skill-scanner 已经出现，但目前只覆盖静态检测。市场还需要持续监控、信誉评分和沙盒执行，才能支撑平台正在尝试打造的技能市场。[@shawmakesmagic](https://x.com/shawmakesmagic/status/2045222901100741026) 和 [@DanKornas](https://x.com/DanKornas/status/2045398936278470918) 分别定义了问题与首个不完整的解决方案。

`[++]` **企业级编码 agent 治理** —— Databricks 虽然先入场，但这个问题具有普遍性。任何运行多个编码 agent 的公司，都需要使用追踪、速率限制、成本分摊和审计留痕。这是一个类似早期云管理平台的企业 SaaS 机会。

`[++]` **面向 agent 的本地推理优化** —— [@jahooma](https://x.com/jahooma/status/2045307453311779296) 表明，提示词缓存管理是自托管编码 agent 的关键瓶颈。能够优化会话级缓存利用率、管理并发用户调度并平衡 GPU 饱和度的工具，将直接降低推理成本。

`[+]` **SRE 专用 agent 技能** —— [@TheNJDevOpsGuy](https://x.com/TheNJDevOpsGuy/status/2045529655357141196) 阐述了 SRE agent 的四组件架构。面向 Kubernetes、云厂商和监控栈，预置事故检测、根因分析和自动修复能力的技能包，将填补一个高价值的垂直空白。

`[+]` **Agent 舰队仪表板** —— Mission Control 以 41 个赞换来 66 次收藏，显示出构建者对 agent 舰队运维可见性的强烈需求。这个市场仍处于早期（软件还在 Alpha 阶段），而且分散在 OpenClaw、CrewAI、LangGraph 和自定义技术栈之间。

## 8. 要点总结

1. harness 工程已从理念之争转向工程模式：Markdown 作为 runbook、记忆可移植性基准，以及具名架构模式，取代了高层次的概念框架。来源：[@_lopopolo](https://x.com/_lopopolo/status/2045245935228510213)、[@ghumare64](https://x.com/ghumare64/status/2045291112454402194)、[@forefy](https://x.com/forefy/status/2045260089808879890)。

2. 技能供应链安全成为当天风险最高的张力点。Shaw 称技能是“历史上最容易被利用的供应链攻击面”，DanKornas 则发布了首款专用扫描器。来源：[@shawmakesmagic](https://x.com/shawmakesmagic/status/2045222901100741026)、[@DanKornas](https://x.com/DanKornas/status/2045398936278470918)。

3. 本地 AI 跨过了实用性门槛：Gemma 4 31B 在消费级硬件上以 15 tok/s 的速度，仅凭单个提示词就生成了可用于生产的 UI。来源：[@sudoingX](https://x.com/sudoingX/status/2045468708307673454)。

4. 多 agent 编排获得了真正的基础设施：Mission Control（4.2k stars、32 个面板）、GBrain v0.11（有基准数据支撑的 10 倍速度说法）和 Regina（用 Markdown 定义 agent，并为每个 agent 提供 SQLite VFS）。来源：[@tom_doerr](https://x.com/tom_doerr/status/2045592487796916239)、[@Voxyz_ai](https://x.com/Voxyz_ai/status/2045432730104582314)、[@matteocollina](https://x.com/matteocollina/status/2045452379085037918)。

5. 企业治理进入编码 agent 领域：Databricks Unity AI Gateway 和 Cisco 在生产环境部署 LangGraph，标志着行业正从开发者实验转向组织级管控。来源：[@databricks](https://x.com/databricks/status/2045209450085040507)、[@LangChain](https://x.com/LangChain/status/2045240475402301710)。

6. Agent 安全首次产出具体成果：AgentWard（清华大学的五层防御安全操作系统）、skill-scanner（提示注入检测），以及一个 GPT-5.4 agent 在 7 秒内发现 82K 美元漏洞赏金。来源：[@jiqizhixin](https://x.com/jiqizhixin/status/2045365707055956440)、[@DanKornas](https://x.com/DanKornas/status/2045398936278470918)、[@nebusecurity](https://x.com/nebusecurity/status/2045398105932353907)。

7. GenericAgent 登上 GitHub Trending 第 1 名，加上其约 3K 行的架构，说明市场对轻量、自进化框架的兴趣高于重量级编排。来源：[@tom_doerr](https://x.com/tom_doerr/status/2045244196483711163)。

8. 技能生态分裂为两种分发模式：经过筛选的第一方插件（Expo、MongoDB、Nous Research 合作）与审查极少的社区 GitHub 仓库。两种模式都还没有解决大规模信任问题。来源：[@Baconbrix](https://x.com/Baconbrix/status/2045310352322433100)、[@NousResearch](https://x.com/NousResearch/status/2045613907004535011)、[@shawmakesmagic](https://x.com/shawmakesmagic/status/2045222901100741026)。
