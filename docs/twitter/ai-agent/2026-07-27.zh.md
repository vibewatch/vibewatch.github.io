# Twitter AI 智能体 - 2026-07-27

## 1. 人们在讨论什么

### 1.1 上下文工程正在演变为运行时架构（🡕）

当天最反复出现的观点是：如今智能体的质量，取决于上下文如何随时间被组装、裁剪和路由，而不是提示词写得越来越长。至少六条高信号帖子都汇聚到同一转变上：删掉臃肿提示词，只在需要时加载参考资料，把持久行为放进技能和记忆里，并将生成与评估分离。

[@harleyfoote_](https://x.com/harleyfoote_) [指出](https://x.com/harleyfoote_/status/2081816997373845733) (137 个赞，7 条回复，231,629 次浏览)称，据报道，Anthropic 工程师在 Opus 5 / Fable 5 中移除了 Claude Code 超过 80% 的系统提示词，却没有带来可测量的代码评测损失；随后又在回复中进一步解释：提示词只是更大环境中的一部分，这个环境还由 Skills、`CLAUDE.md`、记忆及其他运行时状态共同构成。[@aiedge_](https://x.com/aiedge_) [阐述了](https://x.com/aiedge_/status/2081832014442025389) (7 个赞，3 条回复，2,212 次浏览，24 次收藏)则分享了类似的 Claude 5 检查清单：用判断替代僵化规则，设计更干净的工具接口，而不是不断往里塞示例；采用渐进式上下文加载，而不是维护一个臃肿的项目文件。

[@alex_verem](https://x.com/alex_verem) [写道](https://x.com/alex_verem/status/2081709001524548064) (19 个赞，6 条回复，3,515 次浏览，28 次收藏)指出，提示词、上下文、执行框架和循环会分别在不同层级失效；真正的危险在于，循环状态如果持续足够久，就会变成“承重”状态，因此独立的怀疑型评估器比更聪明的生成器更重要。[@0xRafy](https://x.com/0xRafy) [将其定义为](https://x.com/0xRafy/status/2081775487068582105) (22 个赞，9 条回复，2,218 次浏览，26 次收藏)则把图工程视为继提示词、上下文、执行框架和循环之后缺失的第五层，认为图解决的是跨智能体状态与来源追踪问题，而不只是检索。

![知识图谱实战手册页面，展示将图谱工程作为共享记忆、跨代理状态和溯源校验](https://pbs.twimg.com/media/HOPxUFCXoAAyYa9.jpg)

[@AiandTechHub](https://x.com/AiandTechHub) [提到](https://x.com/AiandTechHub/status/2081710019930984451) (46 个赞，11 条回复，615 次浏览)把 IBM 的结构化知识图谱课程视为一个信号：这件事正变得可以系统教授，而不再只是网络热梗。[@kv1nsiii](https://x.com/kv1nsiii) [警告](https://x.com/kv1nsiii/status/2081763951293972942) (24 个赞，9 条回复，1,287 次浏览，22 次收藏)指出，周边技能生态仍然相当混乱：6 个传播广泛的“42 Claude skills”链接指向了错误仓库，另外 4 个只把人带到根目录；而被引用的 ToxicSkills 研究，则把讨论从“安装更多技能”推进到“先读 `SKILL.md`”。

**讨论洞察：** 回复区对“下一层”叫什么并不太感兴趣，更在意的是怎么把它做轻。删减、延迟加载和独立评估器不断被视为成熟信号，而不安全或低质量的技能包则被当作围绕模型形成的真实供应链问题。

**与前一天的比较：** 7 月 21 日的重点，是通过导师卡、课程和论文来解释图工程。到了 7 月 27 日，这个概念更接近实际操作：删掉提示词冗余，把行为拆分到工具和技能中，并把图和评估器视为生产级控制面。

**与前一天的比较：** 7 月更早些时候的讨论，仍 heavily 偏向围绕循环和图的教学。到了 7 月 27 日，讨论明显更偏实证：同一天内，基准产物横跨编码、网络安全、医疗和强化学习基础设施。

### 1.3 安全讨论从“要小心”转向授权、证明与联盟（🡕）

当天最强的信任主题是：智能体安全正在围绕权限边界和公开证据被重新定义，而不再停留于泛泛的红队口号。至少五项较有分量的内容都指向同一种设计直觉：是谁提出请求、允许执行什么任务、什么行动具有正当性，以及系统最终能返回什么证明。

[@NVIDIAAI](https://x.com/NVIDIAAI) [宣布](https://x.com/NVIDIAAI/status/2081666750807171180) (752 个赞，52 条回复，35,377 次浏览)介绍了其对 Open Secure AI Alliance 的贡献，核心是把 NOOA 作为开放智能体执行框架研究项目推出，并把智能体安全从单一厂商定位，转成一个拥有 37 个成员的联盟叙事。[@fly51fly](https://x.com/fly51fly) [链接到](https://x.com/fly51fly/status/2081857231151415591) (2 个赞，101 次浏览)介绍了论文《智能体安全需要通过整体框架重新定义》；其附图显示，同样的动作文本，可能是安全的，也可能是恶意的，区别取决于来源授权、任务一致性、行动一致性和数据隔离。[@posthog](https://x.com/posthog) [认为](https://x.com/posthog/status/2081819814495195393) (24 个赞，2,677 次浏览，31 次收藏)指出，在没有额外控制的情况下信任更聪明的智能体，就像因为车变好了就不系安全带，这与当天更正式的研究语言形成了很好的呼应。

[@Acurast](https://x.com/Acurast) [演示了](https://x.com/Acurast/status/2081769019426718040) (60 个赞，29 条回复，10,641 次浏览)介绍了 OKX AI Marketplace 上的机密 TEE 智能体：它能在去中心化智能手机网络的可信执行环境中运行 Shell 或 Python；回复中则强调了签名执行证明和 x402 支付。[@yashaswini_s_s](https://x.com/yashaswini_s_s) [分享了](https://x.com/yashaswini_s_s/status/2081730466529386707) (9 个赞，3 条回复，407 次浏览)分享了一个为她祖母在 WhatsApp 上订购杂货的智能体；最犀利的回复立刻补上了缺失的控制模型：预先批准的购物篮和硬性价格上限，这样即便语音被克隆或失真，也无法凭空制造新的可支付意图。

**讨论洞察：** 最实用的安全建议并不是“禁止自主性”，而是收紧权限、证明执行过程，并把“被允许的意图”与“只是看起来合理的文本”区分开来。这既符合论文中的框架，也符合更产品化的 TEE/支付案例。

**与前一天的比较：** 7 月 21 日聚焦于钱包和软件包安全中的受限自主性。到了 7 月 27 日，话题扩展成联盟发布、明确的情境化安全框架，以及一个让授权问题一眼可见的消费支付案例。

### 1.4 智能体工作空间开始像完整的操作环境（🡕）

第四个主题是，“使用智能体”越来越意味着围绕它搭建持久化界面：云沙箱、浏览器工作区、终端、语音层、记忆后端和审查循环。最强的帖子，与其说在讨论该选哪个模型，不如说在讨论智能体到底住在哪里、周围配了什么。

## 2. 人们在为什么事感到沮丧

### 技能泛滥，却没有来源可追

想把技能真正用起来的人，仍在被失灵的发现机制和脆弱的信任边界绊倒。[@kv1nsiii](https://x.com/kv1nsiii) [警告](https://x.com/kv1nsiii/status/2081763951293972942) (24 个赞，9 条回复，1,287 次浏览，22 次收藏)指出，6 个传播很广的“42 Claude skills”链接指向了错误仓库，另外 4 个只落到根目录；被引用的 ToxicSkills 研究还发现，受测技能中相当一部分存在严重缺陷。问题不只是链接失效，而是安装一个技能，往往就意味着让陌生人的代码以智能体权限运行。[@vinvan](https://x.com/vinvan) [写道](https://x.com/vinvan/status/2081807325526958552) (65 个赞，10 条回复，16,880 次浏览，132 次收藏)指出，云智能体栈现在需要明确的密钥和沙箱工具；而 [Open-Inspect README](https://github.com/ColeMurray/background-agents) 则说明，其共享 GitHub App 设计只有在单租户部署里才安全。严重程度：高。人们的应对方式，是先看 `SKILL.md` 文件、少装一些 bundle，并尽量缩小仓库或密钥的权限范围。之所以值得投入，是因为无论初次使用技能的人，还是高级云智能体操作者，都还在手动做同样的信任决策。

### 会自我打分的循环，会把坏状态藏起来

可靠性上的核心挫败，仍然是不可见的漂移。[@alex_verem](https://x.com/alex_verem) [写道](https://x.com/alex_verem/status/2081709001524548064) (19 个赞，6 条回复，3,515 次浏览，28 次收藏)指出，糟糕的循环会在多轮交互中把一个错误假设变成“承重”状态，这也是为什么独立怀疑者比更精致的生成器更重要。[@fly51fly](https://x.com/fly51fly) [链接到](https://x.com/fly51fly/status/2081857231151415591) (2 个赞，101 次浏览)介绍了一篇论文，认为同一表面动作可能是无害的，也可能是恶意的，区别取决于来源授权、任务一致性、行动一致性和数据隔离；这意味着只做内容检查，会错过真正的违规。[@witcheer](https://x.com/witcheer) [解释了](https://x.com/witcheer/status/2081845276005085560) (34 个赞，6 条回复，865 次浏览，16 次收藏)指出，Hermes 现在需要明确的记忆和技能审批开关，再加上一套整理流程，才能让自我改进保持可理解。严重程度：高。构建者正在用外部评估器、审批关卡和更显性的记忆写入来应对。之所以值得投入，是因为这种故障隐蔽、代价高，而且在编码、安全和记忆系统里反复被重新发现。

### 云智能体把密钥和执行状态变成了运维问题

转向后台和云端智能体，正在暴露一类新的运维痛点。[@vinvan](https://x.com/vinvan) [认为](https://x.com/vinvan/status/2081807325526958552) (65 个赞，10 条回复，16,880 次浏览，132 次收藏)指出，许多公司还没为云智能体做好准备；一条回复提到，智能体永远不会直接拿到 AWS 访问权限，因为密钥放在 `moto` 后面，数据库状态则通过快照恢复。[面向 Cursor 云代理的 Infisical 指南](https://infisical.com/blog/secure-secrets-management-for-cursor-cloud-agents) 也明确表达了同样的不满：静态密钥界面解决不了轮换、审计轨迹和快照泄漏问题，所以密钥应该在运行时拉取，而不是预先写死在环境里。严重程度：高。人们的应对方式包括机器身份、运行时密钥注入、受限仓库权限和隔离沙箱。之所以值得投入，是因为痛点恰好出现在采用下一阶段要去的地方：拥有真实基础设施访问权限的长时运行智能体。

### 真实操作者栈仍然昂贵、耗电，而且受上下文窗口限制

即便最热情的工作流帖子，也都伴随着日常摩擦。在回复 [@pavlenex](https://x.com/pavlenex) 的 [Buzz 演练指南](https://x.com/pavlenex/status/2081759723771097333) (228 个赞，9 条回复，9,530 次浏览，372 次收藏)时，就有用户抱怨该应用耗电、隐藏 token 用量，而且很快触及会话上限。[@chakhan22](https://x.com/chakhan22) [记录了](https://x.com/chakhan22/status/2081800159898525780) (1 个赞，2 条回复，133 次浏览)则再次提到，把 GPT-5.6 放在 Claude Code 后面测试时，反复遇到上下文限制问题，即使这套工作流已经精心搭配了 Hermes、WezTerm 和运行后复审。严重程度：中。人们在用类似 [Voicebox](https://github.com/jamiepine/voicebox) 这样的本地优先层、类似 [GrokTerm](https://grokterm.com/) 这样的标签式宿主，以及运行后审查循环来缓解，但底层问题并未解决。之所以值得投入，是因为操作者疲劳恰恰出现在那些原本最看好智能体采用的讨论串里。

## 3. 人们希望出现什么

### 具备授权感知的控制面

最明确的实际诉求不是“让智能体更聪明”，而是“让它们知道谁有权要求什么”。[@fly51fly](https://x.com/fly51fly) [链接到](https://x.com/fly51fly/status/2081857231151415591) (2 个赞，101 次浏览)介绍了一个框架，认为同样的动作文本可能安全，也可能恶意，区别取决于来源授权、任务一致性、行动一致性和数据隔离。[@posthog](https://x.com/posthog) [认为](https://x.com/posthog/status/2081819814495195393) (24 个赞，2,677 次浏览，31 次收藏)指出，更聪明的模型并不会消除外部约束的必要性；而在 [@yashaswini_s_s](https://x.com/yashaswini_s_s) 的 [WhatsApp 杂货购物代理](https://x.com/yashaswini_s_s/status/2081730466529386707) (9 个赞，3 条回复，407 次浏览)下，最高赞回复立刻就要求加入预先批准的购物篮和硬性价格上限。[@Acurast](https://x.com/Acurast) [展示](https://x.com/Acurast/status/2081769019426718040) (60 个赞，29 条回复，10,641 次浏览)则在执行侧给出了一部分答案：TEE 支撑的证明，但它还没有覆盖完整的用户意图层。这是一个紧迫的现实需求，而现阶段只有局部答案。机会：直接。

### 面向普通团队的云智能体就绪套件

人们想要的是一套可部署配方，让长时运行的云智能体在密钥、快照、仓库访问和沙箱选择上都有现成方案，而不是逼着每个团队从零发明整套栈。[@vinvan](https://x.com/vinvan) [写道](https://x.com/vinvan/status/2081807325526958552) (65 个赞，10 条回复，16,880 次浏览，132 次收藏)指出，许多公司尚未为云智能体做好准备，并在回复中列出所需栈组件：Open-Inspect、密钥工具、邮箱界面和模拟器支持。[面向 Cursor 云代理的 Infisical 指南](https://infisical.com/blog/secure-secrets-management-for-cursor-cloud-agents) 涵盖了运行时密钥注入，[Open-Inspect README](https://github.com/ColeMurray/background-agents) 则记录了一种强大但明确只适用于单租户的设计，这意味着需求虽被部分满足，但运维负担依旧很重。这是一个会直接影响预算和安全的现实需求。机会：直接。

### 能跨会话延续、并改变下一次决策的记忆

信息流一再把记忆描述为让智能体变得有用的关键，但更尖锐的诉求关注的是行动，而不是回忆。[@Mnilax](https://x.com/Mnilax) [认为](https://x.com/Mnilax/status/2081799872504881346) (12 个赞，3 条回复，182 次浏览，12 次收藏)指出，当前记忆基准测试问的是智能体能否回忆自己见过什么，而不是记忆在经历行动和反馈之后，是否会改变下一次决策。[@witcheer](https://x.com/witcheer) [展示了](https://x.com/witcheer/status/2081845276005085560) (34 个赞，6 条回复，865 次浏览，16 次收藏)讨论了 Hermes 如今如何围绕记忆写入增加明确审批、通知和整理；而 [@chakhan22](https://x.com/chakhan22) [使用](https://x.com/chakhan22/status/2081800159898525780) (1 个赞，2 条回复，133 次浏览)则把 Hermes 放在更大工作流栈中，作为实用的“第二大脑”。[@0xRafy](https://x.com/0xRafy) [将其定位为](https://x.com/0xRafy/status/2081775487068582105) (22 个赞，9 条回复，2,218 次浏览，26 次收藏)把图工程视为一种答案，但整体需求仍未真正闭合。这是一个已有多个局部竞争者的现实需求。机会：竞争性。

### 经过整理、可审计的技能路径，而不是病毒式技能堆

人们想要的是更小、更好、更安全的技能包和学习路径。[@kv1nsiii](https://x.com/kv1nsiii) [展示了](https://x.com/kv1nsiii/status/2081763951293972942) (24 个赞，9 条回复，1,287 次浏览，22 次收藏)说明了原因：失效仓库、重复列表和未经审查的陌生人代码，会构成极差的上手体验。与此同时，[@AiandTechHub](https://x.com/AiandTechHub) [提到](https://x.com/AiandTechHub/status/2081710019930984451) (46 个赞，11 条回复，615 次浏览)把 IBM 的结构化知识图谱专项课程视为人们真正愿意信任的那类课程；[@rlaope](https://x.com/rlaope) [封装了](https://x.com/rlaope/status/2081691230048792662) (18 个赞，1 条回复，1,676 次浏览，26 次收藏)则把 Oh My Hermes 定位为一个经过整理的运行层，而不是另一份零散清单。这是一个已有早期产品化答案的现实需求，但还没有明确默认方案。机会：竞争性。

表格之外，整体满意度大致落在“很有前景，但需要脚手架”到“只有把缺失的控制层再补上才真正有用”之间。[@chakhan22](https://x.com/chakhan22) [使用](https://x.com/chakhan22/status/2081800159898525780) (1 个赞，2 条回复，133 次浏览)把 Claude Code、Codex、Hermes Agent 和运行后审查流水线组合在一起，因为没有任何单一界面能独自覆盖记忆、执行和验证。[@pavlenex](https://x.com/pavlenex) [展示了](https://x.com/pavlenex/status/2081759723771097333) (228 个赞，9 条回复，9,530 次浏览，372 次收藏)展示了协作编排的上行空间，但回复里依然有人抱怨耗电、会话上限和 token 用量不透明。

最常见的变通办法，几乎全是“划边界”：运行时拉取密钥，而不是存储密钥；采用单租户部署，而不是共享信任；明确审批记忆写入，而不是静默写入；使用独立审查循环，而不是自我打分。[@vinvan](https://x.com/vinvan) [将其视为](https://x.com/vinvan/status/2081807325526958552) (65 个赞，10 条回复，16,880 次浏览，132 次收藏)把云智能体就绪度描述为一个横跨沙箱、密钥、邮箱和设备模拟器的栈问题；而 [@witcheer](https://x.com/witcheer) [将其转化为](https://x.com/witcheer/status/2081845276005085560) (34 个赞，6 条回复，865 次浏览，16 次收藏)则把 Hermes 的记忆变成一个明确受治理的子系统。

迁移模式正在从单体式提示词转向分层专精。模型选择依然重要，但当天最强的信号表明，持久优势在于上下文组装、路由、可观测性、记忆和证明。因此，竞争格局越来越不像“一个智能体通吃”，而更像栈的分层拆分：Kimi K3 这类前沿模型拼的是成本/性能，MDASH 这类系统拼的是领域框架质量，Hermes 这类 Shell 和 GrokTerm 这类终端宿主拼的是操作者体验，而 AG2 这类框架或 AgentENV 这类运行时，则竞争模型外围的基础设施层。

反复出现最多的构建模式，是“给智能体一个真实的工作场所”。GrokTerm 把终端变成带语音委派的多会话智能体宿主；Nextbrowser 对浏览器配置文件和脚本做了同样的事；Oh My Hermes 则把这一思路用在记忆、技能和操作流程上。这些是彼此独立的项目，但解决的是同一个问题：聊天界面太薄，所以构建者开始围绕模型加上持久化工作空间。

基础设施密集型项目也在向明确边界收敛。AgentENV 优化的是运行时底座，AG2 提供的是长时运行系统的协议与评估层，Acurast 增加的是机密执行加证明，而 George/RareBench 则把基准设计视为通往医疗智能体的路径，而不是附带产物。四者共同之处在于：严肃的构建者在承诺更多自主性之前，先投资于沙箱、评估、证明和可复用控制面。

## 6. 新动态与值得关注的项目

### Open Secure AI Alliance 把智能体安全带入联盟模式

[@NVIDIAAI](https://x.com/NVIDIAAI) [宣布](https://x.com/NVIDIAAI/status/2081666750807171180) (752 个赞，52 条回复，35,377 次浏览)称，其正在向 Open Secure AI Alliance 贡献 NOOA 和其他开放资产。这之所以重要，是因为公开叙事已经从“一家公司的安全姿态”转向“共同的开放防御行动”，并且附带了具体的执行框架研究和共享工具。

### AgentENV 让智能体运行时层成为一个产品类别

### AG2 v1.0 推动开源框架走向 AgentOS 设计

## 7. 机会在哪里

**[+++] Cloud-agent runtime governance** — The strongest direct opportunity is the layer that sits between a long-running agent and real infrastructure. [@vinvan](https://x.com/vinvan) [描述了](https://x.com/vinvan/status/2081807325526958552) 把云智能体就绪度描述为一个横跨工作者基础设施、密钥、邮箱和模拟器的技术栈问题；与此同时，[Infisical 云代理指南](https://infisical.com/blog/secure-secrets-management-for-cursor-cloud-agents)、[Open-Inspect README](https://github.com/ColeMurray/background-agents)，以及 [@Acurast](https://x.com/Acurast) 的 [TEE 演示](https://x.com/Acurast/status/2081769019426718040) 都指向同一个缺失的组合包：受限凭证、沙箱策略、执行证明，以及可审查状态。

**[+++] 持久化智能体工作空间** —— 多个独立构建者都在尝试给智能体一个耐久的工作场所，而不是再加一个漂浮聊天窗口。GrokTerm、Nextbrowser、Voicebox、Hermes Agent 和 Buzz 分别从终端、浏览器、语音、记忆和团队协作切入，这更像强烈的收敛信号，而不是某种偶发的产品偏好。

**[++] Trustworthy skill and memory supply chains** — [@kv1nsiii](https://x.com/kv1nsiii) [展示了](https://x.com/kv1nsiii/status/2081763951293972942) 指出，技能发现已经变成信任和安装质量问题；而 Hermes 与 Oh My Hermes 展示了一种应对方式：审批、整理、角色打包和生命周期管理。这个机会很实在，但也会很卷，因为很多团队都能做出某种“整理过的技能 + 审查”版本。

**[++] 领域框架与基准产品** —— SlopCodeBench、MDASH、RareBench 和 George 都在说明，价值正在转向针对单一任务调优的基准与编排，而不是通用模型接入。这在安全和医疗领域尤其强，因为买方有理由为围绕更窄工作流提供的评估、路由、停止规则和审计轨迹付费。

**[+] Consumer-safe action agents** — [@yashaswini_s_s](https://x.com/yashaswini_s_s) [展示了](https://x.com/yashaswini_s_s/status/2081730466529386707) 展示了一个可信的日常用例：语音订购杂货；Reelful 也为移动视频编辑展示了类似路径。这个信号仍在形成之中，因为产品需求很直观，但控制层——支付上限、审批计划、验证和语音安全——还没有形成标准。

## 8. 要点

1. **智能体质量越来越被理解为运行时架构，而不是提示词技巧。** Harley Foote 对 Claude Code 的总结、Alex Verem 对提示词/上下文/执行框架/循环的拆分，以及 0xRafy 的图工程层，都把持久优势描述为上下文组装、评估和状态管理，而不是更长的提示词。（[来源](https://x.com/harleyfoote_/status/2081816997373845733)）
2. **基准测试正在迅速变得面向领域、面向工作流。** 同一天里，既有 SlopCodeBench 讨论，也有 Microsoft 的 95.95% CyberGym MDASH 成绩，以及用于罕见病诊断的 RareBench 0.1；这异常有力地说明，智能体构建者如今优化的是具名工作负载，而不是通用排行榜。（[来源](https://x.com/rohanpaul_ai/status/2081839571172761607)）
3. **安全讨论已经从模糊的谨慎，转向权限、证明和范围。** 情境化安全框架、PostHog 的“安全带”比喻、Acurast 基于证明的 TEE 执行，以及那条关于批准购物篮的杂货智能体回复，都在追问：谁能授权某个行动，系统又如何证明发生了什么。（[来源](https://x.com/fly51fly/status/2081857231151415591)）
4. **最活跃的构建者，正在围绕智能体打造工作空间，而不只是打造智能体本身。** GrokTerm、Nextbrowser、Voicebox、Hermes 和 Buzz 分别给模型提供了更持久的环境——终端标签、浏览器配置文件、语音 I/O、托管记忆或团队协作——这说明接口层已经成为主要产品战场。（[来源](https://x.com/Daniel_Farinax/status/2081846465992012044)）
5. **云智能体的采用，首先会被运维成熟度卡住，而不是被原始模型能力卡住。** 当天最强的操作者线程之一，是 Vin Van 的云智能体技术栈清单；它也与 Infisical 和 Open-Inspect 关于密钥、快照和租户隔离的外部指导形成呼应。（[来源](https://x.com/vinvan/status/2081807325526958552)）
