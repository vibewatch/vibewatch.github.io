## 1. 人们在讨论什么

### 1.1 Harness Engineering 正在凝聚为一套第一性原理 🡒

[@Vtrivedy10](https://x.com/Vtrivedy10) 的 [8点宣言](https://x.com/Vtrivedy10/status/2052100726608781363)（245 个赞、327 次收藏、14,976 次浏览）在发布第二天继续积累互动，较 5 月 6 日的 81 个赞明显上升。核心论点是：“只要围绕任务来设计 harness，几乎在任何任务上都能胜过任何默认的 harness+模型组合（包括 codex 和 claude code）。”他认为，评测是护城河；前沿闭源模型“对绝大多数任务来说都贵得过头”；而“解耦（再重组）Agent”的时代正在到来——子 Agent 以工具形式暴露，由编排器调度，代其完成特定领域工作。

[@IntuitMachine](https://x.com/IntuitMachine) [已发布](https://x.com/IntuitMachine/status/2052168539180618011)（20 个赞、17 次收藏）发布了一张内容详尽的信息图，总结 OpenAI 关于 harness engineering 的文章，涵盖实验数据（0 行人工编写代码、5 个月约 100 万行代码、合并约 1,500 个 PR）、6 条 agent-first 工程原则、自主循环，以及熵管理。

![Harness engineering 信息图，涵盖实验结果、agent-first 原则、自主循环和熵管理](https://pbs.twimg.com/media/HHrEZYNXEAgbfm0.jpg)

[@itsandrewgao](https://x.com/itsandrewgao) [指出](https://x.com/itsandrewgao/status/2052115991187141054)（11 个赞、2,067 次浏览）表示：“harness engineering 相比基础模型带来的提升，被严重低估了。”[@atin_devs](https://x.com/atin_devs) [宣布](https://x.com/atin_devs/status/2052236616358580570)（17 个赞、11 次收藏）则介绍了一门关于 AI 代码 Agent 上下文工程的 Hugging Face 课程，内容覆盖“skills、MCP、插件、子 Agent、hooks，以及构建 agent harness”。

**讨论洞察：** @BetterSayAJ 在回复 Vtrivedy10 时，将 harness engineering 与经典信息检索联系起来：“这和经典 IR + 系统思维非常接近。模型一旦固定，大部分提升都来自检索、工具和评测循环。”Vtrivedy10 也承认：“我们今天还没有太多复杂的脚手架。一个好的 skill 就能完成绝大多数任务。”

**与前一天的比较：** 5 月 6 日，Vtrivedy10 的宣言和 @oneill_c 的背书，把 harness engineering 从一种技巧提升为一门学科。5 月 7 日则是巩固阶段：同一篇宣言继续扩大传播，源自 OpenAI 的信息图以可视化方式将这些原则正式化，而 Hugging Face 课程则表明 harness engineering 正在成为可教授的课程内容。

### 1.4 多 Agent 编排成为架构层面的核心问题 🡕

多个彼此独立的信号汇聚到同一结论：多 Agent 编排正在成为核心设计挑战。

[@_vmlops](https://x.com/_vmlops) [报道了](https://x.com/_vmlops/status/2052275875882905932)（9 个赞、9 次收藏）介绍了 Microsoft 开源其完整 agent 框架：“基于图的编排、有状态工作流、检查点和人在回路，全都内建其中。支持 Python 和 .NET，包含 devui，从第一天起就接入 OpenTelemetry。工作流支持时间旅行调试。”

[@shannholmberg](https://x.com/shannholmberg) [已发布](https://x.com/shannholmberg/status/2052348003135205621)（25 个赞、25 次收藏）提出了一种在服务型企业中运行自主 agent 员工的四层架构：Human（客户）-> Brain（信任层、战略）-> Orchestrator（运营层、路由）-> Specialists（垂直执行）。关键架构洞察是：“大多数团队会把 brain 和 orchestrator 合并成一个 agent。不要这样做。当同一个 agent 同时负责战略和执行时，两者都会漂移。”

![Client brain 架构图，展示 agency brain、按客户部署的人类-协调者-专家分层，以及信任支柱](https://pbs.twimg.com/media/HHtnocvbEAAdagT.jpg)

[@Aanuraag46](https://x.com/Aanuraag46) [分享了](https://x.com/Aanuraag46/status/2052220473136800093)（33 个赞）发布了一套完整的 9 层 agentic AI 系统参考架构，涵盖编排/控制平面、agent 层、工具、记忆、监控、可靠性、治理和基础设施。

![九层 agentic AI 参考架构，涵盖编排、代理、工具、记忆、监控、可靠性、治理和基础设施](https://pbs.twimg.com/media/HHrzo0ObQAAOI7_.jpg)

**讨论洞察：** @shannholmberg 在线程中提到——“这家 agency 的第一个客户就是它自己。你卖的应该是你真正正在使用的东西。”这表明，最可信的多 Agent 系统，往往出自既是构建者也是用户的一方。

**与前一天的比较：** 5 月 6 日主要通过 Claude Managed Agents 讨论多 Agent 编排。5 月 7 日则把讨论扩展到更广层面：Microsoft 开源企业框架，实践者发布具体分层架构，参考图谱开始流传——这表明多 Agent 正从功能发布走向架构模式。

### 1.5 Voice Agent 流水线开始接受技术性审视 🡒

## 2. 什么让人沮丧

### Token 成本扩张仍然尖锐

[@RoundtableSpace](https://x.com/RoundtableSpace) [演示了](https://x.com/RoundtableSpace/status/2052089764136837184)（89 个赞、68 次收藏、47,354 次浏览）是 5 月 6 日那组 token 成本对比的延续，且互动仍在增长：“之前：1,040 万 tokens、10 个错误、$9.21。之后：370 万 tokens、0 个错误、$2.81。”做法是用 Insforge Skills 替换 Supabase。@NabilChiheb 在回复中提醒：“insforge 很有前景，而且非常……新。真正的成本会在规模化时显现，而不是第一次跑 CLI 的时候。”47K 次浏览和持续被收藏表明，这不是已经解决的问题，而是持续存在的痛点。

### 开放模型的 Harness Engineering 仍缺少足够工具

[@MrAhmadAwais](https://x.com/MrAhmadAwais) [询问](https://x.com/MrAhmadAwais/status/2052063719702855883)（22 个赞、13 次收藏）提出疑问：“为什么每个编程 agent 在开源模型上都这么差？为开源模型做好 harness engineering 并不容易。”[@Vtrivedy10](https://x.com/Vtrivedy10) 则认为，随着团队开始把成本和 ROI 对齐，“Open Model Harness Engineering 还会进一步起飞”，并指出其潜在的“20 倍以上成本下降”。问题在于：现有 harness engineering 工具主要针对前沿闭源模型优化，而把它适配到开放模型需要额外投入，而大多数团队尚未做这项投入。

### Agent 安全攻击已经真实发生

[@SlowMist_Team](https://x.com/SlowMist_Team) [记录了](https://x.com/SlowMist_Team/status/2052282917867643343)（15 个赞、4 次收藏、1,913 次浏览）记录了一起发生在 Base 链上的具体 AI agent 安全事件：“攻击者向 @grok 发送了精心构造的摩尔斯电码消息，诱导其输出转账指令。随后 @bankrbot 直接解析了这段输出。”这不是理论漏洞，而是已被记录的实际利用事件——攻击者用摩尔斯电码这种编码形式实施提示注入，绕过了基于文本的安全过滤器。

### 本地模型硬件门槛仍然过高

[@andrewchen](https://x.com/andrewchen) [记录了](https://x.com/andrewchen/status/2052449121982898315)（34 个赞、37 次收藏）分享了大量一线实测经验：“除非你有一张强化过的 GPU 卡，否则‘大’本地模型（120B+）都很慢，而且效果不如云端 LLM。”他提到 Mac Studio 缺货、5090 eGPU 存在问题，并指出消费级硬件上的本地 AI 模型只有云端模型“1/100 的规模”。@DnuLkjkjh 回复确认：“30 到 50 tok/s 也是我的临界点。低于这个速度，我就不会再用本地模型做交互式编程了。”

## 3. 人们希望出现什么

### 能超越硬编码列表、且可扩展的动态 Skill 路由

[@SynabunAI](https://x.com/SynabunAI) [发现](https://x.com/SynabunAI/status/2052474800270889354) 在回复 RoundtableSpace 的 Find Skills 演示时指出了这一缺口：“动态 skill 路由是大多数构建者都会跳过的那一块。硬编码工具列表在工作流规模小的时候还行，但一旦工作流变大，你编辑的就不再是产品，而是提示词了。”人们需要的是：agent 能在无需手动配置的情况下，从大型 skill 目录中发现并选择能力。

### 能跨越崩溃与会话的 Agent 持久性

[@heygurisingh](https://x.com/heygurisingh) [强调](https://x.com/heygurisingh/status/2052303632713003437)（10 个赞、5 次收藏）介绍了 holaOS：“一个为持续数小时、数天、数周的工作而建的 agent 环境。记忆可持久，状态能跨崩溃保留，agents 还能真正进化。”[@kunallanjewar](https://x.com/kunallanjewar) [构建了](https://x.com/kunallanjewar/status/2052485005008637995)（2 次收藏）介绍了一款会话记忆工具：“我受够了 Claude Code 的使用限制打断我的工作流。每次切到 Cursor/Codex（或开启新会话），新 agent 都是冷启动——不记得之前做过什么、做过哪些决策，或当前有哪些活跃任务。”实际需求很明确：在 agent 之间切换，或撞上限额时，工作上下文依然要连续。

### 面向财务运营的 Agent 原生治理

[@inflowpayai](https://x.com/inflowpayai) [描述了](https://x.com/inflowpayai/status/2052501998151327837)（2 个赞）指出了治理缺口：“一个 agent 想要配置一个 500 美元的 GPU 集群，却无法开户、注册或付款。”真正的难点不在于给 agent 钱包充值，而在于信任、授权和治理。[@lennyzeltser](https://x.com/lennyzeltser) [指出](https://x.com/lennyzeltser/status/2052436164758434005)（3 个赞、2 次收藏）则提到 AIUC-1 证书的出现，这类证书“能提供证据，证明供应商已针对提示注入等 agent 特有风险测试过其 AI agent”。

### Google 推出企业级 Agent 市场

[@googlecloud](https://x.com/googlecloud) [宣布](https://x.com/googlecloud/status/2052463476954599794)（47 个赞、3,104 次浏览）介绍了 Agent Marketplace 现已集成到 Gemini Enterprise 的 Agent Gallery 中，为用户提供“团队所需全部 agents 的统一入口——无论它们是 Google 构建、公司内部创建，还是通过合作伙伴发现的”。这是首个在企业产品内部推出精选 agent 市场的主要云服务提供商。

### 摩尔斯电码提示注入利用了在线 Agent

[@SlowMist_Team](https://x.com/SlowMist_Team) [记录了](https://x.com/SlowMist_Team/status/2052282917867643343)（15 个赞、1,913 次浏览）介绍了 Base 链上的一种新型攻击：攻击者使用摩尔斯电码编码，绕过 AI agent 的文本安全过滤器，诱使 @grok 输出转账指令，并由 @bankrbot 执行。这代表了一类新的提示注入攻击：利用系统对输入编码格式的默认假设。

### antirez 识别出模型分工模式

[@antirez](https://x.com/antirez) [观察到](https://x.com/antirez/status/2052498568070455351)（40 个赞、2,675 次浏览）表示：“GPT 5.5 是一个很强的编程 agent”，而“Claude Opus 的通用性和高质量回复”则很适合给建议。@chufucious 的回复提炼出了正在形成的模式：“对我来说，Opus 负责解释和规划，GPT 负责执行。”按任务类型进行模型分工——而非笼统比较模型优劣——正逐渐成为实践者共识。

### Flutter 和 Dart 发布官方任务导向 Agent Skills

[@adityathakurxd](https://x.com/adityathakurxd) [报道](https://x.com/adityathakurxd/status/2052373166539124819)（11 个赞、7 次收藏）介绍了 Flutter 和 Dart 团队发布官方 Agent Skills，并明确表示，他们“已经从面向文档的 skills 转向面向任务的 skills”。这标志着一种转变：框架团队开始把 agent 能力封装成一等产物，而不再只是文档附录。

## 7. 机会在哪里

**[+++] 面向开放模型的 Harness Engineering 工具。** @Vtrivedy10 认为，“潜在 20 倍以上的成本下降”值得投入。@MrAhmadAwais 指出，每个编程 agent 在“开源模型上都很差”。@andrewchen 也确认，开放权重模型“大约落后一整年”，但正在进步。缺口在于：harness engineering 的最佳实践（skills、评测、上下文优化）都是为前沿闭源模型建立的。谁能把它们迁移到开放模型上，谁就能抓住对成本更敏感的大多数市场。

**[+++] 企业级 agent 市场与治理层。** NVIDIA + ServiceNow 推出了内建治理的 Project Arc；Google 发布了带 Marketplace 的 Agent Gallery；Microsoft 开源了具备检查点和 HITL 的 agent 框架。汇聚趋势很清晰：所有企业平台都在争夺“agent 应用商店”的位置，而治理能力是关键差异化因素。赢家将同时掌握发现与合规。

**[++] 动态 skill 路由与发现。** @SynabunAI 把 skill 路由称为“大多数构建者都会跳过的那一块”。Google 的 Agent Gallery、Flutter 的官方 skills，以及 Claude Code 的 Find Skills，都指向同一个需求：agent 能在无需人工配置的情况下，从不断增长的 skill 目录中发现并选择能力。用于 skill 索引、版本管理和质量信号的工具仍处于早期阶段。

**[++] 防御基于编码的提示注入的 Agent 安全。** @SlowMist_Team 记录的摩尔斯电码攻击表明，当前安全过滤器默认输入是文本格式。随着 agents 开始处理金融操作（AgenC、Costanza、Tread Fi），能够覆盖编码格式攻击、而不只是文本提示注入的安全工具，需求已经十分迫切。

**[+] 面向服务型企业的多层 Agent 架构。** @shannholmberg 的四层框架（Human -> Brain -> Orchestrator -> Specialists），以及她提出的“agency 的第一个客户就是它自己”，暗示这可能成为服务型机构采用 AI 的可复用架构。能把这一模式产品化的工具——客户隔离、信任层、垂直专家配置——将为面向 agency 的平台带来机会。

**[+] 跨会话 agent 记忆与连续性。** @kunallanjewar 因为“每次切换到 Cursor/Codex，新 agent 都会冷启动”而做了工具。@heygurisingh 在推广具备持久状态的 holaOS。@abdiisan 则在使用 Mnemosyne 做跨会话记忆。趋势已经很清楚；但胜出者尚未出现。

## 8. 要点

1. **Hermes Agent v0.13.0 引入了基于看板的多 Agent 编排，是当天信号最强的发布。** 330 个赞、78K 次浏览，以及 Autobrowse 的效率数据（成本下降 3 倍）验证了这套架构。Hermes 正从 agent 演进为操作系统。（[来源](https://x.com/Teknium/status/2052495174404874714)）

2. **企业级 Agent 基础设施正在收敛到“治理优先”的架构。** NVIDIA + ServiceNow（Project Arc + OpenShell）、Google（Agent Gallery + Marketplace）和 Microsoft（开源 agent 框架）在同一天都推出了企业级 agent 平台——差异化点不在模型能力，而在治理与可审计性。（[来源](https://x.com/nvidia/status/2052146387681259653)）

3. **Harness engineering 正在成为课程体系，而不只是手艺。** Hugging Face 课程、源自 OpenAI 的可视化参考资料，以及 @Vtrivedy10 互动持续增长的宣言，共同表明 harness engineering 已具备可教授的知识基础——5 月 6 日被确立为一门学科后，如今已开始形成相应的教育基础设施。（[来源](https://x.com/atin_devs/status/2052236616358580570)）

4. **一场针对管理资金的在线 agent 的摩尔斯电码提示注入攻击表明，编码格式攻击已是真实且紧迫的威胁。** 当前安全过滤器默认输入是文本；@SlowMist_Team 记录的事件表明，攻击者已经在用替代编码方式绕过这些过滤器。Agent 安全必须覆盖格式多样性，而不只是内容过滤。（[来源](https://x.com/SlowMist_Team/status/2052282917867643343)）

5. **多 Agent 架构正围绕职责分离这一原则收敛。** @shannholmberg 的四层模型（Human/Brain/Orchestrator/Specialists）、Microsoft 的图式编排，以及 Hermes 的看板系统，都指向同一原则：一旦把战略与执行压进同一个 agent，二者都会退化。（[来源](https://x.com/shannholmberg/status/2052348003135205621)）

6. **语音 Agent 流水线的延迟预算已成为公开的工程知识。** @manthanguptaa 的流水线图量化了从 VAD（100-300ms）到 TTS（100-300ms）的每一个环节，总延迟为 700ms-1.95s。结合 @kwindla 在 GTC 的生产验证，以及 @gothburz 对口音协调伦理问题的追问，语音 agents 正进入工程精度与社会影响交汇的阶段。（[来源](https://x.com/manthanguptaa/status/2052241815974330453)）
