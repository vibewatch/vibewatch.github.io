## 1. 人们在讨论什么

### 1.1 Harness 工程成为构建可靠智能体的共同语言 🡕

Harness 工程仍是当天最明确的讨论重心，但相关证据已从零散技巧转向公开课程、设计指南和可复用的运行闭环。最有分量的帖子都把智能体视为需要状态、验证、可观测性、恢复机制、权限和责任归属的系统，而不只是更聪明的提示词。相比 5 月 17 日，当时关于 Harness 的讨论已聚焦课程和生产闭环；到 5 月 18 日，讨论进一步扩展到更明确的设计产物和企业推广角色。

[@_vmlops](https://x.com/_vmlops) [分享了](https://x.com/_vmlops/status/2055887618303570151)（2,034 个赞、11 条回复、119,999 次浏览、3,479 次收藏）[学习 Harness Engineering](https://walkinglabs.github.io/learn-harness-engineering/en/) 课程。页面称，该课程讲授环境设计、状态管理、验证、可观测性，以及面向 Codex 和 Claude Code 类智能体的控制系统；这张截图之所以重要，是因为课程目录围绕具体故障模式来组织：连续性丢失、过早宣布成功、缺少可观测性，以及端到端测试改变结果。

### 1.4 怀疑情绪集中在安全性、分布外失败和模型价格取舍 🡒

当天并非一边倒看多。最强烈的怀疑来自具体失败报告：编码智能体无法构建儿童火箭模拟器；仅靠提示词的安全防护看起来很薄弱；MIT 展示了针对当前模型的提示词注入；Cursor Composer 2.5 则引发了速度与智能之间的争论。

[@omarsar0](https://x.com/omarsar0) [报道了](https://x.com/omarsar0/status/2056392467604205852)（60 个赞、28 条回复、14,785 次浏览、16 次收藏）称，当要求编码智能体构建火箭模拟器等以科学为核心的模拟器时，它们一再让他 10 岁的孩子失望。在回复中，他表示自己尝试过提示辅助和上下文工程技巧，但智能体仍然连半成品的二维模拟器都做不出来。他的结论较为克制，也有证据支撑：编码智能体更擅长扩展训练数据中大量存在的模式，而不擅长处理分布外的创造性模拟器任务。

[@RoundtableSpace](https://x.com/RoundtableSpace) [发布了](https://x.com/RoundtableSpace/status/2056423320745050304)（53 个赞、9 条回复、38,508 次浏览、36 次收藏）发布了一条很长的“安全优先智能体”提示词，涵盖提示词注入、越狱、数据外泄、最小权限和不安全的工具使用。回复立即分化：有人说几乎没人真正保护智能体；[@bygregorr](https://x.com/RoundtableSpace/status/2056423320745050304) 质问安全是否只是“系统提示词里的氛围”；[@sanarsh11](https://x.com/RoundtableSpace/status/2056423320745050304) 则称这是“纸盾上的提示词护甲”。

[@anishathalye](https://x.com/anishathalye) [表示](https://x.com/anishathalye/status/2056395987133018263)（27 个赞、3 条回复、1,692 次浏览、20 次收藏）称，MIT CSAIL 的一场客座讲座成功演示了针对 Anthropic Opus 4.6 模型的提示词注入，并得出结论：智能体安全仍未解决。他在回复中表示，完整讲座涵盖 ReAct、CodeAct、智能体安全、Simon Willison 的双 LLM 模式，以及 CaMeL 的能力系统。

[@minchoi](https://x.com/minchoi) [描述了](https://x.com/minchoi/status/2056473491210403993)（33 个赞、14 条回复、5,962 次浏览、8 次收藏）介绍了 Cursor Composer 2.5，称其价格更低，并且面向长时间运行的智能体工作。一位测试者给出了有价值的回复：Composer 2.5“快得惊人”，性价比扎实，但智能程度仍无法匹敌 Opus 或 GPT-5.5，而且仍会犯“低级错误”。

**讨论洞察：** 关于安全的回复异常直接。凡是提出提示词防御的帖子，都会立刻遭到质疑：仅靠提示词无法阻止数据外泄或多语言泄漏。整体模式并不是反对智能体，而是反对没有验证的主张。

**与前一天相比：** 5 月 17 日已经出现了对恶意智能体供应链的警告；5 月 18 日，怀疑情绪进一步扩展到提示词注入演示、对仅靠提示词防御的批评、分布外编码失败，以及针对具体模型的取舍。

## 2. 什么让人感到挫败

### 可靠的智能体需要责任归属，而不只是更好的模型

严重程度：高。[@dani_avila7](https://x.com/dani_avila7/status/2056181617249390740) [表示](https://x.com/dani_avila7/status/2056181617249390740)（52 个赞、4 条回复、21,387 次浏览、58 次收藏）指出，当没有人负责配置、权限、技能和规范时，企业部署 Claude Code 就会撞上同一堵墙。[@code_rams](https://x.com/code_rams/status/2056357878194131357) [列出了](https://x.com/code_rams/status/2056357878194131357)（5 个赞、4 条回复、415 次浏览、14 次收藏）将约束、状态、验证、可观测性、模块化结构、干净状态协议和行为约束列为 Harness 的必要组件。当前出现的应对方式是设置专门的 Agent Manager/DRI，并加入规范门控，但这一运营层面的需求仍未解决。

### 智能体安全既迫切，又明显尚未建好

严重程度：高。[@anishathalye](https://x.com/anishathalye/status/2056395987133018263) [展示了](https://x.com/anishathalye/status/2056395987133018263)（27 个赞、3 条回复、1,692 次浏览、20 次收藏）介绍了 MIT CSAIL 讲座中针对 Opus 4.6 的提示词注入；[@RoundtableSpace](https://x.com/RoundtableSpace/status/2056423320745050304) [传播了](https://x.com/RoundtableSpace/status/2056423320745050304)（53 个赞、9 条回复、38,508 次浏览、36 次收藏）则介绍了一条被回复批评为不够充分的安全提示词。[@DarkWebInformer](https://x.com/DarkWebInformer/status/2056469586724221262) [分享了](https://x.com/DarkWebInformer/status/2056469586724221262)（9 个赞、2 条回复、2,101 次浏览、17 次收藏）介绍了 Pentest Agents，但一条回复警告，静态智能体脚本可能会幻觉出发现，而不是证明漏洞利用路径。当前的应对模式是分层防护：提示词、最小权限、能力系统、漏洞利用证明和人工审核。

### 编码智能体仍会在分布外的创造性任务上令人失望

严重程度：中。[@omarsar0](https://x.com/omarsar0/status/2056392467604205852) [表示](https://x.com/omarsar0/status/2056392467604205852)（60 个赞、28 条回复、14,785 次浏览、16 次收藏）称，即便有成人的提示辅助和上下文工程，编码智能体仍无法完成他孩子的火箭模拟器及相关科学模拟任务。令人挫败的并不是智能体完全没有帮助；他明确表示，智能体很擅长维护和扩展训练数据中有充分代表性的软件模式。真正的缺口在于，当目标行为缺乏模板时，智能体难以在相关领域进行泛化创作。

### 智能体商业中的信任仍跑在结算基础设施前面

严重程度：高。[@Onyx_goose](https://x.com/Onyx_goose/status/2056391106502271068) [认为](https://x.com/Onyx_goose/status/2056391106502271068)（57 个赞、48 次转发、5 条回复、129 次浏览）称，智能体商业需要 x402B 托管，因为自主参与方可能彼此并不认识。[@tetsuoai](https://x.com/tetsuoai/status/2056261530447225188) [描述了](https://x.com/tetsuoai/status/2056261530447225188)（86 个赞、9 条回复、3,976 次浏览、15 次收藏）介绍了 AgenC 的市场通路和基于证明的完成机制；一条回复追问原生智能体间支付是否已经存在。当前的应对方式是条件式托管、可审查产物和链上协调，但回复显示，信任仍是一个尚待解决的落地问题。

### 工具栈正在分裂为技能、记忆、聊天和工作区

严重程度：中。[@tom_doerr](https://x.com/tom_doerr/status/2056145133544824838) [分享了](https://x.com/tom_doerr/status/2056145133544824838)（22 个赞、6 条回复、1,751 次浏览、21 次收藏）介绍了 OpenSkills，而回复立即开始担心通用技能是否会变成“多工具噩梦”。[@mercury__agent](https://x.com/mercury__agent/status/2056297450328219993) [不得不解释](https://x.com/mercury__agent/status/2056297450328219993)（176 个赞、9 条回复、1,040 次浏览）称，`/code plan` 本身并不是价值所在，真正重要的是可追踪的 Git 原生闭环。问题在于可发现性和系统集成：用户想要可复用技能，但不想要上下文膨胀，也不想再多一个孤立运行时。

## 3. 人们希望出现什么

### 真正负责企业编码智能体的负责人和控制平面

人们希望为 Claude Code 类部署提供一个实用的运营角色和控制界面。[@dani_avila7](https://x.com/dani_avila7/status/2056181617249390740)（52 个赞、21,387 次浏览、58 次收藏）将这一角色称为 Agent Manager，负责配置、权限、市场选择和规范。机会：直接。团队已经在部署智能体，但责任归属尚不明确，因此这一需求既实际又迫切。

### 能守住目标、不让智能体重定义完成标准的 Harness

[@code_rams](https://x.com/code_rams/status/2056357878194131357)（5 个赞、415 次浏览、14 次收藏）希望具备约束、状态、验证、可观测性、干净状态和行为限制；[@nicolasmoute](https://x.com/code_rams/status/2056357878194131357) 的回复补充了规范门控，使规划器无法悄悄重写目标。机会：直接。现有 Harness 模板已部分解决这一问题，但“规划器重定义完成标准”的故障模式需要明确的产品支持。

### 可信的智能体商业基础设施

[@Onyx_goose](https://x.com/Onyx_goose/status/2056391106502271068)（57 个赞、48 次转发）要求类似 x402B 的托管；[@tetsuoai](https://x.com/tetsuoai/status/2056261530447225188)（86 个赞、3,976 次浏览）描述了基于证明的完成机制；[@termix_ai](https://x.com/termix_ai/status/2056244127516565549)（43 个赞、8,130 次浏览）则提供了显示市场活跃度的交易指标。机会：直接且竞争激烈。许多项目已经在解决身份、托管、证明和结算问题，但回复仍在追问支付和验证究竟如何运作。

### 不只是带着防御性提示词的安全智能体

[@RoundtableSpace](https://x.com/RoundtableSpace/status/2056423320745050304)（53 个赞、38,508 次浏览、36 次收藏）提供了一条安全提示词，但回复认为它薄弱不堪。[@anishathalye](https://x.com/anishathalye/status/2056395987133018263)（27 个赞、1,692 次浏览、20 次收藏）在演示提示词注入后，指向讲座中提到的能力系统和双 LLM 模式。机会：直接。市场需要的是可测试、可执行的安全边界，而不是措辞更谨慎的提示词。

### 面向非标准创造性任务的更好基准和 Harness

[@omarsar0](https://x.com/omarsar0/status/2056392467604205852)（60 个赞、14,785 次浏览、16 次收藏）把火箭模拟器失败视为通用 Harness 的证据，并认为最终可能需要原生多模态系统或世界模型。机会：远期。需求真实存在，但当前工具似乎更擅长维护和扩展常见软件模式，而不是创建陌生的模拟器。

## 8. 要点

1. **Harness 工程再次成为智能体领域的主导话题，但它正逐渐变成组织基础设施。** 当天最有力的证据包括一门被广泛收藏的课程、一套 Hermes 部署闭环、一份设计指南，以及一个 Agent Manager 推广角色。（[来源](https://x.com/_vmlops/status/2055887618303570151)）
