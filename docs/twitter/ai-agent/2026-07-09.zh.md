# Twitter AI Agent - 2026-07-09

## 1. 大家在讨论什么

### 1.1 基准测试的焦点从模型之争转向支架经济学 🡕

7 月 9 日最集中的讨论，并不只是哪个模型更聪明，而是哪种“模型 + 支架”组合，能以什么成本、在多大操作摩擦下，为每项任务交付最佳结果。至少有五条不同内容，把讨论从排行榜炫耀推向了成本、路由和工作流设计。

[@danshipper](https://x.com/danshipper) [认为](https://x.com/danshipper/status/2075263920613277809)（649 个赞、42 条回复、108,379 次浏览、395 次收藏）表示，GPT-5.6 Sol 比 Claude Fable 5 更便宜、更快、更易用，但在最难的编程任务上仍落后于 Fable：在一项内部高级工程师基准测试中，他的团队给 Sol 打出 56/100，而 Fable 为 91/100。其独特角度是运营层面的，而非立场之争。他建议把 Sol 作为 Fable 的子代理使用；一条回复则指出，更重要的产品变化其实是工作流压缩——当聊天、仓库状态、浏览器检查和评审都集中在同一个桌面界面里，流程就会大幅缩短。

[@ArtificialAnlys](https://x.com/ArtificialAnlys) [报道](https://x.com/ArtificialAnlys/status/2075268970492657905)（674 个赞、22 条回复、34,448 次浏览、105 次收藏）指出，GPT-5.6 Sol 在其 Intelligence Index 上只比 Claude Fable 5 低 1 分，但单任务成本约为后者的三分之一；同时，Codex 中的 Sol 以 80 分位居其 Coding Agent Index 首位。配图之所以重要，是因为它把这种权衡直观展示了出来：通用智能接近持平，Sol 在 Codex 内部的编码代理排名更高，而成本曲线则明显不同。

![Artificial Analysis 图表：比较 GPT-5.6 Sol、Claude Fable 5 和其他前沿模型在智能与代码代理指标上的表现](https://pbs.twimg.com/media/HMzL8WEbIAEUrM7.jpg)

[@databricks](https://x.com/databricks) [表示](https://x.com/databricks/status/2074982580626051240)（23 个赞、1,682 次浏览）表示，其基于一个数百万行代码库的真实任务基准测试发现，Token 定价并不是现实成本的好代理指标；开源模型和闭源模型都出现在第一梯队；而支架选择会显著改变价格与质量。与常见的模型发布帖相比，这一说法更有分量，因为它基于真实工程任务，而不是简短的合成提示。

![Databricks 散点图：展示在真实工程任务中，不同模型和 harness 的代码代理成本与性能出现分化](https://pbs.twimg.com/media/HMvRpOwXYAAU1zk.jpg)

[@RoundtableSpace](https://x.com/RoundtableSpace) [声称](https://x.com/RoundtableSpace/status/2075010796052992434)（48 个赞、15 条回复、45,057 次浏览）表示，一套名为 Ponytail 的写入前门控系统，通过强制模型先问三个问题——这个功能是否已经存在、是否可以用某个库解决、最小可行代码改动是什么——将 Token 使用量降低 20%，并把终端执行速度提升 27%。[@Vtrivedy10](https://x.com/Vtrivedy10) [补充道](https://x.com/Vtrivedy10/status/2074914320211734763)（20 个赞、1,319 次浏览、21 次收藏）则给出了同一逻辑的企业版：先做支架工程，只有撞到天花板之后再考虑微调；模型一变，再回到支架工程。

**讨论洞察：** 回复里的重点更多是工作流形态、项目隔离、Token 消耗和任务适配，而不是对前沿模型的原始崇拜。读者想弄清的是，如何高效购买智能，而不只是欣赏智能。

**与前一天对比：** 7 月 8 日已经把支架与循环工程视为性能提升的关键所在。到了 7 月 9 日，讨论又向前推进了一步，落到单任务成本图表、真实代码库基准测试，以及明确的门控启发式方法上。

### 1.2 外部验证器与纠错记忆成为产品闭环的一部分 🡕

第二组讨论把自我改进视为一个系统问题：记录用户纠正了什么，用代理之外的机制给轨迹打分，并重写失败的组件，而不是指望模型下次“自己做得更好”。至少有四条内容从不同角度提供了证据。

[@clairevo](https://x.com/clairevo) [展示了](https://x.com/clairevo/status/2074935469381722154)（203 个赞、10 条回复、19,864 次浏览、268 次收藏）介绍了一个用 ClaudeDevs SDK 构建的定制支架，用于分流 Sentry bug、验证根因并交付修复。真正有用的部分不是“关键在支架，不在模型”这句口号，而是那条具体流水线：接收 bug、验证、然后发布修复。一条回复把支架进一步概括为“除了引擎之外的一切”；另一条则提醒，过度外包判断本身也可能成为一种失败模式。

[@free_ai_guides](https://x.com/free_ai_guides) [梳理了](https://x.com/free_ai_guides/status/2075268642833674718)（9 个赞、464 次浏览、12 次收藏）介绍了一个自学习闭环：代理既从自己的执行轨迹中学习，也从用户修复中学习，然后把经验存成事实、案例和规则。配图是关键证据，因为它把记忆模型明确画了出来，也让闭环的控制权保持在代理之外。

![自学习循环示意图：展示 trace 信号、用户修复信号、事实/案例/规则记忆，以及主导学习过程的外循环](https://pbs.twimg.com/media/HMzV1QZaMAA2-dL.jpg)

[@jackyk02](https://x.com/jackyk02) [介绍了](https://x.com/jackyk02/status/2074969820739805275)（32 个赞、3 条回复、70,251 次浏览）介绍了 LLM-as-a-Verifier：通过更细粒度的评分、score token 的对数概率，以及重复评估，为测试时扩展、强化学习和监控提供更强信号。配图之所以重要，是因为它公布了具体基准数字，包括 Terminal-Bench V2 上的 86.5% 和 SWE-Bench Verified 上的 78.2%，而不是把“验证”停留在抽象建议层面。

![LLM-as-a-Verifier 基准卡片：展示 Terminal-Bench V2、SWE-Bench Verified、RoboRewardBench 和 MedAgentBench 的主要分数](https://pbs.twimg.com/media/HMvFN6qbMAA6FeR.jpg)

[@ArchiveExplorer](https://x.com/ArchiveExplorer) [总结](https://x.com/ArchiveExplorer/status/2075224914357891333)（17 个赞、3 条回复、954 次浏览、14 次收藏）介绍了一篇复旦大学的支架工程论文：每个工具、提示词和技能都变成可观测契约；外循环会重写失败的组件；一旦出现回归，系统就会自动回滚。其独特之处在于，模型权重保持冻结，真正持续改进的是工具、中间件、记忆和技能文件。

**讨论洞察：** 共同模式是，闭环的拥有者在代理之外。有时这个拥有者是验证器，有时是记忆层，有时则是只编辑支架中损坏部分的第二个代理。

**与前一天对比：** 7 月 8 日反复强调，验证必须独立于指令。到了 7 月 9 日，这一原则已经具体化为记忆分类法、验证器评分卡和基于契约的重写闭环。

### 1.3 技能更像可复用基础设施，而不是提示词技巧 🡕

围绕“技能”的讨论继续远离巨型提示词，转向可移植、可安装、可独立维护的专业能力单元。证据来自开源仓库、厂商目录和一次主流框架发布。

[@dotnetfdn](https://x.com/dotnetfdn) [宣布](https://x.com/dotnetfdn/status/2075213634981056811)（4 个赞、385 次浏览）表示，Agent Skills for .NET 已走出实验性预览阶段。微软的公开帖子称，代理现在可以通过稳定 API，只在需要时加载指令、参考文档和脚本，用渐进式披露保持上下文精简。

**讨论洞察：** 底层转变是从始终在线的提示词，转向按需加载的能力。重点不在提示词花样，而在复用、版本管理和打包。

**与前一天对比：** 7 月 8 日强调的是注册表和发现机制。7 月 9 日则显示，这个思路正在固化为框架 API 和人们积极组合使用的开源仓库。

### 1.4 围绕代理的操作界面持续扩展为产品 🡕

## 2. 哪些问题令人沮丧

### 成本控制仍取决于支架纪律，而不只是模型选择

严重程度：高。[@ArtificialAnlys](https://x.com/ArtificialAnlys) [展示了](https://x.com/ArtificialAnlys/status/2075268970492657905)（674 个赞、22 条回复、34,448 次浏览、105 次收藏）指出，GPT-5.6 Sol 可以用低得多的成本逼近 Claude Fable 5，但 [@danshipper](https://x.com/danshipper) [仍然发现](https://x.com/danshipper/status/2075263920613277809)（649 个赞、42 条回复、108,379 次浏览、395 次收藏）显示，它在更难任务上的编程质量差距仍然很大。[@databricks](https://x.com/databricks) [补充道](https://x.com/databricks/status/2074982580626051240)（23 个赞、1,682 次浏览）指出，Token 定价并不是现实成本的好代理指标；而 [@RoundtableSpace](https://x.com/RoundtableSpace) [将其定义为](https://x.com/RoundtableSpace/status/2075010796052992434)（48 个赞、15 条回复、45,057 次浏览）则从操作层面点出了痛点：顶级模型默认会重写过多内容，于是团队不得不加装写入前门控，只为阻止浪费。人们的应对方式，是先做子代理路由、写前检查和支架调优，之后才考虑微调。之所以值得围绕这个问题构建产品，是因为这种挫败感同时出现在基准帖子和从业者回复里。

### 团队仍难以记录纠正内容，也难以证明修复确实生效

严重程度：高。[@free_ai_guides](https://x.com/free_ai_guides) [表示](https://x.com/free_ai_guides/status/2075268642833674718)（9 个赞、464 次浏览、12 次收藏）指出，大多数团队会保留执行轨迹，却丢掉用户的纠正编辑；而 [@jackyk02](https://x.com/jackyk02) [提出了](https://x.com/jackyk02/status/2074969820739805275)（32 个赞、3 条回复、70,251 次浏览）则展示了一个更重型的验证器栈，用来从代理行为中提取更丰富信号。[@clairevo](https://x.com/clairevo) [做出了](https://x.com/clairevo/status/2074935469381722154)（203 个赞、10 条回复、19,864 次浏览、268 次收藏）则通过把验证直接嵌入 Sentry bug 修复支架，从操作层面体现了同一点；[@ArchiveExplorer](https://x.com/ArchiveExplorer) [描述了](https://x.com/ArchiveExplorer/status/2075224914357891333)（17 个赞、3 条回复、954 次浏览、14 次收藏）介绍的一篇论文中，损坏的支架组件会被重写，并在出现回归时自动回滚。构建者正在用外部评估器、记忆分类法和明确的通过/失败契约来应对。之所以值得围绕这个问题构建产品，是因为一旦纠正内容消失，或成功无法被独立验证，信任就会崩塌。

### 技能复用正在改善，但打包仍然碎片化

严重程度：中。[@MengTo](https://x.com/MengTo) [不得不结对合作](https://x.com/MengTo/status/2075221793925955897)（21 个赞、2 条回复、2,023 次浏览、35 次收藏）提到两个分别覆盖设计工程和编排的技能仓库，[@dotnetfdn](https://x.com/dotnetfdn) [宣布](https://x.com/dotnetfdn/status/2075213634981056811)（4 个赞、385 次浏览）提到稳定版 Agent Skills API for .NET，[@DivyanshT91162](https://x.com/DivyanshT91162) [指出](https://x.com/DivyanshT91162/status/2075060803410210817)（5 个赞、1 条回复、357 次浏览）则提到 NVIDIA 独立的已验证技能目录。好消息是，打包方式已经出现；令人沮丧的是，专业能力如今分散在仓库、框架 API 和厂商目录中，各自有不同的安装路径和治理规则。之所以值得围绕这一点构建产品，是因为趋势显然正转向可复用技能，但发现和互操作性仍不均衡。

### 代理在需要安全触达现实世界时仍会停滞

严重程度：高。[@Freyabuilds](https://x.com/Freyabuilds) [抱怨](https://x.com/Freyabuilds/status/2075241534195458445)（70 个赞、14 条回复、7,636 次浏览）指出，一旦代理需要托管网站、发送邮件、抓取页面或收款，它们就不再显得神奇，因为人类仍得去追着处理密钥、订阅和配置。[@circle](https://x.com/circle) [从构建者角度作出回应](https://x.com/circle/status/2075293913523372117)（108 个赞、16 条回复、8,814 次浏览）给出了钱包和 USDC 支付入门套件，但回复立刻追问：Gas 费用到底该由谁承担？[@shieldzcash](https://x.com/shieldzcash) [提出了](https://x.com/shieldzcash/status/2075313680883847325)（2 个赞、31 次浏览）提到一个无密钥支付 API，而 [@tom_doerr](https://x.com/tom_doerr) [分享了](https://x.com/tom_doerr/status/2075096548115882071)（3 个赞、1,921 次浏览、5 次收藏）则提到一个专门针对 AI 代理风险的安全扫描器。人们当前的应对方式，是使用入门套件、代理可读的仪表板，以及上线前先扫描的工作流。之所以值得围绕这个问题构建产品，是因为如今自主性更常在执行、花费和安全边界上失灵，而不只是推理能力不足。

## 3. 大家希望有什么产品

### 成本感知的路由与预检策略层

这一需求体现为现实中的工作流缺口，而不是理论问题。[@danshipper](https://x.com/danshipper) [描述了](https://x.com/danshipper/status/2075263920613277809)（649 个赞、42 条回复、108,379 次浏览、395 次收藏）展示了这样一种现实：GPT-5.6 Sol 对许多循环来说已经够用，但不适合最难的编程任务；[@ArtificialAnlys](https://x.com/ArtificialAnlys) [量化了](https://x.com/ArtificialAnlys/status/2075268970492657905)（674 个赞、22 条回复、34,448 次浏览、105 次收藏）展示了不同推理层级之间的成本差异；[@RoundtableSpace](https://x.com/RoundtableSpace) [提出了](https://x.com/RoundtableSpace/status/2075010796052992434)（48 个赞、15 条回复、45,057 次浏览）则展示了一个在生成开始前减少浪费的人工门控框架。人们似乎想要的是一个可复用层：决定何时上切、何时下切，以及模型消耗 Token 之前必须通过哪些检查。机会评级：[+++] 直接。

### 能跨越单次运行持续存在的纠错记忆与验证器层

最强烈的未满足需求，是从错误中进行持久学习。[@free_ai_guides](https://x.com/free_ai_guides) [表示](https://x.com/free_ai_guides/status/2075268642833674718)（9 个赞、464 次浏览、12 次收藏）指出，用户的修复通常不会被记录；[@jackyk02](https://x.com/jackyk02) [展示了](https://x.com/jackyk02/status/2074969820739805275)（32 个赞、3 条回复、70,251 次浏览）表明，更丰富的验证器信号能显著改善代理评估；[@ArchiveExplorer](https://x.com/ArchiveExplorer) [描述了](https://x.com/ArchiveExplorer/status/2075224914357891333)（17 个赞、3 条回复、954 次浏览、14 次收藏）则介绍了一个只重写失败契约、并在回归时自动回滚的支架。缺失的产品不是抽象意义上“更多记忆”，而是一个记忆 + 验证层：存储修复内容、给行为打分，并决定下一步应该改什么。机会评级：[+++] 直接。

### 跨生态可用的可移植技能打包

技能趋势如今已经足够明确，以至于人们开始希望有一种通用分发模式。[@MengTo](https://x.com/MengTo) [好坏参半](https://x.com/MengTo/status/2075221793925955897)（21 个赞、2 条回复、2,023 次浏览、35 次收藏）展示了覆盖不同工作类型的两个独立仓库；[@dotnetfdn](https://x.com/dotnetfdn) [宣布](https://x.com/dotnetfdn/status/2075213634981056811)（4 个赞、385 次浏览）展示了按需加载技能的稳定 .NET 格式；[@DivyanshT91162](https://x.com/DivyanshT91162) [指出](https://x.com/DivyanshT91162/status/2075060803410210817)（5 个赞、1 条回复、357 次浏览）则展示了 NVIDIA 的已验证目录。实际愿望很明显：专业能力打包一次、轻松发现、无需为每个框架重新改写即可安装。机会评级：[++] 竞争型。

### 具备明确支出归属的现实世界行动护栏

这里的需求一半是技术问题，一半是运营问题。[@Freyabuilds](https://x.com/Freyabuilds) [详细说明了](https://x.com/Freyabuilds/status/2075241534195458445)（70 个赞、14 条回复、7,636 次浏览）指出，那些枯燥任务代理仍会交还给人类；[@circle](https://x.com/circle) [开放了](https://x.com/circle/status/2075293913523372117)（108 个赞、16 条回复、8,814 次浏览）提到钱包和 USDC 支付入门套件；[@shieldzcash](https://x.com/shieldzcash) [发布了](https://x.com/shieldzcash/status/2075313680883847325)（2 个赞、31 次浏览）则提到一个无密钥支付 API，可返回支付链接和代理可读的仪表板。回复里仍在追问那个尚未解决的问题：每个动作到底由谁买单，支出可见性又如何？机会评级：[++] 直接。

### 面向多代理工作的受治理操作界面

人们似乎也希望有一层位于代理之上的监督工具。[@gabegreenberg](https://x.com/gabegreenberg) [预览了](https://x.com/gabegreenberg/status/2075043758211555477)（3 个赞、418 次浏览）将 ORC 描述为一个受治理的多代理编码平台；[@trySynara](https://x.com/trySynara) [已上线](https://x.com/trySynara/status/2075042082876518499)（13 个赞、4 条回复、2,245 次浏览、12 次收藏）提到一个更可见的非编码代理工作区；[@tom_doerr](https://x.com/tom_doerr) [将其定义为](https://x.com/tom_doerr/status/2075096548115882071)（3 个赞、1,921 次浏览、5 次收藏）则把安全扫描提升为发布前的一等步骤。这与其说是在希望“更自主的代理”，不如说是在希望更好的界面，用来查看、审查、批准和恢复代理做过的事。机会评级：[++] 竞争型。

## 7. 机会在哪里

**[+++］ 成本感知型 harness 控制平面** —— 目前最有力的证据来自三个不同方向：［@danshipper](https://x.com/danshipper/status/2075263920613277809) 把 Sol 与 Fable 放到真实工作里比较，[@ArtificialAnlys](https://x.com/ArtificialAnlys/status/2075268970492657905) 公布单任务成本差异，[@databricks](https://x.com/databricks/status/2074982580626051240) 展示支架选择会如何改变真实代码库上的经济性。[@RoundtableSpace](https://x.com/RoundtableSpace/status/2075010796052992434) 则补上了一个具体的预检模式。这一方向很强，因为痛点广泛存在，而且应对模式已经相当清晰。

**[+++］ 验证器加纠错记忆层** —— ［@free_ai_guides](https://x.com/free_ai_guides/status/2075268642833674718)、[@jackyk02](https://x.com/jackyk02/status/2074969820739805275)、[@clairevo](https://x.com/clairevo/status/2074935469381722154) 和 [@ArchiveExplorer](https://x.com/ArchiveExplorer/status/2075224914357891333) 都指向同一个缺失层：记录用户修复了什么，在外部给轨迹打分，并且只重写失败的部分。这一方向很强，因为它能同时提升信任、学习和控制。

**[++］ 跨框架技能打包与发现** —— ［@MengTo](https://x.com/MengTo/status/2075221793925955897)、[@dotnetfdn](https://x.com/dotnetfdn/status/2075213634981056811) 和 [@DivyanshT91162](https://x.com/DivyanshT91162/status/2075060803410210817) 表明，可复用技能已经成为现实，但仍然分散在仓库、框架和厂商目录之间。这一方向强度中等，因为需求很明确，但分发标准和发现层可能很快会变得拥挤。

**[++］ 原生面向代理的操作与支付通道** —— ［@circle](https://x.com/circle/status/2075293913523372117)、[@shieldzcash](https://x.com/shieldzcash/status/2075313680883847325) 和 [@Freyabuilds](https://x.com/Freyabuilds/status/2075241534195458445) 都指向推理与执行之间的同一个断点。这一方向强度中等，因为需求具体，但支出归属、合规和用户信任仍是悬而未决的问题。

**[+］ 治理优先的运营者工作区** —— ［@gabegreenberg](https://x.com/gabegreenberg/status/2075043758211555477)、[@trySynara](https://x.com/trySynara/status/2075042082876518499) 和 [@tom_doerr](https://x.com/tom_doerr/status/2075096548115882071) 展示了一类不断增长的产品：围绕审查门、diff 可见性、恢复行为和安全扫描构建。这一方向仍在萌芽期，因为这些界面的需求已经非常明确，但产品本身还早，公开采用信号也更弱。

## 8. 要点总结

1. **购买决策已从“最佳模型”转向“最佳支架经济性”。** GPT-5.6 Sol 发布日的讨论不断回到单任务成本、路由和工作流适配，而不只是原始智能水平。（[来源](https://x.com/ArtificialAnlys/status/2075268970492657905)）
2. **在严肃的代理闭环中，外部验证已不再是可选项。** 当天最有力的自我改进帖子，都依赖模型之外的评估器、根因检查或契约级通过/失败信号。（[来源](https://x.com/jackyk02/status/2074969820739805275)）
