# Twitter AI Agent - 2026-07-12

## 1. 大家在讨论什么

### 1.1 Harness 卫生取代了模糊的提示词建议 🡕

7 月 12 日最密集的一组讨论，把 agent 质量视为一种运行纪律：定义循环、精简技能列表、按通道路由模型，并在生成代码前强制先做规划。共有 8 条高信号内容支撑了这一趋势，其中几条还指出，真正的瓶颈不是生成更多 token，而是决定该加载什么、何时算完成，以及哪些内容需要审查。

[@MengTo](https://x.com/MengTo) [表示](https://x.com/MengTo/status/2076121220605686086)（122 次点赞、13 条回复、14,807 次浏览、137 次收藏）表示，他现在会给 agent 开放式目标，让 GPT-5.6 Sol 将其拆解为 20 多个具体步骤，然后让每个步骤都在独立线程中运行，这样每项变更都可以单独提交、审查或回滚。这里的独特之处并不是抽象意义上的自主性，而是把隔离当作一种控制机制：用一组专注的“工人”替代一个巨大的上下文窗口。回复中也补充提醒，跨步骤耦合仍然必须被明确监控。

**与前一日对比：** 7 月 11 日的重点是面向整个 repo 的 agent 操作系统。到了 7 月 12 日，方向未变，但下沉到了运行卫生这一层：技能裁剪、模型通道，以及可复用的规划流程。

### 1.2 多 agent 工作变得更有边界，也更关注上下文 🡕

大家对多 agent 的热情并未消退，但高信号帖子对“并行在何时有用、哪些部分必须受限”讲得具体得多。构建者反复回到同样的约束：只拆分彼此独立的工作、让每个上下文保持小而清晰，并用关卡或停止条件控制开销和漂移。共有 6 条内容提供了具体证据。

[@shivam74689](https://x.com/shivam74689) [构建了](https://x.com/shivam74689/status/2076312625366143246)（40 次点赞、2 条回复、1,284 次浏览、32 次收藏）展示了一个用 LangGraph 构建的并行多 Agent 股票研究系统，包含独立的财务、新闻、社交情绪和 SEC 文件分支。他的论点很明确：当每个分支都彼此独立且总是需要运行时，扇出加扇入模式比把一切都交给 supervisor 更简单也更快。截图之所以重要，是因为它同时展示了编排图和最终合并报告界面。

[@nyk_builderz](https://x.com/nyk_builderz) [认为](https://x.com/nyk_builderz/status/2076317757126369571)（9 次点赞、1 条回复、706 次浏览、11 次收藏）表示，orchestrator 应当有意保持廉价且“笨”，只有在某个关卡要求升级时才调用昂贵的 sub-agent。这样一来，多 agent 就从展示型功能变成了可计量的系统。

## 2. 什么让人沮丧

### 上下文膨胀与失控的用量

严重程度高。[@pvncher](https://x.com/pvncher) [警告](https://x.com/pvncher/status/2076055682634100900)（61 次点赞、9 条回复、9,698 次浏览、72 次收藏）表示，冗长的技能描述和宽泛的 sub-agent 表述会在 GPT-5.6 Sol 上触发额外用量；而 [@Voxyz_ai](https://x.com/Voxyz_ai) [描述了](https://x.com/Voxyz_ai/status/2076259556397572433)（35 次点赞、6 条回复、3,305 次浏览、42 次收藏）则把全局 Codex 和 Claude Code 技能堆视为彼此冲突的规则堆，模型现在不得不从中协调。[@RoundtableSpace](https://x.com/RoundtableSpace) [展示了](https://x.com/RoundtableSpace/status/2076120608853700672)（53 次点赞、15 条回复、43,315 次浏览）之所以加入预算护栏工作流，正是因为一个不受约束的 agent 可能在任何人察觉之前就烧掉大量昂贵的视频生成额度。人们当前的应对方式包括：加载更少技能、降低推理等级、在安装前先 dry run，并在高成本操作前强制人工检查点。这值得投入去构建，因为当前的解决方案仍是手工式裁剪，而不是一类一等工具。

### Agent 仍然不知道自己何时算完成

严重程度高。[@Saanjana_Nikita](https://x.com/Saanjana_Nikita) [认为](https://x.com/Saanjana_Nikita/status/2076274642436935744)（55 次点赞、43 条回复、1,181 次浏览）表示，真正的生产故障是：假完成、无限循环、工具重试失效和上下文过载。[@gokulr](https://x.com/gokulr) [构建了](https://x.com/gokulr/status/2076403378972991643)（20 次点赞、8 条回复、2,717 次浏览、21 次收藏）提到 ProductSpec 的 `check_completion_claim` 工具，因为 agent 往往看不到原始范围或验收标准；而 [@nyk_builderz](https://x.com/nyk_builderz) [表示](https://x.com/nyk_builderz/status/2076317757126369571)（9 次点赞、1 条回复、706 次浏览）则指出，反复提示“停下来提问”本质上是一条治理规则，应该被放进关卡里。人们目前通过审查关卡、验收标准和 eval 来应对。这值得投入去构建，因为多条彼此独立的帖子都汇聚到同一个缺失原语：可复用的 verifier。

### 模型路由仍然依赖手工，且脆弱

严重程度中高。[@kunchenguid](https://x.com/kunchenguid) [发布了](https://x.com/kunchenguid/status/2076050848501903526)（67 次点赞、18 条回复、3,409 次浏览、57 次收藏）画出了一整张组织结构图，只为解释 Fable、GPT-5.6 Sol、Grok 4.5、Codex 和 Opus 4.8 各自该在何时接手工作。[@bindureddy](https://x.com/bindureddy) [推广了](https://x.com/bindureddy/status/2076165296977858836)（139 次点赞、14 条回复、350,566 次浏览）讨论了自定义 coding-agent 组合，但最有用的回复指出，真正困难的部分是判断哪些代码足够新颖，值得交给昂贵模型，哪些只是模板化内容，适合便宜模型。[@uday_devops](https://x.com/uday_devops) [将其定义为](https://x.com/uday_devops/status/2076245179892383762)（25 次点赞、20 条回复、791 次浏览）则把 Claude Code 和 Cursor 视作完全不同的产品层——一个是系统构建器，一个是 coding assistant——而非可直接替换的产品。人们当前的应对方式是手工制作通道、fallback 规则和工具特定工作流。这值得投入去构建，因为路由逻辑目前大多仍属于部落知识。

### 包与 repo 的来源证明，成了 agent 特有的安全缺口

严重程度中等。[@Azurite_ai](https://x.com/Azurite_ai) [描述了](https://x.com/Azurite_ai/status/2076208475885936736)（57 次点赞、48 条回复、396 次浏览）讨论了 HalluSquatting：攻击者先抢注 agent 幻觉出来的包名或 repo 名，然后等待其安装。[@pengsonal](https://x.com/pengsonal) [补充说](https://x.com/pengsonal/status/2076247308308803587)（16 次点赞、11 条回复、191 次浏览）则从框架侧给出了同一信任问题的第二个版本：请使用官方 FoundationAgents/OpenManus repo，因为假 repo 和诈骗 token 共用同一个名字。人们当前通过优先使用已审计注册表、固定 manifest 和官方来源来应对。这值得投入去构建，因为 agent 化安装会放大原本可能被人类识别出来的错误。

## 3. 大家希望存在什么

### 按项目范围加载技能，而不是全局技能垃圾场

需求说得很明确：只保留那些能提供模型无法自行推断的项目知识，或者团队原本容易忘记的真实命令与检查项。[@Voxyz_ai](https://x.com/Voxyz_ai/status/2076259556397572433) 表示，全局技能堆已经变成上下文成本，而 [autoskills](https://github.com/midudev/autoskills) 则提供了一个部分答案：技术栈扫描、已审计 bundle、哈希校验，以及 dry-run 安装。这是实际需求，不是情绪化诉求。人们想要更少的指令杂讯和更少的误激活。机会评级：[+++] 直接。

### agent 能在编码前查询的产品意图控制文件

[@gokulr](https://x.com/gokulr/status/2076403378972991643) 直接描述了缺失的文件：要解决什么问题、哪些在范围内、哪些不在范围内、哪些验收标准必须通过、该跑哪些 AI eval，以及上线后什么才算成功。ProductSpec MCP 是一个具体实现，但需求并不局限于单个项目。agent 需要一个持久的控制文件，能够跨越 repo、issue、prompt 和 review 边界存续。这很紧迫，因为它正位于反复出现的“假完成”抱怨之下。机会评级：[+++] 直接。

### 可复用的停止条件、预算上限与人工检查点

人们一再要求的是更安全的长时间运行，而不是为了自主性本身追求更多自主。[@RoundtableSpace](https://x.com/RoundtableSpace/status/2076120608853700672) 在昂贵的视频生成前插入了人工检查点，[@Saanjana_Nikita](https://x.com/Saanjana_Nikita/status/2076274642436935744) 表示可靠团队信任 eval 而非 demo，而 [@nyk_builderz](https://x.com/nyk_builderz/status/2076317757126369571) 则希望关卡只编码一次，而不是每天重打。实际需求是一个可复用的 verifier 层，能够停止长时间运行、计量预算，并在正确时机升级处理。现有工具覆盖了其中一些片段，但整个工作流看起来仍然很手工。机会评级：[++] 直接。

### 面向 agent 的付费、可验证服务市场

[@NavenNetwork](https://x.com/NavenNetwork/status/2076366233927348280) 希望 agent 能按调用发现并支付专业服务，而 [@marclou](https://x.com/marclou/status/2075962823843463388) 则希望有 MCP 包装的商业数据 API，能直接回答收购类问题。需求很实际：agent 需要可信的外部能力，而且它们应当比逐个账户集成的定制方案更容易购买和审查。机会评级：[++] 直接。

### 超越提示词技巧的公开 harness 与 loop 课程体系

[@RoundtableSpace](https://x.com/RoundtableSpace/status/2076045111960416617) 和 [@RohOnChain](https://x.com/RohOnChain/status/2076299893334016444) 都在放大免费的 harness 与 loop 资源，因为许多构建者仍缺乏关于 loop、verifier 和 review gate 的共享词汇。这一需求一部分是教育性的，一部分是运营性的：团队要的是今天下午就能拿来用的可迁移模式，而不是另一门泛泛而谈的 AI 课程。机会评级：[+] 竞争性。

|---|---|---|---|---|

| [GPT-5.6 Sol](https://x.com/kunchenguid/status/2076050848501903526) | LLM | (+) | 强规划拆解能力、适合后端和审查通道、小线程工作 | 技能或推理档位配置不当时，用量可能激增 |

| [Grok 4.5](https://x.com/kunchenguid/status/2076050848501903526) | LLM | (+/-) | 快速实现通道、实时 X 和新闻访问 | 在混合栈中，限制和架构分歧会成为问题 |
| [LangGraph](https://x.com/shivam74689/status/2076312625366143246) | 编排框架 | (+) | 清晰的扇出与扇入模式，支持共享状态同步 | 需要有意识地在 supervisor 与并行模式间做选择 |
| [autoskills](https://github.com/midudev/autoskills) | 技能安装器与注册表 | (+) | 技术栈检测、已审计注册表、dry run、哈希校验 | 只有当技能确实携带项目知识或校验价值时才值得 |
| [ProductSpec MCP](https://github.com/gokulrajaram/ProductSpec) | 规格与控制层 | (+) | 将范围、验收标准、AI eval 和完成检查工具化 | 需要有纪律地维护 Product Spec |
| [OpenAI Responses Multi-agent](https://developers.openai.com/api/docs/guides/responses-multi-agent) | API 运行时 | (+) | 托管式 sub-agent 生成、共享工具、有边界的并发 | Beta；额外 token 成本；不适合共享可变状态 |
| [TrustMRR API plus MCP](https://trustmrr.com/docs/api) | 数据背板 | (+) | 已验证的 startup 营收数据和可供 agent 查询的筛选器 | API key 和速率限制；商业数据领域较窄 |
| [Naven Marketplace plus x402](https://docs.cdp.coinbase.com/x402/welcome) | agent 商务层 | (+) | 按调用计价、可验证服务、机器支付 | 生态尚早；信任和验证仍需额外工作 |
| [OpenManus](https://github.com/FoundationAgents/OpenManus) | 开源 agent 框架 | (+/-) | BYO-LLM 通用 agent 基座、CLI 与 MCP 模式、强社区信号 | 用户仍需自行承担模型成本，多 agent 流程被标为不稳定 |

总体满意度最高的情况，是工具消除了某种具体成本，而不是承诺泛化自主性。[@kunchenguid](https://x.com/kunchenguid/status/2076050848501903526) 和 [@bindureddy](https://x.com/bindureddy/status/2076165296977858836) 都把规划者、执行者和审查者拆分到不同模型上；[@pvncher](https://x.com/pvncher/status/2076055682634100900) 和 [@Voxyz_ai](https://x.com/Voxyz_ai/status/2076259556397572433) 持续尝试缩小技能接触面；[@gokulr](https://x.com/gokulr/status/2076403378972991643) 把范围和验收标准移入控制文件；而 [@marclou](https://x.com/marclou/status/2075962823843463388) 与 [@NavenNetwork](https://x.com/NavenNetwork/status/2076366233927348280) 则把外部数据和服务封装成 agent 友好的 API。

因此，迁移压力看起来不再像“选出唯一最好的模型”，而更像“给每条通道一个更窄的任务、更小的上下文，以及更明确的完成证明”。竞争动态也不只存在于模型厂商之间，而是在于哪些脚手架能够路由工作、验证结果并控制成本。

ProductSpec MCP 与 autoskills 都是在工作流更早阶段引入控制。ProductSpec 在 agent 写代码之前，就把范围、验收标准和 AI eval 放到它面前；而 autoskills 则在运行开始前，就决定哪些技能包被允许加载。

TrustMRR MCP 和 Naven Marketplace 更像背板，而不是面向终端用户的聊天体验。两者反复触发的原因其实相同：agent 需要结构化的外部能力，而且这些能力应比临时浏览器操作或一次性集成更容易查询、定价和建立信任。

OpenManus 和 firstmate 表明，开源势能仍然分散在“完整框架”和“叠加于现有 harness 之上的轻行为层”之间。shivam74689 的股票研究原型则再次强化了当天最大的编排教训：当每个子任务都拥有自己的状态，且合并点明确时，并行分支才真正有帮助。

## 6. 新内容与值得关注的事

### Loop engineering 变成了一个明确的 verifier-first 框架

[@RohOnChain](https://x.com/RohOnChain) [提到了](https://x.com/RohOnChain/status/2076299893334016444) 推出了一门免费的 [Loop Engineering 指南](https://www.aibuilderclub.com/blog/loop-engineering-guide-2026)，并提出了一个明确主张：如今的瓶颈是 verifier，而不是 generator。这一点值得关注，因为它把零散的社交媒体 meme 变成了一个可审视的框架，涵盖开放与封闭 loop、明确的停止条件，以及 Andrew Ng 的三层 loop 模型。

![Loop engineering 指南截图，描述了角色从操作员转变为系统设计者，以及围绕 agent 工作的嵌套循环](https://pbs.twimg.com/media/HNBHAFhaYAAz61n.jpg)

### ProductSpec MCP 把产品意图变成了工具界面

[@gokulr](https://x.com/gokulr) [发布了](https://x.com/gokulr/status/2076403378972991643) 推出了 ProductSpec MCP，而公开的 [仓库](https://github.com/gokulrajaram/ProductSpec) 显示，它不只是一个格式公告。它附带 validator、GitHub Action、agent skills、Decision Trace 支持，以及 MCP 工具，让 agent 能直接查询范围、验收标准、AI eval 和完成状态。

### HalluSquatting 为“包幻觉”问题提供了清晰的攻击模型

[@Azurite_ai](https://x.com/Azurite_ai) [将其命名为](https://x.com/Azurite_ai/status/2076208475885936736) 将 HalluSquatting 定义为这样一种利用方式：攻击者先抢占 AI agent 幻觉出的包名或仓库名。这一点值得关注，因为它把模糊的“错误安装”故事重构为一种可重复的供应链模式，安全工具终于可以有针对性地处理。

### OpenAI 的 Responses API 让托管式多 agent 在 beta 阶段正式化

[@gabrielchua](https://x.com/gabrielchua) [重点提到](https://x.com/gabrielchua/status/2076305034447626482) 提到了 OpenAI 的 [多 Agent Responses API 指南](https://developers.openai.com/api/docs/guides/responses-multi-agent)，其中记录了 root-agent 生成、sub-agent 消息传递、等待和并发上限。这很重要，因为产品界面如今已经与许多操作者此前仍靠线程和技能手工搭建的工作流对齐。

## 7. 机会在哪里

**[+++］ 产品意图与完成门控层** — ［@gokulr](https://x.com/gokulr/status/2076403378972991643)、[@Saanjana_Nikita](https://x.com/Saanjana_Nikita/status/2076274642436935744)、[@nyk_builderz](https://x.com/nyk_builderz/status/2076317757126369571)，以及 [Loop Engineering 指南](https://www.aibuilderclub.com/blog/loop-engineering-guide-2026) 都指向同一个缺失层：agent 在宣称完成之前，需要范围、验收标准和 claim-check。这个机会很强，因为同一天里，这一信号同时以“痛点”和“在建项目”的形式出现。

**[+++］ 上下文预算与技能治理工具** — ［@pvncher](https://x.com/pvncher/status/2076055682634100900)、[@Voxyz_ai](https://x.com/Voxyz_ai/status/2076259556397572433) 和 [@RoundtableSpace](https://x.com/RoundtableSpace/status/2076120608853700672) 描述的都是同一种成本：无关指令过多，而成本控制不足。这个机会很强，因为节省是立竿见影的，而绕过方法仍然全靠手工。

**[++］ 混合模型团队的路由与评估器层** — ［@kunchenguid](https://x.com/kunchenguid/status/2076050848501903526)、[@bindureddy](https://x.com/bindureddy/status/2076165296977858836)、[@petergyang](https://x.com/petergyang/status/2076309444909277326)，以及 OpenAI 的 [多 Agent 文档](https://developers.openai.com/api/docs/guides/responses-multi-agent) 都展示了人工划分的规划者、执行者和审查者通道。这个机会中等，因为需求很明确，但正确的分类逻辑仍然取决于具体工作负载。

**[++］ Agent 原生付费服务底座** — ［@marclou](https://x.com/marclou/status/2075962823843463388) 和 [@NavenNetwork](https://x.com/NavenNetwork/status/2076366233927348280) 显示出对机器对机器商务和结构化外部数据的需求。这个机会中等，因为信任、定价和采用必须协同发展。

**[+］ 依赖来源追溯与幻觉安装防御** — ［@Azurite_ai](https://x.com/Azurite_ai/status/2076208475885936736) 和 [@pengsonal](https://x.com/pengsonal/status/2076247308308803587) 暴露出一个狭窄但真实的安全缺口：agent 化安装器比谨慎的人类更容易被欺骗。这一机会仍在萌芽期，因为利用模式已经很明显，但自动化防御市场还很早期。

## 8. 要点

1. **可靠的 agent 工作持续向栈底下沉。** 最强的讨论不再只是关于巧妙提示词，而是规划框架、技能裁剪和模型通道。（[来源](https://x.com/MengTo/status/2076121220605686086)，[来源](https://x.com/shannholmberg/status/2076033805241249895)）
2. **verifier 成了反复出现的控制界面。** ProductSpec 的 `check_completion_claim`、loop engineering 指南，以及生产故障讨论串都汇聚到同一点：稀缺能力在于判断什么才算完成。（[来源](https://x.com/gokulr/status/2076403378972991643)，[来源](https://x.com/RohOnChain/status/2076299893334016444)）
3. **多 agent 配置的使用变得更有选择性，而不是更盲目。** 构建者更偏好把扇出与扇入用于独立任务、让廉价 orchestrator 负责关卡控制，并为每个 sub-agent 保持小上下文，而不是无限制分支。（[来源](https://x.com/shivam74689/status/2076312625366143246)，[来源](https://x.com/petergyang/status/2076309444909277326)）
4. **最具体的商业化动能出现在 agent 背板，而不是 agent 人设上。** TrustMRR 和 Naven 都把外部能力封装成结构化、可付费的界面，供 agent 直接调用。（[来源](https://x.com/marclou/status/2075962823843463388)，[来源](https://x.com/NavenNetwork/status/2076366233927348280)）
5. **agent 侧的供应链信任正在成为一个真实的安全类别。** HalluSquatting 和 OpenManus 的来源告警都表明，agent 化安装器为将恶意依赖混入原本正常的工作流创造了新路径。（[来源](https://x.com/Azurite_ai/status/2076208475885936736)，[来源](https://x.com/pengsonal/status/2076247308308803587)）
