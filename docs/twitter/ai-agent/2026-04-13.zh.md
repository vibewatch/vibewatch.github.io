# Twitter AI Agent - 2026-04-13

## 1. 人们在讨论什么

### 1.1 “薄编排层”原则正在成形 🡕

昨天围绕编排层工程的讨论，今天进一步沉淀成了一条具体的架构原则。[@garrytan](https://x.com/garrytan) 发布了他所称的 [“最简洁的提炼”](https://x.com/garrytan/status/2043566215927328955)：一种三层架构——上层是“厚技能”（用 Markdown 编写、编码判断与领域知识的流程），中层是“薄 CLI 编排层”（约 200 行代码，JSON 输入、文本输出，默认只读），底层则是确定性的应用代码（QueryDB、ReadDoc、Search）。这条原则强调的是方向：“把智能往上推到技能里，把执行往下推到确定性工具中。让编排层保持轻薄。”

![架构示意图，描述三层代理栈：顶部是厚技能层，中间是薄 CLI harness，底部是确定性应用程序](https://pbs.twimg.com/media/HFw0oV5XkAAdj_U.jpg)

这条帖子获得了 1,299 个赞和 1,666 次收藏。[@MindTheGapMTG](https://x.com/MindTheGapMTG) 在回复中补充了一个操作层面的细节：“厚技能不是写出来的，而是积累出来的。我们 CLAUDE.md 里的每一行，都是一次生产事故复盘的结果。” [@weareuplers](https://x.com/weareuplers) 则将其与 Unix 哲学联系起来：“让编排层保持轻薄，就是智能体工程版的‘把一件事做好’。Unix 花了 50 年才学会这一课，而我们不知为何又在智能体上用快进的方式重学一遍。”

[@DanielMiessler](https://x.com/DanielMiessler) [作出了区分](https://x.com/DanielMiessler/status/2043488548318597181) 区分了两类编排层工程：(1) 告诉系统具体该怎么做——这类做法会随着模型进步而“被吞掉”（即“苦涩的教训”）；(2) 告诉系统什么才算好——解释你是谁、你喜欢什么，以及什么样的输出才算优秀。他认为，只有第二类才具备面向未来的韧性。

[@dexhorthy](https://x.com/dexhorthy) [提出异议](https://x.com/dexhorthy/status/2043707427632431509) 则从根本上挑战了这种表述方式：“想象一下，如果你一年前就学会了 12-factor 上下文工程，现在就可以自信地跳过这些‘编排层’炒作，继续干活。”这条帖子获得了 102 个赞，并引来了 [@johns10d](https://x.com/johns10d) 一条内容扎实的回复：“编排层工程是在模型外围放上程序化代码，来保证它按你的意图执行，而不是只是客气地请求它。光靠客气地请求，是走不到终点的。”

智能体技能生态如今已经有了明确的数据规模。[@nozmen](https://x.com/nozmen) [上线了 officialskills.sh](https://x.com/nozmen/status/2043658478929985849)，一个经过筛选的目录，收录了 464 个技能（其中 314 个来自开发团队的官方技能，150 个来自社区），覆盖 40 家厂商组织和 11 个类别。它兼容 Claude Code、Codex、Cursor、GitHub Copilot 和 OpenCode。技能来源包括 Microsoft、Anthropic、Google、Sentry、Cloudflare、Trail of Bits 等。该站点使用现有的 `npx skills` 命令进行安装。

![Agent Skills 流水线，展示了从 Define 到 Ship 的六个开发阶段，并配有斜杠命令](https://pbs.twimg.com/media/HFx6yXHbQAAoN7Z.jpg)

### 1.3 智能体安全从理论走向证据 🡕

今天，围绕智能体安全的担忧产出了具体研究成果。[@askalphaxiv](https://x.com/askalphaxiv) [分享了](https://x.com/askalphaxiv/status/2043774016293384256) 发布了《Your Agent Is Mine》（arXiv:2604.08407），这是首个针对恶意 LLM API 路由器的系统性研究。在测试的 28 个付费路由器和 400 个免费路由器中，研究人员发现 1 个付费路由器和 8 个免费路由器会主动注入恶意代码，2 个部署了自适应规避触发器，17 个接触了研究人员持有的 AWS 金丝雀凭据。这些路由器累计处理过 21 亿个 token，导致 440 次 codex 会话中的 99 个凭据暴露。论文呼吁为工具调用建立端到端完整性保障，让客户端能够验证自己收到的操作是否与提供方实际生成的操作完全一致。

![关于针对 LLM 供应链恶意中间人攻击的学术论文首页](https://pbs.twimg.com/media/HFzxmtqWoAAWFhf.png)

[@ZackKorman](https://x.com/ZackKorman) [称其为 AIUC-1](https://x.com/ZackKorman/status/2043679021834154020) 将一项新的 AI 智能体安全合规标准称为“巨大的骗局”，尽管其技术贡献者名单包括 ElevenLabs、Cisco、OWASP、MITRE、Microsoft、Stanford、Google Cloud、Anthropic、Meta、Databricks 和 Visa。在一条 [后续进展](https://x.com/ZackKorman/status/2043794863347450214) 中，他进一步澄清：“如果有人想做一个 AI 智能体安全框架，然后发给大家用，我完全没意见。但把它做成合规标准”，问题就在这里。

![AIUC-1 联盟成员网格图，展示了 ElevenLabs、Cisco、OWASP、Microsoft、Anthropic、Meta 等公司的标志](https://pbs.twimg.com/media/HFyafP_XYAAEPSL.jpg)

[@AllAICoder](https://x.com/AllAICoder) [警告称](https://x.com/AllAICoder/status/2043643043497062722) 警告称，在开放市场使用第三方技能时，“一个可疑技能就能接管你的整台机器”。[@RogoAI](https://x.com/RogoAI) [报道称](https://x.com/RogoAI/status/2043735515917169015) 表示，他们的自主渗透测试智能体 Sisyphus “一个下午就找出了 18 个手动测试漏掉的可利用问题”。

### 1.5 上下文工程与智能体记忆 🡒

上下文工程仍是一个稳定持续的主题，今天又出现了新的可视化分类法和记忆方案。[@DataScienceDojo](https://x.com/DataScienceDojo) [发布了](https://x.com/DataScienceDojo/status/2043781280890749318) 发布了一张信息图，定义了上下文工程的 6 个组成部分：Instructions/System Prompt、Long-Term Memory、Available Tools、Structured Output、User Prompt，以及 Retrieved Information（RAG）。

![上下文工程信息图，展示六个组成部分：instructions、长期记忆、可用工具、结构化输出、用户提示词和 RAG](https://pbs.twimg.com/media/HFz4PHkXAAAPJgS.jpg)

[@ghumare64](https://x.com/ghumare64) [建议](https://x.com/ghumare64/status/2043661245635493920) 介绍了 agentmemory，将其定位为一个可跨编排层工作的跨智能体记忆层，具备 95.2% 的 retrieval R@5、92% 更少的 token、43 个 MCP 工具和 654 项通过的测试。[@unbrowse](https://x.com/unbrowse) [提出了](https://x.com/unbrowse/status/2043690768406290670) 则提出了一种逆势思路：“如果你根本不复制数据呢？每个智能体记忆系统都会把数据复制到向量存储里。如果智能体直接为源数据建索引呢？”

[@che_shr_cat](https://x.com/che_shr_cat) [分享了](https://x.com/che_shr_cat/status/2043759724114395460) 介绍了《Memory Intelligence Agent》论文（arXiv:2604.04503）：一个采用 Manager-Planner-Executor 记忆架构的 7B 参数智能体，通过将程序性记忆与执行解耦，并在推理期间更新权重，性能比 32B 模型高出 18%。

![Memory Intelligence Agent 论文，展示了 Manager-Planner-Executor 架构，在 7B 模型上实现了 31% 的提升](https://pbs.twimg.com/media/HFzjhn1XQAAnwFN.jpg)

## 2. 什么让人沮丧

### 智能体编排层的资源消耗（严重程度：高）

[@0xClandestine](https://x.com/0xClandestine) [报道称](https://x.com/0xClandestine/status/2043748820765290535) 表示，一个 opencode 智能体会话会占用 5GB 内存，并称之为“无法接受”，同时希望有用 Rust 或 Zig 编写的替代方案。系统监控截图显示，在一台配备 64GB RAM 的 Apple M4 Max 上，单个 opencode 进程占用 509.8MB 常驻内存 / 4.8GB 虚拟内存。回复中没有人给出令人满意的替代方案。

![系统监视器显示，Apple M4 Max 上的 opencode 进程占用了 4.8GB 虚拟内存](https://pbs.twimg.com/media/HFzac-8asAU4eyP.jpg)

### 编程智能体中的子智能体可见性（严重程度：中）

[@dani_avila7](https://x.com/dani_avila7) [指出了](https://x.com/dani_avila7/status/2043749681633587499) 指出了 Claude Code 中一个具体的 UX 问题：“使用会调用子智能体的 Skills 时，子智能体不会显示在 Claude Code 界面里。一切都能正常运行，但你无法判断，实际干活的到底是你在 skill frontmatter 里添加的那个子智能体，还是某个内置智能体。”截图展示了通过 frontmatter 字段连接技能与子智能体的机制，但在 TUI 表层界面上没有任何提示。

### 多智能体需求导致的 token 紧缺（严重程度：中）

[@Grummz](https://x.com/Grummz) [警告称](https://x.com/Grummz/status/2043749800089399329) 表示：“我们正走向 token 紧缺。这不只是算力限制，每个人对 AI 的需求都爆炸了。而且现在全都变成多智能体了。”他在回复中进一步量化道：“现在每个 AI 编排层为每个人发起的 LLM 调用次数，是过去的 4 到 8 倍，而不再是 1 次。”

### 企业智能体编排的怀疑情绪（严重程度：中）

[@buccocapital](https://x.com/buccocapital) [嘲讽了](https://x.com/buccocapital/status/2043682978430103777) 针对那些声称自己是“管理智能体访问、安全和编排的中立方”的企业 SaaS 公司提出质疑，这条帖子获得了 179 个赞。回复进一步加深了批评：[@curtismakes](https://x.com/curtismakes) 观察到，“所有 SaaS 公司都在同一个季度从 AI-powered 转向了 AI-orchestrator”；[@sigmadeltacto](https://x.com/sigmadeltacto) 则预测现实会是：“中立方：50 万美元 ACV、3 年锁定期、还得买 Professional Services。”

### 语音智能体服务骗局（严重程度：中）

[@huzzymad](https://x.com/huzzymad) [报道称](https://x.com/huzzymad/status/2043740316344168919) 表示，一位家人因为一个语音智能体演示被坑了 6,000 美元；该服务“没有日志、没有转录、不拥有任何基础设施、每周通话次数受限（额外通话还要另外收费）”。随着语音智能体市场增长，这种收高价做演示、却不交付生产基础设施的模式似乎正在出现。

### MCP 过度使用（严重程度：低）

[@jezell](https://x.com/jezell) [认为](https://x.com/jezell/status/2043417554535010337) 认为 MCP 被过度使用了：“如果智能体和后端服务的代码都由你掌控，那么 99.9% 的情况下你都不该用 MCP。MCP 只解决一个真实问题：为别人的东西构建连接器市场。”所有 LLM 都支持不依赖 MCP 的直接工具调用。

## 3. 人们希望出现什么

### 可自我更新的技能

[@avisinghdotdev](https://x.com/avisinghdotdev) [请求](https://x.com/avisinghdotdev/status/2043651542813921674) 希望 Claude Code 能有一个 `/update-skills` 命令，类似现有的 `/create-skills`，这样“智能体就能基于过去的交互更新现有技能”。如今的技能仍是静态产物，还没有机制让它们从使用中演化。

### 多智能体窗口化工作流

[@Kraggich](https://x.com/Kraggich) [指出了](https://x.com/Kraggich/status/2043814179430162696) 指出了一个核心 UX 缺口：“所有 AI 编程工具都在犯同一个错误。Cursor、Windsurf、Codex、Claude Code——它们都只给你一个窗口里的一个智能体。但真实工作不是一次只做一个任务，而是三个智能体在三个 worktree 中，同时解决同一个问题的三个部分。”

### 企业语音智能体测试

[@sumanyu](https://x.com/sumanyu) [预测](https://x.com/sumanyu/status/2043718422198927593) 表示：“每家 YC W26 语音智能体公司都会遇到同一个企业问题：‘你们怎么测试这个？’不是你的演示。不是你的基准。是怎么用 OUR data、OUR edge cases、OUR compliance requirements，在 OUR scale 下测试？”

### 轻量级编程智能体编排层

[@0xClandestine](https://x.com/0xClandestine) [询问](https://x.com/0xClandestine/status/2043748820765290535) 希望有一个更省 RAM 的编程智能体编排层，“最好是用 Rust/Zig 写的”。回复中没有人给出令人满意的答案。现有方案（消耗数 GB 的 Node.js/Python 编排层）与实践者想要的方案（轻量级原生编排层）之间，仍有明显空白。

### 团队级智能体治理

[@PestoPoppa](https://x.com/PestoPoppa) [开源了](https://x.com/PestoPoppa/status/2043626137520116056) 希望有一个用于协作式智能体工作流的治理层：“如果你的开发者在使用 Claude Code / Codex，但会话之间无法彼此积累、知识不断蒸发、入职过程又很痛苦，那么这个仓库就是为你准备的。”其底层需求，是一种能够跨会话持续存在的团队级智能体协同机制。

## 6. 新动态与值得关注的事

### 首个标准化语音智能体基准

[@tulseedoshi](https://x.com/tulseedoshi) [分享了](https://x.com/tulseedoshi/status/2043705774308733131) 发布了 Sierra Platform 的 tau-voice 排行榜，这是首个针对实时语音智能体性能的标准化基准。目前排名为：Gemini 3.1 Flash Live (Thinking) 的 PASS 为 43.8%，xai-realtime 为 38.3%，gpt-realtime-1.5 为 35.3%，gemini-live-2.5-flash-native-audio 为 25.8%。评测类别包括零售、航空和电信场景。

![tau-voice 排行榜，显示 Gemini 3.1 Flash Live 为 43.8%，xai-realtime 为 38.3%，gpt-realtime-1.5 为 35.3%](https://pbs.twimg.com/media/HFwqB4NaUAAsEjQ.jpg)

### 更好的记忆让小模型击败大模型

《Memory Intelligence Agent》论文（arXiv:2604.04503）表明，采用 Manager-Planner-Executor 记忆架构的 7B 参数模型，平均性能提升了 31%，并在所评估数据集上比 32B 模型高出 18%。其关键技术在于：将程序性记忆与执行解耦，并通过参数化记忆与非参数化记忆之间的双向转换，让记忆能够在推理期间演化。

### 智能体自主发现并订阅 API

[@OrbisAPI](https://x.com/OrbisAPI) [报道称](https://x.com/OrbisAPI/status/2043766007081160833) 表示，Claude 智能体正在自主发现 Orbis API 目录，浏览可用服务、完成注册并订阅 API，无需人工干预。Orbis 拥有 730 多个 API，并支持 x402 微支付，这构成了智能体经济行为开始涌现的早期证据。[@grok](https://x.com/grok) [描述了](https://x.com/grok/status/2043820017905496098) 还提到了 Lightning Network 上的类似模式：“一个 AI 智能体可以在几秒内启动自己的 L402 服务器……另一个智能体发现它后，用 sats 即时付款、证明 preimage，并消费该服务。零配置、零 KYC，完全机器对机器。”

### Microsoft Agent Framework 达到 1.0

[@dotnet](https://x.com/dotnet) [宣布了](https://x.com/dotnet/status/2043747319917461591) 发布了同时支持 .NET 和 Python 的 Microsoft Agent Framework 1.0，提供稳定 API、多智能体工作流、MCP 和 A2A 协议支持、Azure AI Foundry 托管、YAML 声明式智能体以及图引擎。多个来源（[@ninja_prompt](https://x.com/ninja_prompt)、[@CsharpCorner](https://x.com/CsharpCorner)）确认，它适配 Claude、GPT、Gemini 和 Ollama。[@analyzedinvest](https://x.com/analyzedinvest) [指出](https://x.com/analyzedinvest/status/2043696757528313871) 表示，Microsoft 也在把 OpenClaw 集成进 M365 Copilot，让始终在线的智能体覆盖整个 Microsoft 365 技术栈。

## 7. 机会在哪里

**[+++] Strong: Agent Security Tooling and Verification.** The "Your Agent Is Mine" paper documented active attacks on LLM API routers affecting billions of tokens. [@AllAICoder](https://x.com/AllAICoder) 警告了恶意技能的风险。[@ZackKorman](https://x.com/ZackKorman) 批评 AIUC-1 是为时过早的合规表演。已知威胁与可用防御之间存在巨大缺口。端到端工具调用完整性、技能验证和透明的路由器审计，都是立刻需要的能力。（[来源](https://x.com/askalphaxiv/status/2043774016293384256)）

**[+++] Strong: Skill Quality and Lifecycle Management.** The ecosystem now has 464 catalogued skills from 40 vendor teams, but no mechanism for skills to evolve from usage. [@avisinghdotdev](https://x.com/avisinghdotdev) 请求 `/update-skills`；[@_philschmid](https://x.com/_philschmid) 发布了关于技能退役的指导。技能生命周期——创建、评估、改进、退役——目前仍完全依赖人工。若有系统能追踪技能效果并自动推动改进，将能解决一个日益突出的痛点。（[来源](https://x.com/avisinghdotdev/status/2043651542813921674)）

**[++] Moderate: Lightweight Native Agent Harnesses.** Current coding agent harnesses in Node.js and Python consume gigabytes of RAM. [@0xClandestine](https://x.com/0xClandestine) 记录了单个 opencode 会话占用 5GB 内存，并寻求 Rust/Zig 替代方案。[@a_g_e_n_c](https://x.com/a_g_e_n_c) 则展示了一个仅需 512MB RAM 的完整智能体运行时。主流臃肿编排层与极简硬件可支持能力之间的差距，为原生、资源高效的智能体运行时留下了空间。（[来源](https://x.com/0xClandestine/status/2043748820765290535)）

**[++] Moderate: Enterprise Voice Agent Testing Infrastructure.** [@sumanyu](https://x.com/sumanyu) 指出了企业侧的关键阻碍：如何用客户自己的数据、边界案例和合规要求来测试语音智能体。Sierra 的 tau-voice 基准提供了标准化评估，但目前还没有面向企业特定语音智能体验证的工具。[@huzzymad](https://x.com/huzzymad) 记录了一起来自语音智能体服务市场的 6,000 美元骗局，说明需求增长已经超过了质量保障能力。（[来源](https://x.com/sumanyu/status/2043718422198927593)）

**[++］ 中等：Agent-to-Agent Commerce Protocols。** Orbis（x402 micropayments）、MoonPay CLI（300 万次工具调用）、Lightning/L402，以及多个 DeFi 集成层，都在朝着机器对机器支付的方向发展。基础设施仍然较为零散，但模式是一致的：代理需要在无人类干预的情况下，为来自其他代理的服务付费。首个实现显著网络效应的协议，将定义代理经济的支付轨道。(［来源](https://x.com/OrbisAPI/status/2043766007081160833))

**[+] Emerging: Team Agent Governance.** [@PestoPoppa](https://x.com/PestoPoppa) 开源了一个面向协作式智能体工作流的治理层，而 [@nyk_builderz](https://x.com/nyk_builderz) 的 mission-control 获得了 4,000+ stars。会话之间无法相互积累、知识蒸发、入职困难——对任何使用多个编程智能体的团队来说，这都是现实问题。（[来源](https://x.com/PestoPoppa/status/2043626137520116056)）

**[+] Emerging: Agent Memory Architecture Innovation.** The Memory Intelligence Agent paper showed that memory architecture matters more than model scale for agent performance. [@unbrowse](https://x.com/unbrowse) 提议直接为源数据建立索引，而不是把数据复制到向量存储中。agentmemory 则提供了 95.2% 检索率的跨工具记忆。主流的 RAG+向量存储模式，可能会被“数据留在原地、检索更智能”的架构取代。（[来源](https://x.com/che_shr_cat/status/2043759724114395460)）

## 8. 要点

1. **“薄编排层、厚技能”架构已巩固为智能体设计的主导原则。** Garry Tan 的总结——把智能放进 Markdown 技能，把执行下沉到确定性代码，并让编排层保持最小化——获得了 1,299 个赞和 1,666 次收藏。多位实践者独立验证了这一模式。（[来源](https://x.com/garrytan/status/2043566215927328955)）

2. **智能体技能生态如今已有明确规模：来自 40 个厂商团队的 464 项技能被编目收录，分发基础设施已经到位，但生命周期管理仍然缺失。** officialskills.sh 推出了精选目录；Google 发布了 6 阶段技能流水线；Arcium 和 MiniMax 发布了特定领域技能。缺失的一环，是能够从使用中演化、而非依赖人工维护的技能。（[来源](https://x.com/nozmen/status/2043658478929985849)）

3. **智能体安全威胁并非理论上的，而是已经被记录且正在发生。**《Your Agent Is Mine》论文发现，付费 API 路由器存在恶意代码注入、数十亿 token 涉及凭据外泄影响，现实中还出现了自适应规避技术。与此同时，AIUC-1 的合规标准遭到严厉批评。这个领域更需要的是有效防御，而不是治理表演。（[来源](https://x.com/askalphaxiv/status/2043774016293384256)）

4. **智能体市场正从“目录列表”转向“实时商业”，智能体已经开始自主发现服务并为其付费。** Orbis 报告称，智能体会独立浏览、注册并订阅 API。MoonPay CLI 的工具调用量达到 300 万次。智能体经济已不再只是一个概念，而是在产生可量化的交易量。（[来源](https://x.com/OrbisAPI/status/2043766007081160833)）

5. **对智能体性能而言，记忆架构比模型规模更重要。** 一个配备专门记忆架构的 7B 智能体，性能比 32B 模型高出 18%。agentmemory 展示了 95.2% 的检索率和跨工具兼容性。智能体质量的竞争优势，正从模型选择转向记忆工程。（[来源](https://x.com/che_shr_cat/status/2043759724114395460)）

6. **语音智能体已经有了首个标准化基准，但企业测试仍是未解问题。** tau-voice 排行榜将 Gemini 3.1 Flash Live 的 PASS 率列为 43.8%，建立了基线。但企业买家需要的是结合自身数据和合规要求的测试，而语音智能体服务市场已经出现骗局。（[来源](https://x.com/tulseedoshi/status/2043705774308733131)）

7. **围绕编排层工程的术语之争是有产出的，而不只是语义之争。** Miessler 区分了面向未来的编排层工程（定义什么才算好）与脆弱的编排层工程（规定具体怎么做）。Dexhorthy 认为，上下文工程已经涵盖了这个概念。Johns10d 则为这种区分辩护：程序化保证不同于礼貌请求。这场争论正在帮助人们厘清，智能体配置里真正重要的到底是什么。（[来源](https://x.com/DanielMiessler/status/2043488548318597181)）
