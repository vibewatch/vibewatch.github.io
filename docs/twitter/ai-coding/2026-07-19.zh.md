# Twitter AI 编程 - 2026-07-19

## 1. 人们在讨论什么

### 1.1 技能与规范正被视为围绕智能体的可复用层 🡕

最强烈的实务主题，是把可重复使用的工程判断打包起来，而不是每次都从零开始给模型写提示词。一条高互动帖子将 GitHub 的 Spec Kit 描述为一条六步路径：从项目章程一路走到规范、规划、任务和实施；另一条帖子则把 agent skills 视为可安装的能力库存。相关迹象也表明，发现并不能解决质量控制问题：skills-directory 的作者估计，目录里大约只有一半内容真正有用，并特别指出其中还有一个更小、但值得信赖的核心集合。

[@DivyanshT91162](https://x.com/DivyanshT91162) [提出](https://x.com/DivyanshT91162/status/2078831252145369476)（124 次点赞，6 条回复，11,538 次浏览，262 次收藏）Spec Kit 被视为一种工作流，可将一个想法转化为一份可由多个编码智能体执行的动态规范。[Spec Kit 仓库](https://github.com/github/spec-kit) 介绍了同样的开源流程，并记录了其 constitution、specify、plan、tasks 和 implementation 各阶段；一条回复还补充了一个重要限制：如果规范本身发生漂移，智能体仍然会出错。

[@undefinedKi](https://x.com/undefinedKi) [重点介绍](https://x.com/undefinedKi/status/2078503194951372897)（89 次点赞，20 条回复，8,833 次浏览，160 次收藏）skills.sh 被视为一个跨智能体的软件包管理器和目录。其附带的目录快照内容相当扎实：它将技能组织为 planning、TDD、debugging、documents、design 和 tooling，而不是把它们当作通用提示词来处理。

![Skills 目录快照，将 99 个 agent skills 归类为规划、测试、调试、设计、文档和自动化](https://pbs.twimg.com/media/HNhTo-rW8AAV6RG.jpg)

**讨论洞见：** 实际分歧不在于技能是否有帮助，而在于如何筛选。skills.sh 的作者表示，Anthropic、Vercel 和 Obra 的材料构成了可靠的核心，其余内容仍需进一步过滤。

**与前一天相比：** 7 月 18 日的讨论已经凸显了技能发现的重要性。到了 7 月 19 日，讨论又补上了一个更清晰的互补模式：技能负责打包可复用流程，而规范则约束这些流程要执行的工作。

### 1.2 长时运行的智能体正被框定为规划与验证问题 🡕

关于 loops、编排和多模型路由的帖子，强调的是执行纪律，而不是单一模型谁更强。具体建议包括：使用可验证的终态、审阅计划而非照单全收、分离创建者与验证者角色，并依据上下文、部署方式、权限和可靠性来路由工作。

[@petergyang](https://x.com/petergyang) [分享](https://x.com/petergyang/status/2078846124828545179)（14 次点赞，3 条回复，1,435 次浏览，9 次收藏）这是一则对 Claude Code 团队成员的采访，讨论了 `/loop`、`/goal` 和工作流。配套的 [文章](https://creatoreconomy.so/p/how-i-plan-build-and-run-loops-with-claude-code-thariq-shihipar) 表示，`/goal` 需要一个可验证的完成终点，计划应由人工阅读，且将 creator 与 verifier 子智能体分开会很有帮助；其中还提到，Claude Code 的系统提示词已削减 80%。

[@prasad_pilla](https://x.com/prasad_pilla) [介绍](https://x.com/prasad_pilla/status/2078889548835406216)（6 次点赞，4 条回复，245 次浏览）一种“软件工厂”式方法：Claude 和 GPT 可作为可互换的执行后端，用于规划、读取代码仓库、打补丁、评审、测试、调试和交接。[Alan 网站](https://tryalan.ai) 将模型无关性，以及 SaaS、hybrid、on-prem 和 air-gapped 部署，视为产品层面的选择，这与原帖对路由和运行可靠性的强调一致。

[@Trion129](https://x.com/Trion129) [报道](https://x.com/Trion129/status/2078944505479520605)（3 次点赞，1 条回复，167 次浏览，4 次收藏）使用 oh-my-opencode-slim 可在保持质量尚可的同时降低用量。其 [仓库](https://github.com/alvinunreal/oh-my-opencode-slim) 记录了专门化的后台智能体、多模型 council 运行、模型预设、内置验证技能以及可配置权限；至于“用量下降”这一说法，目前仍只是单个用户的经验。

**讨论洞见：** 最尖锐、也最反复出现的约束，并不只是模型质量本身。一条关于 Kimi CLI 的回复警告称，当智能体不再暴露不确定性时，加载更多代码仓库上下文反而可能让它更自信地出错。**与前一天相比：** 7 月 16 日的重点是独立评分、技能，以及狭窄的委派边界。7 月 19 日则延续了这一方向，并补充了更多操作层面的细节：可验证的目标、明确区分创建者与验证者、模型路由，以及具备权限感知的编排。

### 1.3 编码助手仍主要按界面能力和运行可靠性来评判 🡒

GitHub Copilot 计划中的 Markdown 提示词编写器、XDA 对三款工具的仪表盘对比，以及用户上报的 Codex 性能问题，让当天的讨论始终落在“实际使用代理的体验”这一层面。对比证据虽然范围有限，但相当具体：同一份仪表盘需求简报，Copilot 结果出得很快，但较为浅显；Claude Code 更完整，但 token 消耗更高；而作者最偏好的结果来自 Codex。

[@basiclines](https://x.com/basiclines) [宣布](https://x.com/basiclines/status/2078500225539531085)（97 次点赞、7 条回复、20,012 次浏览、63 次收藏）提到 GitHub Copilot 应用正在面向内部员工进行 Markdown 提示词功能的早期预览。相关引用转发称，下一步原定上线一个更强大的提示词编写器；回复则追问，除了图片和附件之外，更丰富的提示方式到底能带来哪些实际好处。

[@xdadevelopers](https://x.com/xdadevelopers) [比较](https://x.com/xdadevelopers/status/2078525293132669208)（10 次点赞、4,003 次浏览、2 次收藏）比较了 Claude Code、Codex 和 GitHub Copilot 处理同一份金融仪表盘简报的表现。链接中的 [对比](https://www.xda-developers.com/built-same-dashboard-claude-code-codex-copilot-winner-surprised-me/) 表示，Copilot 速度最快，但停留在静态工作流；Claude Code 功能更深入，但更慢，而且接近使用上限；Codex 则是在打磨程度与完整性之间，最符合作者偏好的平衡。

[@jun_song](https://x.com/jun_song) [转发并放大](https://x.com/jun_song/status/2078835286340186165)（54 次点赞、21 条回复、6,149 次浏览、19 次收藏）提到有关 Codex 导致 Mac 卡顿和 SSD 过度写入的报告。由于无法独立获取所链接的 Reddit 报告，这里只能将其视为用户上报的问题，而非已确认的缺陷；但其截图和回复清楚表明，用户希望得到解释，以及可靠的缓解方案。

## 2. 什么让人感到挫败

### 没有明确验证机制时，代理输出仍然很难信任

严重性：高。关于循环的讨论把这种失效模式说得很具体：人们可以让代理运行更久，但这并不能证明结果就是正确的。[@petergyang](https://x.com/petergyang) [分享](https://x.com/petergyang/status/2078846124828545179)（14 次点赞、3 条回复、1,435 次浏览、9 次收藏）建议通过找出未知项来做规划，而不是对 AI 的计划一带而过；原文建议设定一个可验证的终态，并将创建者代理与验证者代理分开。对 [@RituWithAI](https://x.com/RituWithAI) [认为](https://x.com/RituWithAI/status/2078718154289848621)（9 次点赞、4 条回复、243 次浏览、6 次收藏）的 Kimi CLI 回复则表示，更大的仓库上下文并没有让它的代理更敏锐，反而让它更自信地出错。眼下可见的应对方式，是人工审查再加一次独立评估流程；这值得投入构建，因为它反映的是一个直接的操作缺口，而不是对另一个模型的额外诉求。

### 技能过多，带来了筛选与信任问题

严重性：中。[@undefinedKi](https://x.com/undefinedKi) [推广](https://x.com/undefinedKi/status/2078503194951372897)（89 次点赞、20 条回复、8,833 次浏览、160 次收藏）列出了超过 93 万项技能，但评论者立刻追问，其中到底有多少真正有用。作者自己的回答是，也许有一半有用，而真正可靠的核心只来自少数几个发布者，这也清楚说明了当前的应对方式：用户仍然需要自己筛库，或者让另一个代理替他们筛。这个方向值得做，因为分发已经存在，但质量、出处和任务适配性仍然要靠人工判断。

### 对可靠性的担忧，可能压过对编码助手能力的肯定

严重性：高，但尚未验证。[@jun_song](https://x.com/jun_song) [报道](https://x.com/jun_song/status/2078835286340186165)（54 次点赞、21 条回复、6,149 次浏览、19 次收藏）中，用户声称 Codex 负载过高会导致 Mac 卡顿和 SSD 磨损；有一条回复还提到发热，并尝试过重装。由于所链接的报告无法独立审查，这些证据并不足以确立因果关系，但足以说明，用户真正想要的是清晰的诊断和安全的修复方案，而不是功能建议。因此，这一方向值得围绕透明的代理资源遥测和支持工具来构建。

## 3. 人们希望存在什么

### 一种值得信赖的代理技能选择与安装方式

skills.sh 这条讨论直接体现出，实际需求是“如何选择”，而不是“再做一个更大的目录”。[@undefinedKi](https://x.com/undefinedKi) [描述](https://x.com/undefinedKi/status/2078503194951372897)（89 次点赞、20 条回复、8,833 次浏览、160 次收藏）展示了跨多种代理的类似包管理器式安装，但讨论很快将信任范围收缩到少数几个点名的发布者，并建议让 Claude 来筛目录。一个有用但缺失的中间层，应该能在安装前展示质量证据、发布者出处、兼容的代理、所需权限以及任务触发条件。机会：直接。

### 能让规格和长时间运行任务不跑偏的护栏

Spec Kit 的结构化阶段和 Claude Code 访谈指向的是同一种需求：代理执行的工作，应该从需求到验证都带着一个人能理解的完成边界。[@DivyanshT91162](https://x.com/DivyanshT91162) [分享](https://x.com/DivyanshT91162/status/2078831252145369476)（124 次点赞、6 条回复、11,538 次浏览、262 次收藏）提倡“先规格、后执行”的工作流，但有回复提醒，规格漂移依然会导致错误；[@petergyang](https://x.com/petergyang) [分享](https://x.com/petergyang/status/2078846124828545179)（14 次点赞、3 条回复、1,435 次浏览、9 次收藏）则给出了互补建议：设定可验证目标，并认真阅读计划。对于正在委派多步骤工作的用户来说，这一需求既实际又紧迫。机会：直接。

### 面向多模型、多环境执行的统一操作层[@prasad_pilla](https://x.com/prasad_pilla) [表示](https://x.com/prasad_pilla/status/2078889548835406216)（6 个赞、4 条回复、245 次浏览）指出，生产环境中的差异更多体现在上下文、路由、本地/云端执行、身份验证、权限和运行时启动，而不只是代码生成质量。[@Trion129](https://x.com/Trion129) [补充说](https://x.com/Trion129/status/2078944505479520605)（3 个赞、1 条回复、167 次浏览、4 次收藏）则是一份关于多模型委派后使用量更低的个人报告。真正需要的是一个控制界面，让跨代理的路由、成本、能力和审批选择清晰可见。机会：竞争性。

## 6. 新的和值得关注的动态

### Markdown 提示即将登陆 GitHub Copilot 应用

[@basiclines](https://x.com/basiclines) [宣布](https://x.com/basiclines/status/2078500225539531085)（97 次点赞，7 条回复，5 次引用，20,012 次浏览，63 次收藏）表示，Markdown 提示已向员工开放早期预览，并将进入更广泛的 Copilot 应用。相关的 [引用帖子](https://x.com/mariorod1/status/2078506824685232385)（25 次点赞，1 条回复，3,115 次浏览）称，该应用正在获得一个更强大的提示编排器。这个信号之所以重要，是因为它把结构化提示从一种纯文本惯例，升级为一等公民的产品能力，尽管回复区尚未明确证明它会给用户带来哪些可见收益。

### 一次受控的三工具仪表盘测试暴露了不同取舍

## 7. 机会在哪里

**[+++] 委派式工程工作的验证与漂移控制** — Spec Kit 的分阶段流程、关于规范漂移的警告、Claude Code 关于使用可验证目标和人工审查计划的建议，以及 Kimi 回复中提到的“自信地出错”，都指向了同一个缺口。团队需要这样一层能力：能够显示当前工作是否仍与规范一致、哪些地方存在不确定性，以及有哪些证据支持任务已完成。

**[++] 带有质量、来源和权限信号的技能注册表** — skills.sh 线程显示出对跨代理安装和大型技能库的需求，但其自身讨论也表明，用户不能假设其中大多数条目都有用。一个能够公开可信维护者、任务适用性、代理兼容性、访问范围和结果证据的注册表，可以减少当前人工筛选这一步。

**[++] 带有运营护栏的多模型路由** — Alan 从业者的描述、oh-my-opencode-slim 的专用通道、Kimi 的互操作性，以及那次仪表盘比较，都说明模型选择正在超越单一排行榜。机会在于构建一个控制平面，用来记录任务匹配度、成本、上下文、部署、权限、检查项以及交接结果。

**[+] 代理资源与可靠性的可观测性** — 围绕 Codex 相关 Mac 卡顿和 SSD 磨损的用户报告尚未得到独立证实，但它们表明，市场需要透明的进程、I/O、热、内存和后台任务遥测。一个能把资源行为关联到具体代理会话的诊断界面，或许能把模糊的安全担忧转化为可执行的证据。

## 8. 要点

1. **最高信号的工作流主张是“规范优先”，而不是“提示优先”。** Spec Kit 清晰可见的六个阶段及其可观的互动数据，显示出市场对可复用项目约束的需求；而关于规范漂移的回复则说明，这些约束为何需要主动校验。（[来源](https://x.com/DivyanshT91162/status/2078831252145369476)）
2. **技能正逐渐成为代理行为的安装单元，但信任层仍不完整。** skills.sh 提供了类似包管理的跨代理分发方式，而它的作者自己也表示，用户仍需要从目录中筛选出更小、更有用的核心集合。（[来源](https://x.com/undefinedKi/status/2078503194951372897)）
3.**长时运行的智能体正通过可验证的目标和独立审查被投入实际运行。** Claude Code 团队的访谈更看重明确的结束标准、人工审查计划，以及创作者与核验者分离，而不是盲目延长智能体运行时长。 ([来源](https://x.com/petergyang/status/2078846124828545179))
4. **现实中的编码助手选型，考量范围不止是代码生成质量。** 一项基于相同任务说明的测试区分出了速度、工作流完整性、视觉完成度和 token 成本，而“软件工厂”的那则案例还补充了路由、权限和运行时可靠性。 ([来源](https://www.xda-developers.com/built-same-dashboard-claude-code-codex-copilot-winner-surprised-me/))
5. **开发者正将智能体应用于边界明确的产品和编排系统。** Flow Control 将一款硬件配置器限制在文档明确说明的支持边界内，而 Kimi CLI 和 oh-my-opencode-slim 则提供了终端和多智能体执行入口。 ([来源](https://github.com/aaditagrawal/flow-control))
