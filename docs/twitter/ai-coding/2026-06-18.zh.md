# Twitter AI 编程 - 2026-06-18

## 1. 人们在讨论什么

### 1.1 Gemini CLI 的停运变成了一场生态信任测试 🡕

6 月 18 日，Google 的终端策略不再只是纸上谈兵。三条保留条目共同奠定了这一主题：Jack Wotherspoon 的维护者告别帖、官方 @geminicli 的迁移通知，以及一则配图并引用 Google 文档的帖子。随后，回复内容从礼貌致谢转向愤怒，焦点集中在安装失败、遥测门槛，以及 Antigravity CLI 与 Gemini CLI 缺乏 1:1 功能对等。

[@JackWoth98](https://x.com/JackWoth98) [告别](https://x.com/JackWoth98/status/2067697673671450742) (262 个赞、44 条回复、31,344 次浏览、30 次收藏) 面向 Gemini CLI 用户明确表示，Google AI Pro、Ultra 和免费层级的个人账号已于 6 月 18 日停止可用。语气本身也很关键：他称这“是悲伤的一天”，并回复说项目并没有按照他希望的方式结束，这让这次迁移显得更像是被强加的安排，而不是值得庆祝的转变。

[@geminicli](https://x.com/geminicli) [确认](https://x.com/geminicli/status/2067702889837953512) (72 个赞、18 条回复、6,146 次浏览、13 次收藏) 在官方渠道确认了同一截止时间，并明确区分了个人用户与企业用户：Code Assist 许可证持有者和 API 密钥用户不受影响。Google 自己的公开博客文章称，此举是为了整合到 Antigravity 的统一多智能体后端之下，但也承认产品上线时并不具备与 Gemini CLI 的 1:1 功能对等（[博客](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)）。

[@ai_for_success](https://x.com/ai_for_success) [放大了](https://x.com/ai_for_success/status/2067484067269063084) (55 个赞、9 条回复、4,102 次浏览、7 次收藏) 提供了最具体的证据：一张 Google 迁移通知截图写明，Gemini CLI 和 Gemini Code Assist IDE 扩展将于 6 月 18 日停止为个人 Pro、Ultra 和免费用户提供服务。

![Google Developers 迁移通知显示，Gemini CLI 和 Gemini Code Assist 将于 2026 年 6 月 18 日停止为 Google AI Pro、Ultra 以及免费个人用户提供服务](https://pbs.twimg.com/media/HLEtzWraAAEEviS.jpg)

[@robinebers](https://x.com/robinebers) [报道](https://x.com/robinebers/status/2067533536706613319) (25 个赞、10 条回复、1,664 次浏览) 表示，Antigravity IDE 若未启用遥测就无法继续；而 [@_Creation22](https://x.com/_Creation22) [展示了](https://x.com/_Creation22/status/2067294279954043375) (17 个赞、4 条回复、325 次浏览) 则展示了一个卡在中途的安装流程。这些抱怨让这次迁移变成了信任问题，而不只是一次改名。

**讨论洞察：** 最强烈的回复并不是怀旧，而是在追问到底哪里在实际使用中坏掉了：安装循环、Antigravity 与 Antigravity IDE 之间令人困惑的产品拆分，以及在被迫切换后，有人直言 Google“把新模型、CLI 和 Antigravity 都搞砸了”。

**与前一天对比：** 相比 6 月 17 日——当时 Antigravity 还只是更广泛的 Google 编程技术栈讨论中的一个界面——6 月 18 日让这次转变变得不可逆，而且带有明确期限。

### 1.2 工作流录制和操作层更靠近中心位置 🡕

第二大主题不是新模型发布，而是如何更好地把围绕模型的工作流程打包起来。五条保留条目支撑了这一主题：Codex Record & Replay、CLAUDE.md 错误率讨论串、AI DevKit、gstack 和 ClaudeKit Skills。

[@mark_k](https://x.com/mark_k) [发布了](https://x.com/mark_k/status/2067689265941885253) (205 个赞、19 条回复、13,061 次浏览、28 次收藏) 提到了 6 月 18 日 Codex app 的更新日志，重点是 Record & Replay：在 macOS 上向 Codex 演示一次工作流，就能把它变成可复用技能，之后还可以继续管理。OpenAI 的更新日志还补充了影响用户反应的操作限制：该功能依赖 Computer Use，且在上线时无法在 EEA、英国和瑞士使用（[更新日志](https://developers.openai.com/codex/changelog)）。

![Codex app 26.616 更新日志，显示了 Record and Replay、批量自动化历史操作、SSH 深层链接以及 Browser Use 改进](https://pbs.twimg.com/media/HLHn16EWIAAAE3C.jpg)

[@DevAdventur3s](https://x.com/DevAdventur3s) [展示了](https://x.com/DevAdventur3s/status/2067689725100458003) (34 个赞、1 条回复、2,874 次浏览、10 次收藏) 展示了同一功能面向用户的一面：一个插件面板会记录点击、输入文本和窗口内容，最长可达 30 分钟，然后把整个过程转成可通过提示调用的技能。这一点很重要，因为它让“自动化”从营销话术变成了可检查的 UI。

![Codex Record and Replay 插件面板，显示了示例提示词以及关于如何将录制的 macOS 工作流转化为可复用技能的说明](https://pbs.twimg.com/media/HLHon82WoAAMqIF.jpg)

[@cyrilXBT](https://x.com/cyrilXBT) [认为](https://x.com/cyrilXBT/status/2067419526019387560) (60 个赞、5 条回复、4,526 次浏览、11 次收藏) 认为，导致大多数编程智能体失败的主要原因是上下文，而不是模型本身太弱，并总结了随着 CLAUDE.md 指引越来越明确，错误率如何从 41% 降到 11%，再降到 3%。这一论点也得到了构建者而不只是评论者的呼应：[@DanKornas](https://x.com/DanKornas) [发布了](https://x.com/DanKornas/status/2067593408697311734) (10 个赞、6 条回复、559 次浏览、8 次收藏) 将 AI DevKit 描述为带有验证关卡和本地记忆的工作流控制平面；[@oliviscusAI](https://x.com/oliviscusAI) [指出](https://x.com/oliviscusAI/status/2067660787653410989) (5 个赞、1 条回复、184 次浏览、4 次收藏) 提到了 Garry Tan 新近开源的 gstack 工作流；[@tom_doerr](https://x.com/tom_doerr) [链接到](https://x.com/tom_doerr/status/2067492857028489266) (8 个赞、426 次浏览、6 次收藏) 则展示了 ClaudeKit Skills——一个可通过市场安装的可复用智能体技能包。

**讨论洞察：** 回复同时朝两个方向推进：人们喜欢从一次性提示转向可重复工作流，但只要这些工作流被锁死在某个操作系统、某个市场或某个智能体界面上，抱怨也会随之而来。

**与前一天对比：** 6 月 17 日强调的是产品之间的桥接；6 月 18 日则更深入一层，强调产品内部可复用的操作层。

### 1.3 GitHub 和 VS Code 让模型控制变得更显性 🡕

第三个主题显示，GitHub 和 VS Code 正在把模型选择、路由和自动化从隐藏的默认机制，变成可见的产品界面。四条保留条目支撑了这一主题。

[@pierceboggan](https://x.com/pierceboggan) [解释了](https://x.com/pierceboggan/status/2067449111809597803) (29 个赞、4 条回复、1,231 次浏览、5 次收藏) 表示，Copilot Auto 现在会使用一种路由模型，综合考虑推理深度、代码复杂度、调试难度和工具编排需求。GitHub 的配套帖子则表示，提示缓存、延迟工具加载和 HyDRA 路由器，是在减少 token 浪费的同时，仍能在任务需要时向上路由到更强模型的实现机制（[博客](https://github.blog/ai-and-ml/github-copilot/getting-more-from-each-token-how-copilot-improves-context-handling-and-model-routing/)）。

![HyDRA 基准图表，显示 GitHub Copilot Auto 如何在一个由五个模型组成的路由池中权衡结果质量与成本节省](https://pbs.twimg.com/media/HLENrQwWUAAFe5t.jpg)

[@pierceboggan](https://x.com/pierceboggan) [还强调了](https://x.com/pierceboggan/status/2067638151997452597) (23 个赞、3 条回复、1,211 次浏览、5 次收藏) 表示，VS Code Chat 现在可以使用 BYOK 提供商，而无需任何 GitHub 账号或 Copilot 计划。Microsoft 自己的说明明确了范围：BYOK 适用于聊天和智能体工作流，包括离线本地模型配置，但不适用于内联补全或依赖嵌入的功能（[博客](https://code.visualstudio.com/blogs/2026/06/18/byok-vscode)）。

[@github](https://x.com/github) [宣布](https://x.com/github/status/2067704358821597555) (80 个赞、4 条回复、10,455 次浏览、15 次收藏) 表示，MAI-Code-1-Flash 现在已在更多 Copilot 界面中可用；[@_Evan_Boyle](https://x.com/_Evan_Boyle) [添加了](https://x.com/_Evan_Boyle/status/2067378714476953926) (40 个赞、4 条回复、2,087 次浏览、6 次收藏) 则表示，Copilot App 已重新开放 Pro、Pro+ 和 Max 个人计划注册。合在一起看，这些帖子让 6 月 18 日像是 GitHub 在 6 月 17 日 GA 发布后的跟进日。

**讨论洞察：** 主要反弹并不是针对路由本身，而是针对控制权。回复要求更清楚地了解 Auto 何时会选用更便宜的模型、MAI 是否应该进入路由池，以及用户究竟能在多大程度上直接操控工作流。

**与前一天对比：** 6 月 17 日确立了 Copilot App 这一操作界面；6 月 18 日则补上了其下方的控制机制：Auto 路由、BYOK，以及更广泛的 MAI 模型可用性。

### 1.4 智能体原生设计和游戏工作流持续扩张，但回复仍然怀疑 🡒

一个规模较小但持续存在的主题，是 AI 编程正在渗入设计和游戏制作界面。三条保留条目支撑了这一主题。

[@TheShortBear](https://x.com/TheShortBear) [将其描述为](https://x.com/TheShortBear/status/2067410669800956237) (58 个赞、11 条回复、15,044 次浏览、15 次收藏) 将 Unreal Engine 5.8 的实验性 MCP 服务器支持视为迈向用户自定义“增强版 Roblox”游戏创作的一步。被引用的 Unreal 帖子之所以重要，是因为它明确表示，团队可以把任意智能体接入引擎的源码、流水线和工作流。

[@OpenDesignHQ](https://x.com/OpenDesignHQ) [将其定位为](https://x.com/OpenDesignHQ/status/2067551675963822444) (6 个赞、2 条回复、447 次浏览、7 次收藏) 提到了 Open Design——一个以画布编辑、插件和 22+ 个智能体为核心的 Claude Design 开源替代方案。公开仓库说明把这一思路进一步推开：这是一个本地优先的设计工作区，拥有 150 个设计系统、261 个插件、BYOK 模型路由，并支持 Claude Code、Codex、Copilot、Antigravity 及其他编程智能体（[仓库](https://github.com/nexu-io/open-design)）。

[@kr0der](https://x.com/kr0der) [曝光了](https://x.com/kr0der/status/2067737123986538719) (2 个赞、1 条回复、62 次浏览) 展示了一个 Claude Design 的 `/design-sync` 流程：读取代码库的设计系统并复用现有组件。这张截图互动不高，但信号很强，因为它展示了设计工具边界正在往哪里移动。

**讨论洞察：** 回复远没有发布宣传那么乌托邦。在 Unreal 相关讨论下，人们立刻担心 AI 垃圾内容、审核、持久化，以及这个实验性插件是否真的能在 Linux 上运行。

**与前一天对比：** 前一天更多是在讨论编程工具之间的工作流可移植性；6 月 18 日则把同样的逻辑延伸到设计和游戏制作，但近处伴随的是更强的怀疑情绪。

## 2. 什么让人沮丧

### 被迫迁移与安装故障

严重程度：高。最大的挫败感并不来自模型质量，而是用户在新界面还没准备好之前，就被迫迁移过去。[@JackWoth98](https://x.com/JackWoth98) [发布了](https://x.com/JackWoth98/status/2067697673671450742) (262 个赞、44 条回复、31,344 次浏览、30 次收藏) 让个人 Gemini CLI 用户的截止时间一目了然；与此同时，Google 自己的迁移帖子也表示，Antigravity CLI 目前还不具备与 Gemini CLI 的 1:1 功能对等性（[博客](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)）。在用户侧，[@robinebers](https://x.com/robinebers/status/2067533536706613319) [表示](https://x.com/robinebers/status/2067533536706613319) (25 个赞、10 条回复、1,664 次浏览) 表示，Antigravity IDE 若不启用遥测就无法打开；[@_Creation22](https://x.com/_Creation22) [展示了](https://x.com/_Creation22/status/2067294279954043375) (17 个赞、4 条回复、325 次浏览) 则展示了一个一直转圈的安装流程，回复里还称现在可能同时需要 Antigravity 和 Antigravity IDE。人们目前的应对方式包括：能拖就拖、退回到仍受支持的企业版/API 密钥路径，或反复重装多个 Google 界面直到有一个能用。这个方向值得投入，因为故障发生在任何有效编码开始之前。

![Antigravity 安装截图，显示应用在设置过程中卡住；随后用户在回复中澄清，现在可能需要同时安装 Antigravity 和 Antigravity IDE](https://pbs.twimg.com/media/HLCBFgcbIAArcLH.jpg)

### 仓库上下文依然不足且不透明

严重程度：高。[@sudoingX](https://x.com/sudoingX) [询问](https://x.com/sudoingX/status/2067701388709364130) (16 个赞、5 条回复、1,474 次浏览) 追问为什么 Codex 仍不默认给订阅用户启用 1M 上下文模式，并把痛点压缩成一句话：用户不该还得调试智能体到底有没有读够整个仓库。[@cyrilXBT](https://x.com/cyrilXBT) [使用了](https://x.com/cyrilXBT/status/2067419526019387560) (60 个赞、5 条回复、4,526 次浏览、11 次收藏) 则从反方向表达了同一个问题，认为大多数失败来自上下文缺失，而不是模型太弱，并引用了随着指引越来越明确，错误率从 41% 降到 11%，再降到 3%。构建者的应对方式是加 sidecar，而不是信任默认设置：AI DevKit 提供本地记忆和验证关卡，gstack/ClaudeKit 则围绕智能体封装了更明确的工作流规则。这个方向值得投入，因为痛点是结构性的，并且会在不同工具中反复出现，而不只是某一家厂商讨论串里的个案。

### 新能力仍然被硬门槛挡在门外

严重程度：中。当天也反复出现了对访问限制的沮丧：一些本来很吸引人的功能，仍被各种条件卡住。[@mark_k](https://x.com/mark_k) [强调了](https://x.com/mark_k/status/2067689265941885253) (205 个赞、19 条回复、13,061 次浏览、28 次收藏) 提到了 Codex Record & Replay，但回复立刻抱怨它仅支持 macOS；而 OpenAI 自己的更新日志则写明，该功能需要 Computer Use，且在上线时无法在 EEA、英国和瑞士使用（[更新日志](https://developers.openai.com/codex/changelog)）。在 GitHub 一侧，[@pierceboggan](https://x.com/pierceboggan/status/2067665332307943621) [表示](https://x.com/pierceboggan/status/2067665332307943621) (48 个赞、7 条回复、1,419 次浏览) 表示，MAI-Code-1-Flash 正在向个人 Copilot 计划逐步推出，但回复仍在追问这个模型是否已经可见，以及混合模型行为是否可调试。目前的权宜之计是等待分阶段发布、切换到其他地区或设备，或者继续使用功能较弱但更可预测的旧流程。这个方向值得投入，但切入口更窄，因为平台厂商已经在逐步推出部分修复方案。

## 3. 人们希望存在什么

### 持久的仓库记忆与上下文控制

最明确的实际诉求，是让智能体可靠地理解仓库，而不是让用户去猜。[@sudoingX](https://x.com/sudoingX) [降低了](https://x.com/sudoingX/status/2067701388709364130) (16 个赞、5 条回复、1,474 次浏览) 把问题归结为上下文：在智能体编程产品里，用户不该还要调试工具到底有没有读够代码库。[@cyrilXBT](https://x.com/cyrilXBT/status/2067419526019387560) [回应](https://x.com/cyrilXBT/status/2067419526019387560) (60 个赞、5 条回复、4,526 次浏览、11 次收藏) 给出的也不是模型层面的答案，而是工作流层面的答案：真正能把错误率压下来的，是明确规则和检查点。AI DevKit、gstack 和 ClaudeKit 之所以存在，就是因为这个需求既现实又紧迫：人们希望记忆、约定和验证能跨会话保留下来，而不是让每一条提示词都不断膨胀。机会：直接。

### 对密钥安全的智能体执行

第二个需求，是让智能体能够接触真实系统，同时不把密钥带进聊天记录。[@glcst](https://x.com/glcst) [发布了](https://x.com/glcst/status/2067576762481938545) (19 个赞、4 条回复、857 次浏览、7 次收藏) 提到了 keymaxxer：它专门把 token 存在本地加密保险库里，让智能体请求具名 secrets，并要求对敏感执行进行批准。仓库说明把潜台词写得很明白：常见替代方案就是把 API 密钥贴进 shell、提示词，或者两者都贴。这是一个具有即时运营价值的实际需求，因为智能体时代会增加接触凭据的命令、工具和提供商数量。机会：直接。

### 能跨厂商和界面变化存活的工作流包

信息流还显示出一种愿望：即便前端工具变了，工作流也应该能继续迁移。Google 强制个人 Gemini CLI 用户转向 Antigravity；GitHub 推出了 BYOK 和 Auto；构建者则以 AI DevKit、gstack、ClaudeKit Skills 和 Open Design 这样的可移植层作为回应。[@DanKornas](https://x.com/DanKornas/status/2067593408697311734) [描述了](https://x.com/DanKornas/status/2067593408697311734) 将 AI DevKit 描述为可在 Claude Code、Cursor、Codex CLI、Gemini CLI 和 Copilot 之间复用的一套工程工作流；[@tom_doerr](https://x.com/tom_doerr/status/2067492857028489266) [链接到](https://x.com/tom_doerr/status/2067492857028489266) 展示了一个可复用的技能市场；[@OpenDesignHQ](https://x.com/OpenDesignHQ/status/2067551675963822444) [推出了](https://x.com/OpenDesignHQ/status/2067551675963822444) 则把同样的可移植性带进了设计产物。这个需求很实际，但竞争也在加剧，因为多个构建者已经从不同角度切入同一层可移植性。机会：竞争性。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| Antigravity CLI / IDE | 编程智能体界面 | (+/-) | 统一多智能体后端、更快的 Go CLI、保留 Gemini CLI 的关键功能、企业路径仍受支持 | 个人用户被迫迁移、上线时不具备 1:1 功能对等、存在安装和遥测方面的抱怨 |
| OpenAI Codex app | 智能体工作区 | (+/-) | Record & Replay 可将 macOS 上演示过的工作流变成可复用技能；Browser Use 和自动化控制持续扩展 | 新功能仅支持 macOS，在 EEA/英国/瑞士不可用，用户仍在质疑上下文限制 |
| GitHub Copilot Auto + App | 智能体工作区 / 路由 | (+) | 面向任务的模型路由、提示缓存、延迟工具加载、重新开放个人访问、可见的自动化工作流 | 用户仍希望获得更高的路由透明度、更明确的模型控制，以及更少的发布延迟 |
| VS Code BYOK | 编辑器模型层 | (+) | 无需 GitHub 账号或 Copilot 计划即可使用，支持提供商密钥和本地模型，扩展到聊天与智能体工作流 | 不覆盖内联补全或高度依赖嵌入的功能；提供商计费仍需单独处理 |
| AI DevKit | 智能体控制平面 | (+) | 一份配置、一个控制台、本地记忆、跨智能体通信、验证关卡，以及跨工具共享的生命周期 | 增加了一层需要安装和维护的基础设施；价值取决于团队执行纪律 |
| keymaxxer | 密钥管理器 / MCP | (+) | 让密钥不进入对话上下文，只在命令执行时注入，并为敏感用法加入审批 | 仍需本地解锁/审批流程，也无法消除同一用户设备本身的风险 |
| Open Design | 智能体设计工作区 | (+/-) | 本地优先、开源，兼具设计系统和插件，支持多种编程智能体 CLI 以及 BYOK 模型路由 | 独立设计界面仍在稳定中，生态跨度大也增加了配置复杂度 |
| gstack | Claude Code 工作流工具包 | (+) | 通过大量专业命令，把 Claude Code 变成结构化的规划/评审/QA/安全/发布系统 | 工作流强主观，主要围绕 Claude Code，而非完全模型无关的用法 |
| ClaudeKit Skills | 技能市场 / 工作流库 | (+) | 可安装的技能包、覆盖上下文工程、提供 MCP 管理子智能体、可复用的仓库工作流 | 主要受益者仍是已经投入 Claude Code 插件模式的团队 |

整体满意度偏务实，而非意识形态式站队。人们会奖励那些把上下文、自动化或安全做得更显性的工具；而当同类产品把限制藏在分阶段发布、操作系统门槛或迁移断崖之后时，用户就会反弹。

最明显的迁移模式，是远离对单一界面的依赖。Google 把个人用户从 Gemini CLI 推向 Antigravity；而 GitHub 和 VS Code 则通过 Auto、BYOK 和 MAI-Code-1-Flash 扩大模型选择，朝相反方向移动。

竞争分野也不再只是模型对模型，而是厂商原生工作区对可移植控制平面、原始上下文窗口对记忆/检索层，以及直接 shell 访问对需要审批的密钥执行。

## 7. 机会在哪里

**[+++] 经得起迁移的智能体操作层** —— 第 1、3、4、5 节的证据共同指向这一点：Google 强制用户离开 Gemini CLI，GitHub 和 VS Code 扩大模型选择，而构建者则以 AI DevKit、gstack、ClaudeKit Skills 和 Open Design 作出回应。最强的机会，是打造一层即使底层智能体界面变化，也能保留记忆、规则和交接的工作流层。

**[+++] 面向智能体上下文、验证与密钥的信任基础设施** —— 第 2 节对上下文的抱怨、第 3 节对持久仓库记忆和密钥安全执行的需求，以及第 5 节 AI DevKit 和 keymaxxer 的发布，都指向同一个缺口。这是一个强机会，因为痛点既直接又具操作性：用户并不相信智能体看得够多、验证得够充分，或能足够安全地处理凭据。

**[++] 可见的路由与 BYOK 控制平面** —— GitHub 的 HyDRA/Auto 工作、VS Code 的 BYOK 推出，以及 MAI-Code-1-Flash 的扩展，都表明用户希望模型选择是显性的、可操控的。这个机会中等，因为主要厂商已经在这里出货，但回复仍显示出对成本滑杆、更好的调试可见性和更顺畅发布流程的未满足需求。

**[+] 智能体原生设计与游戏流水线** —— Unreal 的 MCP 支持、Open Design，以及 Claude Design 的 `/design-sync` 流程，都指向一个覆盖代码、设计和内容的更广泛智能体栈。这个信号仍在形成中，而非主导趋势，因为相关讨论同时暴露了对垃圾内容、审核，以及这些集成是否真的稳定可靠的担忧。

## 8. 要点总结

1. **6 月 18 日把 Google 的编程智能体转型变成了一次被强制执行的迁移事件，而不再是渐进式的偏好变化。** 维护者告别帖、官方 Gemini CLI 通知和 Google 公开迁移帖都在传达同一件事：个人用户无论是否准备好，都在这一天被切换过去。（[来源](https://x.com/JackWoth98/status/2067697673671450742)）
2. **工作流录制与流程打包的重要性，超过了一次全新的模型发布。** Codex Record & Replay、CLAUDE.md 纪律、AI DevKit、gstack 和 ClaudeKit Skills 都指向围绕模型构建可复用的操作层，而不是只对原始权重本身兴奋。（[来源](https://x.com/mark_k/status/2067689265941885253)）
3. **GitHub 和 VS Code 的竞争点，已经是路由、模型选择和智能体运营，而不只是自动补全。** HyDRA 路由、无需 Copilot 账号的 BYOK、重新开放的 Copilot App 注册，以及 MAI-Code-1-Flash 的可用性，都扩大了围绕编程工作的控制界面。（[来源](https://x.com/pierceboggan/status/2067449111809597803)）
4. **最强的构建者模式，是围绕智能体做中间件：记忆、验证、密钥和设计系统。** AI DevKit、keymaxxer、Open Design、gstack 和 ClaudeKit 分别瞄准了基础智能体仍然留空的工作流缺口。（[来源](https://x.com/DanKornas/status/2067593408697311734)）
