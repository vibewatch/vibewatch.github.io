# Twitter AI 编程 - 2026-09-01

## 1. 人们在讨论什么

### 1.1 Google 把 Antigravity 变成了当天最显眼的编程栈 (🡕)

Google 的编程栈主导了当天的讨论，至少有 5 条独立的高信号内容都在围绕它展开：新的 `/boost` 模式、更大范围的 Gemini 3.7 Flash 展示、一条公开的研究级成果宣称、一条直接建议使用 `/teamwork-preview` 的帖子，以及用户把近期 bug 重新解释成容量问题而不是采用不足的问题。

[@antigravity](https://x.com/antigravity) [发布了](https://x.com/antigravity/status/2094562154657493109) (886 个赞，60 条回复，45,399 次浏览，317 次收藏) `/boost`，把它定位成处理复杂软件任务的更深度推理模式。公开的 `/boost` 文档写得很具体：它使用一个 3 阶段多智能体流水线，带隔离的 worktrees、专门子智能体和独立回归检查；而讨论串里的回复，则把适用场景进一步收窄到了棘手 bug 修复、算法优化、非平凡重构，以及根因排查。这让它看起来不像一次普通模型升级，而更像是 Antigravity 运行框架内部新增的一档付费工作流层级。 ([docs](https://antigravity.google/docs/boost/))

[@Google](https://x.com/Google) [集中展示了](https://x.com/Google/status/2094546921197015547) (692 个赞，73 条回复，151,041 次浏览，175 次收藏) 团队如何在 Google AI Studio、Antigravity 和 Gemini App Spark 里使用 Gemini 3.7 Flash，点名了实时网站生成器、3D 物理模拟器、摄像头工具，以及个性化海滩野外指南等具体产物。Google 还在回复里把这些例子拆得更细，比如用 Google Sheets 做视频生成器，或者做一个单次生成的 Kerr 黑洞模拟器，这让整条帖子更像一次产品合集展示，而不是单个宣传短片。

[@ai_for_success](https://x.com/ai_for_success) [重点提到](https://x.com/ai_for_success/status/2094747233564627047) (249 个赞，22 条回复，11,020 次浏览，43 次收藏) 了 Google 的另一条更技术化宣称：Antigravity 加 Gemini 3.7 Flash，在 FOCS、JMLR 等语境下解出了 7 个公开问题，其中包括给 Knuth 的 Cycles Conjecture 写出 40 多页经过 Lean 验证的证明，以及构建一个 cycle-accurate、out-of-order 的 RISC-V 模拟器，把 xv6 启动到了 shell。之所以要看截图，是因为里面的细节比推文正文那一句压缩说法更完整。

[@ksprashu](https://x.com/ksprashu) [告诉](https://x.com/ksprashu/status/2094497945232323003) (29 个赞，5 条回复，1,966 次浏览，19 次收藏) 付费 Google AI 用户，“先把别的都放下，开始用 `/teamwork-preview`”；而 [@thtbee_](https://x.com/thtbee_) [则认为](https://x.com/thtbee_/status/2094762720302399982) (137 个赞，20 条回复，12,597 次浏览，11 次收藏)，最近暴露出来的 bug，并不是因为 Gemini 3.7 Flash 没人用，而是因为它“被需求打爆了”；他还引用 Google 自家的 Evan Otero 的说法，称它是增长最快的模型，而 Google 正在补容量。

### 1.2 智能体信任从抽象安全讨论，转向具体的安全与验证工作 (🡕)

4 条独立的讨论串都在推同一件事：编程智能体如今已经被信任到足以碰真实工作，因此社区的注意力开始集中到欺诈控制、恶意工具攻击、敌对仓库，以及能证明输出可安全上线的验证闭环上。

[@thdxr](https://x.com/thdxr) [警告](https://x.com/thdxr/status/2094606303393906912) (194 个赞，15 条回复，9,979 次浏览，24 次收藏) Hermes 和 OpenCode Go 用户尽快更新智能体，并设置一个自定义 user agent，因为“现在有多得离谱的欺诈在发生”。回复没有稀释这个判断，反而把它说得更尖锐：有人提到自己用 Hermes 时被临时封禁，有人说在这套栈里身份“不是可有可无”，还有人认为，如果没有 agent ID、task ID 和 approval receipt，光有 user agent 根本不够。

[@rohanpaul_ai](https://x.com/rohanpaul_ai) [概括了](https://x.com/rohanpaul_ai/status/2094673357627101522) (1 个赞，2 条回复，758 次浏览，2 次收藏) 新论文《ContextLeak: Exfiltrating LLM Agent Context via Malicious Tools》，而公开的 arXiv 摘要也证实了它的机制：研究者用强化学习构造恶意工具名和描述，诱导智能体既选中这个工具，又把提示词和运行时上下文泄漏到工具参数里。推文里给出的数字也足够具体：在 user-prompt 攻击上，工具被选中的概率是 92%；在 conversation-history 攻击上是 89%；而只用一个开源代理训练出来的攻击，在 Claude Code 测试里也能做到 100 次里选中 22 次。 ([paper](https://arxiv.org/abs/2608.27800))

![ContextLeak 论文摘要图，描述了恶意工具描述如何从 LLM 智能体中窃取运行时上下文](https://pbs.twimg.com/media/HRGPSjlagAAqyPO.jpg)

[@Ax_Sharma](https://x.com/Ax_Sharma) [点名了](https://x.com/Ax_Sharma/status/2094841596919382070) (4 个赞，2 条回复，101 次浏览，1 次收藏) GitSpawn，而 Manifold Security 的公开文章说，漏洞出在后台的 git 上下文收集：只要打开一个不受信任的仓库，一些智能体就会在 workspace-trust 提示出现之前，先在宿主机上执行代码。Manifold 公布了 7 个智能体中的 8 个发现，并表示在发表时其中 4 个仍未修复。 ([research](https://www.manifold.security/blog/ai-coding-agents-git-hijack))

![GitSpawn 信息图展示了不安全的 git 上下文收集如何让不受信任的仓库在多个 AI 编程智能体中执行代码](https://pbs.twimg.com/media/HRJdnpDXEAACtv-.jpg)

[@ryanvogel](https://x.com/ryanvogel) [展示了](https://x.com/ryanvogel/status/2094788081148694964) (13 个赞，5 条回复，1,383 次浏览，14 次收藏) 这个信任故事的另一面：一个面向 OpenCode mobile 的远程工作流，让一台无头 EC2 Mac 通过 serve-sim 跑 iOS、macOS 和 iPadOS 测试，然后在进入 TestFlight 之前，再用截图验证来把关。配图之所以特别有说服力，是因为它非常具体：PR #9 已经可以评审，附上了竖屏和横屏截图，还有 65 个测试通过。

![OpenCode 智能体日志显示，在评审前已为 PR #9 附上竖屏和横屏截图，并有 65 个测试通过](https://pbs.twimg.com/media/HRIufDJXgAA5mkW.jpg)

**讨论要点：** 回复没有人在问怎么写更好的提示词。人们问的是审计轨迹、明确的智能体身份，以及像截图验证这样的通过条件，怎么才能让一次远程运行对人类来说也说得清楚。

**与前日对比：** 前一天围绕可靠性的讨论，重点还更多在重置、宕机和重试风暴。到了今天，注意力更靠近宿主机本身：信任提示之前到底运行了什么，哪些上下文会泄漏给工具，以及人在什么证据下才愿意相信智能体真的把任务做完了。

### 1.3 可复用规则与技能，成了应对 AI 编程低质输出的首选答案 (🡕)

当天围绕“如何减少 AI 糊活”的讨论，并不主要是换模型，而是把更好的判断固化进技能、工作流和审查门槛里。至少有 5 条独立内容，都在朝这个设计方向收敛。

[@LimestoneHQ](https://x.com/LimestoneHQ) [表示](https://x.com/LimestoneHQ/status/2094539810043986116) (6 个赞，3 条回复，4,399 次浏览，2 次收藏)，大多数团队停在了工具采用这一步，从来没走到生产速度，于是他们围绕 V.U.E. 做了一个 “Velocity Framework”：每一行 AI 生成代码都必须经过验证、被理解，而且说得清楚。图片把剩下的运行模型也补齐了：AI 高参与的部分留在样板代码、测试、重构、CRUD 和文档上，而安全、支付和架构仍然完全由人审查。

![Velocity Framework 图示将 V.U.E. 定义为 Verified、Understood、Explainable，并区分 AI 高参与工作与仅限人类决策的环节](https://pbs.twimg.com/media/HRFM2diXgAA-rug.png)

[@diamai_](https://x.com/diamai_) [提到了](https://x.com/diamai_/status/2094834935886381090) (23 个赞，9 条回复，466 次浏览，11 次收藏) `i-have-adhd`，这是一套适用于 Claude Code、Codex、Cursor、Gemini CLI 和 GitHub Copilot 的规则集，强制智能体先说下一步、把步骤编号、压掉跑题内容，并以一个具体的下一步收尾。公开的 GitHub 元数据还显示，这个仓库已有 26,440 个星标；而最佳回复把价值说得很准：它真正降低的是决策负担，而不只是把输出变短。 ([repo](https://github.com/ayghri/i-have-adhd))

[@Sejan71](https://x.com/Sejan71) [把](https://x.com/Sejan71/status/2094734140012917173) (1 个赞，5 条回复，148 次浏览) Taste Skill 定位成一种修复方式，用来对抗那些“满脸都写着 AI”的网站，承诺为 Claude Code、Codex、Cursor 和 Gemini CLI 带来更好的布局、字体、留白、动效，以及更贴项目本身的视觉风格。关联的 GitHub 仓库目前显示 83,354 个星标，并把自己描述成一个面向 AI 智能体的 anti-slop 前端框架。 ([repo](https://github.com/Leonxlnx/taste-skill))

[@DanKornas](https://x.com/DanKornas) [整理了](https://x.com/DanKornas/status/2094809748436553804) (3 个赞，2 条回复，940 次浏览，8 次收藏) 一个更大的生态入口 Awesome Agent Skills——一个拥有 33,575 个星标、收录 1000+ 技能的索引，覆盖官方团队和社区构建者；而他另一条关于 [OwnYourCode](https://x.com/DanKornas/status/2094911684578013227) 的帖子 (7 个赞，3 条回复，393 次浏览，5 次收藏)，则在推广一个围绕 spec-driven development 和“在结束前先解释清楚”的 6 道门 Claude Code 工作流。 ([Awesome Agent Skills](https://github.com/VoltAgent/awesome-agent-skills), [OwnYourCode repo](https://github.com/DanielPodolsky/ownyourcode))

**讨论要点：** 这簇内容里最强的一条回复，来自 i-have-adhd 下面：它认为“更好的输出规则，可能比更聪明的模型更有用”，因为真正的收益是决策负担更低。这和 V.U.E. 以及 OwnYourCode 的逻辑是同一条线：AI 编码失败更像判断问题，而不只是打字问题。

**与前日对比：** 技能和工作流定制此前已经在背景里出现过，但今天的表达明显更收束了：不再是“这里又有一个新工具”，而是“这里是你的智能体缺失的审查门槛、输出契约或视觉标准”。

### 1.4 成本控制成了产品特性，而不再只是附带抱怨 (🡒)

前一天最响的配额抱怨并没有消失，但当天的讨论重心，已经转向那些能降低成本、抚平限额，或干脆绕开托管定价的工具和习惯。

[@daanisharif](https://x.com/daanisharif) [解释了](https://x.com/daanisharif/status/2094780110826274876) (8 个赞，3 条回复，361 次浏览，1 次收藏) 什么叫“智能体 token 税”：编程智能体会不断重发之前的上下文、工具历史和已经读过的文件，于是团队会反复为模型早就处理过的内容付钱。同一条帖子还引用了 SOMA 的说法：在 GitHub Copilot + DeepSeek V4 Pro 上，大约能减少 10% 的上下文；但它也补上了一条很重要的保留意见——这种节省高度依赖具体工作流，并不是普适定律。

[@Im_IrushiK](https://x.com/Im_IrushiK) [发了一张预算图](https://x.com/Im_IrushiK/status/2094822642243322211) (27 个赞，9 条回复，2,852 次浏览)，认为 Codex 的用量体验已经变得更紧、更不稳定，而在公开额度跟踪里 Claude Code Pro 看起来更平稳。真正让这条帖子有用的，是图本身，而不只是推文文字。

![额度趋势图对比了 2026 年以来 Claude Code Pro 和 Codex Plus 的表现，突出 Codex 更强的波动性和更低的当前周价值](https://pbs.twimg.com/media/HRJOFsqbwAA3Odg.jpg)

[@starmexxx](https://x.com/starmexxx) [给出了](https://x.com/starmexxx/status/2094762912296435769) (26 个赞，9 条回复，1,267 次浏览，21 次收藏) 当天最强的本地优先定价论点，围绕的是 `textgen`：一个拥有 47,595 个星标的本地 LLM 桌面应用，提供兼容 OpenAI 和 Anthropic 的 API、tool-calling，以及 100% 私有执行，被定位成每月 200 美元托管订阅的替代品。回复关注的不是跑分，而是一个更实际的判断：本地 AI 正在变成一整套栈，而不只是“终端里的一个模型”。 ([repo](https://github.com/oobabooga/textgen))

**讨论要点：** 看得见的应对方式都很具体：压缩上下文、提高对会话定价的认知、公开跟踪预算，以及用本地 API 让现有工具改连更便宜的后端，而不用重写整套工作流。

**与前日对比：** 在 2026-08-31，限额重置本身还是笑梗。到了 2026-09-01，更有意思的部分已经变成围绕这些限额搭出来的权宜层。

## 2. 令人困扰的问题

### 智能体栈中不安全的后台行为

最严重的挫败感，并不是模型质量，而是信任边界。[@thdxr](https://x.com/thdxr) [提到](https://x.com/thdxr/status/2094606303393906912) (194 个赞，15 条回复，9,979 次浏览，24 次收藏) Hermes 和 OpenCode Go 周围“有多得离谱的欺诈在发生”，而回复又把这个问题往更具体的控制缺口上推：临时封禁、身份信号缺失，以及 agent ID、task ID 和 approval receipt 的必要性。由 [@rohanpaul_ai](https://x.com/rohanpaul_ai) [概括的](https://x.com/rohanpaul_ai/status/2094673357627101522) (1 个赞，2 条回复，758 次浏览，2 次收藏) ContextLeak 论文，则展示了另一条滥用路径：恶意工具描述会诱导智能体把提示词和运行时上下文泄露到工具参数里。GitSpawn 则把同样的挫败感直接推进到了宿主机层面：[@Ax_Sharma](https://x.com/Ax_Sharma) [点名了](https://x.com/Ax_Sharma/status/2094841596919382070) (4 个赞，2 条回复，101 次浏览) 这个问题，而 Manifold Security 记录了一类 bug——只要打开一个不受信任的仓库，就可能在信任提示之前先执行代码。严重程度：高。这非常值得围绕它做产品，因为用户现在要的不是更会写字，而是明确的身份、输入清洗，以及后台动作确实安全的证据。

### 团队仍不相信原始 AI 输出能直接变成生产代码或完工 UI

当天很多最强的工作流帖子之所以存在，本身就是因为人们不相信“它跑完了”就等于“它值得留下来”。[@LimestoneHQ](https://x.com/LimestoneHQ) [表示](https://x.com/LimestoneHQ/status/2094539810043986116) (6 个赞，3 条回复，4,399 次浏览)，团队可以买 Copilot seat、提高产出，但未必能提高生产速度，于是它用 V.U.E. 审查规则来补这个缺口。[@DanKornas](https://x.com/DanKornas) [推广了](https://x.com/DanKornas/status/2094911684578013227) (7 个赞，3 条回复，393 次浏览，5 次收藏) OwnYourCode，把它直接定位成对“你自己都解释不清的代码”的回应；而 [@Sejan71](https://x.com/Sejan71) [则把](https://x.com/Sejan71/status/2094734140012917173) (1 个赞，5 条回复，148 次浏览) Taste Skill 定义成修复那些长得都一样的 AI 生成界面的方法。就连 [@ryanvogel](https://x.com/ryanvogel) [也从另一个角度得出了同样的结论](https://x.com/ryanvogel/status/2094788081148694964) (13 个赞，5 条回复，1,383 次浏览，14 次收藏)：让远程测试工作流值得信任的，不是自动化本身，而是截图验证。严重程度：中到高。人们现在最常用的权宜方案，是加门、看截图、收紧输出格式，并缩小 AI 自主范围。

### 用量限制如今正被体验成一个上下文管理问题

配额痛感还在，但这天的讨论已经更技术化了。[@daanisharif](https://x.com/daanisharif) [解释了](https://x.com/daanisharif/status/2094780110826274876) (8 个赞，3 条回复，361 次浏览)，智能体如何反复为已经处理过的上下文付费，把长时工作变成一种 token 税，甚至造成几个小时的锁定。[@Im_IrushiK](https://x.com/Im_IrushiK) [则认为](https://x.com/Im_IrushiK/status/2094822642243322211) (27 个赞，9 条回复，2,852 次浏览)，在公开跟踪里 Codex 的预算行为看起来比 Claude Code Pro 更紧、更不稳定；而 [@codeglitch](https://x.com/codeglitch) [指出](https://x.com/codeglitch/status/2094900757082370105) (2 个赞，2 条回复，390 次浏览)，Anthropic 那条最常被重复的定价 卖点，本质上只是 cache-read 折扣，而不是普遍容量上升。严重程度：中。这很值得围绕它做产品，因为人们已经在主动尝试压缩层、预算仪表盘、会话习惯建议和本地后端，而不再等厂商自己把定价简化掉。

## 3. 人们期望的功能

### 可验证、且把控制权留给人的智能体工作流

人们想要的并不是更少的 AI，而是那种会在理解开始丢失之前停下来的 AI。[@LimestoneHQ](https://x.com/LimestoneHQ) [想要](https://x.com/LimestoneHQ/status/2094539810043986116) (6 个赞，3 条回复，4,399 次浏览) 每一行生成代码都 Verified、Understood、Explainable，而 [@DanKornas](https://x.com/DanKornas) [推广](https://x.com/DanKornas/status/2094911684578013227) (7 个赞，3 条回复，393 次浏览，5 次收藏) 的工作流，其核心前提正是“AI 负责引导，你负责构建”。[@ryanvogel](https://x.com/ryanvogel) [又补上了](https://x.com/ryanvogel/status/2094788081148694964) (13 个赞，5 条回复，1,383 次浏览，14 次收藏) 这个需求的操作化版本：只有当截图和通过的测试摆在眼前，一次运行才值得信任。这是一个现实而紧迫的需求。机会：直接。

### 能跨工具迁移、又不用把私有工作送到托管层的技能

多条帖子都收敛到同一个愿望：一旦团队摸索出一个好用的输出契约或工作流，它就不该被锁死在某个厂商表面里。[@DanKornas](https://x.com/DanKornas) [重点提到](https://x.com/DanKornas/status/2094809748436553804) (3 个赞，2 条回复，940 次浏览，8 次收藏) 一个覆盖 Claude Code、Codex、Cursor、Gemini CLI、GitHub Copilot 等工具的 1000+ 技能索引，而他关于 OpenSkills 的帖子 ([tweet](https://x.com/DanKornas/status/2094855043786932434)) 则把这个想法再往前推：通过 MCP 在本地运行技能。[@diamai_](https://x.com/diamai_) [展示了](https://x.com/diamai_/status/2094834935886381090) (23 个赞，9 条回复，466 次浏览，11 次收藏) 对可迁移输出规则的需求，而 [@Sejan71](https://x.com/Sejan71) [也展示了](https://x.com/Sejan71/status/2094734140012917173) (1 个赞，5 条回复，148 次浏览) 对可迁移 UI 审美约束的同一种需求。这既现实，也带战略意义。机会：竞争较强。

### 在不改动整套工作流的前提下降低上下文拖累

当天最强的预算帖子，本质上都是在提一种“隐形基础设施”的功能需求。[@daanisharif](https://x.com/daanisharif) [想要](https://x.com/daanisharif/status/2094780110826274876) (8 个赞，3 条回复，361 次浏览) 的不是一个新 IDE，而是更低的重复上下文税；SOMA 的核心主张也正是“同一个智能体、同一个模型、同一套工作流——只是要少花一点 token”。[@starmexxx](https://x.com/starmexxx) [想要](https://x.com/starmexxx/status/2094762912296435769) (26 个赞，9 条回复，1,267 次浏览，21 次收藏) 的，则是让 Claude Code、Cursor 和 Codex 这种现有工具去连接一个兼容 OpenAI 的本地后端，而不是再买一个新订阅；而 [@codeglitch](https://x.com/codeglitch) [认为](https://x.com/codeglitch/status/2094900757082370105) (2 个赞，2 条回复，390 次浏览)，如果用户不能真正留在同一个会话里享受 cache-read，所谓定价优化就没太大意义。这是一个现实的基础设施需求，而且人们已经很愿意尝试。机会：竞争较强。

### 让 AI 生成界面看起来更有设计意图、而不是千篇一律的更好方法

Taste Skill 的整套论点，就是 AI 做出来的网站总在重复同样的布局、留白和动效，而回复也认同，智能体需要更强的设计标准。这个需求既现实，也带一点情绪成分：构建者想要的，是一眼看上去就不像机器批量吐出来的结果。由于这个方向已经有一个拥有大量开源采用的领先方案，所以它更像是对更好默认值和更强审美层的需求，而不是一片空白。机会：偏愿景型到竞争型。

## 7. 机会在哪里

**[+++] 智能体的信任、验证与安全上下文处理** —— 这是最强的机会，因为失败侧和解决侧都在给它加证据。GitSpawn 展示了不受信任仓库带来的宿主机执行风险，ContextLeak 展示了恶意工具描述如何窃取运行时上下文，而 Hermes/OpenCode Go 那条讨论串则给出了围绕欺诈和身份缺失的真实运营痛感。与此同时，截图验证、V.U.E. 和 OwnYourCode 又都指向了同一个产品方向：更好的证据、更小的作用域，以及明确的人类检查点。

**[++] 能跨厂商迁移的技能层** —— Taste Skill、`i-have-adhd`、Awesome Agent Skills 和 OpenSkills 都存在，是因为人们想把一种行为能力从 Claude Code 带到 Codex、Gemini CLI 或 GitHub Copilot，而不想每换一家就重写一遍。这是一个有意义的机会，因为生态已经大到让发现、筛选和本地执行分别长成了独立产品。

**[++] 保留界面、但改写成本结构的成本控制基础设施** —— SOMA、`textgen`、公开预算图，以及解释 cache-read 的帖子，都指向同一种需求：开发者想继续用熟悉的智能体前端，但又想压低重复上下文的成本，或者把后端换成更便宜的选择。这个机会是中强，因为它同时出现在抱怨、权宜方案和已经发货的产品上，而不是某一家的定价页里单独存在。

**[+] 现有开发界面中的引导式专家工作流** —— Antigravity 的 `/boost`、`/teamwork-preview`，以及 GitHub Copilot 的现代化改造智能体，都说明市场对那种围绕规划、审计和验证来包装难任务的模式有兴趣。这个方向还处在萌芽阶段，而不是已经证实的机会，因为今天的证据更多来自产品动作本身，而不是大规模独立用户证词。

---
## 8. 要点总结

1. **Google 今天花了很大力气，把 Antigravity 讲成一整套工作流栈，而不只是模型入口。** `/boost`、`/teamwork-preview`、Gemini 3.7 Flash 展示，以及那张公开问题截图，都在把同一个方向讲得更完整：更结构化、更长时的编程工作，正在被包进这个运行框架里。 ([source](https://x.com/antigravity/status/2094562154657493109))
2. **围绕智能体采用，信任已经成了主要瓶颈。** Hermes/OpenCode Go 的欺诈报告、ContextLeak 里的恶意工具窃取，以及 GitSpawn 里信任提示前的仓库执行，都说明后台行为正比原始生成质量受到更多审视。 ([source](https://x.com/thdxr/status/2094606303393906912))
3. **验证正在变成产品特性，而不只是最佳实践。** V.U.E.、OwnYourCode 的多道质量门，以及 Ryan Vogel 那套带截图验证的 mobile 测试流，讲的都是人类如何基于证据做判断，而不是靠信念信任一次智能体运行。 ([source](https://x.com/ryanvogel/status/2094788081148694964))
4. **可复用技能正在成为修补低质输出的首选手段。** `i-have-adhd`、Taste Skill、Awesome Agent Skills 和 OpenSkills，从不同角度处理的是同一个问题：更好的输出契约、更强的设计默认值、更容易的发现，以及本地/私有执行。 ([source](https://x.com/diamai_/status/2094834935886381090))
5. **围绕成本控制的讨论，已经上移到了模型之上的那一层。** 今天值得注意的产品，不只是新模型，而是模型外面的上下文压缩、本地 API 兼容运行时、预算跟踪，以及围绕 cache-read 和新会话之间差异的定价认知。 ([source](https://x.com/daanisharif/status/2094780110826274876))
6. **一些最值得注意的构建能量，其实藏在用户界面下面。** Mercor 公开了面向知识工作智能体的 RL 配方，而 GitHub Copilot 和 Codex 则都在把围绕核心模型的操作表面做得更结构化。 ([source](https://x.com/charlie_ruan/status/2094907187797827865))
