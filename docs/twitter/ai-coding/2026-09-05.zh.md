# Twitter AI Coding - 2026-09-05

## 1. 人们在讨论什么

### 1.1 Antigravity 继续扩成更完整的产品表面，但关于运行框架的争论并没有消失 (🡕)
Twitter 上最大的讨论簇仍然围绕 Google Antigravity，但重心已经从“Gemini 3.8 Flash 好不好？”转向“Google 围绕它到底在发布哪些产品表面，以及人们是否足够信任这个运行框架去使用它们？” 至少有 6 条相互独立的内容支撑这一主题，包括 Antigravity 的 Mission Report、Remote Control、创作者 demo、一套泄露的语音控制界面，以及对运行框架本身的直接批评。

[@antigravity](https://x.com/antigravity) [发帖称](https://x.com/antigravity/status/2095966833794863451)（271 点赞、30 回复、20,777 浏览量、42 收藏）它最新一期 Mission Report 已经跟不上 Gemini 3.8 Flash 的发布速度，随后又在回复链里把人们引向新的 [Remote Control 公告](https://x.com/antigravity/status/2090853908138676507?s=20)、一段[演示讲解](https://youtu.be/8QGW7ePYepE?si=VKO0q0A3Iyy82O0l)，以及公开的 [直播中心](https://www.youtube.com/@googleantigravity/streams)。这件事之所以重要，是因为 Antigravity 把自己呈现得更不像一次性的演示外壳，而更像一个拥有浏览器和移动端入口、直播节目和稳定内容节奏的多表面产品。

[@thtbee_](https://x.com/thtbee_) [表示](https://x.com/thtbee_/status/2095988473476075693)（136 点赞、17 回复、5,811 浏览量、14 收藏），一个在 Antigravity 中一次生成的 Gemini 3.8 Flash demo 被 Google News 引用、获得 Google 认可，还被写进了 Antigravity 的官方 Mission Report。附图之所以重要，是因为它同时展示了原始的《Night Forest》结果和后续的放大路径，把一个小型创作者实验变成了 Google 主动扶持社区 demo 的证据。

![截图展示 Google Antigravity 把 thtbee_ 的模拟结果作为官方示例展示出来](https://pbs.twimg.com/media/HRZyZMRacAAF_qE.jpg)

![截图展示一个 Google News 账号转发了 thtbee_ 的 Gemini 3.8 Flash 模拟结果之一](https://pbs.twimg.com/media/HRZyZxPaoAAxtrT.jpg)

一条互动不高、但信息量更大的泄露内容，又补上了新的表面。[@runtimewire](https://x.com/runtimewire) [表示](https://x.com/runtimewire/status/2096006817595941002)（3 点赞、3 回复、343 浏览量），Antigravity 正在测试名为 “Concierge” 的语音激活编程助手：它会把最终语音路由给一个专用智能体，而不是直接塞进提示框。附带的界面模型图里出现了审查队列、CL 分诊、个性化规则以及 skills/plugins 卡片，这比那条短推文本身提供了更具体的产品证据。

![泄露的 Antigravity Concierge 界面模型图，展示了语音驱动的智能体控制、审查队列和个性化规则](https://pbs.twimg.com/media/HRaDDKPWkAAOeG-.jpg)

正面的创作者故事并没有抹掉批评。[@grenish_rai](https://x.com/grenish_rai) [认为](https://x.com/grenish_rai/status/2095973989181169992)（9 点赞、1 回复、1,240 浏览量），Antigravity 会反复重读整个文件、为简单编辑生成 Python 脚本，而且即使开了 auto-approve 也还是会停下来等审批。[@johnennis](https://x.com/johnennis) [补充](https://x.com/johnennis/status/2095932349213024286)（10 点赞、4 回复、1,014 浏览量），如果 Gemini 真的很强，Google 就应该允许订阅用户在第三方运行框架里使用它，而不是实际上把人锁进 Antigravity。

**讨论要点：** 这次分歧异常具体。支持者举出真实的创作者成果和新产品表面，批评者则点名了反复重读文件、审批被打断，以及无法把 Gemini 带进其他运行框架等明确的失灵点。

**与前日对比：** 9 月 4 日的 Antigravity 讨论，中心仍是上下文上限、checkpoint 压缩，以及运行框架是否遮蔽了 Gemini 的真实能力。到了 9 月 5 日，话题扩展到了 Remote Control 和 Concierge 之类的产品表面，但对运行框架可信度的疑问依然伴随着每一次发布。

### 1.2 围绕 Astra 的讨论从盯发布进度，转向了封装层、定价和可量化吞吐 (🡕)
Astra 仍然是一个大主题，但讨论口气又变了。人们这一天不再只是盯着 rollout 线索，而是在比较不同封装层、上下文经济性，以及 Astra 的提升是否真的能在真实工具和类基准测试里看得见。至少有 7 条独立内容支撑了这个主题。

[@GHchangelog](https://x.com/GHchangelog) [宣布](https://x.com/GHchangelog/status/2096014621257687060)（12 点赞、1,431 浏览量）GPT-6 Astra 已在 GitHub Copilot 中可用，并链接到了 GitHub 的公开 [更新日志条目](https://github.blog/changelog/2026-09-04-gpt-6-astra-is-generally-available-in-github-copilot/)。链接文章写道，Astra 正在面向 Pro+、Max、Business 和 Enterprise 用户，逐步覆盖 VS Code、Visual Studio、Copilot CLI、coding agent、Copilot app、github.com、移动端、JetBrains、Xcode 和 Eclipse。

[@TokenGremlin](https://x.com/TokenGremlin) [发了一份](https://x.com/TokenGremlin/status/2096103927305457820)（84 点赞、12 回复、8,273 浏览量、10 收藏）偏前瞻的 Astra 观察清单，但其中最强的证据其实来自它引用的 [@thsottiaux](https://x.com/thsottiaux/status/2096101429832552872) 帖子：后者表示，Astra 已经把生产率提升到足以让一些内部计划提前 6 个月。这让当天的讨论，比单纯的“Astra 感觉很好”多了一条更强的实践者性能证据。

第二层证据来自人们如何兜售 Astra 接入。[@MyTabulon](https://x.com/MyTabulon) [表示](https://x.com/MyTabulon/status/2096042207555862547)（6 点赞、401 浏览量），Astra 已经在它的网关上线，拥有 1.05M 上下文窗口、128K 输出，并且在 272K prompt tokens 以上会出现价格跳升；公开的 [定价页](https://platform.mytabulon.com/pricing) 则把这项服务描述为一个拥有原生上下文、且不会注入 prompt 或工具的编程模型网关。附带的价格卡把不同价格档位和长上下文阈值跃迁放在了一张图里。

![价格卡展示了 MyTabulon 上的 Astra：1.05M 上下文、128K 输出，以及 272K prompt tokens 以上更高的费率](https://pbs.twimg.com/media/HRajObVaUAAEyoN.jpg)

[@rachpradhan](https://x.com/rachpradhan) [分享](https://x.com/rachpradhan/status/2096102151475048850)（9 点赞、539 浏览量）了一张 Codegraff 对比图，声称在 108 次运行和 18 个合成编程任务中，Astra 以少 31.8% 的平均任务时间和少 14.3% 的 token 消耗，达到了与 GPT-5.6 Sol 相同的通过率前沿。这张图很重要，因为它给出的不是又一个泛泛的能力排名，而是一条具体的效率论据。

围绕封装和权宜方案的讨论补齐了剩下的部分。[@claudeebum](https://x.com/claudeebum) [声称](https://x.com/claudeebum/status/2096051571415200012)（20 点赞、7 回复、2,838 浏览量、14 收藏）只要把上下文锁到 1M，就能找到一个 Codex 定价漏洞；其链接回复则指向公开的 [OpenCodex 仓库](https://github.com/lidge-jun/opencodex)，那里把自己描述成 Codex、Claude Code、Claude Desktop 和 Grok Build 的通用提供商代理。[@opencode](https://x.com/opencode) 的 [Zen 模型新增帖子](https://x.com/opencode/status/2096056230405923017)（396 点赞、12 回复、12,134 浏览量、16 收藏）下面，回复也立刻转向了操作者问题：比如是否能通过 API 暴露剩余额度，以及是否能把周期性任务钉死在特定模型版本上。

![一张幻灯片描述了通过 OpenCodex 规避 Astra 长上下文定价跳点的方案](https://pbs.twimg.com/media/HRaruOFbYAAtSHP.jpg)

**讨论要点：** 帖子层面的问题，已经不再是“Astra 出了吗？” 而是“哪个表面给我原生上下文？”“哪一层会隐藏或暴露价格跳点？” 以及“怎样才能不让模型选择在周期性任务里变成手工苦活？”

**与前日对比：** 9 月 4 日主要被 Copilot、Codex 和 ChatGPT 套餐里 Astra 的接入门槛与命名清晰度主导。9 月 5 日保留了接入线索，但新增了第三方 gateway、路由代理，以及更尖锐的速度与 token 证据。

### 1.3 围绕编程智能体的编排和监督层继续升温 (🡕)
第三个强讨论簇，不再是模型本身，而是围绕它的一切：编排、监督、浏览器控制、排队和可复用上下文。至少有 6 条内容支撑了这个主题，而且其中几项已经是具体的开源项目，而不只是工作流建议。

[@DanKornas](https://x.com/DanKornas) [介绍](https://x.com/DanKornas/status/2096293304144900378)（8 点赞、5 回复、747 浏览量）了 Omnigent：一个面向 Claude Code、Codex、Cursor、OpenCode、Hermes、Pi 和自定义智能体的开源元运行框架；回复中还附上了公开的 [GitHub 仓库](https://github.com/omnigent-ai/omnigent)。仓库说明称，Omnigent 加入了跨设备会话、共享历史、策略以及一次性云沙箱，而附图则让“多个智能体、一个控制平面”这个概念更容易被验证。

![Omnigent README 截图，展示多个编程智能体运行框架共享一个控制平面](https://pbs.twimg.com/media/HReHpYqbAAAtvVq.jpg)

[@DanKornas](https://x.com/DanKornas) [也分享了](https://x.com/DanKornas/status/2096157394053001519)（4 点赞、709 浏览量） Hive，公开的 [repo README](https://github.com/hivecommons/hive) 把它描述成一个单一 Go 二进制：它会枚举 GitHub issues 和 PRs，按复杂度分类，再通过一个确定性的 pre-LLM 管线把工作分发给 Claude、Copilot、Gemini 和 Goose。这条帖子的重要性在于，它把排队、合并门槛和节奏控制本身做成了产品。

[@DuncanRogoff](https://x.com/DuncanRogoff) [重点提到](https://x.com/DuncanRogoff/status/2096282647685197828)（3 点赞、3 回复、361 浏览量）Chrome 团队的 [chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp) 项目；无论是回复里的链接还是公开仓库，说的都是同一件事：这个工具能给 Claude、Cursor、Copilot 或 Antigravity 一个实时 Chrome 浏览器，并提供性能 traces、网络检查、截图、console 访问、Puppeteer 控制，以及可选的 CrUX 现场数据。

这些帖子下的回复，汇聚到了同一个痛点上。一条 Omnigent 回复直说：一旦 Claude Code 和 Codex 并排运行，最先坏掉的就是监督。一条 opencode 回复则说：只要每多一个模型，就会让手工选择变得更糟，除非周期性任务可以被钉在具体版本上。[@coreyganim](https://x.com/coreyganim) [描述](https://x.com/coreyganim/status/2096183307822420031)（4 点赞、407 浏览量、6 收藏）了一套业务栈：之所以能在 5 分钟左右启动新的专用智能体，是因为有一个每周 ingest 技能，会持续把经验写回到一个基于 GitHub 的第二大脑里。

GitHub 表面的打磨，也是同一个故事的一部分。[@pierceboggan](https://x.com/pierceboggan) [表示](https://x.com/pierceboggan/status/2096016025842241693)（22 点赞、5 回复、953 浏览量），Copilot app 里新增了一个“在外部浏览器中打开”的动作，而一条回复立刻追问：针对自动化密集型会话，是否已在路线图里考虑默认浏览器 cookies？

![GitHub Copilot app 截图，展示浏览器画布里新的“在外部浏览器中打开”动作](https://pbs.twimg.com/media/HRaLTwbaUAAc6Bc.jpg)

GitHub 公开的 [HydraFusion 研究文章](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/) 在产品层面进一步强化了这个转向：single、cascade 和 critique 三类工作流并存，而且 GitHub 声称在 TerminalBench 2.1 上，HydraFusion 相比 Claude Opus 5 以估算成本低 67% 的代价，换来了 4.9 分的验证质量提升。[@stretchcloud](https://x.com/stretchcloud) [把这种变化概括为](https://x.com/stretchcloud/status/2096038100522991947)（3 点赞、468 浏览量、4 收藏）从“挑一个模型”转向“组合一个工作流”。

**讨论要点：** 整体讨论的默认前提已经变成：模型不再等于整个产品。人们在争论的是如何监督一整队智能体、如何路由周期性任务、如何暴露浏览器状态，以及如何让编排成本保持可见。

**与前日对比：** 9 月 4 日，控制层更多表现为看板、PM 与开发者的角色拆分，以及 spec-first 纪律。到了 9 月 5 日，同样的直觉已经落成软件：元运行框架、队列调度器、浏览器 MCP server，以及复合模型运行时。

## 2. 令人困扰的问题

### 运行框架摩擦与被迫绑定单一运行框架
最尖锐的技术挫败感，并不是抽象层面的模型质量，而是运行框架本身在妨碍模型发挥。[@grenish_rai](https://x.com/grenish_rai) [写道](https://x.com/grenish_rai/status/2095973989181169992)（9 点赞、1 回复、1,240 浏览量），Antigravity 有时会为了改一行代码而重读整个文件，会生成 Python 脚本而不是直接编辑，而且即便开了 auto-approve 也还是会停下来请求批准。[@johnennis](https://x.com/johnennis) [更直白地表达了](https://x.com/johnennis/status/2095932349213024286)（10 点赞、4 回复、1,014 浏览量）更大的抱怨：如果 Gemini 足够强，用户就不该为了访问它而被推入单一运行框架。严重程度：高。人们已经在比较替代运行框架了，所以只要模型由提供商控制、而工作流不满却出在客户端，这里就很值得构建。

### 模型经济性仍然难以实时看清
第二个主要挫败点，是运维层面的可见性。[@claudeebum](https://x.com/claudeebum) [寻找](https://x.com/claudeebum/status/2096051571415200012)（20 点赞、7 回复、2,838 浏览量、14 收藏）绕过 Astra 长上下文价格跳点的方法，[@MyTabulon](https://x.com/MyTabulon) [放出](https://x.com/MyTabulon/status/2096042207555862547)（6 点赞、401 浏览量）了一张在 272K prompt tokens 以上显式跳价的公开价格卡，而 [@opencode](https://x.com/opencode) 那条 [Zen 更新](https://x.com/opencode/status/2096056230405923017)（396 点赞、12 回复、12,134 浏览量、16 收藏）下的回复则要求一个能暴露剩余额度的 API。共同点不只是价格高，而是用户看不见消耗，因而无法足够早地调整行为。严重程度：高。这值得构建，因为权宜方案已经在公开讨论里一再出现。

### 一旦团队同时运行多个智能体，监督就会变成瓶颈
一旦用户走出单一聊天窗口，他们似乎就会撞上同一堵墙：很难看清哪个智能体在做什么、哪个模型被钉在什么位置，以及哪次运行需要被接手。[@DanKornas](https://x.com/DanKornas) [展示](https://x.com/DanKornas/status/2096293304144900378)（8 点赞、5 回复、747 浏览量）Omnigent，部分就是为了回应这个问题；其中一条回复直接说，Claude Code 和 Codex 并排跑时，最先坏掉的就是监督。[@coreyganim](https://x.com/coreyganim) [描述](https://x.com/coreyganim/status/2096183307822420031)（4 点赞、407 浏览量、6 收藏）了一套只有靠第二大脑循环不断给新智能体回灌上下文才能工作的业务栈。[@opencode](https://x.com/opencode) 的回复还补充了类似抱怨：随着模型变多，手工选择只会变得更糟，除非周期性任务可以钉住具体版本。严重程度：中高。这个需求足够具体，也重复得足够多，足以支撑编排、看板和路由产品。

### 智能体反馈循环仍在高噪声代码路径上浪费精力
规模更小、但同样清晰的一簇挫败感，聚焦在循环本身的质量上。[@byteHumi](https://x.com/byteHumi) [认为](https://x.com/byteHumi/status/2096146883466969142)（7 点赞、523 浏览量），编程智能体太容易默认用 TypeScript，在 lint 和类型检查上烧掉 token，用 `as any` 或 `@ts-ignore` 把问题压下去，还会为类型系统本已保证的事实去生成测试。这条抱怨与当天更大的路由讨论正好吻合：人们想要的是更快、更安静的反馈循环，而不只是更大的模型。严重程度：中。这值得构建，尤其是在工具链可以缩短验证、提供更好的编译器指引，或把智能体引向噪声更低的语言和模式时。

## 3. 人们期望的功能

### 面向前沿编程模型的真实使用驾驶舱
人们并不是在含糊地要求更便宜的 AI。他们想要的是一个地方，能在一次会话变贵之前，就把长上下文阈值、剩余额度，以及不同表面的消耗情况展示出来。最有力的证据来自 [@opencode](https://x.com/opencode) 在那条 [Zen 更新讨论串](https://x.com/opencode/status/2096056230405923017) 下的回复：他们想要一个能返回剩余 Zen 余额的 API；再加上 [@claudeebum](https://x.com/claudeebum) 那条 [Astra 定价帖子](https://x.com/claudeebum/status/2096051571415200012) 里的权宜方案，以及 [@MyTabulon](https://x.com/MyTabulon) 那条 [gateway 帖子](https://x.com/MyTabulon/status/2096042207555862547) 里清楚标出的阈值卡片，这个需求已经足够明确。机会：直接。

### 在强模型与偏好运行框架之间拥有更好的可移植性
围绕 Antigravity 最强的未满足需求，是选择权。[@johnennis](https://x.com/johnennis) [表示](https://x.com/johnennis/status/2095932349213024286)，如果 Gemini 本身已经足够强，Google 就应该允许人们在第三方框架里使用它；而 [@grenish_rai](https://x.com/grenish_rai) [列出](https://x.com/grenish_rai/status/2095973989181169992) 了人们为什么会想要这个逃生口的具体原因。像 [Omnigent](https://github.com/omnigent-ai/omnigent) 和 [OpenCodex](https://github.com/lidge-jun/opencodex) 这样的开源项目之所以存在，就是因为这个可移植性问题已经是真问题。这个需求很实际，而且竞争压力也很清晰。机会：竞争型。

### 能跨规模、跨重复运行、跨设备存活的智能体监督层
这一天不断指向同一个缺失的控制平面：人们想快速启动智能体、在它们之间保留上下文、从多个表面监督它们，并知道某个智能体何时卡住。[@coreyganim](https://x.com/coreyganim) [描述](https://x.com/coreyganim/status/2096183307822420031) 了一套基于 GitHub 的第二大脑和每周 ingest 循环，[@DanKornas](https://x.com/DanKornas) [把](https://x.com/DanKornas/status/2096293304144900378) Omnigent 作为共享编排层来推介，而 Antigravity 则不断推出像 [Remote Control](https://x.com/antigravity/status/2090853908138676507?s=20) 这样的表面。这既现实又紧迫，因为权宜方案已经开始固化成架构。机会：直接。

### 让智能体在真实界面上操作的语音和浏览器外设
当天两个最强的辅助信号，都和界面访问有关。[@runtimewire](https://x.com/runtimewire) [展示](https://x.com/runtimewire/status/2096006817595941002) 了一套可能的语音优先 Antigravity 表面，而 [@DuncanRogoff](https://x.com/DuncanRogoff) [指向](https://x.com/DuncanRogoff/status/2096282647685197828) 了 [chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)，后者给编程智能体提供实时浏览器、traces、截图和 console 访问。这些都是很实际的需求，因为它们补上了智能体输出与开发者实际调试界面之间的缺口。机会：直接。

### 把编程智能体变成工作流专家的领域技能包
关于 scientific-skills 的讨论，呈现的是另一种愿望：人们不只想要一个更好的通用 coder，而是想要一包面向特定领域、可复用的流程、参考资料和测试。[@kamin00ntee](https://x.com/kamin00ntee) [重点提到](https://x.com/kamin00ntee/status/2096359596973551828) [scientific-agent-skills](https://github.com/K-Dense-AI/scientific-agent-skills) 仓库，正是因为每一项 skill 都带有文档、示例、参考资料和测试。这是一个实际需求，开源仓库本身已经证明了需求存在，但市场很可能会按领域分裂。机会：愿景型。

整体情绪依然是：对模型能力偏乐观，对围绕模型的运维层偏负面。最让人满意的帖子，描述的是智能体在真实上下文、真实浏览器或结构清晰的指导下能做成什么。态度最复杂的帖子，通常都集中在经济性和控制力上：人们不断加 gateway、代理、模型钉住选项、第二大脑循环和确定性预过滤层，就是为了让成本、上下文和监督更可控。

迁移路径在三个地方尤其明显。第一，模型路由正变得越来越刻意：GitHub 在推 HydraFusion，操作者希望把周期性任务钉在具体版本上，第三方 gateway 则把模型接入本身做成了独立层。第二，浏览器访问正从临时截图转向可复用的 MCP 基础设施，以 chrome-devtools-mcp 为代表。第三，工作流脚手架正在从“建议”变成“软件”，Omnigent 和 Hive 都把监督与治理当作一级特性，而不是附带说明。

## 7. 机会在哪里

**[+++] 智能体监督与控制平面** —— 证据横跨第 1、2、4、5、6 节：Omnigent、Hive、coreyganim 的第二大脑工作流、Antigravity Remote Control、Concierge，以及 GitHub 对 HydraFusion 的公开编排，全都指向同一个缺口。人们已经在自行拼接仪表盘、策略层、队列调度器和跨设备会话视图，因为原始聊天循环已经不够用了。

**[+++] 用量、定价与上下文可观测性** —— Astra 定价漏洞讨论串、MyTabulon 的阈值卡，以及 opencode 回复里对剩余额度 API 的要求，都指向同一个直接需求：开发者想在还能改变行为的时候，就看见成本和上下文状态。这个机会很强，因为权宜方案已经反复公开化。

**[++] 围绕前沿模型的运行框架可移植性** —— 对 Antigravity 的批评、OpenCodex 和 Omnigent，都反映出一个市场事实：人们喜欢某些模型，但不愿被困在单一运行框架里。这个机会属于中等强度，因为已经有多个项目在打这块市场，但用户需求说得非常明白。

**[++] 面向真实界面的智能体外设** —— chrome-devtools-mcp 与 Concierge 的泄露界面都说明，更好的浏览器和语音表面，会实质性改变智能体能做什么。这个机会是中等强度，因为需求具体、技术边界清楚，但也要和平台原生方案竞争。

**[+] 领域技能包** —— Scientific Agent Skills 展示了一条超越通用编程助手的路径：为特定领域提供可复用、经过测试的流程。这个信号今天还处在浮现阶段，而不是主导阶段，但它确实把可服务市场从“写代码”扩展到了“提供工作流专长”。

## 8. 要点总结

1. **Antigravity 的心智份额，现在更多来自已发布的产品表面和创作者放大，而不只是模型 demo。** Mission Report、Remote Control 链接，以及 thtbee_ 的传播链条，都指向 Google 正在围绕 Gemini 3.8 Flash 搭建更大的产品外壳。([来源](https://x.com/antigravity/status/2095966833794863451))
2. **围绕 Astra 的讨论，已经向上爬了一层栈，进入定价、路由和效率证据。** 公开讨论的重点，已变成长上下文阈值、gateway 封装，以及类似基准的速度 / token 对比，而不是简单的可用性传闻。([来源](https://x.com/MyTabulon/status/2096042207555862547))
3. **监督正在变成围绕编程智能体的真正产品类别。** Omnigent、Hive、第二大脑工作流，以及 GitHub 对 HydraFusion 的表达，都把编排和审查当成一等能力。([来源](https://x.com/DanKornas/status/2096293304144900378))
4. **开发者越来越希望智能体连接真实界面，而不只是源代码文件。** chrome-devtools-mcp 和 Concierge 泄露界面都说明，人们对浏览器级和语音级控制表面的需求正在上升。([来源](https://x.com/DuncanRogoff/status/2096282647685197828))
5. **专门化技能库正在扩展“AI 编程”的含义。** Scientific Agent Skills 通过打包 163 个经测试的科学流程和数据库集成，把一场关于编程智能体的讨论，拉向了研究工作流。([来源](https://x.com/kamin00ntee/status/2096359596973551828))
