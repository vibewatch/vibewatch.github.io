# Twitter AI 编程 - 2026-08-18

## 1. 大家在讨论什么

### 1.1 Harness 工程不再是隐藏的实现细节，而成为一等话题（🡕）

最清晰的一组讨论把 AI 编程视为生命周期与运行时问题，而不是提示词问题。至少有四条内容支撑了这一点：一张高互动的 Google Agents CLI 生命周期图、对 Microsoft Agent Harness 的单独总结、一门公开的 Learn Harness Engineering 课程，以及一条关于 ADK 与托管 Agent 该如何取舍的实用规则。反复出现的核心观点是：如今团队对状态、审批、网络边界、评估和部署的关注，已经和代码生成本身同样重要。

[@akshay_pachaar](https://x.com/akshay_pachaar) [认为](https://x.com/akshay_pachaar/status/2089707367172882669) (86 个赞、14 条回复、11,463 次浏览、124 次收藏)指出，交付 Agent 最难的部分都发生在“写完 Agent”之后：脚手架、运行时部署、最小权限身份、网络控制、评估和发布。回复让这条帖子比那张图本身更有价值：一位回复者说，治理和出口 allow-list 才是生产项目真正死掉的地方；另一位则说，生成只要几秒钟，剩下整个下午都耗在各种管线和基础设施连接上。

[@N01ennn](https://x.com/N01ennn) [总结道](https://x.com/N01ennn/status/2089819869831193020) (32 个赞、1 条回复、1,038 次浏览、34 次收藏)将 Microsoft Agent Harness 描述为模型外围的可复用层：工具调用循环、可恢复历史、上下文压缩、持久化待办事项、文件记忆、审批、追踪和技能。尽管互动量不高，但它进一步强化了一个信号：“agent harness”正在成为一个有明确名称的产品类别，而不再只是幕后实现细节。

[@tom_doerr](https://x.com/tom_doerr) [分享了](https://x.com/tom_doerr/status/2089839884060049772) (17 个赞、1,572 次浏览、24 次收藏)介绍了公开的 [学习 Harness Engineering](https://github.com/walkinglabs/learn-harness-engineering) 课程。附带的仓库截图很关键，因为它让这个领域变得具体，而不只是停留在口号层面：14 节课、8 个项目、15 种语言，以及一项关于图工程和可靠控制机制的 8 月更新。

![Learn Harness Engineering 仓库截图，展示了一门包含 14 节课程、8 个项目的可靠 AI 编码代理课程](https://pbs.twimg.com/media/HQCaTMiW8AACwEO.jpg)

[@SeraAndroid](https://x.com/SeraAndroid) [解释了](https://x.com/SeraAndroid/status/2089702431705752002) (2 个赞、1 条回复、509 次浏览、2 次收藏)给出了当天最清晰的一条操作者规则：如果你需要自己掌控拓扑、路由、状态、审批和故障处理，就用 ADK；如果你想要一个边界清晰、且已内置循环的托管运行时，就用 Managed Agent。附图通过对比“工作流由你掌控”和“Google 运行 harness”，把这一差异直观呈现了出来。

![对比 ADK 与托管代理运行时的示意图：前者由开发者掌控工作流，后者由 Google 掌控 harness](https://pbs.twimg.com/media/HQAdSNuWsAApHNw.jpg)

**讨论洞察：** 最有信息量的回复并不是在要求更聪明的模型，而是在问：如何限制故障影响范围，如何把生产事故沉淀为回归项，以及什么时候该自己掌控循环、什么时候该租用它。

**与前一天对比：** 2026-08-17 的控制面讨论，重心还在审查深度、仪表盘和持久化计算机上。到了 2026-08-18，重心进一步下探到更底层，转向运行时所有权、状态、治理和验证。

### 1.2 积分、配额和路由绕行方案持续重塑日常工具选择（🡕）

第二个讨论簇聚焦于整周实际使用编程 Agent 的经济账。讨论已经不再只是“这个套餐太贵”，而是围绕每周重置、用量积分弹窗、临时配额提升、免费备用模型，以及把工作分摊到多个供应商的自建路由层展开。

[@melvindvivas](https://x.com/melvindvivas) [记录了](https://x.com/melvindvivas/status/2089623864896844203) (97 个赞、15 条回复、4,820 次浏览)用一句话概括了人们对 Codex 重置机制的持续不满，而回复则补上了更密集的证据：一位支付 $200 Pro 订阅费的用户说，过去能撑满一周的日常任务，如今大约两天就会耗尽配额；另一位说自己只能等重置窗口；还有人讨论在等待期间把工作迁到别处。

[@monosarin](https://x.com/monosarin) [发布了](https://x.com/monosarin/status/2089811593508868524) (22 个赞、5 条回复、865 次浏览)提供了最具体的可视化证据，说明面向消费者的 AI 编程套餐正在被重新计量。截图显示，Fable 5 从套餐内能力变成了按 usage credits 计费，并附带 $100 的促销额度；发帖者把这条小小的账单提示解读为一个信号：对于重度 Agent 使用，按工作量计费正在取代固定订阅。

![Claude 计费弹窗，显示 Fable 5 现已按用量积分运行，并提供 100 美元促销积分](https://pbs.twimg.com/media/HQBzgZAXYAAn_tE.png)

[@RoundtableSpace](https://x.com/RoundtableSpace) [转述了](https://x.com/RoundtableSpace/status/2089841505674412138) (12 个赞、6 条回复、7,403 次浏览)表示，[@ClaudeDevs](https://x.com/ClaudeDevs) 将 Claude Code 每周限额临时上调 50% 的政策延长至 8 月 31 日，但仍警告容量可能继续紧张。因此，这条信号与其说是“好消息”，不如说是在说明：需求已经跑在清晰稳定的配额政策前面。

[@qilua02](https://x.com/qilua02) [分享了](https://x.com/qilua02/status/2089712069981724776) (1 个赞、119 次浏览、4 次收藏)提供了一个实用的逃生口：通过 b.ai 提供的 DeepSeek V4 Flash，带有公开 base URL 和“Limited-Time Free”标签，明确定位为可接入 OpenCode 和其他 Agent。[@portgasdluci](https://x.com/portgasdluci) [展示了](https://x.com/portgasdluci/status/2089650435460419687) (2 个赞、139 次浏览)则展示了同类应对方式的更高级版本：通过 9router 将 OpenCode 路由到 Codex、Copilot、Grok Build、GLM、MiMo 和免费模型。

**讨论洞察：** 这种应对方式已经相当成熟。用户撞上限制时，不只是暂停工作，而是在拼接免费层、轮询路由器和跨供应商配置，让会话继续跑下去。

**与前一天对比：** 2026-08-17，用户主要还在争论 Codex 重置和账户访问问题。到了 2026-08-18，证据已经扩展到明确的用量积分 UI、临时 Claude 容量政策、免费的 DeepSeek 备用方案，以及自建路由仪表盘。

### 1.3 GitHub 宕机和 Cursor Origin 发布，让围绕仓库控制面的争夺更为尖锐（🡕）

仓库控制的重要性，已经比模型炫技更像当天的大故事。一边的证据说明，AI 编程仍在多大程度上依赖 GitHub 这个共享控制平面；另一边则显示，Cursor 正通过 Origin 从编辑器进一步延伸到仓库、拉取请求和代码浏览。

[@githubstatus](https://x.com/githubstatus) [报道称](https://x.com/githubstatus/status/2089794864917488010) (26 个赞、4 条回复、4,719 次浏览、10 次收藏)指出，GitHub 8 月 17 日的事故持续了 7 小时 47 分钟，影响 Issues、Pull Requests、APIs、Actions 和 Copilot，而 Copilot Token Service 最后才恢复。公开的事后报告使这条帖子真正重要起来：它给出了具体故障机制，而不是泛泛的道歉。

[@dani_avila7](https://x.com/dani_avila7) [强调了](https://x.com/dani_avila7/status/2089841849263382777) (3 个赞、234 次浏览)摘出了该事后报告中最醒目的一句：一个潜伏的 VS Code 重试 bug 在恢复期间将流量放大了约 10 倍。GitHub 自己的事故页面还补充了影响范围：Copilot Token Service 的流量从常态下每秒 7–9K 次请求，飙升至每秒 70–100K RPS。

![GitHub 事故摘录，显示一个潜在的 VS Code 重试漏洞将恢复流量放大了约 10 倍](https://pbs.twimg.com/media/HQCb-LjWkAAhOcO.jpg)

[@MTSlive](https://x.com/MTSlive) [解释了](https://x.com/MTSlive/status/2089493210964111504) (65 个赞、3 条回复、7,181 次浏览、5 次收藏)表示，Origin 正在以早期测试版形式推出，包含 Cursor 上的仓库托管、GitHub 迁移、每个仓库中的 Agent、每秒 22.6 次提交，以及低于 400ms 的全球同步。另一条互动较少的 [@shawnchauhan1](https://x.com/shawnchauhan1) [帖子](https://x.com/shawnchauhan1/status/2089645996737458232) (1 个赞、179 次浏览)给出了更尖锐的战略解读：重点不只是推出一个新的托管平台，而是试图掌控模型外围的完整工作流界面。

![Cursor Origin 营销图片，将 Origin 描述为 agentic 时代的 git forge](https://pbs.twimg.com/media/HP_p9SLaAAAtqXp.jpg)

**讨论洞察：** 真正有价值的问题不是“这次宕机严重不严重”，而是“现代 AI 编程工作流有多少环节共用同一个身份认证和仓库界面，以及谁在试图掌控一个替代面？”

**与前一天对比：** 2026-08-17，关于宕机的讨论主要体现为可用性痛点。到 2026-08-18，讨论变得更锋利：一边是完整的事后故障机制，另一边则是对 agent-native 代码托管的可信推进。

### 1.4 Gemini 3.7 Flash 和 Antigravity 仍然相关，但重点从炫技转向吞吐量（🡖）

Google 的技术栈依然可见，但不像前一天的发布与定价周期那样占据主导。最强的证据已经从“看这个落地页演示”转向了真实用户的实际工作流和速度反馈。

[@googleaidevs](https://x.com/googleaidevs) [展示了](https://x.com/googleaidevs/status/2089443913493033058) (377 个赞、7 条回复、20,711 次浏览、155 次收藏)展示了 Gemini 3.7 Flash 如何解析一本维多利亚时期植物学书籍中的数百页 PDF，并在 Antigravity 中将其转化为交互式 APG IV 分类可视化。它之所以重要，是因为这比前一天泛泛的 Web 演示更具体：在一个托管 Agent 流程里，同时完成长源文档提取、结构化分类和交互式输出。

[@danicat83](https://x.com/danicat83) [表示](https://x.com/danicat83/status/2089780608163569704) (23 个赞、1,312 次浏览、4 次收藏)表示，Gemini 3.7 Flash + Antigravity 2.0 的组合，感觉像是把五个月的工作压缩进了五天；引用的 [@rakyll](https://x.com/rakyll) 则说，这套栈“快得惊人”，而且两周里只需要动用一两次更大的模型。这是当天最清晰的一手验证：Google 这套界面之所以持续吸引注意，靠的不只是功能数量，更是速度。

**讨论洞察：** 当天关于 Google 的证据，与其说关乎惊喜，不如说关乎操作手感：托管 Agent 能否足够快、足够结构化、又足够灵活，以至于用户不再频繁转向更大的模型。

**与前一天对比：** 2026-08-17，关于 Antigravity 的讨论集中在发布定价、界面能力对等和炫目的落地页生成。到了 2026-08-18，这套栈依然在场，但证据已经收窄到实际的文档工作流和吞吐量。

## 2. 什么让人感到沮丧

### 限制、积分和重置机制仍然过于不可预测

这是一个高严重性问题，因为它同时出现在高互动量的用户抱怨和官方配额政策消息里。[@melvindvivas](https://x.com/melvindvivas) [记录了](https://x.com/melvindvivas/status/2089623864896844203) (97 个赞、15 条回复、4,820 次浏览)用一条简短抱怨概括了 Codex 的重置问题，但真正的信号来自回复：用户表示，过去能支撑正常工作节奏的一周配额，如今大约两天就会耗尽，迫使他们要么等待下一次重置，要么把工作迁到别处。

问题并不只存在于 Codex。[@monosarin](https://x.com/monosarin) [发布了](https://x.com/monosarin/status/2089811593508868524) (22 个赞、5 条回复、865 次浏览)展示了 Fable 5 的弹窗，说明一项原本包含在套餐内的能力，现在会消耗 usage credits；与此同时，[@RoundtableSpace](https://x.com/RoundtableSpace) [转述了](https://x.com/RoundtableSpace/status/2089841505674412138) (12 个赞、6 条回复、7,403 次浏览)转发了一条官方 [@ClaudeDevs](https://x.com/ClaudeDevs) 消息，将每周限额临时上调 50% 的政策延长至 8 月 31 日，并警告容量紧张。用户已经用应对行为表明自己真正想要什么：[@qilua02](https://x.com/qilua02) [推荐了](https://x.com/qilua02/status/2089712069981724776) (1 个赞、119 次浏览、4 次收藏)提供了免费的 DeepSeek 备用路径；[@portgasdluci](https://x.com/portgasdluci) [整理了](https://x.com/portgasdluci/status/2089650435460419687) (2 个赞、139 次浏览)则展示了通过 9router/OpenCode 将工作分摊到多个供应商的配置。这看起来值得被直接构建出来。痛点不只是价格，而是用户无法预测工具在一周中途是否仍然可用。

### 共享的仓库与身份认证基础设施，可能一次性拖住整个 AI 编程工作流

这也是一个高严重性问题，因为证据来自官方，细节充分，而且直接关联开发者工作流的核心界面。[@githubstatus](https://x.com/githubstatus) [报道称](https://x.com/githubstatus/status/2089794864917488010) (26 个赞、4 条回复、4,719 次浏览、10 次收藏)指出，8 月 17 日的 GitHub 事故持续了 7 小时 47 分钟，影响 Issues、Pull Requests、APIs、Actions 和 Copilot。公开的事后报告补上了一个破坏性细节：Copilot Token Service 最后恢复，而且恢复路径本身还触发了新的故障放大。

[@dani_avila7](https://x.com/dani_avila7) [强调了](https://x.com/dani_avila7/status/2089841849263382777) (3 个赞、234 次浏览)给出了事后报告中最鲜明的例子：一个潜伏的 VS Code 重试 bug 将流量放大了约 10 倍；GitHub 的事故页面称，恢复期间 Copilot token 流量从每秒 7–9K 次请求暴涨至每秒 70–100K 次请求。这里的挫败感不只是停机本身，而是仓库托管、审查、自动化和编程 Agent 身份认证之间仍然耦合得如此紧密，以至于一次故障就可能同时冻结多层工作。这看起来值得被直接构建或作为竞争切入点：更便于故障转移的仓库工具、更好的降级模式，以及不默认所有服务共用同一个控制平面的界面。

### 通用审查仍然会漏掉 Agent 驱动自动化里最关键的故障

这同样是一个高严重性问题，因为证据里包含的是一条公开的漏洞利用链，而不只是关于“AI 代码质量”的泛泛情绪。[@adamhjk](https://x.com/adamhjk) [认为](https://x.com/adamhjk/status/2089724507867279583) (4 个赞、2 条回复、766 次浏览、5 次收藏)指出，Wiz 公开的 Snowflake 工作流漏洞，正是那类通用审查可能漏掉的 shell escape 问题；相关的 [Wiz 报告](https://www.wiz.io/blog/red-agent-snowflake-copilot-cicd-bug) 说明了这一抱怨为何重要：一个公开的 GitHub issue 标题命中了存在漏洞的 Actions 工作流，GitHub Advanced Security 审查最终 PR 修订版时没有标出注入问题，而 Wiz Red Agent 则不断调整载荷，直到成功外传一个 Jira token。

[@akshay_pachaar](https://x.com/akshay_pachaar) [讨论串](https://x.com/akshay_pachaar/status/2089707367172882669) (86 个赞、14 条回复、11,463 次浏览、124 次收藏)下的回复，则从另一个角度指向了同样的结构性挫败：生产环境中的 Agent 工作，真正会死在治理、评估和故障处理上，而不是死在演示生成上。可见的应对模式，是把质量控制前移并做得更具体：无论是定制的对抗式提示、[Plankton](https://github.com/alexfazio/plankton) 这类写入时强制措施，还是 [GitHub Agentic Workflows](https://github.com/github/gh-aw) 这类沙箱化自动化。这看起来值得被直接构建。

## 3. 人们希望存在什么

### 面向支出、限额与备用路由的控制平面

今天人们持续发出的信号，并不是对某个旗舰模型的忠诚，而是希望在会话开始前就知道：哪个工具仍然有可用配额；如果没有，备用方案应该是什么。[@melvindvivas](https://x.com/melvindvivas/status/2089623864896844203) 暴露了人们对 Codex 重置机制的不满，[@monosarin](https://x.com/monosarin/status/2089811593508868524) 显示 Fable 5 开始转向 usage credits，[@RoundtableSpace](https://x.com/RoundtableSpace/status/2089841505674412138) 传递了 Claude Code 临时提额但仍伴随容量警告的消息，而即时的应对方案则是 [@qilua02](https://x.com/qilua02/status/2089712069981724776) 提供免费 DeepSeek 路线，以及 [@portgasdluci](https://x.com/portgasdluci/status/2089650435460419687) 将 9router 接入 OpenCode。

这不是理想化诉求，而是现实需求。人们已经在手动绕开令人困惑的限额。机会：直接。

### 既保持速度、又不把 harness 隐藏起来的托管 Agent

对托管 Agent 最强烈的需求，并不是“让演示更漂亮”，而是“保留云端速度，同时明确谁掌控循环”。[@SeraAndroid](https://x.com/SeraAndroid/status/2089702431705752002) 完全围绕拓扑、状态、路由、审批和故障处理的所有权，对比了 ADK 和 Managed Agents。[@akshay_pachaar](https://x.com/akshay_pachaar/status/2089707367172882669) 将治理、评估和发布视为一等生命周期阶段，而 [@danicat83](https://x.com/danicat83/status/2089780608163569704) 及引用的 [@rakyll](https://x.com/rakyll) 则称赞 Gemini 3.7 Flash + Antigravity 的纯粹速度。

愿望很明确：既给用户托管运行时的吞吐量和便利性，又让状态、审批、持久化和恢复的边界足够清晰，让他们能放心把它用于真实工作。机会：直接，且具竞争替代空间。

### 面向代码的对抗式审查与安全自动化，而不是泛泛的“AI 审查”

今天关于审查的挫败已经具体到几乎可以直接写成产品需求。[@adamhjk](https://x.com/adamhjk/status/2089724507867279583) 表示，Snowflake/Wiz 这个漏洞说明，真正需要的是理解 GitHub Actions 和 shell 注入的定制化对抗审查 Agent，而不是通用审查提示。同时，[@DotNetTrends](https://x.com/DotNetTrends/status/2089669318153765291) 展示了 GitHub Agentic Workflows 如何把权限、沙箱和结构化任务直接封装进仓库自动化；[@GithubProjects](https://x.com/GithubProjects/status/2089661145087152288) 则指出，Plankton 把格式化、lint 和检查前移到了文件编辑时。

人们想要的似乎不是更多自动评论，而是一套真正理解代码界面、能在合并前执行正确检查，并把 Agent 写入限制在可审查边界内的工作流。机会：直接。

满意度更偏向两类工具：一类是让托管工作显得既快又完整，另一类是把周边控制层说得更明白。Antigravity 中的 Gemini 3.7 Flash 因速度受到称赞；而强调生命周期的工具，则在明确所有权、沙箱、审批和持久化时获得关注。

最主流的应对方式是供应商路由和策略层。当配额或积分显得不稳定时，用户会转向免费 DeepSeek 路线、9router 式轮询配置或多 harness 应用，而不是单纯等待。当审查显得过于通用时，他们会通过写入时门禁，或把权限和输出编码进工作流，把检查进一步前移。

迁移压力如今正同时朝三个方向拉动：从固定订阅转向按用量计费，从单工具忠诚转向跨供应商路由，以及从独立编辑器转向覆盖仓库、PR、沙箱和自动化的完整工作流界面。竞争态势看起来已经不再是纯粹的模型竞赛，而更像是在争夺模型外围的操作层。

## 6. 新鲜且值得关注的内容

### GitHub 的事后报告点名了重试风暴，而不只是宕机

[@githubstatus](https://x.com/githubstatus) [帖子](https://x.com/githubstatus/status/2089794864917488010) (26 个赞、4 条回复、4,719 次浏览、10 次收藏)值得关注的地方，不只是 GitHub 过了糟糕的一天，而是那份公开事故报告给出了读者可以据此推理的具体机制：美国中部地区的网络饱和故障、区域故障转移，以及一个潜伏的 VS Code 重试 bug，在 Copilot Token Service 尝试恢复时把流量放大了约 10 倍。[@dani_avila7](https://x.com/dani_avila7) [提炼出](https://x.com/dani_avila7/status/2089841849263382777) (3 个赞、234 次浏览)摘出了关键句，事故页面还补充了规模：Copilot token 流量从约每秒 7–9K 次请求跃升到每秒 70–100K 次请求。

### Wiz 公开了完整的 AI 对 AI CI 漏洞利用链

第二个值得关注的信号，是 Snowflake/Wiz 事件在公开层面变得极其具体。[@adamhjk](https://x.com/adamhjk) [将其定义为](https://x.com/adamhjk/status/2089724507867279583) (4 个赞、2 条回复、766 次浏览、5 次收藏)把教训概括为“通用审查还不够”，而相关的 [Wiz 报告](https://www.wiz.io/blog/red-agent-snowflake-copilot-cicd-bug) 则给出了具体链条：一个公开的 GitHub issue 标题命中了存在漏洞的 GitHub Actions 工作流，GitHub Advanced Security 审查最终 PR 修订版时没有标出注入问题，而 Wiz Red Agent 不断调整载荷，最终外传了一个 Jira token。这让“AI 审查会漏 bug”从抽象担忧，变成了一个公开、端到端的案例，也解释了为什么团队如今想要的是面向代码的对抗式审查和更紧的工作流边界。

## 7. 机会在哪里

**[+++] 面向支出的路由与配额控制平面** — 第 1–4 节的证据共同指向这一缺口：Codex 重置抱怨、Fable 5 usage credits、Anthropic 对 Claude Code 的临时提额、DeepSeek 备用路线分享，以及 9router/OpenCode 路由，都说明了同一个问题。用户想要的不只是更便宜的模型，而是一个能够预测容量、绕开上限，并在某个供应商计量收紧超出预期时维持工作继续推进的中间层。

**[+++] Harness 验证、对抗式审查与安全仓库自动化** — Akshay Pachaar 的生命周期帖子、Learn Harness Engineering、GitHub Agentic Workflows、Plankton，以及 Wiz/Snowflake 漏洞，共同强化了同一个需求。真正的强机会不在于再做一个编程演示，而在于构建能够在 Agent 输出进入生产环境之前，接管治理、评估、权限和面向代码审查的工具。

**[++] 跨仓库、worktree 和 hosts 的多 Agent 控制界面** — Cursor Origin、GitHub 的故障耦合，以及 Piotr Jura 的原生控制应用，都表明工作流所有权正在从编辑器向外扩展。中等强度的机会在于提供一个能跨托管与本地运行时协调项目、审查和 Agent 会话的界面，而不强迫用户完全活在某一家供应商的全栈里。

**[+] 参考资料蒸馏与会话学习层** — book-to-skill 和 vibe-learn 展示了一种尚早但真实存在的模式：团队开始把文档和历史会话视为应当被结构化加载、查询和审查的资产，而不是每次都重新拷进提示词。这个信号虽然比其他机会更早期，但它对应的是一个明确痛点：重复加载上下文，以及人对 Agent 所做改动缺乏足够理解。

## 8. 结论

1. **Harness 工程走到了台前。** 最强的讨论围绕生命周期所有权、运行时边界和评估，而不是提示词技巧。([来源](https://x.com/akshay_pachaar/status/2089707367172882669))
2. **按量计费正在实时重塑 AI 编程行为。** 积分弹窗、重置抱怨和临时配额政策变化，已经在把用户推向备用模型和多供应商路由。([来源](https://x.com/monosarin/status/2089811593508868524))
3. **仓库与身份认证界面如今已是 AI 编程的战略依赖。** GitHub 的事故报告和 Cursor 对 Origin 的定位都指向同一个结论：谁掌控仓库界面，谁就掌控了工作流中的很大一部分。([来源](https://x.com/githubstatus/status/2089794864917488010))
4. **只要速度足够快，Google 的托管栈仍然有真实吸引力。** 当天关于 Gemini 最有力的证据，不只是炫目的演示，还有实际文档工作流和从业者对持续吞吐的亲身反馈。([来源](https://x.com/googleaidevs/status/2089443913493033058))
5. **构建者正把重心放在 Agent 外围的操作层，而不是新的基础模型上。** 当天值得注意的项目集中在仓库自动化、写入时质量门禁、参考资料蒸馏和会话后理解。([来源](https://x.com/DotNetTrends/status/2089669318153765291))
