# Twitter AI 编程 - 2026-09-18

## 1. 人们在讨论什么

### 1.1 用量可见性、配额绕行和记忆控制仍然处在日常实践的中心（🡕）

当天最密集的一簇讨论，不是某个新模型发布，而是一个操作层问题：当会话越跑越长时，编程智能体究竟如何计算用量、记忆和计费。`codex` 的提及量与 9 月 17 日持平，仍为 47 次，而 `memory` / `compaction` / `context` 的提及量则从 19 次降到 14 次；不过，更强的证据反而集中在更少几条高互动帖子里，主题包括用量分析、压缩策略、缺失的项目记忆，以及套餐异常。

[@OpenAIDevs](https://x.com/OpenAIDevs) [宣布](https://x.com/OpenAIDevs/status/2100733364877803741)（495 次点赞、79 条回复、60,791 次浏览、140 次收藏），Codex 现在会展示用量如何拆分到任务、子智能体和单个聊天里。最有价值的回复并没有把这当成问题结束。大家立刻追问，这套分析能不能继续拆到例程级别，以及怎样的子智能体花费模式才算浪费、怎样才算健康，这说明用户现在要的不只是额度，而是能指导实际操作的遥测。

[@theo](https://x.com/theo) [认为](https://x.com/theo/status/2100762304862384257)（371 次点赞、50 条回复、39,432 次浏览、170 次收藏），Jev 风格的逐行压缩，并不是编程智能体合适的抽象方式，因为它会丢掉工具结果的上下文、破坏缓存的经济性，也保不住前沿 API 的隐藏推理轨迹。这个回复串之所以重要，在于它把一个产品抱怨推进成了技术分歧：压缩到底允许删掉什么、工具调用还是否能保持有意义的关联，以及一个智能体看起来有多聪明，究竟有多少取决于它能否保住完整的工作历史。

[@thtbee_](https://x.com/thtbee_) [列出](https://x.com/thtbee_/status/2100917034372751446)（224 次点赞、16 条回复、19,719 次浏览、28 次收藏）了一份针对 Gemini 4 Pro 和 Antigravity 的愿望清单，而它本质上就是一份项目记忆愿望清单：私有项目空间、可检查的记忆、恢复跨聊天记忆，以及桌面本地文件访问。另一条更直接的一手抱怨来自 [@RileyRalmuto](https://x.com/RileyRalmuto)，他 [贴出](https://x.com/RileyRalmuto/status/2101052413004120145)（19 次点赞、4 条回复、2,428 次浏览）一张 Codex 计费界面截图，显示 9 月 4 日一笔 ChatGPT Pro 20x 付款被系统标为 `Void`，回复则说 OpenAI 当天出过问题，并补发了积存重置。

另一个置信度较低的绕行故事也在流传。[@grokkedd](https://x.com/grokkedd) [分享](https://x.com/grokkedd/status/2100875124089987355)（26 次点赞、7 条回复、387 次浏览、18 次收藏）了一张已删除 r/codex 帖子的截图，声称 Codex 限额耗尽后，OpenAI Prism 仍然暴露 GPT-6 Astra Extra High。由于证据是间接的，而且原帖已经删除，最稳妥的读法是：这反映了人们正在主动寻找替代用量池，而不是一项已经确认的产品政策。

### 1.2 安全问题从背景担忧变成了具体的利用链分析（🡕）

安全讨论从边缘话题陡然跃升为一阶主题。围绕 exploit 或漏洞的提及量，从 9 月 17 日的 2 次升到 15 次，而且最强的帖子并不是猜测式警告，而是公开的利用链、修复状态讨论，以及一步步解释接入智能体的系统会如何失效。

[@justanotherlaw](https://x.com/justanotherlaw) [放大了](https://x.com/justanotherlaw/status/2100754948728508602)（346 次点赞、7 条回复、33,899 次浏览、187 次收藏）《华尔街日报》的报道： “三个订了 Claude 和 Codex 的人” 拿到了 OpenAI 的认证 token 和 `openai/openai` 的写权限。回复链很快追问，这到底是不是模型故事，还是单纯的运维安全太弱，从而帮助这起事件从安全圈讨论推进到了主流编程智能体话语里。

[@IntCyberDigest](https://x.com/IntCyberDigest) [报道了](https://x.com/IntCyberDigest/status/2100874723219460240)（377 次点赞、24 条回复、22,016 次浏览、138 次收藏）更完整的链路：一份做了手脚的 HEIF 上传命中 OpenAI Discourse 论坛里一条过时的 libheif 路径，然后 OpenAI 的 SSO 漏洞把这个立足点升级成员工的 ChatGPT 和 Codex 账号，最后进入内部仓库并发起了一个无害的 pull request。回复又补上了两点重要细节：OpenAI 在当天就修复了问题，并支付了 6,500 美元赏金；研究人员在整个利用过程中把 Claude 当成一个由人类主导流程调用的工具，而不是一个自主攻击者。

![重构后的 Codex 任务视图，展示一个无害的访问证明 pull request，它把 OpenAI README 内容替换成了 Hacktron AI 团队的概念验证标题](https://pbs.twimg.com/media/HSfM0WjWkAAIWyI.jpg)

[@The_Cyber_News](https://x.com/The_Cyber_News) [总结了](https://x.com/The_Cyber_News/status/2100881010846228812)（13 次点赞、1,547 次浏览）另一项 [Plugin4Shell 披露](https://cybersecuritynews.com/plugin4shell-zero-click-rce/)，而链接的 [Air Security 分析文章](https://www.air.security/blog-posts/plugin4shell) 表示，这个漏洞是 Claude Code、Codex、Copilot 和 Gemini CLI 插件安装器中的 SHA 固定绕过。关键的运维细节是：如果代码检出后从未验证工作树是否真的落在已审查的 commit 上，那么已安装插件就可能在自动更新时被替换成恶意代码，攻击也就变成了零点击；Air 表示 Claude Code 2.1.179 和 Codex 0.146.0 已修复，Gemini CLI 因为已经废弃不会补丁，而 Copilot 在披露时还没有已发布修复。

![Plugin4Shell 概要图，说明一种 SHA 固定绕过如何把受信任的插件更新变成主要编程智能体上的零点击远程代码执行](https://pbs.twimg.com/media/HSfT9-ibkAABOGe.jpg)

**讨论要点：** 回复持续反驳“是模型黑进了 OpenAI”这种偷懒式叙事。大家真正讨论的，是当编程智能体紧挨着插件、关联账号、内部仓库和 SSO 系统时，会多出怎样的攻击面。

**与前日对比：** 9 月 17 日还主要聚焦预算、密钥处理和自我审计。9 月 18 日则升级成了具体的利用链、厂商版本号和直接的补丁指引。

### 1.3 运行框架研究和设备执行变得具体得多（🡕）

最强的研究类帖子，讨论的不是如何切换基础模型，而是如何组织智能体工作。`antigravity` 的提及量从 9 月 17 日的 24 次微降到 23 次，但底层内容却更深入，开始围绕具名运行框架机制、共享记忆研究，以及真实设备执行闭环展开。

[@mirrokni](https://x.com/mirrokni) [分享了](https://x.com/mirrokni/status/2100660772393320476)（77 次点赞、3 条回复、4,272 次浏览、40 次收藏）[《Stellar Colosseum》论文](https://arxiv.org/abs/2609.15983)，介绍了一种多智能体工作流：策略探索、就绪门槛、证明拆解、分段求解，以及全局验证。论文给出的结果——TCS-Bench 71.0% 和 4,263 的 Codeforces 分数——再加上它已经被纳入 Antigravity Teamwork 的 “Long Proof” 模式，使它同时成为研究证据和产品迁移信号。

[@omarsar0](https://x.com/omarsar0) [重点提到](https://x.com/omarsar0/status/2101074795643494546)（19 次点赞、4 条回复、1,301 次浏览、33 次收藏）NVIDIA 的 [SoL-Pi 发布](https://github.com/NVlabs/SoL-Pi) 和论文（[arXiv](https://arxiv.org/abs/2609.20519)），其中点名了 4 个保留式效率机制——Action Fusion、Online Context Compact、ObservationPack 和 Evidence-Preserving Reducer。附图之所以重要，是因为它直接展示了宣称的 EdgeBench 结果：token 流量下降 44.7-49.0%，API 成本大约降低三分之一，同时在 GPT-5.6 Sol 和 Opus 5 上仍保持接近基线运行框架的表现。

![SoL-Pi 论文页面，展示其 4 个保留式运行框架机制、EdgeBench 评估设置，以及相较 Codex 和 Claude Code 基线更低的 API 成本示例](https://pbs.twimg.com/media/HSiEZBvaYAEwRbp.jpg)

一个并行的执行故事也出现在移动工具里。[@sl1ma4](https://x.com/sl1ma4) [表示](https://x.com/sl1ma4/status/2100817123857588378)（8 次点赞、12 条回复、944 次浏览、10 次收藏），Google 的 ARTEMIS 让 Claude Code、Codex 和 Antigravity 可以通过 MCP 使用真实 Android 设备，而 [@hasantoxr](https://x.com/hasantoxr) [又补充了](https://x.com/hasantoxr/status/2100954240592302129)（18 次点赞、8 条回复、4,898 次浏览、7 次收藏）其中的闭环价值：先构建应用，再在真机上运行，捕捉截图和追踪信息，然后利用观测到的失败回修代码。公开的 [google/artemis README](https://github.com/google/artemis) 也印证了 MCP 集成、Flash/Pro 执行档位，以及大家反复提到的 99%+ AndroidWorld 成绩。

**与前日对比：** 9 月 17 日已经明显倾向托管式运行框架和长证明工作流。到了 9 月 18 日，讨论又补上了具名效率机制、共享记忆架构，以及真机执行这些更具体的下一步。

### 1.4 构建者继续在智能体外围发货：运行时、队列、控制平面和技能包（🡒）

规模较小的构建者活动，仍然主要集中在基础模型之上那一层。`copilot` 的提及量在 9 月 17 日为 35 次后，9 月 18 日仍维持在 34 次，而最具体的项目帖，谈的都是打包、路由和分发，而不是新颖的模型行为。

[@github](https://x.com/github) [推广了](https://x.com/github/status/2101044801122836501)（43 次点赞、12 条回复、11,547 次浏览、17 次收藏）GitHub Copilot SDK，把它描述为一种无需自己编写智能体循环，就能嵌入会话、工具、MCP 服务器和流式事件的方法。回复很说明问题：不止一位开发者说，现在最难的已经不是循环本身，生产级痛点在于人工审批门、回滚路径，以及如何决定哪些动作必须可逆。同样的上移信号也出现在 GitHub 的 [每周 Copilot 更新日志](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14) 里：新增自动模型选择档位、基于 shell 的审查检查、Copilot 应用里的 Sentry 集成、VS Code Agents 窗口用量指标，以及 AI credit 预算申请。

## 2. 令人困扰的问题

### 支出、计费和配额界面仍然总在中断之后才出现

最直接的挫败感，不是有限额，而是用户仍然只有在工作卡住之后，才知道真正边界在哪里。[@OpenAIDevs](https://x.com/OpenAIDevs) [让](https://x.com/OpenAIDevs/status/2100733364877803741)（495 次点赞、79 条回复、60,791 次浏览、140 次收藏）Codex 的任务、子智能体和聊天级用量拆分变得可见，但回复马上就问起例程级优化建议，而不是把这个功能当成已经完工。[@RileyRalmuto](https://x.com/RileyRalmuto) [又给出](https://x.com/RileyRalmuto/status/2101052413004120145)（19 次点赞、4 条回复、2,428 次浏览）一种更尖锐的失效形式：截图显示付费 Codex 套餐收费被系统标为 `Void`，回复还说 OpenAI 在差不多同一时间已经需要补发积存重置。即便是置信度较低的 [@grokkedd](https://x.com/grokkedd) [绕行帖](https://x.com/grokkedd/status/2100875124089987355)（26 次点赞、7 条回复、387 次浏览、18 次收藏），也属于同一个故事：由于主配额界面仍然卡人，用户正在主动探测替代访问池。

GitHub 的 [9 月 18 日 Copilot 更新日志](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14) 进一步说明这不是单一厂商问题。预算增加申请如今已普遍可用，但前提仍是用户先撞上 AI credit 上限。严重程度：高，因为今天的绕行栈——分析标签页、预算申请流程、积存重置，以及其他产品的传闻入口——仍然都是在中断发生之后才启动，而不是之前。值得投入：高。

### 长时智能体会话里的压缩和项目记忆依然不透明

最深的技术挫败感，是用户既无法预测也无法检查的记忆行为。[@theo](https://x.com/theo) [认为](https://x.com/theo/status/2100762304862384257)（371 次点赞、50 条回复、39,432 次浏览、170 次收藏），逐行压缩会打断工具结果的连续性、迫使缓存高价重写，并丢掉外部总结器根本找不回来的推理轨迹。[@thtbee_](https://x.com/thtbee_) [则把](https://x.com/thtbee_/status/2100917034372751446)（224 次点赞、16 条回复、19,719 次浏览、28 次收藏）用户诉求说得很直白：Antigravity 需要私有项目记忆、可检查记忆，以及跨聊天记忆回归。

严重程度：高，因为现有应对方式都只是次优解：信默认、保留比自己想要更多的历史，或手动重述系统忘掉的内容。它和当天几篇研究帖的对比尤其醒目。Stellar Colosseum、SoL-Pi 和 Agora 都把记忆、状态或证据保留，当成运行框架层的设计问题，这说明用户准确指出的是一个缺失的系统层，而不只是抱怨 UX。值得投入：高。

### 插件和关联账号的信任层，对当下智能体携带的权限而言仍然过于脆弱

最强的恐惧信号，来自两条主要安全故事都发生在模型外层那几层里。[@justanotherlaw](https://x.com/justanotherlaw) [放大了](https://x.com/justanotherlaw/status/2100754948728508602)（346 次点赞、7 条回复、33,899 次浏览、187 次收藏）OpenAI 利用链事件，而 [@IntCyberDigest](https://x.com/IntCyberDigest) [又传播了](https://x.com/IntCyberDigest/status/2100874723219460240)（377 次点赞、24 条回复、22,016 次浏览、138 次收藏）从公开论坛上传，到 SSO 接管，再到 Codex 发起 pull request 的完整链路。与此同时，[Air Security 的 Plugin4Shell 分析](https://www.air.security/blog-posts/plugin4shell) 描述了另一条插件 SHA 固定绕过路径，足以让例行的插件市场更新变成零点击远程代码执行。

严重程度：高，因为爆炸半径正是编程智能体最有价值的地方：本地代码、密钥、SSH 密钥、已连接的 SaaS 工具，以及内部仓库。公开修复指引——明确的 Claude Code 和 Codex 修补版本、Gemini CLI 不会修，以及披露时 Copilot 仍有空缺——说明用户已经在围绕编程助手做事故响应式的版本排查。值得投入：高。

### 在智能体真正成为可管理的工作者之前，团队仍然需要队列和控制平面

另一个较安静但持续出现的挫败感，是协调开销。[@DanKornas](https://x.com/DanKornas) [直接总结道](https://x.com/DanKornas/status/2100769182098808846)（1 次点赞、3 条回复、417 次浏览）：“你的收件箱里堆满了工作，你的智能体需要一个队列。” 同一作者 [又表示](https://x.com/DanKornas/status/2100891068665413843)（1 次点赞、2 条回复、468 次浏览、2 次收藏），把编程智能体协调到多台机器上，不该还得“每次运行都盯着带”。[@github](https://x.com/github) [推广 Copilot SDK](https://x.com/github/status/2101044801122836501)（43 次点赞、12 条回复、11,547 次浏览、17 次收藏）那条帖子下的回复也说了同一件事：即便 SDK 把循环抽象掉了，难点仍在于判断哪些动作需要人工门控，以及如何撤销那些本不该发生的动作。

严重程度：中，因为它不像失去访问权限或被攻破那样灾难性，但一样会杀死工作流。市场信号很明确：构建者不再等基础模型自己解决这个问题，而是在外面另搭队列、仪表盘、审批和 fleet 路由层。值得投入：中。

## 3. 人们期望的功能

### 一个用户可检查、可引导的持久项目记忆

最清晰的未满足需求，不是更聪明的一次性回答，而是一个能跨压缩、跨界面切换、跨长时间运行存活下来，又不变成黑箱的项目记忆。[@theo](https://x.com/theo) [反对](https://x.com/theo/status/2100762304862384257) 外部压缩，因为它可能切断工具结果与其有用推理之间的联系；[@thtbee_](https://x.com/thtbee_) [则明确要求](https://x.com/thtbee_/status/2100917034372751446)（224 次点赞、16 条回复、19,719 次浏览、28 次收藏）Antigravity 提供私有项目记忆、本地文件访问，以及跨聊天记忆回归。就连正面的 [@OpenAIDevs](https://x.com/OpenAIDevs) [分析功能上线](https://x.com/OpenAIDevs/status/2100733364877803741)（495 次点赞、79 条回复、60,791 次浏览、140 次收藏）也指向同一方向：用户想检查一次运行内部到底发生了什么，而不是只好相信助手记得够多。

这不是愿景式需求，而是非常实际的需求。部分答案已经出现在用量分析、默认压缩策略，以及 [《Stellar Colosseum》](https://arxiv.org/abs/2609.15983)、[SoL-Pi](https://arxiv.org/abs/2609.20519) 和 [《Agora》](https://arxiv.org/abs/2609.18094) 这样的研究运行框架里，但这些方案仍没有一个能给日常用户提供跨产品表面的简单、可检查记忆层。机会：可直接切入。

### 一层会在故障发生前介入的支出与权限控制平面

第二个需求，是预防式治理。信号非常整齐：[@OpenAIDevs](https://x.com/OpenAIDevs) [推出](https://x.com/OpenAIDevs/status/2100733364877803741)（495 次点赞、79 条回复、60,791 次浏览、140 次收藏）Codex 用量分析，因为人们需要看清额度花到哪里；[@RileyRalmuto](https://x.com/RileyRalmuto) [显示](https://x.com/RileyRalmuto/status/2101052413004120145)（19 次点赞、4 条回复、2,428 次浏览）套餐计费恰恰会在信任最关键的时候变得混乱；GitHub 的 [每周 Copilot 更新日志](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14) 只在用户撞上上限之后，才加入预算提高申请；而 [Plugin4Shell](https://www.air.security/blog-posts/plugin4shell) 则展示了，当一个被信任的插件供应链继承了开发者全部权限时，会发生什么。

人们看起来想要的是：在一次运行开始前，就有一层东西能回答 4 个问题——还剩多少预算、哪些记忆或上下文会保留、哪些关联账号或密钥在作用域内，以及允许执行哪些插件或动作路径。今天的控制分散在计费页面、按版本发布的安全公告、预算申请队列，以及手动凭据管理里。机会：可直接切入。

### 一个让智能体工作排队和受控、同时仍把人放在主位的控制平面

第三个未满足需求，是工作流协调，而不是原始代码生成。[@DanKornas](https://x.com/DanKornas) [把](https://x.com/DanKornas/status/2100769182098808846)（1 次点赞、3 条回复、417 次浏览）Taskuary 描述为一个带审批检查点的 inbox-to-agent 队列，同一作者 [又把](https://x.com/DanKornas/status/2100891068665413843)（1 次点赞、2 条回复、468 次浏览、2 次收藏）apra-fleet 描述成跨机器、跨提供商长时工作的控制平面。[@github](https://x.com/github) [推销 Copilot SDK](https://x.com/github/status/2101044801122836501)（43 次点赞、12 条回复、11,547 次浏览、17 次收藏）那条帖子下的回复，则从反方向说了同样的话：一旦循环被抽象掉，瓶颈就会变成路由、可逆性和人工门控。

这是一个已有活体原型的现实需求。竞争难点并不是从零发明概念，而是交付一层比今天零散的终端、仪表盘和聊天线程混搭更简单的队列、审批、路由和可观察性。机会：竞争激烈。

### 让智能体在真实环境里观察自己所构建内容的反馈闭环

第四个需求，是一层执行系统，让编程智能体能在真实目标环境中观察自己构建的东西。[@hasantoxr](https://x.com/hasantoxr) [之所以认为](https://x.com/hasantoxr/status/2100954240592302129)（18 次点赞、8 条回复、4,898 次浏览、7 次收藏）[ARTEMIS](https://github.com/google/artemis) 重要，是因为它通过 MCP 赋予智能体在真实 Android 设备上的眼睛和手；[@sl1ma4](https://x.com/sl1ma4) [则把它框定为](https://x.com/sl1ma4/status/2100817123857588378)（8 次点赞、12 条回复、944 次浏览、10 次收藏）对移动端测试和调试立即有用。[@DemoWebAI](https://x.com/DemoWebAI) [也展示了](https://x.com/DemoWebAI/status/2101068674463662099)（3 次点赞、2 条回复、46 次浏览）浏览器产品演示中的同一模式：用提示词发起工作流，在本地执行，观察结果，然后把产物打包出去。

这对移动端、浏览器，以及重工作流产品来说，都是非常现实的需求，因为“代码能编译”并不是充分证据。这个机会属于竞争激烈的区间，因为开源和初创方案已经存在，但从讨论看，人们对更广的平台支持、更安全的凭据处理，以及更紧密的修复闭环都有明确胃口。机会：竞争激烈。

| Antigravity | 托管智能体 / 运行时 | (+/-) | Teamwork 模式、ARTEMIS 集成，以及 Gemini 4 Pro 发布前夕的强烈兴趣 | 用户仍希望它更成熟一些，并补上私有项目记忆、本地文件访问，以及跨聊天记忆恢复 |

| MiniMax Code | 终端编程智能体 | (+) | BYOK、插件、MCP、会话续接，以及开源源码预览 | 生态还新，源码仍是预览状态，平台 / 运行时要求也提高了采用摩擦 |

| apra-fleet | 智能体运维 / 控制平面 | (+) | 跨设备成员注册、按档位路由模型、仪表盘、持久工作流，以及带外密钥 | 多机编排天然运维负担重，而且相较厂商平台仍偏小众 |
| Taskuary | AI 任务枢纽 | (+) | 统一收件箱、AI 分拣、编程智能体路由、实时工作区，以及动作前的人类审批 | 仍是 pre-1.0 的早期产品界面，并依赖连接器加操作员审查 |
| Geoscience Skills | 领域技能包 | (+) | 跨智能体和科学格式可移植的 48 项技能，以及面向真实垂直工作的工作流打包 | 需要任务特定依赖，而且面向的专业人群比通用编程工具更窄 |
| DemoWeb | 浏览器自动化 / 演示生成 | (+/-) | 把带提示词的浏览器工作流变成带旁白的 1080p 视频和 PDF 报告，且能放进聊天工作流 | 热度仍很早期，也带着其他执行层同样的本地浏览器凭据 / 安全担忧 |

当工具能收窄范围，或者让运维变得可见时，整体满意度最高。ARTEMIS、SoL-Pi、apra-fleet、Taskuary、Geoscience Skills 和 MiniMax Code 之所以获得关注，都因为它们减少了含糊地带：一个给智能体一台真手机，一个把运行框架成本机制命名出来，一个管理多机集群，一个整理流入工作，一个打包垂直领域，一个把提供商可移植性讲清楚（[ARTEMIS](https://github.com/google/artemis)、[SoL-Pi](https://github.com/NVlabs/SoL-Pi)、[apra-fleet](https://github.com/Apra-Labs/apra-fleet)、[Taskuary](https://github.com/ldbumble/taskuary)、[Geoscience Skills](https://github.com/SteadfastAsArt/geoscience-skills)、[MiniMax Code](https://github.com/MiniMax-AI/minimax-code)）。

情绪最混合的，还是那些通用平台。人们确实在认真使用 Codex、Claude Code、Antigravity 和 Copilot，但今天的证据每次提到这些工具，都会附上关于预算可见性、压缩、记忆控制或供应链信任的保留意见（[OpenAIDevs 用量分析](https://x.com/OpenAIDevs/status/2100733364877803741)、[theo 压缩讨论串](https://x.com/theo/status/2100762304862384257)、[thtbee_ 的 Antigravity 愿望清单](https://x.com/thtbee_/status/2100917034372751446)、[GitHub 更新日志](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14)、[Plugin4Shell](https://www.air.security/blog-posts/plugin4shell)）。

那些绕行方案本身很说明问题。人们会要求积存重置、盯着分析标签页、在 Prism 里寻找替代 Astra 入口、坚持保留人工审批回路，或者把状态搬进显式的运行框架产物里，而不是相信基础智能体自己能记住一切。最清晰的迁移模式，是从单一提供商的智能体界面转向 BYOK 或多提供商路由、从只看代码的智能体转向借助 ARTEMIS 或 DemoWeb 做真实环境执行，以及从通用助手转向 Geoscience Skills、Taskuary 和 apra-fleet 这类领域或工作流打包。竞争态势因此继续上移：模型质量仍然重要，但眼下真正的竞赛越来越集中在运行时、控制、协同和证据界面。

最重要的构建模式，是位于智能体之上的控制层。apra-fleet 和 Taskuary 在解决相邻的工作流问题：一个负责跨真实机器协调提供商、设备、密钥和多小时工作流，另一个把杂乱的流入工作整理成带显式审批和操作员审查的队列。它们都在证明，构建者认为下一波产品机会不是再开一个助手窗口，而是做一层面向智能体工作的操作层。

![apra-fleet README 视图，展示一个控制平面如何把工作分发到 Claude、Gemini 或 Codex、本地 LLM，以及跨多台机器的测试套件](https://pbs.twimg.com/media/HSfdSeMXoAAfGwk.jpg)

![Taskuary README 视图，展示一个 inbox-to-agent 工作区如何把流入请求分流成任务，并在执行前保留审查环节](https://pbs.twimg.com/media/HSdubxGXcAAhl_e.jpg)

第二种模式，是可复用的专业化。Geoscience Skills 把垂直领域打包成可移植技能，而不是再套一层模型包装；ARTEMIS 则把真机执行打成可复用的 MCP 层，而不是又一个定制移动测试运行框架。Stellar Colosseum 和 SoL-Pi 从研究侧落在同一种模式上：前者把长时程证明工作拆成具名阶段，后者把自动研究中发现的效率机制打包成可安装扩展。

![Geoscience Skills 截图，展示一个覆盖地震、测井、反演、气候、水文、地球化学和可视化任务的可移植能力矩阵](https://pbs.twimg.com/media/HShOlOqX0AEYiEk.jpg)

MiniMax Code 是通用 CLI 类别里最清晰的竞争新进入者。仓库强调项目编辑、测试、会话续接、插件、MCP，以及 OpenAI / Anthropic 兼容的 BYOK；它的差异化点更多在工作流可移植性，而不只是专有基础模型。

![MiniMax Code 仓库截图，展示其开源终端智能体、文档，以及源码预览定位](https://pbs.twimg.com/media/HSgPnq4XkAEWNEF.png)

最小但最能说明问题的构建，是那些已经能直接产出成品的项目。DemoWebAI 展示了 ChatGPT 和 Codex 如何产出一个可安装的插件工作流，能录制浏览器操作并返回 1080p MP4 加 PDF 报告；而 [@raywongy](https://x.com/raywongy) [则展示了](https://x.com/raywongy/status/2100663117223002610)（5 次点赞、3 条回复、608 次浏览）一个可用的一次性 Antigravity 构建，用于移除图像元数据。这些帖子之所以重要，是因为它们表明，智能体式编程的长尾已经从基础设施外溢到简单可交付的实用工具和营销素材。

SoL-Pi 和 Stellar Colosseum 还一起展示了研究到产品的重复回路。前者已经以扩展形式开源，带安装文档和保守的 opt-in 默认设置；后者则已经被描述成 Antigravity Teamwork 的 `Long Proof` 模式的一部分。ARTEMIS 则从测试侧补全了这幅图景：它把真实手机当成编程智能体应该能观察、也应该能在上面修复问题的另一种环境。

## 6. 新动态与亮点

### Codex 上线了原生的用量分析界面
[@OpenAIDevs](https://x.com/OpenAIDevs) [宣布](https://x.com/OpenAIDevs/status/2100733364877803741)（495 次点赞、79 条回复、60,791 次浏览、140 次收藏），Codex 现在会按任务、子智能体和聊天拆分用量。这件事重要，是因为配额管理已经从后台计费顾虑，变成了产品内部一个可见的运维界面。

### Plugin4Shell 让智能体供应链安全再也无法被忽视
[Air Security 的披露](https://www.air.security/blog-posts/plugin4shell) 以及 [@The_Cyber_News](https://x.com/The_Cyber_News) [对它的总结](https://x.com/The_Cyber_News/status/2100881010846228812)（13 次点赞、1,547 次浏览），把插件 SHA 处理变成了主流编程智能体话题。它之所以引人注意，不只是因为影响名单里有 Claude Code、Codex、Copilot 和 Gemini CLI，还因为零点击自动更新这一角度，以及逐版本列清楚的修复状态。

### ARTEMIS 把真机执行带进了日常编程智能体讨论
[@sl1ma4](https://x.com/sl1ma4) [发帖](https://x.com/sl1ma4/status/2100817123857588378)（8 次点赞、12 条回复、944 次浏览、10 次收藏），而 [@hasantoxr](https://x.com/hasantoxr) [又展开说明](https://x.com/hasantoxr/status/2100954240592302129)（18 次点赞、8 条回复、4,898 次浏览、7 次收藏）[google/artemis](https://github.com/google/artemis)，因为它让智能体能通过 MCP 从代码生成迈向真机观察、测试和修复。这比只靠模拟器或截图的工作流，明显往前走了一步。

### GitHub 持续把 Copilot 扩成平台，而不只是助手
GitHub 的 [每周 Copilot 更新日志](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14) 加入了自动模型档位、审查改进、Copilot 应用里的 Sentry 集成、Agents 窗口用量指标，以及 AI credit 预算申请。再结合 [@github](https://x.com/github) [推广 Copilot SDK](https://x.com/github/status/2101044801122836501)（43 次点赞、12 条回复、11,547 次浏览、17 次收藏）这条帖子，信号已经很明显：平台表面积正在成为竞争的重要组成部分。

## 7. 机会在哪里

**[+++] 面向支出、记忆和权限的智能体控制平面** —— 这是数据里最强的横切面信号。Codex 用量分析、RileyRalmuto 那张显示收费被标为作废的截图、thtbee_ 对可检查记忆的要求、Theo 对压缩的批评、GitHub 的预算申请发布、OpenAI 的利用链，以及 Plugin4Shell，都指向同一个缺失层：在一次运行出错之前，有一个地方能看清成本、持久化、关联账号、插件信任和人工门控。

**[++] 面向智能体团队的队列与编排层** —— Taskuary、apra-fleet，以及 Copilot SDK 帖子下的回复，都在说下一个问题是如何路由和治理工作，而不是再生成一条回答。这个机会处在中强区间，因为原型已经存在，但在易用性、审批和多提供商执行上，市场看起来仍然开放。

**[++] 让智能体能测试自己所构建内容的闭环执行层** —— ARTEMIS 通过 MCP 给编程智能体接上一台真实 Android 设备，DemoWeb 把浏览器动作变成可录制产物，Stellar Colosseum 加 SoL-Pi 则在研究和运行框架效率上展示了同一种模式：当智能体能观察环境、保存证据时，它就更有用。这个方向对移动端、浏览器和重工作流产品尤其强。

**[+] 垂直技能包和轻量可交付小工具** —— Geoscience Skills 和由 Antigravity 构建的 Image Metadata Remover，展示了同一市场的两端：一端是给专业人士复用的领域打包，另一端是面向个人的轻量一次性工具。这个信号还在萌芽、还不是主导叙事，但它暗示未来的分发越来越可能落在可移植技能、工作流和以成品为先的构建上，而不是靠全新的单体应用。

## 8. 要点总结

1. **用量可见性已经成了产品界面的一部分，而不再只是后台管理补充。** OpenAI 在同一个 24 小时窗口里，为 Codex 上线了按任务、子智能体和聊天拆分的用量分析；GitHub 则扩展了 Copilot 的指标和预算流程。([OpenAIDevs](https://x.com/OpenAIDevs/status/2100733364877803741), [GitHub 更新日志](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14))
2. **安全叙事已经明确从模型行为转向模型外围各层。** OpenAI 利用链和 Plugin4Shell 讲的都不是模型自己失控，而是论坛、SSO、插件和连接系统如何失守。([IntCyberDigest](https://x.com/IntCyberDigest/status/2100874723219460240), [Air Security](https://www.air.security/blog-posts/plugin4shell))
3. **运行框架设计正变成一个可见的竞争层。** Stellar Colosseum、SoL-Pi、Agora 和 ARTEMIS 都把协同、共享状态、观察或压缩，当成带具名机制和可测结果的一等工程问题。([《Stellar Colosseum》](https://arxiv.org/abs/2609.15983), [SoL-Pi](https://arxiv.org/abs/2609.20519), [《Agora》](https://arxiv.org/abs/2609.18094), [ARTEMIS](https://github.com/google/artemis))
4. **最快的构建者活动，正聚集到控制平面、队列和垂直打包上。** apra-fleet、Taskuary、Geoscience Skills、DemoWeb，以及一个一次性元数据清理工具，都在说明构建者更愿意围绕现有智能体打包工作流，而不是继续等待单一通用助手解决整套栈。([apra-fleet](https://github.com/Apra-Labs/apra-fleet), [Taskuary](https://github.com/ldbumble/taskuary), [Geoscience Skills](https://github.com/SteadfastAsArt/geoscience-skills), [DemoWebAI](https://x.com/DemoWebAI/status/2101068674463662099), [raywongy](https://x.com/raywongy/status/2100663117223002610))
