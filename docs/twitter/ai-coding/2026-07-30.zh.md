# Twitter AI 编程 - 2026-07-30

## 1. 人们在讨论什么

### 1.1 企业级 harness、审查回路与可分支工作流开始具象化 🡕

Twitter 上关于 AI 编程最强的一波讨论，不是新的模型跑分，也不是花哨的一次性演示，而是：当智能体产出必须经受企业治理、代码审查和真实分支结构的约束时，一套可持续的运作模式到底是什么样。共有五条保留内容支撑这一主题：Satya Nadella 演示受治理的 ROIC 应用、GitHub 最新规模指标、GitHub 关于堆叠会话的现代化案例、Copilot 代码审查正式支持 skills/MCP，以及 Rubber Duck 的跨模型家族审查回路。

[@satyanadella](https://x.com/satyanadella) [展示了](https://x.com/satyanadella/status/2082640036949008570)（610 个赞、95 条回复、65,497 次浏览、316 次收藏）展示了一个详细的 ROIC Intelligence 应用：基于一份 Morgan Stanley PDF，用一条提示词，配合 `/drill-me` skill、Copilot autopilot 和 `/rubber-duck` 测试构建而成。真正特别的地方不是“CEO 做了个应用”，而是技术栈纪律：他表示，应用在 Copilot 中，代码在 GitHub Enterprise 中，数据管道、数据湖和语义模型在 Fabric 中，全部处于 IT、安全和 FinOps 的管控之下。架构图进一步明确了这一点：权威数据源通过 Fabric 编排和 OneLake 流入 Direct Lake 语义模型，再进入 React + TypeScript 的应用层。

![Satya Nadella 的 ROIC Intelligence 应用架构图，展示了权威文档如何流经 Fabric 编排、OneLake bronze/silver/gold 层、Direct Lake 语义模型，以及 React + TypeScript 应用运行时](https://pbs.twimg.com/media/HOcFUoObEAAgEUM.jpg)

[@kdaigle](https://x.com/kdaigle) [补充了](https://x.com/kdaigle/status/2082604368399159542)（59 个赞、7 条回复、7,393 次浏览）补上了这一企业叙事的规模背景：GitHub 拥有 2.25 亿开发者、5,000 万 Copilot 用户，且每 3 个 pull request 中就有 1 个涉及智能体。另一条 [推文](https://x.com/kdaigle/status/2082917875531272279)（35 个赞、1 条回复、5,084 次浏览、11 次收藏）指向 Cassidy Williams 的 [关于堆叠会话和拉取请求的文章](https://github.blog/ai-and-ml/github-copilot/stacked-sessions-and-pull-requests-in-the-github-copilot-app/)，其中一次对旧版 React 15 应用的单次现代化改造失败，最终变成一串堆叠会话和堆叠 PR。这很重要，因为它把智能体编程定义为分支编排和审查卫生问题，而不只是更快的提示词循环。

[@GHchangelog](https://x.com/GHchangelog) [报道了](https://x.com/GHchangelog/status/2082590761132949812)（20 个赞、4 条回复、2,392 次浏览、5 次收藏）称，Copilot 代码审查现已正式支持 agent skills 和 MCP 服务器。关联的 [GitHub 更新日志](https://github.blog/changelog/2026-07-29-copilot-code-review-agent-skills-and-mcp-now-generally-available/) 说明，审查可以使用 `.github/skills/.../SKILL.md`，MCP 调用保持只读，现有 cloud-agent MCP 配置也会自动沿用。与此同时，[@burkeholland](https://x.com/burkeholland) [指向](https://x.com/burkeholland/status/2082596001450258832)（30 个赞、3 条回复、3,145 次浏览、11 次收藏）也强化了这一点：[Rubber Duck](https://github.blog/ai-and-ml/github-copilot/github-copilot-cli-combines-model-families-for-a-second-opinion/) 是 GitHub 面向 Copilot CLI 的跨模型家族批评回路。

**讨论洞察：** Satya 这条帖子的回复与原帖本身共同强化了同一个主题：企业价值来自受治理、可复用的产物，而不是一次性输出。Cassidy 的文章补上了这幅图景的另一半：即使智能体能力很强，单次现代化改造仍然失败，必须重启为堆叠式分支流。真正的信任边界不是“模型会不会写代码”，而是“这项工作能否经得住治理和审查？”

**与前一天相比：** 7 月 29 日已经把讨论推向 skills、可观测性和远程工作区。7 月 30 日则更进一步，深入到运作模式层面：受治理的数据栈、感知分支的会话链、审查阶段的仓库上下文，以及明确的第二意见回路。

OpenAI 的 AI 编程叙事，从前一天围绕配额和供应商切换的讨论，转向了更广的产品面：更丰富的视觉编辑、浏览器和计算机使用工作流、更便宜的价格梯度，以及与 harness 设置相关、而不只是基础模型本身的基准提升。共有四条保留内容支撑这一主题。

## 2. 什么让人沮丧

### Harness 与模型不匹配，而且会悄悄失效

严重程度：高。当天最尖锐的挫败并不是“AI 不会写代码”，而是：整个栈看起来像是正常工作的，但 harness 与模型的假设其实早已开始漂移。[@0xJeyx](https://x.com/0xJeyx) [认为](https://x.com/0xJeyx/status/2082465629110428113)（34 个赞、4,817 次浏览、36 次收藏）指出，纯粹的 vibe coding 会产生反复试错的循环——“我们可以尝试一百种不同方法”——但每次仍可能得到不同实现，并明确把 spec-driven development 作为解法。[@radshaan](https://x.com/radshaan) [警告](https://x.com/radshaan/status/2082881023638147106)（184 次浏览）则把这类抱怨说得更具体：Kimi K3 对保留的思考历史很敏感，切换会话或使用不兼容的 harness，都可能让输出质量变得不稳定。

![截图内容指出，Kimi K3 对保留的思考历史较为敏感，建议使用已验证兼容的测试框架，并警告切换正在进行中的会话可能导致质量不稳定](https://pbs.twimg.com/media/HOfhNXUbsAALrnI.png)

同样的信任问题也出现在产品侧。[@OpenAIDevs](https://x.com/OpenAIDevs) [展示](https://x.com/OpenAIDevs/status/2082944138635595782)（359 个赞、28 条回复、31,425 次浏览、117 次收藏）关于 Codex 新灯箱和画布的帖子下，回复立刻追问：这次发布改善的是图像质量，还是只是编辑界面。人们愿意用更聪明的工具，但他们想知道，栈里真正变强的到底是哪一层。

这值得围绕它去构建产品，因为失败方式很隐蔽：模型仍然会回答，智能体仍然能完成，工作流却可能在只有事后才会暴露的地方出错。

### 降价只停留在父智能体层面

严重程度：高。OpenAI 再次把定价变成面向用户的核心叙事，但用户反馈表明，如果编排层不能智能路由任务，更低的标价并不能解决太多问题。[@LuminaXspace](https://x.com/LuminaXspace) [总结了](https://x.com/LuminaXspace/status/2082888693832954155)（19 个赞、1,064 次浏览）介绍了官方调整：Luna 降价 80%，Terra 降价 20%，Codex/ChatGPT Work 的额度也更耐用。但 [@schaerpfcom](https://x.com/schaerpfcom) [立即询问](https://x.com/schaerpfcom/status/2082885895481352305)（11 个赞、5 条回复、2,628 次浏览）则要求 Sol 能生成更便宜的 Luna 或 Terra 子智能体，否则每个子智能体都会继承昂贵的父级配置。

关联的 [GitHub issue](https://github.com/openai/codex/issues/32705) 让这条抱怨变得异常具体：据称，当前运行时隐藏了路由控制、强制模型继承，并阻断了预期的 Sol-to-Terra/Luna 工作流。另一条成本边界则体现在 [@alexcooldev](https://x.com/alexcooldev) [询问](https://x.com/alexcooldev/status/2082831031129067740)（19 个赞、9 条回复、1,106 次浏览）中：尤其当代码库和维护需求越来越大时，与其花价值数千美元的 token 去重造某个 SaaS，是否还不如每月花 $20 继续使用现成产品。

人们的应对方式包括：把重负载任务卡着订阅限制来跑、切换后端，或者要求更便宜的子智能体，而不只是更便宜的父级会话。这值得投入，因为它已不再是单纯的定价问题，而是路由和工作负载塑形问题。

### 跨智能体集成仍然需要桥接器和能力层

严重程度：中。独立构建者持续在做胶水代码，因为核心工具仍然默认不同的 API、认证路径和平台访问规则。[@rightnowai_co](https://x.com/rightnowai_co) [表示](https://x.com/rightnowai_co/status/2082821361953616149)（5 个赞、172 次浏览）称，其构建了一个 localhost 桥接器，让 Claude Code、Codex、Cline、Aider 和 OpenCode 都能指向同一个本地 Kimi 后端，而无需定制改写。[@undefinedKi](https://x.com/undefinedKi) [介绍了](https://x.com/undefinedKi/status/2082836315989487940)（8 个赞、129 次浏览、4 次收藏）介绍了 [Agent Reach](https://github.com/Panniantong/Agent-Reach)，其 README 明确写道：Twitter API 访问每月约需 $215，Reddit 常会对匿名服务器 IP 返回 403，多个平台还需要 cookie 或浏览器会话式绕过方案。

同样的模式也解释了为什么 [@charliejhills](https://x.com/charliejhills) [强调了](https://x.com/charliejhills/status/2082758408198140192)（18 个赞、8 条回复、1,311 次浏览）推出了 The Agency 在 Claude Code、Cursor、Codex 和 Gemini CLI 之间的一键安装器。这些新产品不只是“更多智能体”，而是在努力让一个碎片化的智能体生态，看起来更像同一个环境。

这值得投入，因为多个独立团队已经在从不同角度解决同一个问题：API 翻译、互联网访问和多工具安装。这通常意味着，平台缺口是真实存在的。

## 3. 人们希望出现什么

### Codex 内部的异构子智能体

今天最明确的显性诉求，是父智能体能够选择更便宜或更合适的子模型，而不是强制继承。[@schaerpfcom](https://x.com/schaerpfcom) [询问](https://x.com/schaerpfcom/status/2082885895481352305) 在 OpenAI 下调 Terra 和 Luna 价格后，要求 Sol 能启动 Terra 或 Luna 子智能体；关联的 [issue](https://github.com/openai/codex/issues/32705) 则把这一点扩展成具体产品诉求：可配置的子模型选择、更严格的子智能体权限，以及获取当前被隐藏的路由控制。这是一个务实需求，而不是情绪化诉求，因为当天官方降价的价值，取决于运行时能否真正利用这些价格变化。机会：直接。

### 模型切换的已验证兼容性契约

第二项需求，是在团队把某个工作流押到开放模型上之前，能有信心确认它会在指定 harness 中正确运行。[@radshaan](https://x.com/radshaan) [挖掘出](https://x.com/radshaan/status/2082881023638147106) 展示了一张 Kimi K3 截图，称该模型依赖保留的思考历史，只应与经验证兼容的 harness 搭配使用；而 [@rightnowai_co](https://x.com/rightnowai_co) [构建了](https://x.com/rightnowai_co/status/2082821361953616149) 则介绍了一个 localhost 桥接器，恰恰因为 Claude Code、Codex、Cline、Aider 和 OpenCode 期待的 API 各不相同。[@ridark_eth](https://x.com/ridark_eth) [将其视为](https://x.com/ridark_eth/status/2082819827824042059) 把模型切换视为正常工程工作，但今天的证据表明，这件事仍然脆弱到让人们想要明确担保，而不是靠口耳相传。桥接器和定制封装提供了部分答案，但还没有标准化的信任契约。机会：直接。

### 一键式可移植能力包

人们也希望，自己的可复用能力能跨工具迁移，而不是每换一个厂商栈就要重新拼装。[@charliejhills](https://x.com/charliejhills) [强调了](https://x.com/charliejhills/status/2082758408198140192) 指向跨多种编程工具的一键智能体安装，[@undefinedKi](https://x.com/undefinedKi) [推广了](https://x.com/undefinedKi/status/2082836315989487940) 指向 Agent Reach 提供的一命令社交/Web 访问，而 [@tom_doerr](https://x.com/tom_doerr) [重点介绍了](https://x.com/tom_doerr/status/2082774815220376001) [ClaudeSkills](https://github.com/staruhub/ClaudeSkills) 则代表一组经过测试的端到端工作流，覆盖 PRD、决策简报、演示文稿和文章。这是一个务实需求，而且竞争压力已经可见：多个开源项目都部分回答了它，但各自只覆盖问题的不同切片。机会：竞争性。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| GitHub Copilot 应用和代码审查 | 智能体平台 | (+) | 装机基础大，支持堆叠会话/PR、审查时的 skills 和 MCP 上下文，契合企业治理 | 仍然依赖分支纪律和明确的审查结构 |
| Rubber Duck | 审查方法 | (+) | 使用另一模型家族做批评，可提升复杂多文件审查质量，并内置于 Copilot CLI | 增加编排步骤，且只有团队愿意停下来审查时才有帮助 |
| Codex 应用 | 编程工作区 | (+/-) | 应用内浏览器、计算机使用、历史检索、自动化、PR 审查、工件查看、图像编辑画布 | 用户仍在追问界面升级是否也提升了底层质量；子智能体路由仍受限制 |
| 保留推理加压缩 | 智能体运行时方法 | (+) | 在共享的 GPT-5.6 Sol ARC 示例中，显著提升长任务表现并降低 token 使用 | 需要特定 API/运行时支持；若 harness 把这些旋钮藏起来，很容易被忽略 |
| Antigravity | 智能体工作区 | (+/-) | 支持自然语言评估分析、定量推理、并行子智能体，在 Google 技术栈中能见度高 | 回复仍在要求连接器、更好的讲解和更强证据 |
| Google 免费 AI 工具栈 | 工具套件 | (+) | 在编程、设计、文档和后端工作流上广泛免费分发 | 免费层级仍有各种门槛，且榜单热度可能跑在真实日用前面 |
| DeepSeek 和本地 Kimi 后端 | LLM 后端 | (+/-) | 执行便宜、本地可控、可挂在现有智能体外壳后面，量化后的 Kimi 可跑在单张 32 GB GPU 上 | API 不匹配、兼容性假设，以及对 harness 敏感的质量表现 |
| Autoresearch | 循环框架 | (+) | 提供 14 个跨智能体命令、目标导向改进回路，并声称 token 降低 95% | 需要有意识地搭建并持续衡量，不是一条提示词就能解决 |
| ClaudeSkills | Skill 包 | (+) | 为研究、PRD、演示文稿和文章提供经过测试的端到端工作流 | 覆盖范围比大型通用智能体包更窄，传播面也更小 |
| The Agency | 智能体包与安装器 | (+/-) | 拥有大量角色化智能体，并支持在主流编程工具间一键安装 | 智能体太多可能造成过载；部分运行时会悄悄跳过其中一部分 |
| Agent Reach | 能力层 | (+) | 一条命令提供 Web 和社交访问，研究价值高，并给受限平台提供明确配置路径 | 某些目标仍需 cookie、OpenCLI 或额外本地配置 |

整体满意度更取决于 harness 是否完整，而不是基础模型的品牌。当人们谈论受治理的工件、堆叠式审查流程和第二意见检查时，Copilot 获得正向评价；当人们谈论更广的工作界面和更便宜的价格梯度时，Codex 也获得正向评价，但用户一旦碰到隐藏的路由限制，情绪就变成了混合；Antigravity 则先引发兴趣，随后立刻招来关于连接器和证据的追问。

表中常见的应对方式也很一致：从一次性提示词转向规范和循环、把昂贵后端换成便宜后端、加入第二个审查模型，以及安装数据访问或角色库能力层。当前的竞争格局已形成三方：GitHub 在治理和审查重要的场景里最强，OpenAI 正在推动产品广度和运行时效率，而开源构建者在跨工具可移植性上推进最快。

Satya Nadella 的例子，是这组项目里企业形态最明显的构建。真正有意思的不是“新奇”，而是这个应用被呈现为一个可复用、受治理的系统：数据在 Fabric，代码在 GitHub Enterprise，应用逻辑在 Copilot，审查则通过专门的 `/rubber-duck` 环节完成。这更接近内部产品开发，而不是一次性演示。

Autoresearch、ClaudeSkills 和 The Agency 都指向同一个方向：构建者正在把流程产品化。Autoresearch 把跨智能体迭代变成命令网格；ClaudeSkills 把端到端交付物视作应该经过测试的软件；The Agency 则定义了几十种专业角色，再通过桌面安装器分发出去，使其能被投放到多个工具中。

![ClaudeSkills 截图，展示了仓库 README、验证徽章，以及用于 PRD、演示文稿和研究任务的示例工作流输出](https://pbs.twimg.com/media/HOeAqDYXcAAWZxW.jpg)

Agent Reach 和 Local Kimi bridge 展现了同样的构建者本能，只不过对象不是提示词，而是基础设施。Agent Reach 打包的是那些通常被 API、认证或浏览器状态挡住的数据源访问能力；Kimi bridge 打包的则是跨不兼容本地智能体 API 的模型可移植性。共同触发点不是“我们需要更聪明的模型”，而是“我们需要在任何地方都拥有同样的能力”。

重复出现的构建模式很容易识别。人们在做安装器、桥接器、能力层和 skill 包，是因为真正的痛点在于可移植性、可审查性和数据访问。同一天里，多支团队独立做出了“模型之上一层”的产品，这强烈表明该缺口是结构性的，而不是小众问题。

## 7. 机会在哪里

**[+++] Pricing-aware orchestration across model tiers** — Evidence came from multiple directions at once: OpenAI cut Luna and Terra pricing, [@schaerpfcom](https://x.com/schaerpfcom) [询问](https://x.com/schaerpfcom/status/2082885895481352305) 要求 Sol 把工作路由给那些更便宜的子智能体，[@ridark_eth](https://x.com/ridark_eth) [介绍了](https://x.com/ridark_eth/status/2082819827824042059) 展示了手动“harness swap”，而 [@rightnowai_co](https://x.com/rightnowai_co) [构建了](https://x.com/rightnowai_co/status/2082821361953616149) 则提供了一个桥接器，让现有智能体外壳指向不同后端。这一点很强，因为用户已经在手工拼装这套变通方案。

**[+++] 面向可复用智能体工作的企业治理** — Satya Nadella 受治理的 Fabric + GitHub 构建、GitHub“每 3 个 PR 就有 1 个涉及智能体”的规模说法、堆叠会话与堆叠 PR、Copilot 代码审查 skills，以及 Rubber Duck，都指向同一个机会：团队需要的是能产出持久、经过审查资产的智能体工作流，而不是一次性答案。这个机会很强，因为第一方厂商和实践者都在向同样的控制点收敛。

**[++] 可移植的能力与工作流包** — The Agency、ClaudeSkills、Autoresearch 和 Agent Reach 都在模型之上打包可复用层：角色、skills、命令回路和外部数据访问。这是中等强度机会，而不是完全开放的空白地带，因为开源竞争已经清晰可见，但解决方案仍按能力和运行时碎片化分布。

**[+] 开放模型 harness 的兼容性验证** — Kimi K3 关于保留思考的警告、spec-driven development 对输出不一致的抱怨，以及对 localhost API 桥接器的需求，都表明存在一个更小但正在增长的机会：为智能体 + 模型组合建立标准化兼容性测试。这还是一个新兴机会，因为痛点真实存在，但市场信号目前仍主要集中在更技术型的用户中。

## 8. 要点总结

1. **企业采用智能体，正在被表述为受治理的系统设计，而不只是更快地写提示词。** Satya Nadella 的 ROIC 演示和 GitHub 的规模数据，都把持久工件、治理和审查流程放在核心位置，而不是模型新奇性本身。（[来源](https://x.com/satyanadella/status/2082640036949008570)）
2. **Google 仍凭借广度和免费分发吸引注意力，但用户正在按工作流深度来评判 Antigravity。** 免费工具清单扩大了触达面，而 Antigravity 的评估讨论则引来了关于连接器、证据和真实分析能力的追问。（[来源](https://x.com/antigravity/status/2082534317633290284)）
3. **Codex 正在扩展到浏览器、视觉和长时工作，而不是停留在狭义编程智能体。** 7 月 30 日的应用更新日志和 ImageGen 画布更新，都实质性拓宽了产品面。（[来源](https://developers.openai.com/codex/changelog#codex-2026-07-30-app)）
4. **更便宜的模型，只有在编排层真的能用上它们时才有意义。** OpenAI 下调 Luna 和 Terra 价格后，用户立刻要求异构子智能体；与此同时，构建者仍在持续交付手动桥接和后端切换方案。（[来源](https://github.com/openai/codex/issues/32705)）
5. **开源构建者在模型之上的可移植层推进最快。** Autoresearch、ClaudeSkills、The Agency、Agent Reach 和 Local Kimi bridge，都把 skills、安装、访问和路由本身当作产品面。（[来源](https://github.com/uditgoenka/autoresearch)）
