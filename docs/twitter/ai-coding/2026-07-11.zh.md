# Twitter AI 编程 - 2026-07-11

## 1. 人们在讨论什么

### 1.1 Google 的智能体叙事讲的是工作流栈，而不只是模型（🡕）

与 Google 相关的最强讨论，并不是又一次基准测试口号，而是一套套如何组合研究记忆、技能与长时运行智能体的具体操作方法。至少有两条入选内容表明，人们正在把 Google 的编程栈当作端到端工作流操作面，而不是单独的模型选择。

[@shubham_crazy08](https://x.com/shubham_crazy08) [认为](https://x.com/shubham_crazy08/status/2075756239469089186)（248 个赞、11 条回复、26,396 次浏览、368 次收藏）表示，NotebookLM 加 Google Antigravity 是一组尚未被充分利用的组合，随后又在回复串里详细列出其具体用途：深度研究智能体、会反复读取本地 Markdown 上下文的业务专属技能、具备上下文感知能力的应用生成、自动输出 NotebookLM 报告，以及由 Python 驱动的数据摄取流水线。关键并不在于“Google 很强”，而在于这种组合减少了手动搬运数据的需求，让存储的上下文真正变成智能体可执行的知识。

[@antigravity](https://x.com/antigravity) [指出](https://x.com/antigravity/status/2075622887319318781)（26 个赞、8,747 次浏览、22 次收藏）链接到一个反思记忆构建系列；其源线程把问题拆成了了解用户、了解工作、划清智能体与运行框架的边界，以及用 Google Cloud 加 Antigravity 实现闭环。这让当天围绕 Google 的讨论，比单纯的产品宣传更具架构层面的意味。

**讨论洞察：** 实际关注点落在记忆、摄取和可复用技能上。即便帖子带有宣传色彩，人们真正回应的仍是具体的操作问题：上下文存在哪里、如何更新，以及智能体如何把存储的知识转化为代码或报告。

**与前一天对比：** 7 月 10 日的 Google 信号更偏向生态版图和“全栈”定位。到 7 月 11 日，讨论又往实现层靠近了一步：具体的 NotebookLM + Antigravity 工作流和反思记忆设计，取代了宽泛的平台话术。

### 1.2 运行框架不断演变成可移植产品与验证层（🡕）

第二个主要讨论集群围绕运行框架本身展开：如何证明智能体修复的是对的问题、如何把工作流迁移到不同宿主，以及如何复用成熟界面而不放弃自定义后端。至少有五条入选内容符合这一框架，因此 7 月 11 日更像是在讨论操作面，而不是原始模型发布。

[@thdxr](https://x.com/thdxr) [展示了](https://x.com/thdxr/status/2075752746892828801)（112 个赞、6 条回复、9,432 次浏览、19 次收藏）展示了一个 OpenCode 流程：issue 最终变成 PR，并附带用于验证修复结果的视频。截图把这个承诺讲得很具体：智能体不只是改文件，还必须产出关于改了什么的、可供审查的证据。

![OpenCode 工作流，展示了传入的问题、生成的拉取请求，以及为修复附上的验证视频](https://pbs.twimg.com/media/HM6OHZfWkAEyCcE.jpg)

[@kitlangton](https://x.com/kitlangton) [解释了](https://x.com/kitlangton/status/2075749116760457346)（53 个赞、5 条回复、5,416 次浏览、34 次收藏）介绍了 OpenCode 2.0 的新“hot context”功能；被引用的 beta 线程则明确写出了成熟度权衡：可能丢数据、部分功能损坏、v2 API 尚未定稿，以及内置技能系统。与此同时，[@ArchitectHappy_](https://x.com/ArchitectHappy_) [强调了](https://x.com/ArchitectHappy_/status/2075939322235146595)（36 个赞、10 条回复、3,581 次浏览、38 次收藏）介绍了 [wshobson/agents](https://github.com/wshobson/agents) marketplace，其公开 README 称，该市场从一个 Markdown 源文件生成了适用于 Claude Code、Codex CLI、Cursor、OpenCode、Gemini CLI 和 GitHub Copilot 的 92 个插件、199 个智能体、162 个技能、106 个命令和 16 个编排器。

规模较小但同样有代表性的构建者帖子也指向同一方向。[@S1r1u5_](https://x.com/S1r1u5_) [描述了](https://x.com/S1r1u5_/status/2076041885236465941)（14 个赞、3 条回复、1,090 次浏览、11 次收藏）介绍了一个协议翻译层，让其团队在保留自定义安全导向智能体运行框架的同时，复用 OpenCode 的 TUI 与 UI 界面；[@Marco_Ramilli](https://x.com/Marco_Ramilli) [分享了](https://x.com/Marco_Ramilli/status/2075936793006866560)（1 个赞、1 条回复、35 次浏览、1 次收藏）则介绍了 [ultracodex](https://github.com/YuanpingSong/ultracodex)，该项目公开将自己定位为一种在 Codex 和 OpenCode 上运行 Claude Code 工作流，并提供循环、调度与长期存在组织能力的方式。

**讨论洞察：** OpenCode 验证帖下的回复把主题重新拉回现实。支持者仍指出，PR 终究还是要有人审查，monorepo 依然比玩具演示更难，CPU 或电池问题也依旧重要。大家想要的是更好的证据和更好的操作面，而不是零监督。

**与前一天对比：** 7 月 10 日围绕 OpenCode 的讨论，主要集中在 beta 开放和技能包分发上。到 7 月 11 日，话题已推进到更具体的机制：验证视频、保留缓存的上下文、协议复用，以及跨运行框架、以仓库为单位的可移植性。

### 1.3 基准测试胜利必须经得起分发与预算现实的检验（🡕）

第三个讨论集群表明，“最佳模型”的争论已不再止于排行榜位置。人们不断把基准测试结果与宿主可用性、重置窗口和真实会话经济性联系起来。至少有五条入选内容强化了这一转变。

[@ArtificialAnlys](https://x.com/ArtificialAnlys) [报道称](https://x.com/ArtificialAnlys/status/2075739735822307577)（96 个赞、10 条回复、7,348 次浏览）表示，Muse Spark 1.1 在 OpenCode 运行框架中的编程智能体指数上得分 69，略低于 Codex 中的 GPT-5.5，高于 Claude Code 中的 Claude Opus 4.8，单任务成本约为 $1.4。附带图表之所以重要，在于它展示的是成本与性能之间的权衡，而不只是一个醒目的总排名。

![基准测试图表显示，Muse Spark 1.1 接近 GPT-5.5，并以更低得多的单任务成本领先于 Claude Opus 4.8](https://pbs.twimg.com/media/HM6CSZZbYAAE-3Q.jpg)

但可用性立刻成了下一个问题。[@sethsaler](https://x.com/sethsaler) [抱怨道](https://x.com/sethsaler/status/2075803365640925565)（24 个赞、3 条回复、5,798 次浏览、4 次收藏）指出，Muse Spark 1.1 仍未进入 Cursor、Devin、OpenCode、Replit、Lovable、Venice 和 Manus，Alexandr Wang 回复称相关集成即将推出。在操作层面，[@Aytunc](https://x.com/Aytunc) [提醒道](https://x.com/Aytunc/status/2076065970938888455)（5 条回复、1,826 次浏览）提醒 Codex 用户在未使用的 Ultra 或 Fast 容量重置前运行 `/usage`；而 [@cjzafir](https://x.com/cjzafir) [展示了](https://x.com/cjzafir/status/2075753130084753723)（5 个赞、4 条回复、1,165 次浏览）则记录了一天内烧掉超过 $1,200 额度、手动重置限制、恢复 91% 周容量，同时仍有三个长期目标在运行的情况。

**讨论洞察：** 基准测试帖下的回复，对按运行框架归一化后的排名明显持怀疑态度。人们明确表示，现在真正有用的问题不再是“谁是第一”，而是“这在我的工作负载上要花多少钱？而且我能不能在自己已经在用的产品里真的用上它？”

**与前一天对比：** 7 月 10 日的成本讨论主要围绕发布入口和价格定位。到 7 月 11 日，讨论更偏向日常运营：即将到期的容量、重置时钟、宿主支持缺口，以及长期目标对剩余跑量的争抢。

### 1.4 对 vibe coding 焦虑的答案，是更多结构，而不是更少（🡕）

最后一个清晰主题是：对“vibe coding”最可信的回应，并不是回到一切都手工完成，而是增加规范、评估、验证和明确的护栏。至少有四条入选内容从不同角度指向了这一方向。

[@Pirat_Nation](https://x.com/Pirat_Nation) [报道称](https://x.com/Pirat_Nation/status/2076049893056270336)（389 个赞、28 条回复、21,819 次浏览、57 次收藏）表示，Donkey Kong 64 PC 重编译团队之所以提前宣布项目，主要是为了与另一个据称严重依赖 AI “vibe coding” 的竞争项目区分开来。最有力的回复并不是绝对反 AI，而是认为有经验的团队只要用确定性脚手架和维护纪律把模型包起来，仍然能赢。

[@hasantoxr](https://x.com/hasantoxr) [列出了](https://x.com/hasantoxr/status/2075864853542269183)（45 个赞、24 条回复、6,857 次浏览、54 次收藏）介绍了“能帮你找到工作的 AI 项目”，但核心内容是：如今的入门技术栈已经从评估、监控、护栏和工作流编排开始，包括带评估的 RAG、智能体运维看板、代码审查 AI、提示词安全和多智能体规划器。附带截图把 LangGraph 和 Unstructured 指向了具体构建模块，而不是抽象炒作。

![LangGraph 仓库页面，强调其作为低层级框架提供代理编排能力，并支持持久化执行和 human-in-the-loop](https://pbs.twimg.com/media/HM70FK_bUAALpdC.jpg)

![Unstructured 仓库页面，展示了面向 PDF、HTML、图像及其他非结构化来源的文档摄取与 ETL 工具](https://pbs.twimg.com/media/HM70FUlbAAAd4le.jpg)

同样的倾向也出现在较小的工作流帖子里。[@xieike](https://x.com/xieike) [表示](https://x.com/xieike/status/2075888900053045271)（8 个赞、3 条回复、37 次浏览、6 次收藏）表示，某个 `/grill-me` 技能会在 Claude Code 动手写任何内容前先问 40 多个澄清问题；[@gippp69](https://x.com/gippp69) [展示了](https://x.com/gippp69/status/2076010201468317747)（12 个赞、5 条回复、154 次浏览、5 次收藏）则介绍了一个 vault spec：它在发现一条被埋起来的规则变更后，并没有盲目遵循，而是阻止了 Claude 自动合并笔记。

**讨论洞察：** 支持智能体的一方并没有主张减少流程，而是主张把流程前移：编码前的问题树、可以让一次运行直接失败的规范，以及能在模型动手前捕捉危险假设的仓库或工作流结构。

**与前一天对比：** 7 月 10 日的信任讨论聚焦于配额、隐藏控制项和错误标注的模式。到 7 月 11 日，同样的信任问题被进一步推入工作流内部：规范、评估和执行前检查，正被当作坏智能体输出的真正解药。

## 2. 人们感到沮丧的地方

### 模型可用性、配额和重置时钟仍在决定人们实际上能用什么

严重程度：高。基准测试叙事不断撞上宿主现实。[@sethsaler](https://x.com/sethsaler) [抱怨道](https://x.com/sethsaler/status/2075803365640925565)（24 个赞、3 条回复、5,798 次浏览、4 次收藏）指出，Muse Spark 1.1 缺席于人们实际使用的大多数主流编程产品，尽管 [@ArtificialAnlys](https://x.com/ArtificialAnlys) [展示了](https://x.com/ArtificialAnlys/status/2075739735822307577)（96 个赞、10 条回复、7,348 次浏览）显示其成本性能结果很强。除此之外，[@Aytunc](https://x.com/Aytunc) [表示](https://x.com/Aytunc/status/2076065970938888455)（5 条回复、1,826 次浏览）提醒 Codex 用户在未使用容量重置前检查 `/usage`；[@cjzafir](https://x.com/cjzafir) [展示了](https://x.com/cjzafir/status/2075753130084753723)（5 个赞、4 条回复、1,165 次浏览）则展示了高强度的一天如何迅速变成“烧掉价值 $1,200 的 token”，再加上一次限制重置，而三个长期目标仍在运行。常见应对方式是盯着重置计时器、尽量压缩上下文，并安装诸如 [Token Time](https://tokentime.bar) 这样的封装工具；其官网强调在 macOS 上仅做本地使用量跟踪。这个方向值得投入，因为人们显然会先围绕剩余跑量和宿主支持优化，再考虑基准测试排名。

### 没有更强护栏时，人们仍不信任纯提示词编程

严重程度：高。当天传播最广的质疑来自 [@Pirat_Nation](https://x.com/Pirat_Nation) [报道](https://x.com/Pirat_Nation/status/2076049893056270336)（389 个赞、28 条回复、21,819 次浏览、57 次收藏）：Donkey Kong 64 重编译团队希望将自己与一个据称严重依赖 AI “vibe coding” 的竞争项目区分开来。更技术化的回应，则来自试图在正确位置增加摩擦的构建者：[@xieike](https://x.com/xieike) [表示](https://x.com/xieike/status/2075888900053045271)（8 个赞、3 条回复、37 次浏览、6 次收藏）中的 `/grill-me` 会阻止 Claude Code 在问题澄清前动手写代码；[@gippp69](https://x.com/gippp69) [展示了](https://x.com/gippp69/status/2076010201468317747)（12 个赞、5 条回复、154 次浏览、5 次收藏）中的规范文件会在执行前捕捉危险的自动合并规则；[@michabbb](https://x.com/michabbb) [描述了](https://x.com/michabbb/status/2075746468078719201)（2 条回复、82 次浏览）中的 `dcg` 则作为执行前防火墙，拦截破坏性的 shell 和 git 命令。即便是 OpenCode 的 PR 验证演示，回复里也有人指出结果依然需要人工审查，而且 monorepo 仍比展示型运行更难处理。这个方向值得投入，因为市场并不是要求智能体更快行动，而是要求它们少犯不可逆错误。

### 通用运行框架在领域化或高度定制的工作流里仍会失灵

严重程度：中。[@S1r1u5_](https://x.com/S1r1u5_) [写道](https://x.com/S1r1u5_/status/2076041885236465941)（14 个赞、3 条回复、1,090 次浏览、11 次收藏）表示，Codex、Claude Code、OpenCode 和 Pi 等提供方的运行框架并不适配一个高度定制的安全工作流，因此其团队先做了自定义智能体运行框架，再把它翻译到 OpenCode 的 UI 层。[@Markojak](https://x.com/Markojak) [列出了](https://x.com/Markojak/status/2076008180270965017)（1 条回复、81 次浏览、1 次收藏）则描述了一条冗长的 Apple 应用工具链：由于 WWDC 内容被 JavaScript 锁住，模型在视觉化应用质量上仍然吃力，因此必须借助 computer-use 测试和 MCP 支撑文档，才勉强形成可用工作流。常见补救方式是不断叠加技能、MCP、模板，以及微软的 [power-platform-skills](https://github.com/microsoft/power-platform-skills) 这类领域插件。这个方向值得投入，因为当天不少最出色的实践者帖子，本质上都在讲如何修补基础运行框架的缺口。

## 3. 人们希望存在什么

### 一个跨宿主的统一花费与跑量控制层

最明确的实际需求不是另一个排行榜，而是一个能统一看清智能体会话花了多少钱、容量何时重置，以及长期任务是否还该继续跑的地方。[@Aytunc](https://x.com/Aytunc) [表示](https://x.com/Aytunc/status/2076065970938888455)（5 条回复、1,826 次浏览）提醒用户检查 `/usage`；[@cjzafir](https://x.com/cjzafir) [控制节奏](https://x.com/cjzafir/status/2075753130084753723)（5 个赞、4 条回复、1,165 次浏览）记录了一天的 token 消耗与重置；[@wzulfikar](https://x.com/wzulfikar) [指出](https://x.com/wzulfikar/status/2076061138152731086)（2 个赞、41 次浏览、2 次收藏）到 [Token Time](https://tokentime.bar)，也从另一个角度描述了同一缺口。[@riabcevv](https://x.com/riabcevv) [补充道](https://x.com/riabcevv/status/2075891375963304195)（5 个赞、5 条回复、114 次浏览）则提出了第二种补救方式：通过压缩上下文，避免为重复发送无用历史而付费。机会：直接。

### 能跨模型与宿主切换存活的可移植工作流包

人们反复表明，他们不想为每个运行框架重复搭同一套工作流。[@ArchitectHappy_](https://x.com/ArchitectHappy_) [提到了](https://x.com/ArchitectHappy_/status/2075939322235146595)（36 个赞、10 条回复、3,581 次浏览、38 次收藏）介绍了 [wshobson/agents](https://github.com/wshobson/agents) 这个跨运行框架市场，提供插件、智能体、技能、命令和编排器；[@Marco_Ramilli](https://x.com/Marco_Ramilli) [指出](https://x.com/Marco_Ramilli/status/2075936793006866560)（1 个赞、1 条回复、35 次浏览、1 次收藏）指向 [ultracodex](https://github.com/YuanpingSong/ultracodex)，将其作为在 Codex 和 OpenCode 上运行 Claude Code 工作流的方式；[@schneika](https://x.com/schneika) [链接到](https://x.com/schneika/status/2076020082807849029)（1 个赞、1 次转发、82 次浏览、1 次收藏）则介绍了微软的 [power-platform-skills](https://github.com/microsoft/power-platform-skills) marketplace，面向 Power Platform 工作。实际诉求很简单：工作流写一次，就能跨工具携带，同时不丢失周边技能、命令和安全假设。机会：竞争性。

### 能在执行前拦住错误假设的安全与规范层

这里的诉求不是“让智能体更有创造力”，而是“让智能体在该提问、该检查、该拒绝的时候这么做”。[@xieike](https://x.com/xieike) [推广了](https://x.com/xieike/status/2075888900053045271)（8 个赞、3 条回复、37 次浏览、6 次收藏）强调 `/grill-me`，正因为它会在写代码前强制先提澄清问题；[@gippp69](https://x.com/gippp69) [使用了](https://x.com/gippp69/status/2076010201468317747)（12 个赞、5 条回复、154 次浏览、5 次收藏）把一个 vault spec 当作第二审查者，抓住了隐藏的自动合并规则；[@michabbb](https://x.com/michabbb) [描述了](https://x.com/michabbb/status/2075746468078719201)（2 条回复、82 次浏览）则把 `dcg` 当作一个 hook，在智能体执行破坏性 shell 和 git 命令前将其拦下。这个需求既实际又紧迫：人们想要的是更便宜的错误，而不只是更快的输出。机会：直接。

### 为界面密集型或被 JavaScript 锁住的生态提供更好的领域落地

还有一个更专业但同样重要的需求，来自那些所处技术栈让模型看不清真实环境的人。[@Markojak](https://x.com/Markojak) [表示](https://x.com/Markojak/status/2076008180270965017)（1 条回复、81 次浏览、1 次收藏）指出，Apple 的 WWDC 内容不可抓取，模型在界面和动画输出上仍然较弱；要让应用构建会话更可靠，必须结合 computer use 与基于 MCP 的文档。微软的 [power-platform-skills](https://github.com/microsoft/power-platform-skills) 也从企业侧指向同一需求：通过打包领域专属插件，而不是要求通用智能体从零推断 Power Platform 工作流。与其说这是泛泛的“更好的 AI”诉求，不如说是围绕特定生态构建扎实适配器的需求。机会：理想型。

总体来看，满意度光谱与其说是“最佳模型获胜”，不如说是“最佳操作面获胜”。只要周边工作流讲得通，人们乐于使用 Claude Code、Codex、OpenCode、Antigravity 或 Muse Spark；但他们也在不断绕开缺失的集成、隐藏的使用状态，以及薄弱的领域落地能力。

最常见的补救方式，是在基础工具外再加一层结构：可移植技能包（[wshobson/agents](https://github.com/wshobson/agents)）、运行时桥接（[ultracodex](https://github.com/YuanpingSong/ultracodex)）、领域插件市场（[power-platform-skills](https://github.com/microsoft/power-platform-skills)）、执行前提问（`/grill-me`），以及 [Token Time](https://tokentime.bar) 这样的花费控制封装。迁移压力看起来更务实而非意识形态化。人们想要的是，任何能带来更好的记忆、更强的可审查性、更多剩余容量，或一个真的开放所需模型的宿主组合。

## 8. 要点总结

1. **Google 最强的编程信号是操作性的，而不是宣传性的。** 与 Google 相关的最重要帖子，讲的是 NotebookLM 搭配 Antigravity、反思记忆和可复用技能，而不是单纯夸某个模型名字。（[来源](https://x.com/shubham_crazy08/status/2075756239469089186)）
2. **运行框架层持续吸收产品价值。** OpenCode 的验证闭环、hot context、跨运行框架市场和运行时桥接，都比抽象的“AI 能写代码”更具体。（[来源](https://x.com/thdxr/status/2075752746892828801)）
3. **基准测试胜利如今必须经得起宿主支持与预算现实的检验。** Muse Spark 的公开图表看起来很强，但同一天的回复和配套帖子很快就转向了缺失的集成、重置窗口和跑量管理。（[来源](https://x.com/ArtificialAnlys/status/2075739735822307577)）
4. **市场对 vibe-coding 焦虑的回应，是更多结构，而不是更少结构。** 信号最强的修复方式，是重评估的项目模板、澄清技能、规范检查和命令护栏，而不是放弃 AI 辅助编程。（[来源](https://x.com/hasantoxr/status/2075864853542269183)）
5. **真正交付的成果和保护性封装，比单纯炒作更重要。** 可提交 CRAN 的地图包、官方插件市场和破坏性命令防护，让当天整体语气比泛泛产品宣传更务实。（[来源](https://x.com/YusakuHoriuchi/status/2075871561978962029)）
