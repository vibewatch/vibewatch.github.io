# Twitter AI 编程 - 2026-08-09

## 1. 大家在讨论什么

### 1.1 工作流工程正在取代提示词工程，成为当下的前沿方向（🡕）

至少有四条有实质内容的信息，都将编程代理视为需要路由、重试逻辑、缓存策略和显式收敛检查的工作负载系统，而不只是需要更好提示词的工具。这一转变在从业者讨论和研究总结中都很明显：当模型已经“足够会写代码”之后，图工程、按轮服务和循环控制就成了新的瓶颈。

[@0xMovez](https://x.com/0xMovez) [认为](https://x.com/0xMovez/status/2086481283404710047)（73 个赞、9 条回复、8,756 次浏览、94 次收藏）提到，一位 OpenAI 工程师称，OpenAI 已有 85% 的工程师在用 Codex 运行数百个代理，并将下一层重点定义为图工程，而非提示词技巧。重要的不只是这条醒目的说法；回复几乎立刻就把“提示词只是第一层”当作不言自明的事实来看待，因此这条帖子既是新闻，也是情绪风向标。

[@rohanpaul_ai](https://x.com/rohanpaul_ai) [总结了](https://x.com/rohanpaul_ai/status/2086356354713985266)（20 个赞、5 条回复、2,971 次浏览、19 次收藏）介绍了 Microsoft 的 [现实世界中的智能体编程：在生产规模下刻画 GitHub Copilot 轨迹](https://arxiv.org/abs/2608.00101)，并给出了当天最清晰的一组生产数据：抽样了 1,350 万次 Copilot 会话，87% 的 LLM 调用来自代理而非用户；单轮内 KV cache 命中率从约 45% 提升到 92%–94%，而一旦切换模型，这一比例会降到 8%。这些数字之所以重要，在于它们说明编程代理基础设施应围绕轮次和会话来调度，而不是把每个请求孤立处理。

![论文截图，突出展示了 GitHub Copilot 生产轨迹中关于智能体发起调用以及轮次内缓存行为的研究发现](https://pbs.twimg.com/media/HPQ5ZdaaIAANkCZ.jpg)

[@marfinxx](https://x.com/marfinxx) [补充了](https://x.com/marfinxx/status/2086581462921261122)（4 个赞、40 次浏览、4 次收藏）则补上了另一层偏研究的内容：[LoopsBench](https://arxiv.org/abs/2608.00267) 列举了证据门控重试、上下文隔离的循环状态、检查点、诊断探针，以及确定性的收敛门控，并将这些机制视为区分静态 harness 评估与长时程代理执行的关键。即便规模较小，它也强化了同一个观点：一旦允许代理连续运行数十步，循环设计本身就成了产品。

**讨论洞察：** 回复并没有争论提示词是否仍然重要。大家默认提示词只是入场门槛，争论点转向了重试、缓存边界、任务状态和循环纪律。

**与前一天相比：** 8 月 8 日已经出现了用户围绕代理构建 sidecar 和故障回退层。到了 8 月 9 日，讨论进一步推进到更明确的工作负载工程，并拿出了更多关于按轮服务和自我纠错执行循环的具体证据。

### 1.2 可移植代理打包持续升温，讨论进一步上移到信任与安装语义（🡒）

至少有四条有实质内容的信息都默认一件事：可移植打包已经足够真实，不必再争论它是否可行；接下来更棘手的一层，是谁来安装软件包、它获得哪些权限、来源如何验证，以及同一个打包在不同客户端上应如何表现。共同的框架是，把同一个文件夹交付给 Claude Code、Codex、Cursor、Antigravity 及类似宿主环境，正变得可行，但安全分发仍未解决。

[@bibryam](https://x.com/bibryam) [报告了](https://x.com/bibryam/status/2086147058088497321)（42 个赞、3 条回复、2,980 次浏览、56 次收藏）提到，Google、OpenAI、Amazon、Microsoft、Cursor 和 Vercel 现在共同采用一套开放的 Agent Plugins 规范，可将 skills 和 MCP 一次打包，并在不同客户端之间复用。Google 公开的 [发布文章](https://developers.googleblog.com/agent-plugins-package-your-skills-tools-and-more/) 证实了这一范围有限但重要的约定：一个包含 `plugin.json`、`skills/` 和 `mcp.json` 的可移植目录；至于安装流程、权限、沙箱、信任和来源验证，则被有意留在规范之外。

![Agent Plugins 示例，展示了一个包含 plugin.json、skills 和 mcp.json 的可移植文件夹](https://pbs.twimg.com/media/HPN7Zw6XAAAYECm.jpg)

[@_vmlops](https://x.com/_vmlops) [重新阐释了](https://x.com/_vmlops/status/2086484035669504105)（17 个赞、5 条回复、1,023 次浏览、7 次收藏）将同一标准视为一个分发问题，认为打包只能部分解决它。真正有价值的是回复：有人要求提供共享的合规测试夹具，以确保一个会打开 socket 的 skill 在所有环境里都以相同方式失败；也有人警告说，如果没有 capability manifest，这种打包从第一天起就会继承 npm 供应链的全部教训。

[@sabir_huss50540](https://x.com/sabir_huss50540) [指向了](https://x.com/sabir_huss50540/status/2086332099804397806)（5 个赞、692 次浏览）Google 公开了 [`google/skills` repo](https://github.com/google/skills)。README 将其描述为一个可通过单条命令调用的目录，收录了 Google 编写的技能，以及面向 Claude Code、Codex 和 Antigravity CLI 的插件包。这让“可移植性”不再停留在口头：该标准已经被用于分发现行的云端流程，而不是让模型依据过时文档自行猜测。

[@DanKornas](https://x.com/DanKornas) [展示了](https://x.com/DanKornas/status/2086514333438091491)（10 个赞、4 条回复、1,333 次浏览、11 个收藏）[Citadel](https://github.com/SethGammon/Citadel)：这是一个围绕 Claude Code 和 Codex 的开源操作层，提供 `/do` 路由、仓库本地状态、交接、验证产物和钩子。它不是打包规范，但它展示了可移植性一旦存在，人们会立刻构建什么：位于代理之上的控制平面。

**讨论洞察：** 最受关注的未解问题不是语法，而是审核与权限。打包解决了“我该如何分发这个文件夹”，而生态系统在“这个文件夹被允许做什么”上显然还没跟上。

**与前一天对比：** 8 月 8 日让 Agent Plugins 显得更可信；8 月 9 日则把 Google 推上核心维护者的位置，并让可用的技能包和操作层浮出水面——这些都默认跨客户端流转已是常态。

### 1.3 Google 的 AI 编码栈仍然存在感十足，但最强烈的开发者信号依旧是不信任（🡖）

Google 在信息流中仍然很显眼，但原因并不是开发者在庆祝一套顺畅的编码工作流。公开信号明显分成两类：一边是广泛的生态版图和对标准的参与，另一边则是对政策、绑定和 harness 质量的直接抱怨。

[@coderjohn0](https://x.com/coderjohn0) [梳理了](https://x.com/coderjohn0/status/2086077932410458472)（36 个赞、4 条回复、1,575 次浏览、31 个收藏）梳理了 Google 横跨模型、代理、编码工具、视频、设计和研究的整体栈。随附图片之所以有信息量，是因为它把 Antigravity、Jules、Gemini CLI、Google ADK、A2A、NotebookLM 以及 Gemini/Gemma 模型放进同一张六层架构图里，让这家公司的产品野心一目了然。

[@theo](https://x.com/theo) [认为](https://x.com/theo/status/2085946505555587148)（402 个赞、28 条回复、24,613 次浏览）称，Antigravity 在禁止于 Google 自家工具之外使用订阅方面态度激进，不提供 ACP 绑定，还用封闭的 AGY 路径取代了 Gemini CLI 的开放性。由于回复大多是在放大账号风险，而不是纠正这些说法，这条帖子主导了当天 Google 编码相关的舆论情绪。

[@elshayib_](https://x.com/elshayib_) [对此做了总结](https://x.com/elshayib_/status/2086413689570132477)（16 个赞、3 条回复、791 次浏览）用一句直白的话概括：Google 在发布下一款专业模型之前，需要先拿出一个靠谱的 harness，因为现在的 Antigravity 基本不可用。结合关于标准和技能包的帖子来看，整体图景并不是“Google 缺席”，而是“Google 无处不在，但面向开发者的编码界面仍未获得信任”。

**讨论洞察：** 开发者的反弹针对的是工作流可靠性和账号政策，而不是模型野心。仅有高可见度并不能修复信任。

**与前一天对比：** 8 月 8 日，围绕 Antigravity 的抱怨已经集中在封禁、限制和产品界面错位上。到 8 月 9 日，Google 编码相关的原始提及量虽略少一些，但最尖锐的一线评论仍然是负面的。

### 1.4 用户正把界面当作稳定层，而在其下替换模型或运行时（🡕）

当天几条最强的实用型帖子都默认了一件事：外层的 shell、编辑器或命令界面可以保持不变，底层的模型、端点或运行时则可以替换。这比忠于单一厂商更成熟：人们想保留自己熟悉的工作流，同时根据隐私、价格、速率限制或会话持久性来切换后端。

[@OlivercrestAI](https://x.com/OlivercrestAI) [梳理了](https://x.com/OlivercrestAI/status/2086327944591319333)（48 个赞、15 条回复、7 个收藏）给出了一套五步 LM Studio 配置，可把本地模型变成兼容 OpenAI 的 localhost API，供 Hermes、Codex 或自定义脚本使用。这张图的重要性在于，它把迁移路径说得非常具体：安装 LM Studio、按 RAM 预算选择模型、启用本地服务器，然后把现有工具指向 `localhost`，而不是云端端点。

![五步本地 AI 设置流程，展示了 LM Studio 安装、基于硬件选择模型、启用 localhost API，以及替换工具端点](https://pbs.twimg.com/media/HPQgNJvXoAAJMEb.jpg)[@EOEboh](https://x.com/EOEboh) [推荐了](https://x.com/EOEboh/status/2086402556339605841)（6 个赞，1,101 次浏览）在 `localhost:11434` 上借助 Ollama 在 VS Code 中继续使用，作为一套完全本地化的结对编程方案。公开的 [Continue 网站](https://continue.dev) 和 [repo](https://github.com/continuedev/continue) 证实，该项目作为开源编程代理仍然存在，尽管在被 Cursor 收购后现已转为只读。这让“本地且离线”既成为优势，也带来维护上的权衡。

[@Dan_Jeffries1](https://x.com/Dan_Jeffries1) [描述了](https://x.com/Dan_Jeffries1/status/2086535190520660065)（14 个赞，3 条回复，2,789 次浏览，9 次收藏）则从另一个角度体现了同样的后端切换思路：Cursor 被替换为搭配 Sol/Fable 的 Codex，而 Kimi K3 则放在另一套独立框架中处理其他工作。其主张并不是某一个模型能解决所有问题，而是只有在环境、登录状态、工具和反馈闭环都配置妥当时，长会话才能真正运转起来。

**讨论洞察：** 正向情绪所依附的，不只是智能水平，还有兼容性与控制权。即便是支持本地方案的回复，也立刻提到了代价：你获得了隐私和摆脱套餐限制的自由，但会失去一部分随时按需挑选最佳模型的能力。

**与前一天的对比：** 8 月 8 日还将本地运行时和路由器视为备用方案；到 8 月 9 日，这已经变成了直接的操作建议：界面不变，只换后端。

## 2. 什么最让人沮丧

### 账户风险、配额状态和套餐经济性仍在左右工具选择

这仍然是高严重度问题，因为它直接影响工作流是否还能继续。[@theo](https://x.com/theo) [表示](https://x.com/theo/status/2085946505555587148)（402 个赞，28 条回复，24,613 次浏览）指出，Antigravity 可能会惩罚在 Google 自家工具之外使用订阅的行为，而且至今仍不提供 ACP 绑定；与此同时，[@OlivercrestAI](https://x.com/OlivercrestAI) [主推](https://x.com/OlivercrestAI/status/2086327944591319333)（48 个赞，15 条回复，7 次收藏）则把本地 LM Studio 视为规避封禁、涨价和云端限制的直接出路。人们的应对方式是明确而现实的，不是停留在理论层面：把同一套界面迁移到 `localhost`、切换框架，或者自己掌控端点。

这正是值得直接着手构建的方向。人们要的不是一个更漂亮的计费页面；他们是在通过更换运行时来规避不确定性。一个好用的配额台账、权益调试器，或保障账户安全的适配层，都能解决一个用户已经视为运营层面严重问题的痛点。

### 代理运行一段时间后，框架质量和工作流状态仍然很脆弱

这是另一个高严重度抱怨。[@elshayib_](https://x.com/elshayib_) [称之为](https://x.com/elshayib_/status/2086413689570132477)（16 个赞，3 条回复，791 次浏览）称 Antigravity“基本不可用”；而 [@rohanpaul_ai](https://x.com/rohanpaul_ai) [展示了](https://x.com/rohanpaul_ai/status/2086356354713985266)（20 个赞，5 条回复，2,971 次浏览，19 次收藏）则质疑，为何按“请求”形态构建的基础设施会浪费真实代理工作流中最强的信号。[@tonysimons_](https://x.com/tonysimons_) [披露了](https://x.com/tonysimons_/status/2086436348659929376)（36 个赞，6 条回复，1,523 次浏览，32 次收藏）介绍了一条面向服务器端的新压缩路径，用于处理超长 GPT-5.6 会话；但第一条有价值的回复并不是庆祝，而是要求测试恢复状态是否会悄悄遗忘待处理的审批或工具结果。

当下的变通办法是增加操作纪律：把状态保留在本地、谨慎加入压缩机制，或安装类似 [Citadel](https://github.com/SethGammon/Citadel) 的一层来保留交接和验证。这也说明它值得专门去构建。问题不只是模型质量，还在于长时间运行任务的状态能否持久保持。

### 默认代理行为仍会把简单任务做得过度复杂，并掩盖工程判断

这属于中等严重度问题，但表现得异常具体。[@simplifyinAI](https://x.com/simplifyinAI) [演示了](https://x.com/simplifyinAI/status/2086317184502964476)（14 个赞、3 条回复、1,183 次浏览、16 个收藏）直接点出了日期选择器的失败模式：许多代理会安装 `flatpickr`，对其再做一层封装，然后大谈时区问题，但浏览器本身已经有 `<input type="date">`。公开的 [Ponytail repo](https://github.com/DietrichGebert/ponytail) 则通过其“原生能力/标准库优先”的阶梯和基准测试主张，让同样的抱怨变得可以衡量；而 [@techNmak](https://x.com/techNmak) [认为](https://x.com/techNmak/status/2086540403948560805)（6 个赞、1 条回复、634 次浏览、7 个收藏）指出，AI 正在让语法层面的产出变得商品化，而不是让架构设计、测试判断或边界情况识别变得商品化。

这值得投入去做，因为这种痛点并不抽象。它会体现为额外依赖、不必要的代码，以及虚假的把握感。当前最好的应对方式，是增加一种技能或评审习惯，强制优先考虑那些乏味但更合适的实现。

## 3. 人们希望存在什么

### 位于插件封装之上的可移植信任与能力层

被反复提到的结构性需求，并不是另一套技能包，而是位于技能包之上的控制层。[@bibryam](https://x.com/bibryam) [制作了](https://x.com/bibryam/status/2086147058088497321) 让封装契约变得具体，而 Google 的 [Agent Plugins 文章](https://developers.googleblog.com/agent-plugins-package-your-skills-tools-and-more/) 也同样明确了缺失的部分：安装流程、权限、来源、沙箱隔离和撤销机制。[@_vmlops](https://x.com/_vmlops) [推动了](https://x.com/_vmlops/status/2086484035669504105) 又在回复中把这一点进一步推进，提出应有共享的合规测试夹具和能力清单。机会：直接。

### 状态能够跨长会话、分支和中断保留下来，而不必靠猜

有几项内容从不同角度表达了同一个诉求：不要再在轮次之间丢失工作。[@rohanpaul_ai](https://x.com/rohanpaul_ai) [展示了](https://x.com/rohanpaul_ai/status/2086356354713985266) 指出，编码代理的工作负载是围绕轮次和会话组织的，而不是围绕彼此孤立的请求；[@tonysimons_](https://x.com/tonysimons_) [揭示了](https://x.com/tonysimons_/status/2086436348659929376) 提出了面向长时间 GPT-5.6 运行的具体压缩设置；[@DanKornas](https://x.com/DanKornas) [指向了](https://x.com/DanKornas/status/2086514333438091491) [Citadel](https://github.com/SethGammon/Citadel) 则将其设想为仓库本地的记忆与交接层。这是紧迫的现实需求，不是推测性的需求。机会：直接。

### 保持相同编码工作界面的私有、本地或更便宜的后端

关于本地模型和离线 IDE 的帖子，想要的是连续性，而不是新奇。[@OlivercrestAI](https://x.com/OlivercrestAI) [想要](https://x.com/OlivercrestAI/status/2086327944591319333) 提到一种现有工具已经能够对接的 localhost API，[@EOEboh](https://x.com/EOEboh) [想要](https://x.com/EOEboh/status/2086402556339605841) 提到一个基于 Ollama 的本地 VS Code 代理，以及 [@Dan_Jeffries1](https://x.com/Dan_Jeffries1) [想要](https://x.com/Dan_Jeffries1/status/2086535190520660065) 在更换底层模型时，仍能保留现有 harness 的自由。这个需求确实存在，但赛道已经开始拥挤。机会：竞争型。

### 在构建任何额外功能之前，优先采用最简单可行实现的代理

这是数据集中最明确的直接产品诉求之一，即便它有时是以演示而不是请求的形式出现。[@simplifyinAI](https://x.com/simplifyinAI) [制作了](https://x.com/simplifyinAI/status/2086317184502964476) 把原生日期输入与 `flatpickr` 的示例对比得极其具体，而公开的 [Ponytail 仓库](https://github.com/DietrichGebert/ponytail) 则把这种偏好做成了一套可安装的规则集，并附带公开的基准测试声明。这个需求很务实：代码更少、依赖更少、评审中的意外更少。机会：直接型。

| Agent Plugins 1.0.0 | 标准 | (+/-) | 为多个客户端提供一个可移植的 skills 和 MCP 封装层 | 安装、权限、沙箱、信任和来源追溯都交由各客户端处理 |

| Ponytail | 代理技能 | (+) | 强制优先采用原生功能和标准库，减少不必要的代码和依赖膨胀 | 在默认代理倾向于过度构建时最有帮助；但仍然多了一层需要安装 |

这一天并没有出现赢家通吃的技术栈。它展示的是，人们先把自己喜欢的界面稳定下来，再替换其下方的后端、记忆层或护栏机制。[@Dan_Jeffries1](https://x.com/Dan_Jeffries1) [迁移了](https://x.com/Dan_Jeffries1/status/2086535190520660065) 从 Cursor 切到 Codex，同时为其他模型保留独立的 harness；[@OlivercrestAI](https://x.com/OlivercrestAI) [替换了](https://x.com/OlivercrestAI/status/2086327944591319333) 用带 localhost API 的 ChatGPT Plus 工作流；以及 [@EOEboh](https://x.com/EOEboh) [使用了](https://x.com/EOEboh/status/2086402556339605841) 使用 Continue 加 Ollama，在保留 IDE 界面的同时去掉云端依赖。

满意度分布也遵循同样的模式。底层模型能力仍然重要，但最强烈的正面情绪集中在那些能保留状态、减少过度构建，或让切换供应商不那么痛苦的工具上。最强烈的负面情绪则集中在政策不清晰、长期运行状态脆弱，以及那些始终可见却难以建立信任的编程界面上。

## 6. 最新与值得关注

### 编码代理的会话记录开始被视为个人操作数据

[@EXM7777](https://x.com/EXM7777) [发布了](https://x.com/EXM7777/status/2086512844594679820)（46 个赞、6 条回复、2,797 次浏览、107 次收藏）是一条六阶段提示词，要求代理盘点本地会话存档、谨慎抽样、建立证据文件、采访用户，然后对 `CLAUDE.md`、`AGENTS.md` 和自定义技能提出修改建议。值得注意的并不是“自我改进”这类表述，而是它坚持在解读之前先有凭据、门槛和带日期的证据。回复也立刻抓住了这一点，认为真正有意思的变化，是它强制模型把证据与建议分开。

## 7. 机会所在

**[+++] 面向编码代理的工作流原生操作系统** — 第 1 节展示了重心如何从提示词讨论转向图工程、逐轮服务和循环控制。第 2 节和第 4 节则直接呈现了痛点：脆弱的长会话状态、压缩带来的不确定性，以及按请求构建、却无法匹配真实代理行为的基础设施。Citadel、Hermes 压缩功能和 Copilot traces 论文表明，这一方向现在是个很强的机会。**[+++] 位于可移植插件之上的信任与控制平面** —— 可移植封装的标准化速度，正快于权威、权限、沙箱和来源追溯等机制。Agent Plugins、Google Skills，以及围绕合规配置和能力清单的回复讨论，都指向同一个缺失层。这一方向之所以有力，恰恰是因为现有标准已经足够成熟，足以暴露出下一个瓶颈。

**[++] 本地优先、API 兼容的后备基础设施** —— LM Studio 的 localhost 配置、Continue 加 Ollama，以及在 harness 层面切换模型的做法，都表明市场希望在底层更换价格、隐私属性或供应商的同时，继续使用同一套命令。这是一个持久的机会，但竞争正迅速加剧。

**[++] 先强制采用朴素方案的最小差异护栏** —— Ponytail、日期输入示例，以及更广泛的“基本功上移”论点，都指向一个更窄但非常实际的需求：在审阅者不得不收拾残局之前，先阻止智能体过度构建。它的价值立竿见影，也清晰可见：差异更小、依赖更少、审阅更容易。

**[+] 基于智能体日志构建的个人操作系统** —— mirror prompt 和 Life System Starter Kit 暗示了一个规模较小、正在浮现的品类：Claude Code 会话、日志和决策会沉淀为持久的个人运营记录。与工作流或插件趋势相比，这方面的证据还较薄弱，但这一用例显然已开始走出纯软件开发的范畴。

## 8. 要点

1. **讨论的重心正从提示词转向操作纪律。** 最有实质内容的项目聚焦于图工程、按轮次服务、重试、检查点和循环控制，而不是单条提示词的巧思。（[来源](https://x.com/0xMovez/status/2086481283404710047)）
2. **可移植封装的成熟速度，正在快于信任与权限机制。** Agent Plugins、Google Skills，以及围绕能力清单展开的回复串都表明，分发已不再是唯一的问题。（[来源](https://x.com/bibryam/status/2086147058088497321)）
3. **Google 的编码技术栈已清晰可见，但开发者工作流中的信任仍然薄弱。** 关于 Antigravity，最有力的公开证据关乎账户风险、缺失的绑定以及无法使用的 harness 质量，而不是更优的日常编码结果。（[来源](https://x.com/theo/status/2085946505555587148)）
4. **用户希望拥有后端自由，而不必改变自己的工作界面。** LM Studio 的 localhost API、Continue 加 Ollama，以及多模型 harness 都指向同一个需求：保留编辑器或 shell，只替换其底层运行时。（[来源](https://x.com/OlivercrestAI/status/2086327944591319333)）
5. **最活跃的构建者，正在用状态、操作手册和护栏来封装现有智能体。** Citadel、open-kritt、Google Skills、Life System Starter Kit 和 Ponytail 都表明，目前市场围绕流程的创新多于围绕原始推理能力的创新。（[来源](https://x.com/DanKornas/status/2086514333438091491)）
