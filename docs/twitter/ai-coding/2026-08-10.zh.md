# Twitter AI 编程 - 2026-08-10

## 1. 大家在讨论什么

### 1.1 可安装的智能体操作系统正在取代一次性的提示词打磨（🡕）

至少有六条内容明确将 AI 编程的核心问题视为工作流纪律，而非模型原始智力。它们的共同做法，是把规划、测试、评审、记忆和审批从转瞬即逝的聊天上下文中抽离出来，使其能够跨越交接并支撑长时运行。相比 8 月 9 日——当时工作流工程刚成为一个清晰可见的框架——8 月 10 日则把这一思路进一步推进为可安装的套件、固定流程和明确的验证闭环。

[@ForwardEditor](https://x.com/ForwardEditor) [分享了](https://x.com/ForwardEditor/status/2086786388469715008)（316 个赞、10 条回复、16,830 次浏览、511 次收藏）展示了一种围绕 `define-goal` 构建的 Codex 微型模式：先让一个更高投入的强模型重写任务，再把执行交给更便宜的工作线程，最后由强模型回头充当裁判。关键信号不在于具体用了什么提示词技巧，而在于用户如今开始把编程工作描述为分阶段路由的流程，包含角色分工与验收检查。

[@heyrimsha](https://x.com/heyrimsha) [指向了](https://x.com/heyrimsha/status/2086747351318954402)（15 个赞、14 条回复、994 次浏览、8 次收藏）[ECC](https://github.com/affaan-m/ECC)，它将 `plan → test → implement → review → verify → remember → improve` 封装为一个跨框架的统一操作层。推文和所链接的代码仓库对问题的界定完全一致：智能体可以写代码，但其上方仍需要一个持久的工程系统。

![ECC README，展示了一个适用于 Claude Code 的可安装跨框架工作流层，包含 agents、skills 和 guides](https://pbs.twimg.com/media/HPWdqD2bgAAkCsT.jpg)

[@DanKornas](https://x.com/DanKornas) [介绍了](https://x.com/DanKornas/status/2086672877269418427)（9 个赞、3 条回复、1,258 次浏览、8 次收藏）将 [AG Kit](https://github.com/vudovn/ag-kit) 呈现为 Google Antigravity 一侧的同类思路：一个 `.agents/` 工作区契约，包含专家角色、工作流、持久记忆、MCP 指导，以及一个范围很窄的 PreToolUse 安全闸门。这张图之所以有价值，是因为它把规则、编排、记忆、打包和验证都呈现为产品的一等功能界面，而不是可有可无的提示词习惯。

[@traversymedia](https://x.com/traversymedia) [展示了](https://x.com/traversymedia/status/2086941473530933448)（12 个赞、1,170 次浏览、3 次收藏）展示了一套 [AI Blueprint](https://www.youtube.com/watch?v=L4g6GGLzAyo) 工作流，围绕清晰可见的 `PLAN`、`BUILD` 和 `PROVE` 阶段展开：实现前先做规格评审，验证后归档历史记录。公开证据再次指向同一个结论：人们希望整个闭环是可检查的。

**讨论洞察：** 回复者并不是说提示词已经不重要了，而是认为真正的收益来自让计划、修复前测试、验收规则和记忆回写能够跨会话持续保留，而不是每次都重新解释一遍。

**与前一天的比较：** 8 月 9 日把工作流工程界定为前沿方向。到了 8 月 10 日，这一思路已经开始被做成可安装的操作层和可重复的构建流程。

### 1.2 可移植打包已成现实；现在人们争论的是信任、安装与权限边界（🡕）

至少有五条保留条目都默认：技能和 MCP 的可移植性已不再只是一个假设。讨论上升到了更高一层：谁可以安装一个包、它会获得哪些权限、实际工作如何经由它被委派，以及权限边界究竟应该设在哪里。这比 8 月 9 日围绕打包的讨论更进一步，因为这一天同时出现了官方规范和可运行的实际案例。

[@_vmlops](https://x.com/_vmlops) [报道了](https://x.com/_vmlops/status/2086484035669504105)（17 个赞、5 条回复、1,194 次浏览、8 个书签）提到，Google 已加入 Agent Plugins，成为核心维护者之一，并围绕 `plugin.json`、`skills/` 和 `mcp.json` 总结了可移植目录约定。Google 自己的 [发布文章](https://developers.googleblog.com/agent-plugins-package-your-skills-tools-and-more/) 也确认了同样的结构，并明确指出：安装流程、权限、沙箱、信任和来源溯源被刻意排除在 v1 之外。

![Google for Developers 文章，展示 Agent Plugins 作为 skills 和 MCP 之上的可移植封装层](https://pbs.twimg.com/media/HPSuKqvboAA4S8Z.jpg)

[@sabir_huss50540](https://x.com/sabir_huss50540) [指向了](https://x.com/sabir_huss50540/status/2086332099804397806)（5 个赞、1 条回复、859 次浏览、4 个书签）[google/skills](https://github.com/google/skills)，仓库将其描述为 Google 编写的技能包，以及为 Claude Code、Codex 和 Antigravity 捆绑提供的插件。这让“可移植”真正具备了可操作性：用户不再只是争论该如何打包，而是在安装当下可用的云端流程，让智能体不必再对着过时文档瞎猜。

[@waynesutton](https://x.com/waynesutton) [报道了](https://x.com/waynesutton/status/2086608455155294682)（20 个赞、7 条回复、1,461 次浏览、4 个书签）称，在 Codex 中安装 Cloudflare 和 Convex 插件后，只需一个提示词，就完成了域名购买、DNS、网站与 API 连接、SSL 和重定向。那张截图的信息量很大，因为它把这一说法压缩成了一份可见的检查清单和完成耗时。

[@frantzfries](https://x.com/frantzfries) [总结道](https://x.com/frantzfries/status/2086846894639141026)（15 个赞、1,163 次浏览、12 个书签）则从另一侧展示了现实中的复杂性：API、OpenAPI、MCP、App、Skills、Plugin 和 marketplace 这些层次与语义本就已经足够复杂，以至于即便是有经验的用户，也仍在梳理每一层到底负责什么。

**讨论洞察：** 最尖锐的回复聚焦在能力清单、套接字权限和撤销机制，而不是文件布局。分发的标准化，正在比权限控制更快推进。

**与前一天对比：** 8 月 9 日让可移植插件看起来具备了可信度；8 月 10 日则展示了它们已经能做实事，也让缺失的信任层变得更难忽视。

### 1.3 共享记忆正成为产品层，而不只是权宜之计（🡕）

最强的一批开发者信号，关注点已不再是选出最聪明的模型，而是如何让服务上下文、偏好和项目历史在跨会话、跨工具、跨智能体之间持续保留。这比 8 月 9 日“同一界面，不同后端”的表现又向前迈了一步：今天的产品，正把“可被记住的上下文”当作主要差异化卖点来出售。

[@SpotifyEng](https://x.com/SpotifyEng) [发布了](https://x.com/SpotifyEng/status/2086795659651191106)（14 个赞、4 条回复、1,210 次浏览、11 个书签）[Xirp](https://xirp.spotify.com)，将其定位为面向 Claude Code、Gemini CLI 和 Codex 的中立厂商智能体开发环境。Xirp 的公开网站称，缺失的知识是一个检索问题，而不是文档问题：智能体在技术上可以答得没错，但在实际操作中仍会出错，因为所有权、依赖关系和架构决策往往散落在 Slack 讨论串里，或者只存在于人们脑中。

[@tom_doerr](https://x.com/tom_doerr) [分享了](https://x.com/tom_doerr/status/2086637717912223919)（6 个赞、8 条回复、1,373 次浏览、8 个书签）[holaOS](https://github.com/holaboss-ai/holaOS)，其仓库将其描述为一个本地优先的工作区，让 Claude Code、Codex 或 holaOS 都运行在同一套文件、工具和共享记忆之上。README 的关键之处在于，它把这一承诺说得很具体：这些记忆保留在本地、可读、可在不同智能体之间复用，而不是被困在某一家厂商的对话记录里。

![holaOS README，介绍了一个以本地优先为核心的统一工作区，Claude Code、Codex 和 holaOS 在其中共享工具、文件和记忆](https://pbs.twimg.com/media/HPU58lcXMAADxGF.jpg)[@DanKornas](https://x.com/DanKornas) [重点介绍了](https://x.com/DanKornas/status/2086922010043851004)（1 个赞、1 条回复、552 次浏览、2 个收藏）[OpenCode Memory](https://github.com/tickernelz/opencode-mem)，以及 [@PrajwalTomar_](https://x.com/PrajwalTomar_) [介绍了](https://x.com/PrajwalTomar_/status/2086823391697543202)（3 个赞、2 条回复、269 次浏览）都描述了一个早上 6:37 的例行流程：Claude Code 自动启动，将隔夜的 18 个候选项筛选到只剩 1 个，并把最终保留的摘要发送到他的手机上。两者的关键差异都不在于某一次会话里给出了更好的答案，而在于被记住的上下文，加上一个之后还能恢复并分发工作的系统。

**讨论洞察：** 最强烈的正面评价，指向的是可检查、且保存在本地的记忆能力，而不是幕后拼接起来的隐藏上下文。

**与前一天的对比：** 8 月 9 日展示的是用户在更换后端的同时稳定界面。8 月 10 日则让持久记忆和检索成为一个明确的产品类别。

## 2. 让人们沮丧的是什么

### 如果不由用户事后自行补上记忆机制，Agent 还是会忘记项目

这是一个高严重度问题，因为它存在于多个原本看似无关的构建场景之下。[@heyrimsha](https://x.com/heyrimsha) [表示](https://x.com/heyrimsha/status/2086747351318954402)（15 个赞、14 条回复、994 次浏览、8 个收藏）指出，每次会话依然都得被告知先做规划、修复前先测试、审查自己的工作，并记住自己学到了什么。[@SpotifyEng](https://x.com/SpotifyEng) [发布了](https://x.com/SpotifyEng/status/2086795659651191106)（14 个赞、4 条回复、1,210 次浏览、11 个收藏）也围绕同一个痛点展开，其产品网站称，真正的失效模式不是缺少文档，而是无法检索到关于所有权、依赖关系和架构的上下文。[@DanKornas](https://x.com/DanKornas) [重点介绍了](https://x.com/DanKornas/status/2086922010043851004)（1 个赞、1 条回复、552 次浏览、2 个收藏）[OpenCode Memory](https://github.com/tickernelz/opencode-mem) 则给出了一个直接修复方案：在会话空闲时捕获持久的技术上下文，之后再重新注入。

这值得被直接作为产品方向来建设，因为人们的应对方式已经很明确。大家正在添加记忆库、本地向量存储、工作区契约和检索层，以免每天都要重复提示同样的决策。

### 用量、权益和支出仍然过于不透明

这同样属于高严重度问题，因为它会直接改变人们到底还能用什么工具。[@csharpfritz](https://x.com/csharpfritz) [表示](https://x.com/csharpfritz/status/2086773942891544949)（17 个赞、9 条回复、1,776 次浏览）指出，如果你的 Copilot 账户绑定在企业方案下，就没有个人使用方案可供回退；在触及 GitHub 限额后，他改用了 Codex、Claude 和 Antigravity。[@lippebsd](https://x.com/lippebsd) [询问了](https://x.com/lippebsd/status/2086746244651631091)（2 条回复、19 次浏览）则希望看到一个简单的 Codex 上下文用量视图，按单次会话和按天拆分消息、MCP 工具、技能以及系统提示词权重的占用情况，让用户避免意外撞上限额。[@pengsonal](https://x.com/pengsonal) [提出了](https://x.com/pengsonal/status/2086497308653572241)（65 个赞、5 条回复、3,278 次浏览、68 个收藏）则明确把 ZCode 每天免费提供的 3M GLM-5.2 tokens，当作 Cursor、Claude Code 和 GitHub Copilot 成本的替代方案。

![请求提供上下文使用情况明细，展示 Codex 内部的 messages、MCP tools、skills、system prompt 和 deferred 各类别](https://pbs.twimg.com/media/HPWcd7JXIAAn2rs.png)

这也值得被直接作为产品方向来建设。证据不只是人们在抱怨价格，而是他们在索要用量账本；一旦账本缺失，他们就会切换服务商。

### 一旦技能、插件或后台 Agent 能自行行动，信任依然很薄弱

这一问题的严重度介于中等和高之间。[@_vmlops](https://x.com/_vmlops) [报道了](https://x.com/_vmlops/status/2086484035669504105)（17 个赞、5 条回复、1,194 次浏览、8 次收藏）提到一种打包标准，它有意将权限和来源信息留给各个客户端自行处理；而回复里很快就有人要求加入能力清单、撤销机制和共享的合规测试夹具。[@deepfates](https://x.com/deepfates) [反对称](https://x.com/deepfates/status/2086640807537492293)（17 个赞、3 条回复、593 次浏览）则谈到那些他无法关闭的隐形 Claude Code 技能。[@vasuman](https://x.com/vasuman) [认为](https://x.com/vasuman/status/2086563565486682246)（107 个赞、14 条回复、14,499 次浏览、135 次收藏）支持后台代理，但其中一条最有力的回复提出了反对意见：尚未解决的核心问题，仍然是如何信任 AI 去处理那些需要人类判断的复杂多步骤工作流。另有 [@elshayib_](https://x.com/elshayib_) [表示](https://x.com/elshayib_/status/2086413689570132477)（18 个赞、4 条回复、852 次浏览）指出，Antigravity 作为开发者支撑框架，基本上仍然不可用。

这值得去做，但产品门槛高于“更多自动化”。用户想要的是清晰的权限边界、可选择退出的机制，以及能证明支撑框架本身不会悄悄做错事的证据。

## 3. 人们希望存在的东西

### 可持久、可检索、可检查的记忆，而不是靠猜

最明确的实际需求，并不是抽象意义上的“更多上下文”，而是能跨会话保留下来、始终可见、并可在不同工具之间共享的上下文。[@SpotifyEng](https://x.com/SpotifyEng) [将其定义为](https://x.com/SpotifyEng/status/2086795659651191106)（14 个赞、4 条回复、1,210 次浏览、11 次收藏）围绕一个问题展开：如何检索那些明明已经存在、却难以在恰当时刻浮现出来的服务知识；[@tom_doerr](https://x.com/tom_doerr) [展示了](https://x.com/tom_doerr/status/2086637717912223919)（6 个赞、8 条回复、1,373 次浏览、8 次收藏）则谈到一个本地优先的工作区，让多个代理复用同一个记忆存储。[@DanKornas](https://x.com/DanKornas) [补充说](https://x.com/DanKornas/status/2086922010043851004)（1 个赞、1 条回复、552 次浏览、2 次收藏）给出了最直接的实例——[OpenCode Memory](https://github.com/tickernelz/opencode-mem)，它将项目记忆和用户资料数据存储在由向量支持的本地分片中。机会：明确。

### 由规范驱动的构建循环，带有可见的闸门、审查和证据

人们反复表达的是同一种诉求：不要让我去相信一个黑箱。[@traversymedia](https://x.com/traversymedia) [显示](https://x.com/traversymedia/status/2086941473530933448)（12 个赞、1,170 次浏览、3 次收藏）将 AI Blueprint 描述为一个可见的、由规范驱动的循环；[@DanKornas](https://x.com/DanKornas) [描述](https://x.com/DanKornas/status/2086672877269418427)（9 个赞、3 条回复、1,258 次浏览、8 次收藏）将 AG Kit 描述为可重复的工作流加上一道安全闸门；[@PrajwalTomar_](https://x.com/PrajwalTomar_) [描述](https://x.com/PrajwalTomar_/status/2086823391697543202)（3 个赞、2 条回复、269 次浏览）则描述了一套流程：由简报、负责人、评审组、记忆和闸门组成的结构，可以在他睡觉时继续运行。这里的需求是务实的，而不是理想化的：用户想看到代理当前处于循环的哪个环节、自己可以在哪一步介入，以及有哪些证据能证明工作已经完成。机会：明确。

### 面向技能和插件的权限、来源与使用台账

打包层的到来速度，快于其上层控制层的成熟速度。Google 的 [Agent Plugins 文章](https://developers.googleblog.com/agent-plugins-package-your-skills-tools-and-more/) 表示，v1 有意把安装机制、权限模型、沙箱隔离和信任验证留给各客户端自行处理。在该讨论串中，[@_vmlops](https://x.com/_vmlops) [提出](https://x.com/_vmlops/status/2086484035669504105)（17 个赞、5 条回复、1,194 次浏览、8 次收藏）回帖主张加入能力清单和撤销机制；[@deepfates](https://x.com/deepfates) [反对](https://x.com/deepfates/status/2086640807537492293)（17 个赞、3 条回复、593 次浏览）提到一些自己无法禁用的隐藏技能；[@lippebsd](https://x.com/lippebsd) [要求](https://x.com/lippebsd/status/2086746244651631091)（2 条回复、19 次浏览）则要求给出具体的用量拆分，别再让上下文开销处于不可见状态。用户关心的已不只是插件能不能用；他们还想知道它能做什么、成本是多少，以及该如何关闭。机会：直接。

### 携带最新流程或领域知识的垂直技能包

两条不同的信息指向了同一个产品需求：在快速变化的领域里，基础模型自带的知识还不够。[@sabir_huss50540](https://x.com/sabir_huss50540) [提出](https://x.com/sabir_huss50540/status/2086332099804397806)（5 个赞、1 条回复、859 次浏览、4 次收藏）将 [google/skills](https://github.com/google/skills) 介绍为面向 Claude Code、Codex 和 Antigravity 的云端维护型流程包；而 [@DanKornas](https://x.com/DanKornas) [强调](https://x.com/DanKornas/status/2086854070485012488)（1 个赞、2 条回复、727 次浏览、2 次收藏）则提到 [SciAgent-Skills](https://github.com/jaechang-hits/SciAgent-Skills)，其公开基准声称，借助生命科学技能库，BixBench-Verified-50 的成绩可从 65.3% 的基线提升到 92.0%。在流程变化很快、或领域方法比通用代码生成更重要的场景中，这确实是一个真实需求。机会：竞争性。

## 7. 机会在哪里

**[+++] 面向编程工作的跨会话记忆与检索层** — 第 1、2、3 和 5 节都指向这里：Xirp 把上下文缺失定义为检索问题，holaOS 将共享本地记忆作为核心功能，OpenCode Memory 把自动捕获做成了产品，而多个工作流工具包存在的主要意义，就是防止智能体遗忘。这一方向之所以有力，是因为这个痛点同时出现在企业产品、本地优先产品和个人开发者产品中，而不只是某个细分领域。

**[+++] 位于插件与技能之上的信任、权限与使用控制平面** — Agent Plugins 在标准化打包上的推进速度，快于权限、溯源、撤销和使用记账等能力的建设。Google 的博客、`_vmlops` 讨论串、`lippebsd` 的使用视图请求，以及 `deepfates` 对“不可见技能”的抱怨，都指向同一个缺失层。这一方向之所以有力，是因为生态已经具备足够的可移植性，从而把控制层的缺口暴露了出来。**[++] 带有可见验真关卡的规范驱动构建循环** —— ECC、AG Kit、AI Blueprint 和 agent-council 例程都把规划、评审、验证这套结构打包好了，而不是让用户自己去记。之所以评为中等，是因为这类需求既明确又反复出现，但已有数个可信的开源方案。

**[++] 面向重度智能体工作流的配额与权益优化** —— 关于 Copilot 账号分层的抱怨、对 Codex 使用可见性的需求，以及 ZCode 这类激进的免费 token 替代方案，都说明成本和权益状态仍在左右工具选择。之所以评为中等，是因为用户已经因此更换工具，但围绕额度、路由和捆绑套餐的竞争也正变得拥挤。

**[+] 无需重新训练、却能胜过基础智能体的领域专用技能包** —— Google Skills 和 SciAgent-Skills 都表明，现有流程和深度领域方法可以作为可安装技能交付。这仍处于新兴阶段，而非普遍趋势，因为最有力的证据主要来自云运维和生物信息学；不过，公开基准和流程包示例都很具体。

## 8. 要点

1. **AI 编程领域最重要的讨论，是如何打包工作流，而不是如何改进提示词。** ECC、AG Kit、AI Blueprint 和 define-goal 循环都把规划、测试、评审和记忆当作可复用的系统层。（[来源](https://x.com/heyrimsha/status/2086747351318954402)）
2. **可移植插件如今已足够成形，未解决的首要问题转而变成了信任与权限。** Agent Plugins 的公开发布，以及围绕能力清单的回应，都明确显示了这一转变。（[来源](https://x.com/_vmlops/status/2086484035669504105)）
3. **持久化记忆正成为编程工作空间中的一级产品类别。** Xirp、holaOS 和 OpenCode Memory 都把检索与跨会话回忆作为核心价值主张。（[来源](https://x.com/SpotifyEng/status/2086795659651191106)）
4. **配额设计和使用不透明仍在推动用户更换工具。** 用户要求提供按会话划分的上下文台账，并在碰到共享套餐限制后转离 Copilot。（[来源](https://x.com/csharpfritz/status/2086773942891544949)）
5. **领域专用技能包，是无需重新训练模型就能改善结果的最明确路径之一。** Google Skills 聚焦当前的云端流程，而 SciAgent-Skills 则公布了其在生物信息学工作中的明确基准提升。（[来源](https://x.com/DanKornas/status/2086854070485012488)）
