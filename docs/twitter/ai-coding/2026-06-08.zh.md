# Twitter AI 编程 - 2026-06-08

## 1. 人们正在讨论什么

### 1.1 技能、契约和例程让提示词变成了文件 🡕

6 月 8 日，Twitter 上的讨论继续从一次性提示词转向可复用、可反复执行的产物：技能包、Markdown 契约、检查点文档和定时例程。共有四条保留内容支持这一主题。

[@VaibhavSisinty](https://x.com/VaibhavSisinty) [认为](https://x.com/VaibhavSisinty/status/2063871154583121956)（7 个赞、1 条回复、207 次浏览、10 个书签）称，Addy Osmani 的 Agent Skills 软件包为编程智能体提供了 23 项生产级技能，以及从 `/spec` 到 `/ship` 的 7 个生命周期命令。[Agent Skills 仓库](https://github.com/AddyOsmani/agent-skills) 为这一说法提供了佐证：它将该软件包描述为可复用的工作流、质量门禁和反合理化表，并且可安装到 Claude Code、Cursor、Gemini CLI、GitHub Copilot、OpenCode 和 Codex 中。

[@TheTuringPost](https://x.com/TheTuringPost) [强调](https://x.com/TheTuringPost/status/2063787599316312510)（14 个赞、3 条回复、1,214 次浏览、17 个书签）将 OpenProse 描述为把智能体工作流转化为可复用程序的一种方式。[OpenProse 仓库](https://github.com/openprose/prose) 将 `*.prose.md` 文件描述为 Markdown 契约，并称其 Reactor 运行时只有在订阅输入发生实质性变化时，才会执行成本高昂的模型推理；这比“把这条提示词存下来”更进一步。

[@PrajwalTomar_](https://x.com/PrajwalTomar_) [表示](https://x.com/PrajwalTomar_/status/2063992198472114494)（8 个赞、4 条回复、109 次浏览、3 个书签）称，Matt Pocock 的 `/grill-me` 循环会逐个提问，从中提取决策并写入知识文档；而把每个答案都作为检查点存入 `brainstorms` 文件夹，则能避免长时间会话丢失早期上下文。

[@AunySillyMe](https://x.com/AunySillyMe) [展示了](https://x.com/AunySillyMe/status/2064112493027594639)（1 个赞、1 条回复、70 次浏览、2 个书签）则把同一思路应用到定时任务上：Claude Code 指向 Obsidian 仓库中的协议文件，写出带日期的 Markdown 输出，并在一夜之间跑完 8 项任务，无需重新输入指令。

![图示：Claude Code 例程按计划读取协议文件并写入带日期的 Markdown 输出](https://pbs.twimg.com/media/HKUzX01bEAAH-DS.jpg)

**讨论洞察：** 最关键的细微变化并不是“用更好的提示词”，而是“先把人的上下文做成可持久保存的东西”。在 `/grill-me` 主题下，有回复指出，检查点之所以重要，是因为杂乱的决策会变成可复用的构建上下文，而不是消失在冗长对话里。

**与前一天的比较：** 6 月 7 日的讨论已经偏向技能包和 harness 层系统；到 6 月 8 日，焦点进一步收窄到协议文件、检查点文档和例程，让任务不必每次会话都重新输入提示词也能持续运行。

### 1.2 Antigravity 既成了访问层，也成了工作空间 🡕

Antigravity 出现时，越来越少被当作新奇应用，更多被视为获取高级模型、审查 Codex 输出，或使用 Google 最新智能体功能的场所。共有四条保留内容支持这一主题。

[@hqmank](https://x.com/hqmank) [报道称](https://x.com/hqmank/status/2063634869096444007)（744 个赞、113 条回复、160,975 次浏览、420 个书签）称，Google AI Pro 订阅者无需额外付费，就能在 Antigravity 中使用 Claude Opus 4.6。回复和原帖同样重要：几位用户指出 Opus 从 2 月起就已提供，而 [@hqmank](https://x.com/hqmank) 回应称，真正的价值只是多了一条可用的 Opus 访问路径。截图也提供了具体证据：模型选择器里确实显示了 Opus，而不是停留在模糊的访问声明上。

![Antigravity 模型选择器显示 Claude Opus 4.6 与 Gemini 模型同时可用](https://pbs.twimg.com/media/HKOA0o6acAAi6TU.jpg)

[@sunnykgupta](https://x.com/sunnykgupta) [描述](https://x.com/sunnykgupta/status/2063890251857399872)（36 个赞、9 条回复、2,076 次浏览、9 个书签）描述了一套手动循环：Codex 写代码，Antigravity 负责审查改动，GitHub Copilot 审查 PR，Codex 再应用修改意见。这是一个很有代表性的变化：在这个工作流里，Antigravity 不只是另一个模型入口，而是生成与审查之间的工作环境。

[@Google](https://x.com/Google) [表示](https://x.com/Google/status/2064034690760098018)（60 个赞、2 条回复、4,690 次浏览、7 个书签）称，Search 可以结合 Gemini 3.5 Flash 和 Antigravity 构建定制的生成式 UI 与交互式视觉内容；同一主题中的一条回复则表示，Search 还可以创建监测主题并发送详细更新的信息智能体。另据 [Ars Technica](https://arstechnica.com/ai/2026/06/gemini-3-5-and-antigravity-come-to-google-notebooklm/?utm_campaign=dhtwitter&utm_content=%3Cmedia_url%3E&utm_medium=social&utm_source=twitter) 报道，NotebookLM 现在拥有自己的“云电脑”，内置 Antigravity 和 100 多项软件技能。

**讨论洞察：** 回复并不执着于发布本身的新鲜感，而是反复回到两个问题：Antigravity 是否是一条稳定通往正确模型的路径，以及它能否融入更广泛的工作栈。

**与前一天的比较：** 6 月 7 日的重点还是访问套利；到 6 月 8 日，Antigravity 进一步被推向共享工作空间和 Google 全局运行时的角色。

### 1.3 智能体控制平面开始解决运行时问题，而不只是提示词问题 🡕

最技术向的构建者帖子，讨论的是如何控制长时间运行的智能体：实时引导、预热的搜索状态、隔离的 worktree，以及移动端执行界面。共有四条保留内容支持这一主题。

[@massgen_ai](https://x.com/massgen_ai) [宣布](https://x.com/massgen_ai/status/2064022715808571581)（2 个赞、114 次浏览）介绍了 MassGen v0.1.95：该版本把中途引导从 TUI 和 WebUI 扩展到无头调用方，并升级 Codex 和 Antigravity 后端，使其能够中断并恢复，而不是一直等到某一轮结束。帖子还提到协作式多智能体团队、带权限的工具，以及通过 Docker 隔离的代码执行，因此这更像是一次控制平面更新，而不是提示词库发布。

![发布说明截图，显示面向程序化引导的收件箱，以及对 Codex 和 Antigravity 的中断后恢复支持](https://pbs.twimg.com/media/HKThtiJbAAADHJS.png)

[@nexxeln](https://x.com/nexxeln) [展示了](https://x.com/nexxeln/status/2064039757668303036)（204 个赞、10 条回复、8,076 次浏览、38 个书签）称，下一版 OpenCode 将使用 `fff` 处理文件搜索；智能体打开文件后，这些文件的排序会被提升；同一搜索层还会在多次工具调用之间复用，从而避免每次搜索都从冷状态启动。[@neogoose_btw](https://x.com/neogoose_btw) [新增](https://x.com/neogoose_btw/status/2064041089523449971)（56 个赞、6 条回复、1,765 次浏览、4 个书签）称，该搜索层目前每天已处理至少 5,000 万次搜索。

[@orca_build](https://x.com/orca_build) [推出](https://x.com/orca_build/status/2064091161980268976)（41 个赞、7 条回复、1,961 次浏览、29 个书签）介绍了 Orca ADE 中的移动模拟器：每个 worktree 配备一个模拟器，让智能体能够在代码所在的位置构建、测试、调试和验证移动端流程。[Orca 仓库](https://github.com/stablyai/orca) 补充了这条推文背后的更大能力面：原生支持 worktree 的编排、并排运行的 CLI 智能体、与 GitHub 关联的工作流，以及通知功能。

[@mardehaym](https://x.com/mardehaym) [提出异议](https://x.com/mardehaym/status/2064025247548936416)（12 个赞、3 条回复、603 次浏览、2 个书签）针对近期一波智能体循环图指出，安全循环仍然需要代码库地图、沙箱、成本上限、审计日志、RBAC 和人工关卡。一条回复把差距概括得很清楚：循环是赢下演示的部分，真正能在生产环境活下来的，是那些看不见的基础设施。

**讨论洞察：** 争论已经不再是智能体能不能行动，而是在人们愿意信任这些行动之前，周围必须先具备哪些状态、引导和安全原语。

**与前一天的比较：** 6 月 7 日强调 harness 比模型更重要；到 6 月 8 日，这一点已经被引导收件箱、预热的搜索状态和隔离的执行环境具体化了。

## 2. 什么让人感到沮丧

### AI 编程的预算管理仍然像在配给资源

严重程度：高。[@devXritesh](https://x.com/devXritesh) [询问](https://x.com/devXritesh/status/2063826092314779999)（68 个赞、76 条回复、1,149 次浏览）询问开发者会选择哪一项 20 美元的单次购买，回复在 ChatGPT Plus、Claude Pro 和完全不买之间分化；一条回复表示，许多开发者忙于写代码，根本负担不起那些仍无法解决整个问题的工具。[@edzitron](https://x.com/edzitron) [进一步放大了这一观点](https://x.com/edzitron/status/2064023464022073567)（664 个赞、11 条回复、18,637 次浏览、27 个书签）呈现了主流的“AI 账单惊吓”叙事，回复还补充了具体的价格震惊案例，例如财务团队把用量当作固定订阅成本，以及消费者在聊天中途就撞上信用额度上限。[@hqmank](https://x.com/hqmank) [展示了](https://x.com/hqmank/status/2063634869096444007)（744 个赞、113 条回复、160,975 次浏览、420 个书签）则体现了应对方式：只要某个套餐能额外免费提供 Opus，人们就会迅速切换工作空间。这个方向值得投入，因为工作流选择已经受到计费边界的影响，而不只是模型质量。

### 免费模型和备用模型在 harness 中仍然容易出问题

严重程度：高。[@shaun_on_x](https://x.com/shaun_on_x) [报道称](https://x.com/shaun_on_x/status/2063881601327779892)（10 个赞、5 条回复、1,050 次浏览）称，OpenCode 中免费的 Nemotron 3 Ultra 选项在工具调用时会失败，运行到一半停止，并且与 harness 的配合并不理想。回复表示，MiMo 或 DeepSeek 感觉更好用，因此这更像是实际的质量路由问题，而不是一次性的抱怨。与此同时，[@nexxeln](https://x.com/nexxeln) [将其定义为](https://x.com/nexxeln/status/2064039757668303036)（204 个赞、10 条回复、8,076 次浏览、38 个书签）介绍了 OpenCode 的新 `fff` 层，用于减少冷启动搜索造成的上下文浪费；而 [@sunnykgupta](https://x.com/sunnykgupta) [描述](https://x.com/sunnykgupta/status/2063890251857399872)（36 个赞、9 条回复、2,076 次浏览、9 个书签）展示了仍需手动完成的 Codex → Antigravity → Copilot 交接流程。这个方向值得投入，因为用户已经在拼接各种变通方案，以熬过脆弱的运行过程。

### 循环演示看起来仍然比安全运行更容易卖出去

严重程度：中。[@mardehaym](https://x.com/mardehaym) [认为](https://x.com/mardehaym/status/2064025247548936416)（12 个赞、3 条回复、603 次浏览、2 个书签）称，安全的智能体循环在第一次迭代开始前，就需要具备实时代码库地图、沙箱、成本上限、审计日志、RBAC 和人工关卡。该主题下的一条回复用更尖锐的措辞表达了同样的观点：循环能赢下演示，但真正能在生产环境存活的是那些看不见的基础设施。[@massgen_ai](https://x.com/massgen_ai) [交付中](https://x.com/massgen_ai/status/2064022715808571581)（2 个赞、114 次浏览）提到 Codex 和 Antigravity 已支持无头引导以及中断后恢复，这说明构建者正在实时补上这些缺失的控制界面。这个方向值得投入，因为无人值守的智能体工作来得比其周围的安全护栏更快。

## 3. 人们希望存在什么

### 可移植的工作流契约

人们提出的需求既实际又迫切：有一层工作流，只需安装一次，就能在不同工具之间随身携带。[@VaibhavSisinty](https://x.com/VaibhavSisinty) [提出](https://x.com/VaibhavSisinty/status/2063871154583121956)（7 个赞、1 条回复、207 次浏览、10 个书签）展示了作为可复用斜杠命令工作流的 Agent Skills，[@TheTuringPost](https://x.com/TheTuringPost) [指出](https://x.com/TheTuringPost/status/2063787599316312510)（14 个赞、3 条回复、1,214 次浏览、17 个书签）指向 OpenProse 契约，而 [@Oluwaphilemon1](https://x.com/Oluwaphilemon1) [描述](https://x.com/Oluwaphilemon1/status/2063925320491647303)（2 个赞、73 次浏览、3 个书签）则将 ECC 描述为具备技能和子智能体的跨 harness 操作系统。这个需求并非情绪性的，而是操作层面的：别再在每个智能体里重复搭建同一套流程。机会：直接。

### 自动完成交接的构建—审查—修复循环

[@sunnykgupta](https://x.com/sunnykgupta) [询问](https://x.com/sunnykgupta/status/2063890251857399872)（36 个赞、9 条回复、2,076 次浏览、9 个书签）讨论了如何自动化一套已经横跨 Codex、Antigravity、GitHub pull request 和 Copilot 审查的工作流。由 [@pycoders](https://x.com/pycoders) [解释了](https://x.com/pycoders/status/2064080776291836153)（5 个赞、338 次浏览、3 个书签）分享的 [Real Python 教程](https://realpython.com/github-copilot-code-review/)，则把 Copilot 审查定位为在人类审查缓慢或不稳定时的快速首轮检查；[@orca_build](https://x.com/orca_build) [补充说](https://x.com/orca_build/status/2064091161980268976)（41 个赞、7 条回复、1,961 次浏览、29 个书签）则展示了同一套由 worktree 驱动的工作空间中的移动端验证。这套循环的各个部分如今已经存在，但人们仍需手动把它们串起来。机会：直接。

### 具备引导、沙箱和审计轨迹的安全循环运行

[@mardehaym](https://x.com/mardehaym) [表示](https://x.com/mardehaym/status/2064025247548936416)（12 个赞、3 条回复、603 次浏览、2 个书签）称，生产级循环在值得信任之前，需要先具备代码库地图、沙箱、成本上限、审计日志、RBAC 和人工关卡。[@massgen_ai](https://x.com/massgen_ai) [展示了](https://x.com/massgen_ai/status/2064022715808571581)（2 个赞、114 次浏览）给出的只是部分答案：程序化引导收件箱，以及中断后恢复的支持；但更广泛的控制平面仍然分散在各种小众工具中。这一需求很实际，而非理想化：社区已经在尝试让智能体无人值守地运行。机会：直接。

### 不牺牲质量的预算感知型模型路由

定价带来的痛点很具体，路由行为同样如此。[@hqmank](https://x.com/hqmank) [重视](https://x.com/hqmank/status/2063634869096444007)（744 个赞、113 条回复、160,975 次浏览、420 个书签）展示了在 Antigravity 中获得 Opus 的另一条路径，[@devXritesh](https://x.com/devXritesh) [转向](https://x.com/devXritesh/status/2063826092314779999)（68 个赞、76 条回复、1,149 次浏览）把问题转化为一个 20 美元的分配选择，而 [@shaun_on_x](https://x.com/shaun_on_x) [展示了](https://x.com/shaun_on_x/status/2063881601327779892)（10 个赞、5 条回复、1,050 次浏览）则展示了当免费备用模型过于脆弱、无法信任时会发生什么。套餐和免费模型菜单目前只能部分满足这一需求，但还无法提供稳定的质量底线。机会：竞争性。

## 4. 正在使用的工具和方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| [Claude Code](https://x.com/AunySillyMe/status/2064112493027594639) | 智能体 CLI | (+/-) | 与例程、已保存的协议文件和外部技能包配合时表现良好 | 用户仍需自行添加检查点和记忆模式，以维持长时间运行的一致性 |
| [Google Antigravity](https://x.com/hqmank/status/2063634869096444007) | 多模型工作空间 | (+/-) | 提供高级模型访问权限，可作为 Codex 输出的审查界面，并扩展到 Search 和 NotebookLM | 发现和访问体验不够稳定，用户仍需不断寻找套餐并手动组合工作流 |
| [OpenAI Codex](https://x.com/aakashgupta/status/2064105445162373595) | 编程智能体 | (+) | 快速原型设计、应用内浏览器操作、PR 生成，以及实验审查能力 | 通常仍需额外一层来负责编排、审查或策略检查 |
| [GitHub Copilot](https://realpython.com/github-copilot-code-review/) | PR 审查助手 | (+/-) | 能快速完成第一轮 pull request 审查，也仍适合作为维护层 | 经常位于另一个编程智能体之后，而不是工作流的主导者 |
| [OpenCode](https://x.com/nexxeln/status/2064039757668303036) | 开源智能体 | (+/-) | 更快的文件搜索、预热上下文、大型代码库导航，以及供应商灵活性 | 免费模型在工具调用时可能质量崩溃，或运行到一半停止 |
| [Agent Skills](https://github.com/AddyOsmani/agent-skills) | 技能包 | (+) | 通过验证门禁，把规格、计划、构建、测试、审查和发布纪律编码下来 | 需要安装，并要求用户学习命令驱动的工作流 |
| [OpenProse](https://github.com/openprose/prose) | 工作流 DSL | (+) | 通过 Markdown 契约、回执和期望状态执行，实现可重复的智能体工作 | 词汇体系和运行时复杂度仍处于早期阶段，因此更适合高级用户 |
| [Orca](https://github.com/stablyai/orca) | 多智能体工作空间 | (+) | 原生支持 worktree 的编排、GitHub 集成，以及如今在同一界面中进行移动端验证 | 覆盖面广，团队仍需学习或统一使用方式 |
| [MassGen](https://x.com/massgen_ai/status/2064022715808571581) | 编排层 | (+) | 无头引导、中断恢复控制、多智能体协作，以及通过 Docker 隔离的代码执行 | 仍处于早期 v0.1x 阶段，控制平面包含许多活动部件 |

总体而言，人们对那些能把聊天转化为流程的层最为认可：技能、契约、回执、可复用的搜索状态和 PR 审查。常见的变通方式是叠加工具，而不是等待某一个赢家出现——[@sunnykgupta](https://x.com/sunnykgupta) [描述](https://x.com/sunnykgupta/status/2063890251857399872)（36 个赞、9 条回复、2,076 次浏览、9 个书签）展示了 Codex → Antigravity → Copilot 的链路；而 [@mardehaym](https://x.com/mardehaym) [警告](https://x.com/mardehaym/status/2064025247548936416)（12 个赞、3 条回复、603 次浏览、2 个书签）则指出，循环要达到生产可用的安全标准，仍需要地图、沙箱和成本上限。因此，迁移压力正同时朝两个方向发展：Antigravity 和 Codex 等高级界面在融入更广泛的技术栈时更具优势；OpenCode、Orca、MassGen、Agent Skills、OpenProse 和 ECC 等开放系统，则在提供更多工作流、状态和执行控制时更具优势。

## 8. 要点

1. **最大的升级在于流程的持久化，而不是提示词技巧。** 6 月 8 日最强势的帖子，几乎都把工作流外化为文件或命令：Agent Skills、OpenProse 契约、`/grill-me` 检查点，以及 Claude Code 例程。（[来源](https://x.com/VaibhavSisinty/status/2063871154583121956)）
2. **Antigravity 已从一种套餐技巧，升级为更广泛的工作空间和运行时层。** 它既是访问 Opus 的路径，也是审查 Codex 输出的场所、Search 运行时，以及 NotebookLM 的云电脑。（[来源](https://x.com/hqmank/status/2063634869096444007)）
3. **智能体编程最难的部分，如今已经是控制平面工程。** 无头引导、预热的搜索状态、worktree 原生模拟器，以及安全循环所需的条件，都比再来一套提示词配方更重要。（[来源](https://x.com/massgen_ai/status/2064022715808571581)）
4. **成本对工作流决策的影响，仍然不亚于能力本身。** 用户把订阅当作预算项目来比较，四处寻找捆绑访问，并抱怨免费备用模型太脆弱，不值得信任。（[来源](https://x.com/devXritesh/status/2063826092314779999)）
5. **Codex 正在把构建者群体扩展到工程师之外。** 6 月 8 日最清晰的例子，是一名 OpenAI 产品经理使用 Codex，用一个可运行的原型和 FAQ 取代了仪表板堆和 PRD。（[来源](https://x.com/aakashgupta/status/2064105445162373595)）
