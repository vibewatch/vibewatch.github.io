# Twitter AI 编程 - 2026-10-31

## 1. 大家在讨论什么

### 1.1 规范优先的工作流开始在改代码前加入结构化审查

Google 的 [Elephant-Goldfish 模型仓库](https://github.com/google/elephant-goldfish-model) 介绍了一款开源插件：先由长上下文智能体起草规范，再交由使用全新上下文的审阅者在实施前提出质疑。项目方表示，功能需要做设计决策时，这种方法最有用；它不能取代测试或人的判断，也不是 Google 官方支持的产品。[@thisguyknowsai](https://x.com/thisguyknowsai) [总结了](https://x.com/thisguyknowsai/status/2116453452977152209) 该方法（29 个赞、4 条回复、1,760 次浏览、34 次收藏）。

![Elephant-Goldfish 设计与评审工作流](https://pbs.twimg.com/media/HV8nMwkaAAAHNLr.jpg)

Matt Pocock 的 [工程技能仓库](https://github.com/mattpocock/skills) 采用了更模块化的方式，包含需求澄清、TDD、调试、审查和交接等流程。回复中有人讨论，事先进行详尽访谈是否高效，还是应该让智能体自行做出可撤销的选择，并在代价高昂的决策前询问用户。[@heynavtoor](https://x.com/heynavtoor) [分享了](https://x.com/heynavtoor/status/2116501931778842809) 该代码库（29 个赞、60 条回复、2,974 次浏览、13 次收藏）。

### 1.2 使用额度已成为编码智能体发布时的关注重点之一

一条互动量很高的帖子解读了 Tibo Sottiaux 对 Codex 即将推出的“重置”和“存储”功能的预告，认为这意味着有两次可累积的重置次数。回复中有人讨论这是否够用，也有人猜测还会有更大规模的发布。这条帖子表明用户关注使用限制，但讨论并未确定最终行为或推出细节。[@kimmonismus](https://x.com/kimmonismus) [回应了](https://x.com/kimmonismus/status/2116519700431622224) 该预告（339 个赞、67 条回复、12,949 次浏览）。

### 1.3 常规工具等待也可能改变提示缓存的保留情况

一项对公开 GitHub Copilot 编码智能体轨迹的分析指出，用户发起的提示中，按 token 加权计算的缓存占比从 270–300 秒区间的 59.6% 降至 300–330 秒区间的 26.1%。作者还发现，部分智能体调用在工具运行后也出现类似下降，而其他模型保留了更多上下文。这只是对公开轨迹的一项分析，且模型名称已隐去，并不代表每次 Copilot 会话都必然如此。[@Siddhant_K_code](https://x.com/Siddhant_K_code) [分享了](https://x.com/Siddhant_K_code/status/2116593398660674014) 该测量结果（12 个赞、8 条回复、408 次浏览、4 次收藏）；[完整分析](https://siddhantkhare.com/writing/coding-agent-cache-five-minutes) 介绍了分析方法及其局限。

![基于公开编程代理轨迹分析的提示缓存保留率图表](https://pbs.twimg.com/media/HV-mYFza0AAAv1S.jpg)

**与前一天相比：** 10月30日的讨论聚焦于 IDE 集成、从 Jules 过渡到 Antigravity、扩展和订阅限制。10月31日则转向智能体如何澄清意图、审查自己的计划，以及在暂停期间保留上下文。

## 2. 大家感到困扰的地方

### 再充分的初始访谈，也无法预见每一个决策

Skills For Real Engineers 的讨论认为，理解不一致说明应该在编码前先澄清需求。回复中也提出了一个重要的反面观点：任务进行中会出现许多小决策，事无巨细地访谈可能造成阻碍；一位从业者建议，可撤销的选择就先自行判断，犯错代价高的选择则先询问。这个讨论反映的是设计上的权衡，并非对开发者整体偏好的实测结论。[@heynavtoor](https://x.com/heynavtoor) [分享了](https://x.com/heynavtoor/status/2116501931778842809) 该技能工作流（29 个赞、60 条回复、2,974 次浏览）。

### 长时间等待可能降低提示缓存的复用率

轨迹分析发现，部分模型在接近五分钟时，缓存占比显著下降。但分析无法判断这是因为缓存过期、请求被路由到缺少该前缀的副本，还是缓存因内存压力而被驱逐。因此，它指出的是工作流层面的问题，而非已确定的单一原因。[@Siddhant_K_code](https://x.com/Siddhant_K_code) [总结了](https://x.com/Siddhant_K_code/status/2116593398660674014) 该结果（12 个赞、8 条回复、408 次浏览）。

### 使用功能预告可能造成预期落差

Codex 相关讨论显示，用户会把简短的“重置”预告理解为具体的使用权益，同时也期待更大规模的公告。推出细节尚未公布，用户的期待可能会超出产品更新最终带来的内容。[@kimmonismus](https://x.com/kimmonismus) [回应了](https://x.com/kimmonismus/status/2116519700431622224) 该预告（339 个赞、67 条回复、12,949 次浏览）。

## 3. 大家希望拥有什么

### 根据犯错代价调整澄清方式

回复中提出了一种实用的交互模式：决策代价高或不可逆时先询问；对于可撤销的选择，则继续推进并清楚记录。该技能仓库旨在帮助对齐需求，而讨论进一步指出，澄清的力度应与风险和不确定性相匹配。**机会： 竞争力。** [@heynavtoor](https://x.com/heynavtoor) [分享了](https://x.com/heynavtoor/status/2116501931778842809) 讨论（29 个赞、60 条回复、2,974 次浏览）。

### 兼顾缓存生命周期的长任务代理运行框架

轨迹分析表明，测试任务及其他暂停可能会影响提示令牌的复用。可采取的应对措施包括按模型测量缓存保留时间、围绕服务提供商的限制设计后台任务，或向用户明确显示较长的等待时间。文章将这些视为设计启示，而非经过测试的产品修复方案。**机会：新兴领域。** [@Siddhant_K_code](https://x.com/Siddhant_K_code) [分享了](https://x.com/Siddhant_K_code/status/2116593398660674014) 轨迹分析结果（12 个赞、8 条回复、408 次浏览）。

## 6. 最新动态

### 公开轨迹显示，部分模型的缓存占比在接近五分钟时大幅变化

文章分析了一份公开数据，其中包含 301,026 个会话和超过 900 万次模型调用。对于由用户发起的调用，按令牌加权的缓存占比在 270–300 秒区间为 59.6%，在 300–330 秒区间降至 26.1%；部分模型的缓存占比高得多，另一些则大幅下降。模型标签已匿名化，作者提醒，这份轨迹无法区分缓存过期、路由或驱逐。结果有助于设计代理运行框架，但并不构成 Copilot 服务级别的保证。[@Siddhant_K_code](https://x.com/Siddhant_K_code) [报道了](https://x.com/Siddhant_K_code/status/2116593398660674014) 标题中的对比数据（12 个赞、8 条回复、408 次浏览）；[这篇文章](https://siddhantkhare.com/writing/coding-agent-cache-five-minutes) 介绍了方法。

## 7. 机会在哪里

**[+++] 先写规范、支持独立审查的编码工作流** — EGM 和 Matt Pocock 的技能都强调在实现前或实现过程中明确需求并遵循工程规范。讨论还提出了一个产品设计问题：代理应在什么时候提问，又应在什么时候自行做出可逆的选择？

**[++] 缓存感知型代理运行框架** — 轨迹分析显示，部分匿名模型可能存在五分钟左右的缓存保留断崖。按模型分别测量并根据等待时间编排任务很有前景，但现有数据无法证明这是普遍机制。

**[+] 更清晰的使用控制与发布沟通** — Codex 预告引发了大量关于重置次数能否累积的讨论，但现有证据反映的是用户预期，而非已确认的功能表现。

## 8. 要点

1. **编程代理的工作流正在纳入明确的设计和审查环节。**EGM 会安排审查者在全新上下文中进行审查，而 Matt Pocock 的技能包则提供了一套用于需求澄清、测试和调试的流程。[@thisguyknowsai](https://x.com/thisguyknowsai) [总结了](https://x.com/thisguyknowsai/status/2116453452977152209)EGM（29 个赞、4 条回复、1,760 次浏览）。
2. **澄清需求要兼顾目标对齐与减少打断。**技能帖的回复倾向于在可能造成高昂代价的错误发生前先提问，同时让可逆决策继续推进。[@heynavtoor](https://x.com/heynavtoor) [分享了](https://x.com/heynavtoor/status/2116501931778842809)这场讨论（29 个赞、60 条回复、2,974 次浏览）。
