# Twitter AI 编程 - 2026-06-02

## 1. 大家在讨论什么

### 1.1 Antigravity 把智能体管理变成了产品主界面 🡕

最受关注的产品讨论，已经不再是如何把自动补全做得更好，而是 Google Antigravity 能否成为覆盖研究、设计、编码和后台智能体工作的真正工作流中枢。共有四条保留内容支撑这一主题。

[@antigravity](https://x.com/antigravity) [宣布](https://x.com/antigravity/status/2061519617550340492)（1,378 个赞、68 条回复、69,241 次浏览、421 次收藏）称，Antigravity 现已推出 Science Skills 技能包，支持 30 多个科学数据库和 Alpha* 工作流。公开的 [Science Skills 仓库](https://github.com/google-deepmind/science-skills) 显示，该技能包覆盖基因组学、结构生物学、化学信息学、文献检索等研究任务，因此这更像是一套垂直工作流包，而不是普通的编程演示。

[@kevinhou22](https://x.com/kevinhou22) [解释道](https://x.com/kevinhou22/status/2061880709418213776)（132 个赞、27 条回复、8,167 次浏览、45 次收藏）提出了一个问题：为什么 Antigravity 2.0 要把 IDE 和 Agent Manager 拆开。链接中的产品讨论和公开的 [XDA 评测](https://www.xda-developers.com/google-antigravity-2-beats-claude-code-codex-at-their-own-game/) 都把这个新界面描述为一个指挥中心，包含 Projects、动态子智能体、定时任务和斜杠命令控制；同时，帖子里还有回复要求用更强的总控模型来管理更便宜的子智能体，这说明路由与编排已经成了用户对产品的预期。

[@rseroter](https://x.com/rseroter) [提到](https://x.com/rseroter/status/2061713678731214976)（7 个赞、704 次浏览、5 次收藏）分享了 Guillaume Laforge 使用 [结合 Antigravity CLI 的 Google Stitch](https://glaforge.dev/posts/2026/05/31/iterating-on-frontend-design-with-stitch-and-antigravity-cli/) 改造 Groovy Web Console 的经历。这篇帖子的重要性不在于炒作，而在于它展示了 Antigravity 如何在同一条工作流里协助完成 UI 集成、Cypress 测试、DNS 和 OAuth 修改、Google Cloud 检查，甚至架构图生成。

[@xdadevelopers](https://x.com/xdadevelopers) [分享了](https://x.com/xdadevelopers/status/2061734660544053640)（16 个赞、2,006 次浏览）提出了一条实操层面的判断：Antigravity 2.0“在 Claude Code 和 Codex 最擅长的领域击败了它们”。比起标题，配图本身更有价值，因为它展示了真实的管理器界面，包括项目标签、定时任务、实施计划和长篇计划面板——这正是大家争论的界面转向。

![Antigravity 2.0 管理器视图，展示了项目标签、计划任务、实施步骤，以及一个持久显示的计划面板，而不是单一的聊天线程](https://pbs.twimg.com/media/HJzAv4kWcAAi_xv.jpg)

** 讨论洞察：** 真正有价值的回复，并不是在要求一个稍微更聪明的编辑器，而是在要求混合模型监督、更好的协作界面，以及能够跨越多个 repo 或多个提示的持久工作流。

** 与前一天相比：** 6 月 1 日的讨论已经偏向工作流包和集成；到了 6 月 2 日，管理器界面本身成了主角，科学技能包、多文件夹项目和明确的编排能力都成了重点。

### 1.2 瓶颈已从生成代码转向交付安全、可理解的软件 🡕

当天最有分量的证据表明，AI 编程产出的增长速度，远快于可发布、可维护软件的增长速度。共有四条保留内容支撑这一主题。

[@emollick](https://x.com/emollick) [分享了](https://x.com/emollick/status/2061659432233161023)（122 个赞、22 条回复、9,021 次浏览、60 次收藏）介绍了一篇关于 AI 编程智能体的新论文，明确区分了代码产出量和实际发布量。配图显示，与使用智能体前的基线相比，异步智能体带来了 17.3 倍的代码行数、3.9 倍的修改文件数和 2.8 倍的提交数，但发布次数只有 1.3 倍；论文截图则指出，在计入生产链条中的人为瓶颈后，发布提升大约只有 30%。

![比较自动补全、本地编码代理和远程异步代理的图表，显示代码产出的提升远大于最终发布成果的提升](https://pbs.twimg.com/media/HJx7OF8WYAAwwJs.jpg)

![论文《Writing Code vs. Shipping Code》的摘要，指出 AI 会显著提升编码活动，但已发布版本的增长要小得多，因为这种增益会在生产层级中逐级衰减](https://pbs.twimg.com/media/HJx7PAyWYAAY5k-.jpg)

[@svpino](https://x.com/svpino) [警告说](https://x.com/svpino/status/2061925133275861481)（8 个赞、4 条回复、1,911 次浏览、6 次收藏）称，非技术用户已经在部署通过提示词生成的网站，却并不了解 HTML、安全或 VPC 基础；他还听说过有公司因为“vibe-coding 就够了”而丢了数据。被引用的 [Superblocks 公告](https://x.com/bradmenezes/status/2061838224256061641) 正是这条帖子重要的原因：它把位于 VPC 内、继承 AWS 策略、具备备份、审计轨迹和加密能力的安全数据库，定义为真正缺失的默认配置。

[@zhenthebuilder](https://x.com/zhenthebuilder) [表示](https://x.com/zhenthebuilder/status/2061871071566168166)（12 个赞、350 次浏览）称，Replit 一直在内部使用 ViBench，现在正将其公开。公开的 [ViBench 仓库](https://github.com/ViBench/vibench-public) 将其描述为一套基于 PRD 的基准框架，用于在隔离环境中构建、初始化并评估完整 Web 应用，并配有测试计划；这正好呼应了当天的一个核心抱怨：现有编程基准无法反映应用层的真实情况。

[@jain_harshit](https://x.com/jain_harshit) [认为](https://x.com/jain_harshit/status/2061867787250016686)（5 个赞、166 次浏览、2 次收藏）称，纯粹的 vibe coding 无法持续扩展。截图把这句口号落到了一个具体失败场景上：有人删除了三个月内约 70% 的 AI 生成代码，因为他已经无法追溯系统为什么能工作，只能像读陌生人的项目一样重新理解它。

![一则 Reddit 帖子的截图，内容称三个月生成的大部分 AI 代码最终都被删除，因为作者无法理解或安全地修改由此形成的代码库](https://pbs.twimg.com/media/HJ050k3bYAAMWnV.jpg)

** 讨论洞察：** 最有价值的回应并没有全盘否定 AI 编程，而是不断把问题收束到可维护性、护栏和发布就绪度——这些恰恰不是单纯提升代码生成能力就能解决的。

** 与前一天相比：** 6 月 1 日的重点是定价冲击和基准测试的局限；6 月 2 日则转向了另一个问题：这些生成出来的产出，到底有多少能撑过部署、维护和团队理解。

### 1.3 编程工作区开始充当智能体、插件与可分享输出之间的路由器 🡕

第三个主要主题，是能够在多个智能体、插件和输出格式之间分配工作的界面正在兴起。共有五条保留内容支撑这一主题。

[@dabit3](https://x.com/dabit3) [发布了](https://x.com/dabit3/status/2061931891016478905)（40 个赞、7 条回复、3,156 次浏览）介绍了兼容 ACP 的 Devin Desktop，可与 Codex、Claude Agent、OpenCode 等智能体协同工作。截图是关键证据：它展示了一个实时选择器，包含 Devin Local、Devin Cloud、Claude Agent、Codex CLI 和 Cursor；还有一条回复明确表示，IDE 正在从单一智能体启动器，变成智能体的审查/路由层。

![Devin Desktop 界面，展示了一个代理选择器，可在同一桌面界面中选择 Devin Local、Devin Cloud、Claude Agent、Codex CLI 和 Cursor](https://pbs.twimg.com/media/HJ1paxJW0AASqHY.jpg)

[@waynesutton](https://x.com/waynesutton) [发布了](https://x.com/waynesutton/status/2061872764298944665)（42 个赞、3 条回复、5,921 次浏览、20 次收藏）称，Codex 的 Convex 插件已经上线；[@frankdotlee](https://x.com/frankdotlee) [随后跟进](https://x.com/frankdotlee/status/2061921190521041093)（10 个赞、92 次浏览）则给出了一个具体的 Amplitude 插件案例，把 Codex 变成一名“始终在线的资深产品分析师”，可用于发现机会、基于回放做 UX 审计、生成每周简报，以及调查故障智能体。这两条帖子合在一起，让 Codex 的插件故事显得更像可落地的工作流，而不只是宣传。

[@RoundtableSpace](https://x.com/RoundtableSpace) [将其定义为](https://x.com/RoundtableSpace/status/2061874235807560059)（29 个赞、8 条回复、1,116 次浏览）介绍了 Codex 作为应用构建器的能力：可以把文档和计划转成可分享的网站和交互式应用。这个发布信号之所以重要，是因为 [@_simonsmith](https://x.com/_simonsmith) [立即报告了](https://x.com/_simonsmith/status/2061919879767191778)（11 个赞、827 次浏览、4 次收藏）也记录了一个并不顺利的上线过程：宣传中的插件缺失、部分企业账户里没有 Sites，Codex 还出现了新的归档 bug。

[@orca_build](https://x.com/orca_build) [补充说](https://x.com/orca_build/status/2061929580282413294)（7 个赞、229 次浏览、3 次收藏）展示了一个体量较小、但很能说明问题的技术栈信号：OpenCode + Codex + Hermes 同时出现在一个工作区里。虽然这张截图传播量不高，但它仍是公开范围内最清晰的证据之一，展示了工具如何在多个编程智能体之间路由，而不是要求用户只忠于其中某一个。

![Orca 工作区截图，显示 Hermes、Codex 和 OpenCode 可在同一个代理选择菜单中使用](https://pbs.twimg.com/media/HJ1h-subUAASMDE.png)

** 讨论洞察：** 讨论越来越把 IDE 视为交通调度中心。现在的问题已经不再是团队是否需要多个智能体，而是桌面端、插件层和发布层是否足够稳定，值得信任。

** 与前一天相比：** 6 月 1 日已经出现了统一工作区和“超级应用”式封装的早期信号；6 月 2 日则补上了具体桌面端、真实插件工作流和可分享输出界面，让“路由器”这一模式真正变得可见。

## 2. 什么让人感到沮丧

### 发布软件仍然比生成代码难得多

严重程度：高。[@emollick](https://x.com/emollick) [分享了](https://x.com/emollick/status/2061659432233161023)（122 个赞、22 条回复、9,021 次浏览、60 次收藏）介绍了一篇论文，显示异步编程智能体带来的代码产出增长，远高于实际发布量的增长；与此同时，[@svpino](https://x.com/svpino) [警告说](https://x.com/svpino/status/2061925133275861481)（8 个赞、4 条回复、1,911 次浏览、6 次收藏）称，非技术用户已经在部署提示词生成的网站，却不了解基本的安全常识。[@jain_harshit](https://x.com/jain_harshit) [补充说](https://x.com/jain_harshit/status/2061867787250016686)（5 个赞、166 次浏览、2 次收藏）则给出了一个有截图为证的案例：由于所有者已经无法解释或安全修改 AI 生成的代码，最终不得不大幅删改。人们现在的应对方式，是重写代码、收缩范围，并要求平台提供更安全的默认配置，例如 [Superblocks 的 VPC 内数据库配置](https://x.com/bradmenezes/status/2061838224256061641)。这值得投入，因为问题并不只是表面上的不顺手——它直接卡住了部署、维护和团队接手。

### 限额和发布日的不一致仍在削弱信任

严重程度：高。[@sheriyuo](https://x.com/sheriyuo) [报道称](https://x.com/sheriyuo/status/2061734915864191024)（18 个赞、3 条回复、1,314 次浏览）称，Codex 面向 Free 和 Go 用户的重置节奏已从每周改为每月，配图显示 `0% left` 的重置日期在 7 月。[@_simonsmith](https://x.com/_simonsmith) [表示](https://x.com/_simonsmith/status/2061919879767191778)（11 个赞、827 次浏览、4 次收藏）称，当天 OpenAI 的发布过程比较粗糙：插件缺失、某个企业账户里看不到 Sites，Codex 还出现了归档 bug；与此同时，[@wieslawsoltes](https://x.com/wieslawsoltes/status/2061742323139002490) [总结道](https://x.com/wieslawsoltes/status/2061742323139002490)（17 个赞、653 次浏览）称，Copilot 的定价如今大约只够支撑一个工作日的可接受使用量。公开可见的应对方式很直接：节省高级工具的使用、切换界面，或者干脆等到定价和发布稳定后再回来。这值得投入，因为团队显然同时在意可靠性和可预期的余量。

### 团队在多智能体协作周边仍缺少清晰的协作层

严重程度：中高。[@TaylorPearsonMe](https://x.com/TaylorPearsonMe) [表示](https://x.com/TaylorPearsonMe/status/2061481881959612431)（3 个赞、2 条回复、751 次浏览、2 次收藏）称，他认识的每个人都在试图给 Claude Code 和 Codex“外挂”协作能力，感觉就像在重造 Google Docs。[@dabit3](https://x.com/dabit3) [发布了](https://x.com/dabit3/status/2061931891016478905)（40 个赞、7 条回复、3,156 次浏览）介绍了 Devin Desktop 这个多智能体共享界面；一条回复明确把 IDE 重新定义为审查/路由层，但另一位用户马上表示，自己仍然看不到所有承诺中的智能体。[@OrenMe](https://x.com/OrenMe) [重点提到](https://x.com/OrenMe/status/2061873010664001605)（7 个赞、828 次浏览）则把 Copilot app 以计划为中心的桌面端视为解决同一问题的另一种尝试。这值得投入，因为当下的变通办法，就是把多个工具叠起来，然后祈祷上下文能在交接中存活。

## 3. 人们希望出现什么

### 为能写提示词、却不会运维生产系统的人提供默认安全的部署能力

最明确的实际需求并不是“生成更多代码”，而是围绕数据库、网络、审计轨迹和部署提供安全的默认配置。[@svpino](https://x.com/svpino/status/2061925133275861481) [明确说明了这一点](https://x.com/svpino/status/2061925133275861481)（8 个赞、4 条回复、1,911 次浏览、6 次收藏）以及被引用的 [Superblocks 帖子](https://x.com/bradmenezes/status/2061838224256061641)，都把位于 VPC 内的数据库和继承式 AWS 控制视为答案。[@jain_harshit](https://x.com/jain_harshit/status/2061867787250016686) [补充说](https://x.com/jain_harshit/status/2061867787250016686)（5 个赞、166 次浏览、2 次收藏）则称，当没有人理解最终形成的代码库时，纯粹的 vibe coding 终究会失效。机会：直接。

### 让多个智能体共享计划、状态和审查界面

团队需要的更像是一块共同工作台，而不是一堆彼此隔离的聊天会话。[@TaylorPearsonMe](https://x.com/TaylorPearsonMe/status/2061481881959612431) [描述了](https://x.com/TaylorPearsonMe/status/2061481881959612431)（3 个赞、2 条回复、751 次浏览、2 次收藏）把当前的缺口描述为：围绕 Claude Code 和 Codex 重造 Google Docs。新的 [GitHub Copilot 应用博客文章](https://github.blog/news-insights/product-news/github-copilot-app-the-agent-native-desktop-experience/) 和 [@dabit3](https://x.com/dabit3/status/2061931891016478905) [发布](https://x.com/dabit3/status/2061931891016478905)（40 个赞、7 条回复、3,156 次浏览）都指向同一个需求：可检查的计划、共享的工作状态，以及从一个地方在多个智能体之间路由。机会：直接且具竞争性。

### 能预测已交付质量，而不只是生成产出的基准测试

信息流里不断有人在区分“会写很多代码”和“能帮团队交付好软件”。[@emollick](https://x.com/emollick/status/2061659432233161023) [分享了](https://x.com/emollick/status/2061659432233161023)（122 个赞、22 条回复、9,021 次浏览、60 次收藏）的研究表明，发布量的增长远远落后于产出量的增长；与此同时，[@zhenthebuilder](https://x.com/zhenthebuilder/status/2061871071566168166) [提到](https://x.com/zhenthebuilder/status/2061871071566168166)（12 个赞、350 次浏览）显示，ViBench 正尝试评估端到端 Web 应用交付。需求很实际：人们想要的是一种能预测可维护性、发布就绪度和面向用户正确性的基准测试。机会：直接。

### 为编程智能体中的非编程工作提供稳定的插件层和输出层

6 月 2 日显示，大家对让编程智能体处理分析、文档和应用发布很感兴趣，但相关能力的上线仍然并不均衡。[@waynesutton](https://x.com/waynesutton/status/2061872764298944665) [宣布](https://x.com/waynesutton/status/2061872764298944665)（42 个赞、3 条回复、5,921 次浏览、20 次收藏）介绍了 Codex 的 Convex 插件，[@frankdotlee](https://x.com/frankdotlee/status/2061921190521041093) [描述了](https://x.com/frankdotlee/status/2061921190521041093)（10 个赞、92 次浏览）展示了 Codex 内的 Amplitude 工作流，[@RoundtableSpace](https://x.com/RoundtableSpace/status/2061874235807560059) [将其定义为](https://x.com/RoundtableSpace/status/2061874235807560059)（29 个赞、8 条回复、1,116 次浏览）则介绍了 Codex Sites，作为把计划转成可分享应用的一种方式。[@_simonsmith](https://x.com/_simonsmith/status/2061919879767191778) [立即指出](https://x.com/_simonsmith/status/2061919879767191778)（11 个赞、827 次浏览、4 次收藏）则指出，插件缺失、企业账户可见性也不一致。机会：具竞争性。

整体情绪更偏务实，而不是品牌忠诚。只要各自能把工作流中的某一部分做好，人们愿意混用 Antigravity、Codex、Copilot、Claude Code、OpenCode 和 Hermes。最常见的变通方式包括：把昂贵或脆弱的任务路由到其他界面；用一个桌面端充当审查/路由层，让另一个工具执行实际工作；以及当 vibe-coded 项目进入部署阶段时，要求更安全的默认配置。竞争态势也发生了变化：Antigravity 主打编排和速度，Codex 通过插件和可分享输出扩展边界，GitHub 强调可检查的智能体计划，而 Orca、Devin 这样的较小玩家则更侧重多智能体路由。

## 6. 新近且值得关注的动态

### ViBench 把应用层评估变成了一个公开项目

[@zhenthebuilder](https://x.com/zhenthebuilder) [表示](https://x.com/zhenthebuilder/status/2061871071566168166)（12 个赞、350 次浏览）称，Replit 一直在内部使用 ViBench，现在将其公开以帮助开发者；被引用的 [@pirroh](https://x.com/pirroh/status/2061868189630513509) 则把它定义为一个面向 Web 应用开发的端到端基准。公开的 [ViBench 仓库](https://github.com/ViBench/vibench-public) 也印证了这一点：它包含 PRD、测试计划、运行器框架，以及跨多个模型的 build-seed-evaluate 流水线。这很重要，因为它直接回应了当天的核心争论：以代码为中心的基准，无法衡量用户真正交付出去的东西。

### Codex 进一步向发布和角色化工作延伸

[@RoundtableSpace](https://x.com/RoundtableSpace) [表示](https://x.com/RoundtableSpace/status/2061874235807560059)（29 个赞、8 条回复、1,116 次浏览）称，Codex 现在可以把文档和计划转成可分享的应用和网站；[@frankdotlee](https://x.com/frankdotlee) [展示了](https://x.com/frankdotlee/status/2061921190521041093)（10 个赞、92 次浏览）则展示了另一条更垂直的方向：在 Codex 内运行 Amplitude 工作流。这里值得注意的不只是功能面变广，而是 Codex 正试图成为一个也能承载非编程工作的发布、分析与协作界面。

### Claude 的平台 API 获得了更适合智能体的终端入口

[@minchoi](https://x.com/minchoi) [重点提到](https://x.com/minchoi/status/2061938760678555702)（12 个赞、644 次浏览、7 次收藏）介绍了新的 Claude Platform CLI，可在 shell 中调用 API、创建智能体、上传文件、同步 YAML 并检查运行情况；被引用的 [@ClaudeDevs](https://x.com/ClaudeDevs/status/2061877343078244459) 则称，Claude Code 可以直接使用它。这值得关注，因为它把更多平台层能力带进了开发者本来就用来编排编程智能体的同一个终端界面。

## 7. 机会在哪里

** [+++］ 默认安全的代理交付** - 证据来自多个部分：［@svpino](https://x.com/svpino/status/2061925133275861481) 指出了提示词生成应用带来的数据丢失风险，[@jain_harshit](https://x.com/jain_harshit/status/2061867787250016686) 展示了可维护性的崩溃，而被引用的 [Superblocks](https://x.com/bradmenezes/status/2061838224256061641) 则体现了对默认安全数据库和策略的明确需求。这一方向很强，因为痛点是运营层面的、即时发生的，而且代价高昂。

** [+++］ 具有共享计划的多代理控制中心** - GitHub Copilot app、Devin Desktop 和 Antigravity 2.0 都收敛到了相同的产品形态：在一个界面中整合计划、代理路由、后台任务和审查。［@TaylorPearsonMe](https://x.com/TaylorPearsonMe/status/2061481881959612431) 通过把当下的变通办法描述为“围绕编程智能体重造 Google Docs”，明确点出了尚未被满足的需求。

**[++] 发布就绪度与应用层评估** - Emollick 的论文表明，代码产出增长速度远高于发布量增长；而 ViBench 的存在，则是因为团队需要一种公开方式来测试端到端应用交付，而不是只看代码片段质量。这是一个中等机会：需求很明确，但基准测试仍需证明自己能够预测真实生产结果。

**[+] 领域工作流包与角色化插件** - Science Skills、Codex 的 Convex 插件和 Codex 的 Amplitude 插件都表明，通用智能体正在被封装进面向具体工作流的外层。这还是一个正在形成中的方向，尚未被充分验证，但需求已经覆盖科学、后端构建、分析等各种非聊天任务。

## 8. 要点总结

1. ** AI 编程竞争正在从编辑器功能转向编排界面。** Antigravity 2.0、Devin Desktop 和 GitHub Copilot app 竞争的重点，都是计划、路由、定时/后台工作和多智能体控制，而不再只是自动补全。（[来源](https://x.com/kevinhou22/status/2061880709418213776)）
2. ** 代码变多，并不自动意味着交付的软件也会变多。** Emollick 论文中的图表和摘要把这道鸿沟具体化了，而那张“删除大量代码”的截图，则从一线实践者角度展示了同样的问题。（[来源](https://x.com/emollick/status/2061659432233161023)）
3. ** 下一道信任护城河是护栏，而不是原始产出速度。** 默认安全的基础设施、稳定一致的发布体验和可预期的配额，都比模型再多一点边际优势更迫切。（[来源](https://x.com/svpino/status/2061925133275861481)）
4. ** 插件和领域工作流包正在把编程智能体变成更广泛的工作平台。** Science Skills、Convex、Amplitude 和 Codex Sites 都在把这一类别从代码生成推向研究、分析、后端构建和可分享输出。（[来源](https://x.com/antigravity/status/2061519617550340492)）
