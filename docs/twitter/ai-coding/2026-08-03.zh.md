# Twitter AI 编程 - 2026-08-03

## 1. 人们正在讨论什么

### 1.1 Qwen 把价格、基准和可恢复循环放到一起，让开放权重的前沿模型重新变得有意思（🡕）

今天数据集中最明显的热度峰值来自 Qwen3.8-Max。多条帖子都不把它当作又一次普通的基准榜单发布：真正的信号来自几件事同时出现——下周开放权重、明确标出每百万 token 输入 $2 / 输出 $6 的价格，以及可被用户迁移到自身智能体工作流中的长时程自主编程能力。至少四条高信号内容都在强化同一个主题，后续讨论的焦点也转向了带检查点的执行方式，而不只是参数规模本身。

[@Alibaba_Qwen](https://x.com/Alibaba_Qwen) [宣布](https://x.com/Alibaba_Qwen/status/2084100707423289643)（1,461 个赞、124 条回复、53,679 次浏览、250 次收藏）将 Qwen3.8-Max 描述为一个 2.4T 参数模型，可自主编程 10 多天，支持 500 多轮芯片设计优化；Qwen3.8-Max 和 Qwen3.8-27B 都将在下周开放权重。随帖附上的基准图表让这条内容明显强于一般发布帖：图中显示，Qwen3.8-Max 在 TerminalBench 2.1 上得分 86.6，在 PaperBench 上得分 93.0，同时还列出了 SWE-Pro、FrontierSWE、CoWorkBench 和 OSWorld-Verified 的成绩。推文还把价格直接作为卖点，标出了每百万 token 输入 $2、输出 $6。

![Qwen 发布时的基准测试表格，展示了 Qwen 3.8-Max 在 TerminalBench、PaperBench、SWE-Pro、FrontierSWE 及相关任务上的宣称分数](https://pbs.twimg.com/media/HOw1F2ebgAAkpJJ.jpg)

[@codeglitch](https://x.com/codeglitch) [认为](https://x.com/codeglitch/status/2084396222631252263)（2 个赞、2 条回复、122 次浏览）认为，Qwen 这次发布里真正可复用的部分不是模型大小，而是围绕长期编程任务设计的检查点结构。配图把循环简化为 issue → change → check → state，并明确映射到类似 Claude Code 的交接流程，可配合 `DONE`、`NEXT` 或 `BLOCKED` 使用，把厂商演示转成了具体可执行的工作流建议。

![检查点幻灯片，总结了一个长周期代理循环：问题、变更、检查和状态](https://pbs.twimg.com/media/HO1DQzQXgAAVZ1l.png)

**讨论洞察：** Qwen 官方回复串主要是通过分别补充 LM、VL 和 16 天编程的后续内容来扩展证据集，但社区最有力的回应转向了可检查性。大家持续提炼出的有用部分，是如何把一次马拉松式长跑拆成多个可验证的小状态。

**与前一天对比：** 8 月 2 日的讨论主要由网关、免费层和路由层主导。到了 8 月 3 日，Qwen 带着开放权重时间点、明确价格和可直接用于工作流的产物，把模型层重新推回了前台。

### 1.2 Codex 的帖子从“写代码”转向“跑产品和文档工作流”（🡕）

今天最重要的 Codex 帖子讨论的不是编程基准，而是运营型工作。这个模式反复出现在产品管理、广告运营、文档和应用脚手架等场景里：用户把 Codex 当成一个能执行受限业务流程、并在审批节点停下来的工作者，而不是自动补全界面。

[@thsottiaux](https://x.com/thsottiaux) [声称](https://x.com/thsottiaux/status/2084196918071357707)（1,639 个赞、338 条回复、181,614 次浏览、115 次收藏）在引用一个小型 OpenAI pull request 后表示，你可以“让 Codex 凭空生成一个 PR，并把改进交付给 10 亿用户”。回复里也给出了有价值的反面意见：多位用户抱怨压缩聊天/图片 bug、积分消耗过快，以及 Pro 5x 配额“撑不了一整天”。也就是说，这种头部能力同时伴随着真实的操作成本和可靠性限制。

[@gdb](https://x.com/gdb) [提升了](https://x.com/gdb/status/2084074129930772953)（320 个赞、44 条回复、48,509 次浏览、172 次收藏）介绍了一项 Codex 技能，可把支持工单、访谈、问卷和流失记录转成有证据支撑的路线图。[引用的推文](https://x.com/Kappaemme1926/status/2083957246674042890) 将原始客户表述、底层问题、下一步待验证事项，以及真正可以如实宣称的内容分开；而回复很快点出了真正的难点：不是把抱怨聚类，而是判断声音最大的客户是否也最具战略价值。[@gdb](https://x.com/gdb) [还强调了](https://x.com/gdb/status/2084104354911707518)（84 个赞、12 条回复、11,338 次浏览、32 次收藏）则展示了第二种工作流：Codex 负责剪辑并发布广告活动、建立受众、设置预算，并在付款环节停下等待审批。

[@github](https://x.com/github) [报道](https://x.com/github/status/2084348327387132062)（115 个赞、13 条回复、26,637 次浏览、70 次收藏）给出了最具体、也最可量化的案例：Aspire 团队使用 GitHub Agentic Workflows 创建了 82 个跨仓库文档 pull request，82 个全部合并，中位合并时间为 44.8 小时。链接中的 [文章](https://github.blog/ai-and-ml/github-copilot/automating-cross-repo-documentation-with-github-agentic-workflows/) 补上了缺失的执行细节：只创建草稿 PR、限制 GitHub App 权限、采用安全输出，并由 SME 审核，而不是自动合并。[@waynesutton](https://x.com/waynesutton) [补充说](https://x.com/waynesutton/status/2084043985514090991)（26 个赞、2 条回复、2,139 次浏览、16 次收藏）则展示了一个更小但相似的模式，使用可复用的 [Codex Sites + Convex skill](https://github.com/waynesutton/Codex-Sites-Convex-Backend-Skill)，明确避免前端发布和后端状态管理彼此混杂。

**讨论洞察：** 最实质性的分歧不在于这些工作流是否令人印象深刻，而在于控制权：gdb 的回复在问路线图技能该如何权衡高声量反馈与战略价值；GitHub 的回复把人工审核视为决定性的护栏；而那条标志性的 Codex 成功帖几乎立刻就变成了配额和 bug 投诉串。

**与前一天对比：** 8 月 2 日还在抽象地谈 harness。到了 8 月 3 日，这套 harness 已经被绑定到文档 PR 合并时长、审批关卡和可复用业务工作流等可度量产出上。

### 1.4 信任与安全方面的抱怨不再只是理论问题（🡕）

本周早些时候的“验证”主题，今天变得非常具体。数据集中不再只是关于独立验证器层的抽象争论，而是出现了运行时控制产品、被阻断的安全工作流，以及一条直接的数据丢失投诉。信任问题现在同时表现为一个产品类别和一种支持负担。

[@_ar9av](https://x.com/_ar9av) [展示了](https://x.com/_ar9av/status/2084052318409093354)（19 个赞、7 条回复、576 次浏览）介绍了 Prismor：一个运行时控制平面，可在 Claude Code、Codex、Copilot 和框架 SDK 中拦截破坏性命令、机密外泄和 prompt injection。[仓库 README](https://github.com/PrismorSec/prismor) 与帖子中提到的 observe mode、HITL 审批和 MCP gateway 相呼应；回复则立刻追问误报、回滚语义，以及仓库变化后由谁维护策略。

[@paulbrigner](https://x.com/paulbrigner) [报道](https://x.com/paulbrigner/status/2084319165146370141)（163 次浏览）则展示了另一个方向上的失败：Codex Security 拒绝扫描他自己的 diff，显示的是 Trusted Access 提示，而不是执行防护性检查。[@zero_dovel](https://x.com/zero_dovel) [报道](https://x.com/zero_dovel/status/2084408026987929743)（3 条回复）呈现了更严重的结果，称一条 Antigravity 命令几乎把一台 Windows 机器清空了；照片显示用户目录几乎空白，但在抓取时，这仍是一条单方面投诉。[@stas_sorokin_](https://x.com/stas_sorokin_) [认为](https://x.com/stas_sorokin_/status/2084335717589655568)（82 次浏览）则认为，vibe coding 与 agentic engineering 的区别不在于模型智力高低，而在于“先验证，再信任”。

![Codex Security 阻止了一次 diff 扫描，显示 Trusted Access 警告，而不是运行所请求的安全检查](https://pbs.twimg.com/media/HOz8DdCWEAEIrF7.jpg)

**讨论洞察：** Prismor 的回复很好地体现了这种张力。人们希望在 MCP 服务器和工具调用之上有一层统一策略，但也要求有证据证明，这一层不会把合法的 shell 操作误判出来，或把智能体困在无法使用的审批循环中。

**与前一天对比：** 8 月 2 日强调的是把验证作为设计原则。到了 8 月 3 日，又多了被阻断的扫描、运行时策略产品和一条具体的数据丢失投诉，使得信任缺口更难被轻描淡写地带过。

## 2. 人们感到沮丧的地方

### 安全边界在两个方向上都在失灵

严重程度：高。[@paulbrigner](https://x.com/paulbrigner) [报道](https://x.com/paulbrigner/status/2084319165146370141)（163 次浏览）称，Codex Security 拒绝扫描他自己的 diff，显示的是 Trusted Access 提示，而不是执行防护性检查。[@zero_dovel](https://x.com/zero_dovel) [报道](https://x.com/zero_dovel/status/2084408026987929743)（3 条回复）称，一条 Antigravity 命令几乎把一台 Windows 机器清空了；附图显示用户目录几乎空白，尽管在抓取时这仍是单方面说法。[@_ar9av](https://x.com/_ar9av) [主推](https://x.com/_ar9av/status/2084052318409093354)（19 个赞、7 条回复、576 次浏览）介绍 Prismor，正是瞄准这一失效区间：破坏性命令、机密泄露、prompt injection，以及围绕高风险工具调用设置审批关卡。链接中的 [AISLE 披露](https://aisle.com/blog/aisle-discovers-1-click-rce-vulnerability-in-cursor-vs-code-and-google-antigravity) 还提供了外部证据，说明这些担忧并非假设：它记录了 Cursor、VS Code 和 Google Antigravity 中由恶意 commit-message 链接触发的一键 RCE 路径。今天可见的应对方式，是增加明确的策略层，或重新考虑哪些任务应继续留在封闭托管界面上。值得投入构建：是。

### 配额断崖和模型锁定仍在塑造日常工具选择

严重程度：高。[@thsottiaux](https://x.com/thsottiaux) [撰写关于 Codex 的内容](https://x.com/thsottiaux/status/2084196918071357707)（1,639 个赞、338 条回复、181,614 次浏览、115 次收藏）下的回复变成了一串投诉：压缩聊天和图片 bug、积分消耗过快，以及“无法支撑一整天”的 Pro 5x 配额。[@JustMicrock](https://x.com/JustMicrock) [抱怨](https://x.com/JustMicrock/status/2084254731728191756)（8 个赞、4 条回复、374 次浏览）表示，OpenAI 仍是日常默认选择，因为竞争对手要么暂停订阅、要么没有可比的额度、要么限制模型可用场景，其中包括 Google 在 Antigravity CLI 之外的 OAuth 限制。[@FReza1984](https://x.com/FReza1984) [将其描述为](https://x.com/FReza1984/status/2084246715373363466)（93 次浏览）把 OmniRoute 视为解决同一问题的基础设施，认为供应商频繁变动、免费层耗尽和不断变化的模型经济性，使“路由”比“忠诚”更实际。帖子本身已经很清楚地展示了应对模式：跨供应商路由，在 OpenCode 这类界面里寻找更便宜或免费的模型，并把高价访问额度留给真正需要它的任务。值得投入构建：是。

### 现有智能体界面仍把简单任务做得彼此差异过大

严重程度：中。[@__tosh](https://x.com/__tosh) [展示了](https://x.com/__tosh/status/2084226174847172835)（45 次浏览）展示了三个智能体读取同样八个 Python 文件时，在工具调用形态、token 用量和时延曲线上表现出明显差异。[@0xQuantic](https://x.com/0xQuantic) [总结了](https://x.com/0xQuantic/status/2084205847303877062)（14 个赞、4 条回复、656 次浏览）则从操作侧描述了同样的摩擦：Hermes + Codex 感觉最简单，Claude Code 在特定任务上有帮助，云端智能体主要是在软件工作上显得有前景，而本地模型在普通硬件上仍令人失望。[@akshay_pachaar](https://x.com/akshay_pachaar) [强调了](https://x.com/akshay_pachaar/status/2084285621011689918)（22 个赞、7 条回复、2,106 次浏览、25 次收藏）基本上把 NOOA 视为摆脱 prompt 文件、工具 schema、回调和工作流图的一种出路。今天的绕行办法，是把技术栈收缩到一组可预测的搭配或某一个框架，而不是信任整个类别都已经成熟。值得投入构建：是。

## 3. 人们希望存在什么

### 一层既能检查高风险代码、又不会阻断合法防御工作的信任层

实际需求。最有力的证据来自这组对照：[@_ar9av](https://x.com/_ar9av) [出售](https://x.com/_ar9av/status/2084052318409093354)（19 个赞、7 条回复、576 次浏览）展示的是运行时控制平面，而 [@paulbrigner](https://x.com/paulbrigner) [失败](https://x.com/paulbrigner/status/2084319165146370141)（163 次浏览）则是在想办法让 Codex Security 去扫描他自己的 diff。[AISLE 披露](https://aisle.com/blog/aisle-discovers-1-click-rce-vulnerability-in-cursor-vs-code-and-google-antigravity) 和那条 Antigravity 数据丢失投诉解释了人们为什么想要审批、拒绝规则和审计追踪，但被阻断的扫描也说明，他们并不希望这些控制措施反过来禁用合法的自我保护。机会：直接。

### 工具切换后仍能沿用的可移植技能包与工作流捕获

实际需求。[Skill Recorder](https://github.com/microsoft/skill-recorder)、[AMD Skills](https://x.com/AIatAMD/status/2084376136985764032)、[mimeographs](https://github.com/K-Dense-AI/mimeographs) 和 [mattpocock/skills](https://github.com/mattpocock/skills) 都默认一个前提：可复用的智能体行为应该是可安装、可分享、可跨工具迁移的，而不是被困在某一个聊天窗口或某一次演示里。仓库汇总帖下最有价值的一条回复说得很直白：关键特性不是“有更多工具”，而是技能真的能通过 marketplace 或命令安装。机会：直接。

### 不受任何厂商主场限制的开放、低价模型访问

没有任何单一技术栈彻底胜出。只要业务工作流里内置了人工审核，人们就更倾向于 Codex 和 GitHub 托管的界面；而成本敏感型试验则把人们推向 Qwen 的价格、OmniRoute 的回退机制，以及 OpenCode 的免费模型菜单。

迁移模式带有明显的防御性，而非意识形态性。做法是收窄任务、安装技能包、补上一层路由器或控制平面，并把人工审批或验证步骤放在任何昂贵或高风险的动作附近。OpenCode 的情绪在同一天内明显分裂；即便是相对乐观的云端智能体用户，也仍把这个类别描述为更擅长边界明确的软件任务，而不是普适默认选项。

## 7. 机会所在

**[+++] 严格到足以起作用、又宽松到仍然可用的运行时信任层** - Prismor、被阻断的 Codex Security 扫描、Antigravity 数据丢失投诉，以及 AISLE 的披露，都指向同一个缺口：团队需要审批、策略和审计层，同时又不能妨碍合法的安全与维护工作继续进行。

**[++] 具备审批感知的业务工作流** - 从反馈到路线图的分析、广告活动执行、文档 PR 自动化，以及 Codex Sites + Convex，都显示出对受限智能体工作流的需求：在有意义的检查点停下，而不是试图端到端自动跑完整个业务流程。

**[+] 移动监督界面** - VoiceClaw 显示出从手表或手机审批并引导工作的早期需求，而不必始终守在原始机器前；不过目前证据仍仅限于少量帖子。
