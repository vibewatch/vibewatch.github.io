# Twitter AI 编程 - 2026-05-22

## 1. 人们在讨论什么

### 1.1 技能、行动手册与工作流遥测成了一等资产 🡕

这一组最强势的帖子把 AI 编程的杠杆视为一种应被打包、审视和复用的能力，而不只是临时即兴提示。信号最强的证据来自三方面：Codex 技能分发、新的本地工作流审计仪表盘，以及 GitHub 将更多 Copilot 代理栈开放给公众查验。至少有三条分量十足的内容支撑了这一主题。

[@jxnlco](https://x.com/jxnlco) [表示](https://x.com/jxnlco/status/2057820959189483683)（186 个赞，16 条回复，6,824 次浏览，128 次收藏）称，Codex 用户现在可以让 Codex 检查 [`openai/skills`](https://github.com/openai/skills) 安装器，并推荐应安装哪些技能。链接的仓库将自己描述为 Codex 的技能目录，表示 `.system` 技能会自动安装，并说明如何通过 `$skill-installer` 安装精选和实验性技能，这让技能从抽象概念变成了具体的分发机制。

[@akshay_pachaar](https://x.com/akshay_pachaar) [报道](https://x.com/akshay_pachaar/status/2057901920795378159)（33 个赞，12 条回复，2,948 次浏览，59 次收藏）称，Microsoft 已将 [AI Engineer Coach](https://github.com/microsoft/AI-Engineering-Coach) 开源。该仓库表示，它可以读取本地 AI 会话日志、跟踪实践评分和每周趋势、检测 45 条反模式规则、按 harness 和模型衡量产出、将重复提示识别为技能，并为上下文健康度打分；附带截图显示，这些想法已经不是概念，而是一个可运行的仪表盘。

![AI Engineer Coach 仪表板，显示上下文健康评分、Agentic readiness 检查、harness 对比以及工作区上下文地图](https://pbs.twimg.com/media/HI8i5B6aYAA-Pim.jpg)

[@GHchangelog](https://x.com/GHchangelog) [宣布](https://x.com/GHchangelog/status/2057616196669735020)（27 个赞，1,522 次浏览）称，GitHub Copilot for Eclipse 现已在 MIT 许可下开源。链接中的 [更新日志帖子](https://github.blog/changelog/2026-05-21-github-copilot-for-eclipse-is-open-source) 和 [仓库](https://github.com/microsoft/copilot-for-eclipse) 表示，开发者现在可以直接在代码中检查聊天、补全、代理模式、MCP 集成、技能、BYOK、自定义代理、隔离子代理以及 plan-agent 行为。

**讨论洞察：** 技能相关帖子下的回复提出，希望有共享市场、在欧洲更方便地使用 computer use 和 Chrome，以及更容易把会议记录推送进项目上下文的方法；这表明，在这些已打包能力之外，分发和持久记忆仍是缺失的一层。

**与前一天对比：** 相比 5 月 21 日主要由第一方 Codex 上线说明主导，5 月 22 日的重心转向了面向用户的代理工作流安装、检查与审计方式。

### 1.2 配额与使用控制成为产品叙事的一部分 🡕

第二个主要主题是，使用上限、重置时间和模型控制已不再只是后台计费细节。它们已经足够核心，足以引发状态页截图、退订威胁，以及专门围绕使用情况可见性构建的新工具。至少有四条高信号内容支撑了这一主题。

[@TimJayas](https://x.com/TimJayas) [表示](https://x.com/TimJayas/status/2057748453871243586)（75 个赞，11 条回复，3,674 次浏览）称，即便 Google 已提高每周 Antigravity 和 Gemini 配额，两次 Gemini Pro 提问仍消耗了当天大部分额度。附带截图显示，`83% used` 当前使用量，仅占每周上限的 `4% used`；回复则称这种比例对代理工作流来说“很恶心”，并表示他们正在取消订阅。

**与前一天的对比：** 5 月 21 日已经出现了 Google 3x 配额重置公告；到 5 月 22 日，使用问题不仅没有降温，还进一步扩展到了 Codex 的公开事故追踪。

最具体的构建活动并不是试图取代 Codex、Claude Code、Copilot 或 OpenCode。相反，开发者是在它们外围增加共享服务器、语义索引、聊天桥接和本地路由层。至少有四条项目分享支持了这一主题。

[@Suryanshti777](https://x.com/Suryanshti777) [分享了](https://x.com/Suryanshti777/status/2057704871739171047)（13 个赞，8 条回复，348 次浏览）将 CodeGraph 描述为适用于 Claude Code、Cursor、Codex CLI、OpenCode 和 Hermes Agent 的本地知识图谱，并链接到了 [colbymchenry/codegraph](https://github.com/colbymchenry/codegraph) 仓库。该仓库称自己是一个预索引的代码知识图谱，并发布了在七个开源代码库上的基准测试结果，显示平均达到 `35% cheaper`、`59% fewer tokens`、`49% faster` 和 `70% fewer tool calls`。![CodeGraph 基准测试表，展示了包括 VS Code、Django、Tokio、OkHttp 和 Alamofire 在内的各仓库中位数节省情况](https://pbs.twimg.com/media/HI5vom7aEAA-1jm.jpg)

**与前一天对比：** 这延续了 5 月 21 日的互操作性主题，不过今天的案例更偏向团队控制平面、消息界面和本地路由，而不只是 PR 审查插件。

## 2. 什么让人感到沮丧

### 配额计算不透明，限流额度突然被迅速耗尽

最明显的挫败感在于，人们无法预判高级额度会以多快的速度见底。[@TimJayas](https://x.com/TimJayas) [表示](https://x.com/TimJayas/status/2057748453871243586)（75 次点赞，11 条回复，3,674 次浏览）表示，只问了 Gemini Pro 两个问题，就耗掉了当天大部分额度；附带的使用截图显示，当前窗口已用掉 `83% used`，而每周上限只用了 `4% used`。该帖下的回复称，智能体“午饭前就能把那个套餐烧光”；一位用户表示自己已经取消订阅，另一位则说，Gemini 在消耗掉大部分额度后仍未满足提示要求，于是自己把一项图像生成任务转到了 ChatGPT。严重程度：高。

Codex 用户也在 OpenAI 这边表达了同样的不满。[@weswinder](https://x.com/weswinder) [表示](https://x.com/weswinder/status/2057882979108569103)（68 次点赞，10 条回复，3,360 次浏览）称，OpenAI 已知晓 Codex 限额消耗过快的问题，截图则显示状态页上有一起公开的限流事故。[@ziwenxu_](https://x.com/ziwenxu_) [表示](https://x.com/ziwenxu_/status/2057889533178368472)（15 次点赞，8 条回复，443 次浏览）称，状态页证实了用户在可能重置前“已经喊了好几天”的问题。值得为此构建：是。信息流清楚指向一种直接需求：需要实时的用量可见性、明确的重置时间，以及更清楚地解释为什么一次简短会话就能耗掉一天预算。

### 工作流控制项总在用户眼皮底下变化

当关键控制项消失，或仍被服务端限制时，人们同样感到沮丧。[@marouane53](https://x.com/marouane53) [抱怨](https://x.com/marouane53/status/2057730536987033973)（73 次点赞，7 条回复，2,559 次浏览）称，Codex 悄悄移除了按模型选择思考等级的能力，heavy mode 也不复存在，这让他怀疑供应商是否在牺牲用户利益来节省 token。那张简化后的 GPT-5.5 智能等级选择器截图让这条抱怨更具体，而回复则表示，其他用户也看到了同样的推送。严重程度：高。

同类挫败感的另一种表现，是服务端限制。[@BeauJohnson89](https://x.com/BeauJohnson89) [认为](https://x.com/BeauJohnson89/status/2057930872498598254)（29 次浏览）称，Codex Desktop 只会显示服务端 allowlist 上的模型，并指向 [`0xSero/codex-shim`](https://github.com/0xSero/codex-shim) 作为本地变通方案。该仓库称，这个 shim 会把 Factory BYOK 模型以及可选的 ChatGPT GPT-5.5 透传给 Codex Desktop，这意味着用户正在自己搭建本地逃生通道，而不是等待官方选择器开放。值得为此构建：是。人们想要的是稳定的控制界面和明确的路由，而不是悄无声息的 UI 变化。

### 团队上下文依然很难安全共享

共享上下文仍然困难到让团队不得不自建基础设施。[@thdxr](https://x.com/thdxr) [展示了](https://x.com/thdxr/status/2057634938984210481)（90 次点赞，21 条回复，16,907 次浏览）展示了一个私有 OpenCode 服务器：克隆了所有代码仓库，前面加上 Cloudflare Access，这样整个团队就能针对同一个环境发起提示并查看正在进行的工作。一条回复称，他们也做了类似的东西；另一条则表示，Microsoft 仍未为私有 GitHub 组织推出等效方案。严重程度：中。

技能和 bridge 相关帖子的回复，也从另一个角度指向了同样的缺口。在 [@jxnlco](https://x.com/jxnlco) [分享](https://x.com/jxnlco/status/2057820959189483683)（186 次点赞，16 条回复，6,824 次浏览，128 次收藏）这个技能安装流程帖下，一条回复希望能录制会议纪要并自动更新项目上下文，另一条则希望在欧洲更容易使用 computer use 和 Chrome。[@zarazhangrui](https://x.com/zarazhangrui) [展示了](https://x.com/zarazhangrui/status/2057710284920520906)（7 次点赞，3 条回复，391 次浏览）则提供了一种变通办法：把 Claude Code 接入 Lark，并按聊天划分会话和文档操作。值得为此构建：是。人们需要的是可控、可共享、可持久的上下文，而且要能跨团队、跨设备运作。

### 区域访问限制正在催生代理经济

最具结构性的挫败感来自访问本身。[@Akasheth_](https://x.com/Akasheth_) [表示](https://x.com/Akasheth_/status/2057702607561675199)（24 次点赞，15 条回复，196 次浏览）称，一位牛津研究者揭露了中国廉价 Claude 和 OpenAI 访问的地下市场，随后链接到了文章 [《如何在中国购买便宜的 Claude Tokens》](https://www.chinatalk.media/p/how-to-buy-cheap-claude-tokens-in)。文章称，API 代理、transfer stations，以及相关的规避性基础设施，使中国开发者最低只需 `10% of the official price` 就能访问 Anthropic 模型，而且这个市场在 GitHub、Taobao、Twitter 和 Telegram 上都看得见。严重性：高。

这不是在抱怨模型质量；而是在抱怨根本无法获得合规访问。公开信息里已经能看到应对机制：代理层、区域路由和灰色市场转售商。是否值得构建：是，前提是产品合规且可追溯。现有证据表明，只要官方路径缺失或价格过高，人们就会绕开官方访问壁垒。

## 3. 人们希望出现什么

### 融入工作流的使用可视性

今天信息流里最实际的诉求，不是更好的模型，而是更清楚地看到当前模型花了多少钱，以及额度何时重置。[@_brian_johnson](https://x.com/_brian_johnson) [表示](https://x.com/_brian_johnson/status/2057710914191663436)（207 次浏览）称，这正是 [TokenBar](https://tokenbar.site/) 要解决的痛点：在 Mac 菜单栏中实时显示 Codex 和 Claude 的使用量、成本、重置计时器以及模型搭配。TokenBar 网站称，它能让 OpenAI、Claude、Gemini、OpenCode 及其他受支持工具的使用量、积分、重置和提醒始终可见，而 [AI 工程师教练](https://github.com/microsoft/AI-Engineering-Coach) 还补充了进度、反模式和输出的本地图表。机会评级：直接。

### 可复用的项目记忆与技能分发

[@jxnlco](https://x.com/jxnlco) [展示了](https://x.com/jxnlco/status/2057820959189483683)（186 个赞，16 条回复，6,824 次浏览，128 次收藏）称，Codex 可以检查 [`openai/skills`](https://github.com/openai/skills) 安装器并建议安装哪些技能，但回复立刻提出了下一层需求：共享市场、更便捷地接入浏览器和计算机使用能力，以及录制会议以保持项目上下文持续更新。这清楚地表明，用户想要的是团队可加载、而不是反复手动重输的持久化操作记忆。机会评级：直接。

### 从远程和移动端控制本地编码代理

信息流还显示，人们希望能在终端之外使用本地代理。[@zarazhangrui](https://x.com/zarazhangrui) [介绍了](https://x.com/zarazhangrui/status/2057710284920520906)（7 个赞，3 条回复，391 次浏览）展示了一个 Feishu / Lark 桥接，让 Claude Code 能通过聊天运行，支持按会话分线程、文档操作、图片、文件和交互式卡片。截图之所以重要，是因为它展示的是一个持久化聊天界面，带有类似斜杠命令的工作流和文档发布能力，而不只是一个玩具机器人。机会评级：竞争型。

### 面向可提示仓库的共享团队工作区

[@thdxr](https://x.com/thdxr) [展示了](https://x.com/thdxr/status/2057634938984210481)（90 个赞，21 条回复，16,907 次浏览）展示了这种需求一个已经在构建中的版本：共享的 OpenCode 服务器，代码仓库集中克隆，团队成员可以针对同一环境发出提示，并查看彼此的工作。回复中提到 Microsoft 尚未在私有 GitHub 组织中加入类似功能，这句直白的话本身就是未被满足需求的说明。机会评级：直接。

### 用官方模型路由取代本地应急方案和灰色市场

两条不同的帖子都指向同一个缺失功能：官方支持的路由。[@BeauJohnson89](https://x.com/BeauJohnson89) [指出](https://x.com/BeauJohnson89/status/2057930872498598254)（29 次浏览）指向 [`0xSero/codex-shim`](https://github.com/0xSero/codex-shim)，因为 Codex Desktop 的选择器仍受服务器允许列表限制；而 [@Akasheth_](https://x.com/Akasheth_) [分享](https://x.com/Akasheth_/status/2057702607561675199)（24 个赞，15 条回复，196 次浏览）链接的 ChinaTalk 文章则表明，当官方访问过于僵化或根本不可用时，代理经济就会出现。这里的诉求不是抽象意义上的开放，而是对人们已经在使用的模型和地区提供受支持、合规的路由。机会评级：竞争型。

## 7. 机会在哪里

**[+++] 代理工作流中的用量与支出控制** —— 证据来自市场两端：Gemini 用户在仅仅几个提示后就触及日限额，Codex 用户眼看着限流事件发生，TokenBar 在菜单栏中主打实时重置和额度，AI Engineer Coach 则把本地日志转化为用量和反模式视图。这一方向很强，因为它同时涵盖了产品抱怨、公开事件和构建者的响应。

**[+++] 共享上下文与团队控制平面** —— Gangprompt 的共享 OpenCode 服务器、回复中要求 Codex 接入会议记录和浏览器访问的呼声，以及面向 Claude Code 的 Lark 桥接，都指向同一个机会：团队想要一个可通过提示驱动的统一环境，具备持久记忆、受控访问和远程界面。这一方向很强，因为现有构建与用户诉求高度一致。

**[++] 面向大型代码仓库的语义上下文层** —— 这里最明确的证据来自 CodeGraph：公开仓库基准、广泛的 harness 支持，以及回复中对“大多数代理时间都耗在寻找上下文上”的认同。这一方向属于中等强度，因为在更大的仓库中其收益显而易见，但回复线程仍在担忧部署和维护成本。

**[++] 无需变通的官方路由与模型选择** —— codex-shim 之所以存在，是因为用户希望 Codex Desktop 能把 BYOK 和透传模型作为一等选项提供；而 Copilot for Eclipse 已经文档化了 BYOK 和可扩展的代理界面。这一方向属于中等强度，因为需求很明确，但当前最强的实现仍只是一个早期的本地 shim。

**[+] 合规的区域访问替代路径** —— ChinaTalk 关于代理经济的文章，以及技能线程下关于欧洲访问的请求，都表明人们对官方访问路径存在未被满足的需求，而且这种路径不应迫使用户转向经销商或不受支持的变通方案。这一信号仍在浮现，因为需求真实存在，但当前证据更多体现的是痛点，而非可信的解决方案。
