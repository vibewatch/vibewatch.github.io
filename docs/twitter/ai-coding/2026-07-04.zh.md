# Twitter AI 编程 - 2026-07-04

## 1. 人们在讨论什么

### 1.1 官方多智能体工作流正从“技巧”走向第一方产品（🡕）

最强的一组讨论聚焦于：把智能体协作变成产品层能力，而不再只是私下搭建的配置。至少有四条保留内容从不同角度体现了同一转变：由仓库定义的自定义智能体、官方的 Claude 内嵌 Codex 插件、明确的模型角色分工手册，以及围绕 ChatGPT 和 Codex 的统一应用讨论。相比 7 月 3 日关于 harness 和 handoff 的讨论，7 月 4 日更加具体：出现了具名命令、安装步骤和可复用的工作流文件。

[@github](https://x.com/github) [宣布](https://x.com/github/status/2073492041326088701)（109 个赞、15 条回复、18,420 次浏览、29 次收藏）讨论 GitHub Copilot CLI 中的自定义智能体；关联的 GitHub 博客称，这些智能体配置文件位于 `.github/agents`，采用 Markdown 加 YAML frontmatter，可为可重复的终端工作流定义角色、工具和防护规则。

[@HeyAnjula](https://x.com/HeyAnjula) [展示了](https://x.com/HeyAnjula/status/2073274764572180913)（28 个赞、10 条回复、508 次浏览、4 次收藏）讨论 OpenAI 的 `codex-plugin-cc` 在 Claude Code 中运行。公开 README 印证了关键说法：`/codex:review`、`/codex:adversarial-review`、`/codex:rescue`、`/codex:status` 和 `/codex:result` 都是已提供的命令；该插件使用本地 Codex CLI，并通过 ChatGPT 或 API 密钥认证，而不是依赖单独托管的运行时。

[@Hyde_ai3](https://x.com/Hyde_ai3) [发布了](https://x.com/Hyde_ai3/status/2073151028237922659)（30 个赞、2 条回复、277 次浏览）给出了一套具体的编排方案：由 Fable 5 负责编排，Opus 担任深度推理子智能体，Sonnet 作为快速执行者，Codex 则作为独立的对等工程师。附图是关键证据，因为其中包含实际的 `/agents`、`/plugin` 和 `/codex:setup` 步骤，并建议让每个模型各司其职，而不是让一个模型包办所有工作。

![工作流程图：将 Fable 5 指定为总协调器，Opus 和 Sonnet 作为子代理，Codex 作为同级工程师，全部置于同一个 Claude Code 设置中](https://pbs.twimg.com/media/HMVP3kBbsAEEl8i.jpg)

[@thsottiaux](https://x.com/thsottiaux) [调侃道](https://x.com/thsottiaux/status/2073506936725581911)（656 个赞、89 条回复、24,628 次浏览、27 次收藏）称 OpenAI 正在把“ChatGPT 带到 Codex 中，让 Codex 可以出现在 ChatGPT 里的 Codex 里的 ChatGPT 中”，但回复让这件事回到了实用层面：有人希望实现无需切换标签页的工作流；有人提出大约 500 个 thinking token 被截断的问题；还有一条较长的回复要求目标驱动工作流一旦开始循环时，能显示计划、里程碑和执行状态。

**讨论洞察：** 有价值的回复集中在责任归属、上下文窗口和执行可见性上。人们认可这种集成方向，但仍希望看到清晰的工作单元、分离的记忆，以及一个智能体向另一个智能体委派任务时更好的可追踪性。

**与前一天的比较：** 7 月 3 日将编排视为 harness 问题；7 月 4 日则把它推进到了第一方产品界面，并配套了文档化命令和可版本控制的智能体文件。

### 1.2 配额、重置和成本路由仍是核心，但讨论变得更偏运营（🡕）

成本压力仍然是重要的决策因素，但讨论已经超越了泛泛的价格抱怨。当日更有分量的内容聚焦于绕开限制、查看重置到期时间，以及构建能够承受速率限制的技术栈。与 7 月 3 日公开比价的氛围相比，7 月 4 日更关注运营控制。

[@Mr_Salio](https://x.com/Mr_Salio) [发帖称](https://x.com/Mr_Salio/status/2073357728471269448)（126 个赞、21 条回复、8,739 次浏览、10 次收藏）展示了 Codex 中出现 GPT-5.6 Sol、Terra、Luna 以及新的速度控制选项。回复并未确认 Terra 和 Luna 的具体含义，但表明人们已经开始把模型命名、发布状态和速度档位视为工作流规划的输入。

[@Ananth7e](https://x.com/Ananth7e) [分享了](https://x.com/Ananth7e/status/2073452226488803634)（36 个赞、2,456 次浏览）展示了带有明确到期时间的 Codex 重置面板，随后引用一名 OpenAI 员工称该功能“即将推出”。这很重要，因为重置时间不透明是 7 月 3 日的一个突出抱怨；这是信息流中首个较有力的证据，表明产品正在把到期窗口显示在界面中。

![Codex 重置面板，显示 4 次可用重置及其明确的到期时间，范围从数小时到数周不等](https://pbs.twimg.com/media/HMZhVpKaAAElAUf.png)

[@israfill](https://x.com/israfill) [声称](https://x.com/israfill/status/2073474876762132750)（3 个赞、4 条回复、291 次浏览、3 次收藏）称，通过 Microsoft Foundry 和 Azure credits 路由 Claude Code，可以避开常见的五小时 Claude 限制。即使经济性仍只是用户报告，截图依然是有用的公开证据：其中显示 Azure 成本面板已产生 $32.93 费用，并有 $1,977.07 可用 credits，正是用户如今正在传播的那类路由变通方案。

**讨论洞察：** 读者关注的重点不再是原始基准性能谁更强，而是重置机制、到期倒计时、价格通道，以及工作流能否在没有意外中断的情况下持续运行。

**与前一天的比较：** 7 月 3 日主要讨论价格版图和对重置的焦虑；7 月 4 日增加了关于重置的具体界面证据，以及更明确的 credits 路由技巧。

### 1.3 围绕 AI 编程的安全加固开始成为独立的检查清单类别（🡕）

安全不再被视为未来才需要考虑的问题。三条保留内容都将其视为即时的工作流层：部署检查清单、技能供应链扫描，以及针对某个智能体产品的具体攻击链。这延续了 7 月 3 日的信任主题，但形式更加流程化。

[@dashboardlim](https://x.com/dashboardlim) [警告称](https://x.com/dashboardlim/status/2073165300258718109)（8 个赞、776 次浏览、14 次收藏）称，Cursor、Claude Code、Lovable、Antigravity 和 Codex 发布迅速，但默认并不安全。附带的检查清单是核心证据，其中列出了七项具体检查：Supabase RLS 策略、服务端 API 密钥处理、身份验证边界情况、安全专家审查提示、后端验证、速率限制，以及错误信息泄露。

[@DanKornas](https://x.com/DanKornas) [强调了](https://x.com/DanKornas/status/2073384819715666113)（7 个赞、5 条回复、1,116 次浏览、5 次收藏）介绍了 Skill Scanner，一款面向 AI Agent Skills 的尽力而为型安全扫描器。截图明确展示了其独特之处：它结合静态分析、YAML 和 YARA 模式、LLM 语义判断、行为数据流分析、SARIF 输出以及 GitHub Code Scanning 集成，用于在安装或团队推广前审查智能体资产。

[@TakSec](https://x.com/TakSec) [总结道](https://x.com/TakSec/status/2073111122996302268)（6 个赞、791 次浏览、3 次收藏）介绍了 ODIN 的研究，显示 Google Antigravity 可通过隐藏的 `<title>` 标签和渲染后的图片 URL，被诱导外泄机密。ODIN 研究报告的截图将这一攻击类别从假设变成了具体案例。

**讨论洞察：** 值得注意的变化在于形式。信息流中不再是笼统的“AI 安全”论断，而是出现了实际的部署前检查、扫描器功能和攻击机制。

**与前一天的比较：** 7 月 3 日聚焦信任工具和漏洞研究报告；7 月 4 日则增加了更具运营性的“部署前先执行这些检查”的姿态。

## 3. 人们希望出现什么

### 透明的使用状态和更智能的成本路由

最明确的实际需求，是让工具解释自身的运行边界。[@Ananth7e](https://x.com/Ananth7e) [分享了](https://x.com/Ananth7e/status/2073452226488803634)（36 个赞、2,456 次浏览）展示了重置面板，正是因为到期时间很重要；[@israfill](https://x.com/israfill) [建议](https://x.com/israfill/status/2073474876762132750)（3 个赞、4 条回复、291 次浏览、3 次收藏）展示了通过 Azure credits 路由以避开 Claude 限制；[@CrypSaf](https://x.com/CrypSaf) [将其定义为](https://x.com/CrypSaf/status/2073440886533316933)（119 个赞、73 条回复、4,039 次浏览）则展示了多模型故障回退，作为应对速率限制的直接方案。这是一项紧迫的实际需求：用户希望产品无需外部技巧，就能显示重置时间、当前通道、回退行为和剩余可运行时长。机会：直接。

### 具备可见工作单元、记忆边界和进度的任务委派

最明确的工作流诉求，是让多智能体委派变得可检查。在 [@HeyAnjula](https://x.com/HeyAnjula) 的 [插件帖子](https://x.com/HeyAnjula/status/2073274764572180913)（28 个赞、10 条回复、508 次浏览、4 次收藏）下，有人表示，真正需要管理的对象是被委派的工作单元：负责人、范围、工具、日志、审查者、成本画像和停止条件。[@thsottiaux](https://x.com/thsottiaux) 的 [Codex 帖子](https://x.com/thsottiaux/status/2073506936725581911)（656 个赞、89 条回复、24,628 次浏览、27 次收藏）下有回复要求提供任务计划、里程碑和可见进度，因为当前的目标模式可能陷入循环。这不是一个理想化想法，而是明确的产品缺口。机会：直接。

### 为生成式应用和已安装的智能体技能提供更安全的默认设置

人们要的不是更多泛泛的“AI 安全”，而是能够停止生成高风险默认配置的产品。[@dashboardlim](https://x.com/dashboardlim) [列出了](https://x.com/dashboardlim/status/2073165300258718109)（8 个赞、776 次浏览、14 次收藏）列出了用户如今必须手动记住的具体检查；[@DanKornas](https://x.com/DanKornas) [推广了](https://x.com/DanKornas/status/2073384819715666113)（7 个赞、5 条回复、1,116 次浏览、5 次收藏）则介绍了一款独立扫描器，仅用于在安装前审查智能体技能。这是一项已有检查清单和扫描器参与竞争的实际需求，但用户需要在编程工具之上额外叠加这些工具，说明核心工具仍有机会提供原生方案。机会：竞争性。

### 规格和文档变更能够自动同步到代码

这是一个较弱但已经显现的需求。[@belindmo](https://x.com/belindmo) [询问](https://x.com/belindmo/status/2073536801697108020)（3 个赞、1 条回复、27 次浏览、3 次收藏）希望有一个智能体监控产品文档，并在文档发生变化时更新代码库。当前证据仍然有限，但这符合当天更广泛的规范优先、工作流优先编程趋势。机会：新兴。

| GitHub Copilot | IDE 助手 | (+) | 用于 SQL、Python、PySpark 和 dbt；广泛适配日常工程技术栈 | 重复性工作流仍促使用户增加额外封装层，而不是只依赖原始自动补全 |

| Claude Code | 编程智能体 | (+/-) | 强大的主要工作界面，常被用作编排器或主要编程智能体 | 会话限制、上下文循环问题，以及提示不够明确时容易出现的安全隐患 |
| Codex | 编程智能体 | (+/-) | 在更大的工作流中承担后台救援、审查和第二意见角色 | 重置管理、发布状态不明确，以及关于截断或隐藏状态的部分抱怨 |
| OpenCode | 编程智能体 / 工作区 | (+/-) | 适用于云工作区和基于共享的工作流 | 本地模型冷启动和协作仍需要预热插件或 Gitterm 等附加工具 |
| Azure Foundry | 托管 / 计费通道 | (+/-) | 允许用户通过 credits 和企业计费界面路由 Claude 系列的使用量 | 配置开销高、credits 会过期，而且目前仍是变通方案，而非第一方产品答案 |
| Plan Cascade | 编排框架 | (+) | 将大型项目拆分为并行任务，并提供明确的质量门和多供应商执行能力 | 产品成熟度不一：插件稳定，桌面端处于 alpha，CLI 仍在开发 |
| Skill Scanner | 安全工具 | (+) | 支持多引擎检测智能体技能，并集成 SARIF 和 GitHub Code Scanning | README 明确说明它仅是尽力而为，仍需人工审查 |
| Anthropic Skilljar 课程 | 培训 | (+) | 为 Claude 桌面端、Claude Code、MCP 和子智能体提供结构化学习内容 | 适合入门，但无法消除运行时协调和治理问题 |

总体模式是组合，而非替代。[@parmardarshil07](https://x.com/parmardarshil07) [描述道](https://x.com/parmardarshil07/status/2073310019102367849)（23 个赞、2 条回复、1,321 次浏览、19 次收藏）展示了一套基于角色的数据工程技术栈：Copilot 编写常规代码，Claude 负责架构和调试，Cursor 或 Codex 则按需使用。[@Hyde_ai3](https://x.com/Hyde_ai3) [将其视为](https://x.com/Hyde_ai3/status/2073151028237922659)（30 个赞、2 条回复、277 次浏览）将 Claude、Opus、Sonnet 和 Codex 分配为同一工作流中的不同角色；[@HeyAnjula](https://x.com/HeyAnjula) [展示了](https://x.com/HeyAnjula/status/2073274764572180913)（28 个赞、10 条回复、508 次浏览、4 次收藏）则显示，同样的角色划分正在成为官方插件能力。常见的变通方式，是围绕模型增加结构：用自定义智能体处理重复性终端工作，用 Foundry 处理计费和配额，用预热插件解决本地运行时问题，并在部署前执行安全检查。

## 7. 机会所在

**[+++] 面向编程智能体的使用状态与路由控制平面** —— 第 1、2、3 节提供了相关证据：重置面板、Azure credits 路由、多模型故障回退技术栈，以及反复出现的限制不透明问题。一款能够显示当前通道、重置时间、回退行为和剩余可运行时长，同时无需用户依赖变通方案的产品，看起来尤其有潜力。

**[++] 默认安全的交付流程与智能体技能溯源** —— dashboardlim 检查清单、Skill Scanner 和 ODIN 攻击链都指向同一个缺口：生成式应用和导入的智能体资产仍需要单独进行安全检查。这一机会的潜力中等偏强，因为检查清单和扫描器已经存在，但原生集成仍然缺失。

**[++] 具备明确记忆和进度边界的工作单元编排** —— 官方 Codex 插件、GitHub 自定义智能体，以及要求提供负责人/范围/日志/审查者元数据的回复，都显示出对更好委派界面的明确需求。机会程度中等，因为许多团队已经在自行拼装这类方案，但工作流对象本身仍未得到充分建设。

**[+] 围绕本地或云端智能体工作区的协作与运行时衔接层** —— Gitterm、`lmstudio-warm` 和 OpenCode 工作流帖子表明，围绕会话共享、端口暴露和本地模型就绪状态，正在出现一层新的需求。这一方向仍处于早期，但痛点已经具体到值得持续关注。

## 8. 要点总结

1. **智能体编排正在成为可版本控制的工作流层，而不再只是高级用户的私下技巧。** GitHub 发布了由仓库定义的自定义智能体，OpenAI 的 Codex 插件则将 Claude 到 Codex 的委派变成了具名命令，而不是临时复制粘贴。（[来源](https://x.com/github/status/2073492041326088701)）
2. **配额和重置可见性对用户行为的影响，仍然不亚于模型质量。** 当天最强的成本信号不是基准测试图表，而是重置界面、Azure credits 路由，以及为防止工作在会话中途停止而设计的多模型故障回退。（[来源](https://x.com/Ananth7e/status/2073452226488803634)）
3. **安全已经成为日常 AI 编程工作流的一部分。** 信息流中出现了具体的部署前安全检查、技能供应链扫描器和 Antigravity 攻击研究报告，全部指向运营层面的加固，而不是抽象的安全讨论。（[来源](https://x.com/dashboardlim/status/2073165300258718109)）
4. **构建者正在为智能体增加基础设施，而不是等待一个完美模型出现。** Plan Cascade、Skill Scanner、`lmstudio-warm` 和 Gitterm 的存在，都是因为拆解、审查、预热和共享仍然是彼此独立的产品问题。（[来源](https://x.com/tom_doerr/status/2073468801476178076)）
5. **面向角色的技术栈正在成为常态。** 一名数据工程师公开展示的技术栈，以及 Hyde 明确划分的 Fable/Opus/Sonnet/Codex 角色，都表明人们正越来越多地将不同助手分配给工作的不同阶段。（[来源](https://x.com/parmardarshil07/status/2073310019102367849)）
