# Twitter AI 编程 - 2026-07-07

## 1. 大家在讨论什么

### 1.1 Antigravity 正从演示型新奇工具转向 agent 基础设施（🡕）

今天围绕 Antigravity 的讨论不只是更热，而是明显扩散。当天的话题既有 Google 自家的产品证明，也有教程帖、个人项目和基础设施解读；在当天的帖子中，`antigravity` 提及数从 7 月 6 日的 16 次升至 23 次，`notebooklm` 则从 1 次升至 5 次。人们不再只是把 Gemini 当作聊天端点，而是越来越多地把 Antigravity 视为一个面向研究任务、个人项目和托管 agents 的自然语言前端。

[@GoogleDeepMind](https://x.com/GoogleDeepMind) [发布了](https://x.com/GoogleDeepMind/status/2074513661750546762)（339 次点赞，24 条回复，36,422 次浏览，92 次收藏）展示了一个名为“预测过去”的 Antigravity 技能，将 Gemini 定位为 Aeneas 和 Ithaca 的自然语言接口，用于研究希腊语和拉丁语文本。

[@rahulbais136](https://x.com/rahulbais136) [表示](https://x.com/rahulbais136/status/2074457760427811013)（70 次点赞，13 条回复，708 次浏览，15 次收藏）指出，NotebookLM 加 Google Antigravity 是一个被低估的组合，并把这个说法做成了一份两分钟上手指南；这比泛泛的吹捧更能说明真实采用信号。[@shashwth](https://x.com/shashwth) [补充说](https://x.com/shashwth/status/2074219996381585493)（54 次点赞，5 条回复，5,776 次浏览，17 次收藏）则给出了一个具体的开发者案例：用 Gemini 加 Antigravity 为 2008 年的 PSP 制作定制音乐软件。

[@rohanpaul_ai](https://x.com/rohanpaul_ai) [解释了](https://x.com/rohanpaul_ai/status/2074559295660978521)（18 次点赞，2 条回复，2,296 次浏览，7 次收藏）解释了 Managed Agents 在运营层面为何重要：后台任务、远程 MCP、函数调用、凭证刷新、免费层访问，以及由 Google 托管、能在长任务中保留交互状态的 Linux 沙箱。

**讨论洞察：** 最有支撑力的帖子并不是“Gemini 更聪明了”，而是围绕上手指南、MCP 接入和长时任务的工作流帖子。这说明关注点正从 prompt 新鲜感转向运营框架。

**与前一天对比：** 7 月 6 日，Antigravity 已出现在认证和路由相关讨论中。到了 7 月 7 日，官方产品证据和更多开发者/教程用例加入进来，叙事也从访问问题上移到了基础设施和使用场景这一更高层级。

### 1.2 “控制中心”层成了应对“agent 太多、状态太杂”的默认答案（🡕）

第二个话题簇把编排本身当成产品来做。当天多条帖子都出现了“control center”“mission control”和多 agent 仪表盘这类明确表述，`mission control` 的提及数也环比从 0 升至 2。核心模式不是再做一个单 agent IDE，而是围绕多个后端、多个会话和不同 agent 品牌，提供持续性的统一监管。

[@nyk_builderz](https://x.com/nyk_builderz) [宣布](https://x.com/nyk_builderz/status/2074371723479363727)（16 次点赞，5 条回复，744 次浏览，16 次收藏）发布了 Mission Control v2.1.0，而公开的 [代码库](https://github.com/builderz-labs/mission-control) 和 [网站](https://mc.builderz.dev) 证实了这次发布并非空喊口号：这是一个自托管的 TypeScript/SQLite 仪表盘，支持任务分发、成本监控、RBAC、skills、安全面板，以及 Claude Code 桥接。

[@GithubProjects](https://x.com/GithubProjects) [推出了](https://x.com/GithubProjects/status/2074380404610748765)（1 次点赞，2,243 次浏览，5 次收藏）提到 [OpenHands Agent Canvas](https://github.com/OpenHands/agent-canvas)，其 README 将其描述为一个自托管控制中心，可在本地、Docker、VM 和云后端上运行 OpenHands、Claude Code、Codex、Gemini 或任意兼容 ACP 的 agent，并且不丢失上下文。

![OpenHands Agent Canvas 仪表板，展示了一个用于运行和监管多个编程代理的自托管控制中心](https://pbs.twimg.com/media/HMmt_AYa8AAjOJ6.jpg)

[@omnigent_ai](https://x.com/omnigent_ai) [已发布](https://x.com/omnigent_ai/status/2074293660603052248)（9 次点赞，433 次浏览，2 次收藏）提到带有 harness 插件 SDK 和逐轮路由器的 Omnigent v0.4.0，而 [代码库](https://github.com/omnigent-ai/omnigent) 则支撑了一个更广泛的主张：会话可以跨终端、网页、手机、托管沙箱和策略层延续。[@tom_doerr](https://x.com/tom_doerr) [提到](https://x.com/tom_doerr/status/2074464448115290143)（10 次点赞，3,454 次浏览，15 次收藏）提到 [oh-my-githubcopilot](https://github.com/jmstar85/oh-my-githubcopilot)，其 README 宣称在 Copilot 之上叠加了 28 个 agents、37 个 skills、有状态工作流和 hooks。

**讨论洞察：** 这些发布背后的共同抱怨，不是模型智能不够，而是在同时存在多个 agents 或多个会话时，缺少监管、审批、成本可见性和上下文连续性。

**与前一天对比：** 7 月 6 日，围绕 Omnigent 和工作流壳层的 meta-harness 讨论已经出现。到了 7 月 7 日，仪表盘和控制室式的叙事变得更明确，也更公开。

### 1.4 验证、限制与治理被视为核心产品工作，而不是收尾清理（🡕）

## 2. 什么让大家感到挫败

### 上下文丢失和隐藏配置状态，依然让 agents 像一次性用品

严重程度：高。[@anupamrjp](https://x.com/anupamrjp) [总结道](https://x.com/anupamrjp/status/2074489915103199567)（14 次点赞，5 条回复，250 次浏览）表示，vibe coding 最糟糕的部分，是每次打开新聊天都得先把“整个大脑重新下载”进 IDE，才能开始写第一行代码。[@Kacper95682155](https://x.com/Kacper95682155) [展示了](https://x.com/Kacper95682155/status/2074439943087096053)（6 条回复）则展示了另一端的应对方式：他的 Claude Code 配置大多全局放在 `~/.claude/` 中，而他的回复解释说，一个全局的 `CLAUDE.md`、21 个 skills 和多个 standards 文件，再与项目本地文件组合使用。对重度用户来说这有帮助，但也恰恰证明了问题所在：关键行为往往存在于 repo 之外，也不在共享审查范围内。这个方向值得投入，因为持久、可迁移的上下文，今天仍主要靠 dotfiles 和监管层来拼凑。

### 限额、配额和多提供商切换不断打断正在进行的工作

严重程度：高。[@Jason_Young1231](https://x.com/Jason_Young1231) [更新了](https://x.com/Jason_Young1231/status/2074304513029149121)（48 次点赞，11 条回复，9,727 次浏览，7 次收藏）提到 CC Switch，因为人们希望能跨 Claude Code、Codex、Gemini、Kimi 和 Copilot 实时跟踪使用量并检查余额。[@DataScienceDojo](https://x.com/DataScienceDojo) [主推](https://x.com/DataScienceDojo/status/2074496156432789669)（2 次点赞，1 条回复，823 次浏览，1 次收藏）则围绕同样的痛点提到 9Router：一旦某个提供商触顶，当前会话应该继续，而不是在重构中途死掉。[@0x_sakata](https://x.com/0x_sakata) [分享了](https://x.com/0x_sakata/status/2074496669278773397)（15 次点赞，12 条回复，316 次浏览，4 次收藏）提供了一个包含 40 多个免费提供商 key 页面目录的变通方案，用来缓解额度和速率限制摩擦，而 GitHub 的 [官方更新日志](https://github.blog/changelog/2026-06-23-github-copilot-app-support-for-byok/) 则表明 BYOK 正在 Copilot 应用内部被常态化。这个方向值得投入，因为在限额条件下保持连续性，已经是一项一等产品需求。

### 审查与评估仍然无法支撑 agents 鼓励的工作规模

严重程度：高。[@awakecoding](https://x.com/awakecoding) [展示了](https://x.com/awakecoding/status/2074235982346330266)（5 次点赞，3 条回复，492 次浏览）提到 GitHub Copilot 拒绝审查一个 pull request，因为 diff 超过了 20,000 行变更。[@lgrammel](https://x.com/lgrammel) [提问](https://x.com/lgrammel/status/2074401071041044716)（20 次点赞，6 条回复，4,717 次浏览，8 次收藏）则提出了更尖锐的战略问题：到底有什么证据表明，预构建 harness 相比开放式或自定义 harness 真的更好？作为回应，当天到处都是试图弥合这一缺口的尝试——[@businessbarista](https://x.com/businessbarista) [介绍](https://x.com/businessbarista/status/2074304413263409380) 可重放验证闭环，[LLM as a Verifier](https://llm-as-a-verifier.com) 提供更好的轨迹评分，[AEON-BENCH](http://AEON-BENCH.com) 运行多 harness 基准评测——但显然需求仍未被满足。这个方向值得投入，因为长周期的 agent 工作，已经开始超出原本用于约束它的审查界面能力。

![GitHub Copilot 的消息，称其无法审查拉取请求，因为代码差异超过了 20,000 行变更](https://pbs.twimg.com/media/HMkqjJeWoAAZ2jm.png)

### 安全与合规边界依然脆弱

严重程度：高。[@The_Cyber_News](https://x.com/The_Cyber_News) [警告称](https://x.com/The_Cyber_News/status/2074519613623464004)（31 次点赞，3 条回复，3,274 次浏览，4 次收藏）表示，GitLost 可以通过间接 prompt injection 诱使 GitHub Agentic Workflows 泄露私有仓库。[@TechLead187](https://x.com/TechLead187) [表示](https://x.com/TechLead187/status/2074500316813283470)（5 条回复，65 次浏览）则指出，一旦涉及企业合规、数据主权和生产环境发布，当前 agentic IDE 的缺口就会变得“可怕”。即便是那些偏正面的基础设施帖子，也反映了同样的焦虑：[@rohanpaul_ai](https://x.com/rohanpaul_ai) [强调](https://x.com/rohanpaul_ai/status/2074559295660978521) 提到 Managed Agents 的隔离 Linux 沙箱和凭证刷新，而 Mission Control 的 [代码库](https://github.com/builderz-labs/mission-control) 则强调哈希化密钥、角色和安全审查面板。这个方向值得投入，因为企业采用的门槛，正在由信任边界而不是模型热情来决定。

## 3. 大家希望出现什么

### 能跨聊天和仓库持久存在的共享记忆与可迁移标准

人们要的不只是更长的上下文窗口；他们想要的是能撑过下一次交接的上下文。[@anupamrjp](https://x.com/anupamrjp) [描述了](https://x.com/anupamrjp/status/2074489915103199567)（14 次点赞，5 条回复，250 次浏览）提到了每次新聊天都要重新灌入上下文的痛苦，而 [@Kacper95682155](https://x.com/Kacper95682155) [展示了](https://x.com/Kacper95682155/status/2074439943087096053)（6 条回复）则解释了为什么高级用户会转而把 standards 和 skills 放进全局文件。像 [OpenHands Agent Canvas](https://github.com/OpenHands/agent-canvas) 和 [Omnigent](https://github.com/omnigent-ai/omnigent) 这样的 control-center 项目之所以受欢迎，也指向同一个未满足需求：能在后端切换后依然存续的共享、持久状态。机会：直接。

### 原生的使用遥测、BYOK 路由和优雅故障切换

人们一再围绕同一个连续性问题做各种补丁。[@Jason_Young1231](https://x.com/Jason_Young1231) [希望](https://x.com/Jason_Young1231/status/2074304513029149121)（48 次点赞，11 条回复，9,727 次浏览，7 次收藏）提到跨提供商使用追踪；[@DataScienceDojo](https://x.com/DataScienceDojo) [希望](https://x.com/DataScienceDojo/status/2074496156432789669)（2 次点赞，1 条回复，823 次浏览，1 次收藏）提到一个不会直接停掉、而是降级继续运行的路由器；[@0x_sakata](https://x.com/0x_sakata) [希望](https://x.com/0x_sakata/status/2074496669278773397)（15 次点赞，12 条回复，316 次浏览，4 次收藏）给出了一套拼装多个免费备选方案的操作手册；而 GitHub 的 [Copilot 应用的 BYOK 支持](https://github.blog/changelog/2026-06-23-github-copilot-app-support-for-byok/) 则把同样的需求正式化。这个需求不是愿景性的，而是紧迫且现实的。机会：直接。

### 能在长任务下依然可信的审查与评估界面

社区想要的并不只是泛泛的“judge”式说法。[@awakecoding](https://x.com/awakecoding) [展示了](https://x.com/awakecoding/status/2074235982346330266)（5 次点赞，3 条回复，492 次浏览）展示了大规模 diff 下的硬性产品上限，而 [@lgrammel](https://x.com/lgrammel) [提问](https://x.com/lgrammel/status/2074401071041044716)（20 次点赞，6 条回复，4,717 次浏览，8 次收藏）则要求拿出证据，证明 harness 选择确实会改善结果。答案空间正在形成——[@businessbarista](https://x.com/businessbarista) [介绍](https://x.com/businessbarista/status/2074304413263409380)（30 次点赞，4 条回复，5,552 次浏览，76 次收藏）提到可重放验证环境，[LLM as a Verifier](https://llm-as-a-verifier.com) 提到持续评分，[AEON-BENCH](http://AEON-BENCH.com) 提到多 harness 评估——但仍处于早期。机会：直接。

### 面向团队、具备策略感知的 agent 运营层

一旦 agents 开始接触私有仓库、内部 API 或长时任务，人们想要的就是基础设施，而不是 prompts。[@rohanpaul_ai](https://x.com/rohanpaul_ai) [描述了](https://x.com/rohanpaul_ai/status/2074559295660978521)（18 次点赞，2 条回复，2,296 次浏览，7 次收藏）提到 Google 托管的 managed agents，具备沙箱、远程 MCP 和凭证刷新；[@nyk_builderz](https://x.com/nyk_builderz) [已发布](https://x.com/nyk_builderz/status/2074371723479363727)（16 次点赞，5 条回复，744 次浏览，16 次收藏）提到围绕任务分发、角色和成本治理的 Mission Control；[@The_Cyber_News](https://x.com/The_Cyber_News) [提及了](https://x.com/The_Cyber_News/status/2074519613623464004)（31 次点赞，3 条回复，3,274 次浏览，4 次收藏）则用 GitLost 提醒大家，prompt-injection 风险已经是具体且现实的。现在已有多个早期答案，但还没有明显的标准。机会：竞争型。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪倾向 | 优势 | 局限 |
|---|---|---|---|---|
| Google Antigravity / Managed Agents | Agent 平台 | (+) | 自然语言技能、后台任务、远程 MCP、隔离 Linux 沙箱 | 仍然很新；今天的实践认知主要来自解读和上手指南 |
| NotebookLM + Antigravity | 研究工作流 | (+) | 可快速把笔记和资料转成引导式研究或构建工作流 | 更像前端与综合层，而不是完整编码环境 |
| GitHub Copilot app | 桌面编码助手 | (+/-) | 覆盖所有套餐、支持 BYOK、扩展面不断增长 | Business 和 Enterprise 需要管理员策略；今天仍暴露出大 diff 审查限制 |
| CC Switch | 使用量仪表盘 | (+) | 可跨主流 coding agents 跟踪使用量和余额 | 又增加了一层用户必须维护的覆盖工具 |
| 9Router | 本地路由代理 | (+/-) | 单一端点、配额感知回退、token 压缩、广泛的提供商覆盖 | 增加了一层转换层，且回退后的质量仍是开放问题 |
| ask-search | 自托管搜索技能 | (+) | 通过 SearxNG 为 Claude Code、Antigravity 和 shell 流程提供免费且私密的网页搜索 | 需要自托管 SearxNG，并有一定部署成本 |
| Codex MCP Server | 跨 agent 桥接 | (+) | 让 Claude Code 可调用 Codex 做审查、分析和网页搜索 | 依赖 Codex CLI 配置和外部提供商访问 |
| MCP Unity | 编辑器桥接 | (+) | 将 scenes、assets、logs、packages 和 tests 暴露为 agent 可调用工具 | Unity 专属工作流，且存在配置开销 |
| JVM Pulse | 运行时遥测扩展 | (+) | 把 GC 和 JFR 数据转成 Copilot 可读仪表盘与 AI 调优闭环 | 仅适用于 Java，且仍处于预览阶段 |
| Mission Control | 编排仪表盘 | (+) | 任务分发、成本追踪、RBAC、安全面板和 Claude Code 桥接 | Alpha 软件，自托管成本较高 |
| OpenHands Agent Canvas | 控制中心 | (+) | 可在本地、Docker、VM 和云后端上运行混合 agents 而不丢失上下文 | 早期自托管项目，需自行承担安全加固负担 |
| Omnigent | Meta-harness | (+) | 逐轮 harness 与模型路由、跨设备会话、策略控制 | 工具链较重，依赖多个本地和沙箱组件 |

没有任何单一厂商主导满意度曲线。最明显的模式是分层：人们保留自己偏爱的 agent，然后在外围加上 BYOK、本地代理、自托管搜索、全局标准文件，或一个控制平面。迁移压力看起来不太像“从工具 A 切换到工具 B”，而更像“保留工具 A，但外挂 9Router、ask-search、Codex MCP、CC Switch 或 Mission Control，让工作流不再频繁断裂”。

最强的构建模式不是“新基础模型”，而是“新控制平面”。Mission Control、OpenHands Agent Canvas、Omnigent 和 oh-my-githubcopilot 都是在现有 agents 外包一层路由、持久化、审批或共享状态，这表明开发者认为真正的瓶颈在于协调和监管，而不是替换底层模型。

第二个模式是轻量适配器：它们修补缺失能力，但不要求用户放弃现有工具链。9Router 增加了配额感知回退，ask-search 增加了自托管网页检索，Codex MCP 让 Claude 能调用 Codex，而 last30days 则把跨平台研究做成了可复用技能。

第三个模式是领域暴露。MCP Unity 和 JVM Pulse 把 scene graphs 与运行时遥测暴露为一等 agent 上下文，而 [@alex_barashkov](https://x.com/alex_barashkov) [展示了](https://x.com/alex_barashkov/status/2074492797260870072)（76 次点赞，7 条回复，1,738 次浏览，44 次收藏）提到 Toolcraft 可通过网页 UI 驱动真实的 Blender 渲染，支持 Eevee 预览和 Cycles 最终输出。这将“AI 编程”的边界从文件编辑扩展到了对外部创作系统和运行时系统的操作控制。

## 6. 新动态与值得关注的事

### GitHub Copilot app 已覆盖所有套餐
官方的 [7 月 7 日更新日志](https://github.blog/changelog/2026-07-07-github-copilot-app-available-to-all/) 明确宣布了这一扩展：这款桌面应用现在支持 macOS、Windows 和 Linux 上的 Free、Education、Business 与 Enterprise 用户，而更早的 [BYOK 更新日志](https://github.blog/changelog/2026-06-23-github-copilot-app-support-for-byok/) 则继续为外部提供商保留空间。这个组合很重要，因为它一方面扩大了低端采用面，另一方面也仍支持高端场景所需的企业路由和策略控制。

### Managed agents 开始更像基础设施，而不是功能演示
[@rohanpaul_ai](https://x.com/rohanpaul_ai) [描述了](https://x.com/rohanpaul_ai/status/2074559295660978521)（18 次点赞，2 条回复，2,296 次浏览，7 次收藏）把 Managed Agents 描述为由 Google 托管、具备交互状态、远程 MCP、凭证刷新和沙箱执行能力的 workers。再结合 [@GoogleDeepMind](https://x.com/GoogleDeepMind) [展示](https://x.com/GoogleDeepMind/status/2074513661750546762)（339 次点赞，24 条回复，36,422 次浏览，92 次收藏）所展示的、建立在专用模型之上的 Antigravity 技能，释放出的信号是：Google 希望 Antigravity 被看作执行层和技能入口，而不只是聊天 UI。

### GitLost 让 prompt-injection 风险重新回到头版
[@The_Cyber_News](https://x.com/The_Cyber_News) [报道了](https://x.com/The_Cyber_News/status/2074519613623464004)（31 次点赞，3 条回复，3,274 次浏览，4 次收藏）指出，单个 GitHub Issue 就可能被用来诱使 Agentic Workflows 泄露私有仓库内容。即使不看全文，公开摘要本身也已经足够具体，足以成为所有把 agents 接入仓库自动化的人都该关注的一则警告。

### 验证从理论走向了公开产物
当天出现了几个针对“拿证据出来看”问题的不同回答：[LLM as a Verifier](https://llm-as-a-verifier.com) 对应更细粒度的评分，[AEON-BENCH](http://AEON-BENCH.com) 对应多 harness 基准测试，还有关于 harness engineering 与控制机制的公开课程材料。这样的组合让验证看起来更像一场生态竞赛，而不再只是单一研究线索。

## 7. 机会在哪里

** 持久共享记忆与可迁移标准——[+++] Durable supervisor layer across chats, tools, and agents** - The strongest repeated pain was state loss and fragmented configuration, from [@anupamrjp](https://x.com/anupamrjp) [描述每次聊天都需要重新加载上下文的必要性](https://x.com/anupamrjp/status/2074489915103199567) 到 [@Kacper95682155](https://x.com/Kacper95682155) [将关键行为保存在全局文件中](https://x.com/Kacper95682155/status/2074439943087096053)，而 Mission Control、OpenHands Agent Canvas 和 Omnigent 也都围绕同一个缺口构建。

**[+++] 原生的成本与配额连续性** - CC Switch、9Router、免费提供商目录和 Copilot BYOK 之所以存在，是因为人们仍在为限额、计费边界和提供商切换损失生产时间。一个把可见性、路由和优雅回退结合在一起的第一方答案，将能解决一个日常阻塞问题。

**[++] 能撑住大 diff 和长周期运行的验证** - Copilot 的 20,000 行审查上限、外界对 harness 证据的公开质疑、持续学习讨论以及新的基准测试产物，都指向同一个切入口：当 agent 的任务范围变大后，审查与评估工具仍需保持可用。

**[++] 面向企业 agent 自动化的策略与信任边界** - GitLost、企业合规抱怨、managed-agent 沙箱化，以及带 RBAC 的编排仪表盘，都显示出市场需要的是围绕 agent 工作流的安全运营层，而不只是更好的 prompts。

**[+] 通往更丰富运行时与创意系统的领域桥接** - MCP Unity、JVM Pulse，以及 Toolcraft 的 Blender 工作流，都表明把 scene graphs、遥测和外部工具暴露为一等 agent 上下文，是一个较小但真实存在的机会。

## 8. 要点总结

1. **Antigravity 正在向更高层栈位移动。** 官方产品证据、教程帖、个人项目和 Managed Agents，都把它框定为工作流基础设施，而不是一次性的模型演示。（[GoogleDeepMind](https://x.com/GoogleDeepMind/status/2074513661750546762), [rahulbais136](https://x.com/rahulbais136/status/2074457760427811013), [rohanpaul_ai](https://x.com/rohanpaul_ai/status/2074559295660978521)）
2. **主要的构建模式是“为现有 agents 加一个控制平面”。** Mission Control、OpenHands Agent Canvas、Omnigent 和 oh-my-githubcopilot 都是在现有 agents 外围增加监管、路由、策略或持久状态，而不是试图替换基础模型。（[nyk_builderz](https://x.com/nyk_builderz/status/2074371723479363727), [GithubProjects](https://x.com/GithubProjects/status/2074380404610748765), [omnigent_ai](https://x.com/omnigent_ai/status/2074293660603052248), [tom_doerr](https://x.com/tom_doerr/status/2074464448115290143)）
3. **Copilot 变得更广，而不只是更强。** 全套餐桌面版发布、BYOK 支持、Visual Studio 培训更新、JVM Pulse、Unity MCP 和 Codex bridges，都在扩展 Copilot 的可用表面。（[GHchangelog](https://x.com/GHchangelog/status/2074520080927347029), [GitHub 更新日志](https://github.blog/changelog/2026-07-07-github-copilot-app-available-to-all/), [JamesMontemagno](https://x.com/JamesMontemagno/status/2074264332045893789), [brunoborges](https://x.com/brunoborges/status/2074205616768270751)）
4. **限额下的连续性仍未解决。** 使用量仪表盘、回退代理和免费提供商操作手册之所以兴盛，是因为会话中途因配额失败而中断，仍然常见到足以催生产品。（[Jason_Young1231](https://x.com/Jason_Young1231/status/2074304513029149121), [DataScienceDojo](https://x.com/DataScienceDojo/status/2074496156432789669), [0x_sakata](https://x.com/0x_sakata/status/2074496669278773397)）
5. **验证与安全如今已是一等需求。** 大 diff 审查上限、公众对更好证据的要求、新的 verifier 与 benchmark 产物，以及 GitLost，都说明可信运行与生成能力同样重要。（[awakecoding](https://x.com/awakecoding/status/2074235982346330266), [lgrammel](https://x.com/lgrammel/status/2074401071041044716), [LLM as a Verifier](https://llm-as-a-verifier.com), [AEON-BENCH](http://AEON-BENCH.com), [The_Cyber_News](https://x.com/The_Cyber_News/status/2074519613623464004)）
