# Twitter AI 编程 - 2026-11-09

## 1. 大家在讨论什么

### 1.1 将规划和审查拆分为不同的智能体任务 (↗)

最明确的流程信号是：先制定计划或规格说明，再开始实现；随后交由没有参与起草对话的审查者检查。Google 开源的 Elephant-Goldfish Model (EGM) 会为起草智能体提供完整的项目上下文，为审查者提供全新的上下文；开发者负责权衡取舍并批准设计。当日的帖子也展示了不同做法：一位开发者把任务拆小并手动审查代码差异，另一位则介绍了多模型审查流程。

[@oliviscusAI](https://x.com/oliviscusAI) [介绍了](https://x.com/oliviscusAI/status/2119745987744772191)（44 个赞、20 条回复、2,483 次浏览）介绍了 EGM 的两种角色，并链接到 [公开代码仓库](https://github.com/google/elephant-goldfish-model)。文档指出，新的子智能体会审查草稿和参考材料；人工审批和测试仍不可或缺。

[@johan_builds](https://x.com/johan_builds) [图示了](https://x.com/johan_builds/status/2119528808890134625)（4 个赞、3 条回复、152 次浏览）说明了三种角色之间的分工：Elephant 在掌握项目上下文的情况下起草，Goldfish 审查者能看到草稿但看不到聊天记录，开发者则在编写代码前批准设计。图片清楚展示了这种分工：

![EGM 工作流卡片：由 Elephant 基于上下文制定计划，再由 Goldfish 在全新上下文中进行审查](https://pbs.twimg.com/media/HWoUGwQbMAAxLOh.jpg)
![EGM 的角色：基于项目上下文起草、在全新上下文中审查，以及由开发者批准](https://pbs.twimg.com/media/HWoUGwQaMAAMmxZ.jpg)

[@esrtweet](https://x.com/esrtweet) [介绍了](https://x.com/esrtweet/status/2119843690403242404)（189 个赞、21 条回复、4,529 次浏览）展示了更简单的人工监督方案：在终端中使用 Codex，把任务拆小，以本地 Qwen 作为备用，并在提交前手动审查代码差异。相比之下，[@kevintheo](https://x.com/kevintheo) [报告了](https://x.com/kevintheo/status/2119786737366917286)（1 个赞、3 条回复、118 次浏览）介绍了由四个模型进行 418 轮代码审查、再由 Claude 尝试复现每条发现的流程。作者表示，没有人核查判定结果，而且日志无法统计四位审查者共同漏掉的缺陷，因此这些只是个人工作流数据，并非模型基准测试。

![四位代码审查员自报的已确认提示数量，并附有作者关于未经人工核查的说明](https://pbs.twimg.com/media/HWr-tqhWQAA961Z.jpg)

**讨论要点：** EGM 帖子的回复质疑最终是否仍由人来批准成果。该仓库说明，架构决策由开发者负责，审查也不能取代测试或人的判断。

**与前一天的对比：** Google 在 11 月 8 日发布的 EGM 公告已经备受关注。次日的讨论则补充了实例，展示如何将全新上下文审查与个人审查习惯和模型集成流程结合起来。此外，还有一则介绍该插件的帖子：[@GoogleCloudTech](https://x.com/GoogleCloudTech) [宣布了](https://x.com/GoogleCloudTech/status/2119203243054023129)（426 个赞、22 条回复、23,738 次浏览）。

### 1.2 智能体正跨设备、模式和界面运行 (↗)

多项独立公告都聚焦于智能体的运行位置，以及人们如何恢复任务或引导智能体。[@_samirism](https://x.com/_samirism) [报告了](https://x.com/_samirism/status/2119884573190545726)（376 个赞、71 条回复、13,984 次浏览）宣布，用户可以将多台电脑连接到桌面版 Codex 的“dot”。Google 宣布推出语音驱动编程，以及可在隔离的云环境中构建、测试并准备拉取请求的远程智能体。GitHub Copilot 应用的会话接续功能可将任务、计划、对话和代码更改带入 VS Code。Antigravity 还推出了研究与写作布局，在保留其智能体运行框架、插件和 MCP 工具的同时，去除了终端和 Git 带来的界面干扰。

[@googledevs](https://x.com/googledevs) [推出了](https://x.com/googledevs/status/2119872720234070434)（107 个赞、9 条回复、10,125 次浏览）介绍了 Antigravity 语音模式，可用于结对编程、创建文件，以及在任务进行中提出新要求。[@googledevs](https://x.com/googledevs) [宣布了](https://x.com/googledevs/status/2119920469646225890)介绍了笔记本电脑合上后仍会继续工作的远程智能体（11 个赞、2 条回复、2,436 次浏览）。 [@antigravity](https://x.com/antigravity) [宣布了](https://x.com/antigravity/status/2119913586109579283) 知识工作布局（489 个赞、30 条回复、15,094 次浏览）；有人在回复中批评称，相比新界面，能否使用模型更重要。

[@github](https://x.com/github) [展示了](https://x.com/github/status/2119529896296722931) 如何在 VS Code 中继续 Copilot 应用会话，同时保留任务、计划、对话和更改（96 个赞、30 条回复、21,257 次浏览）。

**讨论要点：** 多台电脑功能的公告下，有人要求在批准前标明目标机器，也有人反映沙盒导致浏览器控制和上下文保留方面的问题。关于 Copilot 会话的回复还指出，重试机制让人难以看出问题出在哪里。这些讨论表明，除了保持连续性，用户也需要控制能力和可观测性。（[@_samirism](https://x.com/_samirism) [讨论串](https://x.com/_samirism/status/2119884573190545726)，376 个赞、71 条回复、13,984 次浏览；[@github](https://x.com/github) [讨论串](https://x.com/github/status/2119529896296722931)，96 个赞、30 条回复、21,257 次浏览。）

**与前一日对比：** Copilot 应用会话接续的话题在 11 月 8 日就已开始讨论；11 月 9 日的记录显示，同一条帖文仍在持续获得回复和浏览量，并非有新功能发布。

### 1.3 本地推理与持久化执行解决的是不同限制 (↗)

本地推理方案通过 GitHub Copilot 使用 Foundry Local 运行 Qwen3.8-27B。Microsoft 的 [文章](https://devblogs.microsoft.com/foundry/foundry-local-agentic-coding-qwen3-8-27b/) 介绍了一种混合工作流：日常工作留在本地处理，较难的问题则交给云端。公布的配置说明称，4 位量化权重约占 18 GB；配备 24 GB 显存的 NVIDIA GPU 支持最高 64K 上下文，显存达到 32 GB 或以上时，最高可支持 262K。文中列出的硬件和模型要求表明，这只是一个特定方案，并非通用的桌面配置基准。

[@arcbang_xyz](https://x.com/arcbang_xyz) [总结了](https://x.com/arcbang_xyz/status/2119588871747096826) 配置说明（2 个赞、3 条回复、109 次浏览）。这张图是作者绘制的示意图，并非 Microsoft 的基准测试结果或产品截图：

Cloudflare 的 [实验性的 Codex 执行框架示例](https://developers.cloudflare.com/changelog/post/2026-11-09-codex-harness/) 采用了另一种方案：在 Durable Object 中持久化会话、文件、流以及已完成的工具或模型结果，使智能体在中断后能够恢复。文档特别说明，这只是使用内部 SDK API 的示例代码，并非完整的 Codex CLI 运行框架。[@mattzcarey](https://x.com/mattzcarey) [分享了](https://x.com/mattzcarey/status/2119858443695853976) 公告截图（3 个赞、1 条回复、370 次浏览）。

## 2. 人们感到困扰的问题

### 任务耗时越长，可靠性越低

** 严重程度：中，依据个别用户反馈。** 一位 Antigravity 用户称，长时间运行的任务会随机报错，需要反复提醒才能继续，执行速度也会越来越慢。另一条涉及多台电脑的 Codex 讨论中，有用户反映智能体在 Windows 沙盒中的浏览器控制会失败，也有人说它在长时间对话中会忘记指令。（[@vipinxtwt](https://x.com/vipinxtwt) [报告了](https://x.com/vipinxtwt/status/2119754376696955210)：26 个赞、9 条回复、2,370 次浏览；[@_samirism](https://x.com/_samirism) [讨论串](https://x.com/_samirism/status/2119884573190545726)：376 个赞、71 条回复、13,984 次浏览。）还有一位用户称，让三个助手同时处理一个代码仓库反而拖慢了进度，但没有提供详细分析，因此这仍只是个例。（[@jsmahay](https://x.com/jsmahay) [报告了](https://x.com/jsmahay/status/2119539038533345322)：4 条回复、30 次浏览。）

用户通常会把任务拆小，并自行审查差异；[@esrtweet](https://x.com/esrtweet) [介绍了](https://x.com/esrtweet/status/2119843690403242404) 也提到了这种做法（189 个赞、21 条回复、4,529 次浏览）。Cloudflare 和 Antigravity 的案例中都出现了持久会话和后台执行，但这些帖子并未证明它们能解决所报告的质量问题或上下文丢失问题。对于长时间任务常见的场景，这类能力值得开发；现有证据表明，用户确实需要任务恢复能力和清晰可见的任务状态，但无法据此估算这类问题的普遍程度。

### 订阅额度难以规划

** 严重程度：中。** 一位用户称，发了五六条简单消息就用完了 Gemini Argon 的五小时额度，编程 20-30 分钟则用掉了每周额度的约三分之一；相比之下，他们更偏好其他服务商，因为其模型更强，或服务使用起来更方便。 ([@jan_volad](https://x.com/jan_volad) [比较了各项计划](https://x.com/jan_volad/status/2119513284399223188)：20 个赞、9 条回复、1,660 次浏览。）另一位开发者将 ChatGPT Plus、OpenCode Go 和 Claude Pro 分别视为适用于通用工作、低成本推理以及编码规划与审查的不同选择，而非可以直接互相替代的产品。（[@yuhasbeentaken](https://x.com/yuhasbeentaken) [比较了这些产品](https://x.com/yuhasbeentaken/status/2119721665898647898)：6 个赞、2 条回复、848 次浏览。）

这些只是个人经历，不能代表平均配额或性价比。但这些反馈说明，用户比较的不只是订阅价格，也会关注实际能完成多少任务。更可预测的按模型用量和更清晰的套餐边界值得探索，不过目前的证据仅来自少数帖子。

### 评审积压可能超出维护者的处理能力

**严重程度：中等（就文中所述团队而言）；普遍程度尚不明确。** [@dani_avila7](https://x.com/dani_avila7) [报告了](https://x.com/dani_avila7/status/2119616979229171986)提到，一个贡献者近 200 人的项目有 350 多个拉取请求等待评审（3 个赞、3 条回复、373 次浏览）。有回复提议构建一个分流代理，但没有提供实测结果或后续进展。这是维护者面临的具体问题，也为评审分流工具提供了一个可行的细分场景，前提是审批仍由人负责。

## 3. 人们希望出现什么

### 便于评审、带有团队专属约束的计划

**需求：**一种能学习代码库规范、在修改文件前先提出计划，并由人负责架构决策和审批的编码代理。GitHub Dev Days 的一位演讲者介绍了如何将常驻指令、按需调用的技能和专用代理分层组合；EGM 则提供了公开的规划与评审工作流。（[@nisalrenuja](https://x.com/nisalrenuja) [概述了各层](https://x.com/nisalrenuja/status/2119491264014135433)：12 个赞、4 条回复、294 次浏览；[EGM 仓库](https://github.com/google/elephant-goldfish-model)。）

从现有证据来看，这是一项实际需求，紧迫性为**中等**：它体现在具体工作流中，而不是以广泛诉求的形式明确提出。现有工具已能部分满足这一需求，但 EGM 的文档仍将权衡取舍和审批交由开发者负责。**机会：直接。**

### 状态透明、可恢复且支持设备级控制的工作

**需求：**当代理在不同设备间切换或在后台继续工作时，用户希望了解发生了什么、恢复上下文，并知道审批会影响哪台机器。针对 [@_samirism](https://x.com/_samirism) 的 [多计算机帖子](https://x.com/_samirism/status/2119884573190545726)，回复中特别要求在审批前标明目标计算机（376 个赞、71 条回复、13,984 次浏览）；针对 [@github](https://x.com/github) 的 [Copilot 交接帖子](https://x.com/github/status/2119529896296722931)，有回复称，重试行为掩盖了出错原因（96 个赞、30 条回复、21,257 次浏览）。

这是一项实际需求， **中等紧迫性**需求。会话交接、远程代理和 Cloudflare 的实验性持久化方案都是部分解决办法，但这些讨论表明，仅有连续性并不能让故障清晰可见，也不能确保控制权明确。**机会：直接。**

### 模型用量可预测，套餐边界清晰

**需求：**限额明确、可用容量充足，并与用户付费使用的模型和任务相匹配。一位订阅用户反映配额消耗很快；另一位则表示，最佳选择取决于用户需要的是通用辅助、成本更低的代码推理，还是更强的规划或审查能力。（[@jan_volad](https://x.com/jan_volad) [据报道](https://x.com/jan_volad/status/2119513284399223188)：20 个赞，9 条回复，1,660 次浏览；[@yuhasbeentaken](https://x.com/yuhasbeentaken) [对比方案](https://x.com/yuhasbeentaken/status/2119721665898647898)：6 个赞，2 条回复，848 次浏览。）

对于重度用户来说，这是一个切实存在的、**中等紧迫性**需求，但样本量较小，相关报告也仅反映个别账户的情况。本地运行 Qwen 推理，以及明确选择模型和提供商，都是不完全的替代方案，但可能需要 GPU，或需要在质量上作出取舍。**机会：竞争性。**

## 7. 机会在哪里

**[+++] Human-approved plans and review gates** — EGM separates project-context drafting from fresh-context review, while a GitHub Dev Days speaker describes repo instructions, task-specific skills, and narrow agents; another practitioner keeps tasks small and reviews diffs before commits. These are multiple concrete approaches to making agent output auditable without handing off final judgment. ([@GoogleCloudTech](https://x.com/GoogleCloudTech) [宣布 EGM](https://x.com/GoogleCloudTech/status/2119203243054023129)，426 次点赞、22 条回复、23,738 次浏览；[@nisalrenuja](https://x.com/nisalrenuja) [描述团队背景](https://x.com/nisalrenuja/status/2119491264014135433)，12 次点赞、4 条回复、294 次浏览；[@esrtweet](https://x.com/esrtweet) [描述人工审核](https://x.com/esrtweet/status/2119843690403242404)，189 次点赞、21 条回复、4,529 次浏览。）

**[++] Recoverable agent sessions with transparent control** — Multi-device Codex and IDE handoff posts show demand for continuity, while their replies identify lost context, unclear failure state, and target-machine approval as gaps. Cloudflare’s experimental harness shows one implementation direction for persistence, but does not establish a general solution. ([@_samirism](https://x.com/_samirism) [报告多台电脑的使用情况](https://x.com/_samirism/status/2119884573190545726)，376 次点赞、71 条回复、13,984 次浏览；[@github](https://x.com/github) [展示会话交接](https://x.com/github/status/2119529896296722931)，96 次点赞、30 条回复、21,257 次浏览；[Cloudflare 示例](https://developers.cloudflare.com/changelog/post/2026-11-09-codex-harness/)。）

**[++] Cost and quota controls matched to task type** — A subscriber reports sharp quota depletion, another separates products by whether they provide general work, cheap inference, or strong coding review, and Foundry Local presents local inference as an option for everyday tasks with cloud escalation for harder ones. ## 8. 要点

1. **置信度最高的工作流信号，是将规划与审批分开。** EGM 会让审查者在全新上下文中进行审核；另一位从业者则会把任务拆小，并在提交前检查差异。（[EGM 仓库](https://github.com/google/elephant-goldfish-model)；[@esrtweet](https://x.com/esrtweet) [描述受监督的工作流](https://x.com/esrtweet/status/2119843690403242404)，189 个赞、21 条回复、4,529 次浏览。）
2. **智能体的连续性正逐渐成为一项产品功能，但用户也希望失败状态清晰可见，并拥有明确的控制选项。** Codex 支持在多台电脑上使用，从 Copilot 切换到 VS Code 也能保留更多工作流信息；回复中有人提到上下文丢失和重试状态不明确。（[@_samirism](https://x.com/_samirism) [报告](https://x.com/_samirism/status/2119884573190545726)，376 个赞、71 条回复、13,984 次浏览；[@github](https://x.com/github) [演示交接](https://x.com/github/status/2119529896296722931)，96 个赞、30 条回复、21,257 次浏览。）
3. **对个人账户而言，可靠性和配额仍是实际限制。** 一位用户称，长任务会出错，系统也会变慢；另一位用户则称 Argon 的配额很快就会耗尽。这些是个人经历，并非对普遍情况的估算。（[@vipinxtwt](https://x.com/vipinxtwt) [报告任务失败情况](https://x.com/vipinxtwt/status/2119754376696955210)，26 个赞、9 条回复、2,370 次浏览；[@jan_volad](https://x.com/jan_volad) [报告配额使用情况](https://x.com/jan_volad/status/2119513284399223188)，20 个赞、9 条回复、1,660 次浏览。）
4. **这些项目都在尝试保留不同类型的上下文。** Understand Anything 梳理代码结构；SessionPal 让对话可供搜索并进行备份；OpsDesk 将智能体操作归集起来，但目前仍处于概念早期阶段。（[@balance0014](https://x.com/balance0014) [展示 Understand Anything](https://x.com/balance0014/status/2119491500140880004)，5 个赞，6 条回复，259 次浏览；[@essjaykay755](https://x.com/essjaykay755) [介绍 SessionPal](https://x.com/essjaykay755/status/2119800789560660201)，2 个赞，3 条回复，21 次浏览；[@lorenzor](https://x.com/lorenzor) [分享 OpsDesk](https://x.com/lorenzor/status/2119542170193653933)，3 个赞，3 条回复，62 次浏览。）
5. **本地推理与持久化会话解决的是不同问题，也各有明确限制。** Foundry Local 处理长上下文时需要大量 NVIDIA GPU 显存；Cloudflare 的 Codex 恢复示例则明确属于实验性尝试。（[Microsoft Foundry 文章](https://devblogs.microsoft.com/foundry/foundry-local-agentic-coding-qwen3-8-27b/)；[Cloudflare Codex 工具框架](https://developers.cloudflare.com/changelog/post/2026-11-09-codex-harness/)。）
