# Twitter AI 编程 - 2026-09-12

## 1. 人们在讨论什么

### 1.1 可观测的智能体工作正从“加分项”变成产品表面 (🡕)

9 月 12 日最明显的变化，是讨论从泛泛的“AI 能写代码”兴奋，转向那些能解释智能体做了什么、改了代码库哪里，以及团队该如何审查或约束这些改动的工具。OpenAI、GitHub 和独立构建者都从不同角度暴露出同一需求：归因、审计轨迹和有证据支撑的审查，正在变成一等产品能力。

[@thsottiaux](https://x.com/thsottiaux) [宣布](https://x.com/thsottiaux/status/2098569976143806918)（1,976 点赞、364 回复、156 收藏、176,186 浏览量），OpenAI 正在吸收 Git AI 团队，并把其开源工具描述为帮助开发者理解编程智能体如何为代码库作出贡献的方式。这条消息之所以落地，是因为它点中了过去几天很多人一直在围着打转的那层缺失能力：不是更好的自动补全，而是更清晰的智能体贡献归因。

[@GHchangelog](https://x.com/GHchangelog) [链接了](https://x.com/GHchangelog/status/2098509415557050533)（9 点赞、1 收藏、1,257 浏览量）GitHub 的 Copilot 代码审查更新：它现在会自动解决已处理评论、为已应用修复生成更聪明的提交说明，并调用更广泛的 命令行工具做更深层的验证。在配套的 [GitHub 更新日志](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review) 中，GitHub 还表示 Lite review 现在使用的是多智能体集成，而不是单个智能体独立工作；同时，高严重级别问题的已处理评论增加了 47%，中等增加 31%，低等级增加 11%，审查成本则大约下降了 8%。

独立构建者也在大平台之外解决同一个问题。[@DanKornas](https://x.com/DanKornas) [介绍了](https://x.com/DanKornas/status/2098558203613368366)（11 点赞、4 回复、4 收藏、861 浏览量）Hive，它在 GitHub issues 和 PR 进入任何 LLM 流程前，先加上确定性过滤器和 合并闸门。[@agenticgirl](https://x.com/agenticgirl) [分享了](https://x.com/agenticgirl/status/2098584882666754387)（2 回复、43 浏览量）Agent Beacon，这是一层开源遥测能力，可在 21+ 种运行时之间统一 提示词、工具调用、文件变更、审批和 token 使用。合在一起看，这些帖子让可观测性不再像合规附加项，而更像严肃智能体工作流的核心组成部分。

**讨论要点：** 大家的共同诉求不是“让模型更聪明”，而是“把发生了什么展示给我、让写入可观测、并留下以后可审计的证据”。

**与前日对比：** 9 月 11 日强调的是智能体周围的护栏与评估器；9 月 12 日则把这套讨论进一步拉近到实际工作表面：贡献归因、基于命令行的审查，以及跨运行时遥测。

### 1.2 Antigravity 还在持续发货，但真正的讨论重心已经变成干预与限制 (🡒)

Antigravity 依然是声量最大的产品线之一，但重心已经从发布新鲜感转向操作者控制。官方叙事说的是更丰富的工作流表面，用户叙事则更关心：当你想插手、改优先级，或是在真实限制下维持系统继续工作时，会发生什么。

[@googledevs](https://x.com/googledevs) [概括了](https://x.com/googledevs/status/2098454423899148382)（323 点赞、32 回复、77 收藏、45,555 浏览量）一组 Antigravity 更新：用于聚焦多智能体推理的 `/boost`、改进后的 `/teamwork-preview`、内联生成产物，以及更新后的 Git 与终端控制。最有价值的回复并不在于确认这些功能存在，而是追问怎样才能放心使用：比如让规划保持并行，但代码库写入仍然串行且可观测；以及在常规命令上提供更安全的权限行为。

[@rodydavis](https://x.com/rodydavis) [发了](https://x.com/rodydavis/status/2098508131949298165)（163 点赞、38 回复、33 收藏、13,244 浏览量）v2.13.0 发布帖，但真正持久的信号来自回复。用户要求在侧边栏里固定项目、调整顺序，还有人希望看到“像 Codex 一样”的模型思考过程。Rody 的回答之所以重要，是因为它划出了当前边界：排序和筛选是有的，详细思考过程也能打开，但人们还是明显觉得，需要更直接的干预工具。

[@ai_for_success](https://x.com/ai_for_success) [提到](https://x.com/ai_for_success/status/2098455665073365017)（193 点赞、16 回复、38 收藏、9,357 浏览量），Teamwork Preview 在复杂项目上很好用，因为多个智能体再加验证，效果优于单一循环；但同样的配置如果设置拉高，30 到 40 分钟就可能烧完 Pro 的 5 小时限额。这并没有削弱好评，反而让它更可信：这正是某个功能有用到足以撞上真实天花板时，用户才会发出的那种抱怨。

更广泛的人机工效批评来自 [@xdadevelopers](https://x.com/xdadevelopers)，其 [文章预告](https://x.com/xdadevelopers/status/2098456646150164835)（23 点赞、10 收藏、8,094 浏览量）链接到一篇 [XDA 对比](https://www.xda-developers.com/after-month-with-vs-code-cursor-google-antigravity-one-different-league/)，认为 Antigravity 的队列和定时任务很有吸引力，但人工干预依然得跳进另一个 IDE。它进一步点亮了当天底层主题：委派做得越来越好，但“人类接管”这一段，仍然是产品差异真正拉开的地方。

![Antigravity CLI 截图，展示在 Gemini 3.8 Flash High 上运行 teamwork-preview 命令，使多智能体工作流不再抽象](https://pbs.twimg.com/media/HR82ASKbIAE5cCa.jpg)

**讨论要点：** 人们越来越接受排队与委派。剩下的摩擦集中在交还给人的那一刻：给这个项目调序、把这个工作区 pin 住、把推理过程展示出来，并允许我在不打断上下文的情况下接手。

**与前日对比：** 9 月 11 日更多是在看 Antigravity 新浮出水面的界面；9 月 12 日这些界面仍在，但讨论已经明显更运营化：干预、人机工效，以及 teamwork 模式一旦真正有帮助后立刻撞上的限流天花板。

### 1.3 路由、可选性与定价逻辑，如今都成了产品的一部分 (🡕)

第三个主题是，模型选择不再只是能力争论。人们越来越用“是否保留供应商可选性、是否暴露真实经济结构、是否能在昂贵运行开始前把套餐逻辑讲清楚”来评价 AI 编程工具。

[@GergelyOrosz](https://x.com/GergelyOrosz) [强调了](https://x.com/GergelyOrosz/status/2098777064417427613)（33 点赞、13 回复、9 收藏、5,357 浏览量）他所说的 Claude Code 和 Codex 之间的巨大差异：Codex 允许用户选择任意模型，而且运行框架开源；Claude Code 则保持封闭，并与模型绑定。Tibo 被引用的解释之所以关键，是因为它把产品逻辑说透了：如果切换模型提供商只需要改几行代码，那强迫用户 fork 整套东西就是无谓开销，而公司真正想要的是保留这种可选性。

[@thdxr](https://x.com/thdxr) [表示](https://x.com/thdxr/status/2098781354611650806)（148 点赞、14 回复、2,659 浏览量），OpenCode Go 已经连续两周打平收支，并把这当作一个里程碑，因为这个品类里太多产品不是在烧钱，就是在悄悄依赖数据转售。回复进一步把“成本可见性”本身变成一项功能：有用户称赞 OpenCode Go 会直接在主页面展示预计使用区间，thdxr 也说，随着他们部署自己的 GPU，这套经济性还会继续改善。

托管式定价混乱也同样明显地冒了出来。[@ex0t1clol](https://x.com/ex0t1clol) [吐槽](https://x.com/ex0t1clol/status/2098518163583312347)（14 点赞、1 收藏、1,274 浏览量）GitHub Copilot 的模型选择器，把 Claude Opus 4.6 放进 Max，而 Astra、GPT-5.5 和几个 Claude 变体则放进 Pro+。[@0x_rody](https://x.com/0x_rody) [提醒](https://x.com/0x_rody/status/2098495409328955841)（7 点赞、1 回复、2 收藏、180 浏览量），GPT-6 Astra 曾被默认自动开启，并附上了最容易让团队措手不及的费率细节：272K 输入 token 以上有一个价格跳变，而且缓存写入还要单独收费。

![GitHub Copilot 的模型选择器截图，Pro+、Max 和模型分组逻辑本身成了抱怨焦点，而不是某个单独模型](https://pbs.twimg.com/media/HR9u_yoaIAAGSeg.png)

![附带的 Astra 定价说明，展示默认启用、272K 长上下文阈值，以及单独的缓存写入费用，这些都可能让团队措手不及](https://pbs.twimg.com/media/HR9aR5XWIAcQdZu.png)

修正性的讨论来自 [@shantanugoel](https://x.com/shantanugoel) [链接的](https://x.com/shantanugoel/status/2098718519349350545)（1 回复、3 收藏、129 浏览量）Quesma [RTK 成本分析](https://quesma.com/blog/does-rtk-make-ai-coding-cheaper/)。它的结论非常直接：减少终端里可见的输出，不等于真的省钱，而且在他们的基准里，DeepSeek 任务成本平均还上升了约 17%。这与当天其他内容很契合：用户奖励的，是把成本结构讲清楚的产品，而不是只承诺“感觉更便宜”的产品。

**讨论要点：** 路由如今越来越像基础设施能力，而不是界面点缀。人们想要的是可选性、可持续经济性、可预测配额，以及在全仓运行开始前就能解释清楚的价格逻辑。

**与前日对比：** 9 月 11 日让 Copilot 看起来像一层路由与定价体系；9 月 12 日则把这套逻辑扩展到 Copilot 之外：开放运行框架、收支平衡的经济模型，以及清晰的使用表面，都开始像持久差异化能力。

### 1.4 本地优先记忆、开放后端与上下文纪律，正在汇合成一套栈 (🡕)

第四个主题是，越来越多有意思的工作发生在模型周围，而不是模型内部。持久化本地记忆、可复用工作区状态、API 兼容的开放后端，以及更好的上下文整理，都像是同一个新栈的组成部分。

[@hasantoxr](https://x.com/hasantoxr) [带出了](https://x.com/hasantoxr/status/2098766600828854358)（27 点赞、6 回复、25 收藏、3,837 浏览量）LLM Wiki：这是一款本地桌面应用，可从文档增量构建维基与知识图谱，既可作为 Obsidian 知识库使用，也暴露 MCP 服务器，让 Claude Code 与 Codex 可以直接查询。[@tonysimons_](https://x.com/tonysimons_) [指出了](https://x.com/tonysimons_/status/2098767483293303051)（5 点赞、4 收藏、527 浏览量）PI-Desktop，它是一个面向编程智能体的本地优先控制中心，能导入 Codex、Claude Code 和 OpenCode 会话，同时支持 MCP、技能、子智能体和插件。这两个项目都把长时上下文视为工作区问题，而不只是提示词问题。

同样的模式也出现在指令卫生上。[@Voxyz_ai](https://x.com/Voxyz_ai) [提醒](https://x.com/Voxyz_ai/status/2098900224525918697)（5 点赞、4 收藏、412 浏览量），对 Sol 或 Luna 有帮助的指令，可能会把 Astra 约束得太死，因此一旦切换模型，就应该重新审查 AGENTS 风格的规则和技能。[@heyrimsha](https://x.com/heyrimsha) [把](https://x.com/heyrimsha/status/2098718915971186698)（3 点赞、2 回复、2 收藏、230 浏览量）Anthropic 的观点翻译成更直白的话：上下文窗口变大，并不能解决“上下文腐烂”；如果错误的文档、工具输出和历史同时争夺注意力，问题依旧存在。

开放后端则进一步强化了这个趋势。[@Oluwaphilemon1](https://x.com/Oluwaphilemon1) [认为](https://x.com/Oluwaphilemon1/status/2098580663184040389)（4 点赞、2 回复、2 收藏、252 浏览量），在免费的 Kaggle TPU 上以 BF16 运行 Qwen3.8-27B，再配合 OpenAI 兼容 API，可能会成为熟悉编程客户端的一个实用可替换后端。此时问题已经不再只是“哪个前沿模型赢”，而是“在换掉底层引擎时，我还能保留多少熟悉的智能体体验”。

[@iammukeshm](https://x.com/iammukeshm) [从人的角度表达了](https://x.com/iammukeshm/status/2098695619531411852)（22 点赞、2 回复、12 收藏、578 浏览量）同一个判断：如果 AI 给了你 60 行看起来能跑的代码，但你仍然无法判断鉴权是不是安全、验证是不是缺失，那模型并没有消除工程判断的需求，它只是让外围工作流变得更重要。

**讨论要点：** 竞争优势正在转向记忆形态、工作区持久性、指令加载方式和后端灵活性——也就是围绕智能体的“操作系统”，而不是单个最强模型。

**与前日对比：** 9 月 11 日已经隐约提到了记忆整理和护栏；9 月 12 日则通过本地优先产品、开放模型后端以及针对模型特定指令漂移的直接警告，把这一点讲得具体得多。

## 2. 令人困扰的问题

### 配额、套餐逻辑与成本主张都太不透明，往往要等运行开始后才看明白

最明显的挫败感，不只是好模型贵，而是用户往往根本看不出一个任务会花多少钱、哪个套餐解锁哪个模型，或者某个号称的优化到底有没有真的把账单压下去。[@ai_for_success](https://x.com/ai_for_success) [展示了](https://x.com/ai_for_success/status/2098455665073365017)（193 点赞、16 回复、38 收藏、9,357 浏览量）这个问题的运营版本：Teamwork Preview 有用到足以在 30 到 40 分钟里撞上 Pro 的 5 小时上限。[@ex0t1clol](https://x.com/ex0t1clol) [抱怨](https://x.com/ex0t1clol/status/2098518163583312347)（14 点赞、1 收藏、1,274 浏览量）Copilot 的模型选择器让套餐逻辑看起来近乎随意，而 [@0x_rody](https://x.com/0x_rody) [附上的](https://x.com/0x_rody/status/2098495409328955841)（7 点赞、1 回复、2 收藏、180 浏览量）Astra 费率卡则把 272K 上下文跳价和缓存写入单独收费这类细节具体摆了出来。

最尖锐的修正来自 [@shantanugoel](https://x.com/shantanugoel)，他[贴出了](https://x.com/shantanugoel/status/2098718519349350545)（1 回复、3 收藏、129 浏览量）Quesma 的 RTK 基准，说明“看起来输出更少”并不等于“真实花费更低”。最正面的反例则是 [@thdxr](https://x.com/thdxr) [庆祝的](https://x.com/thdxr/status/2098781354611650806)（148 点赞、14 回复、2,659 浏览量）OpenCode Go 打平收支，以及回复里可见的 15-60 美元使用区间。严重度：高。当前的应对方式通常是转向更便宜或开放的后端、手工盯用量，或者使用第三方追踪器，因为原生产品表面仍然把太多经济模型藏了起来。

### 委派能力更强了，但人工干预仍然笨拙，权限边界也依然薄弱

第二个挫败点是，智能体工具在自主工作上的进步，快于它们在人类接管上的进步。[@rodydavis](https://x.com/rodydavis) [收到了](https://x.com/rodydavis/status/2098508131949298165)（163 点赞、38 回复、33 收藏、13,244 浏览量）关于项目 pin 住、顺序调整和推理可见性的直接需求。[@xdadevelopers](https://x.com/xdadevelopers) [链接的](https://x.com/xdadevelopers/status/2098456646150164835)（23 点赞、10 收藏、8,094 浏览量）那篇月度对比，一边夸 Antigravity 的队列和定时任务，一边仍然批评人工干预必须跳到另一个 IDE 去做。

同一挫败感的安全版本则来自 [@dextns](https://x.com/dextns)，他[认为](https://x.com/dextns/status/2098717087774486687)（1 点赞、2 回复、20 浏览量）“read”和“delete”权限如今仍然太常被绑在一起，因此最安全的模式是：默认只给智能体数据副本，把观察与变更分开，并把每个动作都记进人类之后还能回看的日志里。Hive 和 Agent Beacon 都能说明构建者同样看到了这个缺口：团队真正想要的是串行写入、更明确的审批，以及耐久日志，而不是一个全能会话。严重度：中高。眼下最主要的应对行为，是在智能体之外再套流程，而不是信任默认边界。

### 当人、提示词或默认项错了时，生成代码仍然会悄悄失败

第三个挫败点更安静，但也许更重要：模型可以产出“看起来能工作”的结果，却依然在判断层面失手。[@iammukeshm](https://x.com/iammukeshm) [讲得很直白](https://x.com/iammukeshm/status/2098695619531411852)（22 点赞、2 回复、12 收藏、578 浏览量）：AI 可能给你 60 行能跑的代码，但你仍然不知道鉴权是否安全、验证是否缺失。[@Soso_fun_yt](https://x.com/Soso_fun_yt) [分享了](https://x.com/Soso_fun_yt/status/2098834026966499505)（7 点赞、2 收藏、268 浏览量）一个小型私有网络安全基准，其中同样的底层能力，会因为 `/boost`、提示词严格程度和是否明确写出需求，而呈现出非常不同的表现。

[@Voxyz_ai](https://x.com/Voxyz_ai) [补充了](https://x.com/Voxyz_ai/status/2098900224525918697)（5 点赞、4 收藏、412 浏览量）这一问题在模型切换时的版本：对 Sol 或 Luna 有帮助的指导，可能会把 Astra 约束过头；而为了适配一个模型去清理提示词，又可能顺手删掉另一个模型仍然依赖的测试命令或验收标准。

![Astra prompt guide 摘录，强调对 Sol 或 Luna 有帮助的指令，可能会把 GPT-6 Astra 过度约束，从而让提示维护本身变成运营问题](https://pbs.twimg.com/media/HSDJvPLWoA0RxMO.jpg)

严重度：对生产工作来说是高，即便抱怨声量没有配额问题那么大。常见的应对方式，是更严格的验收标准、更小的上下文、更多审查和更有经验的人——这也正是为什么上下文工程、审计工具和工作流封装在今天如此显眼。

## 3. 人们期望的功能

### 能理解智能体拓扑，而不只是总 token 数的预算地图

成本这条讨论线暗示出一个相当具体的缺失产品。人们想要的不只是月度用量表，而是一种面向任务的预算视图，能告诉你：到底是哪个模型、哪个子智能体，或哪次长上下文决策，即将把这次运行推入高成本。[@ai_for_success](https://x.com/ai_for_success) [用](https://x.com/ai_for_success/status/2098455665073365017) Teamwork Preview 的快速烧额度，把痛点讲得很具体；[@0x_rody](https://x.com/0x_rody) [暴露了](https://x.com/0x_rody/status/2098495409328955841) Astra 的隐藏阈值；而 [@thdxr](https://x.com/thdxr) [展示的](https://x.com/thdxr/status/2098781354611650806) 则说明，为什么可见的使用区间会受到欢迎。Bot Tracker 只是一个部分答案，更大的需求仍然空着。机会：直接。

### 把“看见”和“改动”分开的权限模型

[@dextns](https://x.com/dextns) [描述了](https://x.com/dextns/status/2098717087774486687)最清晰的理想形态：让智能体以一种方式检查，以另一种方式改动，默认不要指向在线数据，并保留动作轨迹供之后审查。Git AI、Hive 和 Agent Beacon 关于可观测性的帖子，也从不同方向强化了同一个产品缺口。团队并不想要全有或全无的自治，他们想要的是和真实工作流风险相匹配的权限边界。机会：直接。

### 面向特定模型的指令与上下文路由器

[@Voxyz_ai](https://x.com/Voxyz_ai) [提醒](https://x.com/Voxyz_ai/status/2098900224525918697)，而 [@heyrimsha](https://x.com/heyrimsha) [展示了](https://x.com/heyrimsha/status/2098718915971186698)：一个仍未被充分满足的需求是，规则、技能和背景上下文应该随着当前模型和当前工作阶段不同而以不同方式装载。缺的不是另一个超长提示模板，而是一个可靠的路由器，能分发指令、示例、工具和文件，这样从 Astra 切到 Sol 再切到开放模型时，工作流不会无声劣化。机会：竞争型。

### 面向长时智能体会话的混合工作区

Antigravity 的回复和 XDA 那篇对比都说明，人们仍然想要更平滑的“人工接管”表面：给项目列表调序、把重要工作 pin 住、检查推理、看 diff，并且在不跳来跳去的情况下介入。PI-Desktop 是目前最清晰的雏形答案，但今天的讨论也说明，这个需求绝不只属于一个产品。大家真正想要的是一个工作区，能把排队、委派、会话、权限、diff、记忆和后端选择收进同一个界面。机会：适中偏强。

当天工具满意度最高的场景，几乎都出现在产品愿意暴露“运营现实”而不是把它藏起来的时候。因此，Codex 的可选性、OpenCode Go 可见的用量区间、Hive 这种确定性的 pre-LLM 流水线，以及 Agent Beacon 统一后的遥测，才会成为真正有意义的差异化能力，而不是边缘功能。

## 7. 机会在哪里

**[+++] 可观测的贡献与审计层** — Git AI 的消息、Copilot 更深入的命令行支撑审查、Hive 的确定性闸门，以及 Agent Beacon 的遥测，都指向同一个缺口：团队想要一份耐久记录，知道智能体改了什么、如何验证结果，以及人工审批边界落在何处。这一机会很强，因为同一天里，这个信号同时出现在前沿实验室、平台厂商和小型构建者身上。

**[+++] 具备成本感知的智能体运营** — 从 Antigravity 烧额度很快，到 Copilot 套餐逻辑混乱、Astra 隐藏阈值、OpenCode Go 可见用量区间、Bot Tracker 小组件，再到 Quesma 的 RTK 基准，这些信号都反复表明：大家需要运行前预算预测，以及按工作流拆分的成本可见性。这一机会很强，因为痛点具体、反复出现，而且已经开始催生权宜产品。

**[+++] 面向特定模型的指令与上下文路由器** — Voxyz 对 Astra 的提醒、Anthropic 的上下文工程建议，以及 Soso 的基准，都说明默认项与提示词表述框架足以主导结果质量。这一机会很强，因为即便是高级用户，也在不断撞见由指令沿用、上下文腐烂或验收标准缺失造成的质量悬崖，而不是单纯的模型能力不足。

**[++] 带可审查动作的权限拆分式自治** — dextns、Hive 与 Agent Beacon 一起勾勒出一种清晰的产品形态：读和写/删分开，默认不接触在线数据，并把每个动作都记录下来供之后审查。需求清晰而务实，但产品采用看起来仍在早期。

**[++] 本地优先工作区与耐久记忆** — LLM Wiki、PI-Desktop，以及围绕 Qwen 与 DeepSeek 的开放后端讨论，都说明市场上存在空间：在不放弃现代智能体体验的前提下，保留本地状态、可移植会话与后端灵活性。这个信号中等偏强，因为已经浮现出多个不同解法，但使用证据仍然偏早期。

**[+] 带预算的交易与智能体商业化** — [@reeder1865](https://x.com/reeder1865) [设想](https://x.com/reeder1865/status/2098708069052010929)（3 点赞、1 回复、2 收藏、60 浏览量）一个“OpenAI Bank”，在 Codex 已经跑到 Cloudflare 结账页面之后，为不同智能体分配域名、构建工具和账单预算。这仍然是推测性的，但它把“如果智能体继续接手真实运营工作，被委派的花费控制会如何演进”这件事，描画得异常具体。

## 8. 要点总结

1. **讨论已经越过原始代码生成，进入了可观测性层。** Git AI 团队加入 OpenAI、Copilot 更深入的命令行支撑审查、Hive 和 Agent Beacon 都把归因、可审计性和证据当成产品能力，而不是可选治理层。([来源](https://x.com/thsottiaux/status/2098569976143806918); [来源](https://x.com/GHchangelog/status/2098509415557050533); [来源](https://x.com/agenticgirl/status/2098584882666754387))
2. **有用的多智能体工作流，如今更快撞上的是运营天花板，而不是能力天花板。** Teamwork Preview 的好评总伴随着 5 小时限额抱怨，而 Copilot 套餐混乱、Astra 定价细节和 RTK 怀疑论都说明，成本可见性如今已经是产品质量核心。([来源](https://x.com/ai_for_success/status/2098455665073365017); [来源](https://x.com/ex0t1clol/status/2098518163583312347); [来源](https://x.com/0x_rody/status/2098495409328955841); [来源](https://x.com/shantanugoel/status/2098718519349350545))
3. **开放运行框架和可替换后端获得了真正可信度。** Codex 的可选性、OpenCode Go 对收支平衡的推进、PI-Desktop 的提供商无关工作区，以及 Qwen TPU 讨论，都指向一个未来：开发者保留工作流，只替换下面的模型。([来源](https://x.com/GergelyOrosz/status/2098777064417427613); [来源](https://x.com/thdxr/status/2098781354611650806); [来源](https://x.com/tonysimons_/status/2098767483293303051); [来源](https://x.com/Oluwaphilemon1/status/2098580663184040389))
4. **提示词正在转变为运营级上下文设计。** 今天最重要的质量经验，已经是上下文路由、验收标准，以及模型特定的指令卫生，而不只是“换个更聪明的模型”。([来源](https://x.com/Voxyz_ai/status/2098900224525918697); [来源](https://x.com/heyrimsha/status/2098718915971186698); [来源](https://x.com/Soso_fun_yt/status/2098834026966499505))
5. **构建者正在模型外围补齐缺口，而 Codex 论文说明这不是偶然，而是结构性变化。** LLM Wiki、PI-Desktop、Hive、Bot Tracker、Annotate 和 Lilydrift 都位于原始模型体验之上或外围；而 OpenAI 的 Codex 论文则显示，多智能体与技能的使用增长，已经快到足以支撑这层新工具市场。([来源](https://x.com/hasantoxr/status/2098766600828854358); [来源](https://x.com/DanKornas/status/2098558203613368366); [来源](https://x.com/HumanPerson/status/2098690278643114386); [来源](https://x.com/iamprestonlogan/status/2098903028434715135); [来源](https://x.com/NickHirras/status/2098598343513436305); [来源](https://x.com/beamnxw/status/2098878444998131757))
