# Twitter AI 编程 - 2026-06-22

## 1. 人们正在讨论什么

### 1.1 记忆、图谱与编排层正更接近 AI 编程的中心 🡕

最明显的主题是，人们持续把模型质量视为整个技术栈中的其中一层，而不是唯一核心。更重头的讨论集中在持久化记忆、代码库图谱、路由层和编排系统上——这些组件能帮助智能体在长时间会话或大型代码库中保持方向感。共有四项入选内容支撑了这一主题，其中几项还明确指出，如今缺失的价值正位于基础模型之上。

[@SakanaAILabs](https://x.com/SakanaAILabs) [解释了](https://x.com/SakanaAILabs/status/2068862344684581023) （140 个赞、4 条回复、10,465 次浏览、36 次收藏）称，Sakana Fugu 表现得像一个兼容 OpenAI 的单一模型，但内部会在一个智能体池中完成任务选择、委派、验证与综合。随附的架构图和基准测试图之所以重要，是因为它们把原本模糊的“编排”说法落成了具体的产品形态，也展示了 Sakana 如何将 Fugu 和 Fugu Ultra 与前沿推理及编程模型进行对比。

![架构图展示了 Sakana Fugu 如何通过单一端点将一个请求路由到一组专用模型](https://pbs.twimg.com/media/HLYTUWxawAAEJN-.png)

[@cyrilXBT](https://x.com/cyrilXBT) [分享了](https://x.com/cyrilXBT/status/2068885434503966827) （20 个赞、1 条回复、2,589 次浏览、4 次收藏）将 Graphify 视为 Claude Code 的另一种“第二大脑”模式。公开的 [graphify README](https://github.com/safishamsi/graphify) 显示，`/graphify` 能够围绕代码、PDF、markdown 和图片构建持久化图谱、Obsidian 知识库、wiki 导出和图谱报告，并声称在混合语料上每次查询可减少 71.5x token 消耗。

**讨论洞察：** 最有价值的反驳来自这样一种观点：记忆必须可检查，而且要以文件为后端。Jumbo 的回复认为上下文窗口会有信息损耗，而图谱工具和编排工具则试图让结构变得可查询，而不是要求模型每次会话都重新发现一遍。

**与前一天的对比：** 6 月 21 日已经出现了记忆和多智能体监督，但 6 月 22 日把讨论又往下推了一层，深入到图谱构建、编排系统和持久化代码库理解。

## 2. 什么让人感到沮丧

### 为智能体工作付费，却得不到足够的可见性或稳定的经济性

严重程度：高。信息流反复展现出人们对 AI 编程会多快演变成账单问题的焦虑。[@pierceboggan](https://x.com/pierceboggan) [展示了](https://x.com/pierceboggan/status/2069097731856199925) （43 个赞、6,079 次浏览、6 次收藏）介绍了面向 Max 用户的临时 $200 Copilot AI Credit 优惠，把 Copilot app 定位成一个值得通过补贴来拉动使用的产品。[@Anaya_sharma876](https://x.com/Anaya_sharma876) [提问](https://x.com/Anaya_sharma876/status/2068924169790849324) （41 个赞、38 条回复、706 次浏览）询问在假设每月 $10 的价格点上，哪款工具会成为默认选择，让价格敏感度成了整条帖子的核心。[@elbruno](https://x.com/elbruno) [分享了](https://x.com/elbruno/status/2068978771126874569) （7 个赞、2 条回复、365 次浏览）介绍了一个 Copilot app 成本仪表盘，因为用他的话说，AI“在账单出现之前都很有趣”；公开的 [PRD](https://github.com/elbruno/copilot-app-cost/blob/main/docs/PRD.md) 也明确把实时估算和官方账单视为两个不能混淆的数据来源。人们正在通过寻找临时额度、自己搭建仪表盘，以及把流量路由到像 [BTL Runtime](https://runtime.badtheorylabs.com) 这样承诺展示单次请求节省金额的服务来应对。这一方向值得投入，因为这种痛点会反复出现、可以量化，而且已经在推动新工具诞生。

### 遭遇供应商错误、模型可用性不均和脆弱的新端点

### 眼看智能体浪费时间重新探索同一个代码库，或偏离最初目标

## 3. 人们希望有哪些东西

### 能够跨越会话重置和工具切换的持久化项目记忆

最强烈的实际需求，是能够超越单次终端会话和单个供应商的记忆。[@RoundtableSpace](https://x.com/RoundtableSpace) [表示](https://x.com/RoundtableSpace/status/2068779216368443401) （63 个赞、13 条回复、35,896 次浏览、21 次收藏）称，Jumbo Context 之所以存在，是因为编程智能体在不同会话之间遗忘了太多内容；[@pengsonal](https://x.com/pengsonal) [认为](https://x.com/pengsonal/status/2069004920930685013) （34 个赞、15 条回复、1,392 次浏览、15 次收藏）则指出，智能体仍然会浪费大量 token 预算重新发现代码库结构。[@cyrilXBT](https://x.com/cyrilXBT) [分享了](https://x.com/cyrilXBT/status/2068885434503966827) （20 个赞、1 条回复、2,589 次浏览、4 次收藏）则把 Graphify 视为把文件夹转化为持久化知识图谱和 Obsidian 知识库的另一种方式。这一需求既实际又紧迫：人们希望记忆可查询、可检查，并能在 Claude、Codex、Copilot 及相邻工具之间移植。机会：直接。

### 具备清晰成本可见性和自动故障转移的低价路由

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| GitHub Copilot app | 智能体工作空间 | (+/-) | 后台子智能体、agent merge、内置技能，app 界面持续扩展 | 额度消耗仍然突出，用户仍在构建独立的成本可见性层 |
| Impeccable | 质量 / 设计技能 | (+) | 在现有智能体工作流中加入设计和质量检查 | 用户仍在质疑它能否保留本地风格，以及能否做好无障碍覆盖 |
| Jumbo Context | 记忆 / 编排 | (+) | 本地记忆、跨会话连续性、并发智能体、模型可移植性 | 需要用户信任并维护一个结构化记忆层 |
| codebase-memory-mcp | 代码智能 / MCP 服务器 | (+) | 支持 158 种语言的图谱索引、快速结构查询，相比逐文件探索消耗更少 token | 静态分析仍有局限，索引也增加了一步本地配置 |
| Graphify | 知识图谱技能 | (+) | 多模态图谱构建、Obsidian 导出、wiki 导出、持久化图谱报告 | 需要 Claude Code 和 Python，提取质量取决于源语料 |
| OpenCode | 智能体 harness | (+/-) | 易于切换模型，并提供测试 GLM、Claude 及其他供应商的熟悉环境 | 供应商可用性仍不均衡，用户已经暴露出具体的 Anthropic 错误状态 |
| BTL Runtime | 路由 / 成本层 | (+/-) | 兼容 OpenAI 的 URL 替换、缓存、节省金额可见性、可选自带密钥 | 启动期的经济条件可能变化，并会增加另一项运营依赖 |
| GLM-5.2 | 模型 | (+/-) | 具备有数据支持的强劲性价比，价格低于顶级闭源模型，越来越多地通过 OpenCode 这类 harness 使用 | 在引用的基准测试中仍落后于最佳闭源模型，而且通常需要更多引导 |
| Sakana Fugu | 编排模型 | (+/-) | 通过单一端点实现多智能体编排，基准测试定位强劲 | 新近出现的可用性问题和早期可靠性疑虑很快浮现 |
| Interactions API | 智能体 API / 运行时 | (+) | 统一模型推理和托管智能体，支持远程沙盒与后台执行 | 发布当天存在 SDK 支持缺口，也引发了真正的工作应在哪里运行的问题 |
| Codex CLI `/goal` | 工作流控制方法 | (+) | 在长时间会话中固定意图，支持暂停 / 恢复，并可限制 token 预算 | 今天的证据主要来自一条详细的说明帖 |

总体满意度更偏向务实，而不是品牌忠诚。只要能让智能体更易于监督、更便宜，或更不容易丢失上下文，人们就会给予积极反馈，即便这意味着需要把多个层拼起来，而不是信任某个默认平台。

常见的应对方式非常一致：把记忆移入文件或图谱，通过更便宜或备用的供应商路由请求，在工作旁边展示成本估算，并在把长时间重构任务交给模型前固定会话级目标。最明显的迁移模式并不是某个供应商完全取代另一个，而是根据成本、可用性和当前任务类型，混合使用 Claude、Codex、Copilot、GLM 和路由 API。

竞争态势越来越集中在基础模型之上。相比孤立地关注又一个排行榜声明，信息流更关注编排、记忆、成本可见性、质量技能和故障回退行为。

反复出现的构建模式并不是“训练更好的模型”，而是用记忆、结构或可观测性把模型包起来。codebase-memory-mcp 和 Graphify 从不同角度解决同一个浪费问题，而 Jumbo 则把连续性本身当作产品。

多个人独立围绕同样缺失的层进行构建：记忆、成本可见性和明确的工作流控制。这种趋同比任何单条发布推文都更有说服力。

## 7. 机会在哪里

**[+++] 可移植记忆与代码库智能** — Jumbo Context、codebase-memory-mcp、Graphify 以及 `/goal` 相关讨论都指向同一个缺口：智能体仍然会浪费时间重新学习项目结构，或在不同会话之间忘记约束。这个机会很强，因为多个构建者正独立汇聚到图谱、记忆和上下文数据包层。

**[+++] 成本可见的路由与故障转移** — BTL Runtime、Copilot App Cost、Copilot Max 额度推动、GLM-5.2 基准测试讨论，以及当天有关供应商错误的截图，都指向这样一个市场：价格、故障回退行为和对计量器的信任，几乎与原始模型质量同等重要。一个结合路由、成本归因和可靠性处理的产品，有直接证据支持其市场机会。

**[++] app 原生的质量、评审与安全界面** — Copilot app 中的 Impeccable、agent merge 和 Codex Security 都表明，能够在代码发布前介入的工具仍有空间。这个机会中等，因为平台方正在快速进入该领域，但需求真实存在，工作流也仍处于早期。

**[+] 面向长时间智能体工作的可复用工作流脚手架** — `/goal`、Record & Replay、规范驱动技能包，以及 Anthropic 的课程目录，都表明一个围绕明确、可教学智能体工作流的新兴市场正在形成。其信号还不如记忆或成本路由强，但人们已经更容易看出，这些实践如何转化为默认产品功能。

## 8. 核心结论

1. **讨论持续向基础模型之上的层次移动。** Sakana Fugu、Jumbo Context、codebase-memory-mcp 和 Graphify 之所以受到关注，是因为它们改变了模型周围的记忆、路由或结构，而不只是提供另一种模型选择。（[来源](https://x.com/SakanaAILabs/status/2068862344684581023)）
2. **GitHub Copilot app 正在被塑造成持久化的智能体工作空间，而不只是代码助手。** 内置技能、后台子智能体、agent merge 和临时额度激励都指向这一方向。（[来源](https://x.com/github/status/2069121028241174761)）
3. **价格压力如今体现为路由产品、基准测试和迁移行为。** Runtime 的路由器定位、GLM-5.2 基准测试截图，以及当天因 Claude 端点故障而进行的切换，都表明开发者越来越愿意自行组装更便宜的技术栈。（[来源](https://x.com/israfill/status/2068936531780555013)）
4. **可靠性和可见性仍然是最快消耗信任的因素。** OpenCode 供应商错误、Sakana 503，以及成本仪表盘原型都表明，在把智能体工作流视为日常基础设施之前，开发者仍需要稳定的端点和诚实的计量方式。（[来源](https://x.com/FNDEVVE/status/2069124421479002378)）
5. **长时间运行的智能体工作正变得更加明确，也更易于教学。** `/goal`、Record & Replay、规范驱动技能包和 Anthropic 的课程目录，都指向从一次性提示词转向可复用工作流设计的变化。（[来源](https://x.com/sitin_dev/status/2068872841148412131)）
