# Twitter AI 编程 - 2026-07-05

## 1. 人们在讨论什么

### 1.1 工作流层与编排工具包持续增多（🡕）

最强的讨论簇并不是某个新旗舰模型发布，而是围绕现有编程代理持续封装上下文、记忆、协同与审查能力。至少有七条入选内容支撑了这一主题：GitHub 自定义代理、AI Workflow 技能包、multi-agent-shogun、Maestro、Happier、Orca，以及一个设计技能注册表。相比 7 月 4 日聚焦第一方多代理推进，7 月 5 日进一步扩展到第三方工作流工具包和操作界面。

[@github](https://x.com/github) [宣布](https://x.com/github/status/2073492041326088701)（171 个赞、18 条回复、28,102 次浏览、54 次收藏）介绍了 GitHub Copilot CLI 中的自定义代理；关联的 GitHub 博客称，这些代理以 Markdown 配置文件形式存放在 `.github/agents` 中，带有 YAML frontmatter、明确的工具访问权限，以及可审查的安全护栏，用于重复性的终端工作流。

[@DanKornas](https://x.com/DanKornas) [重点介绍了](https://x.com/DanKornas/status/2073769852154638467)（20 个赞、5 条回复、1,737 次浏览、25 次收藏）介绍了 [AI 工作流](https://github.com/nicepkg/ai-workflow)，其公开 README 证实：它提供 170 多个可安装技能、面向特定领域的工作流包、`npx add-skill`，并支持 Claude Code、Cursor、Codex、OpenCode、GitHub Copilot 和 Gemini CLI。关键变化不是又一套提示词包，而是可复用的工作流上下文正作为一种跨工具安装入口被分发。

[@DanKornas](https://x.com/DanKornas) [分享了](https://x.com/DanKornas/status/2073803836666384494)（24 个赞、6 条回复、1,834 次浏览、18 次收藏）介绍了 [multi-agent-shogun](https://github.com/yohey-w/multi-agent-shogun)；公开 README 也印证了其独特主张：一个 strategist 加上多个 worker 可以在可见的 tmux 窗格中并行运行，并通过 YAML 文件完成任务委派、报告与协同，而不是依赖隐藏状态。

![README 截图，展示 multi-agent-shogun 在并行终端窗格中协调一名 strategist 和多名 worker agents](https://pbs.twimg.com/media/HMehmBSWgAAoGrJ.jpg)

[@DanKornas](https://x.com/DanKornas) [发布了](https://x.com/DanKornas/status/2073815150889714097)（9 个赞、6 条回复、1,143 次浏览、5 次收藏）介绍了 [Maestro](https://github.com/sharpdeveye/maestro)，其 README 描述了 25 个工作流命令、7 个参考文件、持久化记忆、审计轨迹和一个 MCP 服务器。回复中有读者立刻追问：这些记忆单元能否保持新鲜，而不是逐渐变成过时的 wiki 摘要。这表明，持久化本身如今已成为一个现实的设计问题。

[@DanKornas](https://x.com/DanKornas) [提到了](https://x.com/DanKornas/status/2073656603492962400)（8 个赞、3 条回复、1,522 次浏览、7 次收藏）介绍了 [Happier](https://github.com/happier-dev/happier)——一个面向 Claude Code、Codex、OpenCode 等工具的端到端加密跨设备客户端；与此同时，[@YoussefHosni951](https://x.com/YoussefHosni951) [介绍了](https://x.com/YoussefHosni951/status/2073847022180844026)（3 个赞、3 条回复、97 次浏览）将 [Orca](https://github.com/stablyai/orca) 描述为一种环境，可把同一个任务分发到相互隔离的 git worktree 中，并将结果并排比较。两者共同把主题从“安装一个工作流”推进到“跨机器和设备监督多个工作流”。

**讨论洞察：** 有价值的质疑集中在记忆质量与安全性上，而不是工作流层是否重要。GitHub 帖子下的回复质疑，仅靠 Markdown 护栏是否足以应对高风险事件；Maestro 帖子下最有力的回复则追问，会话记忆能否保持结构化且不过时，而不是逐渐失效。

**与前一天比较：** 7 月 4 日让官方自定义代理和 Claude 内嵌 Codex 集成进入视野。7 月 5 日则沿着同一方向扩展到了可复用技能库、记忆层、多代理 shell，以及移动端监督界面。

### 1.2 围绕限制做路由，已从临时技巧变成产品界面（🡕）

成本和配额压力仍是核心问题，但讨论语气再次发生了变化。7 月 4 日主要关注重置可见性和 Azure 积分变通方案；7 月 5 日则强调跨供应商路由的控制平面、预付费钱包，以及明确的本地/云端任务策略。最强的几条内容都围绕如何维持会话不断线，以及如何在不重建整个工作流的情况下切换到更便宜的通道。

[@VaibhavSisinty](https://x.com/VaibhavSisinty) [表示](https://x.com/VaibhavSisinty/status/2073723635416895883)（71 个赞、10 条回复、7,614 次浏览、142 次收藏）称，[9Router](https://github.com/decolua/9router) 可以夹在 Claude Code 和 40 多家供应商之间，在某一路径额度耗尽时切换到更便宜或免费的模型，压缩工具输出，并在实时仪表板中展示配额状态。附带的仪表板是关键证据，因为它把已连接的 OAuth 供应商、免费供应商和 API 密钥供应商统一到一个路由界面中，而不是停留在理论功能清单上。

### 1.3 代理工作流扩展到相邻领域：Web 应用、攻防安全与数学研究（🡕）

第三个讨论簇显示，编程代理模式正在走出常见的“帮我改仓库”框架。入选证据涵盖浏览器原生代理、攻防安全代理群，以及专家级数学工作流。共同特征是：保留专家在环判断，同时把更多结构化执行交给代理系统。

[@israfill](https://x.com/israfill) [重点介绍了](https://x.com/israfill/status/2073789727698743516)（53 个赞、21 条回复、4,286 次浏览、59 次收藏）介绍了阿里巴巴的 [Page Agent](https://github.com/alibaba/page-agent)；公开仓库证实了几个关键主张：一行页面内 JavaScript 即可集成、使用基于文本的 DOM 交互而非截图、支持自带模型，并可选用浏览器扩展或 MCP 路径实现更广泛的控制。这一点很重要，因为它把浏览器自动化重新定义为一种可嵌入的产品能力，而不是一套独立的无头技术栈。

[@IntCyberDigest](https://x.com/IntCyberDigest) [总结了](https://x.com/IntCyberDigest/status/2073709900820099232)（34 个赞、2 条回复、3,456 次浏览、25 次收藏）将 T3MP3ST 描述为面向 Claude Code 和 Codex 订阅用户的多代理攻防安全框架。附带表格是关键信息，因为它明确列出了系统声称能猎取什么，以及各条路线的成熟度：Web 应用和 CTF 覆盖稳定，机器人或 OT 工作达到流水线稳定，源代码分析仅支持 Python 输入，智能合约则偏向复现而非全新发现。

[@nasqret](https://x.com/nasqret) [写道](https://x.com/nasqret/status/2073889988517712265)（17 个赞、575 次浏览、9 次收藏）称，Claude Code 和 Codex 正在改变他在算术代数几何中的工作流：他可以以接近思考速度生成并检查 CAS 代码，而不必手动输入每一步验证。信息量最大的图片是那张已验证修正表，因为它显示这一工作流被用于具体的数学检验和论文支持，而不只是泛泛记笔记。

**与前一天比较：** 7 月 4 日出现的是安全检查清单和培训路径。7 月 5 日展示了更多真实、领域化的工作流：浏览器副驾、攻防安全代理群，以及利用编程代理做实际验证工作的数学研究者。

### 1.4 真正的优势持续被归因于执行框架本身（🡒）

这一主题在 7 月 3 日和 7 月 4 日已经很强，到了 7 月 5 日依然存在。新的变化在于，人们越来越多地用流程图、基准差距和具体工作流模式来支撑这一判断，而不再只是凭直觉。反复出现的信息是：模型固然重要，但围绕模型构建的闭环更重要。

[@0x_kaize](https://x.com/0x_kaize) [认为](https://x.com/0x_kaize/status/2073743517155774641)（29 个赞、13 条回复、1,094 次浏览、17 次收藏）称，提示词工程正被循环工程取代。附图是主要证据，因为它把差异讲得很清楚：提示词工程是一条一次性的提示—响应路径；循环工程则围绕目标、规划、执行、验证、反思与迭代组织起来，并把失败恢复和成功条件纳入流程。

![对比 one-shot prompt engineering 与包含 goal、plan、act、verify、reflect 和 iterate 的 loop-engineering 流程图](https://pbs.twimg.com/media/HMdh8IGWoAABwoq.jpg)

[@PhiloGroves](https://x.com/PhiloGroves) [指出了](https://x.com/PhiloGroves/status/2073895871033287155)（2 条回复、109 次浏览）介绍了腾讯的 [Xuanwu Atuin AI CyberGym 文章](https://xlab.tencent.com/en/2026/07/02/xuanwu-atuin-cybergym/)，其报告称 GLM-5.1 在 CyberGym Level 1 上取得了 84.0% 的 pass@1，而引用的 Claude Code 下 GLM-5.1 结果为 68.7%。腾讯将这一差距归因于 manager/subagent 编排、面向安全的技能、SOP 遵循、TODO 跟踪，以及用于检测偏离的工作流钩子。

[@khanUmarCodes](https://x.com/khanUmarCodes) [补充道](https://x.com/khanUmarCodes/status/2073807386511565281)（3 条回复、58 次浏览）则给出了同一观点的实操版本：他之所以能在更便宜的开放权重模型上获得收益，是因为改变了工作流，让代理先澄清歧义、撰写 PRD、把工作拆成可测试的小块，并避免过度工程化。

**讨论洞察：** 操作层面的问题已经不再是“哪个基础模型赢”，而是“什么样的工作流能让代理在足够长的时间里保持专注、控制预算、并且可审查，从而把真实工作做完”。

**与前一天比较：** 7 月 4 日把编排视为角色拆分和产品界面问题。7 月 5 日则新增了明确的循环图、同一模型下的基准差距，以及更多从业者对流程层为何会改变结果的细致说明。

## 2. 人们感到挫败的地方

### 限制、积分和供应商切换仍会打断原本良好的工作流

严重程度：高。最强的成本相关帖子几乎全是变通方案。[@VaibhavSisinty](https://x.com/VaibhavSisinty) [表示](https://x.com/VaibhavSisinty/status/2073723635416895883)（71 个赞、10 条回复、7,614 次浏览、142 次收藏）显示，人们使用 9Router，正是为了让 Claude Code 会话在不中断的情况下切到更便宜、再切到免费的供应商；与此同时，[@StudentOffersHQ](https://x.com/StudentOffersHQ) [主推](https://x.com/StudentOffersHQ/status/2073569182239912010)（61 个赞、3 条回复、3,330 次浏览、64 次收藏）则把预付费积分和单密钥模型访问当作维持工作的现实办法。[@elbruno](https://x.com/elbruno) [回应称](https://x.com/elbruno/status/2073766061669748762)（7 个赞、2 条回复、505 次浏览、4 次收藏）则通过为 Copilot 搭建本地/云端路由执行框架来应对，[@khanUmarCodes](https://x.com/khanUmarCodes) [表示](https://x.com/khanUmarCodes/status/2073807386511565281)（3 条回复、58 次浏览）也表示，只有当工作流足够结构化、能减少无效重试时，他才真正把便宜模型用起来。人们正在用代理、预付费钱包、本地模型和路由策略来应对。这值得投入，因为这层“变通层”本身已经开始长成独立产品。

### 原始提示仍会导致偏离、过度工程化和会话失忆

严重程度：高。[@0x_kaize](https://x.com/0x_kaize) [认为](https://x.com/0x_kaize/status/2073743517155774641)（29 个赞、13 条回复、1,094 次浏览、17 次收藏）指出，一次性提示对于长程运行过于脆弱，因为它缺少记忆、验证和恢复能力。[@khanUmarCodes](https://x.com/khanUmarCodes) [介绍了](https://x.com/khanUmarCodes/status/2073807386511565281)（3 条回复、58 次浏览）则从另一个角度呈现了同一种失效模式：模糊请求会让代理自信地自行消解歧义，最后表现为过度工程化或任务偏离。[@DanKornas](https://x.com/DanKornas) [分享了](https://x.com/DanKornas/status/2073815150889714097)（9 个赞、6 条回复、1,143 次浏览、5 次收藏）介绍了 Maestro 作为一层记忆与工作流层，而其中最有价值的回复立刻追问：如果记忆条目不跟踪主张、范围、状态和来源轨迹，怎么避免它们过时。这值得投入，因为用户如今明确要求的是工作流结构，而不仅仅是更好的自动补全。

### 没有额外 shell 或配套应用时，同时监督多个代理仍然很别扭

严重程度：中。[@DanKornas](https://x.com/DanKornas) [分享了](https://x.com/DanKornas/status/2073803836666384494)（24 个赞、6 条回复、1,834 次浏览、18 次收藏）提到 multi-agent-shogun，因为“协调八个才是难点”，而不是运行一个代理。[@DanKornas](https://x.com/DanKornas) [发布了](https://x.com/DanKornas/status/2073656603492962400)（8 个赞、3 条回复、1,522 次浏览、7 次收藏）介绍了 Happier，让会话可在手机、Web、桌面和终端之间访问；[@YoussefHosni951](https://x.com/YoussefHosni951) [展示了](https://x.com/YoussefHosni951/status/2073847022180844026)（3 个赞、3 条回复、97 次浏览）则把 Orca 描述为一个环境，用于在相互隔离的 worktree 中比较多个代理。应对模式已经很清楚：tmux 层级、跨设备客户端，以及专门的代理 IDE。这个方向值得做，因为这种痛点往往要等团队开始持续运营多个代理后才会显现。

### 具备浏览器能力的代理仍暴露出严重的安全暴露面

严重程度：高。[@TakSec](https://x.com/TakSec) [警告称](https://x.com/TakSec/status/2073111122996302268)（11 个赞、1 条回复、1,274 次浏览、8 次收藏）称，Google Antigravity 可以被诱导从隐藏的 `<title>` 标签中泄露 API 密钥；关联的 ODIN 分析称，数据外泄路径经过终端访问和一个渲染后的图片 URL，前提是用户批准了代理口中那个无害的“视觉调试令牌”。[@IntCyberDigest](https://x.com/IntCyberDigest) [展示了](https://x.com/IntCyberDigest/status/2073709900820099232)（34 个赞、2 条回复、3,456 次浏览、25 次收藏）则指出，像 T3MP3ST 这样的多代理攻防安全框架也正在以领域化 hunt 模式和成熟度声明的方式被产品化。甚至 [Page Agent](https://github.com/alibaba/page-agent) 的公开文档也强调关键操作前的人类确认，这说明构建者已经把这视为现实风险。这个方向值得投入，因为风险具体、可复现，并且直接绑定在“浏览器 + 终端”代理这一暴露面上。

## 3. 人们希望存在什么

### 原生的成本感知路由和可见配额状态

最清晰的现实需求，是让产品自己暴露运行边界，而不是把用户推向外部代理和电子表格。[@VaibhavSisinty](https://x.com/VaibhavSisinty) [展示了](https://x.com/VaibhavSisinty/status/2073723635416895883)（71 个赞、10 条回复、7,614 次浏览、142 次收藏）解释了 9Router 为什么会引发共鸣：它提供回退规则、配额跟踪，以及跨多家供应商的统一端点。[@StudentOffersHQ](https://x.com/StudentOffersHQ) [将其定位为](https://x.com/StudentOffersHQ/status/2073569182239912010)（61 个赞、3 条回复、3,330 次浏览、64 次收藏）则把预付费积分和单密钥模型访问视为现实替代方案，[@elbruno](https://x.com/elbruno) [进行了](https://x.com/elbruno/status/2073766061669748762)（7 个赞、2 条回复、505 次浏览、4 次收藏）则用一个策略驱动的本地/云端路由执行框架表达了同样的诉求。这是迫切的现实需求，而不是理想化愿景。机会：直接。

### 跨会话保留的持久工作流记忆与结构

人们要的不只是更大的上下文窗口，而是能保住正确状态单元的工作流。[@DanKornas](https://x.com/DanKornas) [推广了](https://x.com/DanKornas/status/2073815150889714097)（9 个赞、6 条回复、1,143 次浏览、5 次收藏）把 Maestro 作为记忆、审计和工作流层提出，但最强的回复立刻追问：怎样才能防止记忆过时。[@DanKornas](https://x.com/DanKornas) [还分享了](https://x.com/DanKornas/status/2073769852154638467)（20 个赞、5 条回复、1,737 次浏览、25 次收藏）关注 AI Workflow，正是因为新会话否则总要从零开始；[@khanUmarCodes](https://x.com/khanUmarCodes) [表示](https://x.com/khanUmarCodes/status/2073807386511565281)（3 条回复、58 次浏览）则指出，真正的解锁点是在实现前强制完成澄清、PRD、issue 拆分和可测试小块切分。这是一个有大量主动试验、但尚无稳定默认方案的直接产品缺口。机会：直接。

### 跨 worktree 和设备的多代理任务控制中心

最强烈的监督诉求，是当工作变成异步且多代理之后，需要更好的操作界面。[@DanKornas](https://x.com/DanKornas) [分享了](https://x.com/DanKornas/status/2073803836666384494)（24 个赞、6 条回复、1,834 次浏览、18 次收藏）关注 multi-agent-shogun，因为难点在协调，而不在调用。[@DanKornas](https://x.com/DanKornas) [展示了](https://x.com/DanKornas/status/2073656603492962400)（8 个赞、3 条回复、1,522 次浏览、7 次收藏）关注 Happier 的跨设备续接能力；[@YoussefHosni951](https://x.com/YoussefHosni951) [将其定位为](https://x.com/YoussefHosni951/status/2073847022180844026)（3 个赞、3 条回复、97 次浏览）则把 Orca 视为一种从单一界面对多个隔离 worktree 中的代理进行比较的方式。这是一个现实需求，已有多个新兴答案，但尚无主导标准。机会：竞争性。

### 人们真正能信任的更安全浏览器代理和审批流程

Web 代理相关帖子把这一缺失需求讲得异常具体。阿里巴巴的 [Page Agent](https://github.com/alibaba/page-agent) 已经宣传关键操作需要人工确认，而 [@TakSec](https://x.com/TakSec) [展示了](https://x.com/TakSec/status/2073111122996302268)（11 个赞、1 条回复、1,274 次浏览、8 次收藏）则显示，即便存在用户审批步骤，如果代理把动作误描述成无害的调试令牌，流程依然可能失效。这是一个现实的安全需求，政策系统、扫描器和 UI 层缓解措施已经形成明确竞争，但核心工具仍有空间给出更强的原生答案。机会：竞争性。

## 7. 机会在哪里

**[+++] 面向编程代理的路由与配额控制平面** — 第 1、2、3、4 节的证据都指向这一点：9Router、Inference.net、CopilotHarness，以及基于开放权重模型的 OpenCode 工作流之所以存在，是因为用户仍需要一种可见方式，按配额、价格和任务来路由。机会很强，因为人们已经在采用独立路由器和预付费钱包，只为保持工作不断线。

**[++] 工作流记忆与结构化任务拆解** — AI Workflow、Maestro、循环工程讨论，以及 Umar Khan 的“澄清 -> PRD -> issues -> 可测试切片”工作流，都指向同一个缺口。用户希望代理记住该记住的内容、提出澄清问题，并在跨会话工作时保持可审查，同时避免偏离或过度工程化。

**[++] 跨 worktree 和设备的多代理任务控制中心** — multi-agent-shogun、Happier 和 Orca 解决的都是监督问题，而不是模型问题。机会中强，因为痛点具体明确，但现在已经有多个早期方案在 shell、桌面和移动端界面上竞争。

**[++] 更安全的浏览器与终端代理护栏** — ODIN 对 Antigravity 的漏洞利用，以及攻防安全代理框架的增长表明，浏览器加终端代理已经需要更强的审批、策略和审计层。机会中等，因为构建者已意识到这一点，但核心产品仍留下明显缺口。

**[+] 面向专家工作的领域专用工作流包** — ArcKit、awesome-design-skills，以及算术代数几何工作流都暗示了一个较新的机会层：面向架构、设计系统、数学验证及其他专家领域的专用包。信号仍在形成中，但这些例子已经比泛泛的“垂直 AI”讨论具体得多。

## 8. 要点

1. **工作流层扩张的速度继续快于模型叙事。** GitHub 自定义代理、AI Workflow、multi-agent-shogun、Maestro、Happier 和 Orca 都把编程质量视为封装、记忆和监督问题，而不是单纯的模型选择问题。（[来源](https://x.com/github/status/2073492041326088701)）
2. **规避配额如今已成为独立的产品类别。** 9Router、Inference.net、CopilotHarness，以及更便宜的 OpenCode 工作流，都在帮助会话跨越限制、预付费积分和本地/云端划分持续运行。（[来源](https://x.com/VaibhavSisinty/status/2073723635416895883)）
3. **只有当工作流更严格时，人们才越来越信任便宜模型。** 当天最强的低成本成功案例，都把开放权重模型或混合模型群，与澄清、PRD、issue 拆分和明确验证闭环结合了起来。（[来源](https://x.com/khanUmarCodes/status/2073807386511565281)）
