# Twitter AI 编程 - 2026-05-24

## 1. 人们在讨论什么

### 1.1 Antigravity 招来的怀疑多于信任 🡖

Google 的 Antigravity 依然话题度很高，但现有证据更偏向于挫败感，而不是采用情况的证明。互动量最高的帖子是对 Google AI 周的泛化抱怨；当天被反复传播最多的 Antigravity 讨论，则在多个账号间重复了同样的 NotebookLM 搭配、设置时长和四个使用场景。这让整体讨论呈现出明显分裂：一边是高度依赖分发的推广，另一边是尚未解决的产品摩擦。

[@ishuagra02](https://x.com/ishuagra02) [辩称](https://x.com/ishuagra02/status/2058412929045971445)（380 个赞、43 条回复、30,706 次浏览、52 次收藏）称 Google“这一周糟透了”，具体点名 Gemini 3.5 Flash 表现平平、Antigravity CLI 损坏且闭源，以及 Google Cloud 对 Railway 的处理方式不可接受。

[@jackcoder0](https://x.com/jackcoder0) [声称](https://x.com/jackcoder0/status/2058579610779173210)（50 个赞、30 条回复、12,018 次浏览、25 次收藏）称，NotebookLM 加上 Antigravity 可以实现自主深度研究、自定义业务技能、上下文感知应用和自动报告；与此同时，[@Heykazitarek](https://x.com/Heykazitarek) [提出了几乎相同的观点](https://x.com/Heykazitarek/status/2058273126518239523)（41 个赞、13 条回复、1,137 次浏览、28 次收藏）也发布了几乎相同的配置和使用场景列表。

[@koltregaskes](https://x.com/koltregaskes) [抱怨](https://x.com/koltregaskes/status/2058556891295633672)（9 个赞、6 条回复、864 次浏览）称，Antigravity 2.0 仍缺少真正可用的自动模式，即便权限已设为允许，系统还是不断要求批准点击。

![Antigravity 批准对话框，显示重复的一次性确认，而不是持久的自动模式](https://pbs.twimg.com/media/HJF2lZEbEAAwxch.png)

**讨论洞察：** 反复出现的 NotebookLM 线程详细铺陈了看多逻辑，但回复区和其他单独的抱怨帖，又不断把讨论拉回到信任、权限，以及 Google 是否真的交付了更顺滑工作流的问题上。

**与前一天相比：** 5 月 23 日，Antigravity 仍是一个好坏参半、且有积极辩护者的话题。到了 5 月 24 日，互动最强的信号进一步转向反感和批评，而正面论据主要来自重复的配置帖，而不是新的证明性案例。

## 2. 什么让人沮丧

### Antigravity 仍在把自动化变成审批劳动

严重程度：高。与 Google 相关的最强烈不满，并不是抽象的模型质量，而是工作流阻滞。[@koltregaskes](https://x.com/koltregaskes) [表示](https://x.com/koltregaskes/status/2058556891295633672)（9 个赞、6 条回复、864 次浏览）称，即使把权限设为允许，Antigravity 2.0 仍会反复要求同一项批准，并强制用户先做选择、再点提交。[@ishuagra02](https://x.com/ishuagra02) [表示](https://x.com/ishuagra02/status/2058412929045971445)（380 个赞、43 条回复、30,706 次浏览、52 次收藏）则称 CLI 已损坏且闭源，并把这一抱怨纳入对 Google AI 周的整体批评。今天的应对模式与其说是绕过方案，不如说是公开的恼火。这一点值得投入，因为故障发生在内循环：如果批准不能持续生效，代理就永远不会显得真正自主。

### 上下文负载较重的 Codex 会在最不该出问题的时候失败

严重程度：中高。[@zerotalktoai](https://x.com/zerotalktoai) [展示了](https://x.com/zerotalktoai/status/2058443112934949293)（3 个赞、4 条回复、75 次浏览）称，Codex 在一次远程 compact 任务中返回了 `context_length_exceeded`，随后表示实际可行的应对方式是新开一个聊天，尽管客户工作仍在进行中。这张截图很重要，因为它把模糊的可靠性抱怨，变成了活跃会话中的一个具体故障模式。

![Codex 错误界面，显示一个远程任务因 context-length-exceeded 消息而失败](https://pbs.twimg.com/media/HJEPFdcXgAAk7FF.jpg)

这值得投入，因为痛点是操作层面的，而不是表面问题：一旦会话崩掉，用户失去的是流畅度、连续性，以及对长时间运行工作的信任。

### 套餐层级的模型访问权限，正比品牌更影响感知价值

严重程度：中。[@cheatyyyy](https://x.com/cheatyyyy) [抱怨](https://x.com/cheatyyyy/status/2058577429355241591)（15 个赞、3 条回复、806 次浏览）称，GitHub Copilot 学生套餐展示的是一份老旧或以 mini 模型为主的列表，而不是前沿模型选项。[@morganlinton](https://x.com/morganlinton) [展示了](https://x.com/morganlinton/status/2058395466262626581)（29 个赞、8 条回复、2,807 次浏览、9 次收藏）则说明了这为何重要：Pi 的路由流程明确把 Anthropic、ChatGPT / Codex 和 GitHub Copilot 订阅视为可比较、可切换的输入。

![GitHub Copilot 学生计划的模型选择器，显示 GPT-4.1、GPT-5 mini、GPT-5.2、GPT-5.2-Codex 和 GPT-5.4 mini，但没有 frontier 级别选项](https://pbs.twimg.com/media/HJGIP2pbEAAFrZK.jpg)

当用户可以在不同套餐之间路由时，受限的模型菜单会立刻变成竞争劣势。因此，这既是一个定价透明度问题，也是一个路由 / 仪表盘问题，都值得为之构建。

## 3. 人们希望出现什么

### 持久自动模式，而不是没完没了的一次性批准

信息流中最直接的诉求，就是一个真正的自动模式。[@koltregaskes](https://x.com/koltregaskes) [明确询问](https://x.com/koltregaskes/status/2058556891295633672) 询问 Antigravity 2.0 的自动模式在哪，并表示应该用一键批准取代当前“先选再提交”的循环。这是现实需求，而不是理想化愿景。机会：直接。

### 面向订阅、模型和路由的中立控制平面

人们已经开始默认，模型访问应该可以跨工具迁移。[@morganlinton](https://x.com/morganlinton) [展示了](https://x.com/morganlinton/status/2058395466262626581) 展示了 Pi 在 Anthropic、ChatGPT / Codex 和 GitHub Copilot 账号之间切换；与此同时，[@cheatyyyy](https://x.com/cheatyyyy) [将其表述为](https://x.com/cheatyyyy/status/2058577429355241591) 认为 Copilot 学生套餐缺乏吸引力，因为它的模型菜单落后于市场。当前缺失的是一个清晰的仪表盘：解释每个套餐能解锁什么、哪些内容已经过时，以及何时改走其他路由更合适。机会：直接且具竞争性。

### 可跨代理客户端迁移、且经过审计的技能包

围绕技能的构建活动持续暗示着一个封装层缺口。[@tom_doerr](https://x.com/tom_doerr) [披露了](https://x.com/tom_doerr/status/2058491231626252426) 提到一个包含 99 项技能的 Claude 工作流库；当天稍晚，[分享了](https://x.com/tom_doerr/status/2058618831443030037) 又提到一个围绕 `n8n-mcp` 构建的 n8n 专用工具包。如今人们需要的已经不再是“给我一个提示词”，而是“给我一个可安装、可信赖的工作流模块”。机会：直接。

### 长时运行的会话应能优雅失败，而不是直接重置

[@zerotalktoai](https://x.com/zerotalktoai) [描述了](https://x.com/zerotalktoai/status/2058443112934949293) 提到，在真实客户工作中遇到 Codex 上下文窗口故障后，不得不新开一个聊天。这指向一个缺失的恢复层：压缩、检查点或交接，应该能保留任务状态，而不是强迫用户手动重来。机会：具竞争性。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| OpenAI Codex | 编程代理 | (+/-) | 在 1,400 条回复图表中拥有很强心智份额；仓库将其定位为开源终端代理；用户演示显示它可以路由到本地模型 | 实际工作中仍会出现上下文窗口故障；使用和路由方式仍显得较为临时 |
| Google Antigravity | 代理 IDE / 运行时 | (+/-) | 常与 NotebookLM 搭配，用于研究、自定义技能、应用生成和报告工作流 | “损坏 / 闭源”的抱怨、审批摩擦和重复宣传文案削弱了信任 |
| NotebookLM | 研究 / 上下文工具 | (+) | 在 Antigravity 相关帖子中充当深度研究、笔记生成和内容输出的来源层 | 今天的证据主要是捆绑式搭配帖，而非独立的编程证据 |
| Pi | 路由承载层 | (+) | 允许用户从订阅或 API key 起步，并在 Anthropic、ChatGPT / Codex 和 Copilot 账号之间切换 | 今天体现出来的价值是路由，而不是独特的编程能力 |
| OpenCode | 开源编程代理 | (+) | 官方站点承诺提供终端、桌面和 IDE 入口，并支持 GitHub、ChatGPT 及多提供商认证；Grok 集成扩大了其提供商叙事 | 今天的大多数证据集中在配置和集成截图，而不是深入的构建案例 |
| Claude Code | 编程代理 | (+) | 仍足够核心，能够催生大型技能库和 n8n 工作流工具包；在 rauchg 的图表中，Anthropic 模型主导模型层 | 用户仍在寻找更便宜的路由、更窄的工作流包，或围绕它的替代承载层 |
| GitHub Copilot | 编程助手 / 承载层 | (+/-) | 在路由工具中仍有存在感，也出现在 AI 辅助 Linux 内核补丁的报道里 | 学生套餐的模型可用性相较竞争对手显得陈旧 |
| Gemini CLI | 开源编程代理 | (+) | 官方仓库将其定位为支持 MCP 和大上下文的开源终端代理 | 当天的讨论更多聚焦于对 Antigravity 的抱怨，而不是 Gemini CLI 本身的使用 |

总体来看，当工具提升了可移植性，或把工作流知识打包出来时，满意度最高；当工具把价值藏在审批、过时的套餐层级或脆弱的会话行为后面时，满意度最低。现实中的迁移模式并不是从工具 A 干净利落地切到工具 B，而是路由：通过 Pi 或 OpenCode 复用现有订阅，通过 Ollama 测试本地模型，再把专用技能包叠加在仍然可用的承载层之上。
