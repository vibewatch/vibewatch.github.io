# Twitter AI 编程 - 2026-07-27

## 1. 人们在讨论什么

### 1.1 Google 仍在 AI 编程讨论中居于中心，但争论焦点已转向模型选择与接入成本（🡒）

Google 依然是 AI 编程讨论中的高频主角，但当天最强的一批 Google 相关帖子，关注点已不再是某个单一的 Antigravity 突破，而是你能接入什么、要花多少钱、以及哪些模型还缺席。五条入选内容共同支撑了这一主题：广泛传播的 Google AI Plus 学生优惠、官方 Antigravity SDK 演示、反复要求加入 Kimi K3 的呼声、OpenCode Zen 上线 Kimi K3，以及一张虽小却颇具说明性的 Copilot 截图，显示 Kimi 2.7 已经出现在别处。实际问题已经不再是 Google 有没有智能体，而是你在什么框架里能用到哪套模型菜单，以及对应的条件是什么。

[@StudentOffersHQ](https://x.com/StudentOffersHQ) [报道](https://x.com/StudentOffersHQ/status/2081416266708074997) (287 个赞，14 条回复，33,284 次浏览，332 次收藏) 表示，通过面向学生的分发渠道，印度、美国和加拿大用户可免费使用 Google AI Plus 12 个月，同时指出这项优惠并不会提高 Antigravity 的使用限额。这一点很重要，因为它将 Google 的 AI 编程推进方式呈现为一种捆绑与分发策略，而不只是一次模型发布。

[@antigravity](https://x.com/antigravity) [展示了](https://x.com/antigravity/status/2081792828300984577) (478 个赞，40 条回复，30,655 次浏览，86 次收藏) 展示了一个 Antigravity 2.0 智能体如何在 3.6 Flash 上构建支持实时多智能体状态同步和实时预览的协作式 Markdown 编辑器。这次演示为 Google 提供了一个已交付的具体成果，但回复区很快又把注意力拉回到模型清单：多名用户要求加入 Anthropic 或 Kimi，而不是只用 Gemini，并质疑 Flash 级模型是否足以胜任复杂工作。

![Antigravity 模型选择器的截图，显示有 Gemini、Claude 和 GPT-OSS 选项，但没有 Kimi K3](https://pbs.twimg.com/media/HOPtazbbcAAISs1.png)

[@HarshithLucky3](https://x.com/HarshithLucky3) [询问](https://x.com/HarshithLucky3/status/2081769103107481879) (342 个赞，32 条回复，20,416 次浏览) 呼吁 Google 把 Kimi K3 加入 Antigravity。这张截图之所以重要，在于它把抱怨具体化了：实时菜单里有多个 Gemini 档位、Claude 4.6 的不同版本，以及 GPT-OSS 120B，却没有 Kimi K3。[@opencode](https://x.com/opencode) [从另一边回应](https://x.com/opencode/status/2081807045917880551) (290 个赞，16 条回复，5,488 次浏览) 则用在 OpenCode Zen 上线 Kimi K3 作出回应，而最早几条回复已经在讨论成本，以及这场开放权重的胜利是否来得太晚。

这种竞争对比并不止于 Google。[@pamelafox](https://x.com/pamelafox) [展示了](https://x.com/pamelafox/status/2081801273419202980) (5 个赞，2 条回复，1,473 次浏览) 展示了 GitHub Copilot 中已选中 Kimi 2.7，这让 Antigravity 缺少 Kimi 选项更像是产品缺口，而不是一个停留在理论层面的功能诉求。

**讨论洞察：** 最尖锐的回复并不是在为某个品牌站队，而是在讨论模型菜单、延迟、成本，以及一个框架能否提供人们真正想拿来写代码的模型。

**与前一天对比：** 此前以 Google 为中心的讨论，主要围绕捆绑定价，以及 Antigravity 与 Codex 的信任之争。到 7 月 27 日，Google 仍居于中心，但最强的压力已经转向框架内部的模型可用性。

### 1.2 缓存行为、路由、技能和策略控制，开始成为摆在用户眼前的产品功能（🡕）

过去只存在于文档或后端架构图里的运行细节，如今成了社交平台上的一线内容。五条入选内容共同支撑了这一主题：GitHub 公开介绍 HyDRA 路由、Burke Holland 列出缓存失效场景、Burke 发布缓存中断通知插件、Skills.sh 推出技能市场定位，以及 GitHub 扩大企业托管设置的覆盖范围。贯穿其中的主线是：人们比较的不再只是模型，也是在比较模型外层的控制界面。

[@github](https://x.com/github) [表示](https://x.com/github/status/2081782838635143342) (55 个赞，9 条回复，13,070 次浏览) 表示，提示缓存和工具搜索能让 Copilot 会话中更大一部分内容用于真正有价值的工作，而 Auto 会根据任务意图和实时模型健康状况选择模型。GitHub 的公开帖子补上了关键机制：路由发生在自然缓存边界处，工具定义按需加载，而不是每一轮都硬塞进上下文；HyDRA 在达到与 OpenRouter Auto 相同 70.8% 解决率的同时，成本节省高出 3.3 倍。

![图表显示 GitHub 的 HyDRA 路由器在达到与 OpenRouter Auto 相同解析效果的同时，宣称可节省高得多的成本](https://pbs.twimg.com/media/HOP5vwxbEAE7ZD8.jpg)

[@burkeholland](https://x.com/burkeholland) [列出了](https://x.com/burkeholland/status/2081756969753333949) (25 个赞，8 条回复，3,766 次浏览) 列出了会破坏 Copilot 缓存复用的操作：切换模型、修改推理级别、启用或关闭技能或 MCP 服务器、等待超过 TTL、更换自定义智能体，或触发压缩。在他自己的截图显示 63,153 个复用 token 归零之后，他又 [分享了](https://x.com/burkeholland/status/2081829612116435345) (13 个赞，2 条回复，1,465 次浏览，15 次收藏) 发布了一个明确显示缓存掉线的 Copilot CLI 插件，让这条帖子又有了一个更实用的后续。回复区里的举证标准也非常偏操作层面：人们在问，路由器到底有没有把缓存账算进去，以及能否用一个本地小模型先判断缓存相关性，而不是直接触发一次失效。

[@ihteshamali](https://x.com/ihteshamali) [认为](https://x.com/ihteshamali/status/2081780438415380785) (17 个赞，5 条回复，1,412 次浏览，13 次收藏) 认为，Skills.sh 本质上就是一个智能体能力应用商店，支持一条命令安装、查看源码、查看安装量、查看支持的智能体以及安全审计结果。网站本身信息不多，但确实确认了这个基本产品构想：围绕可复用能力和 `npx skills add <owner/repo>` 构建开放式智能体技能生态。最有价值的回复也最具怀疑色彩：有用户追问，技能仓库一旦更新，审计结果是否就会过期。

治理层也在变化。[@pierceboggan](https://x.com/pierceboggan) [报道](https://x.com/pierceboggan/status/2081853555040755752) (5 个赞，1 条回复，411 次浏览) 表示，企业托管设置现在已覆盖 Copilot 应用；GitHub 的更新日志则称，同一份策略文件现在也适用于云端智能体。

**讨论洞察：** 围绕这些工具的讨论，已经明显转向可操作的运行层面。人们在问的是缓存 TTL、审批绕过、审计时效，以及基于模型健康状况的路由，而不只是模型智商。

**与前一天对比：** 本周稍早，效率与技能已经开始升温；但 7 月 27 日，它们真正落到了具体的操作界面上：图表、插件、安装命令和策略文件。

### 1.3 开发者持续围绕现有模型，交付本地优先工作区、记忆层和审查闭环（🡕）

最强的开发者信号在于，很多项目都把模型视为系统中的一个部件，而不是系统本身。八条入选内容共同构成这一主题：OpenWorker、jcode、Claudian、pauliusztin_ 的 coding-agent 循环、Ködade/KödWeb、fjzeit 的多框架控制台、Victor Kildahl 的智能体凹口界面，以及 alphabatcher 的垂直切片交付图。它们的共同动作，是用本地文件、审批、记忆、仪表盘、审查面板或远程工作区，把智能体包裹起来。

[@socialwithaayan](https://x.com/socialwithaayan) [分享了](https://x.com/socialwithaayan/status/2081678025528332769) (36 个赞，18 条回复，5,741 次浏览) 将 OpenWorker 描述为一个本地 AI 协作者：它会把工作拆成多个步骤，跨越桌面文件和已连接应用，并在执行有后果的操作前请求审批。代码仓库和截图进一步坐实了这一定位：25+ 个连接器、基于 aisuite 的 Python 后端、React/Tauri 桌面 UI、MCP 支持和定时运行，都表明该产品试图取代人工在多应用之间复制、粘贴、跟进的流程，而不只是生成建议。

![OpenWorker 截图，显示本地运行时、需审批的操作、25+ 个连接器，以及已完成交付流程](https://pbs.twimg.com/media/HOObIQdaoAEeaoL.png)

[@thisguyknowsai](https://x.com/thisguyknowsai) [推广](https://x.com/thisguyknowsai/status/2081680037544427793) (31 个赞，13 条回复，2,500 次浏览，35 次收藏) 将 jcode 描述为一个围绕低 RAM 占用、语义记忆图和蜂群式多智能体协作构建的 Rust 框架。公开仓库印证了其架构，但真正让这条帖子保持价值的是回复区：多名用户立刻追问，如果启动更快，但首个真正有用的交付物、审批流程或冲突处理仍然滞后，那么更快启动究竟意味着什么。

[@gippp69](https://x.com/gippp69) [将其描述为](https://x.com/gippp69/status/2081731223206998352) (27 个赞，10 条回复，18 次收藏) 介绍 Claudian 如何让 Obsidian 库可被 Claude Code 搜索和使用，而 [@pauliusztin_](https://x.com/pauliusztin_) [解释了](https://x.com/pauliusztin_/status/2081718748424057075) (1 条回复，156 次浏览) 指出，真正有意思的工程部分，其实是智能体循环外围的队列、运行器、权限门、引导和追踪。[@contractorkeith](https://x.com/contractorkeith) [展示了](https://x.com/contractorkeith/status/2081731973978984915) (2 条回复，186 次浏览) 将 Ködade 描述为一个内置审查功能的 ADE，并支持与浏览器配对的 KödWeb 模式；[@VictorKildahl](https://x.com/VictorKildahl) [展示了](https://x.com/VictorKildahl/status/2081804495655166220) (2 个赞，1 条回复，26 次浏览) 则展示了一个小型“智能体凹口”界面，专门用于让多个会话始终可见，并标记哪些会话正在等待人工处理。

在工作流层面，[@alphabatcher](https://x.com/alphabatcher) [警告](https://x.com/alphabatcher/status/2081861559601729964) (7 个赞，2 条回复，1,135 次浏览) 反对一次性交出 2,000 行代码的智能体 PR，转而主张按垂直切片交付；[@fjzeit](https://x.com/fjzeit) [展示了](https://x.com/fjzeit/status/2081747554476396640) (1 个赞，2 条回复，25 次浏览) 则展示了一个本地控制台，具备命令门控、代码质量策略，以及并排显示 GitHub Copilot 和 Claude Code 的面板。

**讨论洞察：** 最有力的纠偏声音并不是说“别用智能体”，而是说真正有意思的部分在于框架本身：记忆、权限、审查边界、远程会话处理，以及对智能体行为的可见性。

**与前一天对比：** 先前关于记忆系统的讨论，大多还停留在原则和方法论层面。到 7 月 27 日，则出现了更多具体界面：桌面协作者、浏览器配对工作区、内置审查面板，以及并发会话仪表盘。

## 2. 人们感到沮丧的地方

### 隐藏的缓存、路由和安全状态，让智能体行为既昂贵又难以预测

严重程度：高。[@burkeholland](https://x.com/burkeholland) [列出了](https://x.com/burkeholland/status/2081756969753333949) (25 个赞，8 条回复，3,766 次浏览) 列出了会破坏 Copilot 缓存复用的模型、推理、技能、MCP、TTL、自定义智能体和压缩事件。随后，他 [分享了](https://x.com/burkeholland/status/2081829612116435345) (13 个赞，2 条回复，1,465 次浏览，15 次收藏) 发布了一个通知插件，因为默认 UI 并没有把这些失效显示得足够明显。GitHub 的公开路由帖子解释了这为什么会痛：缓存感知路由之所以有价值，恰恰是因为会话中途切换模型，带来的成本可能高于节省。

![截图显示一次 Copilot 会话在缓存中断后，复用 token 从 63,153 降至零](https://pbs.twimg.com/media/HOQk0pEWEAAtfTV.png)

[@aramh](https://x.com/aramh) [抱怨](https://x.com/aramh/status/2081709334514327864) (10 个赞，3 条回复，352 次浏览) 表示，一条关于 interaction nets 的 GPT-5.6/Codex 请求没有得到答案，反而被重定向到了 OpenAI 的安全说明页面。OpenAI 自己的帮助文章也证实了这一总体模式：某些网络安全和生物学请求会触发额外的自动检查，从而延迟或压制回应。今天能看到的应对方式是务实而非意识形态化的：尽量保持会话稳定、在界面里显式展示失效，并在出现安全页面时缩窄提示范围。之所以值得围绕这个问题做产品，是因为痛点不只是输出差，而是隐藏的会话状态会在缺乏足够提示的情况下改变成本和行为。

### 大规模一次性交付的智能体改动，仍不如垂直切片和早期审查那样值得信任

严重程度：高。[@alphabatcher](https://x.com/alphabatcher) [警告](https://x.com/alphabatcher/status/2081861559601729964) (7 个赞，2 条回复，1,135 次浏览) 指出，AI 编程智能体往往会在用户还来不及点任何东西前，就先甩出 2,000 行代码；而 dex 的替代方案，是把同一功能拆成小型垂直切片，并在推进过程中逐个检查。关键数字很直接：大多数一次性交付的 PR，回来后都需要大约 50% 的返工，而前置 30 分钟规划，能省下后面数小时。

![图示展示了一个垂直切片式 AI 开发循环，包括代理构建、自动化测试、代理式评审，以及上线前明确的人类审核](https://pbs.twimg.com/media/HORB9djX0AA69ns.jpg)

类似的纠偏也出现在别处。[@thisguyknowsai](https://x.com/thisguyknowsai) [推广](https://x.com/thisguyknowsai/status/2081680037544427793) (31 个赞，13 条回复，2,500 次浏览，35 次收藏) 下面的回复指出，jcode 的启动时间不如首个有用交付物、清晰日志和审批门重要。[@antigravity](https://x.com/antigravity) [展示](https://x.com/antigravity/status/2081792828300984577) (478 个赞，40 条回复，30,655 次浏览，86 次收藏) 下面的回复则表示，其 Markdown 编辑器演示所用的 Flash 级模型，仍不足以让人信任其处理更难的工作。人们的应对方式，是强制拆成更小切片、加入 curl 或浏览器检查，并把人工审查放在改动发生附近，而不是整个 PR 完成之后。之所以值得围绕它做产品，是因为应对智能体粗糙输出的现实答案，是工作流架构，而不是更大的截图。

### 工具泛滥和并行会话泛滥，仍然跑在 UI 前面

严重程度：中。[@mark_k](https://x.com/mark_k) [询问](https://x.com/mark_k/status/2081710473666244991) (39 个赞，41 条回复，2,707 次浏览) 询问大家最喜欢的 AI 编程环境，回复却分散到了 Grok Build、Orca、Herdr、通过 OpenRouter 使用的 Pi、Codex、Claude Code、Cursor 和 Devin，而不是收敛到同一套栈。[@VictorKildahl](https://x.com/VictorKildahl) [表示](https://x.com/VictorKildahl/status/2081804495655166220) (2 个赞，1 条回复，26 次浏览) 表示，氛围编程式多任务处理中最难的部分，是跟踪所有正在运行的智能体；随后他展示了一个凹口 UI，用来标记哪些会话正在等他。

[@gippp69](https://x.com/gippp69) [使用了](https://x.com/gippp69/status/2081731223206998352) (27 个赞，10 条回复，18 次收藏) 介绍 Claudian 如何把 Obsidian 库变成智能体记忆，而 [@contractorkeith](https://x.com/contractorkeith) [展示了](https://x.com/contractorkeith/status/2081731973978984915) (2 条回复，186 次浏览) 则介绍了内置审查界面和浏览器配对工作区的 Ködade。这些都是在应对同一种压力：工具太多、会话太多，而共享上下文和监督又不够。之所以值得围绕它做产品，是因为当前答案大多是定制化、低覆盖的，这通常意味着产品界面仍处于开放状态。

## 3. 人们希望存在什么

### 同一编程工作流中的模型可移植性

这是一项立刻就有实际价值的需求，而不是抽象的基准测试闲聊。[@HarshithLucky3](https://x.com/HarshithLucky3) [询问](https://x.com/HarshithLucky3/status/2081769103107481879) (342 个赞，32 条回复，20,416 次浏览) 呼吁 Google 把 Kimi K3 加入 Antigravity，而他的截图让当前菜单里缺少 Kimi 这件事无比醒目。[@opencode](https://x.com/opencode) [展示了](https://x.com/opencode/status/2081807045917880551) (290 个赞，16 条回复，5,488 次浏览) 表示 OpenCode Zen 已经有了 Kimi K3，而 [@pamelafox](https://x.com/pamelafox) [展示了](https://x.com/pamelafox/status/2081801273419202980) (5 个赞，2 条回复，1,473 次浏览) 展示了 Kimi 2.7 在 GitHub Copilot 中运行。

OpenWorker 和 jcode 在工具层面也朝着同一方向推进：两者都允许工作流保持不变，而底层服务提供方可以切换。机会：竞争性。未被满足的需求，并不是另一个孤立的模型菜单，而是一个稳定的编程框架，让记忆、工具、审批和审查习惯在更换模型后仍能保留。

### 跨会话、跨工具持续存在的记忆

这是一项已有多种具体答案的实际需求。[@gippp69](https://x.com/gippp69) [使用了](https://x.com/gippp69/status/2081731223206998352) (27 个赞，10 条回复，18 次收藏) 介绍 Claudian 如何把 Obsidian 库变成可搜索的 AI 记忆系统，而 Claudian 仓库则确认，这个库会成为智能体的工作目录，而不是一个被动附件。[@thisguyknowsai](https://x.com/thisguyknowsai) [推广](https://x.com/thisguyknowsai/status/2081680037544427793) (31 个赞，13 条回复，2,500 次浏览，35 次收藏) 介绍了 jcode 的语义记忆图和后台整合机制，而 KödWeb 的公开文档则称，项目记忆会保留在托管工作区的常开主机上。

## 6. 新动态与值得关注的内容

### Copilot 的跨客户端治理能力扩展到了应用和云端智能体

[@pierceboggan](https://x.com/pierceboggan) [报道](https://x.com/pierceboggan/status/2081853555040755752) (5 个赞，1 条回复，411 次浏览) 表示，GitHub Copilot 应用现在支持企业托管设置。GitHub 的更新日志进一步说明了范围：同一个 `managed-settings.json` 现在可以在 Copilot 应用和 Copilot 云端智能体中统一管理插件、市场、审批绕过行为和 Auto 默认设置，而不再只覆盖 CLI 和 IDE 界面。这一点之所以值得注意，是因为对智能体编程而言，策略一致性正在成为产品功能，而不是事后补上的东西。

### OpenAI 额外安全检查的 UX，成了可见的编程工作流抱怨

[@aramh](https://x.com/aramh) [抱怨](https://x.com/aramh/status/2081709334514327864) (10 个赞，3 条回复，352 次浏览) 表示，一条技术查询没有得到有用回应，反而把他带到了 OpenAI 的安全说明页面。帮助中心文章也证实，某些网络安全和生物学请求会触发额外的自动审查，从而拖慢或阻止回答。

![OpenAI 通知称，由于系统正在进行更多思考，请求耗时更长，并建议改用更快的模型重试](https://pbs.twimg.com/media/HOO26J0WAAAZb0m.png)

这之所以值得注意，并不是因为安全检查本身是新东西，而是因为这种 UX 已经明显到足以让用户把它与路由、缓存失效和模型菜单并列，视为日常编程工具行为的一部分。

### Kimi 从抽象热度走向真实菜单位置

[@opencode](https://x.com/opencode) [发布了](https://x.com/opencode/status/2081807045917880551) (290 个赞，16 条回复，5,488 次浏览) 展示了 OpenCode Zen 中的 Kimi K3，而 [@pamelafox](https://x.com/pamelafox) [展示了](https://x.com/pamelafox/status/2081801273419202980) (5 个赞，2 条回复，1,473 次浏览) 展示了 GitHub Copilot 中选中的 Kimi 2.7。

这很重要，因为当天真正的信号，并不是某条基准测试帖子声称 Kimi 很强，而是 Kimi 家族模型已经肉眼可见地进入了真实智能体菜单，这会让所有缺少它们的框架显得更老旧。

## 7. 机会在哪里

**[+++] 缓存感知路由与可见性层** — GitHub 对 HyDRA 和提示缓存的推进、Burke Holland 的缓存中断清单与通知插件，以及 aramh 对安全检查的抱怨，都指向同一个缺口：长时间运行的智能体会话里有太多隐藏状态。能够展示缓存边界、模型路由后果、审批状态以及阻塞/变慢路径的产品，会直接回应官方产品帖和用户抱怨里都清晰可见的痛点。

**[+++] 共享项目记忆与会话总览层** — Claudian、jcode、Ködade、pauliusztin_ 的智能体循环图，以及 Victor Kildahl 的凹口界面，都在攻击同一个缺失层：持久上下文，加上一个面向人的、多智能体活动总览。这个机会之所以强，是因为它在同一天同时以主题、挫折、未满足需求和实际构建活动的形式出现。

**[++] 面向本地优先协作者的审批与策略控制面** — OpenWorker 的审批门、GitHub 企业托管设置的扩展，以及 KödWeb 的浏览器配对远程工作区，都说明人们需要的是边界明确的自主性。这个机会强度中等，因为真实产品已经开始出现，但当前界面仍按环境和用户群体分裂。

**[+] 现有框架中的即插即用模型菜单** — 对 Antigravity 加入 Kimi K3 的呼声、OpenCode Zen 上线 Kimi，以及 Copilot 中出现 Kimi 2.7，都说明把工作流忠诚度与模型忠诚度分离开来的产品，仍有空间。这个信号仍处于形成期，因为需求很明显，但主要证据还来自菜单截图、回复和早期集成，而不是广泛部署的案例。
