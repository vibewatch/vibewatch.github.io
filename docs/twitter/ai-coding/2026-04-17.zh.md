### 1.1 GitHub Copilot 速率限制危机逼近临界点 🡕

当天关于 Copilot 速率限制问题最详尽的梳理，来自 [@OwenGregorian](https://x.com/OwenGregorian)，后者 [分享了 The Register 的完整报道](https://x.com/OwenGregorian/status/2045113347230560431)（6 个赞、1 个收藏、1,024 次浏览）。文中记录了几件事：2026 年 3 月发现的令牌计数漏洞，低估了 Claude Opus 4.6、GPT-5.4 等新模型的令牌消耗；漏洞修复后，限制值恢复为原先配置，导致最长达 181 小时的锁定；Anthropic 的 Opus 4.6 Fast 面向 Copilot Pro+ 用户下线；以及 GitHub 因滥用暂停了所有 GitHub Copilot Pro 免费试用。文中引用的一名开发者称，自己遭遇了 44 小时的“每周速率限制”，并表示切换到 Auto 模式后，“性能明显更差”。

[@edandersen](https://x.com/edandersen) [提供了量化分析](https://x.com/edandersen/status/2045126509120356713)（2 个赞、3 条回复、195 次浏览）显示，Opus 4.7 的新分词器在处理相同文本时会多产生 35% 的令牌，在处理高分辨率图像时则会多产生 3 倍令牌（约从 1.15MP 到 3.75MP），而 API 定价仍维持不变：输入 $5/MTok，输出 $25/MTok。他指出，单凭这一点仍无法解释 GitHub Copilot 使用量倍率为何会从 3 倍升到 7.5 倍，这意味着 Anthropic 可能调整了向 Microsoft 收取的价格。

![Opus 4.6 与 4.7 成本对比表，显示新 tokenizer 使 token 数增加了 35%，图像处理的 token 数则增加了 3 倍](https://pbs.twimg.com/media/HGG_S6laQAAo_W1.png)

此外，[@shaneleexcx](https://x.com/shaneleexcx) [链接到一篇 GitHub 博文](https://x.com/shaneleexcx/status/2045135293238444233)（1 个赞、1 个收藏）宣布，自 4 月 24 日起，Free、Pro 和 Pro+ 用户的 Copilot 交互数据——包括输入、输出、代码片段和上下文——将用于模型训练，除非用户主动退出。Business 和 Enterprise 用户不在此列。这项政策变化进一步加深了速率限制问题造成的信任流失。

**讨论要点：** The Register 将这场危机界定为定价模型崩塌，而非容量问题：新模型打破了固定费率订阅赖以成立的成本假设。分词器分析则给出了一个具体机制——在每令牌价格不变的情况下，Opus 4.7 让文本令牌数膨胀 35%，图像令牌数膨胀 3 倍。两者叠加，对订阅用户形成双重挤压。

**与前一天对比：** 昨天还只是用户对速率限制的抱怨；今天则升级为行业媒体的调查报道，附带结构性分析、量化成本拆解，以及一项在开发者信任层面另开战线的数据使用政策变化。

[@draginol](https://x.com/draginol)（Brad Wardell，Stardock CEO）[推荐了 Clairvoyance](https://x.com/draginol/status/2045253484409131269)（4 个赞、2 个收藏、570 次浏览），展示了它如何在单一界面中，通过 8 个具名且职责分工明确的 AI“员工”智能体（Bug Fixer、Memory Monger、Publisher 等）管理一个游戏迁移项目：“我人在咖啡店，却可以通过和 Claude Code 对话，安全地让我的桌面电脑干活。”

![Clairvoyance AI 界面展示了 8 位具名代理员工，以专业分工和详细迁移规划管理一项游戏屏幕迁移工作](https://pbs.twimg.com/media/HGIy8IsXAAAkPTz.jpg)

**与前一天对比：** 昨天 Warp 发布的是智能体通知功能（任务完成或被阻塞时提醒）；今天则扩展到完整的远程会话共享和终端内代码评审，从被动监控走向跨设备主动协作。

### 1.3 令牌压缩正在成为一个新品类 🡕

同一天出现了两个彼此独立、却在解决同一问题的工具：AI 编程智能体会把大量令牌浪费在嘈杂的 shell 输出和样板化上下文上。

[@ItsRoboki](https://x.com/ItsRoboki) [分享了 ztk](https://x.com/ItsRoboki/status/2045028524227182888)（2 个赞、1 个收藏、23 次浏览），这是一款基于 Zig 的 CLI 工具，位于 Claude Code 与 shell 之间，在命令输出到达模型前先做压缩。[GitHub 仓库](https://github.com/codejunkie99/ztk) 记录了它在 256 条真实命令上的表现：总体令牌削减 90.6%；`git diff HEAD~5` 从 92,000 个令牌降到 18,000 个；`cargo test`（全部通过）从 397 个令牌降到 21 个。该二进制文件大小仅 260KB、零依赖，内置 56 个过滤器，支持 SIMD 文本处理，并有 217 个测试。

![VS Code 中的 ztk 源代码，展示了使用 SIMD 向量操作去除 ANSI 转义序列的 Zig 实现](https://pbs.twimg.com/media/HGFmmUcaMAATIzE.jpg)

[@pratikbin](https://x.com/pratikbin) [称赞了 Headroom 压缩引擎](https://x.com/pratikbin/status/2045209141061485018)（1 个赞、1 次转发、1 个收藏、26 次浏览）称，在 Opus 4.7 令牌消耗偏高的情况下，这个工具与 Claude Code 配合良好。[GitHub 仓库](https://github.com/chopratejas/headroom) 显示，Headroom 作为任意智能体与 LLM 提供方之间的代理运行，并提供 Python 和 TypeScript SDK。配图中的仪表板显示：642 次请求共节省 6,822,424 个令牌，省下 $27.35，缓存命中率 93.2%，且零失败。

![Headroom 仪表盘显示：642 个请求、节省了 680 万 token、93.2% 的缓存命中率，以及 Claude Opus、Haiku 和 Sonnet 的模型分布情况](https://pbs.twimg.com/media/HGIHaQYbgAATr7E.jpg)

**讨论要点：** 两个独立工具同时瞄准同一问题，说明需求真实存在。ztk 工作在 shell 层（命令输出进入上下文窗口前先压缩），Headroom 工作在 API 层（压缩智能体与 LLM 之间的全部上下文）。两者都在回应同一经济压力：Opus 4.7 令牌膨胀 35%，再叠加速率限制收紧，使上下文效率不再只是优化项，而成了硬性要求。

**与前一天对比：** 昨天，令牌压缩还不是一个显著话题；今天，它已以两个带有可量化结果的已发布工具正式出现，直接由 Opus 4.7 的令牌成本上升和 Copilot 速率限制收紧所推动。

## 2. 什么让人感到沮丧

### 速率限制与定价模型崩塌 — 高

The Register 的调查给出了迄今最完整的解释：2026 年 3 月的令牌计数漏洞让新模型看起来比实际便宜。GitHub 修复后，限制值回弹至原先配置，结果就是 181 小时锁定和任务中途强杀智能体。GitHub 还已面向 Pro+ 用户下线 Opus 4.6 Fast，并暂停所有免费试用。[@OwenGregorian](https://x.com/OwenGregorian) [分享了全文](https://x.com/OwenGregorian/status/2045113347230560431)（1,024 次浏览）。一名被引述的开发者表示，自己改用会自动选择更便宜模型的 Auto 模式后，“我的项目几乎没什么进展，Auto 模式选出来的模型质量很差，还经常不告诉我就抄近路。”这已经不是容量问题，而是定价模型失灵：固定费率订阅无法消化前沿模型的成本。

### Opus 4.7 令牌成本膨胀 — 中

[@edandersen](https://x.com/edandersen) [量化了影响](https://x.com/edandersen/status/2045126509120356713)（195 次浏览）：Opus 4.7 的新分词器在相同文本上会产生多 35% 的令牌，在高分辨率图像上则会多出 3 倍令牌，而每令牌 API 成本并未变化。上下文窗口仍是 1M 令牌，但会更快被填满。这对所有 Opus 4.7 用户都构成了一次隐性涨价，也进一步加剧了 Copilot 的速率限制问题。

### 智能体认证基础设施脆弱性 — 中

[@levelsio](https://x.com/levelsio) [无法使用 OpenClaw/Codex](https://x.com/levelsio/status/2045085201995370840)（5,027 次浏览）因 OAuth 令牌刷新失败而受阻。修复过程需要在两个系统中执行三条 CLI 命令。另一名用户则因无法 SSH 登录自己的 Raspberry Pi 完成重新认证而被卡住。用户调试的不是自己的代码，而是一层层认证基础设施。

### 更新做法不透明 — 低

[@uncooloj](https://x.com/uncooloj) [呼吁提供更新日志](https://x.com/uncooloj/status/2045135895544705125)（3 个赞、150 次浏览）写道：“我每天都看到更新提示，但完全不知道会发生什么、有什么新东西、又改了什么。”在快速发布却缺少文档的情况下，用户信任会被持续侵蚀。

### GitHub 正把用户引向 Copilot — 低

[@_avdept](https://x.com/_avdept) [展示了一张截图](https://x.com/_avdept/status/2045058371380715957)（3 个赞、67 次浏览）展示了 GitHub 的冲突解决下拉菜单：由于“过于复杂”，“在网页上编辑”被置灰，而“使用 Copilot 修复”成了替代选项。该用户的抱怨是：“从什么时候开始，你们居然限制我在网页编辑器里解决冲突了？”

![GitHub 冲突解决下拉菜单显示“Edit on the web”因过于复杂而被置灰，并提供“Fix with Copilot”作为替代方案](https://pbs.twimg.com/media/HGGBm05WwAAGK7Y.png)

## 7. 机会在哪里

**[+++] 令牌压缩与上下文优化** —— 同一天发布了两个独立工具（ztk：shell 层削减 90.6%；Headroom：代理层节省 6.8M 个令牌），再加上 SuperBased（截图到令牌转换）。需求驱动是结构性的：Opus 4.7 分词器带来 35% 的令牌膨胀，再叠加 Copilot 对速率限制的严格执行，形成了硬性的经济约束。任何能降低每次智能体会话令牌消耗的工具，都能直接延长可用时长。市场正按层分化（shell、代理、采集）；若有一体化方案能同时覆盖三层，就有机会拿下整条技术栈。

**[+++] 智能体会话评审与协作基础设施** —— Warp 在同一天发布了远程会话共享和终端内代码评审。Clairvoyance 则展示了具名角色的多智能体团队管理。背后的模式是：随着智能体运行时间变长、产出代码增多，人工评审会成为瓶颈。能够提供 PR 式评审工作流、协作光标和基于角色的智能体管理的工具，正在填补一个会随每次 Opus 4.7 长时会话而持续扩大的空白。

**[++] 面向 AI 智能体的设计到代码流水线** —— Codex 的设计质量被点名为阻碍全面采用的“最大问题”。Claude Design 的“交接到 Claude Code”是首个集成方案，但会把用户锁定在单一生态。一个与模型无关的设计层——能根据智能体提示生成可用于生产的 UI/UX，并可供任意编程智能体调用——正好填补了今天数据里最常被提及的能力缺口。

**[++] 智能体认证与基础设施调试** —— levelsio 的 OAuth 故障获得了 5,027 次浏览和 18 条回复。修复需要跨两个系统执行三条 CLI 命令。随着智能体栈加深（编排器 + 网关 + OAuth + 提供方），调试焦点正从“我的代码哪里错了”转向“哪一层认证坏了”。能够跨智能体基础设施层追踪故障、并提供清晰可归因错误信息的诊断工具，将解决一个会随每次新增集成而持续放大的痛点。

**[+] 面向网站资产的智能体就绪优化** —— Cloudflare 的智能体就绪扫描器已经建立起一套评分框架（可发现性、内容、机器人访问控制）。随着 AI 智能体成为重要流量来源，网站也需要像过去为搜索引擎优化那样，为智能体可访问性做优化。能够审计并提升智能体就绪评分的工具——类似 SEO 工具——将在“你的网站准备好迎接智能体了吗？”这一标准逐步普及的过程中填补一个新兴细分市场。

## 8. 要点

1. **Copilot 速率限制危机有其结构性解释。** The Register 的调查显示，2026 年 3 月的令牌计数漏洞让新模型看起来比实际便宜。漏洞修复后，限制值回弹，导致 181 小时锁定。这不是容量问题，而是定价模型失灵——固定费率订阅无法消化前沿模型成本。（[帖子](https://x.com/OwenGregorian/status/2045113347230560431)）

2. **令牌压缩在一天之内成为一个新品类。** 两个独立工具——ztk（shell 层削减 90.6%，260KB Zig 二进制文件）和 Headroom（API 代理层节省 6.8M 个令牌）——带着可量化结果发布。它们都是对 Opus 4.7 35% 分词器膨胀和速率限制收紧的直接回应。（[帖子](https://x.com/ItsRoboki/status/2045028524227182888), [帖子](https://x.com/pratikbin/status/2045209141061485018)）

3. **Warp 正在构建多智能体终端层。** 同一天推出的两项功能——带实时光标的远程会话共享，以及支持 LSP 的终端内 PR 式代码评审——让 Warp 成为不受提供方限制的编程智能体评审与协作界面。（[帖子](https://x.com/warpdotdev/status/2045253339055595649), [帖子](https://x.com/warpdotdev/status/2045141526674624620)）

4. **设计质量是 AI 编程智能体最常被提及的缺口。** 用户想要 Codex 的智能，却无法接受它的视觉输出。Claude Design 的“交接到 Claude Code”是首个集成式设计到代码桥梁，但会把用户锁定在单一生态。（[帖子](https://x.com/weswinder/status/2045265078069403857), [帖子](https://x.com/dani_avila7/status/2045209320787206150)）

5. **GitHub 正从多个方面收紧 Copilot 生态。** 速率限制、Opus 4.6 Fast 下线、免费试用暂停、交互数据训练退出机制（4 月 24 日生效），以及把冲突解决引向 Copilot，都表明该平台正在对开发者体验施加更多控制。（[帖子](https://x.com/shaneleexcx/status/2045135293238444233), [帖子](https://x.com/_avdept/status/2045058371380715957)）
