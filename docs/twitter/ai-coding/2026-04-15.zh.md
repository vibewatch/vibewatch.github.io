# Twitter AI 编程 - 2026-04-15

## 1. 人们在讨论什么

### 1.1 OpenAI Agents SDK 推出生产级基础能力 🡕

OpenAI 发布了 Agents SDK 的一次重大更新，面向生产环境中可持久、长时间运行的智能体。[@snsf](https://x.com/snsf) [宣布推出](https://x.com/snsf/status/2044514160034324793)（424 个赞、310 次收藏、30,339 次浏览）详细介绍了多项新基础能力：文件与计算机操作、技能、带压缩机制的记忆，以及将 harness 与计算执行分离。harness 已开源，计算执行则可委托给 Blaxel、Cloudflare、Daytona、E2B、Modal、Runloop 和 Vercel 等沙箱合作伙伴。官方表述非常明确：“你现在可以构建自己的 Codex 风格智能体了。”

[@rohanvarma](https://x.com/rohanvarma) [报道称已在内部采用](https://x.com/rohanvarma/status/2044519070142500914) 提到了 OpenAI 内部的情况（302 个赞、9,762 次浏览）：“在 OpenAI 里走动时，每隔 2—3 分钟，你几乎都会听到一句话：‘我现在在问 Codex。’”[@MatiBuildsWith](https://x.com/MatiBuildsWith) 回复说：“一旦人们像说‘我去 Google 一下’那样说‘我去问 Codex’，界面之争基本就结束了。”另一条来自 [@JDoeg53617](https://x.com/JDoeg53617) 的回复则要求推出一个超越 5.3 的新 Codex 模型，并指出即便使用持续学习技能和 CLI hooks，当前模型仍然存在局限。

**讨论洞察：** 这次 Agents SDK 更新，将 OpenAI 面向开发者的叙事从“使用 Codex”重塑为“构建你自己的 Codex”。harness 与计算执行的分离在架构上意义重大——这意味着智能体逻辑与执行环境可以彼此独立替换。[@stefanjrice](https://x.com/stefanjrice) 将可观测性称为“下一个重大突破口”：团队不仅需要知道智能体是否完成了任务，还需要看清它为什么会采取某个动作。

**与前一天对比：** 昨天的报告追踪的是 Codex 向桌面超级应用演进；而今天，OpenAI 则把重点上移到更底层——开源 harness，让开发者自己构建生产级智能体基础设施。这是一次平台级布局，而不是普通的产品更新。

### 1.2 速率限制成为跨平台的头号痛点 🡕

今天，三个平台都出现了关于速率限制的抱怨，而且互动异常高。

[@rsuyoy](https://x.com/rsuyoy) [点名 OpenAI](https://x.com/rsuyoy/status/2044551173575708762) 指责 Codex 在未公开说明的情况下“把限制大幅砍低了”（161 个赞、39 条回复、17,833 次浏览——是今天数据集中回复数最高的帖子）。作者系统性地排除了其他解释：不是 fast mode，不是高推理模型，不是技能使用过多，也不是 x2 之后的调整。“现在的限制和 Claude Code 差不多，甚至更严。”[@Jacoob_shi](https://x.com/Jacoob_shi) 回复说：“悄悄下调限制最糟糕。你只是某天醒来，发现一切都变慢了，却没人说过任何一句话。”

[@TheRegister](https://x.com/TheRegister) [报道了更广泛的 Copilot 反弹](https://x.com/TheRegister/status/2044513493580382660)：“GitHub Copilot‘修复’速率限制，引发客户反弹。”[@mandraketech](https://x.com/mandraketech) [报道称触及速率限制](https://x.com/mandraketech/status/2044503553847505399) 表示，自己第一次在 Copilot Pro+ 订阅上撞到限制，尽管日均请求量大约只有 60 次，且分布在 3—4 个并行会话中——“却没有任何关于具体限制内容或时间线的说明。”

在 Anthropic 一侧，[@ChrisHayduk](https://x.com/ChrisHayduk) [提出了对可靠性的担忧](https://x.com/ChrisHayduk/status/2044533710947598833)（46 个赞、11,588 次浏览）表示：“Claude API 和 Claude Code（它们企业收入的主要驱动项）只有两个 9 的可用性，这完全不可接受。尤其是在 Codex 和 OpenAI API 已经做到四个 9 的情况下。”

**讨论洞察：** 用户对速率限制的不满已经不再局限于某一个工具——如今它同时横跨 OpenAI（Codex）、GitHub（Copilot）和 Anthropic（Claude Code 的可用性）。共同问题是缺乏透明度：用户看不到自己的限制，无法预判何时会撞线，限制变化时也收不到正式通知。

**与前一天对比：** 昨天的报告记录了 Claude Code 的成本不透明问题（每天 200 美元却毫无可见性）以及 token 膨胀。今天，这种不满进一步加剧并扩散到了 Codex 和 Copilot，而且还得到了 The Register 的机构媒体报道。

### 1.3 VS Code 和 GitHub Copilot CLI 推出智能体基础设施 🡕

官方 [@code](https://x.com/code) 账号 [宣布发布新版 VS Code](https://x.com/code/status/2044555141039190157)（348 个赞、68 次收藏、24,669 次浏览）介绍了多项智能体体验增强功能，包括历史会话调试日志、终端交互工具，以及内置 GitHub Copilot。[@m_emanaftab](https://x.com/m_emanaftab) 则从竞争角度评论道：“现在每个工具都在推出智能体功能。VS Code、Claude Code、Codex、Cursor。长期胜出的不会是功能最多的那个，而是那个能真正深入理解你的项目、让你敢在离开时把工作放心交给它的工具。”

[@cinnamon_msft](https://x.com/cinnamon_msft) [推广 Copilot CLI 的 /remote 命令](https://x.com/cinnamon_msft/status/2044527066591150535)，支持用户从任意设备访问本地开发环境。[@JamesMontemagno](https://x.com/JamesMontemagno) [称赞 Copilot CLI 团队的推进速度](https://x.com/JamesMontemagno/status/2044539850339324246)：一条 PR 在中午到下午 1 点之间完成了提交、文档更新、合并、排队和生产部署——而负责的工程师午饭都还没回来。

[@tristanbob](https://x.com/tristanbob) [调查了 Copilot 用户](https://x.com/tristanbob/status/2044544589194006671) 发起了一项关于“你使用哪个智能体”的投票，并链接到 [GitHub 的第三方 agents 文档](https://docs.github.com/en/copilot/concepts/agents/about-third-party-agents)。可选项包括 VS Code 原生智能体、Anthropic Claude（Opus 4.5/4.6、Sonnet 4.5/4.6）和 OpenAI Codex（GPT-5.2-Codex、GPT-5.3-Codex、GPT-5.4）。每个智能体会话都会消耗 1 次 premium request，以及 GitHub Actions 分钟数。

**讨论洞察：** GitHub 的智能体平台如今让用户在原生、Claude 和 Codex 三类智能体之间做选择——而每类又有不同的模型选项和成本结构。这种碎片化是有意为之的（竞争会提升质量），但也增加了用户的决策负担。

**与前一天对比：** 昨天追踪了 Copilot CLI 向远程和移动场景扩展；今天通过 /remote 命令的演示进一步确认了这一方向，同时又叠加了 VS Code 的智能体基础设施更新，强化了微软的双轨策略（IDE + CLI）。

### 1.4 OpenCode 远程环境方案接近发布 🡕

[@jlongster](https://x.com/jlongster) [详细介绍了分布式系统相关工作](https://x.com/jlongster/status/2044563154038845775) 介绍了 OpenCode 远程环境背后的实现方案（76 个赞、29 次收藏、7,839 次浏览）。这套架构通过控制平面服务器将写操作代理到远程环境，而读操作则来自本地同步副本。这样会带来最终一致性问题：更新可能不会反映到后续读取中。解决办法是一种“fence”机制——远程环境会在响应头中返回最新同步状态，而控制平面会等到自己的同步状态匹配之后，才完成读取。帖子还附上了相关 PR，并称该功能“已经非常非常接近发布”。

后续评论透露了路线图：Cloudflare 集成即将到来（“@threepointone lots to talk about next week”），未来还会支持 provider plugins，让不同的沙箱提供商能原生利用各自的平台。当前系统会在远程环境中运行一个完整的 OpenCode 服务器，但后续计划拆分组件，以支持更灵活的部署。

[@LukeParkerDev](https://x.com/LukeParkerDev) [发布了一篇 2 分钟 TUI 插件教程](https://x.com/LukeParkerDev/status/2044562909611888748)（49 个赞、23 次收藏、5,865 次浏览）展示了如何在 OpenCode 里构建自定义面板，体现出 OpenCode 终端界面的可扩展性。

[@atbeme](https://x.com/atbeme) [开始搭建一个 wiki](https://x.com/atbeme/status/2044555175084626203) 记录了 OpenClaw、Hermes、OpenCode 及类似开源智能体 harness 的内部机制，灵感来自 Karpathy 的 LLM personal wiki 概念。

**讨论洞察：** OpenCode 正在打造 Codex 已经具备的远程执行能力，但采用的是开放架构和 provider-plugin 模式。fence 机制解决的是一个真实存在的分布式系统问题，而公开 PR 的方式也让社区能够直接检查实现细节。

**与前一天对比：** 这是一个新主题。OpenCode 在昨天的报告中并不突出，而这项远程环境工作正在把 OpenCode 推向 Codex 云端执行能力的开源替代方案位置。

### 1.5 Claude Code 向多智能体与企业工作流扩展 🡒

[@TheTuringPost](https://x.com/TheTuringPost) [报道称 OpenAI 发布了一个插件](https://x.com/TheTuringPost/status/2044561927905677558) 让用户可以在 Claude Code 中直接调用 Codex。这个插件把 Claude Code 变成了一个多智能体配置，让 Codex 作为专门的子智能体，承担代码审查、调试、异步后台任务和状态跟踪等工作。

![Claude Code 的 Codex 插件 README，展示了用于审查、对抗性审查和后台任务管理的斜杠命令](https://pbs.twimg.com/media/HF--PQnbEAAR8HM.jpg)

该插件提供 6 个斜杠命令：`/codex:review` 用于只读审查，`/codex:adversarial-review` 用于可引导的挑战式审查，`/codex:rescue`、`/codex:status`、`/codex:result`、`/codex:cancel` 用于委派和管理后台任务。其许可证为 Apache-2.0。

[@wmthomson22](https://x.com/wmthomson22) [介绍了如何构建一个金融建模系统](https://x.com/wmthomson22/status/2044565268102266977) 介绍了一个在 Claude Code 中构建的金融建模系统：大约用了 40 小时，覆盖 75 家公司。其方法是先把 Claude Code 当成“一个什么都不懂的分析师”，然后迭代式地教会它——先理解财务报表，再从商业模式和经营分部中识别收入驱动因素，最后对照 10-Q、10-K 和电话会纪要验证假设。现在，这套系统已经可以部署给“完全没有任何相关知识”的分析师使用。

[@JeremyNguyenPhD](https://x.com/JeremyNguyenPhD) [探索了 Claude Code Routines](https://x.com/JeremyNguyenPhD/status/2044369835166241023) 用它来做每日简报，但也提出了隐私担忧：“我到现在都还没把主邮箱连接到任何 AI，上来就会想到隐私之类的问题。”

![Claude Code Routines 界面，显示 Briefing、Email triage、System health check 和 Issue triage 的模板选项，以及日程安排和集成详情](https://pbs.twimg.com/media/HF8Ph-maQAAvGvq.jpg)

**讨论洞察：** 这个 Codex-inside-Claude-Code 插件体现出一种很特别的竞争行为——OpenAI 不是只与 Anthropic 竞争，也在主动进入其生态系统。金融建模这一案例则说明，Claude Code 正在被用于复杂的企业工作流；这类工作流需要数周的迭代式教学，而不是一次性提示词就能完成的任务。

**与前一天对比：** 昨天的报告介绍了 Claude Code Routines 和桌面版改版。今天则看到了第二天的采用情况：用户开始探索 Routines（同时对隐私有所顾虑），而金融建模案例则以迄今最详细的企业实例，进一步延展了“Claude Code 不止用于编程”这一主题。

## 2. 人们在为什么烦恼

### 各平台悄然下调速率限制（高）

[@rsuyoy](https://x.com/rsuyoy) [记录了](https://x.com/rsuyoy/status/2044551173575708762) 表示，OpenAI 在没有任何公开公告的情况下，大幅削减了 Codex 的限制。该帖获得了 39 条回复——是今天数据集中回复最多的一条——作者还排除了所有常见的替代解释。[@TheRegister](https://x.com/TheRegister) [报道了](https://x.com/TheRegister/status/2044513493580382660) 则反映了平行发生的 Copilot 用户反弹，而且还触达了机构媒体（仅这条推文本身就有 970 次浏览）。[@mandraketech](https://x.com/mandraketech) [触及 Copilot Pro+ 速率限制](https://x.com/mandraketech/status/2044503553847505399) 第一次撞到限制，尽管使用模式一切正常，却没有收到任何关于限制细节或时间线的说明。贯穿始终的抱怨是缺乏透明度：限制变了，没人通知，而用户只能靠亲自撞上去才知道新边界在哪里。

### Anthropic API 和 Claude Code 的可靠性（中）

[@ChrisHayduk](https://x.com/ChrisHayduk) [量化了差距](https://x.com/ChrisHayduk/status/2044533710947598833)：Anthropic 的 Claude API 和 Claude Code“只有两个 9 的可用性”，而 Codex 和 OpenAI API 则有四个 9。帖子将 Claude Code 和 API 视为 Anthropic 的“主要企业收入驱动项”，因此不稳定性会直接构成业务风险。这延续了昨天关于可靠性的担忧，同时也给出了一个明确的竞争基准。

### Google Antigravity 和 Gemini 的不稳定性（中）

有 4 条独立帖子表达了对 Google AI 编程工具的不满。[@tinyblue_dev](https://x.com/tinyblue_dev) [取消了 Gemini Ultra](https://x.com/tinyblue_dev/status/2044473573662732741) 称 Antigravity“不过就是 VS Code 的一个 fork”，还是“半成品软件”。[@procesor_x](https://x.com/procesor_x) [报道称绿色额度问题持续存在](https://x.com/procesor_x/status/2044464416368762886) 分别来自两个账号（Pro 和 Ultimate），但 Google 都没有回应。[@gujjutweeter](https://x.com/gujjutweeter) [报道称](https://x.com/gujjutweeter/status/2044480316107272687) 表示，在 Antigravity 中使用 OpenCode 触发了 policy violation，目前还在等待申诉结果。[@ultramathi](https://x.com/ultramathi) [抱怨](https://x.com/ultramathi/status/2044476353437962270) 则抱怨“server at high usage”错误持续不断。

## 3. 人们希望出现什么

### 透明、公开的速率限制政策

今天所有主要平台都收到了关于速率限制的投诉。用户想要的是公开的限制说明、变更通知和实时用量仪表盘——而不是等请求被限流之后，才被动倒推出发生了什么。现在这种悄悄调整限制的做法，正在同时侵蚀用户对 Codex、Copilot 和 Claude Code 的信任。

### 智能体可观测性与审计轨迹

[@stefanjrice](https://x.com/stefanjrice) [指出了](https://x.com/stefanjrice/status/2044514160034324793) 在得分最高的帖子里点出了这个缺口：“下一个重大突破口是更好的可观测性，让团队能看见智能体为什么采取某个动作，而不仅仅是它有没有完成。”VS Code 新增的历史智能体会话调试日志只解决了其中一部分问题，而这一需求实际上适用于所有智能体平台——尤其是那些运行在远程环境中，或作为定时 routines 运行的自治智能体。

### 与模型无关的智能体可移植性

[@joe_lgtm](https://x.com/joe_lgtm) [指出](https://x.com/joe_lgtm/status/2044538564109803574) 表示，Codex CLI 只需修改配置，就可以接入 OpenRouter、Databricks 以及任何兼容 OpenAI 的 API。[@JulianGoldieSEO](https://x.com/JulianGoldieSEO) [演示了](https://x.com/JulianGoldieSEO/status/2044551342107316475) 则展示了在 OpenCode 中使用 Qwen 3.6。用户希望可以自由替换模型，而不必因此更换智能体工具链——开放式 harness（如 OpenCode、Codex CLI）能做到这一点，而被厂商锁定的工具则做不到。

## 6. 新发布与值得关注的内容

### OpenAI Agents SDK：构建你自己的 Codex

今天最重要的发布（2,111.2 分）是将智能体 harness 与计算执行分离。开发者现在可以把持久执行、记忆、文件/计算机操作和技能，与 7 个沙箱提供商中的任意一个结合使用——也可以自带提供商。harness 已经开源。这让 OpenAI 的智能体战略从“使用我们的产品”转向“构建在我们的平台之上”。（[帖子](https://x.com/snsf/status/2044514160034324793)）

### Claude Code 的 Codex 插件：跨平台智能体集成

OpenAI 发布了一个 Apache-2.0 插件，把 Codex 作为子智能体嵌入 Claude Code。6 个斜杠命令支持代码审查、对抗式审查，以及带状态跟踪的后台任务委派。这不是单纯的竞争动作，而更像是一种合作式竞争——OpenAI 进入 Anthropic 的生态，无论最终由哪个智能体担任编排者，都能获得 Codex 的使用量。（[帖子](https://x.com/TheTuringPost/status/2044561927905677558)）

### 带 fence 一致性的 OpenCode 远程环境

OpenCode 的远程环境实现通过 fence 机制解决了分布式一致性问题——远程写操作会在响应头中返回同步状态，而控制平面会等待同步收敛后再完成读取。未来计划加入 provider plugins（Cloudflare 集成即将到来）。该功能“已经非常非常接近发布”。（[帖子](https://x.com/jlongster/status/2044563154038845775)）

### 用于控制编程智能体的 Flipper Zero 应用

[@kasentuner](https://x.com/kasentuner) 做了一个实体遥控器，用来控制终端编程智能体，并让它进入了 Official Flipper App Catalog。用户可以在房间另一头、窝在沙发上，或者边踱步边控制 Claude Code 会话。这为 AI 辅助开发带来了一种新颖的物理—数字交互方式。（[帖子](https://x.com/kasentuner/status/2044562353459462454)）

### EDINET DB：覆盖 7 种工具的金融数据 MCP

一项覆盖 3,847 家日本上市公司的结构化金融数据服务，通过单一 MCP 服务器连接 Claude Code、Cursor、Codex、Copilot、Cline、Antigravity 和 ChatGPT。数据以确定性方式从 XBRL 文件中解析，不涉及 LLM——“从结构上就不存在幻觉”。该服务覆盖 JP GAAP、IFRS 和 US GAAP 下的 121 个财务字段，并按日更新。（[帖子](https://x.com/edinetdb_en/status/2044536326461264128), [网站](https://edinetdb.com)）

## 7. 机会在哪里

**[+++] 速率限制透明度与用量仪表盘** —— 今天所有主要 AI 编程平台都收到了关于速率限制的投诉：Codex（悄然削减限制，39 条回复）、Copilot（Pro+ 首次撞线）、Claude Code（只有两个 9 的可用性）。The Register 还报道了 Copilot 引发的用户反弹。目前没有任何平台公开清晰的限制标准、变更通知或实时用量仪表盘。谁能率先提供透明、可预测的使用政策，谁就能获得单靠功能对等无法复制的信任优势。

**[+++] Open Agent Harness Ecosystem** — OpenAI open-sourced the Agents SDK harness with 7 sandbox partners. OpenCode is building remote environments with provider plugins. [@atbeme](https://x.com/atbeme) 正在记录 harness 的内部机制。机会在于生态层：标准化的 harness 接口、provider marketplace，以及能跨 OpenCode、Codex CLI 和其他开放式 harness 运作的智能体技能注册体系。“构建你自己的 Codex”这一信息，会催生对组件、托管和集成服务的需求。

**[++] 智能体可观测性平台** —— 得分最高的帖子中，最有洞察力的一条回复把可观测性称为“下一个重大突破口”。VS Code 已经为历史会话增加了调试日志，但需求远不止于此：远程运行的自治智能体、定时 routines，以及多智能体配置（Codex-inside-Claude-Code）都需要更强的可观测能力。随着智能体从交互式工具转向自主执行，能够展示其行动原因、单次决策成本和置信度轨迹的工具将变得不可或缺。

**[++] 垂直领域 MCP 连接器** —— EDINET DB 证明了 MCP 作为通用数据协议的潜力：一个连接器、7 种 AI 编程工具、3,847 家公司，且没有幻觉风险。这一模式可以推广到任何结构化领域数据——医疗记录、法律文件、物流、合规等。每个垂直领域都需要自己的 EDINET 式 MCP 连接器，具备确定性数据提取和跨工具兼容能力。

**[+] 智能体控制的实体接口** —— Flipper Zero 智能体遥控器进入了 Official App Catalog，验证了 AI 编程会话中对实体控制方式的需求。随着智能体会话变得更长、更自主，交互模式将从高度依赖键盘转向“监控 + 干预”。专用硬件（遥控器、状态显示器、通知设备）可能会服务于这一新出现的工作流模式。

## 8. 要点

1. **OpenAI 开源了智能体 harness，并将其与计算执行分离。** 这次 Agents SDK 更新是今天得分最高的项目（2,111.2 分），提供持久执行、记忆、文件/计算机操作和技能，并支持 7 个沙箱合作伙伴。其核心信息是“构建你自己的 Codex”，把 OpenAI 的智能体基础设施从封闭产品转成了平台。（[帖子](https://x.com/snsf/status/2044514160034324793)）

2. **三大主流平台上的速率限制不满已达到临界点。** Codex 因悄然削减限制引发了 39 条回复，Copilot 引来了 The Register 关于用户反弹的报道，而 Claude Code 只有两个 9 的可用性也被视为企业风险。共同失误在于不透明——没有任何平台公开清晰的限制标准或变更通知。（[Codex](https://x.com/rsuyoy/status/2044551173575708762)、[Copilot](https://x.com/TheRegister/status/2044513493580382660)、[Claude](https://x.com/ChrisHayduk/status/2044533710947598833)）

3. **OpenAI 做出了一个可在 Claude Code 内运行的 Codex 插件。** OpenAI 并非只是在竞争，还发布了一个 Apache-2.0 插件，通过 6 个斜杠命令在 Claude Code 内完成审查、调试和后台任务委派。这种竞合并存的做法，使其无论由哪个智能体担任主要编排者，都能获得 Codex 的使用量。（[帖子](https://x.com/TheTuringPost/status/2044561927905677558)）

4. **OpenCode 远程环境已接近发布，并采用了新颖的 fence 一致性机制。** 这套架构通过控制平面代理写操作，同时从本地同步副本读取，并借助 fence 机制确保同步收敛。Cloudflare 集成即将到来，provider plugin 体系也将允许沙箱提供商构建原生集成。（[帖子](https://x.com/jlongster/status/2044563154038845775)）

5. **Claude Code 正被用于构建需要数周训练的企业级金融建模系统。** 这套耗时 40 小时、覆盖 75 家公司的金融建模系统，通过迭代教学来理解财务报表、识别收入驱动因素，并对照 SEC 文件进行验证，展示了 Claude Code 作为复杂、非编程企业工作流平台的能力。这是本系列迄今记录到的最深入企业用例。（[帖子](https://x.com/wmthomson22/status/2044565268102266977)）
