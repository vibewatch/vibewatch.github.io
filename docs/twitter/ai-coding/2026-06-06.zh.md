# Twitter AI 编程 - 2026-06-06

## 1. 人们正在讨论什么

### 1.1 技能、规格与画布成为协调层 🡕

五个信号都指向同一变化：围绕智能体的协调层——规格、技能、插件和画布——比原始上下文长度更重要。最有分量的流程类帖子，关注的是如何让智能体行为具备可移植性、可检查性和可治理性，而不是简单地把更多指导塞进更长的提示词。

[@rohanpaul_ai](https://x.com/rohanpaul_ai) [认为](https://x.com/rohanpaul_ai/status/2063246343842501091)（24 个赞、5 条回复、1,713 次浏览、20 个收藏）认为，GitHub 的 Spec Kit 通过在实现前强制执行“规格优先”的循环，解决了 vibe coding 的问题。这个帖子之所以重要，是因为其附带的仓库截图以及公开仓库和文档，展示了一套具体流程——定义规格、制定计划、拆分任务、实现——覆盖 30 多种编程智能体集成，将规格变成可执行的契约，而不是用过即弃的文档（[仓库](https://github.com/github/spec-kit)、[文档](https://github.github.com/spec-kit/)）。回复进一步明确了从业者的判断：有人说，真正持久的竞争空间正在转向规格、评测和治理工具；也有人表示，没有真正规格阶段的智能体，仍会自信地交付错误代码。

![Spec Kit 仓库截图，展示了这一面向 AI 编码代理、拥有超过 10.9 万星标的规范驱动开发工具包](https://pbs.twimg.com/media/HKIfDz8bIAEgQb-.png)

[@DanKornas](https://x.com/DanKornas) [认为](https://x.com/DanKornas/status/2063244741798494710)（13 个赞、3 条回复、466 次浏览、5 个收藏）认为，编程智能体需要的不是更多上下文，而是更好的技能：按需加载可复用的指令集，而不是把所有内容整段粘进提示词。这与公开的 Agent Skills 规范一致：该规范定义了基于 SKILL.md 的目录结构，并采用渐进式披露；GitHub 的 `gh skill` 发布则为可移植技能增加了安装、版本锁定和发布功能，使其能够在 Copilot、Claude Code、Cursor、Codex 和 Gemini CLI 之间使用（[规范](https://github.com/agentskills/agentskills)、[更新日志](https://github.blog/changelog/2026-04-16-manage-agent-skills-with-github-cli/)）。

[@JohannesVink](https://x.com/JohannesVink) [指出](https://x.com/JohannesVink/status/2063293574133760454)（1 个赞、2 条回复、264 次浏览、1 个收藏）表示，其团队标准仓库中的技能无法在新版 Copilot 应用中加载；而 GitHub 自己的文档目前也将智能体技能限制在云端智能体、代码审查、CLI 和 VS Code 智能体模式中（[文档](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills)）。与此同时，[@GHchangelog](https://x.com/GHchangelog) [报道称](https://x.com/GHchangelog/status/2063010494152061146)（12 个赞、1,233 次浏览、5 个收藏）指出，VS Code 1.122 现在支持由企业管理的插件与 Copilot CLI，从而让管理员能够在两个客户端之间分发共享钩子、MCP 配置和基线标准（[更新日志](https://github.blog/changelog/2026-06-05-enterprise-managed-plugins-in-vs-code-in-public-preview/)）。

GitHub 的 Copilot 应用文档和发布文章，在 UI 层面也推动着同一方向：画布是使用 `/create-canvas` 创建的双向工作界面；而该应用本身则被定位为面向智能体原生开发、以工作树为基础的控制中心，让人们可以直接在共享界面上检查和引导工作，而不是任其埋没在聊天记录中（[文档](https://docs.github.com/en/copilot/how-tos/github-copilot-app/working-with-canvas-extensions)、[博客](https://github.blog/news-insights/product-news/github-copilot-app-the-agent-native-desktop-experience/)）。

**讨论洞察：** 真正有价值的分歧不在于技能是否存在，而在于每个新的智能体界面是否真的都能承载这些技能。文档、插件发布以及 Johannes Vink 的抱怨共同表明，标准化进展快于产品之间的功能对等。

**与前一天对比：** 6 月 5 日已经将“文档优先”的 harness 设计推上台面。6 月 6 日则进一步推进到可移植规格、可安装技能、企业分发以及基于画布的工作界面。

### 1.2 领域定制工作流胜过通用提示词 🡕

四篇技术帖子之所以重要，是因为它们都把 AI 编程封装进了狭窄且可测试的闭环：温室控制、Pine Script 回测、本地代码审查和安全评测。共同点不是更好的通用聊天提示词，而是更紧密的任务专用 harness。

[@VaibhavSisinty](https://x.com/VaibhavSisinty) [报道称](https://x.com/VaibhavSisinty/status/2063109171751588024)（100 个赞、2 条回复、5,007 次浏览、65 个收藏）称，北海道的一名西兰花农户如今即使没有正式编程背景，也能通过 Codex 运营温室。这个说法并不只是一个温情故事，因为附图展示了带有控制器接线和电机组件的日本温室控制面板示意图；帖子还介绍了通过手机控制通风口、监测传感器、由 AI 生成接线图，以及用数据库协调田地、工人和任务。

![温室电机控制装置示意图，展示了控制器接线和电气组件，附于由 Codex 驱动的农场故事中](https://pbs.twimg.com/media/HKGi2lgaYAAXuIq.jpg)

[@Axel_bitblaze69](https://x.com/Axel_bitblaze69) [展示了](https://x.com/Axel_bitblaze69/status/2063087304131158338)（1 个赞、2 条回复、89 次浏览、2 个收藏）介绍了一套工作流：Claude 将口述或书面的交易策略转换为 Pine Script，TradingView 执行回测，用户则根据权益曲线、回撤、交易次数以及图表层面的视觉正确性进行迭代。最关键的细节是要求 Claude 列出歧义而不是自行猜测；此外，还有一条基于 MCP 的路径，让 Claude Code 能够将代码推送到 TradingView、编译代码、读取错误，并将回测结果拉回同一会话。

[@df00z](https://x.com/df00z) [报道称](https://x.com/df00z/status/2063105501794095412)（2 个赞、2 条回复、239 次浏览）介绍了在 Ampere Altra 系统上通过 OpenCode 本地运行 Qwen 3.6 35b a3b：无需 GPU，输入代码时速度约为每秒 120 个 token，输出约为每秒 20 个 token。附带的 diff 截图展示了真实的代码审查场景，包括 token 和成本读数；后续回复称，使用 Vulkan 让 3080 与 CPU 协同后，输入速度约达到每秒 250 个 token，输出速度达到每秒 35 个 token，同时仍能在项目中纠正 Opus 4.8 生成的代码。

[@trynullsec](https://x.com/trynullsec) [报道称](https://x.com/trynullsec/status/2063310859099636034)（24 个赞、6 条回复、337 次浏览、5 个收藏）称，Nullsec S1 在安全场景中达到 0.94 的精确率和 0.91 的召回率，在控制误报方面超过 Codex 5.3 和 Claude Opus 4.7。基准测试细节仅来自帖子和图片，因此公开程度有限；但它仍然值得关注，因为其定位明确是领域定制的安全审查，而不是又一个通用型编程助手。

**讨论洞察：** 这些帖子反复表明，相比通用化，专业化更受青睐：询问歧义、接入正确的外部工具、使用本地硬件进行审查，或针对真正重要的任务进行基准测试。

**与前一天对比：** 本周早些时候，最受关注的帖子围绕控制平面和 Antigravity 界面展开。6 月 6 日，注意力转向这些界面究竟用来做什么：构建可测试的领域专用闭环。

### 1.3 定价压力仍是核心问题 🡒

经济因素仍处于讨论中心。最有力的定价类帖子不是抽象抱怨，而是描述了行为变化、即时追赶额度，以及与低成本或自托管替代方案的明确比较。

[@slicknet](https://x.com/slicknet) [表示](https://x.com/slicknet/status/2063009045720469753)（83 个赞、16 条回复、6,860 次浏览）称，GitHub Copilot 改价后，仅仅五天的极轻度使用就已经消耗了每月 token 配额的 33%。回复让这一问题更加具体：一名用户说用了两次 Opus 后就达到 50%；另一人说现在主要把 Copilot 用于 PR 审查；还有人表示，新版 6 月额度第一天就用完，随后转向 Blackbox AI。

[@0x_beni_](https://x.com/0x_beni_) [分享了](https://x.com/0x_beni_/status/2063253087402205543)（26 个赞、9 条回复、841 次浏览、25 个收藏）介绍了一个面向开源项目的 Codex 套餐：提供六个月的 ChatGPT Pro with Codex、来自 OpenAI 100 万美元 Codex Open Source Fund 的 API 额度，以及有条件的 Codex Security 使用权。截图让补贴变得具体，而回复之所以重要，是因为维护者立即表示已经申请。

![截图列出了面向 Open Source 的 Codex 优惠，包括六个月的 ChatGPT Pro、API 额度，以及有条件提供的 Codex Security 访问权限](https://pbs.twimg.com/media/HKIlvI7WwAAqKOS.jpg)

`/last30days` 的 README 从构建者角度讲述了同样的经济逻辑：它明确将自托管、使用用户密钥的安装方式，与每月 15 至 20 美元的付费搜索产品进行对比，并将价值定位为使用自己的 API 密钥，而不是再租用一层订阅服务（[仓库](https://github.com/mvanhorn/last30days-skill)）。

**讨论洞察：** 回复已经转向战术层面：监控 token 倍率、削减用量、切换工具，或申请额度。争论已经从“AI 编程是否值得付费”转向“哪些工作应该采用哪种计费模式”。

**与前一天对比：** 6 月 5 日，人们已经在转向免费模型和企业促销。6 月 6 日延续了同样的压力，但进一步凸显了消耗速度与补贴之间的权衡。

### 1.4 构建者正在补齐智能体周边缺失的基础设施 🡕

四篇构建者帖子关注的不是模型智力，而是智能体周边缺失的基础设施：一个项目打通了受限的数据源，一个开放了 GitHub 的运行时供嵌入，另外两个则构建了用于权限管理或移动访问的控制平面。

[@sharbel](https://x.com/sharbel) [展示了](https://x.com/sharbel/status/2063369348828610886)（21 个赞、8 条回复、600 次浏览、23 个收藏）介绍了 `/last30days`：这是一项技能，可以并行搜索 Reddit、X、YouTube、TikTok、Hacker News、Polymarket、GitHub 和整个 Web，随后根据真实互动度和市场活跃度为结果评分，再综合生成简报。README 截图很重要，因为它展示了将其安装到 Claude Code、Codex、Cursor、Copilot、Gemini CLI 以及 50 多个智能体宿主中的路径；公开 README 则解释了更深层的主张：没有任何单一 AI 原生拥有所有这些数据源，因此其价值在于利用用户提供的密钥和一次性配置流程，打通这些封闭平台（[仓库](https://github.com/mvanhorn/last30days-skill)）。

**与前一天对比：** 6 月 5 日还只是在原则上讨论控制平面。6 月 6 日，构建者已经开始交付具体产品。

## 2. 什么让人感到沮丧

### 账单冲击与配额不透明

严重程度：高。[@slicknet](https://x.com/slicknet) [表示](https://x.com/slicknet/status/2063009045720469753)（83 个赞、16 条回复、6,860 次浏览）称，极轻度的 GitHub Copilot 使用在五天内就消耗了每月 token 配额的 33%；回复让这种痛感变得具体：一名用户用了两次 Opus 后就达到 50%，另一人将 Copilot 的用途缩减为 PR 审查，还有人说 6 月额度第一天就用完，随后切换到 Blackbox AI。与此同时，[@0x_beni_](https://x.com/0x_beni_) [分享了](https://x.com/0x_beni_/status/2063253087402205543)（26 个赞、9 条回复、841 次浏览、25 个收藏）介绍了一个 1,200 美元的开源 Codex 套餐，人们立即开始申请；而在 [@sharbel](https://x.com/sharbel) [询问](https://x.com/sharbel/status/2063369348828610886) 下的一条回复中，有人询问 `/last30days` 是否能通过仅为每次查询路由合适的数据源来降低 token 消耗。这值得投入建设，因为用量规划已经成为产品问题：人们正根据消耗速度，主动调整工具、工作负载和审批阈值。

### 技能与治理领先于产品一致性

严重程度：中高。[@DanKornas](https://x.com/DanKornas) [认为](https://x.com/DanKornas/status/2063244741798494710)（13 个赞、3 条回复、466 次浏览、5 个收藏）认为，更好的技能胜过更大的上下文窗口；GitHub 的 `gh skill` 预览版以及开放的 Agent Skills 规范，也通过跨多个宿主的可移植、可版本化安装支持了这一判断（[更新日志](https://github.blog/changelog/2026-04-16-manage-agent-skills-with-github-cli/)、[规范](https://github.com/agentskills/agentskills)）。但 [@JohannesVink](https://x.com/JohannesVink) [展示了](https://x.com/JohannesVink/status/2063293574133760454)（1 个赞、2 条回复、264 次浏览、1 个收藏）指出，新版 Copilot 应用仍然无法加载仓库托管的技能，尽管 GitHub Docs 表示技能可用于云端智能体、代码审查、CLI 和 VS Code 智能体模式（[文档](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills)）。这值得投入建设，因为团队现在已经有了封装智能体行为的可移植方式，但仍不能指望每个产品界面以同样方式遵循这些技能。

### 智能体会话仍会卡在审批和重启上

严重程度：中高。[@__morse](https://x.com/__morse) [表示](https://x.com/__morse/status/2063199801588502847)（2 个赞、3 条回复、104 次浏览）称，Kimaki 现在会在十分钟后自动拒绝 OpenCode 权限提示，仅将关键调用通过 Discord 升级审批；这只有在默认行为很容易陷入死锁时才有意义。[@sharbel](https://x.com/sharbel) [表示](https://x.com/sharbel/status/2063369348828610886) 下的一条回复表示，许多宿主仍缺少在重启后保留会话且不发生静默截断的能力；[@itsnishu](https://x.com/itsnishu) [分享了](https://x.com/itsnishu/status/2063257418398871627)（9 个赞、5 条回复、168 次浏览）则将 Sakura 描述为本地 Claude、Codex 和 OpenCode 会话的一种移动端解决方案。这值得投入建设，因为长时间运行的智能体工作仍会被审批对话框、重启以及只能在桌面前操作等问题困住。

### 单一供应商宕机仍会让编程工作停摆

严重程度：高。[@The_Cyber_News](https://x.com/The_Cyber_News) [报道称](https://x.com/The_Cyber_News/status/2063084278372864441)（5 个赞、1 条回复、259 次浏览）介绍了一次同时影响 claude.ai、Claude API、Claude Code 和 Claude Cowork 的服务中断；链接文章称，故障于 6 月 5 日 15:08 UTC 开始，并于 18:27 UTC 完全恢复（[文章](https://cybersecuritynews.com/anthropics-claude-services-down/)）。[@df00z](https://x.com/df00z) [运行中](https://x.com/df00z/status/2063105501794095412)（2 个赞、2 条回复、239 次浏览）展示了通过 OpenCode 使用 Qwen 本地模型的反例，因为它说明了用户为何希望拥有不依赖单一托管供应商的可用备用路径。这值得投入建设，因为如今服务中断影响的是正在进行的编程工作流，而不只是随意的聊天会话。

## 3. 人们希望有什么

### 在每个智能体界面都能运行的可移植规格与技能层

人们想要的是一层可复用的流程，能够随着他们在 Copilot、Claude Code、Codex、Cursor 以及更新的应用界面之间切换而持续存在。[@rohanpaul_ai](https://x.com/rohanpaul_ai) [将其描述为](https://x.com/rohanpaul_ai/status/2063246343842501091)（24 个赞、5 条回复、1,713 次浏览、20 个收藏）将 Spec Kit 视为阻止智能体在规则明确前直接写代码的方式；[@DanKornas](https://x.com/DanKornas) [将其描述为](https://x.com/DanKornas/status/2063244741798494710)（13 个赞、3 条回复、466 次浏览、5 个收藏）则将可复用技能视为避免把每条指导都塞进提示词的方式。缺失的部分是一致性：[@JohannesVink](https://x.com/JohannesVink) [展示了](https://x.com/JohannesVink/status/2063293574133760454)（1 个赞、2 条回复、264 次浏览、1 个收藏）表示，Copilot 应用目前仍然打破了这一预期，尽管 GitHub 正在推出 `gh skill` 和企业托管插件。现有标准部分满足了需求，但产品层仍不均衡。机会：直接且竞争激烈。

### 具备预算意识的路由与用量可视化

人们实际上是在要求一种工具：预测消耗，将工作路由给满足要求的最低成本模型，并在触及限制前解释用量。[@slicknet](https://x.com/slicknet) [展示了](https://x.com/slicknet/status/2063009045720469753)（83 个赞、16 条回复、6,860 次浏览）指出，当前的 token 计量方式甚至会让轻度用户感到意外；[@0x_beni_](https://x.com/0x_beni_) [分享了](https://x.com/0x_beni_/status/2063253087402205543)（26 个赞、9 条回复、841 次浏览、25 个收藏）则介绍了面向开源维护者的额度和套餐式解决方案。最明确的愿望来自 [@sharbel](https://x.com/sharbel) [询问](https://x.com/sharbel/status/2063369348828610886) 下的一条回复：有人询问 `/last30days` 是否能只路由查询所需的数据源，而不是每次都承担所有数据源的成本。额度、BYOK 和自托管工具如今可以部分解决这一问题，但规划能力和可预测性仍然缺失。机会：直接。

### 离开办公桌后仍能保留会话状态、审批和上下文的远程控制

构建者希望离开办公桌，却不丢失会话，也不被审批卡住。[@itsnishu](https://x.com/itsnishu) [分享了](https://x.com/itsnishu/status/2063257418398871627)（9 个赞、5 条回复、168 次浏览）将 Sakura 作为本地 Claude、Codex 和 OpenCode 会话的手机控制器；[@__morse](https://x.com/__morse) [分享了](https://x.com/__morse/status/2063199801588502847)（2 个赞、3 条回复、104 次浏览）则展示了 Kimaki 通过自动拒绝过期权限提示、仅升级关键请求，来维持长时间运行会话的尝试。[@sharbel](https://x.com/sharbel) [补充说](https://x.com/sharbel/status/2063369348828610886) 下的一条回复表示，许多宿主仍无法在重启后干净地保留会话状态；而 GitHub 的 Copilot 应用和文档将画布定位为共享工作界面的起点，而不是最终解决方案（[文档](https://docs.github.com/en/copilot/how-tos/github-copilot-app/working-with-canvas-extensions)、[博客](https://github.blog/news-insights/product-news/github-copilot-app-the-agent-native-desktop-experience/)）。各个组件已经存在，但用户仍需要自行拼装。机会：直接。

### 带有真实评测闭环的领域专用智能体套件

最有力的技术帖子表明，人们需要真正理解某个领域的智能体套件：它们能够提出正确的澄清问题，生成可验证的产物，并使用领域指标而非通用代码质量来衡量结果。[@trynullsec](https://x.com/trynullsec) [报道称](https://x.com/trynullsec/status/2063310859099636034)（24 个赞、6 条回复、337 次浏览、5 个收藏）展示了安全定制模型的精确率和召回率数据；[@Axel_bitblaze69](https://x.com/Axel_bitblaze69) [展示了](https://x.com/Axel_bitblaze69/status/2063087304131158338)（1 个赞、2 条回复、89 次浏览、2 个收藏）介绍了 Claude 到 TradingView 的回测闭环；[@VaibhavSisinty](https://x.com/VaibhavSisinty) [报道称](https://x.com/VaibhavSisinty/status/2063109171751588024)（100 个赞、2 条回复、5,007 次浏览、65 个收藏）则展示了由 Codex 驱动、结合硬件图纸和传感器操作的农场控制工作流。通用前沿智能体可以部分满足这一需求，但当前证据更支持缩小上下文并加入明确评测。机会：具有竞争性且正在形成。

## 4. 正在使用的工具与方法

| 工具 | 类别 | 情绪 | 优势 | 局限 |
|---|---|---|---|---|
| Spec Kit | 工作流工具包 | (+) | 强制执行规格 -> 计划 -> 任务 -> 实现流程，并支持 30 多种智能体集成 | 需要前期编写，且本身无法解决下游产品界面的缺口 |
| Agent Skills | 技能打包标准 | (+/-) | 可移植的 SKILL.md 目录、渐进式披露、版本锁定，以及跨宿主复用的行为 | 在 Copilot 应用等宿主中的支持仍不均衡 |
| GitHub Copilot App / Canvases | 智能体工作区 | (+/-) | 基于工作树的会话、My Work 控制中心、共享画布、`/create-canvas` 工作流 | 仍处于技术预览阶段，并存在仓库技能兼容性缺口 |
| GitHub Copilot SDK | 运行时 / SDK | (+) | 稳定运行时、六种语言、自定义工具、钩子、MCP、BYOK | 团队仍需自行构建 UX、审批模型和产品界面 |
| Codex / ChatGPT Pro | 智能体运行时 | (+/-) | 可信的非工程师操作工作流、开源额度，以及不断扩展的远程/移动访问 | token 经济性和对补贴的依赖仍是核心问题 |
| Claude Code | 智能体 CLI | (+/-) | 擅长领域闭环、歧义处理和 MCP 辅助工作流 | 托管服务中断和对单一供应商的依赖仍是风险 |
| OpenCode + 本地 Qwen | 开放/本地运行时 | (+) | 可信的本地代码审查、开放模型的灵活性，以及在普通硬件上的实用吞吐量 | 需要手动配置、硬件调优，以及额外的会话/权限工具 |
| Kimaki | 编排层 | (+) | 将 Discord 频道作为项目、线程作为会话，提供队列、工作树、手机 diff 查看器，并复用订阅 | 依赖 Discord/OpenCode，仍在解决审批和会话生命周期摩擦 |
| Nullsec S1 | 专用安全模型 | (+) | 明确采用精确率/召回率框架，并在安全场景中降低误报 | 当前公开证据仅限于供应商自己的基准测试帖子 |

总体而言，人们对结构层——规格、技能、运行时和编排封装——的态度最为积极；对昂贵的托管智能体则褒贬不一。最常见的解决方式，是围绕模型增加更多流程：代码之前先写规格、用技能替代提示词堆砌、通过 Discord 或移动端控制平面操作，或使用本地开放模型进行溢出处理和故障备用。最明显的迁移模式，是从单一界面的提示词闭环转向打包流程加多界面控制；最清晰的竞争动态，则是希望掌控完整闭环的托管运行时，与让这些运行时更便宜、更可移植或更可控的封装工具之间的竞争。

Spec Kit 是“流程成为产品”的最清晰例子。其公开仓库和文档将需求、计划和任务变成实现前的一等产物；[@rohanpaul_ai](https://x.com/rohanpaul_ai) [进行了](https://x.com/rohanpaul_ai/status/2063246343842501091)（24 个赞、5 条回复、1,713 次浏览、20 个收藏）下的回复则明确说明了其理由：如果规格不完善，智能体就会自行猜测。

`/last30days` 将同一原则应用到了研究，而不是编程。其独特之处不只是数据源数量多，而是将 Reddit、X、YouTube、TikTok、Hacker News、Polymarket、GitHub 和 Web 搜索打包成一个可安装技能，使其能够跨多个智能体宿主使用；回复也立即开始追问路由效率和会话持久性。

GitHub Copilot SDK、Kimaki 和 Sakura 从三个不同角度展示了同一种构建模式。GitHub 正在开放运行时，Kimaki 通过 Discord 线程、队列、工作树和适合手机的审查功能封装现有运行时，而 Sakura 则在推动面向本地会话的直接移动控制界面。这些项目反复针对的痛点是编排、权限处理、状态连续性和远程访问，而不是原始模型能力不足。

## 7. 机会在哪里

**[+++] 面向智能体宿主的可移植流程层** —— 证据来自第 1、2、3 和 5 节：Spec Kit、Agent Skills、`gh skill`、企业托管插件以及 Copilot 画布，都指向对可复用行为的需求，使其能够跨产品持续存在；而 Johannes Vink 对 Copilot 应用的抱怨则表明，这一缺口仍然真实存在。这一机会很强，因为用户和平台正从两端汇聚到同一种基础原语上。

**[++] 具备预算意识的路由与支出控制** —— 证据来自 Copilot 消耗过快的抱怨、Codex 开源额度套餐、`/last30days` 提出的路由问题，以及 Kimaki 对复用现有订阅的强调。这一机会中等，因为痛点强烈且会改变用户行为，但市场上已经充斥着各种不完整的解决方案。

**[++] 持久的远程控制与会话连续性** —— 证据来自 Kimaki 的权限兜底机制、Sakura 的移动控制器、`/last30days` 下关于重启后安全保留会话的回复，以及 Copilot 应用推动可检查共享界面的做法。这一机会中等，因为多个构建者已经证明了需求，但尚无一种方案明显占据主导地位。

**[+] 带有内置评测的领域专用智能体套件** —— 证据来自 Nullsec S1 的安全基准声明、Claude 到 TradingView 的回测闭环、本地 Qwen 代码审查，以及 Codex 驱动的温室控制案例。这一机会仍处于早期阶段，因为相关使用场景很有吸引力，但目前仍分散在不同领域，主要通过个别从业者报告呈现。

## 8. 要点

1. **协调层正在移到提示词之上。** 最有力的流程证据来自 Spec Kit、Agent Skills、企业托管插件和 Copilot 画布；它们都将行为封装在一次性提示词闭环之外。（[来源](https://x.com/rohanpaul_ai/status/2063246343842501091)）
2. **最可信的 AI 编程案例都经过领域调优且可测试。** 温室控制图、Pine Script 回测、本地代码审查 diff 以及安全场景中的精确率/召回率数据，都胜过模糊的“AI 会写代码”论断，因为它们展示了评测闭环。（[来源](https://x.com/Axel_bitblaze69/status/2063087304131158338)）
3. **经济因素对产品使用方式的影响，已经不亚于模型质量。** 一名 Copilot 用户仅轻度使用五天就消耗了每月额度的 33%；另一篇帖子则宣传为开源维护者提供六个月的 Codex 补贴。（[来源](https://x.com/slicknet/status/2063009045720469753)）
4. **构建者正在竞相补齐智能体基础设施的缺口。** `/last30days`、Copilot SDK、Kimaki 和 Sakura 都在解决编排层缺口——跨平台数据访问、运行时嵌入、审批处理和远程控制，而不是原始生成质量。（[来源](https://x.com/sharbel/status/2063369348828610886)）
