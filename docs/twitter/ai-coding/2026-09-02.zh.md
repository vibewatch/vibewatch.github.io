# Twitter AI 编程 - 2026-09-02

## 1. 人们在讨论什么

### 1.1 Antigravity 的讨论从泛泛热度转向具体的 Gemini 3.8 上线信号 (🡕)

当天 Twitter 上最强的一簇内容，已经不再是对 Google 编程栈的抽象称赞。讨论重点变成了 Gemini 3.8 Flash 发布当天，Antigravity 内部到底发生了什么：模型选择器里某些模型消失了、二进制里出现了额外模型的引用、用户一线感受是限制放松了，以及 Google 自己发出的定价与可用性公告。至少有 4 条独立样本共同支撑了这个主题。

[@thtbee_](https://x.com/thtbee_) [提到](https://x.com/thtbee_/status/2094818778593067502) (109 个赞，11 条回复，7,983 次浏览，5 次收藏)，Gemini 3.5 Flash 已经从 Antigravity 的模型选择器里消失，并把这当成 Gemini 3.8 Flash 即将上线的信号。回复很快把话题从基准转成产品成熟度：有人说不会想念 3.5，也有人立刻追问，是否会有更强的 Pro 档位。

![Antigravity 模型选择器截图，显示已选中 Gemini 3.7 Flash High，而 Gemini 3.5 Flash 已不见踪影](https://pbs.twimg.com/media/HRJKkcYawAESPqr.jpg)

[@mrfanduu](https://x.com/mrfanduu) [报告](https://x.com/mrfanduu/status/2095076109696250059) (389 个赞，31 条回复，21,629 次浏览，31 次收藏，8 次引用)，他们发现了对 `glm-5.2-fp8` 的引用，位置就在 `antigravity-cli` 1.1.24 里。那张图之所以重要，是因为它把一条传闻落成了一个具体界面、一个具体提供商，以及一个和二进制审计绑定的显示名称；而回复则立刻开始争论，Google 真要上的到底该是 GLM 5.2 还是 5.3。

[@SalenoXP](https://x.com/SalenoXP) [说](https://x.com/SalenoXP/status/2095083480216416396) (302 个赞，35 条回复，17,219 次浏览，26 次收藏，3 次引用)，Antigravity 的使用体验突然像“被加强过”一样，要么是 Google 抬高了限制，要么是 Gemini 3.8 Flash 在类似负载下的效率，实质上比之前服务这些任务的模型更高。这是当天最清楚的实践者帖子之一，因为它不是靠基准分数评价产品，而是直接从配额行为来判断。

**与前日对比：** 2026-09-01 的 Antigravity 讨论，重点还是 `/boost`、3.7 Flash 的展示案例，以及公开的“研究级效果”宣称。到 2026-09-02，这股热度已经转成围绕 Gemini 3.8 Flash 及其相邻模型界面的具体 rollout 观察。

### 1.2 GitHub Copilot 成了模型发布与真实世界评估相遇的分发层 (🡕)

GitHub Copilot 这一天出现时，已经不太像一个单纯的编程助手品牌，而更像一层切换模型、控制推理成本，以及承接长时智能体宣称的分发层。至少有 5 条高信号内容支撑了这个判断：GitHub 上线 Claude Fable 5.1、Copilot 产品界面里的直接确认、一款公开的一次性游戏演示、SOMA 给 Copilot 加的压缩层，以及围绕可审查性与治理展开的回复讨论串。

[@github](https://x.com/github) [宣布](https://x.com/github/status/2094936182945886329) (153 个赞，23 条回复，21,087 次浏览，14 次收藏，3 次引用)，Claude Fable 5.1 已在 GitHub Copilot 中正式可用，面向长时编程任务、深度代码库研究和复杂的智能体式工作流。回复补上的关键企业保留条件是：与 Copilot 里的其他 Claude 模型不同，Fable 5.1 默认要求为 Anthropic 的安全分类器保留数据，只有符合条件的企业客户，才可能在一个有时限的例外条件下获得 zero-retention 访问。另一条来自 [@enhansai](https://x.com/enhansai) 的回复则指出，长时任务的失败方式和短任务不同，因为它可能在“三步之前”就已经走偏，但最终输出仍然能编译。

[@code](https://x.com/code) [从产品账号角度再次确认了](https://x.com/code/status/2095158875804549282) (157 个赞，13 条回复，18,603 次浏览，13 次收藏)这次发布，而截图显示，Fable 5.1 已经可以在 Copilot Agent mode 中被直接选择。最有价值的回复并不是欢呼，而是在问这个模型能否从错误转向中恢复、能否避免凭空发明辅助文件，以及在真实代码库里是否还能保持可审查性。

[@LisaFlorentina8](https://x.com/LisaFlorentina8) [概括了](https://x.com/LisaFlorentina8/status/2095067702624940068) (11 个赞，12 条回复，395 次浏览) SOMA 在 GitHub Copilot 上的发布：通过在智能体的重复上下文送进模型前先压缩，DeepSeek V4 Pro 会话大约能省下 10% 的 token，而且早期访问阶段赠送 5 美元额度、没有平台费。真正重要的细节，不在价格，而在架构：SOMA 被放在智能体和模型之间，而不是被定位成另一个替代模型。

**与前日对比：** 2026-09-01 的 Copilot 更像一个现代化和代码审查界面。到 2026-09-02，它更像企业侧的分发层：新模型和新基础设施都会先在这里经受实战检验。

### 1.3 Spec、技能和市场继续取代自由提示词，成为控制层 (🡕)

面对 AI 生成的“糊感”，人们给出的答案仍然不是“换个更聪明的模型”，而是“增加结构、把判断打包、再把这些东西分发出去”。有 4 条内容把这个趋势讲得特别清楚：围绕 Spec Kit 的规格优先工作流、庞杂的智能体商店与注册表地图、Obsidian vault 技能，以及市场里的记忆插件。

[@txbrraa](https://x.com/txbrraa) [认为](https://x.com/txbrraa/status/2095061557180825911) (56 个赞，18 条回复，790 次浏览，11 次收藏)，GitHub 的 Spec Kit 通过“先写规格说明、再动手编码”修复了 vibe coding 最大的问题。它链接的 [repo](https://github.com/github/spec-kit) 把这套可复用流程写得很清楚：围绕 `/speckit-constitution`、`/speckit-specify`、`/speckit-plan`、`/speckit-tasks`、`/speckit-implement` 和 `/speckit-converge` 组织起来；而最强的回复则说，真正的考验不是第一次演示看起来多干净，而是第三轮改需求之后，规格说明和代码还能不能保持一致。

[@illyism](https://x.com/illyism) [断言](https://x.com/illyism/status/2094925888991203395) (14 个赞，7 条回复，4,413 次浏览，79 次收藏)，“传统 SEO 已死”，因为 AI 智能体、插件和技能现在都需要在第一方商店、规范化注册表、托管型 MCP 目录和社区目录里争夺分发。那条讨论串点名了 ChatGPT 应用和 GPTs、Claude Marketplace、Claude Code 目录、Cursor 插件市场、GitHub Copilot 插件、官方 MCP Registry、Smithery、Glama、PulseMCP 和 Vercel 市场界面，这让“发现”本身看起来像一个新的类别问题。

### 1.4 本地优先和编排层继续包裹现有智能体，而不是替换它们 (🡕)

另一个相互呼应、但相对独立的主题，是那些在底层替换后端、搜索层或控制平面、但继续保留熟悉智能体工作流的基础设施正在增长。4 条内容特别突出：Unsloth 让现有智能体接本地模型、Agentic API 在 vLLM 前面做服务端编排、zg 负责本地优先检索，以及 Orca 提供并排 worktree 编排。

[@starmexxx](https://x.com/starmexxx) [表示](https://x.com/starmexxx/status/2095072097466741027) (24 个赞，12 条回复，1,026 次浏览，13 次收藏)，Unsloth 让付费订阅变得“可选”，因为用户可以在 Claude Code、Codex 和 OpenCode 后面改接本地开源模型。它链接的 [repo](https://github.com/unslothai/unsloth) 确认支持本地 GGUF 和 MLX 模型、兼容 OpenAI 和 Anthropic 的 API，以及 `unsloth start claude` 和 `unsloth start codex` 这样的直接命令。

[@techNmak](https://x.com/techNmak) [把](https://x.com/techNmak/status/2095247529525047448) (14 个赞，1 条回复，734 次浏览，14 次收藏) Agentic API 描述成 vLLM 前面的一层有状态服务：它负责会话状态、tool-call 循环、续跑、持久化，以及兼容 OpenAI Responses 的行为。[repo](https://github.com/vllm-project/agentic-api) 把定位说得很直白：客户端只发出一次调用，gateway 则接手状态注水、服务端工具、流式输出和后续 continuation。

![Agentic API 总览图，展示一个位于客户端和 vLLM 之间的 Rust gateway，负责状态注水、服务端工具和 SQLite 持久化](https://pbs.twimg.com/media/HRPQc4lbsAA04zI.jpg)

[@QwenDevs](https://x.com/QwenDevs) [分享了](https://x.com/QwenDevs/status/2095157452904018263) (11 个赞，2 条回复，415 次浏览，6 次收藏) [zg](https://github.com/zvec-ai/zvec-grep)，这是一个本地优先搜索工具，把语义搜索、BM25、混合检索和 `rg` 放进同一个界面，同时面向开发者和智能体。仓库把它定位成一种办法，用来减少大范围扫描、重复工具调用和上下文膨胀。

[@DanKornas](https://x.com/DanKornas) [提到了](https://x.com/DanKornas/status/2095274056039739753) (2 个赞，3 条回复，402 次浏览) [Orca](https://github.com/stablyai/orca)，这是一个编排环境，可以让 Codex、Claude Code、OpenCode 或 Pi 在不同 worktree 里并排运行，并统一追踪在一个工作空间中，还配有一个移动伴侣应用来收通知和继续跟进。回复把它的核心价值主张说得更清楚：只要每个并行智能体都有自己的 git 通道，管理它们就会容易得多。

![Orca README 截图，展示多个 CLI 智能体在独立 worktree 中并排运行，并配有移动伴侣应用](https://pbs.twimg.com/media/HRPopO1WoAEgMLB.jpg)

**讨论要点：** 这一簇内容反复承诺的，是连续性。用户想保留自己已经熟悉的工具和习惯，同时在底层替换成本、隐私、状态管理、检索质量或并行能力。

**与前日对比：** 2026-09-01 的成本控制讨论，还主要围绕压缩层和本地 API 作为权宜方案。到 2026-09-02，这一层看起来已经更像产品了：搜索、编排、有状态 gateway 和本地运行时，都各自长出了清晰的产品故事。

## 2. 令人困扰的问题

### 长时运行智能体即使推理看起来很强，也仍然会在执行和审查上翻车

最尖锐的挫败感是：再强的模型发布，也解决不了长时工作在操作层面的那一团乱。Fable 5.1 的发布讨论串里，[@enhansai](https://x.com/enhansai) [回复](https://x.com/github/status/2094936182945886329)说，长任务可能在“三步之前”就已经失败，但最后产物仍然能编译；而 [@phicerhq](https://x.com/phicerhq) [又补充说](https://x.com/code/status/2095158875804549282)，团队真正会拿来判断的，是错误转向后的恢复能力、上下文保持、可审查性和可靠性。[@SnorkelAI](https://x.com/SnorkelAI) [进一步给出了](https://x.com/SnorkelAI/status/2095219425276273102) 更具体的基准说法：在 Terminal-Bench+ 上，Fable 5.1 的错误主要集中在终止、工具使用和输出格式，而不是推理本身，尽管它每次成功运行的 token 用量还能少 58%。严重程度：高。这非常值得围绕它做产品，因为人们现在要的是更好的执行轨迹、更好的恢复点，以及更清楚的审查产物，而不只是更会写字。

![Fable 5.1 的失败模式图，显示在基准拆解中，termination、tool use 和输出错误占了大头](https://pbs.twimg.com/media/HRO2kiVXwAEmVnR.png)

[@kimburgaard](https://x.com/kimburgaard) [描述了](https://x.com/kimburgaard/status/2095245983689154688) 这个问题在 PR 审查里的第一手版本。他说，某个 PR 上 Copilot 审查的发现数依次从 5、4、3、3、3、4、1、2 逐渐收敛后合并；而 Claude Code 审查一个 cached-token billing PR 时，跑了 9 轮仍然产出 123 条行内发现，最后他直接关掉没合并。他的应对方式，并不是放弃 AI 审查，而是做了公开的 review-triage skills，把那些除非会造成高风险生产事故、否则都只是猜测性或潜在性的发现压下去。

![审查轮次图，对比逐步收敛的 Copilot review，与一个产出 123 条发现后被关闭的 Claude Code review](https://pbs.twimg.com/media/HRPPFOla8AAzMBV.jpg)

![审查分诊表，按证据等级把 PR findings 分成 proven、latent、speculative、opinion、contract 和 consequence](https://pbs.twimg.com/media/HRPPFOzaEAABav-.jpg)

这批数据里最好的应对模式，是坚持明确证据。[@rseroter](https://x.com/rseroter) [指向了](https://x.com/rseroter/status/2094823346164691420) 一个 Antigravity Teamwork walkthrough，其中截图显示，在宣布任务收尾前，已有 758 个测试通过、247 个 E2E 测试通过、typecheck 干净、生产构建也干净。这正是那些更弱的发布日宣称里最缺的东西。

### 隐藏路由、配额行为和成本控制层正在扭曲产品评估

人们显然很挫败，因为他们往往不是通过清晰的更新日志，而是通过盯限制、盯缺失模型，或盯压缩提示条，才知道产品到底变了什么。[@SalenoXP](https://x.com/SalenoXP) [说](https://x.com/SalenoXP/status/2095083480216416396) Antigravity 突然显得更慷慨，而 [@thtbee_](https://x.com/thtbee_) [跟踪了](https://x.com/thtbee_/status/2094818778593067502) 模型选择器中某个模型的消失，[@mrfanduu](https://x.com/mrfanduu) [则跟踪了](https://x.com/mrfanduu/status/2095076109696250059) 一个隐藏的二进制引用。Copilot 这边，[@LisaFlorentina8](https://x.com/LisaFlorentina8) [把](https://x.com/LisaFlorentina8/status/2095067702624940068) SOMA 描述成一种在不改变可见工作流的前提下，回收约 10% token 成本的方法；而 [@github](https://x.com/github) [则不得不在回复里解释](https://x.com/github/status/2094936182945886329)，Fable 5.1 在 Copilot 里默认还带数据保留。严重程度：中到高。这值得围绕它做产品，因为用户想要的是透明的限制记账、看得见的模型路由，以及自己能检查的成本控制层。

这种挫败感，在人们从营销走向真实使用时最明显。[@SimonasLTU1](https://x.com/SimonasLTU1) [说](https://x.com/SimonasLTU1/status/2095067177778852214)，自己通过 OpenRouter 试 Fable 5.1，很快就把一小笔余额烧光了，而截图直接拍下了那条额度耗尽的错误弹窗。[@starmexxx](https://x.com/starmexxx) [给出的回应](https://x.com/starmexxx/status/2095072097466741027) 是一个本地优先替代方案：前端继续用 Claude Code 或 Codex，后端则改接自己机器上的 Unsloth 开放模型。

### 移动端和后续跟进界面在真实编程工作流里仍然会掉链子

当天最弱的一环，不是桌面端智能体能力，而是人一离开主工作站之后会发生什么。[@heitor_lessa](https://x.com/heitor_lessa) [说](https://x.com/heitor_lessa/status/2095247303896408238)，ChatGPT Work 加上一套移动端 Codex 权宜方案，仍然显得太不完整，以至于他可能下个月就取消订阅；而截图也解释了原因：等完整消息时流式输出被打断，以及在一个与 PR 有关的工作流中出现 unknown error。严重程度：中。这值得围绕它做产品，因为长时智能体工作流越来越需要在手机上做升级、跟进和审查，而现有界面偏偏就在这些交接时刻失灵。

![ChatGPT Work 移动端界面截图，显示在等待完整消息时流式输出被中断](https://pbs.twimg.com/media/HRPQUM7XkAMEMrt.jpg)

![ChatGPT Work 移动端界面截图，显示一个与 PR 有关的工作流中出现 unknown error](https://pbs.twimg.com/media/HRPQUNcaUAAQBBO.jpg)

相比之下，[@DanKornas](https://x.com/DanKornas) [提到 Orca 的一个原因](https://x.com/DanKornas/status/2095274056039739753)，就是它带有一个移动伴侣应用来收通知和继续跟进；而 [@kimburgaard](https://x.com/kimburgaard) [展示了](https://x.com/kimburgaard/status/2095245983689154688) 一旦 AI 审查循环开始自转，分诊工作会积累得多快。这个对比说明，未满足的需求并不是抽象意义上的“手机上也能用 AI”，而是一个可靠的尚未收尾的智能体工作的控制界面。

## 3. 人们期望的功能

### 带明确检查点、可验证的长时工作流

人们最想要的，不是又一个自治模式，而是一个能让人信它的自治模式。GitHub 发布 Fable 5.1 之后的回复，反复在问错误转向后的恢复、上下文保持和可审查性；而 [@rseroter](https://x.com/rseroter) 指向的 Teamwork 流程，则拿一串通过的测试和构建结果，证明任务已经收尾；[@kimburgaard](https://x.com/kimburgaard) 更是不得不自己做出审查分诊技能，来压住 PR 审查的反复折腾。这是一个现实而紧迫的需求，因为长时智能体已经存在，人们缺的只是标准化的证明层。机会：直接。

### 可跨智能体宿主迁移的技能、记忆和知识层

人们显然在要求一种能跨工具边界存活下来的工作流智能。[@RoundtableSpace](https://x.com/RoundtableSpace) 展示了能跨 Claude Code、Codex 和 OpenCode 运行的 Obsidian 技能，[@DhravyaShah](https://x.com/DhravyaShah) 展示了 supermemory 如何延伸到 Cursor 以及一长串其他宿主，而 [@illyism](https://x.com/illyism) 则画出了一整层商店、注册表和目录，让这些包开始在其中竞争。这个需求既现实，也带战略意义：人们想要持久行为和持久记忆，但不想为每个运行框架都重写一遍。机会：竞争较强。

### 在保持同一可见工作流的前提下，换成更便宜、也更可检查的底层基础设施

当天构建者的大量精力，都花在替换隐藏管道，而不是替换前端。[@LisaFlorentina8](https://x.com/LisaFlorentina8) 把 SOMA 描述成 Copilot 底下的一层压缩层，[@starmexxx](https://x.com/starmexxx) 把 Unsloth 描述成保留 Claude Code 或 Codex、但改接本地模型的方法，[@techNmak](https://x.com/techNmak) 把 Agentic API 描述成 vLLM 前面的服务端状态与工具层，而 [@QwenDevs](https://x.com/QwenDevs) 则把 zg 定位成本地优先的开发者与智能体检索层。这个需求极其现实，而且人们已经在积极试验。机会：竞争较强。

### 面向尚未收尾的智能体工作的可靠远程控制

Burke Holland 的游戏演示、Orca 的移动伴侣应用，以及 Heitor Lessa 对移动端 ChatGPT Work 的抱怨，都指向同一个需求：一旦任务活得比一个桌面会话更久，人们就想从别处稳定地监控、解阻、审批或终止它。从公开证据看，这个需求里真正带情绪的部分，不是便利性，而是控制感。机会：直接。

Fledgling Game 是当天最典型的“少说、多给证据”型产物。[@burkeholland](https://x.com/burkeholland) 没有只发一段视频，而是把游戏直接放到了 [fledglinggame.com](https://fledglinggame.com/) 上，同时也坦白说托管很便宜、没有做过压测。这种“公开产物 + 明确保留意见”的组合，让它的说服力比一段打磨得很漂亮的演示视频更强。

第二类重复出现的构建模式，是保留熟悉界面、替换底层一层。SOMA 在 Copilot 和模型之间压缩上下文，Agentic API 在客户端和 vLLM 之间接手状态与工具循环，zg 则站在用户和代码库之间，把搜索工作压缩成排序更好的证据。这些工具都没有要求用户放弃外围工作流。

第三个重复模式，是把记忆和协同外置出来。obsidian-skills 和 supermemory 把上下文推到可复用包和插件里，而 Orca 则把多智能体工作明确改写成一个 worktree 加移动控制的问题，而不再是一堆相互重叠的会话。这些构建背后的共同触发点，不是原始模型能力不够，而是让智能体工作保持可检查、可重复、可迁移时的操作摩擦。

## 6. 新动态与亮点

### Qwen3.8-Max-0902 拿下公开 WebDev 排行榜第一
[@Alibaba_Qwen](https://x.com/Alibaba_Qwen) [表示](https://x.com/Alibaba_Qwen/status/2094976556494209206) (91 个赞，7 条回复，5,530 次浏览，7 次收藏，7 次引用)，Qwen3.8-Max-0902 在 Code Arena: WebDev 上以 1691 分拿到第 1。被引用的基准测试帖子来自 @arena，其中说它比 Claude Opus 5 高 3 分、比 Kimi K3 高 17 分、也比前一个版本的 Qwen3.8-Max 高 22 分，同时还宣称价格上有更强的 Pareto 位置。它之所以重要，是因为这给当天带来了一个具体的、既不是 Google 也不是 GitHub 的模型对比信号。

### 基准测试开始被拿来推销“把任务交给智能体”，尤其是对新手开发者
[@Gyome1_](https://x.com/Gyome1_) [认为](https://x.com/Gyome1_/status/2094897410413678719) (5 个赞，108 次浏览)，一项基于 GitHub 的研究发现，开发者把任务交给 AI 智能体后，平均产出提高了 26%，而收益最大的群体是初级开发者。随附图表之所以值得注意，是因为它展示了采用 Claude 之后，每月涉及的不同编程语言数量出现跃升，这让讨论从“智能体更快”推进到了“智能体可能会扩大低经验开发者愿意尝试的范围”。

![研究图表，展示采用 Claude 之后，每月涉及的不同编程语言数量出现上升](https://pbs.twimg.com/media/HRKR9_gX0AAa95H.png)

### 公开基准讨论也开始更具体地谈强模型究竟怎么失败
[@SnorkelAI](https://x.com/SnorkelAI) [报告](https://x.com/SnorkelAI/status/2095219425276273102) (3 个赞，64 次浏览)，在它们的 Terminal-Bench+ 评估中，Fable 5.1 在调试和游戏任务上超过了 Opus 5，而且每次成功运行消耗的 token 更少；但它同时强调，失败根因主要聚集在执行，而不是推理。这个表述之所以值得注意，是因为它和实践者在发布回复里的抱怨完全对上了：模型确实在进步，但剩下的失败模式越来越偏操作层。

## 7. 机会在哪里

**[+++] 面向长时智能体工作的验证与分诊层** —— 证据横跨 GitHub 发布 Fable 5.1 后的回复、SnorkelAI 对执行型失败的拆解、R. Seroter 的 Teamwork 验证截图，以及 kimburgaard 那个 123 条 PR 发现的折腾故事。这个机会很强，因为团队已经足够信任智能体，愿意让它们跑长任务，但还没有一套标准方法来做检查点、归类问题和证明任务收尾。

**[++] 在不改前端的前提下，替换成本、状态或检索层的即插即用基础设施** —— SOMA、Unsloth、Agentic API 和 zg 虽然切入点不同，但赌的是同一件事：用户想保留 Copilot、Claude Code、Codex 或 OpenCode，只替换底下昂贵或黑箱的那一层。这个机会中到强，因为这种模式同时出现在成本控制、自托管、有状态编排和搜索这几条线上。

**[+] 面向可移植技能、记忆和智能体插件的打包与分发** —— illyism 画出的注册表地图、obsidian-skills，以及 supermemory，都在说明同一个新表面：技能和插件现在需要跨大量宿主做发现、安装、兼容性判断和信任信号。这个机会是真实的，但相比验证层或基础设施层，也更拥挤、更竞争。

## 8. 要点总结

1. **Google 编程栈的叙事，已经硬化成了具体产品界面证据。** 这个故事从前一天对 3.7 Flash 的泛泛热情，推进到了 Gemini 3.5 从 picker 中消失、Gemini 3.8 Flash 正式上线，甚至连 Antigravity 工具里出现的 GLM 二进制引用都被拿出来审计。([thtbee_](https://x.com/thtbee_/status/2094818778593067502), [Google](https://x.com/Google/status/2095193922884468964), [mrfanduu](https://x.com/mrfanduu/status/2095076109696250059))
2. **Copilot 的价值主张在扩展，但围绕它的审查负担也在上升。** GitHub 用 Copilot 发布了 Claude Fable 5.1，用户也放出了 Fledgling Game 这种有野心的公开产物；但最有内容的回复，关注的却是数据保留、错误转向恢复，以及 PR 审查里的来回折腾，而不是模型 IQ 本身。([GitHub](https://x.com/github/status/2094936182945886329), [Burke Holland](https://x.com/burkeholland/status/2095159380513624201), [kimburgaard](https://x.com/kimburgaard/status/2095245983689154688))
3. **修复 AI 编程“糊感”的首选方案，如今是结构，而不是更多提示词。** Spec Kit、Obsidian 技能、supermemory 和注册表地图，都在指向同一种操作直觉：把工作流编码出来、打包起来，再让它能跨宿主迁移。([txbrraa](https://x.com/txbrraa/status/2095061557180825911), [RoundtableSpace](https://x.com/RoundtableSpace/status/2095085573706748156), [DhravyaShah](https://x.com/DhravyaShah/status/2094962042365222918), [illyism](https://x.com/illyism/status/2094925888991203395))
4. **构建者越来越多地是在熟悉智能体底下换基础设施，而不是把智能体本身换掉。** SOMA 在 Copilot 下面压缩上下文，Unsloth 在 Claude Code 和 Codex 背后换成本地模型，Agentic API 把编排挪到 vLLM 前面，zg 则把搜索工作压缩成排序更好的证据。([LisaFlorentina8](https://x.com/LisaFlorentina8/status/2095067702624940068), [starmexxx](https://x.com/starmexxx/status/2095072097466741027), [techNmak](https://x.com/techNmak/status/2095247529525047448), [QwenDevs](https://x.com/QwenDevs/status/2095157452904018263))
