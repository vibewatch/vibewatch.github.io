# Twitter AI 编程 - 2026-07-29

## 1. 大家都在讨论什么

### 1.1 成本、配额和供应商替换，取代了单纯的演示热议 🡕

Twitter 上关于 AI 编程最热烈的讨论，已经不再是哪个演示更炫，而是智能体的运行成本是否在下降、配额修复是否真的恢复了可用空间，以及大型团队究竟信任哪家供应商到愿意将其标准化。四条高信号内容共同支撑了这一主题：OpenAI 关于 Codex 自我优化的说法、Disney 据称从 Copilot 转向 Codex、Microsoft 更广泛的 Copilot 增长更新，以及一条围绕 Sol 使用限制、回复量很高的帖子。

[@OpenAIDevs](https://x.com/OpenAIDevs) [表示](https://x.com/OpenAIDevs/status/2082580211552457102)（881 个赞、53 条回复、44,085 次浏览、73 次收藏）表示，GPT-5.6 Sol 已在 Codex 内部用于优化 Codex 自身的基础设施和性能。被引用的 OpenAI 帖子补上了主帖里缺失的具体数字：生产环境中的 GPU 内核改进让服务成本下降 20%，推测解码让 token 生成效率提升 15% 以上。回复很快把这一基础设施层面的成果转成了用户价值问题：这些收益是否会体现为更低延迟、更少配额消耗，还是仅仅提升后端吞吐量。

[@wallstengine](https://x.com/wallstengine) [报道称](https://x.com/wallstengine/status/2082521298576757117)（60 个赞、6 条回复、17,167 次浏览）表示，Disney 计划于 8 月在美国停用 GitHub Copilot，采用 OpenAI Codex，同时保留 Claude Enterprise 和 Cursor，并移除 Amazon Kiro 和 Q。[Business Insider](https://www.businessinsider.com/disney-microsoft-github-copilot-openai-codex-ai-tools-claude-cursor-2026-7) 补充了一线使用层面的细节：Disney 的 8 名技术员工表示自己很少或从不使用 Copilot；一名产品经理称其输出“复杂得毫无必要”；一名工程师则表示，他们约 80% 的编程 AI 使用都发生在终端里的 Claude 上。帖子的回复对过度解读单一泄露信息持怀疑态度，但仍将其视为一项有意义的证据，说明企业团队正在积极重新测试供应商选择，而不是锁定在单一技术栈上。

[@wallstengine](https://x.com/wallstengine) [补充道](https://x.com/wallstengine/status/2082584264378548623)（60 个赞、13,654 次浏览）表示，Satya Nadella 称 Copilot 营收环比增速超过 60%，覆盖多数员工的企业级部署增长近 75%，GitHub 用户达到 2.25 亿，GitHub Copilot 达到 5,000 万。这反而让 Disney 的消息更值得关注：据报道，一家大型采购方正在转向别处，而 Microsoft 的整体 Copilot 采用率却仍在持续上升。

![OpenAI 的 Tibo Thsottiaux 表示 ChatGPT Work 和 Codex 限额已重置，GPT-5.6 Sol 的使用时长预计可延长约 18% 的截图](https://pbs.twimg.com/media/HOYYIP3aQAACAJ6.jpg)

**讨论洞察：** [@TimJayas](https://x.com/TimJayas) [描述为](https://x.com/TimJayas/status/2082386017139773651)（27 个赞、11 条回复、1,786 次浏览）将当天的 Codex 重置解读为使用额度提升了 18%，但回复中的怀疑多于庆祝：一名用户认为，这次调整只恢复了此前损失容量的一小部分；另一名用户讽刺道：“好耶，我们被限制得更厉害了”；还有人追问现在真正的周上限到底是多少。最明显的模式并不是对某一家模型供应商的盲目忠诚，而是对不透明配额算法的不信任。

**与前一日对比：** 7 月 28 日的 Copilot 讨论主要由模型可用性驱动，尤其是 Grok 4.5 进入 Copilot。到 7 月 29 日，Copilot 和 Codex 仍处于讨论中心，但重心已转向成本、限制和企业采购。

### 1.2 Google 的智能体栈继续从演示应用向外扩展 🡒

Google 和 Antigravity 仍然高度吸睛，但重点已从单纯的 UI 小技巧转向真实工作流和更宽的产品组合。三条延续关注的内容支撑了这一主题：一条关于 Antigravity 研究评估的讨论、Google 的 Farm Brain 部署案例，以及一份被大量收藏的 Google 免费 AI 工具栈盘点。

[@antigravity](https://x.com/antigravity) [显示](https://x.com/antigravity/status/2082534317633290284)（376 个赞、14 条回复、18,155 次浏览、125 次收藏）介绍了 Antigravity 如何用于研究评估分析：系统用自然语言分析表格、提出假设，并启动并行子智能体来定位失败模式。相比前一天“从画布生成 UI”的演示，这是一种更偏实际运营的产品主张：它试图用可复用的分析工作流，取代手动编写评估脚本和解析表格。最有代表性的回复来自一名付费用户，他希望支持手机到笔记本的任务接力以及 BYOK 模型，因为原生 Opus 选项目前仍停留在 4.6。

[@Google](https://x.com/Google) [显示](https://x.com/Google/status/2082217242066817281)（353 个赞、51 条回复、121,037 次浏览、94 次收藏）介绍了密歇根农民 Paul Windemuller 的“Farm Brain”：这是一个据称在 Antigravity 中使用 Gemini 3.6 Flash 构建的本地多智能体系统，用于自动化追踪农场日常经营表现。这让当天关于 Google 的讨论很难再被简单视为只是面向程序员的营销：回复集中讨论了，一个成本低到足以每天早晨运行的闭环，如何服务一个拥有 260 头奶牛的农场；以及基于过往数据训练的模型，在市场转差时是否仍能保持韧性。

[@AIHighlight](https://x.com/AIHighlight) [列出了](https://x.com/AIHighlight/status/2082493726010589211)（133 个赞、11 条回复、9,158 次浏览、111 次收藏）盘点了 14 款 Google AI 工具，覆盖设计、编程、文档、后端和内容任务，包括 Pomelli、Stitch、Opal、Gemini CLI、Code Wiki、Jules 和 Antigravity。该帖之所以受到关注，是因为它把 Google 的产品包装成一整套免费工具栈，而不是单一聊天机器人；[Pomelli 的 Google Labs 页面](https://labs.google.com/pomelli/about/) 证实，其中至少一款 headline 产品确实真实存在且已经上线。

**讨论洞察：** 反对意见是务实的，而非意识形态上的。Antigravity 用户希望支持手机与笔记本之间的任务接力，并获得更新模型的访问权限；免费工具栈的读者则在追问，像 Pomelli 这样的工具是否真的好用，以及“免费”是否只是把真正的限制藏在别处。**与前一天相比：** 7 月 28 日，Antigravity 演示和 Farm Brain 已经在传播。到了 7 月 29 日，这一叙事进一步扩展到研究运营和“免费技术栈”的分发，而围绕访问权限和模型选择的抱怨也仍在持续。

### 1.3 远程控制与智能体原生工作空间，从技巧走向产品 🡕

另一个清晰的趋势是，人们不再把远程控制和多智能体协同当作支线玩法，而是开始把它们做成一等产品。支撑这一主题的有两篇帖子：一篇对 Buzz 的长篇演示，以及 Theo 发布的 T3 Connect。

[@rileybrown](https://x.com/rileybrown) [详细介绍了](https://x.com/rileybrown/status/2082569013280796930)（146 个赞、12 条回复、12,645 次浏览、232 次收藏）将 Buzz 描述为一个免费的类 Slack 工作空间，在这里，智能体是“平等成员”，而不是附加功能；Codex 和 Claude Code 订阅可以接入共享频道。帖子塞进了大量具体工作流细节——接入 OpenCode 和 Cursor、移动应用、共享算力、自动化，以及“管理频道”的用例——而收藏数表明，读者更像是把它当作操作手册保存下来，而不只是对这个想法表示兴趣。

[@theo](https://x.com/theo) [发布了](https://x.com/theo/status/2082277789395501263)（319 个赞、31 条回复、29,820 次浏览、103 次收藏）将 T3 Connect 介绍为一个极简的开源隧道层，用于远程控制 T3 Code 实例，而无需先搭好 Tailscale。主帖承诺的是一个四步流程：安装你的编码工具、运行 `npx t3 connect`、登录，然后通过网页端、桌面端或即将推出的移动应用控制那台电脑；第一条回复则指向 [app.t3.codes](https://app.t3.codes/)，说明如何实现与账号绑定的控制。

**讨论洞察：** 最有价值的回复并不是一味叫好。在 Buzz 的演示帖下，一位用户问，这个产品如何防止两个智能体同时编辑同一组文件；另一位用户则提醒，大多数智能体演示一旦需要在多步之间保留真实上下文或记忆，就会崩掉。在 Theo 的帖子下，反复出现的反应则更直接：“终于不用再折腾 Tailscale 这条支线了”，紧接着就是对承诺中移动应用的催更。

**与前一天相比：** 7 月 27 日和 7 月 28 日已经出现了许多多会话、多智能体演示。到了 7 月 29 日，讨论又往下探了一层，进入控制平面本身：共享频道、远程隧道和设备切换。

### 1.4 技能、定制与可观测性成为封装层 🡕

当天还出现了异常具体的证据，表明新的差异化层正在模型外围形成：可复用技能、评审时上下文、支出遥测，以及打包好的 Copilot 配置。社区案例和 GitHub 官方界面都指向同一个方向。

[@RoundtableSpace](https://x.com/RoundtableSpace) [推广了](https://x.com/RoundtableSpace/status/2082409548053176756)（17 个赞、11 条回复、14,115 次浏览）将 Matt Pocock 的 `mattpocock/skills` 仓库展示为一套完整的 AI 编程工作流，包含 26 个可用于生产环境的技能。这张图之所以重要，是因为它展示了实际结构：既有 `to-spec`、`implement`、`code-review`、`diagnosing-bugs` 和 `wayfinder` 这样的工程技能，也有生产力和杂项层，全部都可通过 `npx skills@latest add mattpocock/skills` 安装。GitHub 的仓库 API 目前显示，[mattpocock/skills](https://github.com/mattpocock/skills) 有 194,783 个星标，而 README 也明确将这套包定位为一组小巧、可组合的技能，而不是一个庞大的流程框架。

**与前一天的对比：** 本周稍早，“技能”主要还出现在应用市场、使用技巧和缓存相关建议里。到了 7 月 29 日，这个概念开始沉淀为更持久的资产：大型公开技能仓库、GitHub 第一方代码审查支持、支出遥测，以及可复用的 Copilot 配置包。

## 2. 让人沮丧的是什么

### 计费计算不透明，以及对配额的不信任

严重程度：高。最一致的挫败感，并不在于模型抽象意义上“很贵”，而在于开发者往往要等到 token 已经烧掉之后，才知道一次真实会话到底花了多少钱。[@forgebitz](https://x.com/forgebitz) [一语概括](https://x.com/forgebitz/status/2082462311227281587)（72 个赞，19 条回复，2,057 次浏览）写道：“一旦你开始按 API 价格付费，你对 vibe coding 的看法就真的会变。”回复随即补充了切身经历：一名用户称自己收到了 599 欧元的 Gemini 账单；另一人说，API 定价是唯一能让人“看清楚”的方式；还有人描述了如何通过 Codex 插件手动把提示词路由到不同模型。

[@TimJayas](https://x.com/TimJayas) [庆祝了](https://x.com/TimJayas/status/2082386017139773651)（27 个赞，11 条回复，1,786 次浏览）提到 OpenAI 关于 Sol 使用时长大约延长 18% 的说法，但回复区更像是把那张截图视为一次修复信任的尝试，而不是一场胜利。一名用户表示，这次修复后 Sol 仍然不可能连续完整使用五个小时；另一人认为，用户不过是拿回了自己原本已经失去的一小部分；第三人则追问，隐藏的每周上限到底是多少。另有一条传播范围较小、但异常具体的帖子来自 [@notjazii](https://x.com/notjazii) [声称](https://x.com/notjazii/status/2082535319858290691)（6 个赞，4 条回复，202 次浏览），称同一个 K3 模型在 Kimi Code、Hermes 和 Claude Code 中处理一个中位数任务时，分别消耗了约 61k、67k 和 340k 个 token；这虽然只是一张截图，却呼应了当天更广泛的担忧：框架层的额外开销可能会压过模型本身的成本。

人们正在借助路由器、更便宜的模型和遥测插件来应对，而不是信任默认的计费方式。这值得投入，因为这种痛点是运营层面的、反复出现的，而且直接关系到购买行为：就在开发者争论配额的同一天，有报道称 Disney 正在用 Codex 替换 Copilot。

### 悄悄出错的输出，与无声失效的工作流

严重程度：高。从业者反复在同一处划出信任边界：AI 很有用，但前提是有人持续审查。[@NateSilver538](https://x.com/NateSilver538) [写道](https://x.com/NateSilver538/status/2082284425446867087)（229 个赞，21 条回复，33,994 次浏览）表示，在相关领域知识参与闭环时，AI 工具非常有帮助；但如果没有人类专家把关，它们很可能会生成“漏洞极多的模型”。他的回复给出的不是泛泛恐惧，而是具体失效模式——一名用户说 Claude 忘了基本上下文，还把图表文字弄乱了；另一人则描述了模拟工作流中出现的荒谬数学结果。

同样的抱怨也出现在技能层。[@RoundtableSpace](https://x.com/RoundtableSpace) [分享](https://x.com/RoundtableSpace/status/2082409548053176756) Matt Pocock 的技能包主题帖下，有人回复称，一套相似配置在 Flutter 代码库里表面运行正常，却因为这些技能默认项目结构是 Next.js 风格，而悄悄产出了错误结果。[@onderceylan](https://x.com/onderceylan) [构建了](https://x.com/onderceylan/status/2082557882491711629) 明确主张采用 SHIP，因为“编码代理越来越快”，而“软件质量正在失控”，其理由是：评审、测试和成本把关都没有跟上生成速度。

当下的应对之道，是增加更多护栏，而不是投入更多盲目信任：可复用规范、评审能力、QA 关卡、安全扫描和人工审批。之所以值得投入，是因为这类失败往往悄无声息：它们能通过命令行，却依然没有满足真正的需求。

### 远程连续性依然脆弱，因此足以催生新工具

严重程度：中等。围绕远程控制产品的回复表明，在代理式编程里，“随时随地工作”依然很脆弱。[@theo](https://x.com/theo) [推出了](https://x.com/theo/status/2082277789395501263)（319 个赞、31 条回复、29,820 次浏览、103 次收藏）专门推出 T3 Connect，就是为了消除 Tailscale 和公网 IP 配置的负担；而最热烈的反应，几乎只是松了一口气——这段支线折腾也许终于可以消失了。与此同时，帖子下一个问题就是“我怎么才能用上那个移动应用？”——这说明远程访问仍然不完整。

[@antigravity](https://x.com/antigravity) [展示](https://x.com/antigravity/status/2082534317633290284)（376 个赞、14 条回复、18,155 次浏览、125 次收藏）那篇 research-eval 分析下，一位付费用户的回复从另一个方向提出了同样缺失的能力：让用户能通过手机向运行在宿主笔记本上的代理发送任务，并且通过 BYOK 接入更新的模型。[@ryanvogel](https://x.com/ryanvogel) [将其描述为](https://x.com/ryanvogel/status/2082522122119680290)（2 个赞、1 条回复、927 次浏览、5 次收藏）则给出了一个基于 [Coast](https://coast.app) 和 Hark 的变通方案：从屏幕录像中重建他做过什么，并生成一个晨间总结站点。它之所以有用，恰恰是因为会话连续性仍然太容易丢失。

之所以值得为此构建产品，是因为人们已经在自己拼装各种局部修补方案——隧道、本地记忆工具、晨间摘要、手机任务交接——而不是直接从主流编程产品里获得端到端的连续性。

## 3. 人们希望存在什么

### 可预测的代理预算与 harness 级成本控制

这是当天最明确、最务实的需求。[@forgebitz](https://x.com/forgebitz) [认为](https://x.com/forgebitz/status/2082462311227281587)（72 个赞、19 条回复、2,057 次浏览）指出，API 定价会从根本上改变你对“vibe coding”的看法；而 [@TimJayas](https://x.com/TimJayas) [分享了](https://x.com/TimJayas/status/2082386017139773651)（27 个赞、11 条回复、1,786 次浏览）则晒出一张截图，显示 OpenAI 正试图安抚用户，称 Sol 现在大约能多撑 18%。这两条帖子读起来都不像满意，更像是在表达：人们想要一个控制平面，能在开始之前就告诉他们一项任务大概会花多少钱，以及何时是 harness 在白白浪费 token。

局部答案已经存在。[@tpschmidt_](https://x.com/tpschmidt_) [显示](https://x.com/tpschmidt_/status/2082361487281242606)（1 个赞、3 条回复、541 次浏览、4 次收藏）提到了 CloudWatch 支出跟踪；而在 [@forgebitz](https://x.com/forgebitz) [称](https://x.com/forgebitz/status/2082462311227281587)（72 个赞、19 条回复、2,057 次浏览）下面，有一条回复描述了一个按具体场景手动选模型的路由插件。机会：直接。尚未被满足的需求，是一个位于供应商和 harness 之上的预算与路由层，而不是另一个彼此孤立的定价仪表盘。

### 移动端交接、远程控制，以及可跨设备延续的记忆

这同样是直接需求，用户说得很明白。[@antigravity](https://x.com/antigravity) [展示](https://x.com/antigravity/status/2082534317633290284)（376 个赞、14 条回复、18,155 次浏览、125 次收藏）那篇 research-eval 分析下，一位付费用户表示，希望有一款移动应用，能把任务发给运行在宿主笔记本上的代理，并明确把这一差距拿来与 Cursor 和 Claude 对比。[@theo](https://x.com/theo) [显示](https://x.com/theo/status/2082277789395501263)（319 个赞、31 条回复、29,820 次浏览、103 次收藏）表明，T3 Connect 已经通过网页远程控制解决了部分问题，但第一个追问仍然是：移动应用怎么获得？

[@ryanvogel](https://x.com/ryanvogel) [显示](https://x.com/ryanvogel/status/2082522122119680290)（2 个赞、1 条回复、927 次浏览、5 次收藏）则展示了同一需求的另一面：使用 [Coast](https://coast.app) 记住屏幕录像中发生过什么，然后生成晨间回顾。机会：直接。人们想要的不只是一个远程终端，而是能在手机、笔记本电脑和昨天的工作之间保持连续性。

### 能理解本地技术栈的可复用团队技能

当天对技能的热情，本身也带着一个内置警告。[@RoundtableSpace](https://x.com/RoundtableSpace) [放大了这一点](https://x.com/RoundtableSpace/status/2082409548053176756)（17 个赞、11 条回复、14,115 次浏览）提到 Matt Pocock 的 26 项技能仓库；[@GHchangelog](https://x.com/GHchangelog) [确认了这一点](https://x.com/GHchangelog/status/2082590761132949812)（5 个赞、440 次浏览）则提到 GitHub 现已把审查时技能和 MCP 上下文作为第一方功能支持。不过，Matt Pocock 那条帖子下最有价值的一则回复指出，类似技能在一个 Flutter 代码库里曾悄然失灵，因为它默认项目是基于 Next.js 的。

[@DanKornas](https://x.com/DanKornas) [构建了框架](https://x.com/DanKornas/status/2082448849902137432)（4 个赞、2 条回复、912 次浏览）也从 Copilot 的角度指出了同样的问题：团队想要的是可复用的指令、提示词、聊天模式、钩子和工作流，而不是每次都从零重建配置。机会点在于：竞争激烈。虽然已有部分解决方案，但真正缺少的是一层可移植的技能/配置层，能够在开始执行前先检查自身假设是否与仓库相符。

## 7. 机会所在

**[+++] Cost-control plane for agentic coding** — Evidence showed up everywhere: [@forgebitz](https://x.com/forgebitz) [表示](https://x.com/forgebitz/status/2082462311227281587)（72 个赞、19 条回复、2,057 次浏览）称，API 定价改变了整个 vibe-coding 的计算方式；[@TimJayas](https://x.com/TimJayas) [流传](https://x.com/TimJayas/status/2082386017139773651)（27 个赞、11 条回复、1,786 次浏览）向持怀疑态度的受众展示了 OpenAI“使用时长增加 18%”的截图；[@tpschmidt_](https://x.com/tpschmidt_) [显示](https://x.com/tpschmidt_/status/2082361487281242606)（1 个赞、3 条回复、541 次浏览、4 次收藏）则展示了 CloudWatch 支出遥测。以及 [@wallstengine](https://x.com/wallstengine) [报道称](https://x.com/wallstengine/status/2082521298576757117)（60 个赞、6 条回复、17,167 次浏览）中提到的 Disney 转向 Codex。一个很强的机会点，是构建与供应商无关的中间层：在会话开始前预测成本、路由工作，并暴露浪费。

**[+++] 模型之上的审查与治理机制**——Nate Silver 对错误输出的警告、Matt Pocock 技能讨论串里 Flutter 与 Next.js 的不匹配、SHIP 对质量闸门的主张，以及 Codex Security 的扫描与修复工作流，都指向同一个缺口。市场正在奖励那些围绕现有模型增加审查、验证、安全性和可审计性的系统，而不是试图取代这些模型。

**[++] 远程、移动与记忆连续性**——Buzz、T3 Connect、Antigravity 的移动端接续请求，以及 Coast 的本地记忆回顾工作流，都指向一个现实缺口：从“代理只成功运行过一次”到“代理成为我日常的一部分”之间，仍有明显距离。一个耐用的跨设备控制平面，如果其记忆能在休眠、出行和关闭标签页后继续保留，显然存在需求，而目前的解决方案还不完整。

**[+] 具备技术栈感知能力的可移植技能包**——可复用技能和 Copilot 自定义功能显然已经获得采用，但数据集中最尖锐的一条回复指出：当技能对框架的假设有误时，同样的技能可能会悄无声息地失效。这使得兼容性检查、代码仓库分析和假设验证成为一个正在浮现、但真实存在的产品方向。

## 8. 要点

1. **成本已经成为面向用户的功能，而不只是后端基础设施。** [@OpenAIDevs](https://x.com/OpenAIDevs) [表示](https://x.com/OpenAIDevs/status/2082580211552457102)（881 个赞、53 条回复、44,085 次浏览、73 次收藏）称 Codex 变得更便宜、更高效，但回复中仍有人追问，用户是否真的能在配额或延迟上感受到这种节省。
2. **即便在大规模场景中，企业级 AI 编程技术栈仍处于流动变化之中。** [Business Insider](https://www.businessinsider.com/disney-microsoft-github-copilot-openai-codex-ai-tools-claude-cursor-2026-7) 报道了 Disney 从 Copilot 转向 Codex，而 [@wallstengine](https://x.com/wallstengine) [报道称](https://x.com/wallstengine/status/2082584264378548623)（60 个赞、13,654 次浏览）则称 Copilot 的用户数仍已达到 5,000 万。
3. **Google 的代理叙事正从炫目的演示，扩展到工作流与运营层面的故事。** [@antigravity](https://x.com/antigravity) [显示](https://x.com/antigravity/status/2082534317633290284)（376 个赞、14 条回复、18,155 次浏览、125 次收藏）展示了一套研究评估工作流，而 [@Google](https://x.com/Google) [显示](https://x.com/Google/status/2082217242066817281)（353 个赞、51 条回复、121,037 次浏览、94 次收藏）则将 Farm Brain 呈现为一个日常运营闭环。
4.**真正的产品之争正转向 harness 层。** [@theo](https://x.com/theo) [推出](https://x.com/theo/status/2082277789395501263)（319 个赞、31 条回复、29,820 次浏览、103 次收藏）T3 Code 的远程控制功能，以及 [@RoundtableSpace](https://x.com/RoundtableSpace) [分享](https://x.com/RoundtableSpace/status/2082409548053176756)（17 个赞、11 条回复、14,115 次浏览）一个可复用的技能仓库，包含 26 个智能体工作流。
5. **人工审核仍然是最难跨越的信任边界。** [@NateSilver538](https://x.com/NateSilver538) [写道](https://x.com/NateSilver538/status/2082284425446867087)（229 个赞、21 条回复、33,994 次浏览、23 次收藏）认为，只有在领域专家参与把关时，AI 工具才有帮助；否则就会产出“漏洞百出的模型”。
