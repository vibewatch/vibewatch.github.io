# HackerNews AI - 2026-08-26

## 1. 大家在讨论什么

8 月 26 日的内容量与 8 月 25 日几乎持平——前者有 91 位作者发布 92 篇内容，后者则是 90 位作者发布 93 篇——但讨论参与度更高，热度也不再过度集中。总得分从 468 分升至 611 分，评论数从 275 条增至 382 条，而排名前三的讨论串占全天总得分的比例则从约一半降至 29%。与 8 月 25 日偏重构建者工作流层的讨论相比，8 月 26 日更多地同时追问两个更棘手的问题：Web 应在多大程度上适配智能体，以及当前模型在编程、浏览和现实工作中究竟赢得了多少信任。

### 1.1 Web 与智能体之间的接口之争更加明确，也更具争议（🡕）

当天最明确的一组高价值帖子，讨论的是如何让网站和在线系统变成智能体可用的形态，而不必暴力处理原始 HTML、依赖脆弱的 UI 自动化，或使用临时拼凑的商家逻辑。同样值得注意的是，回复显示大家仍未就这种适配应由网站端、执行框架端，还是两者之间的某一层负责达成共识。

[sreenathmenon](https://news.ycombinator.com/user?id=sreenathmenon) 发布了 [WebMCP：教你的网站与 AI 智能体对话](https://news.ycombinator.com/item?id=49450417)（55 分，55 条评论）。链接中的[文章](https://sreenathmenon.com/blog/2026-08-04-webmcp-teaching-websites-to-talk-to-ai-agents/)介绍了一种浏览器端标准：页面通过 JSON Schema 注册结构化工具和共享状态，使智能体可以在已登录的标签页中直接调用 `book_table`，而不必根据 DOM 猜测操作。[tilt](https://news.ycombinator.com/user?id=tilt) 发布了[通过 Accept 请求头向 AI 智能体提供 Markdown](https://news.ycombinator.com/item?id=49454764)（54 分，19 条评论）；链接中的[网站](https://acceptmarkdown.com/)以更轻量的方式提出了同一主张：通过 `Accept: text/markdown`，在同一 URL 上提供 Markdown 表示，让智能体把 token 用在内容上，而不是浪费在布局、脚本和导航栏等界面框架上。

同样的思路也扩展到了其他场景。[Lui371](https://news.ycombinator.com/user?id=Lui371) 发布了 [Show HN：Shelf Protocol——面向电商的 Robots.txt](https://news.ycombinator.com/item?id=49449679)（3 分，0 条评论）；链接中的[仓库](https://github.com/Signal-All/shelfprotocol)介绍了 `shelf.json` 声明、DNS 验证和 `can_buy()` 门控机制，用来告诉智能体商家是否真实，以及它获准自主支出多少。[Radek-B3](https://news.ycombinator.com/user?id=Radek-B3) 发布了[为什么 AI 智能体需要持久化浏览器身份](https://news.ycombinator.com/item?id=49454780)（6 分，0 条评论）；链接中的[文章](https://github.com/Radek-B3/browser3/blob/main/WHY_AI_AGENTS_NEED_PERSISTENT_BROWSER_IDENTITIES.md)认为，即使智能体能够浏览网页，也仍需要一个在重启后保持稳定且内部一致的浏览器配置，而不是每次会话都重新生成随机身份。

**讨论洞见：** 回复从不同角度对两种方案提出了质疑。在 WebMCP 讨论串中，[mg](https://news.ycombinator.com/user?id=mg)（得分 0）追问，为什么不能让一个简单表单同时服务人类和 AI；[stillpointlab](https://news.ycombinator.com/user?id=stillpointlab)（得分 0）则表示，相比从零构建的新系统，WebMCP 似乎更适合拥有旧式 UI 流程的现有 SaaS。在 Markdown 讨论串中，[joshum97](https://news.ycombinator.com/user?id=joshum97)（得分 0）认为执行框架本就应该把 HTML 转换成可读形式；[lekevicius](https://news.ycombinator.com/user?id=lekevicius)（得分 0）则表示，在主流聊天机器人真正发送该请求头之前，采用率并无意义。

**与前一天相比：** 8 月 25 日已经出现 Keenable 和 only-cli 等面向智能体的信息检索产品。8 月 26 日延续了同一思路，但更偏向协议，也引发了更多争论：讨论从狭义工具转向浏览器标准、内容协商、商家注册表和持久化身份。

### 1.2 开发者想要的是对编程智能体的更多控制，而不只是更多智能体行为（🡕）

编程工具方面最强烈的信号，并不是大家期待更多自主循环，而是反复要求工具更专注、更简洁、更可观测。相比把又一层判断权交给冗长的执行框架，人们似乎更在意保住高效的快速路径。

[akras14](https://news.ycombinator.com/user?id=akras14) 发布了[我怀念旧版 Claude Code](https://news.ycombinator.com/item?id=49444863)（36 分，21 条评论）。链接中的[文章](https://alexkras.com/focus-is-the-main-feature-why-i-miss-the-old-claude-code/)称，旧版产品给人的感觉是“像我自己一样 grep 仓库”，而新版则因模型话太多、工具范围不断扩张，以及围绕编辑操作增加了更多 AI 原生流程而显得臃肿。回复让这种抱怨变得更具体：[gorayobi](https://news.ycombinator.com/user?id=gorayobi)（得分 0）表示，该工具现在会先读取整个代码库并执行一大堆检查，然后才开始写代码；[Dathuil](https://news.ycombinator.com/user?id=Dathuil)（得分 0）则称，新模型还没做完前期准备，旧模型就已经开始编程了。

另外两个 Ask HN 讨论串从不同角度补充了同一种挫败感。[jawuilp](https://news.ycombinator.com/user?id=jawuilp) 发布了 [Ask HN：你还在使用 AI 代码自动补全吗？](https://news.ycombinator.com/item?id=49449290)（4 分，9 条评论）。其中，[hollowturtle](https://news.ycombinator.com/user?id=hollowturtle)（得分 0）表示，编程智能体出现后，Cursor 的自动补全变得过于主动；[jMyles](https://news.ycombinator.com/user?id=jMyles)（得分 0）则认为，理想形态应该是自动补全与持续运行的智能体上下文相结合，而不是在两者之间二选一。[JacobWolf](https://news.ycombinator.com/user?id=JacobWolf) 发布了 [Ask HN：为什么 Claude 模型如此啰嗦？](https://news.ycombinator.com/item?id=49444272)（4 分，8 条评论）；该讨论既有对多余注释和无视指令的直接抱怨，也包含一些有价值的补充：[alwillis](https://news.ycombinator.com/user?id=alwillis)（得分 0）提到了 Claude Code 的 Concise 模式，[thingstohappy](https://news.ycombinator.com/user?id=thingstohappy)（得分 0）则表示，执行框架的影响可能与基础模型同样大。

构建者的应对方式，是精简或审计模型外围的层。[rryoung98](https://news.ycombinator.com/user?id=rryoung98) 发布了 [Show HN：Declaude](https://news.ycombinator.com/item?id=49443296)（7 分，2 条评论）；链接中的[服务](https://speak-english.tenken.co/)通过 Claude Code 插件、MCP 服务器和文档流水线，将 Claude 式套话改写成直白英语，使用的是运行在团队自有 GPU 上的 Qwen2.5-14B。[actualis](https://news.ycombinator.com/user?id=actualis) 发布了 [Actualis——看看编程智能体在你的机器上做了什么](https://news.ycombinator.com/item?id=49453056)（3 分，1 条评论）；链接中的[仓库](https://github.com/digital-foundry/actualis)会在本地读取 Claude Code 和 Codex 的会话记录，事后呈现执行过的命令、被拒绝的调用、暴露的凭据及开支。

**讨论洞见：** 重要之处在于，人们并不是简单地反对 Claude 或反对智能体。他们在区分模型行为与执行框架行为，希望默认循环更克制；当主产品本身无法保持专注时，他们就构建后处理器或审计工具加以补救。

**与前一天相比：** 8 月 25 日的工作流层讨论聚焦记忆、路由和并行会话监管。8 月 26 日延续了这一关注，但转向内部：抱怨从“帮我管理更多智能体”变成了“别让智能体在帮我之前先做那么多事”。

### 1.3 模型质量呈现出明显的领域依赖性，而非全面“变好”（🡕）

另一项主导讨论并不是模型到底有没有用，而是它们在哪些地方仍然脆弱。最有价值的证据来自人们指出现实任务中的具体失败模式，再将这些脆弱之处与某些模型仍能在偏好测试中胜出的狭义任务进行对比。

[davidest](https://news.ycombinator.com/user?id=davidest) 发布了 [Ask HN：LLM 连哪一件简单的事都做得离谱地差？](https://news.ycombinator.com/item?id=49443820)（32 分，82 条评论）。最有力的回复都很具体：[jampa](https://news.ycombinator.com/user?id=jampa)（得分 0）表示，没有模型能生成合理的建筑平面图；[ghostpepper](https://news.ycombinator.com/user?id=ghostpepper)（得分 0）称，模型生成的关键词搜索查询依旧令人尴尬；[mojuba](https://news.ycombinator.com/user?id=mojuba)（得分 0）认为模型不擅长为自己设计提示词；[busyant](https://news.ycombinator.com/user?id=busyant)（得分 0）则描述了上传图片后反复出现的鸟类物种幻觉。[michaefe](https://news.ycombinator.com/user?id=michaefe) 的 [SurveyorBench](https://news.ycombinator.com/item?id=49451896)（6 分，0 条评论）提供了更有力的外部证据：链接中的[文章](https://buntinglabs.com/blog/surveyorbench-ai-cant-generate-cad-from-land-surveys)称，即使是最强模型，在高难度测绘任务上的通过率也只有 0-4%，尽管它们偶尔能在中等难度样例中获得满分。

同一种弱点在交互场景中也有所体现。[jiggle123](https://news.ycombinator.com/user?id=jiggle123) 发布了[前沿推理智能体无法通过交互式 2D 迷宫](https://news.ycombinator.com/item?id=49449349)（12 分，2 条评论）。链接中的[网站](https://multinet.ai/)表示，该基准通过可控的迷宫环境测试长程行动、因果推理、规划、错误恢复和视觉关联能力，这与答好一道静态问题截然不同。与此同时，[pasharayan](https://news.ycombinator.com/user?id=pasharayan) 发布了[分析学生对大学申请文书辅助 AI 模型的投票](https://news.ycombinator.com/item?id=49443871)（43 分，83 条评论）；链接中的 [StudyArena 分析](https://studyarena.com/blog/chatgpt-vs-claude-vs-gemini-college-essays-2026)称，在 6,851 次学生盲投中，Gemini 以 39.6% 的支持率领先 Claude 的 31.8% 和 OpenAI 的 29.2%，但也指出，被选中的答案平均长 37%，而提高推理设置并未提升入选率。

**讨论洞见：** 贯穿始终的主题是校准，而非崩塌。HN 并不是说前沿模型一无是处，而是认为，模型在文章写作或偏好测试中的胜出，并不能抹去其在空间布局、关键词搜索、提示词设计、CAD 重建或交互式导航方面的脆弱表现；即使答案“更好”，也可能只是更长或更精致。

**与前一天相比：** 8 月 25 日更关注本地算力、信任边界和智能体脚手架。8 月 26 日则把讨论重新拉回评估：哪些任务真正取决于模型，哪些取决于执行框架，哪些仍需要专用系统。

### 1.4 AI 周边规模较小的治理与清理市场持续浮现（🡒）

这并非当天最大的主题，但出现得足够频繁，不容忽视。随着 AI 进入生产工作流，HN 持续涌现出一类企业：它们的主要工作，是为模型周围的混乱提供保险、内容审核、人工复核或标记服务。

[AlexRisio](https://news.ycombinator.com/user?id=AlexRisio) 发布了 [Launch HN：Risklytics（YC S26）——面向前沿科技公司的保险经纪服务](https://news.ycombinator.com/item?id=49451495)（24 分，17 条评论）。发布说明称，前沿科技公司可能仅仅因为使用 AI 或 CAD 就被拒保或错误归类；ISO 已于 1 月发布 AI 除外条款；Risklytics 则构建了六步投保流程和保险公司知识库，让创始人知道哪些保险公司真正愿意承保其设备。[smb06](https://news.ycombinator.com/user?id=smb06) 发布了 [CodeRabbit 承诺未来 12 个月向开源项目投入 $10M+](https://news.ycombinator.com/item?id=49450921)（10 分，4 条评论）；链接中的[博客文章](https://www.coderabbit.ai/blog/coderabbit-expands-its-commitment-to-open-source)称，维护者如今需要投入精力审查 AI 生成的变更，并强调这项新支持按实际直接成本计算，而不是赠送额度；[CodingJeebus](https://news.ycombinator.com/user?id=CodingJeebus)（得分 0）随即质疑其中到底有多少价值会真正以现金形式落地。

内容溯源也成为焦点。[sbulaev](https://news.ycombinator.com/user?id=sbulaev) 发布了[Microsoft Paint 和 Photos 为 AI 生成内容添加不可见水印](https://news.ycombinator.com/item?id=49449471)（4 分，1 条评论）；链接中的[报道](https://www.tomshardware.com/tech-industry/artificial-intelligence/microsoft-paint-and-photos-apps-add-invisible-watermark-to-ai-generated-content-developer-reverse-engineers-guid-embedding)称，Paint 会嵌入隐藏的 GUID 水印及 C2PA 凭证，如果该步骤失败，生成过程就会中止。就连 [jofo_s](https://news.ycombinator.com/user?id=jofo_s) 的 [Show HN：Tabu——用于露骨内容审核的 NSFW 图片与视频 API](https://news.ycombinator.com/item?id=49450127)（4 分，0 条评论）也符合这一趋势：链接中的[网站](https://tabushield.com/)提供快速分类、人工复核和透明度报告，因为应用商店与监管要求已经对模型输出形成约束。

**讨论洞见：** 共同主题并不是抽象的“AI 伦理”，而是运营中介服务：一旦 AI 进入真实工作流，总得有人消化保险公司的困惑、维护者的审核负担、内容审核职责或溯源规则。

**与前一天相比：** 8 月 25 日将信任视为运行时和沙箱问题。8 月 26 日延续了这一关注，但信任问题更多通过保险公司、审查平台、水印和内容审核产品来解决。

## 2. 大家在为什么感到沮丧

### 一些用户希望编程智能体更克制时，它们却变得更庞杂、更啰嗦

[akras14](https://news.ycombinator.com/user?id=akras14) 的[我怀念旧版 Claude Code](https://news.ycombinator.com/item?id=49444863)（36 分，21 条评论）最清楚地表达了这种挫败感：真正有价值的是快速、专注地探索和编辑仓库，令人烦恼的则是如今围绕它增加的上下文收集和额外流程。[gorayobi](https://news.ycombinator.com/user?id=gorayobi)（得分 0）表示，该工具现在会先读取整个代码库并执行大量检查，然后才开始编写代码；[hollowturtle](https://news.ycombinator.com/user?id=hollowturtle)（得分 0）称，编程智能体出现后，自动补全反而没那么好用了；[JacobWolf](https://news.ycombinator.com/user?id=JacobWolf) 的[冗长问题讨论串](https://news.ycombinator.com/item?id=49444272)（4 分，8 条评论）还补充了一项抱怨：Claude 模型会无视指令，并在代码中添加过多注释。主要应对方式包括把任务拆成更小单元、切换输出风格，或添加 [Show HN：Declaude](https://news.ycombinator.com/item?id=49443296)（7 分，2 条评论）之类的工具，在事后精简文字。严重程度：高。是否值得为此开发产品：是，直接机会。

### 没人能就“网站适配智能体”还是“智能体适配 Web”达成一致

[sreenathmenon](https://news.ycombinator.com/user?id=sreenathmenon) 的 [WebMCP 帖子](https://news.ycombinator.com/item?id=49450417)（55 分，55 条评论）、[tilt](https://news.ycombinator.com/user?id=tilt) 的 [Accept 请求头帖子](https://news.ycombinator.com/item?id=49454764)（54 分，19 条评论），以及 [Lui371](https://news.ycombinator.com/user?id=Lui371) 的 [Shelf Protocol 发布帖](https://news.ycombinator.com/item?id=49449679)（3 分，0 条评论），都认为当前智能体访问方式过于脆弱、消耗太多 token，或缺乏可信度。但回复也立即体现了相反的挫败感：[mg](https://news.ycombinator.com/user?id=mg)（得分 0）追问为什么表单还不够；[joshum97](https://news.ycombinator.com/user?id=joshum97)（得分 0）认为执行框架本就应该把 HTML 转成可读形式；[lekevicius](https://news.ycombinator.com/user?id=lekevicius)（得分 0）则表示，在主流聊天机器人参与之前，采用率毫无意义。痛点确实存在，但究竟应由哪一层解决仍有争议。严重程度：中高。是否值得为此开发产品：是，直接但竞争激烈。

### 现实任务仍会暴露令人难堪的失败模式

[davidest](https://news.ycombinator.com/user?id=davidest) 的 [Ask HN 讨论串](https://news.ycombinator.com/item?id=49443820)（32 分，82 条评论）就像一本细小却顽固的错误目录：平面图、关键词查询、提示词设计、鸟类物种识别和幻觉控制。[michaefe](https://news.ycombinator.com/user?id=michaefe) 的 [SurveyorBench](https://news.ycombinator.com/item?id=49451896)（6 分，0 条评论）将同样的感受转化为基准测试，称即使是最强模型，在高难度测绘任务上的通过率也仍处于 0-4% 区间。[jiggle123](https://news.ycombinator.com/user?id=jiggle123) 的[迷宫基准帖子](https://news.ycombinator.com/item?id=49449349)（12 分，2 条评论）将同样的担忧延伸到长程行动和错误恢复；[pasharayan](https://news.ycombinator.com/user?id=pasharayan) 的 [StudyArena 帖子](https://news.ycombinator.com/item?id=49443871)（43 分，83 条评论）则表明，即使模型在文章写作上胜出，也可能部分源于篇幅和呈现方式，而不只是推理质量。应对策略是专业化：更聚焦的基准、垂直模型和更多人工复核。严重程度：高。是否值得为此开发产品：是，直接机会。

### 现实中的 AI 应用开始附带保险、审查、审核和溯源负担

## 4. 正在使用的工具与方法

| 工具 | 类别 | 评价 | 优势 | 局限 |
|---|---|---|---|---|
| WebMCP | 浏览器接口标准 | (+/-) | 在已登录标签页中通过 Schema 声明结构化工具，无需迫使智能体猜测 DOM | 仍处于早期草案阶段，且不断有人质疑表单或 API 是否已经足以解决问题 |
| `Accept: text/markdown` | 发布 / 内容协商 | (+/-) | 减少 token 消耗、去除布局噪声，同时沿用同一权威 URL | 目前鲜有主流智能体采用，而且需要网站提供支持 |
| Claude Code | 编程智能体 | (+/-) | 生产力足以让它继续成为日常主力工具，并催生周边产品 | 用户抱怨前期准备过多、过度读取仓库，以及输出冗长或过度设计 |
| Cursor Tab / Copilot 式自动补全 | 编辑器辅助 | (+/-) | 当程序员已经知道下一步时，可提供快速、低摩擦的补全 | 一些用户认为智能体模式令其过于主动，或彻底取代了它 |
| Declaude | 输出规范化工具 / MCP | (+) | 通过插件、MCP 和文档流程将套话改写得更直白，而且无需使用商业服务商 | 增加了另一层，只能修正表达，无法改变底层任务行为 |
| Browser3 | 浏览器运行时 / 配置持久化 | (+) | 为智能体提供跨重启保持稳定、一致且相互隔离的身份配置 | 受限于 Windows 和 GPU，并明确不声称能绕过所有限制 |
| SurveyorBench | 垂直评测 / CAD 基准 | (+) | 以精确输出来衡量真实测绘工作，并揭示聊天基准遗漏的失败模式 | 领域狭窄，而且其记录的高难度任务通过率仍然极低 |
| CodeRabbit | 审查 / 维护者工具 | (+/-) | 尝试通过免费的公开仓库审查和安全检查，消化 AI 生成内容带来的审查负担 | 维护者仍质疑激励机制，以及支持中有多少是现金、多少只是产品使用权 |
| Risklytics | AI 运营 / 保险服务 | (+) | 将保险公司知识、除外条款和拒保理由转化为可用的投保流程 | 类别尚处早期，涉及执照、承保公司和措辞等复杂问题 |
| Shelf Protocol | 电商智能体注册表 | (+/-) | 为智能体提供统一查询入口，用于验证、权限和支出限额 | 需要商家和智能体构建者双方采用，才能发挥作用 |
| Actualis | 会话记录审计 / CLI | (+) | 在本地读取 Claude Code 和 Codex 日志，呈现命令、成本、被拒操作和暴露风险 | 只能分析已记录的内容，目前支持的智能体数量有限 |

只要工具能够缩小工作范围或恢复可观测性，整体满意度就会提高。WebMCP、Markdown 协商、Shelf Protocol 和 Browser3 都试图让智能体输入或会话更加明确，而 Declaude 与 Actualis 则负责清理或审查智能体已经生成的内容。通用编程层的评价最为复杂，因为人们依然重视它，却越来越希望配套更多控制手段。

常见的变通方式不是简单升级模型，而是在模型周围增加结构。用户会切换输出模式，在短流程中偏好自动补全，对冗长文本做后处理，通过盲测比较写作结果，或在浏览和电商操作之前加入注册表与协商层。主要迁移趋势是从一个包办一切的助手，转向一组支持工具构成的技术栈，用来约束输入、精简输出，或解释运行结束后究竟发生了什么。竞争压力最强的两个领域分别是：浏览器标准与执行框架端适配之间的竞争，以及编程智能体厂商与其上方日益增多的轻量控制层之间的竞争。

## 7. 机会在哪里

**[+++] 为编程智能体保住专注度的控制层** - Claude Code 抱怨帖、自动补全讨论、冗长问题讨论、Declaude 和 Actualis 都指向同一缺口：用户希望智能体保持简洁、遵守范围、保住快速路径，并留下清晰可读的操作记录。

**[+++] 以人类 Web 为权威内容源的智能体原生接口** - WebMCP、Markdown 协商、Shelf Protocol 和持久化浏览器身份从不同方向解决同一问题：智能体用户需要摩擦更小的契约和可信状态，但团队不想把整个产品分叉成独立的 AI 专用界面。

**[++] 面向现实工作的垂直基准与受约束副驾** - 平面图、测绘、交互式迷宫和文章盲测表明，模型质量依然高度取决于任务。市场仍有空间容纳将领域专用评测、更聚焦的交互模型和可由人类清晰验证的输出结合起来的产品。

**[++] AI 运营与合规中间件** - Risklytics、CodeRabbit、Microsoft 的水印方案和 Tabu 都反映了同一商业现实：一旦 AI 进入生产环境，企业就需要围绕它配置保险、审查分流、内容溯源、内容审核和政策基础设施。

## 8. 要点总结

1. **信息流仍然广泛，但讨论开始转向自身。** 8 月 26 日的内容量与前一天相当；与此同时，HN 用户也在当天最热门的讨论串之一中衡量 HN 自身有多少内容已经与 AI 有关。([来源](https://news.ycombinator.com/item?id=49449648))
2. **Web 与智能体之间的接口问题正从临时方案走向契约，但尚未走向共识。** WebMCP、Markdown 协商、商家注册表和浏览器身份工具都获得了关注，但评论区对于适配工作究竟应由网站还是执行框架负责，依然意见分裂。([来源](https://news.ycombinator.com/item?id=49450417)、[来源](https://news.ycombinator.com/item?id=49454764)、[来源](https://news.ycombinator.com/item?id=49449679)、[来源](https://news.ycombinator.com/item?id=49454780))
3. **开发者要求的是对编程智能体拥有更多控制，而不只是赋予它们更多自主权。** 当天最主要的编程讨论聚焦臃肿、冗长、自动补全退化、直白英语后处理和会话记录审计，而不是更彻底地把循环交给智能体。([来源](https://news.ycombinator.com/item?id=49444863)、[来源](https://news.ycombinator.com/item?id=49449290)、[来源](https://news.ycombinator.com/item?id=49444272)、[来源](https://news.ycombinator.com/item?id=49443296)、[来源](https://news.ycombinator.com/item?id=49453056))
4. **模型质量依然明显取决于任务。** HN 一方面展示了某一模型家族在写作盲测中的强劲表现，另一方面也反复证明，模型在平面图、测绘、提示词设计、关键词搜索、鸟类识别和交互式导航方面仍然脆弱。([来源](https://news.ycombinator.com/item?id=49443871)、[来源](https://news.ycombinator.com/item?id=49443820)、[来源](https://news.ycombinator.com/item?id=49451896)、[来源](https://news.ycombinator.com/item?id=49449349))
5. **AI 工作流周边正在形成真正的商业边界。** 保险、维护者审查分流、内容溯源和审核都成为了产品机会，因为围绕 AI 的行政负担正变得与模型本身同样重要。([来源](https://news.ycombinator.com/item?id=49451495)、[来源](https://news.ycombinator.com/item?id=49450921)、[来源](https://news.ycombinator.com/item?id=49449471)、[来源](https://news.ycombinator.com/item?id=49450127))
